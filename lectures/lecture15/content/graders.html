先看结论

  • 评分器（grader）是判定 agent 交出的结果对不对的那段逻辑。agent 指能自己调用工具、分很多步去完成一个任务的语言模型系统。一种很常用的评分器是代码：把期望的行为写成确定的检查，也就是同样的输入每次都得到同样判定的检查，比如单元测试。
  • 很多 agent 任务没有唯一确定的答案。有多个正确答案、要看过程、要看质量、要给部分分的时候，预先写好的代码检查可能覆盖不到。
  • 评分器会判错，而且两个方向都有：把做对的判成错的，分数偏低；把做错的判成对的，分数偏高。
  • 评分器有三种：代码、人、语言模型。代码便宜、快、结果确定，但只能检查写进去的东西。人的判断最接近真实，但又贵又慢，评分的人意见可能不一，结果也难以重跑。语言模型评审能大批量地跑，也能做细致的判断，但结果不确定、有偏差，还需要校准。校准指拿它的判定和人的判定对照，让两者保持一致。
  • 实际的评估有时把几种组合起来用：能用代码的地方用代码，必须判断的地方用语言模型，人用在抽查和校准上。

这一讲主要看「验证」这一块

第 13 讲讲过，一个 agent 基准测试（benchmark，一组题目加一个报告成绩的办法）的任务定义有三样：问题描述、环境、验证。环境是 agent 执行任务的地方，里面有它能读写的东西，比如代码仓库、数据库和文件。验证判定 agent 交出的结果算不算通过。这一讲的前五个部分把这第三样放大来看。

做验证的那段逻辑叫评分器。Anthropic 2026 年 1 月的文章《Demystifying evals for AI agents》给的定义是：评分器是给 agent 某一方面的表现打分的逻辑。这里的打分包括判定通过或不通过，也包括给出一个分数。一个任务可以有多个评分器，每个评分器里可以有多条检查。出处：Anthropic，2026。

这一页有三个相近的词。验证是任务定义里的一步，评分器是做这一步的逻辑，评审专指用语言模型做的评分器。

{{fig 5 | 任务定义的三样从左到右排成一行。agent 读问题描述，在环境里工作，交出结果，最后由验证判定通过或不通过。绿框圈出的验证是这一讲主要讲的一块。框里列了三类验证办法：单元测试或端到端测试、评分标准（Rubrics）、偏好（Preference）。}}

图里的三类验证办法是这样的。单元测试检查程序的一小部分，端到端测试把整个系统从头到尾跑一遍，检查最后的结果。评分标准是一份写明什么样的表现得几分的说明。偏好指把两个结果摆在一起，让人或模型选出更好的一个，后面讲到这种做法时叫它两两比较。

这三类办法和这一页要讲的三种评分器大致这样对应：测试由代码来跑，评分标准和偏好由人或语言模型来判。

这一讲有七个部分。总览页给每个部分各列了一个问题，这一页把前六个部分的内容归成下面四个问题。第二个问题的前一半「什么时候需要」看第二、第三、第四部分，后一半「怎么搭」看第五部分。

表里的前三个问题属于验证。第四个问题讲多次运行的结果怎么汇总，第 13 讲把它归在评估协议里，也就是跑分时每题跑几次、结果怎么汇总这类规定。第七部分讲把评估跑起来的那套程序和搭评估的步骤。

两个例子的细节

τ²-bench 的例子。τ²-bench 是 τ-bench 的后续版本，也是让 agent 和一个模拟的用户对话、完成客服任务的基准测试。这个任务里 agent 扮演航空公司的客服，一位顾客想改签一张基础经济舱的机票。航空公司的规定是这个舱位不能改签，基准测试期望 agent 拒绝。Claude Opus 4.5 的做法是先给顾客升舱，再改签，两步都符合规定。评分器没有预料到这种做法，判为失败。出处：Anthropic 介绍 Claude Opus 4.5 的文章；Anthropic，2026。

Anthropic 把这一次的做法称为正当的。它同时提醒：在别的场合，模型绕开任务本来的限制去达到目的，可能算作钻空子（reward hacking）。钻空子指靠利用评分办法的漏洞拿到分数，Anthropic 的说法是模型用设计者没有料到的方式去利用规则或目标。

SWE-bench 的例子。SWE-bench 的每道题取自开源代码仓库里一个真实的问题。这个问题已经由仓库的开发者用一次代码合并修好，这次合并除了改代码，也加了或改了测试。agent 拿到的是问题的描述和修复之前的代码，要自己写出补丁。

SWE-bench 用两组测试来判定一个补丁。一组叫 fail-to-pass，简称 F2P，是修复之前不通过、修复之后应该通过的测试，用来确认 bug 修好了。另一组叫 pass-to-pass，简称 P2P，是修复前后都应该通过的测试，用来确认没有改坏别的功能。

Wang 等人 2025 年的研究指出，SWE-bench 判定补丁时只跑一部分测试文件：开发者修复这个问题的那次代码合并改过哪些测试文件，就只跑哪些，仓库里其他的测试不跑。F2P 和 P2P 两组测试都在这几个文件里，所以补丁改坏了其他文件所测的功能时，SWE-bench 发现不了。

他们的实验用了 SWE-bench Verified，它是 SWE-bench 里经过人工确认的一部分题目。他们把三个系统在这些题目上被判为解决的补丁，拿去跑仓库里全部的测试，平均有 7.8% 的补丁通不过，这三个系统的解决率平均因此下降 4.5 个百分点。出处：Wang 等，2025。

第 13 讲讲过 Zhu 等人 2025 年的检查：10 个常用的 agent 基准测试里，7 个的评分存在把对的判成错的或把错的判成对的问题。评分器判得准不准，要像被评的 agent 一样拿数据来检验。这是这一讲的主线。

三种评分器的对照

按任务的不同，三种评分器在分析 agent 交出的东西时各有长短，花费也不同。

{{fig 13 | 三种评分器在六个方面的对照。绿色表示好，红色表示差，黄色居中。下面的两个蓝框是每种评分器都可以看的两样东西。}}

不管哪一种评分器，能看的东西有两样：环境的最终状态，和运行轨迹（trajectory，agent 每一步的动作和看到的结果的完整记录）。看最终状态是评结果，看运行轨迹是评过程。

代码评分器

代码评分器是确定的检查，写成可以运行的脚本，检查的对象是环境或运行轨迹。

{{fig 14 | 左边是常见的五类检查。右边是一个示意的评分函数，它同时检查了结果和过程。}}

图里的评分函数如下。前两条看结果：测试有没有通过，订单在不在数据库里。第三条看过程：运行轨迹里有没有调用过核实身份的工具。

def grade(env, transcript):
    # outcome: did the fix work?
    ok = run('pytest tests/') == 0
    # outcome: is the order there?
    ok &= env.db.has_order('u42')
    # transcript: identity checked?
    ok &= 'verify_id' in transcript.tools
    return ok

代码评分器的三个缺点

代码只检查写进去的那些东西。它的三个缺点见下表。

人工评分

人工评分是让人直接判断 agent 做出来的东西。对开放式的工作，这往往是有效的办法。

{{fig 17 | 左边是四种常见的做法。右边是两两比较的界面：两个回答并排，评分的人选「A 更好」「一样」或「B 更好」。}}
  • 专家评分。请这个领域的专业人员来看。
  • 大众投票。请很多非专业的人来投票。
  • 两两比较（pairwise）。把两个结果放在一起，问哪个更好。
  • 真实使用。让真实的用户和 agent 一起工作，用完之后打分。

评的主题不同，找的人也不同。下面是三个例子。

第一个例子 Chatbot Arena 是一个让用户给两个匿名模型的回答投票的网站。第二个例子 GDPval 是 OpenAI 2025 年发布的评估，任务取自各行业专业人员有代表性的实际工作，模型要交出一份工作成果，再由同一职业的专家来评。

第三个例子 Co-Gym 的全名是 Collaborative Gym，是研究人和 agent 怎样协作的评估框架。它有两种实验设置。一种由程序来模拟和 agent 协作的用户。另一种是真人在网页应用里和 agent 协作。表里说的是真人参加的那一种。

人工评分的三个缺点

人的判断是最可信的参照，它最接近真实的情况。但收集起来很花时间。

语言模型评审

语言模型评审是用一个语言模型来代替人类评分员：把评分标准（rubric，写明每一档分数对应什么表现的说明）写进 prompt（交给模型的那段输入文字），让模型照着判断。英文叫 LLM-as-a-Judge。

{{fig 20 | 左边是四种常见的问法。右边是一个示意的评审 prompt：给出问题、agent 的回答和参考答案，只判断最后的答案是否一致。评审输出三项：从回答里提取出的答案、理由、是否正确。}}

交给评审的判断有多开放

不同的基准测试，交给评审的判断有的很具体，有的很开放。一头是很具体的问题：答案对上了没有。另一头是开放的偏好：哪个更好。

{{fig 21 | 三组基准测试排在一条轴上。从左到右，交给评审的判断越来越开放。}}

第二行的 MT-Bench 是一套 80 道人工设计的两轮问答题，聊天模型的回答交给评审来打分或比较。第三行的 AlpacaEval 2.0 是一个用语言模型当评审的聊天模型排行榜，按胜率排名。表里说的按长度校正，指用统计的办法扣掉回答长短对胜率的影响，因为评审偏向更长的回答。

语言模型评审的三个缺点

语言模型评审像代码一样能大批量地跑，像人一样能做判断。它的缺点有三个，见下表。

组合起来用
