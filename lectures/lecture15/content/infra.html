先看结论

  • 一套评估除了任务和评分器（判定结果对不对的那段逻辑），还要有一套把它们跑起来的程序，叫评估的运行框架（evaluation harness）。被评的是 agent，也就是能自己调用工具、分很多步去完成一个任务的语言模型系统。评估的运行框架负责给 agent 指令和工具、并发地跑任务、记录每一步、调用评分器、汇总结果。
  • Anthropic 2026 年的一篇文章对评估的运行框架提了三条要求：评估里的 agent 和线上的基本一样，每次运行互相隔离、从干净的环境开始，环境本身不干扰分数。运行之间共享了文件或缓存，分数会失真，方向可高可低。
  • 这篇文章把从零搭一套评估的经验写成了一份路线，编号从第 0 步到第 8 步，分三组：收集任务，设计评估的运行框架和评分器，长期维护。
  • 分数低的时候，先怀疑评估这一边：评分有没有判错，任务说明有没有歧义，评估给模型配的 agent 的运行框架有没有限制它。agent 的运行框架是包在模型外面、给它工具的程序。文章举的一个例子出在 CORE-Bench 这个基准测试（benchmark，一组题目加一个报告成绩的办法）上。Claude Opus 4.5 在它最难一档任务上答对的比例，用基准测试自带的 agent 的运行框架时是 42%，换了 agent 的运行框架、改掉评分的错之后是 95%。基准测试的作者说明，只换 agent 的运行框架时是 78%。
  • 要知道评分器是不是在正常工作，必须去读运行记录和评分的结果。运行记录是 agent 每一步的动作和结果的完整记录，前面各部分叫它运行轨迹。

这一部分的依据

前面六个部分讲的是评分器，以及多次运行的结果怎么汇总。把它们用起来，还需要一套工程上的东西。

这一部分依据的是 Anthropic 在 2026 年 1 月 9 日发表的文章《Demystifying evals for AI agents》，作者是 Mikaela Grace、Jeremy Hadfield、Rodrigo Olivares 和 Jiri De Jonghe。文章总结的是 Anthropic 自己和它的客户搭评估的经验，讨论的是开发过程中不需要真实用户就能跑的自动评估。出处：Anthropic，2026。这一部分引用的内容都来自这篇文章，另有出处的地方单独注明。

第 13 讲站在两个角度讲基准测试：出题的人和拿别人的题来跑分的人。这篇文章站的是第三个角度：一个开发 agent 产品的团队，要给自己的 agent 搭一套评估。很多原则是相通的，侧重点不同。

用词对照

文章给评估的各个组成部分下了定义。下面的表列出这些定义，最后一列是第 13 讲和这一讲前面各部分对同一样东西的叫法。

运行记录和最终结果的区别，文章用订机票的 agent 举例：agent 在运行记录的最后说「您的机票已经订好」，这是运行记录里的一句话。数据库里有没有这条预订，才是最终结果。第一部分说评分器可以看两样东西，指的就是这两样。

两种运行框架，以及评估的那一种要做到什么

「运行框架」这个词指两样不同的东西，要分清。

关于前一种，文章有一句话和第 13 讲的结论相同：评估「一个 agent」的时候，评的是 agent 的运行框架和模型合在一起的表现。

关于后一种，文章列了它要做的五件事：给 agent 提供指令和工具，并发地运行任务，记录所有的步骤，给输出评分，汇总结果。

两种运行框架的定义里都提到工具，说的是两件事。评估的运行框架面对的是整个 agent，它把任务的指令和做这个任务能用的工具交给 agent。agent 的运行框架在 agent 里面，它把工具交给模型，替模型安排每一次工具调用。

在搭评估的运行框架的时候，文章提了三条要求。

做到第二条的一种办法是用容器。上面提到的 Harbor 就是把 agent 放进隔离的容器里去跑任务的。

第二条和第三条都和第六部分有关。pass@k 和 pass^k 是汇总多次运行结果的两种办法，前一个是 k 次里至少成功一次的机会，后一个是 k 次全部成功的机会。两者的定义都要求各次运行互不影响，也就是一次运行成不成功，和别的运行无关。运行之间有共享的状态，或者好几次运行因为同一个环境限制而失败，这个要求就不满足，算出来的数和它名字所说的意思就对不上了。

两种评估集：测能力的和防退步的

文章把评估集按用途分成两种，它们期望的通过率正好相反。

测能力的评估集可以转成防退步的评估集：它的通过率变得很高之后，就把它当作防退步的评估集，持续地跑。同一批任务，以前回答的是「这件事我们做不做得到」，以后回答的是「这件事我们是不是还能可靠地做到」。

第 13 讲讲过基准测试的生命周期：最好的系统接近满分之后，这个基准测试就要被替换。产品团队自己的评估集也会碰到同样的情况，文章把它叫作饱和：agent 通过了所有可以解决的任务，从分数上已经看不出它还有哪里可以改进。文章还指出一个容易忽略的后果：评估集接近饱和时，剩下的都是最难的任务，能力上很大的进步，在分数上只表现为很小的提高。

从零搭一套评估的路线

文章把经验整理成一份路线，从「一个评估都没有」走到「有一套可以信任的评估」。它的总纲是：尽早定义什么叫成功，把它清楚地量出来，然后不断地改。

路线见下表。文章里的编号是从第 0 步到第 8 步，一共九项，分成三组。第 0 步「尽早开始」可以看作正式开始之前的一条提醒。

几条值得展开的建议

  • 通过率是 0%，多半是任务本身有问题。第 2 步里有一条判断办法：对前沿的模型来说，一个任务跑很多次全都不通过，多数时候说明任务本身有问题，要回头检查任务说明和评分器，不能直接断定 agent 没有这个能力。测能力的评估集里也会有 agent 确实还做不到的任务，区分这两种情况靠的就是这次检查。第 2 步要求的参考解法可以用来做这个检查：它能通过所有评分器，就证明任务可解、评分器配置正确。
  • 两个方向都要测。第 3 步的例子来自 Anthropic 给 Claude 的网页搜索功能做评估。难点是既要让模型在不该搜的时候不去搜，又要保住它在该搜的时候深入搜索的能力。团队做了两个方向的题：应该搜的，比如查天气；应该直接回答的，比如「苹果公司是谁创立的」。如果只测前一种，得到的会是一个什么都要搜一下的 agent。
  • 评结果，少评步骤。第 5 步里说，人们常常想检查 agent 是不是照着特定的步骤做的，比如按某个顺序调用了某几个工具。文章认为这样太死板：agent 经常找到出题的人没想到的正确做法，只认固定步骤的测试会把这些做法判为失败。出题的人没想到的正确做法，第一部分有一个例子：在 τ²-bench 这个测客服 agent 的基准测试里，Claude Opus 4.5 用一种评分器没预料到、但符合规定的办法帮顾客改了机票，被判为失败。
  • 给部分分。一个客服 agent 正确地找出了问题、核实了顾客的身份，但没能办成退款，它比一上来就失败的 agent 好得多。评分的结果应该反映出这种差别。
  • 先写评估，再做功能。第 8 步里建议，在 agent 还做不到的时候，就把计划中的能力写成评估，再不断改进直到通过。这样新模型发布时，跑一遍评估就知道哪些事现在能做了。

「评结果，少评步骤」这一条，看上去和第一部分的一个说法相反。第一部分说，有些任务除了结果还要看过程。两处针对的是两种情况。少评的是 agent 自己选的做法：先调用哪个工具、分几步做，可以和出题的人想的不一样。任务的规定明确要求的步骤仍然要查。第一部分的例子是客服 agent 退款之前要先核实用户的身份，所以那里的示意评分函数会检查运行轨迹里有没有调用核实身份的工具。上面「给部分分」那一条里，文章也把核实顾客的身份算作应该得分的一步。

第 2 步里两位专家的那条判断办法，文章说也适用于语言模型评审用的评分标准，也就是写明每一档分数对应什么表现的说明：评分标准含糊，评审的判定就会前后不一。这一条和第 5 步里与语言模型评审有关的几条建议，都收在第五部分的检查表里。

分数低的时候，先怀疑评估

文章有一个反复出现的观点：有些评估出的问题不容易发现，agent 表现得不错，分数却很低，原因在评分的 bug、agent 的运行框架对模型的限制，或者任务说明的歧义。文章说，经验丰富的团队也会漏掉这些问题。它举了几个例子。

四个例子里都有把对的判成错的情况，也就是第一部分那张表里「实际上正确、评分器判为错误」的那一格。CORE-Bench 的例子还有另一个原因：分数的提高有一大半来自换 agent 的运行框架，见本节最后的说明。

文章给出的规矩是：在有人去查过评估的细节、读过一些运行记录之前，不直接相信评估的分数。如果评分不公平、任务有歧义、正确的解法被扣分，或者 agent 的运行框架限制了模型，这个评估就应该修改。

i
这些例子出自模型厂商自己的文章。四个例子里有三个写明了被低估的是哪个模型：CORE-Bench、METR 和 τ²-bench 的例子里，被低估的都是 Anthropic 自己的 Claude。在这三个例子里，举例的一方同时是被评模型的厂商。Terminal-Bench 的例子没有提到具体的模型。这四个例子能说明评估会低估 agent。但这种情况有多常见，要看独立的来源。第 13 讲里，Zhu 等人检查的 10 个常用 agent 基准测试里，7 个的评分有判错的问题，方向有高估也有低估。

反方向的情况，也就是评分器把错的判成对的，文章在第 5 步里也提到了：评分器要能防住绕过检查的做法，任务和评分器要设计成只有真的解决了问题才能通过。

CORE-Bench 的三个分数

CORE-Bench 的例子里，同一个模型先后有三个分数。下表列出每个分数是在什么做法下得到的。

从 42% 到 78% 的差别来自 agent 的运行框架。这个基准测试为了让各个模型在同样的条件下比较，给所有模型配了同一个 agent 的运行框架。换成 Claude Code 之后，同一个模型的分数就从 42% 变成了 78%。Anthropic 的文章对这件事的说法是，换上的 agent 的运行框架对模型的限制更少。基准测试的作者说还不确定原因，给了两个猜测。一个是 Claude 4.5 这一代模型和 Claude Code 配合得更好。另一个是原来的 agent 的运行框架里写给模型的细致指示，对能力较弱的模型有帮助，对能力更强的模型反而成了妨碍。

从 78% 到 95% 的差别来自评分。评分器允许回答和参考结果有一点出入，允许的范围是按基准测试的作者自己把任务跑三次的结果算出来的。有些任务三次的结果完全相同，算出的范围就没有宽度，回答在小数位上有很小的差别也被判错。Anthropic 的文章举的例子是期望 96.124991 这样的数，回答 96.12 被判错。另一些任务的说明有歧义，合理的理解被判为失败。这两类加起来是 8 个任务，基准测试的作者人工复核之后改判为正确。被删掉的那个任务，数据集的下载地址已经失效，不可能复现。

agent 的运行框架按前面的对照表属于被评的对象。在这个例子里，它是基准测试统一配给各个模型的，对想知道模型能力的人来说，它也是评估这一边定下的条件。这和前面说的一致：评的是 agent 的运行框架和模型合在一起的表现，42% 说的是这个模型配上基准测试自带的那个 agent 的运行框架的表现。

读运行记录

第 6 步只有一件事：读。文章的说法是，不去读很多次运行的记录和评分，就没法知道评分器是不是在正常工作。一个任务失败时，运行记录能告诉你是 agent 真的犯了错，还是评分器拒绝了一个正确的解法。

文章给了一个判断评估好不好的标准：一个任务被判失败时，读记录的人会觉得判得合理，能清楚地看出 agent 错在哪里、为什么错。分数涨不上去的时候，得有把握说原因在 agent 身上，和评估无关。

第 13 讲把这件事列为好的基准测试的一条性质，叫可解释：失败了看得出原因。那里是对出题的人的要求，这里是对用评估的人的要求。

第四部分里 WebVoyager 的结果说明了为什么只看总分不够。那项研究让一个语言模型当评审，判断网页任务做成了没有。它给出的总体成功率和人工评分只差 2 个百分点。按网站拆开才看到，在 Coursera 这个网站上，它判出的成功率比人工评出的低 15.9 个百分点。要知道差在哪里，下一步就是去读那个网站上的运行记录。

自动评估只是办法之一

自动评估可以在不上线、不影响真实用户的情况下，把 agent 放到成千上万个任务上去跑。但它只是了解 agent 表现的办法之一。文章列了六种办法。

为什么要几种办法一起用，文章引用了安全工程里的瑞士奶酪模型（Swiss Cheese Model）来说明。这个模型把每一道防护看成一片带孔的奶酪，几片叠在一起，一片上的孔会被另一片挡住。用到评估上的意思是：没有哪一种评估办法能发现所有的问题，几种办法一起用，一种办法漏掉的失败可以由另一种办法发现。

文章的总结是：最有效的团队把这些办法组合起来，用自动评估在每次改动之后很快看到效果，用线上监控来了解真实情况，用定期的人工检查来校准。

表里的最后一行，和第一部分的结论是同一件事：人的判断很贵，所以用在校准评审这样的地方。

整讲的小结

这一讲前六个部分的内容可以归纳成五条。

  • 第 13 讲把基准测试的任务定义拆成问题描述、环境、验证三样，验证指判定 agent 交出的结果算不算通过的那一步。这一讲的前五个部分看的是验证这一块，它会出错：评分器会把对的判成错的，也会把错的判成对的，分数因此偏低或偏高。
  • 评分器有三种：代码、人、语言模型。实际的评估有时把几种组合起来用：能用代码检查的地方用代码，必须判断的地方用语言模型，人用在抽查和校准上。
  • 用语言模型当评审的做法，这一讲按被评的东西分成三个阶段：代替文本指标（用程序给一段文字自动算分的办法），判断人的偏好，评 agent 的动作。每个阶段都有研究拿评审的判定和人的判断对照，报告两者有多一致。
  • 偏差是总朝同一个方向的误差，多评样本消不掉。语言模型评审有位置偏差和长度偏差，也就是偏向排在某个位置的回答、更长的回答。位置偏差在评审和排列顺序都固定时总朝同一个方向，随机排列顺序可以把它变成随机误差。自我偏好指评审偏向和它出自同一个模型的回答，几项研究看到了迹象，证据不如前两种充分。位置偏差用对调顺序来处理，长度偏差可以用统计模型扣掉。评审可不可信，要拿一批人判过的样本来检验。
  • agent 每次运行的结果不同。报分数时要写明用的是平均成功率、pass@k 还是 pass^k，k 是多少，每个任务跑了几次。各次运行之间有没有共享的东西、基础设施故障造成的失败怎么处理，也要写明。

前四条讲的是同一件事，也是这一讲的主线：评分器本身是一个测量工具，它也要被检验。第五条讲的是另一件事：多次运行的结果怎么汇总，报分数时要写明。这一页讲的是把这两件事做起来要用的东西：评估的运行框架，搭评估的路线，和读运行记录。

第 13 讲的结论是没有哪一个基准测试能说明一切。这一讲的结论接着往下说：单看一个基准测试给出的分数，也要在评分器经过检验、汇总办法写明之后，才知道它说明了什么。对语言模型评审来说，检验就是拿它的判定和人的判定对照。
