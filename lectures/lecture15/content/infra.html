先看结论

  • 一套评估除了任务和评分器（判定结果对不对的那段逻辑），还要有一套把它们跑起来的程序，叫评估的运行框架（evaluation harness）。被评的是 agent，也就是能自己调用工具、分很多步去完成一个任务的语言模型系统。运行框架负责给 agent 指令和工具、并发地跑任务、记录每一步、调用评分器、汇总结果。
  • 运行框架最要紧的要求是每次运行互相隔离，从干净的环境开始。运行之间共享了文件或缓存，分数会失真，方向可高可低。
  • Anthropic 的文章把从零搭一套评估的经验写成了一份路线，编号从第 0 步到第 8 步，分三组：收集任务，设计运行框架和评分器，长期维护。
  • 分数低的时候，先怀疑评估本身。文章举的例子里，一个模型在一个基准测试（benchmark，一组题目加一个报告成绩的办法）上的分数最初是 42%，换了 agent 的运行框架（包在模型外面、给它工具的程序）之后是 78%，再修掉评分的问题之后是 95%。
  • 要知道评分器是不是在正常工作，必须去读运行记录和评分的结果。

这一部分的依据

前面六个部分讲的是评分器和分数的算法。把它们用起来，还需要一套工程上的东西。

这一部分依据的是 Anthropic 在 2026 年 1 月 9 日发表的文章《Demystifying evals for AI agents》，作者是 Mikaela Grace、Jeremy Hadfield、Rodrigo Olivares 和 Jiri De Jonghe。文章总结的是 Anthropic 自己和它的客户搭评估的经验，讨论的是开发过程中不需要真实用户就能跑的自动评估。出处：Anthropic，2026。这一部分引用的内容都来自这篇文章，另有出处的地方单独注明。

第 13 讲站在两个角度讲基准测试：出题的人和拿别人的题来跑分的人。这篇文章站的是第三个角度：一个开发 agent 产品的团队，要给自己的 agent 搭一套评估。很多原则是相通的，侧重点不同。

先对一下用词

文章给评估的各个组成部分下了定义。下面的表列出这些定义，并对上这个网站前面用的说法。

运行记录和结果的区别，文章用订机票的 agent 举例：agent 在运行记录的最后说「您的机票已经订好」，这是运行记录里的一句话。数据库里有没有这条预订，才是结果。第一部分说评分器可以看两样东西，指的就是这两样。

两种运行框架，以及评估的那一种要做到什么

「运行框架」这个词指两样不同的东西，要分清。

关于前一种，文章有一句话和第 13 讲的结论相同：评估「一个 agent」的时候，评的是运行框架和模型合在一起的表现。

关于后一种，文章列了它要做的五件事：给 agent 提供指令和工具，并发地运行任务，记录所有的步骤，给输出评分，汇总结果。在搭它的时候，文章提了三条要求。

做到第二条的一种办法是用容器。上面提到的 Harbor 就是把 agent 放进隔离的容器里去跑任务的。

第二条和第六部分直接有关。pass@k 和 pass^k 是两种汇总多次运行的指标，前一个是 k 次里至少成功一次的机会，后一个是 k 次全部成功的机会。两个式子都假设各次运行互不影响。运行之间有共享的状态，这个假设就不成立，算出来的数和它名字所说的意思就对不上了。

两种评估集：测能力的和防退步的

文章把评估集按用途分成两种，它们期望的通过率正好相反。

两者之间可以转换。一个测能力的评估集，通过率变得很高之后，可以转成防退步的评估集，持续地跑。同一批任务，以前回答的是「这件事我们做不做得到」，以后回答的是「这件事我们是不是还能可靠地做到」。

第 13 讲讲过基准测试的生命周期：被做满之后要被替换。这里是同一件事在产品团队里的版本。文章把它叫作饱和：agent 通过了所有可以解决的任务，评估就不再提供改进的信号。文章还指出一个容易忽略的后果：评估接近饱和时，剩下的都是最难的任务，能力上很大的进步，在分数上只表现为很小的提高。

从零搭一套评估的路线

文章把经验整理成一份路线，从「一个评估都没有」走到「有一套可以信任的评估」。它的总纲是：尽早定义什么叫成功，把它清楚地量出来，然后不断地改。

路线见下表。文章里的编号是从第 0 步到第 8 步，一共九项，分成三组，文章自己没有说过一共几步。第 0 步「尽早开始」可以看作正式开始之前的一条提醒。

几条值得展开的建议

  • 通过率是 0%，多半是任务坏了。第 2 步里有一条判断办法：对前沿的模型来说，一个任务跑很多次全都不通过，多数时候说明任务本身有问题，要回头检查任务说明和评分器，不能直接断定 agent 没有这个能力。
  • 两个方向都要测。第 3 步的例子来自 Anthropic 给 Claude 的网页搜索功能做评估。难点是既要让模型在不该搜的时候不去搜，又要保住它在该搜的时候深入搜索的能力。团队做了两个方向的题：应该搜的，比如查天气；应该直接回答的，比如「苹果公司是谁创立的」。如果只测前一种，得到的会是一个什么都要搜一下的 agent。
  • 评结果，少评步骤。第 5 步里说，人们常常想检查 agent 是不是照着特定的步骤做的，比如按某个顺序调用了某几个工具。文章认为这样太死板，测试会很脆弱，因为 agent 经常找到出题的人没想到的正确做法。第一部分讲过一个例子：在 τ²-bench 这个测客服 agent 的基准测试里，Claude Opus 4.5 用一种评分器没预料到、但符合规定的办法帮顾客改了机票，被判为失败。
  • 给部分分。一个客服 agent 正确地找出了问题、核实了顾客的身份，但没能办成退款，它比一上来就失败的 agent 好得多。评分的结果应该反映出这种差别。
  • 先写评估，再做功能。第 8 步里建议，在 agent 还做不到的时候，就把计划中的能力写成评估，再不断改进直到通过。这样新模型发布时，跑一遍评估就知道哪些事现在能做了。

第 5 步里和语言模型评审有关的几条建议，已经收在第五部分的检查表里。

分数低的时候，先怀疑评估

文章有一个反复出现的观点：有些评估的失败方式很隐蔽，agent 表现得不错，分数却很低，原因在评分的 bug、agent 的运行框架对模型的限制，或者任务说明的歧义。文章说，经验丰富的团队也会漏掉这些问题。它举了几个例子。

四个例子里都有把对的判成错的情况，也就是第一部分那张表里「实际上正确、评分器判为错误」的那一格。CORE-Bench 的例子还有另一个原因：分数的提高有一大半来自换 agent 的运行框架。这和前面说的一致，评的是运行框架和模型合在一起的表现。

文章给出的规矩是：在有人去查过评估的细节、读过一些运行记录之前，不直接相信评估的分数。如果评分不公平、任务有歧义、正确的解法被扣分，或者 agent 的运行框架限制了模型，这个评估就应该修改。

i
这些例子出自模型厂商自己的文章。四个例子里有三个点了名：CORE-Bench、METR 和 τ²-bench 的例子里，被低估的都是 Anthropic 自己的 Claude。Terminal-Bench 的例子没有提到具体的模型。也就是说，举例的一方同时是被评模型的厂商。这四个例子能说明评估会低估 agent，这种情况有多常见，要看独立的来源。第 13 讲里，Zhu 等人检查的 10 个常用 agent 基准测试里，7 个的评分有判错的问题，方向有高估也有低估。

反方向的情况，也就是评分器把错的判成对的，文章在第 5 步里也提到了：评分器要能防住绕过检查的做法，通过评估应该真的要求解决问题。

读运行记录

第 6 步只有一件事：读。文章的说法是，不去读很多次运行的记录和评分，就没法知道评分器是不是在正常工作。一个任务失败时，运行记录能告诉你是 agent 真的犯了错，还是评分器拒绝了一个正确的解法。

文章给了一个判断评估好不好的标准：失败应该看上去是公平的，能清楚地看出 agent 错在哪里、为什么错。分数涨不上去的时候，得有把握说原因在 agent 身上，和评估无关。

第 13 讲把这件事列为好的基准测试的一条性质，叫可解释：失败了看得出原因。那里是对出题的人的要求，这里是对用评估的人的要求。

第四部分里 WebVoyager 的结果说明了为什么只看总分不够。那项研究让一个语言模型当评审，判断网页任务做成了没有。它给出的总体成功率和人工评分只差 2 个百分点，按网站拆开才看到 Coursera 上差了 15.9 个百分点。要知道差在哪里，下一步就是去读那个网站上的运行记录。

自动评估只是办法之一

自动评估可以在不上线、不影响真实用户的情况下，把 agent 放到成千上万个任务上去跑。但它只是了解 agent 表现的办法之一。文章列了六种办法。

文章引用了安全工程里的瑞士奶酪模型（Swiss Cheese Model）来说明这一点：没有哪一种评估办法能发现所有的问题，几种办法一起用，一种办法漏掉的失败可以由另一种办法发现。它的总结是：最有效的团队把这些办法组合起来，用自动评估来快速迭代，用线上监控来了解真实情况，用定期的人工检查来校准。

表里的最后一行，和第一部分的结论是同一件事：人的判断很贵，所以用在校准评审这样的地方。

整讲的小结

这一讲可以归纳成五条。

  • 第 13 讲把基准测试的任务定义拆成问题描述、环境、验证三样，验证指判定 agent 交出的结果对不对的那一步。这一讲看的是验证这一块，它会出错：评分器会把对的判成错的，也会把错的判成对的，分数因此偏低或偏高。
  • 评分器有三种：代码、人、语言模型。能用代码检查的用代码，需要判断的地方用语言模型，人用在校准上。
  • 用语言模型当评审经历了三个阶段：代替文本指标，判断人的偏好，评 agent 的动作。每一个阶段的研究都是先拿评审和人的判断对照，再谈它能用来做什么。
  • 语言模型评审有位置、长度和自我偏好这几种偏差。它们总朝同一个方向，要靠对调顺序、统计校正和人工标注来发现和修正。
  • agent 每次运行的结果不同。报分数时要说明用的是平均成功率、pass@k 还是 pass^k，以及 k 和每个任务跑的次数。

把五条合起来就是这一讲的主线：评分器本身是一个测量工具，它也要被验证。第 13 讲的结论是没有哪一个评测能说明一切。这一讲补上了另一半：一个评测给出的分数，要在评分器和人对过、汇总的算法写明之后，才知道它说明了什么。
