先看结论

  • agent 是能自己调用工具、分很多步去完成任务的语言模型系统，训练它用的数据叫 agent 数据，有两种。运行轨迹（trajectory，也叫 trace）是一次解题过程的完整记录，模型照着它模仿，这种训练叫监督微调。环境（environment）是一个任务加一个可以动手的沙盒，再加一个判断做成没有的验证器，沙盒是一个隔离的运行空间。模型在里面反复练习，每次按验证器给的分数（奖励）来更新，这种训练叫强化学习。
  • 拿运行轨迹训练时，模型要学着预测的只有 agent 自己写的那几段（想法和动作）。系统 prompt、任务和工具返回的结果只作为上下文。轨迹的格式由包在模型外面的程序决定。
  • 环境的奖励有四种来源：代码测试、评分细则、用语言模型当评审、真人的偏好。排在前面的可靠但适用面窄，排在后面的适用面广但不精确。
  • 让模型在一个环境里跑很多次，这些运行有两种用法：挑出好的，把它们的运行轨迹拿去做监督微调，或者给每一次运行打分，再按分数做强化学习的更新。所以环境可以产出运行轨迹。反过来，只有轨迹是造不出环境的：轨迹只是一次过程的记录，里面没有可以重新动手的沙盒，也没有判断做成没有的验证器。
  • 各阶段的数据量很少有公司公开。DeepSeek 公开过的数字是：V3 预训练用 14.8 万亿个 token，监督微调用 150 万条样本；一年后的 V3.2 在强化学习里用了大约 8.5 万个 agent 任务，后训练的算力超过了预训练的 10%。预训练是模型在海量文字上做的第一段训练。token 是模型处理文字的最小单位，大致是一个词或半个词。后训练（post-training）指预训练之后再用少量专门的数据继续训练的阶段，监督微调和强化学习都属于它。

两种数据各是什么

trajectory 和 trace 是一回事。这一讲里这两个词可以互换，都指一次运行的完整记录，下面统一叫运行轨迹。一次运行本身叫 rollout：把模型放进环境，让它从拿到任务一直做到提交。规定的步数用完还没有提交的，这次运行也到此结束。每一次 rollout 留下一条运行轨迹。

一条运行轨迹里，哪些部分算进训练

一条运行轨迹是几种角色轮流出现的一长串文字。训练时，模型要学着预测的只有 agent 自己写的那几段。

这样做的理由很直接。系统 prompt 和任务是别人给的，工具返回的结果是环境产生的，模型将来用不着自己去生成它们。模型要学会的是：看到前面这些内容之后，下一步该想什么、做什么。

{{fig 14 | 一条修 bug 的运行轨迹。左边一列是角色，中间是内容，右边一列方块标出这一段是否计入损失：深红色的计入，白色的不计入。损失（loss）指模型的预测和实际内容之间的差距。}}

下表按角色写出图里这条轨迹的内容，以及每种角色的文字是否计入损失。这条轨迹修的是 astropy 这个 Python 代码仓库里的一个 bug。任务是一个 issue，也就是代码仓库的使用者提交的问题报告。

表里有三个词来自这个仓库。separability_matrix 是这个仓库的 modeling 模块里的一个函数。「嵌套的模型」指这个模块里一个套一个的模型对象，和语言模型无关。_cstack 是同一个模块的 separable.py 文件里的一个内部函数，separability_matrix 在计算由几个模型组合成的模型时会用到它。

具体的做法是这样的。语言模型的训练目标是预测下一个 token。把整条轨迹交给模型，让它在每个位置预测下一个 token，但只有 agent 的那几段计入损失，其余位置的损失被屏蔽掉。哪些位置计入、哪些位置屏蔽，用一张表来标，这张表英文叫 loss mask，图右边那一列方块画的就是它。

轨迹的格式由运行框架决定

同一个动作可以写成几种样子。一种是一次工具调用（tool call），模型按固定的结构写出要调用的工具名和参数。一种是一段 ReAct 式的文字，模型用普通的文字先写想法、再写要做的动作，由包在模型外面的程序从这段文字里读出动作。还有一种是一段可以直接执行的代码。

用哪一种写法，由运行框架决定。运行框架（harness，也叫 scaffold）指包在模型外面、给它工具并管理多轮对话的程序。

第七部分拿三个常用的运行框架作例子，看同一个动作在每个框架里怎么写，并讲这件事的后果。后果是：一批轨迹如果都来自同一个运行框架，模型会把这个框架的格式和解题的能力一起学进去。

一个环境里有什么

用于后训练的一个环境由三样东西组成：任务、沙盒、验证器。

图上有几个词需要解释。沙盒返回的结果图上叫 observations，就是运行轨迹里工具返回的结果。模拟器指用软件模拟出来的系统，图上没有写明具体是哪一种。第五部分也用模拟器这个词，在那里专指扮演用户或环境的语言模型。端到端测试是把整个程序从头到尾运行一遍、检查最终结果的测试。评分细则是一份逐条检查的要求清单。偏好指让人或模型在几个回答里挑出更好的。评分细则和偏好在下一节细讲。

这和基准测试里一道题的结构完全一样。基准测试（benchmark）是一套固定的题目，用来给模型打分，第 13 讲会再讲到这三样。区别只在用途：拿来打分的时候它是基准测试的一道题，拿来训练的时候它是一个训练环境。Andrej Karpathy 2025 年 8 月 27 日发在 X 上的一篇帖子里也说，环境既可以用来训练模型，也可以用来评估模型。

环境还能产出运行轨迹。让一个语言模型在环境里解题，把它解题的过程录下来，就是一条轨迹。所以后面几部分讲数据来源时，有的办法直接造轨迹，有的办法先造环境，再从环境里得到轨迹。

反过来不行，只有轨迹是造不出环境的。轨迹只是一次过程的记录，里面没有可以重新动手的沙盒，也没有判断做成没有的验证器。

环境的奖励从哪里来

拿运行轨迹做监督微调时，更新模型的依据是 agent 的想法和动作预测得对不对。在环境里做强化学习时，依据是验证器给的奖励，也就是验证器在模型做完一次之后给的分数。上一节图里的通过或不通过，是只有两档的分数。

奖励有四种常见的来源，可以排在一条轴上：一头可靠但适用面窄，另一头适用面广但不精确。

上一节的图里，验证器的办法列了三类：测试、评分细则、偏好。这里的四种来源里，代码测试和评分细则同那张图上的前两类名字相同。那张图上的「偏好」可以理解为对应这里的后两种：由语言模型来排名次，和由真人来选。

后面几部分里的环境，大多数选的是轴左端的办法，也就是测试或者检查数据库的最终状态，因为大规模训练需要便宜、自动、每次结果一致的奖励。检查数据库的最终状态用在工具调用类的任务上：agent 调用工具会改动一个数据库，做完之后由程序比较数据库里的内容和预期是否一致。它和代码测试一样由程序判定，所以也在轴的左端，例子见第五部分的 τ-bench，一个考客服场景的基准测试。

两种数据怎么用来训练

前面说，运行轨迹用监督微调来模仿，环境用强化学习来练习。这两种训练可以从同一个环境出发。让模型在一个环境里做很多次 rollout（一次运行，从拿到任务到提交），这些运行有两种用法。一种是留下其中一部分的运行轨迹，拿去做监督微调。另一种是给每一次运行打分，做强化学习的更新。

{{fig 17 | 一个环境产生很多次运行，这些运行有两种用法。右上的方框是第一种：筛选之后变成监督微调的数据，模型模仿留下来的那些。右下的方框是第二种：给每次运行打分，再做强化学习的更新，每次运行在更新里占多大的分量，由它的奖励决定。}}

下表写出这两种用法各自怎么做，运行由谁产生，以及模型从中学到什么。

两种用法各有问题。监督微调学的是模仿示范，示范里有什么缺点也会被照着学。强化学习只按奖励来更新模型，奖励有漏洞的话，模型就会学会利用漏洞。这两个问题分别在第七部分和第六部分讲。

强化学习另有一个好处：模型有机会做得比示范更好。Karpathy 在前面提到的那篇帖子里说，这样有望比 statistical expert imitation 好很多，这个词的意思是照着专家的示范去模仿。

每个阶段用多少数据

这一节看各个训练阶段用多少数据和算力。能看到的趋势有两个。第一个是训练越往后，用的数据越少。第二个是后训练的算力相对预训练的比例变高了：DeepSeek 的 V3 按下表的数算是 0.19%，一年后的 V3.2 超过了 10%。

各家公司通常不公开每个训练阶段的数据量。DeepSeek 是少数写出过具体数字的：2024 年 12 月的 DeepSeek-V3 技术报告和 2025 年 12 月的 DeepSeek-V3.2 论文各给了一部分。

这一节的阶段按训练的先后来分。语言模型的训练常被分成预训练（pre-training）、中期训练（mid-training）和后训练（post-training）三段，Stanford 的语言模型课程 CS336 的数据一讲用的就是这个分法。按它的说法，中期训练是预训练之后，再拿质量更高的数据接着训练一段，用来加强模型的能力。监督微调和强化学习都属于后训练，排在中期训练之后。DeepSeek-V3 的后训练分两步，先做监督微调，再做强化学习。

这个分法和这一讲的另外两种说法可以这样对应。这一页开头和总览页把后训练说成预训练之后继续训练的阶段，这个说法没有把中期训练单独分出来。第一部分把训练分成三个阶段：预训练，监督微调和 RLHF，强化学习。RLHF 指用人对回答的评价当奖励来做强化学习。这三个阶段是按每个阶段用的数据来分的，其中的后两个阶段在这里都算后训练。

V3.2 的 8.5 万个任务是怎么来的

V3.2 论文里的表把强化学习用的 agent 任务分成四类，每一类的来源都能在后面几部分要讲的数据来源里找到。这一讲把 agent 数据的来源分成五种：人工演示，从现成的材料里提取，合成运行轨迹，合成任务和环境，模拟的用户和环境。下表最后一列写的是每一类任务对应其中哪一种。四类任务只用到了五种里的两种：从现成的材料里提取，合成任务和环境。

表里的「代码 agent」和「代码解释器」是两类不同的任务。代码 agent 要修改一个代码仓库，把 issue 里的问题解决掉。代码解释器这一类是解一道数学、逻辑或数据科学的题：模型可以在 Jupyter Notebook 里写代码并运行，用运行的结果来得出答案。Jupyter Notebook 是一种可以一段一段写代码、马上看到运行结果的工具。

「搜索 agent」这一类是用搜索工具查资料，回答一个问题。表里「环境」一列写「真实的」，指 agent 用的是真实的工具，论文举的是真实的网页搜索接口、编程工具和 Jupyter Notebook。「任务描述的来源」一列在论文里叫 prompt。

论文对通用 agent 那一类有一句概括：这些任务很难解，但很容易验证。例子是按一组约束条件规划三天的行程。城市、酒店、景点和餐馆可以组合出的方案数量极多，论文把它叫作很大的组合空间，要从里面找到一个满足全部约束的方案很难。检查一个给定的方案是否满足约束却很简单。

「很容易验证」这半句，和前面讲奖励时的要求是一回事：奖励要能便宜、自动、每次结果一致地给出。为什么要「很难解」，论文没有说明理由，只写了造任务时会一轮一轮地加大任务的难度。

这一部分的小结

  • 运行轨迹是示范，用监督微调来学，只有 agent 的想法和动作计入损失。
  • 环境是练习的地方，由任务、沙盒和验证器三样组成，用强化学习来学，按验证器给的奖励来更新模型。
  • 环境可以产出轨迹，所以造环境的办法也是造轨迹的办法。
  • DeepSeek 公开的数字里，训练越往后用的数据越少。这几个数单位不同，又来自两个模型，只能看出大致的趋势。后训练的算力相对预训练的比例，从 V3 的 0.19%（粗略估算）升到了一年后 V3.2 的超过 10%。
