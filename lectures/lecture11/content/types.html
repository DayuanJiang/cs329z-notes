先看结论

  • agent 数据有两种。运行轨迹（trajectory，也叫 trace）是一次解题过程的完整记录，模型照着它模仿。环境（environment）是一个任务加一个可以动手的沙盒，再加一个判断做成没有的办法，模型在里面反复练习。
  • 拿运行轨迹训练时，只有 agent 自己写的那几段（想法和动作）计入训练目标。系统 prompt、任务和工具返回的结果只作为上下文。轨迹的格式由包在模型外面的程序决定。
  • 环境的奖励有四种来源：代码测试、评分细则、用语言模型当评审、真人的偏好。排在前面的可靠但适用面窄，排在后面的适用面广但不精确。
  • 环境可以产出运行轨迹：让模型在环境里跑很多次，挑出好的拿去模仿，或者给每一次打分再按分数更新模型。反过来，只有轨迹是造不出环境的。
  • 各阶段的数据量很少有公司公开。DeepSeek 公开过的数字是：V3 预训练用 14.8 万亿个 token，监督微调用 150 万条样本；一年后的 V3.2 在强化学习里用了大约 8.5 万个 agent 任务，后训练的算力超过了预训练的 10%。

两种数据各是什么

上一部分说，agent 数据通常指对话和环境。放到 agent 任务上，对话就是运行轨迹。这两种数据的样子、用法和教给模型的东西都不一样。

{{fig 13 | 左边是运行轨迹：一串「想、做、看结果、再做、再看结果、提交」的记录。右边是环境：任务、沙盒和验证器三样。}}
i
trajectory 和 trace 是一回事。这一讲里这两个词可以互换，都指一次运行的完整记录，下面统一叫运行轨迹。一次运行本身叫 rollout：把模型放进环境，让它从头做到提交或者用完步数。每一次 rollout 留下一条运行轨迹。

一条运行轨迹里，哪些部分算进训练

一条运行轨迹是几种角色轮流出现的一长串文字。训练时，模型要学着预测的只有 agent 自己写的那几段。

{{fig 14 | 一条修 bug 的运行轨迹。左边一列是角色，中间是内容，右边一列方块标出这一段是否计入训练的损失：深红色的计入，白色的不计入。}}

具体的做法是这样的。语言模型的训练目标是预测下一个 token（模型处理文字的最小单位，大致是一个词或半个词）。把整条轨迹交给模型，让它在每个位置预测下一个 token，但只在 agent 的那几段上计算损失（预测和实际内容的差距），其余位置的损失被屏蔽掉。图右边那一列方块就是这张屏蔽表，英文叫 loss mask。

这样做的理由很直接。系统 prompt 和任务是别人给的，工具的输出是环境产生的，模型将来用不着自己去生成它们。模型要学会的是：看到前面这些内容之后，下一步该想什么、做什么。

轨迹的格式由运行框架决定

同一个动作可以写成几种样子：一次工具调用（tool call，模型按固定的结构写出要调用的工具名和参数），一段 ReAct 式的文字，或者一段可以直接执行的代码。用哪一种，由运行框架（harness，也叫 scaffold，指包在模型外面、给它工具并管理多轮对话的程序）决定，模型本身不决定。

这件事的后果在第七部分讲：一批轨迹如果都来自同一个运行框架，模型会把这个框架的格式和解题的能力一起学进去。

一个环境里有什么

用于后训练的一个环境由三样东西组成：问题描述、沙盒、验证。

{{fig 15 | 从左到右：问题描述（一段关于 ffmpeg 命令的求助），agent 读它；agent 在沙盒里工作，沙盒可以是终端、浏览器、模拟器或真实世界，两者之间来回的是动作和观察结果；agent 交出一份提交；验证用单元测试或端到端测试、评分细则、偏好这三类办法之一判定通过或不通过。}}

这和基准测试里一道题的结构完全一样，第 13 讲讲基准测试时会再讲到这三样。区别只在用途：拿来打分的时候它是基准测试的一道题，拿来训练的时候它是一个训练环境。Andrej Karpathy 在 2025 年 8 月的那篇帖子里也说，环境既可以用来训练模型，也可以用来评估模型。

环境还能产出运行轨迹。让一个语言模型在环境里解题，把它解题的过程录下来，就是一条轨迹。所以后面几部分讲数据来源时，有的办法直接造轨迹，有的办法先造环境，再从环境里得到轨迹。

环境的奖励从哪里来

拿运行轨迹做监督微调时，学习的信号来自「下一步动作预测得对不对」。在环境里做强化学习时，信号来自验证器给的奖励。奖励有四种常见的来源，可以排在一条轴上：一头可靠但适用面窄，另一头适用面广但不精确。

{{fig 16 | 四种奖励来源从左到右排列。左端标着「可靠，但窄」，右端标着「通用，但模糊」。}}

奖励的类型和用语言模型当评审的细节在第 15 讲展开。这里只要记住一点：后面几部分里的环境，大多数选的是轴左端的办法，也就是测试或者检查数据库的最终状态，因为大规模训练需要便宜、自动、每次结果一致的奖励。

两种数据怎么用来训练

有了一个环境，可以让模型在里面做很多次 rollout（一次运行，从拿到任务到提交）。这些运行的结果有两种用法。

{{fig 17 | 一个环境产生很多次运行。上面一条路是筛选之后变成监督微调的数据，模型模仿留下来的那些。下面一条路是给每次运行打分，再做强化学习的更新，每次尝试按奖励加权。}}

两条路的差别可以这样理解。SFT 学的是模仿示范，示范里有什么毛病也会被照着学。RL 让模型有机会做得比示范更好，Karpathy 的说法是有望比「统计意义上模仿专家」好很多；但模型会全力去争取奖励，奖励有漏洞的话，它就会学会利用漏洞。这两个问题分别在第七部分和第六部分讲。

每个阶段用多少数据

各家公司通常不公开每个训练阶段的数据量。DeepSeek 是少数写出过具体数字的：2024 年 12 月的 DeepSeek-V3 技术报告和 2025 年 12 月的 DeepSeek-V3.2 论文各给了一部分。

{{fig 18 | 左边三个数分别是 V3 预训练的 token 数、V3 监督微调的样本数，以及 V3.2 强化学习里 agent 任务的 prompt 数。右边的柱子是 V3 三个阶段的算力，单位是 H800 GPU 小时（H800 是 NVIDIA 的一款 GPU）。柱子的高度没有按比例画。}}

从这张表可以读出两件事。

  • 越靠后的阶段，数据的条数越少。预训练是 14.8 万亿个 token，监督微调是 150 万条样本，V3.2 强化学习里的 agent 任务是大约 8.5 万个。这三个数的单位不同（token、样本、任务），第三个数来自另一个模型，而且只算了 agent 任务，所以只能看出大致的趋势，不能换算成相差多少倍。CS336 的数据一讲对这个趋势的概括是：整个训练过程是从大量质量较低的数据，走向少量高质量的数据。
  • 后训练的算力占比在一年里涨了很多。V3 的后训练用了 0.5 万 GPU 小时，是预训练 266.4 万的 0.19%（粗略估算，用表里两个数相除）。V3.2 的论文说，后训练的算力预算已经超过预训练成本的 10%，并且说过去几个月里，模型的成绩随着强化学习预算的增加持续提高。

V3.2 的 8.5 万个任务是怎么来的

V3.2 论文里的表把强化学习用的 agent 任务分成四类，正好对应后面几部分要讲的数据来源。

论文对通用 agent 那一类有一句概括：这些任务很难解，但很容易验证。例子是按一组约束条件规划三天的行程：要在很大的组合空间里找到一个满足全部约束的方案很难，检查一个给定的方案是否满足约束却很简单。这正是一个好的训练环境需要的性质。

i
图上的 Mid 指什么。语言模型的训练常被分成预训练（pre-training）、中期训练（mid-training）和后训练（post-training）三段，Stanford CS336 的数据一讲用的就是这个分法。图上中间那根柱子的 11.9 万 GPU 小时，在 V3 的技术报告里是「上下文长度扩展」这一步的花费，也就是把模型能处理的文字长度拉长的那段训练。这种分法按训练的先后来分，监督微调和强化学习都属于后训练。第一部分的三个阶段是按各个时期最看重的数据来分的，那里的后两个阶段在这里都算后训练。

这一部分的小结

  • 运行轨迹是示范，用监督微调来学，只在 agent 的想法和动作上计算损失。
  • 环境是练习的地方，由问题描述、沙盒和验证三样组成，用强化学习来学，信号来自验证器给的奖励。
  • 环境可以产出轨迹，所以造环境的办法也是造轨迹的办法。
  • 越靠后的训练阶段，数据的条数越少，质量要求越高。DeepSeek 公开的数字显示，后训练的算力相对预训练的比例在一年里升了很多。
