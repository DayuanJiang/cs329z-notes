先看结论

  • 合成运行轨迹有两条路。先有指令：从一个任务或一篇教程出发，让语言模型把步骤写出来，不真正执行（Synatra）。先有交互：让模型先在环境里随意探索，事后再给这次探索配上一条它像是在完成的指令（OS-Genesis、NNetNav）。
  • 先有指令的做法最便宜，Synatra 每条样本 0.031 美元，但没有任何一步在真实环境里执行过。先有交互的做法里，轨迹中的观察都来自真的执行过的操作（NNetNav 训练用的动作是事后对着指令重新生成的），代价是要有能跑的环境，还要有模型来判断哪些探索有用。
  • 合成任务和环境更进一步：成批地造出沙盒（一个隔离的、可以随意操作的运行环境）、任务和验证器（判断任务做成没有的程序），每个任务自带可以验证的奖励。任务和验证器由程序和模型生成，搭沙盒这一步有的还要人参与。SWE-smith 往真实仓库里注入 bug，得到 50,137 个任务。R2E-Gym 把普通的代码提交变成 8,135 个任务。AgentScaler 把每个工具都写成对一个数据库的读或写，造出一千多个领域的模拟环境。
  • 这几个系统报告的成绩，比较的对象各不相同：有的和没训练的模型比，有的和另一种合成办法比，有的是每道题试 26 次再挑一个。读数字的时候要先看清它和谁比、怎么比。

合成运行轨迹的两条路

运行轨迹（trajectory）是一次解题过程的完整记录：任务，加上一步一步的观察和动作。上一部分的办法都要有现成的记录作为起点。合成的办法是：给定一个任务或者一个环境，让语言模型自己把步骤写出来或者跑出来，再用一个过滤器留下好的。

{{fig 39 | 两条路都通向运行轨迹。上：先有指令，从任务或教程出发，语言模型写出步骤但不执行，过滤器去掉无效的样本。下：先有交互，先自由探索环境，事后给这次运行配上指令，再给各次运行打分，丢弃分数低的。}}

下表把两条路逐项对照。

先有指令的做法有一个固有的问题：模型事先想出来的任务，在具体的环境里不一定做得成，写出来的步骤也不一定和真实的界面对得上。先有交互的做法把顺序倒过来，先看环境里能做什么，再决定任务是什么。

Synatra：把教程和网页改写成十万条示范，不执行任何一步

Synatra（Ou 等，NeurIPS 2024）的出发点是：网上有很多「间接的知识」，比如给人看的教程和各种网页，它们不能直接当训练数据，但可以让语言模型把它们改写成 agent 能用的示范。

{{fig 40 | 左：间接的知识，一篇「取消 PayPal 付款」的教程和一些网页。中：合成出的任务（在 PayPal 上取消 Amazon Prime 会员）和已经做过的动作。右：当前的观察（一段网页的 HTML，其中一个元素的 id 是 156）和下一步动作（点击这个元素）。图片来源：Ou 等，2024。}}

一条样本是什么

这里的一条示范是一个「状态和下一步动作」的对，每条只教下一步该做什么。状态包括任务、之前做过的动作和当前的观察，模型要学的是下一步动作。所以 10 万条示范是 10 万个单步的例子，准确数字是 99,920 个。

观察是文字形式的无障碍树（accessibility tree），没有截图。无障碍树是一份界面元素的清单，列出每个按钮和输入框的名称和类型。

两种材料，两种改写

Synatra 用了两种材料：wikiHow 上给人看的操作教程，和 ClueWeb 里的真实网页。ClueWeb 是一个研究用的网页数据集，保存的是大量真实网页的 HTML 快照。下表列出语言模型对这两种材料各做了什么，以及得到的样本里哪部分是真的、哪部分是模型编的。

同样从教程出发：Synatra 和 AgentTrek 的差别

上一部分的 AgentTrek 也是从教程出发的，两者正好是一组对照：一个只写不做，一个照着做一遍。

OS-Genesis：先在应用里探索，再反过来推出任务

OS-Genesis（Sun 等，2024，发表于 ACL 2025）针对的是手机和网页的图形界面。它把自己的做法叫作反向任务合成（reverse task synthesis）：先操作，再从操作的结果反推出任务。

{{fig 43 | 左：一条训练数据的样子，包括高层指令、历史和当前的界面截图、低层指令和动作。右：流程。在网页和手机环境里交互并记录，得到「截图和动作」，由它写出低层指令，再写出高层指令。图片来源：Sun 等，2024。}}
  1. 没有任务的探索。一个按规则运行的程序在 Android 模拟器里的应用和 Chrome 里的网站上，逐个尝试可以交互的元素，动作只有点击、输入、滚动三种。只有遇到输入框时才调用 GPT-4o 生成要填的内容。每次操作记下一个三元组：操作前的截图，动作，操作后的截图。
  2. 写低层指令。GPT-4o 看一个三元组，写出这一步做了什么。比如点击之后出现了一个下拉菜单，低层指令就是「点击下拉菜单显示选项」。
  3. 写高层指令。GPT-4o 再设想一个更大的任务，这一步可能是它的一部分。比如上面那一步可以属于「配置应用的设置」。
  4. 重新执行。把高层指令交给一个 GPT-4o 驱动的 agent，让它在环境里从头做一遍。这一遍的记录才是最后用来训练的运行轨迹。
  5. 打分。一个基于 GPT-4o 的轨迹奖励模型（trajectory reward model，简称 TRM）看高层指令、每一步的低层指令和最后三张截图，给整条轨迹打 1 到 5 分。5 分是任务完全做成，3 分是做成了一部分，1 分是完全失败。
  6. 按分数取样。分数用来当训练时抽样的权重：分数越高，被抽到的机会越大。分数低的轨迹也留在数据里。
{{fig 44 | 轨迹奖励模型的两个例子。上：任务是在 Broccoli 应用里把一个菜谱标成收藏，三步做完，得 5 分。下：任务是给一个日程设提醒并保存，没有做完，得 3 分，旁边标着「任务没完成，但轨迹有价值」。图片来源：Sun 等，2024。}}

第 6 步是它和别的办法不一样的地方。以前常见的做法是用一个判断函数，把没完成任务的轨迹直接丢掉。OS-Genesis 的作者认为，没完成的轨迹里也有对界面的有用探索，而且它们占的比例很大，丢掉太浪费。

「成功率接近翻倍」是和谁比

论文说用 OS-Genesis 的数据训练之后，成功率接近翻倍。下表是同一个模型 Qwen2-VL-7B 用不同的数据训练之后，在 AndroidWorld 上的任务成功率。

「接近翻倍」是从 9.82% 到 17.41%，也就是和先有指令的两种做法里成绩较好的那一种比。这种拿来作比较的对照做法叫基线（baseline）。这个提升来自整套流程，奖励模型只是其中一环。

还要注意表的最后一行：训练出来的 7B 模型，仍然低于不经训练的 GPT-4o。产生这些数据的正是 GPT-4o，论文在局限性里也写到，能构造出多少成功的轨迹，受执行任务的那个模型能力的限制。

NNetNav：边探索边检查，走不通的尽早停掉

NNetNav（Murty 等，2024）同样是先有交互，针对的是网页。它要解决的问题是：自由探索大多数时候得不到有意义的轨迹，探索得越久，浪费越多。它的办法是每隔几步就检查一次，看到目前为止的这段探索能不能对应上一个说得通的任务，对应不上就停。

{{fig 45 | 上半部分：探索策略（exploration policy，这里的策略指负责决定下一步做什么动作的那个模型）在网站上一步步操作，每隔几步由轨迹标注器写出一条指令，由奖励模型打分；右上角打叉的地方表示这次探索被停掉。右侧的方框是这次探索用的人设：一个活跃在某个论坛投资板块的投资者。下半部分：拿标注好的指令，在轨迹的每一步重新生成动作。左边一列是图里的四个角色：探索策略、轨迹标注器、结果奖励模型，以及按指令行动的策略，它们用的是同一个基础模型，配不同的 prompt。图片来源：Murty 等，2024。}}

下表逐个列出 NNetNav 的组件，一共五行。图里画了其中四个，变化摘要那一个没有单独画出来。

检查每 4 步做一次。标注器为目前这段轨迹写一条指令，奖励模型打分。得 0 分，这次探索就此结束，重新开始一次新的。得 1 分，把「这条指令加这段轨迹」存成一条示范，然后继续探索。所以一次探索可以产出好几条长度递增的示范。

提前停掉省下了不少计算。在 WebArena 的网站上，超过 60% 的探索在前 16 步之内，也就是前 4 次检查里，就被停掉了，没有走满 40 步。

这背后的想法是：一个复杂的任务做到一半时，已经做的部分本身也应该是一个说得通的小任务。

还有一步容易被忽略。探索时的动作是没有目标地做出来的，不一定是完成那条指令的好办法。所以指令定下来之后，要让模型在轨迹的每一步上，对着这条指令重新生成一次动作，训练用的是重新生成的动作。

规模和效果

一共得到 10,272 条示范，大约 10 万个「状态和动作」对，来自 20 个网站：15 个真实的在线网站，5 个自己部署的 WebArena 网站。在真实网站上探索时不登录、不提交内容。

下表是用这些示范微调 Llama-3.1-8B 之后，在两个基准测试上的成绩。

论文摘要里的说法是 WebArena 上超过 16%、WebVoyager 上 35%。从表里可以看到，这两个数来自两个不同的模型。16.3% 的那个模型，训练用的示范就出自 WebArena 基准测试所用的那几个网站，指令是生成的，没有照搬测试题。它换到真实网站上只有 28.1%。

用全部示范训练的单个模型，在 WebArena 上是 14.9%，在 WebVoyager 上是 34.1%，比 GPT-4 分别高 0.8 和 0.6 个百分点。

合成任务和环境：每个任务自带验证

前面的办法造的都是运行轨迹，更有用的是直接造环境。理由在讲两种数据的那一部分说过：有了环境，轨迹可以随时再生成，而且环境还能用来做强化学习。强化学习是让模型自己去做任务，做完之后由验证器给一个分数，这个分数叫奖励，再按奖励更新模型。

造环境要成批地造出三样东西：沙盒、任务和验证器。沙盒是一个隔离的、可以随意操作的运行环境。验证器是判断任务做成没有的程序，有了它，每个任务都带着可以验证的奖励。下面三个系统里，任务和验证器由程序和模型生成，搭沙盒这一步有的还要人参与，各节会分别说明。

下面的图和表列出这三样东西在两类 agent 上分别是什么。

对写代码的 agent 来说，沙盒就是一个 Docker 镜像。后面两节里说的「搭环境」，指的是把这个镜像做出来。

SWE-smith：往真实仓库里注入 bug

SWE-bench 式的任务是从真实的 issue 和修复它的代码改动里找出来的，能找到多少，取决于历史上有多少这样的记录。SWE-smith（Yang 等，NeurIPS 2025）反过来做：拿一个测试能通过的仓库，往里面放 bug，只要这个 bug 让原来通过的测试变成不通过，就得到了一个任务。修好它的标准是让这些测试重新通过。

{{fig 48 | 流程从左到右。真实的仓库，带着源代码和通过的单元测试。搭环境：SWE-agent 尝试安装仓库并运行测试，开发者根据它的结果写 Dockerfile。生成任务的四种策略。最后得到新的任务：环境镜像，加上合成的任务，其中有生成的 issue、带 bug 的代码改动和核实过的测试。图片来源：Yang 等，2025。}}

环境：每个仓库一个，共用

仓库选的是下载量最高的 5,000 个 Python 包里，GitHub 星数在 1,000 以上的那些，并且去掉了 SWE-bench 测试用的 12 个仓库。

每个仓库只搭一次环境，搭的时候用到 SWE-agent。SWE-agent 是一个写代码用的运行框架，也就是包在模型外面、给它工具并管理多轮对话的程序。先让一个语言模型在 SWE-agent 里尝试把仓库装好、把测试跑起来，再由人检查安装步骤，确认 80% 以上的现有测试能通过，然后做成 Docker 镜像。同一个仓库的所有任务共用这一个镜像，SWE-bench 则是每个任务一个镜像。

五种造 bug 的办法

论文把造 bug 的办法分成四种策略。其中「让语言模型生成」有 LM Modify 和 LM Rewrite 两个做法，所以下面的图和表里是五种。

{{fig 49 | 左：128 个仓库按六个类别分组，每个仓库的任务数的分布。右：五种办法各自的统计。}}

bug 留下来之后，再让语言模型根据代码改动、一个不通过的测试和测试的输出，写一份 GitHub 风格的 issue。论文里为大约 1 万个 bug 生成了 issue，花了 200 美元。实验表明，用模型写的 issue 来训练，和用人写的原始 issue 效果差不多。

人力和花费

人工方面，整个数据集用了一位作者大约 20 小时，其中估计有 18 小时用在检查 128 个仓库的安装过程上。作为对照，论文估计 SWE-bench 里 pallets/flask 这一个仓库的 11 个任务，收集时就花了大约 38 小时。

调用模型的费用一共是 1,360 美元，其中生成 bug 用了 1,000 美元，自动安装仓库用了 160 美元，生成 issue 用了 200 美元。

存储方面，全部镜像一共占 295 GB。论文估计按 SWE-bench 每个任务一个镜像的做法造 5 万个任务，需要 50 到 150 TB。

从环境到轨迹，再到模型

环境造好之后，还要有一个强的模型在里面把任务做一遍，才得到训练用的运行轨迹。论文让 Claude 3.7 Sonnet 在 SWE-agent 里去解这些任务，一共在 8,686 个任务上尝试了 17,906 次，其中 36% 成功。只留成功的轨迹，每个任务最多留 3 条，得到 5,016 条。

用这 5,016 条轨迹微调 Qwen 2.5 Coder 32B，得到的模型在 SWE-bench Verified 上每题只尝试一次，解决了 40.2%。SWE-bench Verified 是 SWE-bench 里经过人工筛选的 500 道题。

论文还比较了哪种 bug 做出的训练数据最好。做法是每种办法各取 1,000 个任务，让 Claude 3.7 Sonnet 去解，再各取 507 条成功的轨迹来微调 Qwen 2.5 Coder 7B，然后比较微调出的模型在 SWE-bench Verified 上的解决率。Combine 不在这次比较里。

PR Mirror 最好，LM Rewrite 和 Procedural 和它接近，LM Modify 比其余三种低 3 个百分点左右。也就是说，直接让语言模型「加一个 bug」得到的任务最多，训练效果却最差。

R2E-Gym：把普通的代码提交变成任务

SWE-bench 式的收集办法依赖两样人写的东西：issue 和测试。大量的代码提交两样都没有。R2E-Gym（Jain 等，COLM 2025）用语言模型把缺的补上，得到 8,135 个可以运行的任务。

  1. 找提交。找提交次数多的 Python 仓库，取出每次提交和它的代码改动，用规则和语言模型筛出小而集中的改动，比如最多改 5 个非测试文件、最多改 100 行。
  2. 搭环境。为每个留下的提交建 Docker 环境。论文说这一步是半人工的，不容易扩大。
  3. 补测试。提交自带测试的，用自带的。没有的，让语言模型看着正确的代码改动来生成测试，要求这些测试在改动之前不通过、之后通过。
  4. 反向翻译出 issue。把提交说明、代码改动和不通过的测试的输出交给语言模型，让它写出一份 issue，描述这个问题但不透露解法。这一步叫反向翻译（back-translation），因为方向和平常相反：平常是先有 issue 再有代码，这里是从代码倒推 issue。
{{fig 50 | 论文的总览图。左：用这套办法得到的可运行环境，是只靠人写的 issue 能得到的 2.5 倍以上。中：四根柱子是训练出的模型在 SWE-Bench Verified 上的四个成绩。右：和别的系统比较，上面四个是闭源模型，下面是开放权重的模型。图片来源：Jain 等，2025。}}

中间那四根柱子需要分开读，它们的跑法不同。

所以 51.0% 和 SWE-smith 的 40.2% 不能直接比。SWE-smith 的论文专门写了这一点：R2E-Gym 的 51% 是每道题尝试 26 次的结果。能直接比的是只跑一次的 34.4%。

论文也报告了挑选结果时用的测试的问题。这里说的测试，是挑选结果那一步里由模型为每道题临时写的，用来给候选的改动排序，和前面第 3 步给任务补的测试是两批。在多数题目上，这些测试里只有不到 20% 能把对的改动和错的改动分开。在一小部分题目上，最多有 10% 的测试会让错的改动通过、让对的改动不通过，把错的改动排到对的前面。

AgentScaler：把每个工具都写成对数据库的读或写

写代码的任务有测试可以当验证器。调用工具的任务（查订单、改航班、退货）靠什么来验证？AgentScaler（Fang 等，2025）的回答是：任何一次工具调用，都可以看成对背后一个数据库的读或者写。读的工具查询数据库，写的工具改变数据库的状态。这样一来，任务做得对不对，就可以通过比较数据库最后的状态来判断。

{{fig 51 | 左：模拟的用户带着一个意图和 agent 对话，比如「我能退掉这个订单吗」。中：agent 调用环境里的工具，每个工具背后都连着数据库。右：两种检查，把实际的工具调用序列和标准的序列比，把环境最后的状态和标准的状态比。图片来源：Fang 等，2025。}}
  1. 收集工具。从几个公开的工具数据集和内部的工具库里收集 3 万多个 API 的定义。
  2. 划分领域。把工具当成图上的节点，两个工具的参数相似度超过阈值就连一条边，表示它们可能互相依赖。再用社区发现算法（community detection，把图里彼此连得紧的节点分到同一组的算法）把图分成一个个领域，一共 1,000 多个。
  3. 造数据库和工具代码。对每个领域，根据其中所有工具的参数生成一个数据库的结构，再把每个工具写成一段读写这个数据库的 Python 代码。原来的那些真实服务不会被调用，环境完全是模拟的。
  4. 造任务。先生成数据库的初始状态，然后在这个领域的工具图上走一段，得到一串工具；填上参数，真的执行一遍，记下数据库最后变成了什么样。这串调用和这个最终状态就是标准答案。
  5. 模拟对话。一个模拟的用户拿着这个任务的意图和 agent 对话，agent 用工具来满足用户的要求，直到用户认为任务完成。
  6. 三道筛选。一条对话要过三道检查才留下：格式完整，数据库的最终状态和标准的一致，工具调用的序列和参数和标准的完全一致。

有了第二道检查还要第三道，是因为有的任务只用到读的工具，数据库从头到尾不会变，只比较状态分不出做对和没做。

训练出的模型在三个工具调用的基准测试上，总成绩都比各自的基础模型好，个别子项有下降。其中两个基准测试是 τ-bench 和它的后续版本 τ²-bench。τ-bench 考的是客服场景，agent 要用工具为语言模型扮演的顾客办事，下一部分会细讲。

举两个数。AgentScaler-30B-A3B 在 τ-bench 的零售任务上成功率是 70.4%，它的基础模型是 67.8%。在 τ²-bench 的电信任务上，它是 55.3%，基础模型是 26.3%。

论文同时指出，闭源的大模型在多数项目上仍然领先。论文没有给出任务和训练轨迹的数量，也没有写明扮演用户的是哪个模型。
