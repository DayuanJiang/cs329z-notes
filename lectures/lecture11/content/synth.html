先看结论

  • 运行轨迹是一次解题过程的完整记录，做题的是 agent，也就是能自己调用工具、分很多步去完成任务的语言模型系统。合成运行轨迹有两条路：先有指令，和先有交互。
  • 先有指令：从一个任务或一篇教程出发，让语言模型把步骤写出来，不真正执行（Synatra）。这样做不需要能跑的环境。Synatra 的一条数据只教下一步该做什么，这一页叫它单步样本，每个的成本是 0.031 美元，但没有任何一步在真实环境里执行过。这里的环境，指 agent 可以动手操作的应用或网站。
  • 先有交互：先在环境里没有目标地探索，再根据探索时发生了什么写出指令（OS-Genesis、NNetNav）。NNetNav 的探索由语言模型来做，写出的指令直接配给这段探索的记录。OS-Genesis 的探索由一个按规则运行的程序来做，写出指令之后再让 agent 照着指令在环境里重做一遍，用的是重做的记录。这两个系统得到的轨迹里，每一步看到的界面都是在环境里真的操作出来的，代价是要有能跑的环境，还要有模型来判断哪些探索有用。
  • 合成任务和环境更进一步：成批地造出沙盒、任务和验证器。沙盒是一个隔离的运行空间，agent 可以在里面随意操作。验证器是判断任务做成没有的程序或评分办法，它给的分数叫奖励。这样每个任务做完之后，都有验证器来判断做成没有。任务和验证器由程序和模型生成，搭沙盒这一步有的还要人参与。
  • 这一部分讲三个这样的系统。SWE-smith 往真实仓库里注入 bug，得到 50,137 个任务。R2E-Gym 把普通的代码提交变成 8,135 个任务。AgentScaler 把每个工具都写成对一个数据库的读或写，给一千多组工具各造了一个模拟的数据库，工具读写的是它，不调用真实的服务。
  • 这几个系统报告的成绩，比较的对象各不相同：有的和没训练的模型比，有的和另一种合成办法比，有的是每道题试 26 次再挑一个。读数字的时候要先看清它和谁比、怎么比。

合成运行轨迹的两条路

运行轨迹（trajectory）是一次解题过程的完整记录：任务，加上一步一步的观察和动作。观察（observation）指 agent 每一步看到的东西，在这一页里是网页的内容、界面的截图或界面元素的清单。

上一部分的两种办法，一种要请人把每个任务做一遍，另一种要有记录了人怎样完成任务的现成材料。合成的办法是：给定一个任务或者一个环境，让语言模型自己把步骤写出来或者跑出来，再用一个过滤器留下好的。讲合成运行轨迹的这几节里，环境指 agent 可以动手操作、并给它返回结果的应用或网站。

{{fig 39 | 两条路都通向运行轨迹。上：先有指令，从任务或教程出发，语言模型写出步骤但不执行，过滤器去掉无效的样本。下：先有交互，先自由探索环境，事后给这次运行配上指令，再给各次运行打分，丢弃分数低的。}}

上表把 Synatra 归到先有指令这一条路。这个归法对它用教程做的那部分数据说得通：这部分从教程出发，任务和步骤都出自教程。它用真实网页做的那部分从一张网页出发，任务、之前的动作和下一步动作都是语言模型看着网页编出来的，下一节细讲。两部分的共同点是步骤都由语言模型写出来，没有在环境里执行。

先有指令的做法有一个固有的问题：模型事先想出来的任务，在具体的环境里不一定做得成，写出来的步骤也不一定和真实的界面对得上。先有交互的做法把顺序倒过来，先看环境里能做什么，再决定任务是什么。

Synatra：把教程和网页改写成十万个单步样本，不执行任何一步

Synatra（Ou 等，NeurIPS 2024）的出发点是：网上有很多「间接的知识」，比如给人看的教程和各种网页，它们不能直接当训练数据，但可以让语言模型把它们改写成能直接用来训练 agent 的样本。

{{fig 40 | 左：间接的知识，一篇「取消 PayPal 付款」的教程和一些网页。中：合成出的任务（在 PayPal 上取消 Amazon Prime 会员）和已经做过的动作。右：当前的观察（一段网页的 HTML，其中一个元素的 id 是 156）和下一步动作（点击这个元素）。图片来源：Ou 等，2024。}}

一条样本是什么

Synatra 的一条数据是一个「状态和下一步动作」的对，每条只教下一步该做什么。这一页把它叫作单步样本，简称样本。状态包括任务、之前做过的动作和当前的观察，模型要学的是下一步动作。所以标题里的十万个样本，每个只有一步，准确数字是 99,920 个。

论文把这样的一条数据叫作示范（demonstration）。这一页把「示范」这个词留给后面的 NNetNav，那里的一条示范是一条指令加一段多步的轨迹。

交给模型的观察是文字形式的无障碍树（accessibility tree），没有截图。无障碍树是一份界面元素的清单，列出每个按钮和输入框的名称和类型。上图里的观察写的是 HTML，它和无障碍树的关系在下一小节的表后面说明。

同样从教程出发：Synatra 和 AgentTrek 的差别

上一部分的 AgentTrek 也是从教程出发的，两者正好是一组对照：一个只写不做，一个照着做一遍。

OS-Genesis：先在应用里探索，再反过来推出任务

OS-Genesis（Sun 等，2024，发表于 ACL 2025）针对的是手机和网页的图形界面。它把自己的做法叫作反向任务合成（reverse task synthesis）：先操作，再从操作的结果反推出任务。

{{fig 43 | 左：一条训练数据的样子，包括高层指令、历史和当前的界面截图、低层指令和动作。右：流程。在网页和手机环境里交互并记录，得到「截图和动作」，由它写出低层指令，再写出高层指令。图片来源：Sun 等，2024。}}
  1. 没有任务的探索。一个按规则运行的程序在 Android 模拟器里的应用和 Chrome 里的网站上，逐个尝试可以交互的元素，动作只有点击、输入、滚动三种。只有遇到输入框时才调用 GPT-4o 生成要填的内容。每次操作记下一个三元组：操作前的截图，动作，操作后的截图。
  2. 写低层指令。GPT-4o 看一个三元组，写出这一步做了什么。比如点击之后出现了一个下拉菜单，低层指令就是「点击下拉菜单显示选项」。
  3. 写高层指令。GPT-4o 再设想一个更大的任务，这一步可能是它的一部分。比如上面那一步可以属于「配置应用的设置」。
  4. 重新执行。把高层指令交给一个 GPT-4o 驱动的 agent，让它在环境里从头做一遍。这个 agent 每做一步，除了给出动作，还写下这一步要做什么，这句话是这条轨迹里这一步的低层指令，和第 2 步给探索的三元组写的低层指令是两批。这一遍的记录才是最后用来训练的运行轨迹。
  5. 打分。一个基于 GPT-4o 的轨迹奖励模型（trajectory reward model，简称 TRM）看高层指令、第 4 步的轨迹里每一步的低层指令和最后三张截图，给整条轨迹打 1 到 5 分。5 分是任务完全做成，3 分是做成了一部分，1 分是完全失败。
  6. 按分数取样。分数决定训练时每条轨迹被抽到的机会：分数越高，被抽到的机会越大。分数低的轨迹也留在数据里。
{{fig 44 | 轨迹奖励模型的两个例子。上：任务是在 Broccoli 应用里把一个菜谱标成收藏，三步做完，得 5 分。下：任务是给一个日程设提醒并保存，没有做完，得 3 分，旁边标着「任务没完成，但轨迹有价值」。图片来源：Sun 等，2024。}}

第 6 步是它和别的办法不一样的地方。以前常见的做法是用一个判断函数，把没完成任务的轨迹直接丢掉。OS-Genesis 的作者认为，没完成的轨迹里也有对界面的有用探索，而且它们占的比例很大，丢掉太浪费。

「成功率接近翻倍」是和谁比

论文说用 OS-Genesis 的数据训练之后，成功率接近翻倍。下表是同一个模型 Qwen2-VL-7B 用不同的数据训练之后，在 AndroidWorld 上的任务成功率。

表里拿来作比较的是两种先定任务的做法，论文叫 task-driven，都是论文作者自己搭的。第一种是给 GPT-4o 看应用或网页的起始截图和几个任务的例子，让它写出高层指令，再照着指令在环境里操作，把过程收集成轨迹。第二种在第一种的基础上，让 GPT-4o 参照已有的指令再多写出一批高层指令，所以轨迹的条数多一些。

先定任务的做法和本页开头说的先有指令有一处相同、一处不同。相同的是指令在前、步骤在后。不同的是这里的步骤在环境里真的执行了，Synatra 那样的先有指令只把步骤写出来，不执行。

「接近翻倍」是从 9.82% 到 17.41%。9.82% 是先定任务的第二种做法的成绩。两种先定任务的做法里，第二种的成绩较好，它用了 1,500 条轨迹，比 OS-Genesis 的 1,000 条多。这种拿来作比较的对照做法叫基线（baseline）。这个提升来自整套流程，奖励模型只是其中一环。

还要注意表的最后一行：训练出来的 7B 模型，仍然低于没有用这些数据训练过的 GPT-4o。产生这些数据的正是 GPT-4o，论文在局限性里也写到，能构造出多少成功的轨迹，受执行任务的那个模型能力的限制。

NNetNav：边探索边检查，对应不上任务的探索尽早停掉

NNetNav（Murty 等，2024）同样是先有交互，针对的是网页。它要解决的问题是：自由探索大多数时候得不到有意义的轨迹，探索得越久，浪费越多。它的办法是每隔几步就检查一次，看到目前为止的这段探索能不能对应上一个说得通的任务，对应不上就停。

{{fig 45 | 上半部分：探索策略（exploration policy）在网站上一步步操作，每隔几步由轨迹标注器写出一条指令，由奖励模型打分。这里的策略指负责决定下一步做什么动作的那个模型。右上角打叉的地方表示这次探索被停掉。右侧的方框是这次探索用的人设：一个活跃在某个论坛投资板块的投资者。下半部分：拿标注好的指令，在轨迹的每一步重新生成动作。左边一列是图里的四个角色：探索策略、轨迹标注器、结果奖励模型，以及按指令行动的策略，它们用的是同一个语言模型，配不同的 prompt。图片来源：Murty 等，2024。}}

下表逐个列出 NNetNav 的组件，一共五行。图里画了其中四个，变化摘要那一个没有单独画出来。

检查每 4 步做一次。标注器为目前这段轨迹写一条指令，奖励模型打分。得 0 分，这次探索就此结束，重新开始一次新的。得 1 分，把「这条指令加这段轨迹」存成一条示范，然后继续探索。所以一次探索可以产出好几条长度递增的示范。NNetNav 的一条示范是一段多步的轨迹，和 Synatra 一条只有一步的样本是两种单位。

提前停掉省下了不少计算。在 WebArena 的网站上，超过 60% 的探索在前 16 步之内，也就是前 4 次检查里，就被停掉了，没有走满 40 步。

这背后的想法是：一个复杂的任务做到一半时，已经做的部分本身也应该是一个说得通的小任务。

还有一步容易被忽略。探索时的动作是没有目标地做出来的，不一定是完成那条指令的好办法。所以指令定下来之后，要给轨迹的每一步换一个动作：把这条指令和探索时这一步看到的网页交给模型，让它写出此时该做的动作。训练用的是这个新写的动作，网页仍是探索时真的操作出来的那些。

新写的动作可能和探索时实际做的动作不同。论文没有写新的动作有没有再执行一遍，也没有写两者不同时轨迹里后面的网页怎么处理。

合成任务和环境：每个任务自带验证

前面的办法造的都是运行轨迹，更有用的是直接造环境。从这一节起，环境指沙盒、任务和验证器三样合在一起。前面几节说的环境是 agent 动手操作的应用或网站，在这三样里对应沙盒。

造环境更有用的理由在第二部分说过：有了环境，轨迹可以随时再生成，而且环境还能用来做强化学习。强化学习是让模型自己去做任务，做完之后由验证器给一个分数，这个分数叫奖励，再按奖励更新模型。

造环境要成批地造出沙盒、任务和验证器这三样东西。沙盒是一个隔离的运行空间，agent 可以在里面随意操作。验证器是判断任务做成没有的程序或评分办法，有了它，每个任务做完之后都能检查做成没有，检查的结果就是奖励。

下面三个系统里，任务和验证器由程序和模型生成。搭沙盒这一步，SWE-smith 和 R2E-Gym 还要人参与，AgentScaler 的论文说是自动完成的，各节会分别说明。

下面的图和表列出这三样东西在两类 agent 上分别是什么。表里的 issue，指代码仓库的使用者提交的问题报告。PR 是 pull request 的缩写，意思是合并请求。

{{fig 47 | 环境的三样东西，在两类 agent 上分别是什么。图上第一行写的 Environment，指的是三样里的沙盒。}}

对写代码的 agent 来说，沙盒就是一个 Docker 镜像。后面两节里说的搭沙盒，指的是把这个镜像做出来。

SWE-smith：往真实仓库里注入 bug

SWE-bench 是让模型修复真实代码仓库里问题的基准测试。SWE-bench 式的任务是从真实的 issue 和修复它的代码改动里找出来的，能找到多少，取决于历史上有多少这样的记录。SWE-smith（Yang 等，NeurIPS 2025）反过来做：拿一个测试能通过的仓库，往里面放 bug，只要这个 bug 让原来通过的测试变成不通过，就得到了一个任务。修好它的标准是让这些测试重新通过。

{{fig 48 | 流程从左到右分四栏。第一栏是一个真实的仓库，带着源代码和能通过的单元测试。第二栏是搭沙盒，图上写的是 Environment Creation：SWE-agent 这个运行框架尝试安装仓库并运行测试，开发者根据它的结果写 Dockerfile，也就是构建 Docker 镜像用的配置文件。第三栏列出生成任务的四种策略。第四栏是得到的新任务：一个沙盒的镜像（图上写的是 Environment Image），加上合成的任务，其中有生成的 issue、带 bug 的代码改动和核实过的测试。图片来源：Yang 等，2025。}}

沙盒：每个仓库只搭一个，这个仓库的所有任务共用

仓库选的是下载量最高的 5,000 个 Python 包里，GitHub 星数在 1,000 以上的那些，并且去掉了 SWE-bench 测试用的 12 个仓库。

每个仓库只搭一次沙盒，搭的时候用到 SWE-agent。SWE-agent 是一个写代码用的运行框架。先让一个语言模型在 SWE-agent 里尝试把仓库装好、把测试跑起来，再由人检查安装步骤，确认 80% 以上的现有测试能通过，然后做成 Docker 镜像。同一个仓库的所有任务共用这一个镜像，SWE-bench 则是每个任务一个镜像。

论文把造 bug 的办法分成四种策略。其中「让语言模型生成」有 LM Modify 和 LM Rewrite 两个做法，所以下面的图和表里是五种。

bug 留下来之后，再让语言模型根据代码改动、一个不通过的测试和测试的输出，写一份 GitHub 风格的 issue，当作任务的描述。论文给出的花费是为大约 1 万个 bug 生成 issue 用了 200 美元。上表里的任务数 50,137 是留下来的 bug 的总数，其余的 bug 有没有生成 issue，论文没有写明。模型写的 issue 用来训练效果如何，这一节最后有一个对照。

人力和花费

人工方面，整个数据集用了一位作者大约 20 小时，其中估计有 18 小时用在检查 128 个仓库的安装过程上。作为对照，论文估计 SWE-bench 里 pallets/flask 这一个仓库的 11 个任务，收集时就花了大约 38 小时。

调用模型的费用一共是 1,360 美元，其中生成 bug 用了 1,000 美元，自动安装仓库用了 160 美元，生成 issue 用了 200 美元。

存储方面，全部镜像一共占 295 GB。论文估计按 SWE-bench 每个任务一个镜像的做法造 5 万个任务，需要 50 到 150 TB。

从环境到轨迹，再到模型

环境造好之后，还要有一个强的模型在里面把任务做一遍，才得到训练用的运行轨迹。论文让 Claude 3.7 Sonnet 在 SWE-agent 里去解这些任务，一共在 8,686 个任务上尝试了 17,906 次，其中 36% 成功。只留成功的轨迹，每个任务最多留 3 条，得到 5,016 条。

用这 5,016 条轨迹微调 Qwen2.5-Coder-32B，得到的模型在 SWE-bench Verified 上每题只尝试一次，解决了 40.2%。SWE-bench Verified 是 SWE-bench 里经过人工筛选的 500 道题。

论文还比较了哪种 bug 做出的训练数据最好。做法是每种办法各取 1,000 个任务，让 Claude 3.7 Sonnet 去解，再各取 507 条成功的轨迹来微调 Qwen2.5-Coder-7B，然后比较微调出的模型在 SWE-bench Verified 上的解决率。Combine 不在这次比较里。

按表里的数，PR Mirror 最高，LM Rewrite 和 Procedural 比它低 0.4 和 0.6 个百分点。这点差距小于表注里说的浮动范围，前三种分不出高下。LM Modify 比其余三种低 3 个百分点左右，这个差距大约是浮动范围的两倍。论文的结论是 PR Mirror 的效果最好，LM Rewrite 和 Procedural 和它相当，LM Modify 明显更低。也就是说，直接让语言模型「加一个 bug」得到的任务最多，在这次比较里解决率却排在最后。

论文用类似的做法比较了任务描述的几种写法，其中两种是模型写的 issue 和人写的 issue。它取 600 个用 PR Mirror 造的任务。PR Mirror 的任务来自真实的 PR，有的 PR 原本就关联着人写的 issue。任务描述用模型写的 issue 时，微调出的模型在 SWE-bench Verified 上的解决率是 7.7%。用 PR 原来关联的、人写的 issue 时是 7.8%。两者差不多。

R2E-Gym：把普通的代码提交变成任务

SWE-bench 式的收集办法依赖两样人写的东西：issue 和测试。大量的代码提交两样都没有。R2E-Gym（Jain 等，COLM 2025）用语言模型把缺的补上，得到 8,135 个可以运行的任务。

  1. 找提交。找提交次数多的 Python 仓库，取出每次提交和它的代码改动，用规则和语言模型筛出小而集中的改动，比如最多改 5 个非测试文件、最多改 100 行。
  2. 搭沙盒。为每个留下的提交建一个 Docker 镜像。论文说这一步是半人工的，不容易扩大。
  3. 补测试。提交自带测试的，用自带的。没有的，让语言模型看着正确的代码改动来生成测试，要求这些测试在改动之前不通过、之后通过。
  4. 反向翻译出 issue。把提交说明、代码改动和不通过的测试的输出交给语言模型，让它写出一份 issue，描述这个问题但不透露解法。这一步叫反向翻译（back-translation），因为方向和平常相反：平常是先有 issue 再有代码，这里是从代码倒推 issue。
{{fig 50 | 论文的总览图。左：用这套办法得到的可以运行的任务，是只靠人写的 issue 能得到的 2.5 倍以上，图上把它们叫作 Executable Training Environments。中：四根柱子是训练出的模型在 SWE-bench Verified 上的四个成绩。右：和别的系统比较，上面四个是闭源模型，下面是开放权重的模型，也就是把权重公开出来、谁都可以下载的模型。权重是模型里通过训练得到的那些数值。图片来源：Jain 等，2025。}}

中间那四根柱子需要分开读。四个成绩的测法不同，差别在每道题跑几次，以及怎样从多次的结果里挑一个交上去。

负责挑选的有两个：一个不运行代码的模型，和一个会写测试、运行测试的 agent。论文把它们也叫 verifier。它们是在测试时从多个候选结果里挑一个，和前面说的验证器是两回事，验证器是每个任务自带的、判断任务做成没有的测试。下面把它们叫作挑选用的模型和挑选用的 agent。

所以 51.0% 和 SWE-smith 的 40.2% 不能直接比。SWE-smith 的论文专门写了这一点：R2E-Gym 的 51% 是每道题尝试 26 次的结果。能直接比的是只跑一次的 34.4%。

论文也报告了挑选结果时用的测试的问题。这里说的测试，是挑选结果那一步里由模型为每道题临时写的，用来给候选的改动排序，和前面第 3 步给任务补的测试是两批。在多数题目上，这些测试里只有不到 20% 能把对的改动和错的改动分开。在一小部分题目上，最多有 10% 的测试会让错的改动通过、让对的改动不通过，把错的改动排到对的前面。

AgentScaler：把每个工具都写成对数据库的读或写

写代码的任务有测试可以当验证器。调用工具的任务（查订单、改航班、退货）靠什么来验证？AgentScaler（Fang 等，2025）的回答是：任何一次工具调用，都可以看成对背后一个数据库的读或者写。读的工具查询数据库，写的工具改变数据库的状态。这样一来，任务做得对不对，就可以通过比较数据库最后的状态来判断。

{{fig 51 | 左：模拟的用户带着一个意图和 agent 对话，比如「我能退掉这个订单吗」。中：agent 调用环境里的工具，每个工具背后都连着数据库。右：两种检查，把实际的工具调用序列和标准的序列比，把环境最后的状态和标准的状态比。图片来源：Fang 等，2025。}}
  1. 收集工具。从几个公开的工具数据集和内部的工具库里收集 3 万多个 API 的定义。
  2. 把工具分组。把工具当成图上的节点，两个工具的参数相似度超过阈值就连一条边，表示它们可能互相依赖。再用社区发现算法（community detection，把图里彼此连得紧的节点分到同一组的算法）把图分成一组一组的工具，一共 1,000 多组。论文把每一组叫作一个领域（domain）。这一讲里的领域另指网页、操作电脑、代码、工具调用这四类 agent 任务，所以这一页把论文说的领域叫作工具组。
  3. 造数据库和工具代码。对每个工具组，根据其中所有工具的参数生成一个数据库的结构，再把每个工具写成一段读写这个数据库的 Python 代码。原来的那些真实服务不会被调用。工具的代码是真的会执行的，它读写的是这个专门造出来的数据库，也就是前面说的模拟的数据库。论文把这样搭出来的环境叫作完全模拟的环境（fully simulated environments），把从收集工具到这一步的过程叫作环境的自动构建（Environment Automatic Build），没有写明生成数据库结构和工具代码用的是哪个模型。
  4. 造任务。先生成数据库的初始状态，然后在这个工具组的工具图上随机选一个工具当起点，沿着边一步一步走下去，经过的工具连成一串。再给这串工具填上参数，真的执行一遍，记下数据库最后变成了什么样。这串调用和这个最终状态就是标准答案。
  5. 模拟对话。一个模拟的用户拿着这个任务的意图和 agent 对话，agent 用工具来满足用户的要求，直到用户认为任务完成。
  6. 三道筛选。一条对话要过三道检查才留下：格式完整，数据库的最终状态和标准的一致，工具调用的序列和参数和标准的完全一致。

有了第二道检查还要第三道，是因为有的任务只用到读的工具，数据库从头到尾不会变，只比较状态分不出做对和没做。

训练出的模型在三个工具调用的基准测试上，总成绩都比各自的基础模型好，个别子项有下降。其中两个基准测试是 τ-bench 和它的后续版本 τ²-bench。τ-bench 考的是客服场景，agent 要用工具为语言模型扮演的顾客办事，下一部分会细讲。

举两个数，都出自 AgentScaler-30B-A3B 这个模型。它是用 Qwen3-Thinking-30B-A3B 微调出来的，名字的后半段沿用了基础模型的名字。在 τ-bench 的零售任务上，它的成功率是 70.4%，基础模型 Qwen3-Thinking-30B-A3B 是 67.8%。在 τ²-bench 的电信任务上，它是 55.3%，基础模型是 26.3%。

论文同时指出，闭源的大模型在多数项目上仍然领先。论文没有给出任务和训练轨迹的数量，也没有写明扮演用户的是哪个模型。

i
这里已经用到了模拟的用户。AgentScaler 的第 5 步让一个语言模型来扮演用户。第三部分把 agent 数据的来源分成五种，这是其中最后一种「模拟的用户和环境」的做法，下一部分专门讲。几种来源在实际系统里经常是组合起来用的。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • Synatra 摘要里的 3%。按每条样本 0.031 美元和 Mind2Web 每条人工轨迹 0.8 美元这两个数算，比例是 3.9%，摘要写的是 3%。出处：Ou 等，2024。
  • Synatra 微调的模型的名字。论文讲训练设置时写的是 CodeLlama-7b，引言里写的是 7B 的 CodeLlama-instruct，成绩表和结果一节写的是 CodeLlama-instruct-7b，并把它称作微调出的模型的基础模型。这一页把它们当作同一个模型，统一写成 CodeLlama-7B。出处：Ou 等，2024。
  • Mind2Web 每条轨迹有多少步。Synatra 的论文说，它把 Mind2Web 训练集里大约 1 千条人工轨迹处理成了 9 千个单步样本，折合每条大约 9 步。Mind2Web 的论文给出的是每个任务平均 7.3 个动作。Synatra 的论文没有说明这 9 千个样本是怎样拆出来的，正文里每步 0.089 美元和 35% 这两个估算用的是 Synatra 论文自己的数。出处：Ou 等，2024；Deng 等，2023。
  • SWE-smith 五种办法的表里，合计一行的成本。论文没有说明合计一行的 2.32 美分是怎样平均出来的。按生成 bug 的总花费 1,000 美元和 50,137 个任务粗略估算，每个留下的任务摊到的生成成本大约是 2 美分。出处：Yang 等，2025 的表 1。
  • R2E-Gym 的任务从哪个代码版本开始。「合成任务和环境」一节的表里说，任务的起点是这次提交之前的代码。这句话是按论文写的做法推出来的：论文要求验证用的测试在提交之前带 bug 的版本上不通过，在提交之后的版本上通过，生成测试时把这次提交的代码改动当作标准答案。论文没有单独写明任务从哪个版本开始。出处：Jain 等，2025。
