先看结论

  • 语言模型可以顶替用户，可以顶替环境，也可以两样都顶替。这样 agent 不需要真人，也不需要真实的系统，就能无限次地练习。
  • 模拟用户：τ-bench 让一个语言模型扮演来找客服的顾客，agent 用工具办事，最后检查数据库的状态和回复的内容。APIGen-MT 在同样的环境里，先由几个语言模型把任务和标准答案审好，再让模拟的用户和 agent 对话，把每个任务变成一条多轮的运行轨迹。
  • 模拟环境：DreamGym 训练一个语言模型来预测「这个动作之后，下一个状态是什么、奖励是多少」，用它代替真实环境来做强化学习。强化学习是让 agent 自己去做任务，做完之后得到一个分数，这个分数叫奖励，再按奖励更新模型。
  • 代价是模拟器的错误也会被学进去。模拟的用户会说错话，模拟的环境会预测错，agent 分不出哪些是真实世界的规律，哪些是模拟器的错误。
  • 五种来源放在一起看：越便宜、越容易做大的来源，离真实的人和真实的系统越远。实际的系统通常把几种组合起来用。

τ-bench：让语言模型扮演来找客服的顾客

τ-bench（Yao 等，2024，发表于 ICLR 2025）本身是一个基准测试（benchmark，一套固定的题目，用来给模型打分）。论文把它当作评估工具来做，任务数量有意做得很少，全部由人工编写和核对。它出现在这里，是因为它定下的这套做法后来被直接拿去造训练数据：用语言模型扮演用户，用真的工具和数据库，用数据库的最终状态来验证。下面的 APIGen-MT 就是在 τ-bench 的两个环境里生成数据的，上一部分的 AgentScaler 也沿用了同样的设计。

τ-bench 模拟的是客服场景，有零售和航空两个领域。agent 是客服，可以使用一组 API 工具，要遵守一份业务规定。顾客由一个语言模型扮演。背后是一个数据库，里面有用户、订单或者航班。

{{fig 54 | 左：τ-bench 的三个部分。agent 可以调用工具读写数据库，系统 prompt 里是业务规定，比如基础经济舱不能改签。用户由语言模型扮演，它的系统 prompt 里写着这个顾客是谁、想办什么、办不成的时候怎么办。右：航空领域的一段对话。顾客要改航班，agent 查了订单，发现是基础经济舱不能改，但订票不满 24 小时可以取消，问顾客要不要取消重订，顾客同意后 agent 调用工具取消了订单，数据库被改写。图片来源：Yao 等，2024。}}

τ-bench 还提出了一个衡量稳定性的指标 pass^k：同一个任务独立跑 k 次，k 次全部成功的概率，再对所有任务取平均。它和常见的 pass@k 相反，pass@k 是 k 次里有一次成功就算。

需要这个指标，是因为用户是语言模型扮演的，每次说的话不完全一样，同一个任务跑几次的结果会不同。gpt-4o 在零售任务上单次成功率超过 60%，但 8 次全部成功的比例不到 25%。

模拟的用户会出什么错

τ-bench 的论文列了模拟用户的几种问题：给它的指令里可能有错字或歧义，指令里不一定包含办这件事需要的全部知识，扮演用户的模型在推理、计算、记住长对话、严格照指令行事这些方面能力有限。

这些问题在失败的例子里占的比例不大。作者人工检查了 gpt-4o 在零售任务上失败的 40 个例子，其中 4 个的原因出在用户的指令上，其余 36 个是 agent 自己的问题。

i
评分办法里后来也查出了问题。拿 τ-bench 这样的环境直接做训练，「什么都不做」在相当一部分任务上也能拿到奖励。这是从 Zhu 等人 2025 年论文的发现推出来的：一个什么都不做、只返回空回答的 agent，在航空任务上能拿到 38%。原因是航空任务里有 38% 是有意设计成办不成的，比如改签一张不能改的票，这些任务的成功标准就是数据库没有被改动。第 13 讲会讲到这件事。出处：Zhu 等，2025。

APIGen-MT：先把任务审好，再让模拟的用户把它演成对话

APIGen-MT（Prabhakar 等，NeurIPS 2025）要造的是多轮对话的训练数据。让语言模型一次生成整段对话很容易出错。中间任何一步出了差错，整段对话就不能用了。每一轮说什么，又取决于前面调用了什么工具、返回了什么。所以它分成两个阶段：先把任务和标准答案审好，再让模拟的用户和 agent 把任务演成对话。

{{fig 55 | 第一阶段：生成任务和标准答案。数据生成器根据 API、规定和领域数据提出一个任务；先过格式和执行检查，再由评审委员会的几个模型投票；不通过的，由反馈生成器汇总原因、写出改进计划，交回生成器重做。通过的任务包括任务意图和标准答案。图片来源：Prabhakar 等，2025。}}

第一阶段：审出一份任务蓝图

一份蓝图包含三样：给用户的指令，一串可以验证的标准动作，以及预期的最终输出。

  1. 一个语言模型根据抽样出来的 API、业务规定、领域数据和用户人设，提出一个任务。标准动作围绕会改写数据库的 API 来构造，办法是在 API 的依赖关系图上随机走一段。这张图把每个 API 当成一个节点，一个 API 的输入要用到另一个 API 的输出时，就从后者到前者连一条边。
  2. 规则检查：动作的格式要对，要能在环境里真的执行。业务规定被写成了 Python 的单元测试，标准动作不能违反。
  3. 评审委员会：几个语言模型从正确、完整、合理等方面给任务打分，按多数票决定通过与否。
  4. 不通过的任务，由一个反馈生成器汇总失败的原因和评审意见，写成一份改进计划，交回第 1 步重做。

有这个反馈循环时，任务的通过率是 70%，没有时是 28%。

第二阶段：模拟的用户和 agent 把蓝图演成对话

蓝图审好之后，由模拟的用户和 agent 把它演成一段对话，过程见下图。

{{fig 56 | 第二阶段：一个模拟的人拿着任务意图，一点一点地向被测的 agent 提要求；agent 在带有可执行 API 的模拟环境里调用工具。最后把这次交互的结果和标准的动作、输出比较，一致的才算成功的轨迹。图片来源：Prabhakar 等，2025。}}

一个语言模型扮演用户，把任务的要求一点一点说出来。agent 这一边是 gpt-4o，它理解用户的意图，调用工具把事情办完。只有环境的最终状态和标准动作的结果一致、agent 最后的回复和预期输出一致的轨迹才留下。每个任务最多试三次，这一阶段的成功率是 67%。

为了让模拟的用户更稳定，每一轮让它生成 4 个候选的回复，再让模型自己找出这些候选的问题，选出一个。

DreamGym：让语言模型来预测下一个状态和奖励

强化学习是让 agent 反复做任务：每做一步看到环境的新状态，任务做成了得到奖励，再按奖励更新模型。在真实环境里做强化学习很贵：每一步都要真的打开网页、真的执行动作，环境不容易重置，奖励也常常很稀少。

DreamGym（Chen 等，2025，发表于 ICLR 2026）的做法是训练一个语言模型来充当环境。agent 发出一个动作，这个「经验模型」用文字写出下一个状态和奖励，agent 再根据它继续。

{{fig 57 | 左上：传统的做法，agent 在真实环境里行动，任务稀少而且昂贵，环境不容易扩大，奖励稀疏而且不稳定。左下：用经验模型代替真实环境。右：系统的结构。agent 的动作交给经验模型，经验模型先推理，再给出下一个状态和奖励；它可以从经验回放缓冲区（一个存放过往交互记录的库）里检索相似的经验；任务生成器根据哪些任务 agent 有时成功有时失败，生成更难的任务变体。图片来源：Chen 等，2025。}}

这个设计背后的判断是：训练 agent 要的是足够多样、信息量足够、因果关系说得通的交互数据，环境不必完全逼真。

它并没有完全离开真实数据

经验模型本身要用真实的轨迹来训练。以 WebArena 为例，用了 4,800 条从真实环境里收集的轨迹，由一个强的语言模型给每一步补上「为什么这个动作会导致这个结果」的推理，再拿来微调经验模型。

训练 agent 时也可以再接上一段真实的交互。论文用了三个基准测试：WebArena、WebShop 和 ALFWorld。WebShop 是一个模拟购物网站的环境，agent 要搜索并找到符合要求的商品。ALFWorld 是一个用文字操作的家居任务环境。对下表里的这个 agent（Llama-3.1-8B）来说，在 WebShop 和 ALFWorld 上成绩最好的版本，是先在合成的经验上训练，再用 5 千步真实的交互接着训练。下面的表里有 WebArena 和 WebShop 两列，没有 ALFWorld。

经验模型预测错了怎么办

对这个问题，论文给出的是一个理论上的保证和两样间接的证据。

理论上的保证在论文附录里，是一个下界，也就是「至少有这么多」的保证。在论文设定的条件下，agent 在真实环境里的进步，至少是它在合成环境里的进步减去两项。

第一项和每次更新的幅度有关。训练算法会给模型的行为一次最多改变多少设一个上限。按论文的公式，这一项和这个上限成正比：上限放得越宽，要减掉的就越多。

第二项和经验模型的误差有关，这个误差由两部分组成：奖励预测的误差，和状态转移的误差。状态转移的误差指经验模型预测的下一个状态和真实环境会给出的下一个状态之间的差别。

合成环境里的进步超过这两项之和，真实环境里的表现才有保证不变差。

作者认为奖励和状态转移这两项误差可以做得很小。论文里和它有关的证据有两样：用 GPT-4o 给 100 条生成的轨迹打分的结果，以及最后的任务成功率。这两样都是间接的证据，经验模型预测的状态和奖励同真实环境不一致的比例有多高，没有直接的数。

论文也写了适用范围的限制，说的是把在一个环境的合成经验上训练出的 agent 拿到另一个环境里去用。在 WebShop 和 WebArena 这两个网页环境之间这样换，成绩比直接在目标环境上做监督微调（让模型模仿现成的示范）的模型还高。从这两个网页环境换到差别很大的家居任务环境 ALFWorld，效果明显下降。

这和前面说的 ALFWorld 上成绩最好的版本是两件事。那个版本是在 ALFWorld 自己的任务上训练的，这里说的是在网页环境上训练、拿到 ALFWorld 上去用。

五种来源放在一起

对每种来源，都可以问三个问题：花多少钱，离真实多近，能做到多大。下面把第三到第五部分的内容汇总成一张表。表里的验证器，指判断任务做成没有的程序。

不同的领域适合不同的来源。代码有测试和版本历史，天然适合从 GitHub 提取和注入 bug。网页和桌面操作没有现成的验证器，所以大量依赖语言模型来判断轨迹的好坏。客服这类工具调用的任务离不开用户，所以要模拟用户。

实际的系统往往把几种来源接在一起，下面是三个例子。VideoAgentTrek 用逆动力学模型（inverse dynamics model，看着前后画面的变化反推出鼠标和键盘动作的模型）从视频里标出动作，而训练这个模型要用人工录制的数据：用 OpenCUA 的录制工具录下的、同时带有真实鼠标和键盘记录的视频。AgentScaler 合成了环境，又用模拟的用户来产生对话。SWE-smith 造出环境之后，要让一个强的模型在里面跑，才得到训练用的运行轨迹。

+
还有一种来源：产品上线之后的使用记录。这一讲讲的是训练模型用的数据。对用现成模型搭应用的人来说，最容易拿到的数据是自己产品的运行记录。Shreya Shankar 2024 年的文章《Data Flywheels for LLM Applications》讲的就是怎样用这些记录。她的出发点是很多团队用的是模型的 API，不去微调，所以改进主要靠把修正过的记录当作示例放进 prompt。文章里的 data flywheel 指这样一个循环：应用在真实使用中产生记录，人和程序给这些记录打分，分数低的被修正，修正过的例子再放回 prompt 或用来改进系统，这样每一条使用记录都可以用来改进应用。她把这个循环分成三部分：定义评估指标，持续监控这些指标是否还和人的判断一致，以及用评估的结果不断改进。出处：Shankar，2024。
+
延伸阅读：用语言模型标注和合成数据的综述。Tan 等人 2024 年的综述《Large Language Models for Data Annotation and Synthesis: A Survey》梳理了怎样用语言模型来标注和合成数据、怎样评估这些标注的质量、怎样使用它们。它和这一讲的关系可以这样看：上面的表里，第二到第四种来源让语言模型改写材料、写指令、给轨迹打分，做的也是用语言模型标注和合成数据。出处：Tan 等，EMNLP 2024。

这一部分的小结

  • 模拟的用户让多轮对话的任务可以大规模地生成和验证。它的前提是工具和数据库是真的程序，所以最后的状态可以检查。
  • 模拟的环境把强化学习阶段的真实交互也省掉了，经验模型本身仍要用真实的轨迹来训练。换来的是无限的练习，付出的是预测可能不准。
  • 五种来源各有适合的领域，实际中常常组合使用。
