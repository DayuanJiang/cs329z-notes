先看结论

  • 做软件有两种办法。演绎式：人写规则，程序把规则用到新的输入上。归纳式：人给出输入和期望的输出，由训练过程找出规则。传统软件工程是前一种，机器学习是后一种。
  • 演绎式的软件，原则上可以靠读代码推出它会做什么。归纳式的产物，对不对只能靠在例子上测量。
  • 模型是从数据里学出来的。agent（能自己调用工具、分很多步完成任务的语言模型系统）是靠评估调出来的，也就是每次改动之后，都要拿一批任务去测、给结果打分，才知道是变好还是变坏。越来越多的软件是 agent 生成的。这三层都在变成归纳式，所以评估成了开发流程的中心。
  • 对 agent 来说，训练数据和测试数据是同一种东西：一个个任务。每个任务有任务说明、一个可以动手的环境，和一个判断结果的验证器。

写程序的三个阶段：人写的东西离机器越来越远

今天用 agent 写软件，人写的是一段任务说明，代码由 agent 生成。这是同一个方向上的又一步：在它之前，写程序的方式已经经过三个阶段，每往后一个阶段，人写的东西离机器的指令更远，离人的想法更近。下表用同一件事「把一个数加 5」在三个年代的三种写法来说明。

用 agent 写软件这一步，和前三个阶段有一个根本的区别。下一节先用一个例子看这个区别，再往后的两节说明它。

+
延伸：前几次换阶段时有人抵触。高级语言 FORTRAN 的主要设计者 John Backus 在 1976 年回忆 1950 年代时说，当时很多程序员把自己看作掌握着一门技艺的神职人员，认为这门技艺复杂到普通人学不会。凡是想让更多人也能编程的系统，他们都抱着敌意和嘲笑。出处：Backus 的演讲《Programming in America in the 1950s》的摘录。
+
延伸：也有人过分乐观。IBM 在 1954 年写的 FORTRAN 初步报告里有一句话：FORTRAN 应该能基本消除编码和调试，所以解决一个问题的成本可以降到原来的一半以下。七十多年过去，编码的方式变了很多次，调试一直都在。

两个版本各有各的错法。规则的版本会漏掉规则没写到的格式，或者只取出号码的一部分。模型的版本可能在某些输入上取错，或者在号码之外多输出一些文字。区别在于怎么发现这些错：前一种可以靠读，后一种只能靠测。

按多数标准，调用模型的版本更好用，因为它适用的范围更广。代价是可预测性。同一段输入跑一百万次，规则的版本每次输出什么，事先就能说出来。模型的版本在这样简单的任务上很可能几乎每次都一样，但没有人能保证。交给模型的任务越难，它的输出越难预料。

演绎式：人写规则，对不对可以读出来

机器码、汇编语言、高级语言这三个阶段，和上面例子里用规则写的版本，有一个共同点：规则是人写的。程序做的事是把这些规则用到新的输入上，得到输出。这种做软件的办法可以叫演绎式。

演绎式的软件有一个很强的性质。Tony Hoare 在 1969 年的论文《An Axiomatic Basis for Computer Programming》开头这样说：计算机编程是一门精确的科学，一个程序的所有性质，以及它在任何给定环境里运行的所有后果，原则上都可以只凭程序的文本，用纯粹的演绎推理得出来。

换成日常的话：原则上，想知道一段代码会做什么，读它就能推出来，不必运行。代码评审、静态检查和形式化验证都建立在这一点上。代码评审是人读代码，静态检查是让工具在不运行程序的情况下检查代码，形式化验证是用数学方法证明程序符合写明的要求。

传统的软件开发流程也是按这个性质排的：先写规格说明（specification，用文字或文档写明软件应该做什么），再实现，再测试，再上线。写代码的人读得懂自己写的东西，每一步都知道自己做了什么，所以测试排在实现之后，用来确认代码做到了规格说明写的事。实际的软件开发里，读代码和跑测试是一起用的。

在这个流程里，规格说明是起点。软件实际会做什么，最后以代码为准。

归纳式：人给例子，对不对只能测出来

机器学习把方向反了过来。人提供的是输入和期望的输出，也就是数据和标注，规则由训练过程从例子里找出来，找出来的规则就是模型。这种办法可以叫归纳式。上面例子里被调用的语言模型就是这样来的。

对这种靠数据找规则的办法，有过一个很绝对的说法：数据足够多的时候，可以不要理论。它出自《连线》杂志的 Chris Anderson 在 2008 年 6 月发表的文章，题目就叫《The End of Theory: The Data Deluge Makes the Scientific Method Obsolete》。文章还说，人们为了解释现象而事先提出的模型也可以不要。这里的模型指一种解释现象的理论，和机器学习里训练出来的模型是两回事。文章举的例子是 Google：它给网页排序，不需要知道一个网页为什么比另一个好，只要链接的统计数据显示它更好就够了，给内容配广告也是同样的做法。文章把这种做法概括成一句话：有相关性就够了，不必追问因果。

题目的说法很绝对，但它指向一个后来确实发生的变化：在图像识别、语音识别、机器翻译这些问题上，从数据里学出来的系统后来都比人写规则的系统做得好。

下表把演绎式和归纳式并排比较。最后一行是两种开发流程，表后的图画的就是这两种流程。

{{fig 22 | 上面一行是传统的软件开发流程，四步依次是规格说明、实现、测试、上线，标注为演绎式。下面一行是模型、agent 和软件现在的开发流程，四步是目标、评估、实验、优化，标注为归纳式，并且从优化有一条线回到评估，表示这几步要反复做。}}

两行流程里，测试和评估的位置不同。上面一行里，测试排在实现之后，是用来确认的。下面一行里，评估排在实验之前：要先有一个能给结果打分的办法，才谈得上做实验和优化。没有评估，后面两步无从下手。

下面一行的四步可以这样理解。目标是想让产物做到什么。评估是给结果打分的办法。实验通常是对照试验，也就是只改一处、其余不变，比较改动前后的结果，例如消融实验（ablation，去掉或改动一个部分，看结果变化多少）。优化相当于上面一行的实现，因为产物是在这一步被改动的。

拿前面取电话号码的函数举一个例子，四步可以这样对应。目标是从各种写法的文字里取对号码。评估是一批有代表性的输入和正确答案，跑一遍就能数出取对了多少。实验是换一种 prompt 再跑一遍，看取对的比例变了多少。优化是把取对比例更高的 prompt 留下来，然后回到评估再来一轮。

两行的走法也不同。上面一行大体上从前往后走一遍，写的人读得懂代码，每一步都知道自己做了什么。下面一行要一轮一轮地试，靠试错逐步得到更好的结果。

三层都在变成归纳式

从传统软件到机器学习，再到语言模型和 agent，归纳式的范围一步步扩大。到今天，模型、agent 和软件这三层都越来越多地用归纳式的办法做出来，程度各不相同。下面先说模型和 agent 这两层是怎么来的，再用一张表把三层放在一起。

语言模型是机器学习的一个分支。它的输入和输出都是文字，训练的目标是预测下一个 token（模型处理文字的基本单位）。互联网上的大量文字因此成了现成的带标注数据：前面的文字是输入，紧跟着的文字是标注。

agent 让模型能在计算机上动手做事。模型按约定的格式输出一段文字，外面的程序把它转成对另一个程序的调用，或者直接当作代码去执行。到这一步，在计算机上动手做事的是模型，它的行为没有人逐条编写，是从大量数据里学出来的。这是归纳式最彻底的情形。

模型外面的那层程序仍然是人写的，但它改得好不好，读代码看不出来。agent 实际怎么做由模型决定，同一个任务跑两次，过程和结果都可能不同，所以这层程序的每次改动都要靠评估来判断，见下表的第二行。

深度学习库 Keras 的作者 François Chollet 在 2026 年 2 月的一条帖子里把第三层说得很直接：用足够强的 agent 来写代码，本质上就是在做机器学习。

他把这件事和机器学习逐项对应起来。工程师定下优化目标，再给 agent 的尝试划定范围，原话叫搜索空间的约束（constraints on the search space），这两样就是规格说明和测试。agent 相当于优化过程，反复尝试，直到目标达成。得到的代码库相当于一个黑盒模型，也就是只看得到输入和输出的模型，人不看它内部的逻辑就把它部署出去。

他接着指出，机器学习里的老问题也会跟着来。一个是对规格说明过拟合，也就是只对写明的那些要求有效，换一种情况就不行。一个是只在测试范围内有效的捷径。还有一个是数据泄漏，也就是答案提前漏给了被测的一方。

Chollet 说的「只在测试范围内有效的捷径」，在 agent 的评估里有一个专门的名字，叫钻空子（reward hacking，靠利用评分办法的漏洞拿到分数）。第三部分会专门讲它。

规格说明的位置，现在是评估的

把上面几节合起来，从传统软件到 agent，有两处换成了评估。这两处说的是两件事，要分开看。

第一处是流程的起点。以前开发流程的第一步是写规格说明，现在第一步是定目标和做评估。这一节的标题说的就是这一处：规格说明原来的位置，现在是评估的。

第二处是最终依据（source of truth），也就是想确认软件实际会做什么，最后以什么为准。在传统软件里，代码是最终依据。用 agent 做软件时，评估是最终依据。

下表的前两行是这两处变化，后三行是跟着一起变的另外三件事。

流程的起点换了，做第一步的人是谁也成了问题。以前写规格说明的人是软件工程师。现在做评估的人是谁，这个角色要会什么，目前没有现成的答案。它可能是一种新的职业，也可能是现有的职业换一套开发方法，合适的工具和分工都还在形成当中。

Harbor 的团队给过一个方向。Harbor 是一套用来做评估和运行评估的开源工具，它的团队在 2026 年 10 月的一篇文章里说：开发流程从设计和实现转向评估和优化之后，人的工作越来越多地是设计给结果打分的办法。出处：Cracking down on reward hacking。

要达到什么目标，仍然要用文字写下来。在一个评估任务里，它写在任务说明里，由验证器（给结果打分的程序）逐条检查。第三部分会讲到，任务说明和验证器要一一对应。

agent 的训练数据和测试数据是什么

先比较两个目标。训练一个预测房价的模型，训练数据和测试数据是什么样子很容易想到：一张数字表格，每一行是一套房子的各项特征和成交价。把目标换成「让 agent 接手牙科诊所前台的日常工作」，训练数据和评估数据是什么样子，就不容易想出来了。

机器学习里，训练数据和测试数据是一条条「输入加标注」。agent 要做的是在一个环境里分很多步完成一件事，一条「输入加标注」描述不了这样一件事。对应的东西是任务。

下表左列是机器学习里的几个词，右列是它们在 agent 开发里对应的东西。左列的权重是模型里在训练时被调整的大量数值参数。损失函数给模型的输出打分，衡量它离正确答案有多远。优化器按这个分数去调整权重。测试集和验证集是不拿来训练、专门用来检查模型的例子。右列的技能文档（skills）是写给 agent 看的说明，告诉它某一类事情该怎么做。

表里最要紧的是前两行：训练用的和测试用的是同一种格式的东西。一个任务拿来算分，它就是评估；拿它的得分去改进 agent 或训练模型，它就是训练数据。所以把任务的格式定好、把任务写对，两头都受益。

这一讲后面三部分，讲的就是做评估这份工作的具体内容：一个评估长什么样，一个评估任务怎么写，写完之后怎么运行和维护。下一部分先用 Terminal-Bench 做例子，看这样一批任务实际长什么样。Terminal-Bench 是一个基准测试（benchmark，一组题目加一个打分的办法），题目是让 agent 在命令行环境里完成真实的技术工作。
