先看结论

  • Terminal-Bench 的出发点是一个判断：命令行是一件通用的工具，agent（能自己调用工具、分很多步完成任务的语言模型系统）只要会用 bash 这个命令行解释器，就能做软件工程、科学计算、系统管理等很多种工作。
  • 一个任务有三样：一段任务说明，一个 Docker 容器（隔离的、可以整个重建的运行环境），一组检查容器最终状态的测试。测试只看结果，不看 agent 敲过什么命令。
  • 它已经出了六个版本。有的版本换了一批更难的任务，有的版本是修任务。现在的 4.1 版有 66 个任务，2026 年 11 月 16 日排行榜上最好的成绩是 65.8%。
  • 排行榜的每一行除了解决率，还有 95% 置信区间（一种误差范围）、token 总量（token 是模型处理文字的基本单位）和花费，并且每一行都能点进去看到每一次运行的完整记录。
  • 做完这一个基准测试之后，作者把做法整理成了一套通用的工具 Harbor，让别人也能做自己的评估。

出发点：一个 bash 就够用

Terminal-Bench 建立在一个判断上：bash 这一个工具可以顶替其他所有工具。bash 是 Linux 和 macOS 上最常用的命令行解释器，在终端里敲的命令由它执行。

{{fig 31 | 同一件事的两种做法。左下是云服务的网页控制台，要在很多菜单和表单里点选。右下是一条命令，写明了镜像、机型、密钥、安全组，一次就启动一台云服务器。}}

图里比的是启动一台云服务器。在网页上做，agent 得看懂界面、找到按钮、一步步点。用命令行做，是一段文字。语言模型最擅长的就是读写文字，而几乎所有的技术工作都有命令行的做法：编译代码、训练模型、配置服务器、处理数据、转换文件。所以给 agent 一个终端，它能做的事的范围就非常大。

Terminal-Bench 的论文在引言里也是这样说的：终端无处不在、用途广、能力强，被用在软件工程、科学计算、网络安全、机器学习这些高技能的工作里；加上它是纯文字的，所以成了 Cursor、Codex CLI、Claude Code、Gemini CLI 这些 agent 的标准工具。出处：Merrill 等，2026。

i
名字里有终端，但不要求只用终端。论文明确写着：虽然名字叫 Terminal-Bench，并不要求 agent 只用终端这一种工具，它可以用任何方式操作容器。很多 agent 是直接装进容器里的程序，自带读写文件、搜索网页的工具。为了有一个中立的参照，作者自己写了一个最简单的运行框架（包在模型外面、给它工具并管理多轮对话的程序）Terminus 2，它只有一个工具，就是一个没有图形界面的终端，只靠 bash 命令完成任务。

这个想法是怎么来的

Terminal-Bench 出自两条线索。第一条是一场比赛。2024 年 12 月，Databricks 和 Perplexity 的联合创始人 Andy Konwinski 宣布了 K Prize：拿出 100 万美元，奖给第一个在新版 SWE-bench 上解决率（这里指做对的题目所占的比例）超过 90% 的开源系统。SWE-bench 是一个让 agent 修复真实 GitHub 代码仓库里的问题的基准测试。K Prize 的版本在参赛者提交之后才收集新的题目，所以这些题目不可能出现在模型的训练数据里。后来成为 Terminal-Bench 负责人之一的 Alex Shaw 是这场比赛的核心成员。出处：Konwinski 对这场比赛的说明。按 Terminal-Bench 作者的说法，团队在 2024 年底花了大约三个月，在 SWE-bench 的代码基础上搭出自动生成新题目的流程；这个时间没有在别处核对到。

读过大量 SWE-bench 的任务之后，K Prize 的团队开始问几个问题：一个任务为什么一定要是一个 GitHub 仓库、一条问题报告、一次代码合并请求加一组单元测试？为什么不能是人想在计算机上做的任何一件事？agent 在计算机上的任务，最一般的形式是什么？第二条线索是对终端的看重。Andy Konwinski 和当时在 Stanford 任教的 Ludwig Schmidt 都认定，终端这一件工具能顶替计算机上几乎所有别的工具。想做一个新的基准测试，想把「计算机上的任务」推广到最一般的形式，想测 agent 用终端的能力，这几个想法合在一起，就成了 Terminal-Bench。

一个任务长什么样

每个任务由三样东西组成：任务说明、环境、测试。下面是 Terminal-Bench 现在的版本里的一个真实任务，名字叫 cad-model。

{{fig 38 | 一个任务的三个部分。上：任务说明的核心要求，一句话：根据一张二维的工程图，输出一个三维模型文件。中：环境的定义，一个带 Python 的基础镜像，里面放了那张工程图。下：测试，一共九条检查，第一条查文件是否合法，后面八条各查一项几何性质。右边是那张工程图和它描述的零件。图里的环境定义和测试是简化过的写法。}}

这个任务有两点很能说明 Terminal-Bench 的思路。

  • 它考的是一件真实的专业工作。任务的作者在说明里写道，现实中这件事是机械工程师做的，难点是三维空间的推理，以及照着一份画在图片里的规格说明精确地做。它考的是机械设计的能力，写代码只是完成它的手段，整件事可以在命令行里完成。
  • 测试列了很多条，是为了让「通过」和「做对」对得上。只查体积，一个形状不同但体积凑巧相近的零件也能过。体积、表面积、惯性矩、凸包、欧拉示性数、曲率的积分要全都对上，形状不对的零件凑巧通过的机会就小得多。任务的作者还写了一点：这张工程图改编自一份公开的教程，图和参考解法都改动过，所以照抄教程里的答案通不过测试。

按 Terminal-Bench 作者的说法，这个任务的说明、环境和测试在整个任务集里都算简单的。其他任务的形式相同，内容分属编程、网络、安全、生物、化学、音乐、平面设计等领域。环境通常用一个 Docker 镜像来定义，也可以用别的能把环境启动起来的配置；测试可以像这里一样用程序检查，也可以让语言模型或 agent 来评审。

和 SWE-bench 比，差别在哪里

前面提到的 SWE-bench 是测 agent 编程能力时最常用的基准测试之一。Terminal-Bench 的作者认为，从方法上看 SWE-bench 是 Terminal-Bench 的一个子集：SWE-bench 的任何一个任务都能写成 Terminal-Bench 的任务，反过来做不到。

作者还有一个印象：在 SWE-bench 上，agent 读进上下文（模型一次能看到的全部文字）的 token 明显更多，因为它面对的是真实的大型代码库和很大的文件。这是定性的观察，没有给出数字。

从 2025 年 1 月到现在：六个版本

Terminal-Bench 代码仓库的第一次提交是在 2025 年 1 月 17 日。Anthropic 在同年 2 月 24 日发布了 Claude Code 的研究预览版，这是后来最常用的命令行编程 agent 之一。也就是说，这个基准测试开始做的时候，在终端里工作的 agent 还没有流行起来。2.0 版论文的作者单位里，排在最前面的两个是 Stanford University 和 Laude Institute。

表里有两种不同的版本变化，容易混在一起。

  • 换题。1.0 到 2.0、2.1 到 3.0，换的是任务集。3.0 的公告给了两条理由：2.1 的很多任务已经被做满（saturated，各个系统都能稳定通过），排行榜上各个系统的分数挤在很窄的范围里，分不出差距；任务的种类也要更有代表性。1.0 换成 2.0 的理由，没有查到官方的专门说明，2.0 的论文只说当时已有的基准测试对最强的模型不够难。这篇论文还预计 2.0 自己可能在一年内被做满。
  • 修题。2.0 到 2.1、3.0 到 4.0、4.0 到 4.1，任务还是那些，改的是任务里的问题：说明和测试对不上、外部依赖变了、资源给得太紧、验证器有漏洞。

4.0 删掉的 8 个任务，官方给了理由：2 个被做满，2 个会让模型拒绝执行，2 个的答案已经能在网上找到，2 个有没解决的质量或平台兼容问题。这里「做满」的判断标准是：最新一代的各家各档模型，5 次运行全部通过。

从 3.0 到 4.0 没有换题，版本号的第一位却加了 1，原因在第四部分的版本号一节：现在版本号的每一位表示旧的结果还能不能用，第一位变了，表示所有系统都要重新跑。

接下来的版本往哪里走，Terminal-Bench 的作者说了三个方向：覆盖更多种类的工作，因为现在的任务只是人在计算机上做的事情里很小的一部分；让环境更复杂；让任务要走的步骤更多、耗时更长。他们也说明，现在这种任务形式是有意做得小而规整的：一个任务只测一件事，是测一种能力时最小、最便宜的单元。它装不下所有的工作，十年后回头看，很可能会显得过于简单。

700 多万这个数量的是下载次数。Terminal-Bench 团队把这个数叫作「7M+ benchmark runs」，也就是运行了 700 多万次。同一张图的纵轴写的是「Reported all-time downloads」，也就是累计下载次数。很可能是因为运行之前要先把任务数据下载下来，所以拿下载次数来近似运行次数。两者并不相等：下载了不一定跑，一次下载也可能跑很多遍。图上没有写明统计的是哪个下载渠道。

从一个基准测试到一套工具：Harbor

做 Terminal-Bench 的过程中，作者积累了一套做法：任务用什么格式写，怎样并行地跑几千次运行，怎样检查任务的质量，怎样保存和查看结果。他们把这套做法做成了一个开源的框架，叫 Harbor。官方文档对它的一句话介绍是：一个可以让任何 agent、配任何模型、在任何沙箱（sandbox，隔离的运行环境）里并行地跑任何任务的框架。

两者的关系在论文里写得很清楚：Terminal-Bench 的任务用 Harbor 的任务格式来写，用 Harbor 来运行。这个格式并不限于 Terminal-Bench，论文说作者已经把另外 26 个已有的基准测试改写成了同一种格式。

为什么要让每个人都能做评估？第一部分的结论是，软件实际会做什么，最后以评估为准。公开的基准测试回答的是「哪个模型在这批通用的任务上更强」。一个团队真正要回答的问题通常更具体：哪个模型加哪个运行框架，在自己的代码库、自己的业务流程上做得最好，花多少钱。这个问题只有用自己的任务做的评估能回答。

Terminal-Bench 的作者还给了一个更直接的理由：做 Terminal-Bench 这样的基准测试很难扩大规模，每个任务都要靠真正懂那件工作的人来写和审。他们认为，今后十年里用来衡量最强模型的那些基准测试不会都出自自己这一个团队，所以把时间花在 Harbor 上，让懂某一小块工作的人自己做评估。这些人只关心很窄的一类任务，也希望它被做满，因为他们要的就是这类工作能交给 agent 自动完成。每个行业、每个产品的每项功能都有这样一个评估的话，它们合起来就相当于对模型的全面评估。
