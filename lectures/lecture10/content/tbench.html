先看结论

  • Terminal-Bench 是一个基准测试（benchmark，一组题目加一个打分的办法），题目是让 agent（能自己调用工具、分很多步完成任务的语言模型系统）完成真实的技术工作。
  • 它的出发点是一个判断：命令行是一件通用的工具，agent 只要会用 bash 这个命令行解释器，就能做软件工程、科学计算、系统管理等很多种工作。
  • 一个任务有三样：一段任务说明，一个 Docker 容器（隔离的、可以整个重建的运行环境），一组检查容器最终状态的测试。测试只看结果，不看 agent 敲过什么命令。
  • 它已经出了六个版本。有的版本换了一批更难的任务，有的版本是修任务。现在的 4.1 版有 66 个任务，2026 年 11 月 16 日排行榜上最高的解决率是 65.8%。解决率指测试通过的运行占全部运行的比例。
  • 排行榜的每一行除了解决率，还有 95% 置信区间（一种误差范围）、token 总量（token 是模型处理文字的基本单位）和花费，并且每一行都能点进去看到每一次运行的完整记录。
  • 做完这一个基准测试之后，作者把做法整理成了一套通用的工具 Harbor，让别人也能做自己的评估。

出发点：一个 bash 就够用

Terminal-Bench 建立在一个判断上：bash 这一个工具可以顶替其他所有工具。bash 是 Linux 和 macOS 上最常用的命令行解释器，在终端里敲的命令由它执行。

{{fig 31 | 同一件事的两种做法。左下是云服务的网页控制台，要在很多菜单和表单里点选。右下是一条命令，一次就启动一台云服务器。命令的参数写明了镜像、机型、密钥和安全组。镜像是创建服务器用的模板，里面装好了操作系统。机型是服务器的硬件规格。密钥用来登录服务器。安全组是一组控制网络访问的规则。}}

图里比的是启动一台云服务器。在网页上做，agent 得看懂界面、找到按钮、一步步点。用命令行做，是一段文字。语言模型最擅长的就是读写文字，而几乎所有的技术工作都有命令行的做法：编译代码、训练模型、配置服务器、处理数据、转换文件。所以给 agent 一个终端，它能做的事的范围就非常大。

Terminal-Bench 的论文在引言里也是这样说的：终端无处不在、用途广、能力强，被用在软件工程、科学计算、网络安全、机器学习这些高技能的工作里。它又是纯文字的，所以成了 Cursor、Codex CLI、Claude Code、Gemini CLI 这些 agent 的标准工具。出处：Merrill 等，2026。

i
名字里有终端，但不要求只用终端。论文明确写着：虽然名字叫 Terminal-Bench，并不要求 agent 只用终端这一种工具，它可以用任何方式操作容器。很多 agent 的运行框架（包在模型外面、给它工具并管理多轮对话的程序）是直接装进容器里的程序，自带读写文件、搜索网页的工具。

论文为比较模型准备了一个中立的参照，叫 Terminus 2。需要这个参照，是因为分数属于「模型加运行框架」这个整体，同一个模型换一个运行框架，分数就会不同。论文指出，模型和运行框架各自起了多少作用很难分开，而且很多运行框架是照着某些模型的习惯做的，同一家公司出的模型和运行框架尤其如此。Terminus 2 是作者自己写的一个最简单的运行框架：它只有一个工具，就是一个没有图形界面的终端，只靠 bash 命令完成任务。

这个想法是怎么来的

Terminal-Bench 出自两条线索：一场比赛，和两个人对终端的看重。

第一条线索是一场叫 K Prize 的比赛。2024 年 12 月，Databricks 和 Perplexity 的联合创始人 Andy Konwinski 宣布了它：拿出 100 万美元，奖给第一个在新版 SWE-bench 上解决率超过 90% 的开源系统。SWE-bench 是一个让 agent 修复真实 GitHub 代码仓库里的问题的基准测试，这里的解决率指做对的题目所占的比例。出处：Konwinski 对这场比赛的说明。

这个新版 SWE-bench 的题目是新收集的。K Prize 在参赛者提交之后才收集题目，所以这些题目不可能出现在模型的训练数据里。

后来成为 Terminal-Bench 负责人之一的 Alex Shaw 是这场比赛的核心成员。按 Terminal-Bench 作者的说法，团队在 2024 年底花了大约三个月筹备这场比赛，在 SWE-bench 的代码基础上搭出自动生成新题目的流程。

筹备的过程中，团队读了大量 SWE-bench 的任务，开始问几个问题：一个任务为什么一定要是一个 GitHub 仓库、一条问题报告、一次代码合并请求加一组单元测试？为什么不能是人想在计算机上做的任何一件事？agent 在计算机上的任务，最一般的形式是什么？

第二条线索是对终端的看重。Andy Konwinski 和当时在 Stanford 任教的 Ludwig Schmidt 都认定，终端这一件工具能顶替计算机上几乎所有别的工具，也就是本节开头的那个判断。

想做一个新的基准测试，想把「计算机上的任务」推广到最一般的形式，想测 agent 用终端的能力，这几个想法合在一起，就成了 Terminal-Bench。终端是它的出发点。做成之后，它检查的是容器最后的状态，并不要求 agent 只用终端，上面的蓝色框说的就是这一点。

一个任务长什么样

每个任务由三样东西组成：任务说明、环境、测试。这组测试合起来就是给结果打分的程序，后面讲版本和排行榜时把它叫作验证器，第一部分说的验证器也是它。

下面是 Terminal-Bench 现在的版本里的一个真实任务，名字叫 cad-model。

{{fig 38 | 一个任务的三个部分。上：任务说明的核心要求，一句话：根据一张二维的工程图，输出一个三维模型文件。中：环境的定义，一个带 Python 的基础镜像（镜像是创建容器用的模板），里面放了那张工程图。下：测试，一共九条检查，第一条查文件是否合法，后面八条各查一项几何性质。右边是那张工程图和它描述的零件。图里的环境定义和测试是简化过的写法。}}

下表逐项列出这个任务的三个部分。测试那一行用到几个几何上的词。三角网格是用许多小三角形拼成的物体表面。主惯性矩描述零件的质量怎样分布在三条主轴周围，主轴是由零件的形状决定的三个互相垂直的方向。凸包是包住零件的最小凸形外壳。欧拉示性数是一个反映孔洞数量的整数，属于拓扑性质。平均曲率在整个表面上的积分，是把表面每一处的弯曲程度加起来得到的一个数。参考解法是出题的人写的正确做法。

这个任务有两点很能说明 Terminal-Bench 的思路。

  • 它考的是一件真实的专业工作。任务的作者在说明里写道，现实中这件事是机械工程师做的，难点是三维空间的推理，以及照着一份画在图片里的规格说明精确地做。它考的是机械设计的能力，写代码只是完成它的手段，整件事可以在命令行里完成。
  • 测试列了很多条，是为了让「通过」和「做对」对得上。只查体积，一个形状不同但体积凑巧相近的零件也能过。体积、表面积、惯性矩、凸包、欧拉示性数、曲率的积分要全都对上，形状不对的零件凑巧通过的机会就小得多。任务的作者还写了一点：这张工程图改编自一份公开的教程，图和参考解法都改动过，所以照抄教程里的答案通不过测试。

按 Terminal-Bench 作者的说法，这个任务的说明、环境和测试在整个任务集里都算简单的。其他任务的形式相同，内容分属编程、网络、安全、生物、化学、音乐、平面设计等领域。

任务的环境和测试也有别的写法。环境通常用一个 Docker 镜像来定义，也可以用别的能把环境启动起来的配置。测试可以像这里一样用程序检查，也可以让语言模型或 agent 来评审。

从 2025 年 1 月到现在：六个版本

Terminal-Bench 开始做的时候，在终端里工作的 agent 还没有流行起来。它的代码仓库的第一次提交是在 2025 年 1 月 17 日。Anthropic 在同年 2 月 24 日才发布 Claude Code 的研究预览版，这是后来最常用的命令行编程 agent 之一。

从那时到现在，它出了六个版本。版本之间的变化有两种，容易混在一起，读下面的表时先分清每一版属于哪一种。

  • 换题。1.0 到 2.0、2.1 到 3.0，换的是任务集。
  • 修题。2.0 到 2.1、3.0 到 4.0、4.0 到 4.1，没有加进新任务，改的是已有任务里的问题：说明和测试对不上、外部依赖变了、资源给得太紧、测试有漏洞。修题时也会删任务，3.0 到 4.0 删了 8 个。

表里有两个词要先说明。系统指一个模型配一个运行框架，排行榜上的每一行是一个系统。解决率指测试通过的运行占全部运行的比例。

换题的理由，3.0 的公告给了两条。第一条是 2.1 的很多任务已经被做满（saturated，各个系统都能稳定通过），排行榜上各个系统的分数挤在很窄的范围里，分不出差距。第二条是任务的种类要更有代表性。

1.0 换成 2.0 的理由，2.0 的论文只说当时已有的基准测试对最强的模型不够难。这篇论文还预计 2.0 自己可能在一年内被做满。

修题的时候也会删任务。4.0 删掉的 8 个任务，官方给了理由：2 个被做满，2 个会让模型拒绝执行，2 个的答案已经能在网上找到，2 个有没解决的质量或平台兼容问题。4.0 判断一个任务被做满，用的标准是：最新一代的模型，不论哪个系列、哪个档次，每一个做这个任务的 5 次运行都全部通过。公告说，这样的任务已经分不出模型之间的差距。

从 3.0 到 4.0 没有换题，版本号的第一位却加了 1。现在版本号的每一位表示旧的结果还能不能用，第一位变了，表示所有系统都要重新跑。4.0 重新校准了每个任务的 CPU 和内存，把时间上限统一成 8 小时，这些都是 agent 面对的条件。它还删掉了任务，任务集也变了。4.0 的公告把这两项都算作必须重跑的改动，旧的结果不能再用。版本号的规则在第四部分的版本号一节展开。

接下来的版本往哪里走，Terminal-Bench 的作者说了三个方向。第一是覆盖更多种类的工作，因为现在的任务只是人在计算机上做的事情里很小的一部分。第二是让环境更复杂。第三是让任务要走的步骤更多、耗时更长。

他们也说明，现在这种任务形式是有意做得小而规整的：一个任务只测一件事，是测一种能力时最小、最便宜的单元。这种形式表达不了所有的工作，十年后回头看，很可能会显得过于简单。

被使用的规模

Terminal-Bench 运行得多，和它的用法有关。按 Terminal-Bench 作者的介绍，它被用在三个时候。第一是模型发布的时候，用来报告成绩。第二是训练模型的过程中，每存下一个中间版本（checkpoint）就跑一遍，看能力有没有提高。第三是开发运行框架的时候，开发的人用它来评估自己的框架。

它被使用的另一种方式是衍生出别的项目。作者提到，从它衍生出来的项目有好几个，例如面向科研工作的 Terminal-Bench-Science 和 OpenThoughts-Agent。后者是一个为训练小型 agent 模型准备数据和工具的开源项目，它的说明文件写明用 Harbor 来生成数据和运行评估，评估用的基准测试里有 Terminal-Bench 2.0。

使用的规模有多大，Terminal-Bench 团队在 2026 年 10 月公开给过五个数。它们各自量的东西不一样，见下表。其中 64 和 700 万这两个数各出自一张图，两张图在表的后面。

从一个基准测试到一套工具：Harbor

做 Terminal-Bench 的过程中，作者积累了一套做法：任务用什么格式写，怎样并行地跑几千次运行，怎样检查任务的质量，怎样保存和查看结果。他们把这套做法做成了一个开源的框架，叫 Harbor。官方文档对它的一句话介绍是：一个可以让任何 agent、配任何模型、在任何沙箱（sandbox，隔离的运行环境）里并行地跑任何任务的框架。这句话里和模型搭配的 agent，指的是运行框架。Harbor 和 Terminal-Bench 的分工见下表。

两者的关系在论文里写得很清楚：Terminal-Bench 的任务用 Harbor 的任务格式来写，用 Harbor 来运行。这个格式并不限于 Terminal-Bench，论文说作者已经把另外 26 个已有的基准测试改写成了同一种格式，其中有 SWE-bench Verified。

为什么要让每个人都能做评估？第一部分的结论是，软件实际会做什么，最后以评估为准。公开的基准测试回答的是「哪个模型在这批通用的任务上更强」。一个团队真正要回答的问题通常更具体：哪个模型加哪个运行框架，在自己的代码库、自己的业务流程上做得最好，花多少钱。这个问题只有用自己的任务做的评估能回答。

Terminal-Bench 的作者还给了一个更直接的理由：做 Terminal-Bench 这样的基准测试很难扩大规模，每个任务都要靠真正懂那件工作的人来写和审。他们认为，今后十年里用来衡量最强模型的那些基准测试不会都出自自己这一个团队，所以把时间花在 Harbor 上，让懂某一小块工作的人自己做评估。

这些人只关心很窄的一类任务，也希望它被做满，因为他们要的就是这类工作能交给 agent 自动完成。每个行业、每个产品的每项功能都有这样一个评估的话，它们合起来就相当于对模型的全面评估。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • K Prize 的筹备时间。「团队在 2024 年底花了大约三个月筹备这场比赛」是 Terminal-Bench 作者自己的说法，这个时间没有在别处核对到。
  • 版本表里按第三方介绍写的几格。1.0 的时间和任务数、2.1 的发布月份只在第三方的介绍里查到。
  • 版本表里没有查到的成绩和理由。1.0 和 2.1 两个版本，公告和论文里给出的成绩没有查到。1.0 换成 2.0 的理由，没有查到官方的专门说明。
  • 4.0 和 4.1 的任务数。66 是按代码仓库里的任务目录数出来的，等于 74 减 8，也就是 3.0 的 74 个任务减去 4.0 删掉的 8 个。
  • 64 份模型发布文档。这个数只见于「被使用的规模」一节那张填色的统计图，没有在别处核对到。图的读法按 Terminal-Bench 作者的说明。
  • 171 位贡献者。这个数没有在别处核对到。3.0 的公告写的是 100 多位任务贡献者和审查者。
  • 1,000 以上的 GitHub 参与者。这个数没有在别处核对到。
  • 5,000 以上的 Discord 成员。这个数对得上。Discord 的公开接口在 2026 年 11 月 19 日显示这个社区大约有 6,540 名成员。
  • 700 万以上的下载次数。这个数只见于「被使用的规模」一节那张累计下载次数的曲线图，没有在别处核对到。图上没有写明统计的是哪个下载渠道。
