先看结论

  • 跑评估的基础设施要满足四条：出了故障能自己恢复，结果可复现，能并行地跑很多次运行，本机和云上都能跑。基础设施本身会影响分数。
  • 同一套「让 agent 在沙箱里做任务」的基础设施，可以用来评估，可以用来产生训练数据，也可以用来做实际的工作。agent 指能自己调用工具、分很多步完成任务的语言模型系统，沙箱指隔离的运行环境。
  • 任务出了错往往不容易看出来，所以发布前要过一组自动检查。先用程序扫描任务的文件，再让 agent 审查这些文件。然后运行参考解法（出题的人写的正确做法），它应该得满分。再启动环境，什么都不做就评分，这时应该得零分。最后让前沿的 agent（当下能力最强的那一批）正常做一遍，让一个 agent 故意去钻空子，再让 agent 读这两类运行的运行轨迹。钻空子指没有按本意完成任务，却靠漏洞拿到分数，运行轨迹指每一步动作和结果的完整记录。
  • 任务是软件，软件有 bug。再仔细的发布前检查也查不完，大量的问题是在使用中暴露的。所以基准测试（benchmark，一组题目加一个打分的办法）要持续地修、持续地发新版本。
  • 每个任务有一个版本号，由用点分开的三个数字组成，依次叫第一位、第二位、第三位。第一位变了，旧的结果不能再用，要重新运行。第二位变了，只要重新评分。第三位变了，可以直接沿用。这样修任务的成本才低到可以经常修。

做评估的九个步骤

把评估从无到有做起来，再长期维护下去，Anthropic 的文章《Demystifying evals for AI agents》把它分成三个阶段、九个步骤。这一节先列出这九步，再对照这一讲的各部分讲的是其中哪几步。

下面的图和表里会出现评估框架（evaluation harness）这个词，它指把评估从头跑到尾的那套程序：准备环境、并行地跑任务、记录每一步、打分、汇总。

{{fig 55 | 三栏。左栏是建立任务集，四步：尽早开始，从手工测试开始，写没有歧义的任务，正反两种情况都覆盖。中栏是搭建评估框架，两步：搭一个可靠的评估框架，认真设计评分。右栏是维护，三步：检查运行轨迹（每一步动作和结果的完整记录），留意评估是否饱和（saturated，指 agent 已经通过了全部做得成的任务，分数没有再提高的余地），长期维护。图上的步骤名是简写，下表里有四步用的是文章正文里更长的标题，见表注。图片来源：Anthropic 的同一篇文章。}}

对照这一讲的内容：第三部分讲的是第 2 步和第 5 步，也就是怎么写任务、怎么评分。这一部分讲第 4 步、第 6 步和第 8 步。第 7 步说的是整个评估饱和。

Terminal-Bench 是这一讲用作例子的基准测试，第二部分讲版本的一节讲到了它的两种饱和。一种是整个基准测试饱和，和第 7 步说的是同一件事。另一种是单个任务饱和，也就是各个系统都能稳定通过这个任务，Terminal-Bench 的应对办法是删掉或换掉这样的任务。系统指一个模型配一个运行框架，运行框架是包在模型外面、给它工具并管理多轮对话的程序。

跑评估的基础设施：四条要求

这一节说的基础设施，就是上一节第 4 步里的评估框架。它要应付的运行次数很多。一个基准测试有几十个任务，每个任务跑 5 次，再乘上几十种模型和运行框架的组合，就是上万次运行。每一次都要启动一个容器（隔离的、可以整个重建的运行环境），让 agent 在里面工作几分钟到几小时。容器是沙箱的一种，云上的沙箱服务给的也可能是一台虚拟机。

这一页用 Terminal-Bench 当例子。它是一个基准测试，让 agent 在容器里完成真实的技术工作，再用测试检查结果。它已经出了六个版本，后面会提到其中的 2.0、2.1、3.0、4.0 和 4.1，各版的差别见第二部分的版本表。运行它用的是 Harbor 里的评估框架，Harbor 是同一批作者做的开源工具。Terminal-Bench 2.0 的论文里一共有 32,155 次运行：6 种运行框架配 16 个模型，每个能配上的组合把全部 89 个任务至少跑 5 遍。

能把这么多次运行跑好的基础设施，要满足四条。

这四条为的是同一件事：靠比较分数来做决定的时候，分数必须可比，并且要尽快、尽量便宜地拿到。其中三条值得多说一句。

可复现这一条，要求基础设施自己不给结果添波动。agent 本身有随机性，同样的配置跑两遍，结果已经有不小的波动，基础设施不应该再给结果添一份波动。

快这一条受几种有限资源的限制。能同时跑多少次运行，要看模型接口的 token 配额、沙箱服务的容量，以及镜像仓库这类外部服务允许的访问频率。token 是模型处理文字的基本单位，配额是厂商允许一个账号在一段时间里调用的总量。镜像（image）是创建容器用的模板，镜像仓库是存放镜像的服务。把并行度调到合适通常要花一些工夫。

可移植这一条的用处不限于公开的基准测试。一个团队在本机调试任务、在云上大规模运行，两边的结果也要能互相比较。

+
基础设施的配置能让分数差出 6 个百分点。Anthropic 在 2026 年 2 月发表过一项实验：用同一个模型、同一个运行框架跑 Terminal-Bench 2.0，只改变给容器的 CPU 和内存。严格按任务标明的资源来限制时，有 5.8% 的运行因为基础设施出错而失败。完全不限制时，这个比例降到 0.5%。解决率也跟着变：完全不限制时的解决率，比严格限制时高 6 个百分点。这 6 个百分点说的是 agent 做成任务的比例，和前面基础设施出错的比例是两个量。两种配置下解决率各是多少，文章没有给出。出处：Quantifying infrastructure noise in agentic coding evals。

这篇文章给读分数的人的建议是：排行榜上相差不到 3 个百分点的两个分数，在弄清双方的运行配置之前，不要当成有差别。文章给的依据有两条。第一条是资源配置带来的差距：给容器的资源在中等的范围里变动时，不同配置下的解决率最多相差将近 2 个百分点。文章没有写明中等的范围是任务标明资源的几倍到几倍。前面的 6 个百分点，是完全不限制和严格限制这两头之间的差距。第二条是分数本身的统计误差：文章说，用最简单的统计办法算出的置信区间（一种误差范围）已经有 1 到 2 个百分点宽。这份误差要叠加在第一条的差距上面。

这篇文章在结尾还给了一个设定资源的办法：给容器的资源上限要比任务标明的数值高，高出多少靠实测来定，要让基础设施的出错明显减少，解决率又没有因此明显变高。文章举的例子是 Terminal-Bench 2.0：上限定在任务标明数值的 3 倍时，基础设施出错的比例从 5.8% 降到 2.1%，解决率的变化在误差范围以内。

Terminal-Bench 4.0 重新校准每个任务的资源时，照的就是这个办法：4.0 的公告写明，校准资源用的是这篇文章给出的方法。具体怎么做，公告只写了一句：在资源留有很大余量的条件下运行这些任务，就能选出一个不影响最终指标的合理配置。公告没有写怎样从这次运行里选出配置。最终指标指什么，公告也没有另外说明，按 Anthropic 文章的办法来理解是解决率。出处：4.0 版的公告。

同一套基础设施，三种用途

前面一直说的「一次运行」（trial，也叫 rollout），指的是让某个运行框架配某个模型，在一个沙箱里做一个任务，把过程和结果存下来。评估只是它的一种用途。

{{fig 57 | 中间是 Harbor 的运行引擎。上面一排是输入：任务、模型、agent、沙箱、技能文档（skills，写着某类工作该怎么做的说明文件，agent 需要时再读）。下面一排是五项产出：轨迹分析、评估、优化、任务质量检查、产物（agent 交出的文件）。图上方的一句话是 Harbor 的自我介绍：一个让任何 agent 配任何模型、在任何沙箱里并行地跑任何任务的框架。图里和模型并列的 agent 指运行框架。}}

这和第一部分「agent 的训练数据和测试数据是什么」一节说的是同一件事：对 agent 来说，测试数据和训练数据是同一种格式的任务。按 Terminal-Bench 作者的说法，有人卖给模型厂商用来训练模型的任务，用的就是这同一种任务格式。

任务的格式相同，基础设施也就可以共用。训练模型时也要批量运行 agent、收集轨迹，做这件事的服务要解决的，也是上一节四条要求对应的问题：故障怎么恢复，结果怎么复现，怎么并行，怎么换一个地方运行。把 agent 放到生产环境里工作时，常常也要解决同样的问题。

图里下面一排的五项各属于哪一种用途，图上没有标出。按图和表的内容，可以这样对照：「评估」就是第一种用途，「优化」属于第二种，「产物」是第三种用途要的东西。另外两项和评估本身有关：读运行轨迹来分析 agent 为什么失败，以及用 agent 去检查任务的质量。后一项是下一节的内容。

任务的质量检查：静态检查加上用 agent 来查

任务出了错，往往不容易看出来。一个任务能跑、能出分，不代表它是对的。

现在的任务已经相当大。Terminal-Bench 官网的文章 Continuous Benchmarks 举过一个数：3.0 版里一个中等规模的任务有 20 个文件、4,000 行代码。它运行时还依赖操作系统、沙箱、模型接口和互联网。出题的人自己读一遍，已经不足以判断它对不对。所以检查也要自动化，而且其中很多步是让 agent 来做的。

下面的图和表会用到第三部分讲的三个词。任务说明是交给 agent 的那段文字，写明要做成什么。环境是 agent 动手的地方，通常是一个容器。验证器是给结果打分的程序。

{{fig 59 | 上面的方框是一个任务，下面是对它做的几类检查，每一类都和任务之间有来回的箭头，表示查出问题就回去改。从左到右：静态检查；让 agent 当评审来审查任务；参考解法、前沿的 agent、钻空子的 agent 各跑一遍。后两种的运行轨迹再交给一个 agent 评审。}}

这七项检查可以分成三档。第一档只看任务的文件，不运行任务。第二档启动任务的环境，但没有模型来做任务。这一档两项检查的英文名里都有 agent：oracle agent 是在环境里运行参考解法的程序，no-op agent 启动环境后什么都不做，两者都不调用模型。第三档真的让 agent 把任务做一遍。第三档最贵，能发现的问题也最多。下表列出每一档包括哪几项检查、要不要启动任务的环境、要不要调用模型。

第一档的两项直接给出不合格或告警，出题的人照着改。静态检查查的是能用程序判断的东西，例如任务的配置文件 task.toml 写得对不对，也可以自己加规则，比如限制任务说明的长度。每条规则也可以按任务关掉，例如必须让验证器和 agent 共用环境的任务可以关掉对应的那一条，见第三部分。

任务说明和验证器是否一一对应，要读懂两边的意思才能判断，所以交给 agent 评审。

第三档要真的让 agent 跑，常常能发现事先想不到的问题。例如环境里装的某个软件包的版本在这个任务里用不了。软件包用不了这类障碍和想测的能力无关，应该修掉。

第三档更常见的发现是：出题的人以为任务难在一处，agent 实际卡住的是另一处。要看清任务真正难在哪一步，还有一种做法：给 agent 一些提示，看最少要给多少它才能做成。

这套检查接在代码仓库的持续集成（CI，每次有人提交改动就自动运行一遍的检查流程）上。新任务和对旧任务的每一次修改，都要全部通过才能合并。在使用中发现的新型问题，会被加成新的检查项。

i
通过了全部检查，任务仍然可能有问题。下一节的例子说明这一点：Terminal-Bench 2.0 的每个任务在发布前都过了检查，发布后仍然在 28 个任务里确认了问题。单说静态检查这一项，Harbor 的文档写明它是对别的检查的补充，不保证任务或验证器是对的。

持续更新的基准测试：任务是软件，软件有 bug

传统的做法是把基准测试当成一份发布之后就不再改动的数据。Terminal-Bench 的作者在 2026 年 7 月提出另一种做法，叫持续更新的基准测试（continuous benchmark）：把它当成一个软件来维护。

{{fig 60 | 右边是一个循环。新的任务提交到代码仓库，经 Harbor 发布成基准测试的一个带版本号的新版本，排行榜上的各个系统在这个版本上运行，结果公布在官网。运行中发现的问题再回到代码仓库，成为下一轮修改。左边列出了使用中会暴露的五类问题。}}

这个循环的关键是从运行回到代码仓库的那一步：排行榜上的大量运行，相当于这个基准测试的真实使用。问题主要是在这里暴露的，一共有五类，见下表。

误判不通过和钻空子这两类，特别依赖更强的新模型来暴露。较弱的模型在任务的前几步就失败了，验证器里有问题的那几项检查还没有机会起作用。模型变强之后，它把任务做对了，验证器却判它不通过，这个问题才第一次显现。钻空子也一样，模型越强，用出的手法越出人意料。这两类问题一出现，就要据此修改任务。

发布前的检查查不完这些问题，有一份专门的研究可以说明。Buchanan 等人 2026 年 11 月的论文，记录了对 Terminal-Bench 2.0 的一次回头检查。检查和修复在先：官网的公告显示，修复后的 2.1 版在 2026 年 5 月 6 日就发布了。论文是之后才发表的。

2.0 版发布前，每个任务都过了上一节表里的几项检查：运行参考解法，让什么都不做的 agent 去跑，让一个 agent 专门去找能钻的空子。此外还有人工审查和语言模型辅助的审查，其中人工审查平均每个任务大约三小时。发布后几个月内，问题跟踪页（记录使用者报告的问题和处理进度的公开列表）上仍然积累了 50 多条标记为任务缺陷的报告。这篇论文的作者把全部 89 个任务重新检查了一遍，在其中 28 个里确认了问题，修复之后发布为 2.1 版。

修复改变了评估的结果。论文拿 19 个系统（模型和运行框架的组合）在 2.0 和 2.1 上各测了一遍，比的是解决率，也就是测试通过的运行占全部运行的比例。单个系统的解决率最多变动 12 个百分点，排行榜上的名次最多变动三位。总体上解决率是升高的，最弱的两个系统反而降低。变动最大的那个系统是升还是降，论文的这句话没有写明。2.1 版的公告列出的 14 个系统里，变动最大的一个是提高了 12.1 个百分点，见资料说明。2.0 和 2.1 两版给这 19 个系统排出的名次大体一致：论文给出两份名次的 Spearman 等级相关系数是 0.958，这个系数等于 1 表示两份名次完全相同。

论文把这 28 个任务的缺陷分成三类，见下表。它和上面的五类是两种分法，可以这样对照着读：上面的五类说的是问题在运行中表现成什么样，下表的三类说的是缺陷出在哪里。例如测试过严属于下表的第一类，表现出来就是上面的误判不通过。资源给得不合适属于下表的第三类，表现出来就是上面的基础设施噪声。

基准测试用得久了，任务里的缺陷会越积越多。这篇论文给这种情况起了个名字，叫 benchmark maintenance debt，字面的意思是基准测试在维护上欠下的债：缺陷越积越多，分数和它想测量的能力之间的差距越拉越大。

版本号：旧的结果还能不能用

经常修任务有一个现实的障碍。排行榜上有几十个系统，每个系统跑一遍要花几千美元。如果每修一个任务都要所有系统重跑，就没有人愿意修。解决的办法是给每个任务一个由三个数字组成的版本号，数字之间用点分开，例如 2.3.1。三个数字依次叫第一位、第二位、第三位，哪一位变了，表示旧的结果该怎么处理。

{{fig 61 | 版本号的三位各表示一类改动，图上给每一类写了一个标题。第一位加一，标题是 Agent Environment，表示改的是 agent 面对的东西，也就是任务说明、环境和给它的资源，旧的结果不能再用，要重新运行。第二位加一，标题是 Verifier，表示改的是验证器，旧的结果只要重新评分。第三位加一，标题是 Metadata，也就是元数据（关于任务的说明性信息，例如文档和分类），这一类改的是不影响分数的东西，旧的结果可以直接沿用。每一类下面列了几种典型的改动。第一类标题里的 environment 指 agent 面对的全部东西，任务说明和资源也算在内，比这一讲里专指容器的「环境」范围大。}}

表里的典型改动照上面的规则图列出，其中只有第一位那一行的「新增任务」改的是任务集，其余各项都是对单个任务的改动。新任务没有旧的结果，每个系统都要在它上面运行一遍，规则图把它列在要重新运行的这一类里。

第三位里有两项改动也改到了任务说明和环境：改任务说明里的错别字，把会变动的依赖固定到具体版本。它们归在第三位，因为分界看的是改动对分数有没有实质影响。Continuous Benchmarks 一文的说法是，对分数没有实质影响的改动可以直接沿用旧的结果，agent 面对的东西有了明显的变化才需要重新运行。

整个基准测试的版本号，按各个任务版本号的变化来定。一次发布里只要有一个任务加了第一位，基准测试的版本号就加第一位。没有任务加第一位、但有任务加了第二位，就加第二位。各个任务加的都是第三位，就加第三位。基准测试的版本号也是三个数字，Terminal-Bench 4.1 的完整版本号是 4.1.0，平常省掉末尾的 0。

升级排行榜的时候，Harbor 把已有的全部运行和新版本逐个任务对比，只有第一位变了的任务才重跑，第二位变了的重新评分，其余的沿用。

这套版本规则是 2026 年 7 月和持续更新的做法一起提出的，Terminal-Bench 从 3.0 版起采用。更早的版本号不按它来定：2.1 版修任务时改过任务说明、环境和资源配置，版本号只从 2.0 变成 2.1。

采用这套规则之后的版本里，有两处看起来奇怪，见第二部分的版本表。4.0 没有新任务，用的还是 3.0 的那些，第一位却加了一。4.1 让一部分运行的得分变了，却只加了第二位。按上面的规则，两处都能解释。

  • 4.0 为什么不叫 3.1。4.0 的公告举了两项改动，都算作必须重跑的改动。一项是每个任务给 agent 的 CPU、内存和时间上限变了，这些资源属于 agent 面对的东西。另一项是删掉了任务，任务集变了。所以加的是第一位。上面的规则表在第一位那一行列了新增任务，没有列出删任务这一种，公告也没有另外说明删任务为什么算必须重跑的改动。公告承认这在短期内会让人困惑，因为大家习惯把第一位的变化看成换了全新的一代。
  • 4.1 为什么只加第二位。它只改了验证器，agent 面对的东西没有变，所以旧的运行只要重新评分。这样省下的钱很多：4.0 排行榜上全部系统的运行一共花了 11.6 万美元的模型调用费用，升级到 4.1 时用保存下来的产物重新评分，新增的模型调用费用是 0。

这次重新评分改变的得分很少。11,550 次运行里，得分有变化的是 162 次。其中 134 次确认是验证器的改动带来的。另外 28 次，公告说是同一份产物让验证器评两次、结果不一样造成的，和验证器的改动无关。这 28 次保留了原来的得分。持续更新一节的表里提到，团队另外用原来的验证器重评过一遍，找出并修掉了几处时对时错的验证器。这 28 次和那几处是什么关系，公告没有说明。出处：4.1 版的公告。

重新评分之所以做得到，前提是第三部分讲的那个设计：验证器在单独的环境里运行，只检查 agent 交出的产物，而产物是保存下来的。防钻空子和省钱，用的是同一个办法。

每个任务自己的版本历史写在任务目录的 README 文件里。README 是写给人看的说明，和交给 agent 的任务说明 instruction.md 是两份文件。例如第二部分的三维建模任务 cad-model，把时间上限改成 8 小时、内存改成 8 GB 的那一次，版本号从 1.0.7 变成 2.0.0。之后的几次改动加的都是第三位，内容大多是固定依赖版本、更新元数据。其中 2.0.4 这一次和规则对不上，见资料说明。

任务经常改，不同时间测的分数还能不能比

基准测试的一个基本用途是比较结果。任务经常改，这周发布的模型和下周发布的模型面对的题目就可能不同。Terminal-Bench 的作者讲了三点。前两点是他们自己的做法，第三点是模型厂商已有的习惯。

  • 控制发布的节奏。前面说的经常发新版本，间隔是按月算的：3.0、4.0 和 4.1 三版分别发布于 2026 年 7 月 30 日、8 月 28 日和 11 月 9 日。作者的说法是，新版本不会每天都发，两次发布之间留出一段时间，厂商报告成绩时不至于赶上题目中途变动。
  • 排行榜尽快更新到新版本，并保留全部历史结果。新模型仍然可以和以前所有的模型比较。
  • 厂商的发布文档里本来就带着对比。发布文档（model card）是模型厂商发布新模型时公布的说明和测评成绩。每个新模型发布时，成绩表里会同时列出其他模型的成绩，读的人不用自己去找别的模型以前的分数。表里其他模型的成绩是不是在同一个版本上测的，作者没有说明。

他们同时认为，整个行业应该改掉只用一张图片来公布成绩数据的做法，把每个数连到完整的结果上，也就是全部的运行和每一次的得分。下一节讲 Terminal-Bench 自己是怎么做的。

结果：每一行都能查到全部的运行记录

排行榜上的一个数，背后是几百次运行。Terminal-Bench 的做法是把每一次运行的全部材料都公开：运行轨迹、日志、agent 交出的产物、得分。排行榜上的每一行都能点进去，一直看到某一次运行的某一步。第二部分的图里就是这样一个页面。

这样做有四个用处。

  • 别人可以检查分数。怀疑某个系统的高分是靠钻空子来的，可以去读它的轨迹。按 Terminal-Bench 作者的说法，结果公布之后，社区里有人去读这些记录，找到过钻空子的运行。作者没有说是哪几次运行、属于哪一种钻空子。4.1 版修掉的问题里，有一部分就是外部的机构审查这个基准测试之后提出来的。
  • 出题的人可以发现任务的问题。读轨迹能分清一次失败是 agent 真的错了，还是验证器把正确的做法判错了，也能看出一次通过是不是靠钻空子得来的。持续更新一节说的五类问题里，误判不通过和钻空子这两类可以这样查。轨迹太多，人读不过来，所以也让 agent 来读：给它任务的文件、这次运行的日志和轨迹，让它判断两件事，这次的分是不是靠钻空子拿的，以及失败是不是任务说明不清造成的。
  • 保存的产物可以重新评分。这是上一节版本规则的基础。
  • 能回答一个总分回答不了的问题。agent 的行为有很多个方面，评估为了方便把它概括成一个数。因为全部的记录是公开的，有人统计过各个模型交出的代码的长度，画成图，能看出哪个模型在同样的任务上写的代码明显更冗长。手里只有「一个系统的解决率是 60%、另一个是 55%」这样两个数时，这类问题无从回答。

Anthropic 的文章《Demystifying evals for AI agents》里有一句话可以当作这一节的总结：在有人深入看过评估的细节、读过一些运行轨迹之前，不要直接相信评估的分数。

自动评估之外的几种办法

这一讲说的都是自动评估：不需要真实的用户，用程序来跑和评分。它只是了解 agent 表现的办法之一。Anthropic 的文章把它和另外五种办法放在一起比较。下面的图里有四种：自动评估本身，加上线上监控、人工阅读运行轨迹和有组织的人工评测。图里没有的两种是 A/B 测试和用户反馈，见表注。

{{fig 63 | 一张对比表的两个部分，每一行是一种办法，列出它的长处和短处。左边是自动评估和线上监控，右边是人工阅读运行轨迹和有组织的人工评测。图片来源：Anthropic，Demystifying evals for AI agents。}}

文章的建议是把这些办法搭配着用。自动评估用在上线之前和每次改动之后，是第一道检查，线上监控在上线之后发现评估没覆盖到的问题。运行轨迹定期抽一些来读，有组织的人工评测留给校准模型评审和主观性强的输出。在线上发现的失败，可以再改写成新的评估任务。

Terminal-Bench 的作者补充了一点：自动评估的反馈来得最快，改一次 agent 就能测一次，所以它也是逐步提高 agent 表现的主要工具。

能不能从真实使用的记录里自动生成任务

一个自然的想法是：记录人实际工作的过程，或者从产品的使用记录里挑出失败的对话，让 agent 把它们自动改写成评估任务。Terminal-Bench 的作者认为这个方向是对的，难点在验证器。从观察里通常能得到任务说明，也能得到环境的一部分，手里有文件系统的副本时得到的更多。但是一次观察，不管看到的是做对还是做错，对验证器这个分类器（把每次运行分成通过和不通过两类的程序）来说只是一个样本。要写好验证器，得设想出各种可能的结果，再把通过和不通过的分界划对。

他们建议眼下把自动的办法和人工结合起来：从真实的使用里取材，用程序和模型把它整理成不需要真实用户、可以反复运行的任务，再让人检查验证器对不对。人的精力花在验证器上最划算：一个验证器要给成千上万次运行评分，自动的优化过程也是照着它给的分去改进 agent 的，在它上面做一点人工的改进，影响的是后面全部的结果。

整讲的小结

  • 评估是开发的中心。模型和 agent 对不对只能靠测量来判断，agent 生成的软件也越来越靠测量来判断。传统的开发流程从写规格说明（写明软件应该做什么的文档）开始，现在从定目标和做评估开始。模型和 agent 实际会做什么，最后以评估的结果为准。
  • 评估用的是一个个任务，任务是软件。一个任务是一个文件夹，里面有任务说明、环境、验证器、参考解法和一份配置文件。它要写，要测，要修，要发版本。
  • 最常见的问题是任务说明和验证器对不上。对不上的时候，验证器会把对的判错，也会把错的判对。第三部分写验证器的第一条原则管的就是这两种错：验证器的检查和任务说明里的要求一一对应。第二条原则是检查结果、不检查过程，它防的是把做法不同的正确结果判错。
  • 模型越强，越要防钻空子。主要的办法是把验证器和 agent 隔离开，只检查保存下来的产物。这个设计同时让重新评分成为可能。
  • 发布之后还要一直修。Terminal-Bench 2.0 发布前每个任务平均审查了大约三小时，之后仍然在 28 个任务里查出了问题。让一个基准测试长期可信的办法有三条：持续更新，按版本规则决定旧的结果是重新运行、重新评分还是直接沿用，公开每一次运行的记录。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • 2.1 版论文摘要里的「超过 10 个百分点」。Buchanan 等人的论文摘要里有一句「准确率上升超过 10 个百分点」，没有写明指的是哪些系统。持续更新一节用的是论文正文里的说法：单个系统的解决率最多变动 12 个百分点。
  • 解决率变动最大的系统。论文正文只说单个系统的解决率最多变动 12 个百分点，没有写是哪个系统，也没有写是升是降。2.1 版的公告列了 14 个系统在 2.0 和 2.1 上的成绩，其中变动最大的是模型 Opus 4.6 加运行框架 Claude Code，从 58.0% 提高到 70.1%，提高 12.1 个百分点。论文测的是 19 个系统，它说的 12 个百分点是不是这个系统，没有核对到。出处：2.1 版的公告。

  • 28 个任务里的 16 个。持续更新一节的缺陷分类表说 28 个任务里有 16 个属于任务说明和验证器对不上。论文正文只给了百分比 57%，附录里列出各类任务的表写明这一类是 16 个。
