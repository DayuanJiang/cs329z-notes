先看结论

  • 跑评估的基础设施要满足四条：出了故障能自己恢复，结果可复现，能并行地跑很多次运行，本机和云上都能跑。基础设施本身会影响分数。
  • 同一套「让 agent（能自己调用工具、分很多步完成任务的语言模型系统）在沙箱（隔离的运行环境）里做任务」的设施，可以用来评估，可以用来产生训练数据，也可以用来干实际的活。
  • 任务会以很不起眼的方式坏掉。发布前要过一组自动检查：静态检查，让 agent 审查任务的文件，跑参考解法（出题的人写的正确做法，应该满分），什么都不做（应该零分），让前沿的 agent 正常做一遍，让一个 agent 故意作弊一遍，再让 agent 读后两类运行的轨迹。
  • 任务是软件，软件有 bug。再仔细的发布前检查也查不完，大量的问题是在使用中暴露的。所以基准测试要持续地修、持续地发新版本。
  • 版本号有三位，分别表示旧的结果要重新运行、只要重新评分、可以直接沿用。这样修任务的成本才低到可以经常修。

做评估的九个步骤

把评估从无到有做起来，再长期维护下去，Anthropic 的文章《Demystifying evals for AI agents》把它分成三个阶段、九个步骤。

{{fig 55 | 三栏。左栏是建立任务集，四步：尽早开始，从手工测试开始，写没有歧义的任务，正反两种情况都覆盖。中栏是搭建评估框架，两步：搭一个可靠的评估框架，认真设计评分。右栏是维护，三步：检查运行轨迹（每一步动作和结果的完整记录），留意评估是否被做满（最好的系统接近满分），长期维护。图片来源：Anthropic 的同一篇文章。}}

对照这一讲的内容：第三部分讲的是第 2 步和第 5 步，也就是怎么写任务、怎么评分。这一部分讲第 4 步，以及第 6 到第 8 步。

跑评估的基础设施：四条要求

一个基准测试有几十个任务，每个任务跑 5 次，再乘上几十种模型和运行框架（包在模型外面、给它工具并管理多轮对话的程序）的组合，就是上万次运行。Terminal-Bench 2.0 的论文里一共跑了 32,155 次。每一次都要启动一个容器（隔离的、可以整个重建的运行环境），让 agent 在里面工作几分钟到几小时。能把这件事做好的基础设施，要满足四条。

+
基础设施的配置能让分数差出 6 个百分点。Anthropic 在 2026 年 2 月发表过一项实验：用同一个模型、同一个运行框架跑 Terminal-Bench 2.0，只改变给容器的 CPU 和内存。严格按任务标明的资源来限制时，有 5.8% 的运行因为基础设施出错而失败；完全不限制时降到 0.5%。资源最紧和最松的两种配置之间，成功率相差 6 个百分点。文章的建议是：排行榜上相差不到 3 个百分点的两个分数，在弄清双方的运行配置之前，不要当成有差别。Terminal-Bench 4.0 就是按这篇文章的办法重新校准每个任务的资源的。出处：Quantifying infrastructure noise in agentic coding evals。

同一套设施，三种用途

「让某个 agent 配某个模型，在一个沙箱里做一个任务，把过程和结果存下来」，这件事叫一次运行（rollout）。评估只是它的一种用途。

{{fig 57 | 中间是 Harbor 的运行引擎。上面一排是输入：任务、模型、agent、沙箱、技能。下面一排是产出的用途：轨迹分析、评估、优化、任务质量检查、产物（agent 交出的文件）。图上方的一句话是 Harbor 的自我介绍：一个让任何 agent 配任何模型、在任何沙箱里并行地跑任何任务的框架。}}

这和第一部分最后一节说的是同一件事：对 agent 来说，测试数据和训练数据是同一种格式的任务。基础设施也就可以共用。图里下面一排还有两项和评估本身有关：读运行轨迹来分析 agent 为什么失败，以及用 agent 去检查任务的质量。后一项是下一节的内容。

任务的质量检查：静态检查加上用 agent 来查

任务会以很不起眼的方式坏掉。一个任务能跑、能出分，不代表它是对的。

现在的任务已经相当大。按官方的说法，Terminal-Bench 3.0 里一个中等规模的任务有 20 个文件、4,000 行代码。它运行时还依赖操作系统、沙箱、模型接口和互联网。出题的人自己读一遍，已经不足以判断它对不对。所以检查也要自动化，而且其中很多步是让 agent 来做的。

{{fig 59 | 上面的方框是一个任务，下面是对它做的几类检查，每一类都和任务之间有来回的箭头，表示查出问题就回去改。从左到右：静态检查；让 agent 当评审来审查任务；参考解法、前沿的 agent、作弊的 agent 各跑一遍。后两种的运行轨迹再交给一个 agent 评审。}}

这七项检查按成本可以分成三档。前两项只看任务的文件，不启动环境：静态检查几秒钟，不花模型的钱；agent 评审要调用模型。参考解法和什么都不做这两项要启动一次环境，但不调用模型，很便宜。最后三项要真的让 agent 把任务跑一遍再读轨迹，最贵，能发现的问题也最多。在 Harbor 里，前两项对应 harbor lint 和 harbor check 两条命令，最后一项对应 harbor analyze。

这套检查接在代码仓库的持续集成（CI，每次有人提交改动就自动运行一遍的检查流程）上。新任务和对旧任务的每一次修改，都要全部通过才能合并。在使用中发现的新型问题，会被加成新的检查项。

i
通过了全部检查，任务仍然可能有问题。Harbor 的文档自己写着，静态检查是对别的检查的补充，不保证任务或验证器是对的。Terminal-Bench 2.0 的每个任务都经过了这类自动检查，外加平均大约三小时的人工审查，后来仍然在 89 个任务里的 28 个里查出了问题。这就是下一节要讲的事。

持续更新的基准测试：任务是软件，软件有 bug

传统的做法是把基准测试当成一份发布之后就不再改动的数据。Terminal-Bench 的作者在 2026 年 7 月提出另一种做法，叫持续更新的基准测试（continuous benchmark）：把它当成一个软件来维护。

{{fig 60 | 右边是一个循环。新的任务提交到代码仓库，经 Harbor 发布成一个带版本号的数据集，排行榜上的各个系统在它上面运行，结果公布在官网。运行中发现的问题再回到代码仓库，成为下一轮修改。左边列出了使用中会暴露的五类问题。}}

这个循环的关键在右下角那条回去的线：排行榜上的大量运行，相当于这个基准测试的真实使用。问题主要是在这里暴露的。有五类。

发布前的检查查不完这些问题，有一份专门的研究可以作证。Buchanan 等人在 2026 年 11 月的论文里回头检查了 Terminal-Bench 2.0。这个版本发布前经过了人工审查、语言模型辅助的审查和专门的找漏洞测试，但发布后几个月内，问题跟踪页上就积累了 50 多条标记为任务缺陷的报告。他们的系统检查在 89 个任务里的 28 个里确认了问题，修复之后发布为 2.1 版。论文拿 19 个模型和运行框架的组合在 2.0 和 2.1 上各测了一遍：单个组合的解决率最多变动 12 个百分点，排行榜上的名次最多变动三位，整体的排序仍然高度相关。摘要里还有一句「准确率上升超过 10 个百分点」，没有写明指的是哪些组合。

这篇论文给这种现象起了个名字，叫基准测试的维护债：任务里的缺陷越积越多，分数和它想测量的能力之间的差距越拉越大。

版本号：旧的结果还能不能用

经常修任务有一个现实的障碍。排行榜上有几十个系统，每个系统跑一遍要花几千美元。如果每修一个任务都要所有系统重跑，就没有人愿意修。解决的办法是给每个任务一个三位的版本号，用哪一位变了来表示旧的结果该怎么处理。

{{fig 61 | 版本号的三位各管一类改动。第一位加一，表示改的是 agent 面对的环境，旧的结果要重新运行。第二位加一，表示改的是验证器，旧的结果只要重新评分。第三位加一，表示改的是元数据，旧的结果可以直接沿用。每一类下面列了几种典型的改动。}}

整个基准测试的版本号跟着任务走：这一次发布里，各个任务的改动里最大的是哪一位，基准测试的版本号就加哪一位。升级排行榜的时候，Harbor 把已有的全部运行和新版本逐个任务对比，只有第一位变了的任务才重跑，第二位变了的重新评分，其余的沿用。

有了这个规则，第二部分版本表里两处看起来奇怪的地方就能解释了。

  • 4.0 为什么不叫 3.1。4.0 没有新任务，但它改了每个任务给 agent 的资源和时间上限，还删掉了任务。这些都是 agent 面对的东西，旧的运行要重跑，所以加的是第一位。官方也承认这在短期内会让人困惑，因为大家习惯把第一位的变化当成一个全新的续作。
  • 4.1 为什么只加第二位。它只改了验证器。4.0 排行榜上全部系统的运行一共花了 11.6 万美元的模型调用费用。升级到 4.1 时，用保存下来的产物重新评分，新增的模型调用费用是 0。11,550 次运行里，分数有变化的是 162 次，其中 134 次确认是验证器的改动带来的，另外 28 次是两次验证之间的测量差异，保留了原来的分数。出处：4.1 版的公告。

重新评分之所以做得到，前提是第三部分讲的那个设计：验证器在单独的环境里运行，只检查 agent 交出的产物，而产物是保存下来的。防钻空子和省钱，用的是同一个办法。

每个任务自己的版本历史写在它的说明文件里。例如第二部分那个三维建模的任务，把时间上限改成 8 小时、内存改成 8 GB 的那一次，版本号从 1.0.7 变成 2.0.0；之后的几次改动加的都是第三位，内容大多是固定依赖版本、更新元数据。其中 2.0.4 这一次还把验证器改成了用统一的评分库来写，按上面的规则，改验证器应该加第二位。说明文件没有解释原因，很可能是因为这次改动不改变评分的结果。

结果：每一行都带着全部的凭据

排行榜上的一个数，背后是几百次运行。Terminal-Bench 的做法是把每一次运行的全部材料都公开：运行轨迹、日志、agent 交出的产物、得分。排行榜上的每一行都能点进去，一直看到某一次运行的某一步。第二部分的图里就是这样一个页面。

这样做有三个用处。

  • 别人可以检查分数。怀疑某个系统的高分是靠钻空子来的，可以去读它的轨迹。4.1 版修掉的问题里，有一部分就是外部的机构审查这个基准测试之后提出来的。
  • 出题的人可以发现任务的问题。前面说的五类问题，大多是读轨迹读出来的。轨迹太多，人读不过来，所以也让 agent 来读：给它任务的文件、这次运行的日志和轨迹，让它判断两件事，这次的分是不是靠钻空子拿的，以及失败是不是任务说明不清造成的。
  • 保存的产物可以重新评分。这是上一节版本规则的基础。

Anthropic 的文章里有一句话可以当作这一节的总结：在有人深入看过评估的细节、读过一些运行轨迹之前，不要直接相信评估的分数。

自动评估之外的几种办法

这一讲说的都是自动评估：不需要真实的用户，用程序来跑和评分。它只是了解 agent 表现的办法之一。Anthropic 的文章把它和另外几种办法放在一起比较，下面的图里能看到其中四种。

{{fig 63 | 一张对比表的两个部分，每一行是一种办法，列出它的长处和短处。左边是自动评估和线上监控，右边是人工阅读运行记录和系统的人工评测。图片来源：Anthropic，Demystifying evals for AI agents。}}

文章的建议是把这些办法搭配着用：自动评估用在上线之前和每次改动之后，是第一道检查；线上监控在上线之后发现评估没覆盖到的问题；定期抽一些运行记录来读；系统的人工评测留给校准模型评审和主观性强的输出。在线上发现的失败，可以再改写成新的评估任务。

整讲的小结

  • 评估是开发的中心。模型和 agent 对不对只能靠测量来判断，agent 生成的软件也越来越靠测量来判断。规格说明在传统软件开发里的位置，现在由评估占着。
  • 评估由任务组成，任务是软件。一个任务有任务说明、环境、验证器和参考解法。它要写，要测，要修，要发版本。
  • 最常见的问题是任务说明和验证器对不上。验证器会把对的判错，也会把错的判对。让两者一一对应，按结果评分，是写任务时最要紧的两件事。
  • 模型越强，越要防钻空子。主要的办法是把验证器和 agent 隔离开，只检查保存下来的产物。这个设计同时让重新评分成为可能。
  • 发布之后还要一直修。Terminal-Bench 2.0 发布前每个任务平均审查了大约三小时，之后仍然在 28 个任务里查出了问题。持续更新、按版本规则迁移旧结果、公开每一次运行的记录，是让一个基准测试长期可信的办法。
