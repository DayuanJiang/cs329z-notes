先看结论

  • 跑评估的基础设施要满足四条：出了故障能自己恢复，结果可复现，能并行地跑很多次运行，本机和云上都能跑。基础设施本身会影响分数。
  • 同一套「让 agent（能自己调用工具、分很多步完成任务的语言模型系统）在沙箱（隔离的运行环境）里做任务」的基础设施，可以用来评估，可以用来产生训练数据，也可以用来干实际的活。
  • 任务出了错往往不容易看出来，所以发布前要过一组自动检查。先用程序扫描任务的文件，再让 agent 审查这些文件。然后运行参考解法（出题的人写的正确做法），它应该得满分。再启动环境，什么都不做就评分，这时应该得零分。最后让前沿的 agent（当下能力最强的那一批）正常做一遍，让一个 agent 故意去钻空子（靠利用评分办法的漏洞拿到分数），再让 agent 读这两类运行的运行轨迹（每一步动作和结果的完整记录）。
  • 任务是软件，软件有 bug。再仔细的发布前检查也查不完，大量的问题是在使用中暴露的。所以基准测试要持续地修、持续地发新版本。
  • 版本号有三位，分别表示旧的结果要重新运行、只要重新评分、可以直接沿用。这样修任务的成本才低到可以经常修。

做评估的九个步骤

把评估从无到有做起来，再长期维护下去，Anthropic 的文章《Demystifying evals for AI agents》把它分成三个阶段、九个步骤。这一节先列出这九步，再对照这一讲的各部分讲的是其中哪几步。

下面的图和表里会出现评估框架（evaluation harness）这个词，它指把评估从头跑到尾的那套程序：准备环境、并行地跑任务、记录每一步、打分、汇总。

{{fig 55 | 三栏。左栏是建立任务集，四步：尽早开始，从手工测试开始，写没有歧义的任务，正反两种情况都覆盖。中栏是搭建评估框架，两步：搭一个可靠的评估框架，认真设计评分。右栏是维护，三步：检查运行轨迹（每一步动作和结果的完整记录），留意评估是否被做满（agent 已经通过了全部做得成的任务，分数没有再提高的余地），长期维护。图片来源：Anthropic 的同一篇文章。}}

对照这一讲的内容：第三部分讲的是第 2 步和第 5 步，也就是怎么写任务、怎么评分。这一部分讲第 4 步、第 6 步和第 8 步。第 7 步说的是整个评估被做满。第二部分讲版本的一节讲的是单个任务被做满，也就是各个系统都能稳定通过这个任务，Terminal-Bench 的应对办法是删掉或换掉这样的任务。

跑评估的基础设施：四条要求

这一节说的基础设施，就是上一节第 4 步里的评估框架。它要应付的运行次数很多。一个基准测试有几十个任务，每个任务跑 5 次，再乘上几十种模型和运行框架（包在模型外面、给它工具并管理多轮对话的程序）的组合，就是上万次运行。每一次都要启动一个容器（隔离的、可以整个重建的运行环境），让 agent 在里面工作几分钟到几小时。下面把一个模型配一个运行框架的组合叫作一个系统。

这一页用 Terminal-Bench 当例子。它是一个基准测试，让 agent 在容器里完成真实的技术工作，再用测试检查结果。它已经出了六个版本，后面会提到其中的 2.0、2.1、3.0、4.0 和 4.1，各版的差别见第二部分的版本表。运行它用的评估框架叫 Harbor，是同一批作者做的开源工具。Terminal-Bench 2.0 的论文里一共跑了 32,155 次。

能把这么多次运行跑好的基础设施，要满足四条。

这四条为的是同一件事：靠比较分数来做决定的时候，分数必须可比，并且要尽快、尽量便宜地拿到。其中三条值得多说一句。

可复现这一条，要求基础设施自己不给结果添波动。agent 本身有随机性，同样的配置跑两遍，结果已经有不小的波动，基础设施不应该再添一份。

快这一条受几种有限资源的限制。能同时跑多少次运行，要看模型接口的 token（模型处理文字的基本单位）配额、沙箱服务的容量，以及镜像仓库这类外部服务允许的访问频率。镜像（image）是打包好的环境，容器从它启动，镜像仓库是存放镜像的服务。把并行度调到合适通常要花一些工夫。

可移植这一条的用处不限于公开的基准测试。一个团队在本机调试任务、在云上大规模运行，两边的结果也要能互相比较。

+
基础设施的配置能让分数差出 6 个百分点。Anthropic 在 2026 年 2 月发表过一项实验：用同一个模型、同一个运行框架跑 Terminal-Bench 2.0，只改变给容器的 CPU 和内存。严格按任务标明的资源来限制时，有 5.8% 的运行因为基础设施出错而失败。完全不限制时，这个比例降到 0.5%。资源最紧和最松的两种配置之间，成功率相差 6 个百分点。文章的建议是：排行榜上相差不到 3 个百分点的两个分数，在弄清双方的运行配置之前，不要当成有差别。Terminal-Bench 4.0 就是按这篇文章的办法重新校准每个任务的资源的。出处：Quantifying infrastructure noise in agentic coding evals。

同一套基础设施，三种用途

前面一直说的「一次运行」（trial，也叫 rollout），指的是让某个运行框架配某个模型，在一个沙箱里做一个任务，把过程和结果存下来。评估只是它的一种用途。

{{fig 57 | 中间是 Harbor 的运行引擎。上面一排是输入：任务、模型、agent、沙箱、技能文档（skills，写着某类工作该怎么做的说明文件，agent 需要时再读）。下面一排是产出的用途：轨迹分析、评估、优化、任务质量检查、产物（agent 交出的文件）。图上方的一句话是 Harbor 的自我介绍：一个让任何 agent 配任何模型、在任何沙箱里并行地跑任何任务的框架。图里和模型并列的 agent 指运行框架。}}

这和第一部分最后一节说的是同一件事：对 agent 来说，测试数据和训练数据是同一种格式的任务。按 Terminal-Bench 作者的说法，有人卖给模型厂商用来训练模型的任务，用的就是这同一种任务格式。

任务的格式相同，基础设施也就可以共用。训练模型时也要批量运行 agent、收集轨迹，做这件事的服务遇到的问题，和评估的基础设施遇到的一样。把 agent 放到生产环境里干活时，也常常遇到这些问题。

图里下面一排还有两项和评估本身有关：读运行轨迹来分析 agent 为什么失败，以及用 agent 去检查任务的质量。后一项是下一节的内容。

任务的质量检查：静态检查加上用 agent 来查

任务出了错，往往不容易看出来。一个任务能跑、能出分，不代表它是对的。

现在的任务已经相当大。Terminal-Bench 官网的文章 Continuous Benchmarks 举过一个数：3.0 版里一个中等规模的任务有 20 个文件、4,000 行代码。它运行时还依赖操作系统、沙箱、模型接口和互联网。出题的人自己读一遍，已经不足以判断它对不对。所以检查也要自动化，而且其中很多步是让 agent 来做的。

{{fig 59 | 上面的方框是一个任务，下面是对它做的几类检查，每一类都和任务之间有来回的箭头，表示查出问题就回去改。从左到右：静态检查；让 agent 当评审来审查任务；参考解法、前沿的 agent、钻空子的 agent 各跑一遍。后两种的运行轨迹再交给一个 agent 评审。}}

这七项检查可以分成三档。第一档只看任务的文件，不运行任务。第二档启动任务的环境，但没有 agent 来做任务。第三档真的让 agent 把任务做一遍。第三档最贵，能发现的问题也最多。下表列出每一档包括哪几项检查、要不要运行任务、要不要调用模型。

第一档的两项直接给出不合格或告警，出题的人照着改。静态检查查的是能用程序判断的东西，例如任务的配置文件 task.toml 写得对不对，也可以自己加规则，比如限制任务说明的长度。任务说明和验证器是否一一对应，要读懂两边的意思才能判断，所以交给 agent 评审。

第三档要真的让 agent 跑，常常能发现事先想不到的问题。例如环境里装的某个软件包的版本在这个任务里用不了。软件包坏了这种障碍不属于想测的能力，应该修掉。

第三档更常见的发现是：出题的人以为任务难在一处，agent 实际卡住的是另一处。要看清任务真正难在哪一步，还有一种做法：给 agent 一些提示，看最少要给多少它才能做成。

这套检查接在代码仓库的持续集成（CI，每次有人提交改动就自动运行一遍的检查流程）上。新任务和对旧任务的每一次修改，都要全部通过才能合并。在使用中发现的新型问题，会被加成新的检查项。

i
通过了全部检查，任务仍然可能有问题。Harbor 的文档自己写着，静态检查是对别的检查的补充，不保证任务或验证器是对的。下一节用 Terminal-Bench 2.0 的例子说明这一点。

持续更新的基准测试：任务是软件，软件有 bug

传统的做法是把基准测试当成一份发布之后就不再改动的数据。Terminal-Bench 的作者在 2026 年 7 月提出另一种做法，叫持续更新的基准测试（continuous benchmark）：把它当成一个软件来维护。

{{fig 60 | 右边是一个循环。新的任务提交到代码仓库，经 Harbor 发布成基准测试的一个带版本号的新版本，排行榜上的各个系统在这个版本上运行，结果公布在官网。运行中发现的问题再回到代码仓库，成为下一轮修改。左边列出了使用中会暴露的五类问题。}}

这个循环的关键是从运行回到代码仓库的那一步：排行榜上的大量运行，相当于这个基准测试的真实使用。问题主要是在这里暴露的。有五类。

误判不通过和钻空子这两类，特别依赖更强的新模型来暴露。较弱的模型在任务的前几步就失败了，走不到验证器有问题的地方。模型变强之后，它把任务做对了，验证器却判它不通过，这个问题才第一次显现。钻空子也一样，模型越强，用出的手法越出人意料。这两类问题一出现，就要据此修改任务。

发布前的检查查不完这些问题，有一份专门的研究可以作证。Buchanan 等人 2026 年 11 月的论文，记录了对 Terminal-Bench 2.0 的一次回头检查。检查和修复在先，修复后的 2.1 版按第三方的介绍在 2026 年 5 月就发布了，论文是之后才发表的。

2.0 版发布前，每个任务都过了上一节那类自动检查，还经过了人工审查、语言模型辅助的审查和专门的找漏洞测试，其中人工审查平均每个任务大约三小时。发布后几个月内，问题跟踪页上仍然积累了 50 多条标记为任务缺陷的报告。这篇论文的作者对全部 89 个任务做了一次系统的检查，在其中 28 个里确认了问题，修复之后发布为 2.1 版。

修复改变了评估的结果。论文拿 19 个系统（模型和运行框架的组合）在 2.0 和 2.1 上各测了一遍，比的是解决率，也就是测试通过的运行占全部运行的比例。单个系统的解决率最多变动 12 个百分点，排行榜上的名次最多变动三位，整体的排序仍然高度相关。

论文把这 28 个任务的缺陷分成三类，见下表。它和上面的五类是两种分法，可以这样对照着读：上面的五类说的是问题在运行中表现成什么样，下表的三类说的是缺陷出在哪里。例如测试过严属于下表的第一类，表现出来就是上面的误判不通过。资源给得不合适属于下表的第三类，表现出来就是上面的基础设施噪声。

这篇论文给这种现象起了个名字，叫基准测试的维护债（benchmark maintenance debt）：任务里的缺陷越积越多，分数和它想测量的能力之间的差距越拉越大。

版本号：旧的结果还能不能用

经常修任务有一个现实的障碍。排行榜上有几十个系统，每个系统跑一遍要花几千美元。如果每修一个任务都要所有系统重跑，就没有人愿意修。解决的办法是给每个任务一个三位数字的版本号，用哪一位变了来表示旧的结果该怎么处理。

{{fig 61 | 版本号的三位各表示一类改动。第一位加一，表示改的是 agent 面对的环境，旧的结果要重新运行。第二位加一，表示改的是验证器，旧的结果只要重新评分。第三位加一，表示改的是元数据（关于任务的说明性信息，例如文档和分类），旧的结果可以直接沿用。每一类下面列了几种典型的改动。}}

第三位里有两项改动也碰了任务说明和环境：改任务说明里的错别字，把会变动的依赖固定到具体版本。它们归在第三位，因为分界看的是改动对分数有没有实质影响。Continuous Benchmarks 一文的说法是，对分数没有实质影响的改动可以直接沿用旧的结果，明显改变了 agent 所处环境的改动才需要重新运行。

整个基准测试的版本号跟着任务走：这一次发布里，各个任务的改动里最大的是哪一位，基准测试的版本号就加哪一位。升级排行榜的时候，Harbor 把已有的全部运行和新版本逐个任务对比，只有第一位变了的任务才重跑，第二位变了的重新评分，其余的沿用。

Terminal-Bench 的版本里有两处看起来奇怪，见第二部分的版本表。4.0 没有新任务，用的还是 3.0 的那些，第一位却加了一。4.1 让一部分运行的得分变了，却只加了第二位。按上面的规则，两处都能解释。

  • 4.0 为什么不叫 3.1。4.0 的公告举了两项改动，都算作必须重跑的改动。一项是每个任务给 agent 的资源和时间上限变了，这属于 agent 面对的东西。另一项是删掉了任务，任务集变了。所以加的是第一位。公告也承认这在短期内会让人困惑，因为大家习惯把第一位的变化看成换了全新的一代。
  • 4.1 为什么只加第二位。它只改了验证器，agent 面对的东西没有变，所以旧的运行只要重新评分。这样省下的钱很多：4.0 排行榜上全部系统的运行一共花了 11.6 万美元的模型调用费用，升级到 4.1 时用保存下来的产物重新评分，新增的模型调用费用是 0。

这次重新评分改变的得分很少。11,550 次运行里，得分有变化的是 162 次。其中 134 次确认是验证器的改动带来的。公告把另外 28 次归为两次运行验证器之间的测量差异，也就是同一份产物评两次、结果不一样，和验证器的改动无关。这 28 次保留了原来的得分。出处：4.1 版的公告。

重新评分之所以做得到，前提是第三部分讲的那个设计：验证器在单独的环境里运行，只检查 agent 交出的产物，而产物是保存下来的。防钻空子和省钱，用的是同一个办法。

每个任务自己的版本历史写在任务目录的 README 文件里。README 是写给人看的说明，和交给 agent 的任务说明 instruction.md 是两份文件。例如第二部分那个三维建模的任务，把时间上限改成 8 小时、内存改成 8 GB 的那一次，版本号从 1.0.7 变成 2.0.0。之后的几次改动加的都是第三位，内容大多是固定依赖版本、更新元数据。其中 2.0.4 这一次和规则对不上，见资料说明。

任务经常改，不同时间测的分数还能不能比

基准测试的一个基本用途是比较结果。任务经常改，这周发布的模型和下周发布的模型面对的题目就可能不同。Terminal-Bench 的作者讲了三点。前两点是他们自己的做法，第三点是模型厂商已有的习惯。

  • 控制发布的节奏。新版本不会每天都发，两次发布之间留出足够的时间，厂商报告成绩时不至于赶上题目中途变动。
  • 排行榜尽快更新到新版本，并保留全部历史结果。新模型仍然可以和以前所有的模型比较。
  • 厂商的发布文档里本来就带着对比。发布文档（model card）是模型厂商发布新模型时公布的说明和测评成绩。每个新模型发布时，成绩表里会同时列出其他模型的成绩，读的人不用自己去找别的模型以前的分数。表里其他模型的成绩是不是在同一个版本上测的，作者没有说明。

他们同时认为，整个行业应该改掉在图片里贴一张成绩表的做法，把每个数连到完整的结果上，也就是全部的运行和每一次的得分。下一节讲 Terminal-Bench 自己是怎么做的。

结果：每一行都能查到全部的运行记录

排行榜上的一个数，背后是几百次运行。Terminal-Bench 的做法是把每一次运行的全部材料都公开：运行轨迹、日志、agent 交出的产物、得分。排行榜上的每一行都能点进去，一直看到某一次运行的某一步。第二部分的图里就是这样一个页面。

这样做有四个用处。

  • 别人可以检查分数。怀疑某个系统的高分是靠钻空子来的，可以去读它的轨迹。Terminal-Bench 公布结果之后，社区里就有人翻这些记录，找出了钻空子的运行。4.1 版修掉的问题里，有一部分就是外部的机构审查这个基准测试之后提出来的。
  • 出题的人可以发现任务的问题。前面说的五类问题，大多是读轨迹读出来的。轨迹太多，人读不过来，所以也让 agent 来读：给它任务的文件、这次运行的日志和轨迹，让它判断两件事，这次的分是不是靠钻空子拿的，以及失败是不是任务说明不清造成的。
  • 保存的产物可以重新评分。这是上一节版本规则的基础。
  • 能回答一个总分回答不了的问题。agent 的行为有很多个方面，评估为了方便把它概括成一个数。有了全部的记录，就有人统计了各个模型交出的代码的长度，画成图，能看出哪个模型在同样的任务上写的代码明显更冗长。手里只有「一个 60 分、另一个 55 分」这样两个数时，这类问题无从回答。

Anthropic 的文章里有一句话可以当作这一节的总结：在有人深入看过评估的细节、读过一些运行轨迹之前，不要直接相信评估的分数。

自动评估之外的几种办法

这一讲说的都是自动评估：不需要真实的用户，用程序来跑和评分。它只是了解 agent 表现的办法之一。Anthropic 的文章把它和另外几种办法放在一起比较，下面的图里能看到其中四种。

{{fig 63 | 一张对比表的两个部分，每一行是一种办法，列出它的长处和短处。左边是自动评估和线上监控，右边是人工阅读运行记录和系统的人工评测。图片来源：Anthropic，Demystifying evals for AI agents。}}

文章的建议是把这些办法搭配着用：自动评估用在上线之前和每次改动之后，是第一道检查；线上监控在上线之后发现评估没覆盖到的问题；定期抽一些运行记录来读；系统的人工评测留给校准模型评审和主观性强的输出。在线上发现的失败，可以再改写成新的评估任务。

Terminal-Bench 的作者补充了一点：自动评估的反馈来得最快，改一次 agent 就能测一次，所以它也是逐步提高 agent 表现的主要工具。

能不能从真实使用的记录里自动生成任务

一个自然的想法是：记录人实际工作的过程，或者从产品的使用记录里挑出失败的对话，让 agent 把它们自动改写成评估任务。Terminal-Bench 的作者认为这个方向是对的，难点在验证器。从观察里通常能得到任务说明，也能得到环境的一部分，手里有文件系统的副本时得到的更多。但是一次观察，不管看到的是做对还是做错，对验证器这个分类器来说只是一个样本。要写好验证器，得设想出各种可能的结果，再把通过和不通过的分界划对。

他们建议眼下把自动的办法和人工结合起来：从真实的使用里取材，用程序和模型把它整理成不需要真实用户、可以反复运行的任务，再让人检查验证器对不对。人的精力花在验证器上最划算：一个验证器要给成千上万次运行评分，自动的优化过程也是照着它给的分去改进 agent 的，在它上面做一点人工的改进，影响的是后面全部的结果。

整讲的小结

  • 评估是开发的中心。模型和 agent 对不对只能靠测量来判断，agent 生成的软件也越来越靠测量来判断。规格说明（写明软件应该做什么的文档）在传统软件开发里的位置，现在由评估占着。
  • 评估由任务组成，任务是软件。一个任务有任务说明、环境、验证器和参考解法。它要写，要测，要修，要发版本。
  • 最常见的问题是任务说明和验证器对不上。验证器会把对的判错，也会把错的判对。让两者一一对应，按结果评分，是写任务时最要紧的两件事。
  • 模型越强，越要防钻空子。主要的办法是把验证器和 agent 隔离开，只检查保存下来的产物。这个设计同时让重新评分成为可能。
  • 发布之后还要一直修。Terminal-Bench 2.0 发布前每个任务平均审查了大约三小时，之后仍然在 28 个任务里查出了问题。持续更新、按版本规则迁移旧结果、公开每一次运行的记录，是让一个基准测试长期可信的办法。
