先看结论

  • LangGraph 是一个把程序写成图的 Python 框架（framework，写程序时调用的库）。它有三个概念：state（状态）是整张图共用的一份数据，node（节点）是读写状态的函数，edge（边）规定一个节点跑完之后去哪个节点。
  • 带条件的边由一个普通的 Python 函数来判断走哪条路。有了它，图就能表达带分支的 workflow。workflow 指步骤由程序写定的多次模型调用，这一页的日历程序就是一个：邮件里有日程才继续，没有就结束。
  • agent（能自己调用工具、分很多步完成任务的语言模型系统）也可以写成一张很小的 LangGraph 图：一个模型节点，一个工具节点，在两者之间循环，状态是消息的历史。用 LangChain 这个库里的函数 create_agent 两行就能建出来。
  • DSPy 是第二、第三部分讲的另一个 Python 框架。它和 LangGraph 能解决同一类问题，提供给写程序的人的概念不同。DSPy 的重点是声明输入输出和自动优化 prompt（给模型的输入文字）。LangGraph 的重点是把控制流（程序里「接下来执行哪一步」的决定）写成一张图：每一步跑完之后的状态都看得到，另外配上一个保存状态快照的部件之后，流程可以在中断后恢复。两者可以一起用。

三个概念：状态、节点、边

第二部分用 DSPy 写了一个日历程序：读一封邮件，里面提到日程就把它加到日历上。那个程序里的分支只是一个普通的 if。LangGraph 要把同一个程序写成一张图。

这样写有两个好处。一是每一步跑完之后的状态都看得到，便于观测。二是另外配上一个保存状态快照的部件之后，流程可以在中断后恢复。

先说观测。这一页后面的例子都用 invoke 方法运行图，只取了最后的状态。要看中间的每一步，可以改用图的 stream 方法运行，它每跑完一步就输出一次当时的状态。stream 方法在这一页的例子里没有用到，它的用法见 LangGraph 文档的 streaming 一节。

再说恢复。保存状态快照的部件叫 checkpointer，它存下的每一份快照叫检查点（checkpoint）。图每推进一轮，checkpointer 就存一份检查点。一轮指一批同时运行的节点跑完，这一页的图里节点都是一个接一个运行的，所以每跑完一个节点就存一份。

LangGraph 出自 LangChain 公司。LangChain 是这家公司的另一个 Python 库。这一页用到 LangChain 的两样东西：一是调用模型用的对象，二是建 agent 的函数 create_agent，这个函数建出来的 agent 就是一张 LangGraph 的图。

官方文档对 LangGraph 的定位是一个底层的编排框架和运行时，面向长时间运行、带状态的 agent。编排（orchestration）指安排多个步骤按什么顺序执行、中途出错怎么办。运行时（runtime）指负责把写好的程序实际跑起来的那部分软件。带状态指 agent 在各步之间一直保留着一份数据。

「底层」是和 create_agent 这类现成的 agent 循环相比说的。LangGraph 只提供状态、节点和边这几样基本部件，图怎么搭、prompt 怎么写，都由写程序的人决定。

可以这样理解 LangGraph 的位置：它管的事介于 DSPy 和第六部分的 Temporal 之间。和 DSPy 一样，它用来把多次模型调用写成一个程序。它还管一部分程序怎样运行的事，也就是上面说的存检查点和中断后恢复，而 Temporal 是专门做这件事的工具。

用 LangGraph 写程序，就是回答三个问题：整张图共用的那份数据有哪些字段，有哪些步骤，步骤之间怎么走。

最简单的图：一个节点

先准备一个输出有结构的模型

这里调用模型用的是 LangChain 的模型封装，也就是 LangChain 把模型的接口包成的一个 Python 对象。下面代码里的 langchain_llm 就是这样一个对象。它调用的模型是 gpt-5.4-nano，和第二部分的 DSPy 版本用的是同一个。

要让模型的输出符合固定的结构，先用 Pydantic（一个用类来声明数据格式的 Python 库）写一个类，再用 with_structured_output 把模型和这个类绑在一起：

from pydantic import BaseModel, Field

class EventDetails(BaseModel):
    """Extract event details from an email."""
    event_name: str | None = Field(description="short title for the event, e.g. 'Dentist' or 'Meeting'. Always set when the email mentions an event")
    date: dt.date | None
    start: dt.time | None = Field(description="24-hour clock")
    duration_minutes: int | None = Field(description="duration of the event in minutes, if known")

extract_llm = langchain_llm.with_structured_output(EventDetails)

第二部分的 DSPy 版本里，声明提取结果的那个类叫 ExtractEvent。这里的四个字段和它的四个输出字段是同一组：名称、日期、开始时间、时长。之后调用 extract_llm，得到的就是一个 EventDetails 对象。

状态和节点

状态有两个字段：邮件原文，和提取出来的日程。节点只有一个，它从状态里读邮件，调用模型，把结果写回 details。

from typing import TypedDict

class State(TypedDict):
    email: str
    details: EventDetails | None

def extract_node(state: State):
    return {"details": extract_llm.invoke(state["email"])}

注意节点的返回值：它只返回自己改动的字段。LangGraph 看到返回的字典里只有 details，就只更新状态里的这一项，email 保持原样。

把图搭起来

搭图分三步：登记节点，连上边，最后编译。编译（compile）这一步检查图的结构，比如有没有连不到的节点，然后返回一个可以调用的图。图必须先编译才能运行。DSPy 里也有一个叫 compile 的方法，它属于优化器，也就是 DSPy 里自动改进程序的部件，做的事和这里的编译是两回事。

from langgraph.graph import StateGraph, START, END

builder = StateGraph(State)
builder.add_node("extract", extract_node)
builder.add_edge(START, "extract")
builder.add_edge("extract", END)
graph = builder.compile()

这张图只有一条路：从起点到 extract，再到终点。用一封邮件调用它：

graph.invoke({"email": "We have a meeting scheduled for this Friday, October 9th at 10 AM PST."})

调用时传入的是初始的状态，返回的是跑完之后的状态。返回值里 email 还是那封邮件，details 是 EventDetails(event_name='Meeting', date=datetime.date(2026, 10, 9), start=datetime.time(10, 0, tzinfo=TzInfo(-25200)), duration_minutes=None)。

TzInfo(-25200) 是时区，括号里的数是它相对 UTC（协调世界时）的偏移，单位是秒，-25200 秒也就是比 UTC 晚 7 小时。这个偏移和邮件有 1 小时的出入：邮件里写的是 PST，PST 比 UTC 晚 8 小时，模型给出的偏移对应的是晚 7 小时。这是演示里模型输出的原样。

i
同一封邮件，两个框架的结果在细节上不一样。DSPy 版本提取出的开始时间是 datetime.time(10, 0)，不带时区，名称是小写的 meeting。这里的开始时间带上了时区，名称是大写开头的 Meeting。模型是同一个。差别很可能来自两个框架发给模型的 prompt 和解析回答的方式不同，比如这里的字段说明里举的例子就是大写开头的 Meeting。模型的输出在两次运行之间本来也会有一点波动。这一次的差别里，框架不同和模型自身的波动各占多少，演示没有做对照。换框架之后，后面用到这些提取结果的代码要重新检查。

带条件的边：让图能分支

完整的程序有一个分支：邮件里有日程才继续，没有就结束。先扩充状态，再加两个节点。

class CalendarState(State):
    emoji: str
    status: str

def pick_emoji_node(state: CalendarState):
    reply = langchain_llm.invoke(f"Reply with exactly one emoji character, nothing else, for a calendar event called '{state['details'].event_name}'.")
    return {"emoji": reply.text.strip()}

def add_to_calendar_node(state: CalendarState):
    d = state["details"]
    tinycal.add_event(d.event_name, d.date, d.start, duration_minutes=d.duration_minutes, emoji=state["emoji"])
    return {"status": "added to calendar"}

两个节点里放的东西不一样。pick_emoji_node 调用了一次模型，prompt 是直接手写的一句话。add_to_calendar_node 没有调用模型，只调用了日历的接口。节点里可以写任何 Python 代码，所以不同的节点也可以用不同的模型。

带条件的边要配一个做判断的函数。这个函数读状态，返回下一个节点的名字：

from typing import Literal

def route(state: CalendarState) -> Literal["pick_emoji", "__end__"]:   # plain Python decides where to go next
    d = state["details"]
    return "pick_emoji" if d.event_name and d.date and d.start else END

判断的规则和 DSPy 版本里的 if 是同一条：名称、日期、开始时间都有，就去挑表情符号；缺了任何一样，就直接走到终点。

然后把三个节点和五条边登记到图里。连边的调用是四次，其中 add_conditional_edges 这一次把 route 交给图，登记了从 extract 出发的两条带条件的边：

builder = StateGraph(CalendarState)
builder.add_node("extract", extract_node)
builder.add_node("pick_emoji", pick_emoji_node)
builder.add_node("add_to_calendar", add_to_calendar_node)

builder.add_edge(START, "extract")
builder.add_conditional_edges("extract", route)        # dotted arrows in the drawing
builder.add_edge("pick_emoji", "add_to_calendar")
builder.add_edge("add_to_calendar", END)

calendar_graph = builder.compile()

在 LangGraph 里搭一个 agent

和 DSPy 一样，LangGraph 这一边也有现成的办法建 agent，用的是 LangChain 里的函数 create_agent：

from langchain.agents import create_agent
langchain_cal_agent = create_agent(langchain_llm, tools=tinycal.TOOLS)

它返回的是一张 LangGraph 的图，可以像前面的图一样画出来。

{{figs 58 74 | 左：一个 LangGraph agent 的示意图。状态可以是消息的历史。模型节点和工具节点之间可以循环任意多次，直到模型决定结束。右：create_agent 建出来的图。从 model 出来有两条带条件的边，一条去 tools，一条去终点；tools 跑完再回到 model。}}

这张图和上一节「带条件的边：让图能分支」里的 workflow 用的是同一套部件，差别在于带条件的边由谁来判断。workflow 里是 route 这样一个规则由人事先写定的函数。agent 里，走哪条边取决于模型刚才的回答：回答里要求调用工具，就去工具节点；没有要求调用工具，就结束。图的结构还是人定的，交给模型决定的是每次从模型节点出来走哪一条边。

LangChain 的文档对这个循环的描述是：调用模型，让它选择要执行的工具，它不再调用工具时就结束。这和第三部分的 ReAct 是同一类循环。ReAct 是一种 agent 的结构，模型在一个循环里交替地写想法、调用工具、读结果。

第三部分里，用 DSPy 搭的 agent 在日历上排了一个 10 月 7 日 15:00 到 15:30 的「Coffee with John」。给这里的 agent 一个请求，把这个日程往后挪 30 分钟：

langchain_cal_agent.invoke({"messages": [("user", "Please move my coffee with John on Oct 7th to be 30 minutes later")]})

DSPy 和 LangGraph 怎么选

两个框架写出了做同一件事的程序，只在提取结果的细节上有差别，见前面「同一封邮件，两个框架的结果在细节上不一样」那个框。下表把两种写法并排放在一起。表里的优化器是 DSPy 里根据数据和度量自动改进程序的部件，改的是程序里的 prompt 或模型权重（模型里经过训练得到的参数），度量是给程序的输出打分的函数。

关于这张表，还有四点要说明。

  • 两者可以组合。LangGraph 的节点是普通的函数，里面可以调用一个 DSPy 的 module。这样 prompt 由 DSPy 来写和优化，整张图的编排交给 LangGraph。
  • 结构化输出上两者差别不大。两边都能让模型按固定的格式输出：DSPy 靠 signature 里声明的类型，LangGraph 这一边靠 LangChain 的 with_structured_output。这一讲的演示里两边的输出都符合规定的类型。选哪个通常取决于别的需求，也有一部分是个人偏好。
  • 图是写程序的人定义的。使用这个系统的人只需要给输入，系统沿着图跑完，把结果交回来。
  • 把问题想成状态机有时很有用。状态机就是「有限的几个状态，加上状态之间的转移规则」。这里的「状态」指流程走到了哪一个阶段，和 LangGraph 里那份共用的数据是两个概念。前面那张日历程序的图就可以看成一个状态机：流程走到 extract、pick_emoji、add_to_calendar 里的哪一个节点，就是处在哪一个阶段，边是阶段之间的转移规则。流程里有明确的阶段和分支时，画成图比写成一长串 if 更容易看清。
+
LangGraph 文档里列的五项能力。官方的概览页列了五项。第一项是确定的步骤和由模型决定的步骤可以放在同一张图里。第二项是持久化，也就是存下检查点，在失败或暂停之后恢复。第三项是在流程中插入人的审核。第四项是记忆，包括一次对话之内保留的状态和跨多次对话保留的信息。第五项是流式输出，也就是结果一边生成一边送出来，不必等整张图跑完。出处：LangGraph Overview。
+
检查点怎样让流程恢复。配了 checkpointer 之后，图每推进一轮，在这一页的图里也就是每跑完一个节点，checkpointer 就把当时的状态存一份快照。恢复时从最近的一份快照接着跑，已经成功的节点不用重跑。checkpointer 要在编译图的时候显式配置，也就是把它作为参数传给 compile，这一讲的演示没有用到。第六部分的 Temporal 是专门做「失败之后恢复」这件事的。出处：LangGraph 文档的 checkpointer 一节。

同一类的框架还有不少，比如 LlamaIndex 和 CrewAI。前者自称是帮人搭建语言模型应用的「数据框架」，意思是它提供的工具用来把用户自己的数据接进来、整理好，再交给模型使用。后者是一个安排多个 agent 配合完成任务的框架。它们各有各的一套概念，要解决的问题是同一类：把模型调用、工具和程序逻辑组合成一个更大的系统。

第二到第四部分的小结

  • workflow 把模型调用、工具和程序逻辑组合成一个更大的 AI 系统。
  • 不同的框架提供给写程序的人的概念不同：写程序时 DSPy 用 signature 和 module，LangGraph 用状态、节点和边。
  • 控制流是人设计的，由人选择在哪些位置让模型来做决定。这一页的 agent 里，模型和工具之间的循环是人搭的，循环里每一步「调用哪个工具，还是结束」交给模型决定，这就是第一部分说的 agent 的下一步由模型决定。
  • 改进系统需要数据和评估。DSPy 通过优化器把这一点做成了显式的步骤。就算是手工修改系统，也同样需要数据和评估来判断改得对不对。

第一部分按控制流把系统排成了一条线：模型、workflow、agent。第二到第四部分讲的是用框架自己写 workflow 和 agent。下一部分看别人已经搭好的开源 agent 运行框架。
