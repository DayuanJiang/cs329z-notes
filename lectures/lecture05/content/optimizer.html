先看结论

  • 优化器要用到三样东西：一个程序（系统），一批带标注的样例（数据），一个打分的函数（度量）。这正是第一部分说的三根支柱。
  • 演示里，同一个提取日程的 signature（DSPy 里对模型输入和输出的声明）交给小模型 Gemma 3 12B，20 封测试邮件只有 11 封全对。用 GEPA 优化器在 30 封训练邮件上优化之后，20 封全对。整个过程只改了 prompt（给模型的输入文字）里的那段指令。
  • 优化要花钱，结果要在没参与优化的数据上检验，度量要量的是你真正关心的东西。训练模型时的那些规矩在这里全部适用。
  • DSPy 里搭一个 agent（能自己调用工具、分很多步完成任务的语言模型系统）也只要一行：把 signature 和一组工具交给 dspy.ReAct。

要回答的问题：小模型能不能做同样的事

上一部分的提取程序用的是 gpt-5.4-nano。现在换一个问题：一个权重公开、小到可以在普通硬件上运行的模型，能不能把同一件事做好？演示里选的是 Gemma 3 12B，因为它不做任何调整就能把这个任务做出一部分，但做得不够好，正好留出改进的空间。

Gemma 3 是 Google 在 2025 年 3 月发布的一组开放权重的模型，有 1B、4B、12B、27B 四档。名字里的数字按惯例表示参数量，12B 是 120 亿上下。

要让它做好，可以手工反复改 prompt，也可以让优化器来改。优化器需要三样东西，下面依次准备。

数据：50 封带标准答案的邮件

仓库里的 data/emails.json 有 50 封邮件。它们是用一个脚本生成的，内容模仿真实的邮件，比如预约提醒、会议通知、面试安排。脚本用了固定的随机种子，也就是给随机数生成器一个固定的起点，所以每次运行生成的邮件都相同。

每封邮件配有四项标准答案：日程名称、日期、开始时间、时长。其中 9 封邮件没有提到时长，这一项的标准答案是空。

第一封邮件和它的标准答案是这样的：

Dear Prof. Lindqvist,

My thesis committee meeting is scheduled for Wednesday, October 28, 2026 at 2:45pm in Huang 018.
It will run for one hour. I'll circulate slides two days before.

Best,
Tomas
GOLD: {'event_name': 'thesis committee meeting', 'date': '2026-10-28', 'start': '14:45', 'duration_minutes': 60}

接着把每条数据包成 dspy.Example，声明 email 是输入，其余字段是标注，再随机打乱，切成两份：

examples = [dspy.Example(**row).with_inputs("email") for row in rows]
random.Random(0).shuffle(examples)
trainset, testset = examples[:30], examples[30:]

30 封是训练集，优化器只能看这一份。20 封是测试集，留到最后检验用。

度量：三项全对才算对

度量是一个函数，输入是标准答案 gold 和程序的输出 pred，返回一个分数。这里用的是精确匹配：

def event_metric(gold, pred, trace=None, pred_name=None, pred_trace=None):
    checks = {
        "date": str(pred.date) == gold.date,
        "start": str(pred.start)[:5] == gold.start,
        "duration_minutes": pred.duration_minutes == gold.duration_minutes,
    }
    score = float(all(checks.values()))
    wrong = [f"{k}: expected {getattr(gold, k)!r}, got {getattr(pred, k)!r}" for k, ok in checks.items() if not ok]
    feedback = "All fields correct." if not wrong else "Wrong -> " + "; ".join(wrong)
    return dspy.Prediction(score=score, feedback=feedback)

evaluate = dspy.Evaluate(devset=testset, metric=event_metric, num_threads=8, display_progress=True)

有三处值得留意。

  • 只查三项。日期、开始时间、时长必须和标准答案完全一致。日程名称是自由的文字，「meeting」和「team meeting」都说得通，所以不计分。
  • 分数只有 0 和 1。三项里错一项就是 0 分。
  • 除了分数，还返回一段文字反馈。它列出错了哪一项、标准答案是什么、程序给的是什么。反馈是可选的，只返回分数也可以。但 GEPA 这个优化器会把反馈拿给负责改 prompt 的模型看，有了它，新的指令能改得更准。

最后一行用测试集和这个度量建了一个评估器 evaluate。之后要给任何一个程序打分，调用 evaluate(程序) 就行。

优化之前：gpt-5.4-nano 全对，小模型对了 11 封

先确认任务本身和度量没有问题：让默认的 gpt-5.4-nano 跑一遍测试集，20 封全对。然后建一个用小模型的提取器，signature 和之前是同一个，只是单独给它指定了模型：

small_lm = dspy.LM("openrouter/google/gemma-3-12b-it", api_key=OPENROUTER_API_KEY, max_tokens=1024, temperature=0.0)

extract_small = dspy.Predict(ExtractEvent)   # same signature...
extract_small.set_lm(small_lm)               # ...but this predictor uses the small model

before = evaluate(extract_small)

小模型的成绩是 20 封里 11 封全对，也就是 55%。这时它拿到的指令只有 signature 的文档字符串里的那一句：Extract event details from an email.

优化：让 GEPA 改写指令

优化只需要两行。第一行建一个 GEPA 优化器，告诉它用哪个度量、度量调用的预算是多少、由哪个模型来反思。第二行把小模型的提取器和训练集交给它。

gepa = dspy.GEPA(metric=event_metric, max_metric_calls=100, reflection_lm=dspy_llm, num_threads=8)
extract_optimized = gepa.compile(extract_small, trainset=trainset)

这里有两个模型，分工不同。被优化的是小模型 Gemma 3 12B 的 prompt。负责读错误、写新指令的是 reflection_lm，也就是 gpt-5.4-nano，下面叫它反思模型。

预算是大约 100 次度量调用，也就是整个优化过程中大约给程序的输出打 100 次分。仓库的说明写着这一步大约要 3 分钟。

+
GEPA 的出处和思路。GEPA 出自 Agrawal 等人 2025 年的论文 GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning，发表在 ICLR 2026。它的思路是让一个模型用自然语言反思程序哪里做错了，从反复的尝试里总结出规则，再提出新的 prompt。摘要里报告，它比此前领先的 prompt 优化器 MIPROv2 高出 10% 以上，举的例子是在数学题集 AIME-2025 上准确率高 12%。摘要没有写明这两个数是百分点还是相对比例。

它在过程中做了什么

GEPA 的算法第 9 讲会讲到。这里先说看懂运行日志需要的两点。

  • GEPA 保留一批各有所长的指令，每一版叫一个候选，每一轮从里面挑一个来改。开始时只有原始的那一句话指令这一个候选。
  • 每一轮做的事是：挑一版指令，在一小批训练样例上运行，把出错的地方交给反思模型写新指令。新指令在这一小批上更好，才拿去做完整的评估，也就是在全部 30 封训练邮件上运行一遍。

结果

最后用测试集的 20 封邮件给优化后的提取器打分，和优化之前的两个成绩放在一起：

模型没有变，signature 的字段没有变，变的只有那段指令。原来是一句话，现在是几十行，节选如下：

You are given a single email (plain text). Your job is to extract calendar event details from it and return them in a structured JSON-like set of fields.
...
2. date:
   - Identify the explicit calendar date mentioned for the event.
   - Convert it to YYYY-MM-DD regardless of how it appears in the email (e.g., “12/7/2026” -> 2026-12-07, “20 November 2026” -> 2026-11-20).
...
4. duration_minutes (critical):
   - If the email includes a duration like “two-hour”, “15-minute”, “It's a two-hour session”, etc., convert to minutes accurately:
     - “two-hour session” -> 120
     - “15-minute check-in” -> 15
   - Do NOT leave duration_minutes as null when an explicit duration is present. Example 3 shows the assistant must extract “two-hour session” as 120 (the prior response was marked wrong for missing it).

这些内容本来可以由人一条一条写进文档字符串。优化器做的，是让反思模型读小模型在训练邮件上的错误和反馈，把纠正的规则写进指令。

日志里先后写出的几版指令都在强调两件事：10/13/2026、11/17/2026 这类斜线写法的日期不要读错，「two-hour session」这类用文字写的时长不要漏掉。小模型原先很可能主要错在这两处。这是从指令的内容推断出来的，日志里没有按字段统计的错误数。

i
自动写出来的 prompt 也要读一遍。上面节选的最后一句提到了「Example 3」。它指的是优化过程中反思模型当时看到的那一小批样例。到了实际使用时，prompt 里并没有这些样例，模型读到这句话不知道 Example 3 是什么。这一版指令在测试集上仍然全对，说明这句多余的话在这里没有造成问题，但它提醒了一件事：优化器给出的是一段要由人过目的文字。第七部分会回到这个话题。
+
DSPy 的优化器各调什么。DSPy 里的优化器各自调整三样东西里的一样或几样：指令、示例、模型权重。GEPA 和 MIPROv2 这类只改 prompt，不动模型，所以也能用在不公开权重的模型上。dspy.BootstrapFinetune 则会微调（fine-tuning，用新的数据接着训练模型，改动它的权重），需要模型提供微调的接口。它们的用法是一样的：给一个程序、一份数据、一个度量。出处：DSPy 文档的优化器一节。

用优化器要注意的几件事

优化器用起来只要两行，它给出的结果却有六件事要留意，列在下表里。

表里的过拟合（overfitting）指 prompt 只在优化时见过的数据上表现好，换成新数据就变差。防它的办法和训练模型权重时一样，把数据分成三份。训练集给优化器看，用来找错误、写新指令。验证集用来在优化过程中比较几版指令，从中挑出最好的一版。测试集留到最后检验。

奇怪的 prompt：《星际迷航》的例子

「奇怪的 prompt」那一行有一个例子，出自 Battle 和 Gollapudi 2024 年的论文 The Unreasonable Effectiveness of Eccentric Automatic Prompts。他们用 DSPy 的优化器，让 Llama2-70B 为小学数学应用题的数据集 GSM8K 优化自己的 prompt。优化时给优化器看的题目数量试了几种，其中一种是 50 道。

在用 50 道题优化的那一次里，得分最高的一条 prompt 是《星际迷航》风格的。system message（对话开头给模型的总说明）让模型在湍流中规划航线、找出异常的来源，回答则以「舰长日志，星历某年某月」开头。论文说，模型的数学推理似乎因为表现出对《星际迷航》的喜爱而变好了。

!
这条《星际迷航》风格的 prompt 常被说成「让模型的数学变好了」。论文表里的得分要分两组题来看。它只在用来优化的那 50 道题上领先，在另外留出的评估题上低于最好的手写 prompt。

下表列出两组题上的得分和两组的平均分。得分是精确匹配得分，也就是答案和标准答案完全一致的题所占的比例。

论文按两组题的平均分来比较，所以把这条 prompt 算作胜出。这正是上面「过拟合」那一行说的情形：在优化用的数据上变好，不等于在新数据上变好。

在 DSPy 里搭一个 agent

前面的程序都是 workflow：步骤由代码规定，模型只在规定的位置被调用。如果想让模型自己决定调用哪些工具、调用几次，DSPy 有一个现成的 module（DSPy 里决定怎样调用模型的部件），叫 dspy.ReAct。

agent = dspy.ReAct("request -> summary", tools=tinycal.TOOLS)

result = agent(request="Schedule a 30-minute coffee with John on Oct 7, 2026 in the afternoon after my lectures, "
                       "and put a book emoji on every one of my lectures for that same week.")
print(result.summary)

第一行就是整个 agent。signature 是 request -> summary：给一个请求，把请求里的事都办了，最后交一段总结。工具是 tinycal 的七个 Python 函数。tinycal 是配套仓库自带的小日历应用，这七个函数用来查看、添加、修改和删除日程，以及查当天的日期和空闲的时段，名字列在第二部分。每个函数自己的参数和说明就是工具的定义。

请求里有两件事：10 月 7 日下午课后安排一个 30 分钟的咖啡，以及给那一周的每一节课加上一个书本的表情符号。要办成，得先查日历上有哪些课、几点下课，这些步骤都没有写在代码里。运行之后，agent 给两节课加上了书本的表情符号，并在 10 月 7 日 15:00 到 15:30 排了「Coffee with John」。课是 14:50 结束的。

{{fig 47 | 运行之后的 tinycal 界面。10 月 5 日和 7 日的两节课前面多了书本的表情符号，10 月 7 日 15:00 到 15:30 多了 Coffee with John。}}

ReAct 是一种 agent 的结构，名字来自 Reasoning 和 Acting。模型在一个循环里交替做三件事：写一段想法（Thought），发出一个动作（Action，比如调用一个工具），读到结果（Observation），然后再想下一步，直到它认为可以结束。ReAct 的细节第 6 讲会讲到。

{{fig 49 | ReAct 论文里的一个例子。问题是：除了 Apple Remote，还有什么设备能控制 Apple Remote 最初要操作的那个程序。模型先搜索 Apple Remote，得知那个程序叫 Front Row；再搜索 Front Row，没有找到；改搜 Front Row (software)，得知它可以用键盘的功能键控制；最后给出答案。图片来源：Yao 等，2022。}}
i
这个 signature 写得比较随意。request -> summary 靠的是模型把 request 理解成「要办的事」，把 summary 理解成「办完之后的总结」。它在这里行得通。要求更明确的时候，可以像上一部分那样写成一个类，加上任务说明和字段描述。

处理很长的输入：dspy.RLM

有的输入长到放不进模型的上下文窗口（模型一次能读入的文字上限）。DSPy 内置了另一种 agent 式的 module，叫 dspy.RLM，用来处理这种很长的输入。RLM 是 Recursive Language Model（递归语言模型）的缩写。

下面的例子只是演示用法：把 50 封邮件拼成一个很长的字符串，当作收件箱，然后问一个问题：哪些日程在 Gates 楼举行，各在哪一天。50 封邮件加起来并不长，现在的模型一般都能直接读完。

rows = json.load(open("data/emails.json"))
inbox = "\n\n=====\n\n".join(row["email"] for row in rows)

rlm = dspy.RLM("inbox, question -> event_names: list[str], dates: list[str]", max_iters=8)
result = rlm(inbox=inbox, question="Which events are held in the Gates building, and on what dates?")
print(result.event_names)
print(result.dates)

输出是 ['The thesis defense for Wei Zhang'] 和 ['Monday, December 7, 2026']。50 封邮件里确实只有这一封提到了 Gates：Wei Zhang 的论文答辩，地点是 Gates 104。

模型并没有把 50 封邮件从头读一遍。在别的例子里，signature 的输入会原样放进 prompt。dspy.RLM 的做法不同：它开一个隔离的、可以执行 Python 代码的环境，把 inbox 作为一个变量放进去。

模型看到的只是这个变量的名字、类型、长度和开头的一小段。然后它写代码去查看这个变量，比如打印其中一段，或者搜索 Gates 这个词，再根据看到的内容决定下一步。max_iters=8 限定它最多写 8 轮代码。

需要时，模型还可以在代码里把其中一段文字交给另一次模型调用去处理，「递归」指的就是这个。下面的示意图画的是外层的一次调用怎样发起下一层的调用。

{{fig 50 | RLM 的示意图。左边是最外层的一次调用：很长的 prompt 被装进环境里的一个变量，模型通过写代码查看它的开头、把它切成几段，再对每一段发起新的模型调用。右边两个小框就是这些下一层的调用，它们各自处理一段，把结果返回给外层。图片来源：Zhang、Kraska 和 Khattab，2025。}}

收件箱这个例子的写法，可以原样用在放不进上下文窗口的输入上。

DSPy 的小结

  • signature 定义输入和输出的约定。
  • module 组合 signature 和程序逻辑，并规定怎样完成这个约定，比如 dspy.Predict、dspy.ChainOfThought、dspy.BestOfN。
  • 有了数据和度量，optimizer 可以改进程序里的 prompt 或模型权重。
  • DSPy 有内置的 module 让 agent 来完成 signature：dspy.ReAct 和 dspy.RLM。
