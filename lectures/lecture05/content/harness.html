先看结论

  • 运行框架（harness，也叫 scaffold）是包在语言模型外面的那层程序：它给模型工具，管理多轮对话的历史，执行模型发出的动作，再把结果交还给模型。一个 agent 等于模型加运行框架。
  • 搭一个运行框架要做一连串设计选择：给哪些工具，历史怎么存、怎么裁剪，命令怎么执行。四个开源的例子（mini-SWE-agent、OpenHands、Pi、OpenClaw）在这些事上的选择各不相同。
  • 没有哪一种搭法是唯一正确的。好的运行框架要在任务成功率、花费、延迟和用户的控制权之间取得平衡，怎样平衡取决于用途。
  • 同一个模型换一个运行框架，结果会变。一项对三个成熟运行框架的测量里，变得最明显的是花费；成功率在多数模型上只差几个百分点，那批数据分辨不出谁高谁低。

运行框架是什么

在第一部分的那条线上，这一部分走到了最右端：控制流由模型决定的 agent（能自己调用工具、分很多步完成任务的语言模型系统）。前面三部分的 DSPy 和 LangGraph 是框架（framework），是给你写程序用的库。这一部分的主角是运行框架，是别人已经搭好、装上就能用的 agent 程序。

{{fig 80 | 一个 agent 的组成。红框里是运行框架和模型：规划和推理、记忆、模型本身、工具，以及 agent 发出的动作。红框外面是环境，比如桌面操作系统、浏览器、数据库。agent 对环境做动作，再观察环境的变化。}}

图里除了外部环境以外的东西，都算在 agent 这一边。其中围绕着模型搭起来、让 agent 能工作的那部分程序，就是运行框架。

四个开源的例子

下面四个运行框架都是开源的。先用一张表列出它们各自最有特点的选择，再逐个说明。

mini-SWE-agent：能省的都省掉

mini-SWE-agent 出自普林斯顿和斯坦福的一个团队，2025 年 7 月发布 1.0 版。这个团队之前做了 SWE-bench（一组取自 GitHub 上真实软件问题的评测题目）和 SWE-agent。它的三个特点都是「不做什么」。

  • 除了 bash 没有别的工具。读文件、改文件、搜索，全部由模型自己写 shell 命令完成。
  • 历史完全是一条线。agent 每走一步，就往消息列表后面追加一条，仅此而已。发给模型的消息和事后保存的运行轨迹（trajectory，每一步的动作和结果的完整记录）是同一份东西。这和平时用聊天产品的体验一样：对话越聊越长，每次都带着全部历史。
  • 每个动作互相独立。它不维持一个持续的 shell 会话，每条命令都在一个新的进程里执行。后果是 cd 换的目录、export 设的环境变量，到下一条命令就没有了，需要的话得在每条命令前面重新写一遍。好处是没有一个长期存活的会话需要维护，放进 Docker 这类隔离环境里做评测时省去不少麻烦。
+
细节。仓库的说明写着 agent 的主体类只有大约 100 行 Python，在 SWE-bench Verified（SWE-bench 里经过人工筛选的 500 道题）上的成绩超过 74%。按 2026 年 11 月的代码，这个类大约是 150 行。2.0 版起默认使用模型原生的工具调用接口，声明的工具仍然只有 bash 一个。「每条命令开一个新进程」在说明里写的是用 subprocess.run，现在的代码换成了一个等价的写法，超时时能把子进程一并结束。出处：mini-SWE-agent 的说明和常见问题。

OpenHands：把每一步都记成事件

OpenHands 原名 OpenDevin，对应的论文是 Wang 等，2024。和 mini-SWE-agent 相比，它在三件事上都选了更复杂的做法。

  • 每一步存成一个事件。模型的每次回答、每个动作、每个结果都是一个事件，追加到一份只增不改的事件日志里。开启持久化之后，每个事件在磁盘上是一个单独的 JSON 文件。每次调用模型之前，发给模型的消息由这些事件转换出来。这样做，完整的历史和「给模型看的内容」是两样东西，磁盘上的事件还可以用来恢复一次中断的会话。
  • 终端是持续存在的。它用 tmux（一个让终端会话在后台持续运行的工具）开一个会话，所以切换过的目录、设过的环境变量、激活过的 Python 虚拟环境，在后面的命令里都还在。这一点正好和 mini-SWE-agent 相反。
  • 卡住了会自己停。它有一个检测器，发现 agent 反复做同样的动作而没有进展，就结束运行。
+
检测器查的是什么。文档列了五种情形，默认的界限如下：同一个动作得到同一个结果，重复 4 次；同一个动作反复报错，3 次；agent 连续发了 3 条消息，中间没有用户输入，也没有实质进展；两组动作和结果来回交替，6 步；反复出现上下文窗口超限的错误。最后一种在目前的代码里还没有实现。另外，tmux 只在系统里装了它的时候才用，没装就退回到普通的子进程终端。出处：OpenHands 文档的 Stuck Detector 一节、会话持久化一节。

Pi：四个工具，没有权限系统

Pi 是 Mario Zechner 写的编程 agent，同样走极简的路线。

  • 只有四个工具。read、write、edit 和 bash。作者在 2025 年 11 月的文章里说，system prompt（对话开头给模型的总说明）加上工具的定义，合起来不到 1,000 个 token（模型处理文字的最小单位）。这个数包含了工具的定义，只把它说成 system prompt 的长度就说窄了。
  • 没有权限系统。它用启动它的那个账号的全部权限运行，执行工具之前不询问。作者的说法是，它假定你知道自己在做什么。
  • 历史是一棵树。可以回到之前的某一条消息，改一改再发出去，从那里长出另一支；原来的那一支不会丢。发给模型的只有当前所在的这一支。
  • 刻意保持简单。没有计划模式，没有专门的子 agent 工具。需要的话可以用扩展加回来。
+
「不到 1,000 个 token」是 2025 年 11 月的数。HarnessTax 文章在 2026 年 9 月测量了三个运行框架第一次调用模型时的上下文大小，这个数包含了任务本身的文字：Pi 平均 1,972 个 token，Codex 平均 11,308 个，Claude Code 平均 27,011 个。工具的数量分别是 4 个、约 7 个、23 个。Pi 仍然是三者里最小的，Claude Code 的这个数是它的 10 倍以上。出处：Zechner 的文章；Pi 文档的会话一节；HarnessTax。

OpenClaw：一个一直开着的个人助手

OpenClaw 由 Peter Steinberger 发起，最初叫 Clawdbot，2026 年 1 月两次改名后定为现在的名字。它的用户已经远远超出了做 AI 工程的圈子：人们把它装在自己的机器上，通过 WhatsApp、Telegram 这类聊天软件和它说话。它的设计选择和前三个面向编程任务的运行框架很不一样。

  • 每 30 分钟自己醒来一次。除了等用户发消息，它还按固定的间隔自己运行一轮，看看有没有需要处理的事。没有事的时候，它回复一个约定的标记 NO_REPLY，用户就不会收到任何消息。
  • 一个长期运行的 Gateway 进程。所有聊天渠道的连接都由这一个进程持有，一台机器上只运行一个。
  • 身份由 Markdown 文件拼成。AGENTS.md、SOUL.md、IDENTITY.md、USER.md 和 MEMORY.md 这几个文件的内容会被放进 system prompt（对话开头给模型的总说明）。agent 是谁、该怎么做事、用户是谁、记得些什么，都写在这些文件里，人可以直接打开来读和改。
  • 每晚整理记忆。凌晨 3 点有一个后台任务，把近期的笔记过一遍，把值得长期保留的内容写进 MEMORY.md。
i
这些机制一直在变，上面写的是 2026 年 10 月上旬的样子。
  • 定时醒来。2026 年 6 月的文档里，表示「没事」的标记还是 HEARTBEAT_OK，到 10 月的文档里已经是 NO_REPLY。用 Anthropic 的账号登录时，默认间隔是 1 小时。2026 年 10 月 21 日之后，这个独立的机制被取消，换成一个普通的定时任务，要用户明确设置才会创建，默认仍是每 30 分钟一次。
  • 记忆整理。文档里把它叫作 dreaming。它从 2026 年 7 月底起默认开启，之前要用户自己打开。它分三个阶段依次运行，读的东西除了每天的笔记，还有近期的召回记录和会话记录，只有最后一个阶段会写 MEMORY.md。
  • MEMORY.md 只在一部分情况下被读入。文件存在、并且是和用户的私聊会话时，它才放进 system prompt。子 agent 只拿到 AGENTS.md。
出处：OpenClaw 文档的 heartbeat、架构、system prompt、dreaming 各节。

四个例子摆在一起，可以看到同一个问题有不同的答案。命令之间要不要保留状态：mini-SWE-agent 不保留，OpenHands 保留。历史怎么存：mini-SWE-agent 用一条线，OpenHands 用事件日志，Pi 用一棵树。每个答案都有它适合的场合。

换一个运行框架，结果差多少

设计选择不同，结果自然会不同。Arena 团队 2026 年 9 月的文章 HarnessTax 专门量了这件事：让同一个模型分别装在三个运行框架里，在同一批任务上跑，比较成功率和花费。三个运行框架是上一节的 Pi、OpenAI 的 Codex 和 Anthropic 的 Claude Code。

{{fig 86 | Terminal-Bench 2.0 上，四个 Claude 模型各自配三个运行框架的结果。左边一组横条是每次运行的平均花费（美元），右边一组是成功率。绿色的框标出每个模型下花费最低和成功率最高的那一个。每个横条上的细线是误差范围。图片来源：HarnessTax。}}

Terminal-Bench 是一个让 agent 在命令行环境里完成任务的基准测试（benchmark，一组题目加一个打分的办法），2.0 版有 89 个任务。文章一共测了 7 个模型，用了 Terminal-Bench 2.0 和 SWE-bench Lite 两个基准测试；上面的图和下面的表只包含其中 4 个 Claude 模型在 Terminal-Bench 2.0 上的结果。把图里的数连同文章给的 95% 置信区间列成表。置信区间的意思是：按同样的办法重复做很多次实验，算出来的范围大约有 95% 会包含真实的平均值。

怎么读这张表

  • 样本不大。每个组合只跑了 30 个任务，没有跑全部 89 个。所以每个成功率的置信区间都很宽，上下大约各 15 个百分点。
  • 成功率在多数模型上只差几个百分点。Fable 5、Opus 4.8、Sonnet 4.6 这三个模型，三个运行框架之间最多相差不到 5 个百分点。以 Claude Fable 5 为例，Claude Code 的 75.6% 比 Pi 的 71.1% 高 4.4 个百分点。文章给出的这个差值的置信区间是负 1.1 到正 11.1 个百分点，包含了零，也就是这批数据分不出两者谁高。差距最大的一组是 Claude Haiku 4.5 在 Pi 和 Codex 上，相差 16.7 个百分点。这个差值的置信区间没有在文章里找到，图表附带的数据把每一行都标为描述性的估计、没有做检验，所以 30 个任务不足以判断这个差距是否可靠。
  • 花费的差距更确定。同样是 Claude Fable 5，Claude Code 每次运行的花费是 Pi 的 1.44 倍，这个比值的置信区间是 1.08 到 1.94 倍，整个区间都在 1 以上。表里花费差得最多的也在这个模型上：Claude Code 的 1.55 美元是 Codex 的 0.98 美元的约 1.6 倍。
  • 模型自家的运行框架不一定最好。Claude Code 是 Anthropic 为 Claude 做的。四个 Claude 模型里，它只在 Fable 5 上成功率最高。
!
「换运行框架会让成功率差很多」，要看是哪一组数据。单看上面的图，很容易读成运行框架对成功率影响很大。HarnessTax 的作者自己的结论是另一个方向：在他们测的两个基准测试上，运行框架的选择对任务成功率影响很小，对花费的影响可以很大，同一个模型可以用高达 5 倍的花费拿到差不多的成功率。文章的正文没有写明这个最大的倍数出现在哪个模型上；上面的表只有四个 Claude 模型在 Terminal-Bench 2.0 上的结果，表里最大的差距约 1.6 倍。文章的名字就是这个意思：只用默认的运行框架、不和别的比一比，可能在为同样的质量多付钱。他们还报告，平均来看 Claude Code 在 Terminal-Bench 2.0 上的花费是 Pi 的 1.5 倍，而运行框架对成功率的平均影响在正负 5% 左右以内，原文没有写明这是百分点还是相对比例。作者也说明，这些结论限于他们测的两个公开的基准测试，换别的任务可能不同。另一方面，如果把范围放宽到排行榜上各式各样的运行框架，成功率的差距就大得多，见下一节的数字。出处：HarnessTax。

Meta-Harness：让模型自己改运行框架

既然运行框架是一段代码，而模型会写代码，那么可以让模型来写运行框架。Lee 等人 2026 年的论文 Meta-Harness 做的就是这件事：在外面套一层搜索，不断提出新的运行框架代码，在任务上评估，保留好的。

{{fig 87 | Meta-Harness 的搜索循环。第一步，一个 agent 读一个文件系统，里面存着之前所有候选运行框架的源代码、运行记录和分数，然后提出一个新的运行框架。第二步，在评估任务上运行这个新的运行框架。第三步，把这一轮的代码、推理过程和分数全部存回文件系统，再开始下一轮。图片来源：Lee 等，2026。}}

负责提出新代码的那个 agent，在论文的实验里是装着 Opus 4.6 的 Claude Code。历史都存在文件里，它用 grep、cat 这样的命令按需查看，需要看哪次失败的运行记录就打开哪个。每个候选的运行框架是一个单文件的 Python 程序。

{{fig 88 | 论文的两组结果。左：在文本分类任务上，横轴是评估过的运行框架个数，纵轴是到那时为止最好的准确率。Meta-Harness 的红线上升得最快，也停在最高处。右：在 Terminal-Bench 2.0 上（论文里写作 TerminalBench-2），模型固定为 Claude Haiku 4.5，各个运行框架的通过率。红色是 Meta-Harness 搜出来的，深蓝色是人写的。图片来源：Lee 等，2026。}}

同一个模型，排行榜上人写的运行框架从 13.9% 到 35.5% 都有，Meta-Harness 搜出来的是 37.6%。上一节的三个运行框架在多数模型上只差几个百分点，这里的差距大得多。换成 Opus 4.6，Meta-Harness 搜出来的运行框架通过率是 76.4%，在使用 Opus 4.6 的 agent 里排第二。排第一的是另一个编程 agent ForgeCode，成绩是 81.8%，论文作者说明他们没能用公开的代码复现这个成绩。

i
读这些数字要带着三个保留。
  • 搜索和报告成绩用的是同一批题。论文写明，在 Terminal-Bench 2.0 这个实验里，搜索和最终评估用的是同样的 89 个任务。作者的理由是这个基准测试题少、跑一遍很贵，再分出一份留作测试会削弱搜索的信号，并且公开的运行框架本来也在这批题上反复调整过。他们另外用人工检查和正则匹配排查了运行框架里有没有混入针对具体题目的字符串。即便如此，这个 37.6% 是一个针对 Terminal-Bench 2.0 调出来的运行框架在 Terminal-Bench 2.0 上的成绩。拿它和 Claude Code 直接比，条件并不对等：Claude Code 是面向各种任务的通用产品。
  • 它是从两个现成的强运行框架出发的。搜索的起点是 Terminus 2 和 Terminus-KIRA。
  • 同一个组合，两处的数不一样。Claude Code 配 Claude Haiku 4.5，这里是 27.5%，上一节 HarnessTax 的表里是 41.1%。两个数的来历不同：一个取自排行榜，针对全部 89 个任务；一个是抽 30 个任务自己跑的，Claude Code 的版本和设置也不一定相同。第 13 讲会讲到这一点：分数要连同它是怎么跑出来的一起看。
论文的另外两组实验有独立的测试数据。文本分类上，它比此前最好的人工设计的上下文管理方法 ACE 高 7.7 个百分点，用的上下文 token 只有四分之一左右。数学题上，搜出来的一个运行框架让五个没参与搜索的模型在 200 道国际数学奥林匹克难度的题上平均提高 4.7 个百分点。出处：Lee 等，2026。

这一部分的小结

  • 搭 agent 没有唯一的办法。工具、记忆、上下文管理、执行，每一项都有不止一种合理的选择。
  • mini-SWE-agent 和 Pi 走极简的路线，OpenHands 把状态和历史管得更细，OpenClaw 面向的是长期在线的个人助手。它们的差别来自各自要做的事不同。
  • 运行框架是 agent 表现的一部分。报告一个 agent 的成绩时，模型和运行框架要一起说明。
  • 运行框架本身也可以被优化，前提和优化 prompt 一样：要有任务和评估。
