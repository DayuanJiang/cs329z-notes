先看结论

  • 运行框架（harness，也叫 scaffold）是包在语言模型外面的那层程序：它给模型工具，管理多轮对话的历史，执行模型发出的动作，再把结果交还给模型。一个 agent 等于模型加运行框架。
  • 搭一个运行框架要做一连串设计选择：给哪些工具，历史怎么存，命令怎么执行。四个开源的例子（mini-SWE-agent、OpenHands、Pi、OpenClaw）在这些事上的选择各不相同。
  • 没有哪一种搭法是唯一正确的。好的运行框架要在任务成功率、花费、延迟和用户的控制权之间取得平衡，怎样平衡取决于用途。
  • 同一个模型换一个运行框架，结果会变。一项对三个成熟运行框架的测量里，变得最明显的是花费；成功率在多数模型上只差几个百分点，那批数据分辨不出谁高谁低。

运行框架是什么

这一讲的第一部分把 AI 系统排成了一条线。排的依据是控制流，也就是程序里「接下来执行哪一步」由谁决定。线的左端是单个模型，它被调用一次，给出一个回答。中间是 workflow，多次模型调用的步骤由写程序的人事先写定。右端是 agent（能自己调用工具、分很多步完成任务的语言模型系统），下一步做什么由模型自己决定。这一部分讲的是最右端。

前面三部分的 DSPy 和 LangGraph 是框架（framework），是给你写程序用的库。这一部分的主角是运行框架：包在模型外面、给它工具并管理多轮对话的那层程序。这一部分看的几个运行框架都是别人已经搭好、装上就能用的。

{{fig 80 | 一个 agent 的组成。红框里是运行框架和模型：规划和推理、记忆、模型本身、工具，以及 agent 发出的动作。红框外面是环境，比如桌面操作系统、浏览器、数据库。agent 对环境做动作，再观察环境的变化。}}

图里除了外部环境以外的东西，都算在 agent 这一边。其中围绕着模型搭起来、让 agent 能工作的那部分程序，就是运行框架。

下表是两份资料给运行框架下的定义。Meta-Harness 论文着眼于信息：存什么，取什么，给模型看什么。HarnessTax 文章着眼于运行框架管的三样东西：工具、上下文和任务执行。上下文（context）指每次调用模型时发给它的全部内容。这两份资料后面还会讲到：Meta-Harness 论文在「Meta-Harness：让模型自己改运行框架」一节，HarnessTax 文章在「换一个运行框架，结果差多少」一节。

运行框架之间差在哪

搭一个 agent 要做很多设计选择。主要的有四类：

不同的运行框架针对各自的任务和运行环境，做了不同的取舍。一个好的运行框架要在四件事之间取得平衡：任务成功率、花费、延迟、用户的控制权。合适的平衡点取决于用途。

举两种用途。Claude Code（Anthropic 做的、面向编程任务的运行框架）这样的产品是给人在终端里一边看一边用的，用户怎样和它交互就很重要。另一些运行框架主要用来自动地跑完任务，中途有没有人参与就不那么要紧。

四个开源的例子

下面四个运行框架都是开源的。先用一张表列出它们各自最有特点的选择，再逐个说明。

mini-SWE-agent：能省的都省掉

mini-SWE-agent 出自普林斯顿和斯坦福的一个团队，2025 年 7 月发布 1.0 版。这个团队之前做了 SWE-bench（一组取自 GitHub 上真实软件问题的评测题目）和 SWE-agent。

SWE-agent 是这个团队之前做的面向编程任务的运行框架，给模型配了不少专门的工具和接口。mini-SWE-agent 是照着「简单得多、效果仍然接近」的目标重做的，它的三个特点都是「不做什么」。

  • 除了 bash 没有别的工具。读文件、改文件、搜索，全部由模型自己写 shell 命令完成。
  • 历史完全是一条线。agent 每走一步，就往消息列表后面追加一条，仅此而已。发给模型的消息和事后保存的运行轨迹（trajectory，每一步的动作和结果的完整记录）是同一份东西。这和平时用聊天产品的体验一样：对话越聊越长，每次都带着全部历史。
  • 每个动作互相独立。它不维持一个持续的 shell 会话，每条命令都在一个新的进程里执行。后果是 cd 换的目录、export 设的环境变量，到下一条命令就没有了，需要的话得在每条命令前面重新写一遍。好处是没有一个长期存活的会话需要维护，放进 Docker 这类隔离环境里做评测时省去不少麻烦。

仓库的说明给出的成绩是：在 SWE-bench Verified（SWE-bench 里经过人工筛选的 500 道题）上得分超过 74%，得分是解决了的题所占的比例。说明没有写这个成绩用的是哪个模型。

+
2.0 版改了什么，没改什么。2.0 版起，它默认使用模型原生的工具调用接口：程序把工具的名字和参数格式声明给模型，模型按这个格式发出调用。声明的工具仍然只有 bash 一个，每条命令也仍然在一个新的进程里执行。出处：mini-SWE-agent 的说明和常见问题。

OpenHands：把每一步都记成事件

OpenHands 原名 OpenDevin，对应的论文是 Wang 等，2024。和 mini-SWE-agent 相比，它在三件事上都选了更复杂的做法。

  • 每一步存成一个事件。模型的每次回答、每个动作、每个结果都是一个事件，追加到一份只增不改的事件日志里。每次调用模型之前，发给模型的消息由这些事件转换出来。这样做，完整的历史和「给模型看的内容」是两样东西。开启持久化之后，每个事件在磁盘上是一个单独的 JSON 文件，可以用来恢复一次中断的会话。这一点见 OpenHands 文档的会话持久化一节。
  • 终端是持续存在的。它用 tmux（一个让终端会话在后台持续运行的工具）开一个会话，所以切换过的目录、设过的环境变量、激活过的 Python 虚拟环境，在后面的命令里都还在。这一点正好和 mini-SWE-agent 相反。系统里没装 tmux 时，它退回到普通的子进程终端。
  • 卡住了会自己停。它有一个检测器，发现 agent 反复做同样的动作而没有进展，就结束运行。
+
检测器查的是什么。文档列了五种算作卡住的情形，前四种各有一个默认的界限。
  • 同一个动作得到同一个结果，重复了 4 次。
  • 同一个动作反复报错，达到 3 次。
  • agent 连续发了 3 条消息，中间没有用户输入，也没有实质进展。
  • 两组动作和结果来回交替了 6 步。
  • 反复出现上下文窗口超限的错误，也就是发给模型的内容超过了它一次能读的长度。这一种在目前的代码里还没有实现。
出处：OpenHands 文档的 Stuck Detector 一节。

Pi：四个工具，没有权限系统

Pi 是 Mario Zechner 写的面向编程任务的运行框架，同样走极简的路线。

  • 只有四个工具。read、write、edit 和 bash。作者在 2025 年 11 月的文章里说，system prompt（对话开头给模型的总说明，第二、第三部分里写作 system message）加上工具的定义，合起来不到 1,000 个 token（模型处理文字的最小单位）。
  • 没有权限系统。它用启动它的那个账号的全部权限运行，执行工具之前不询问。作者的说法是，它假定你知道自己在做什么。
  • 历史是一棵树。可以回到之前的某一条消息，改一改再发出去，从那里长出另一支；原来的那一支不会丢。发给模型的只有当前所在的这一支。这一点见 Pi 文档的会话一节。
  • 刻意保持简单。它没有计划模式，也就是先让 agent 只读代码、写出计划，等用户同意再动手修改的工作方式。它也没有专门的子 agent 工具，子 agent 是由 agent 另外启动、替它完成一部分任务的另一个 agent。这两样都可以用扩展加回来，扩展是自己写或者装上别人写好的附加功能。

Pi 带给模型的内容比别的运行框架少多少，后面「换一个运行框架，结果差多少」一节要讲的 HarnessTax 文章在 2026 年 9 月量过。它量的是三个运行框架第一次调用模型时的上下文大小，也就是那一次发给模型的全部内容。三个运行框架是 Pi、Codex（OpenAI 做的、在命令行里用的运行框架）和 Claude Code。这个数除了 system prompt 和工具的定义，还包含任务本身的文字，所以它量的范围比上面的「不到 1,000 个 token」大，两个数不能直接比。

Pi 是三者里最小的，Claude Code 的这个数是它的 10 倍以上。

OpenClaw：一个一直开着的个人助手

OpenClaw 由 Peter Steinberger 发起，最初叫 Clawdbot，2026 年 1 月两次改名后定为现在的名字。

它是一个长期在线的个人助手：人们把它装在自己的机器上，通过 WhatsApp、Telegram 这类聊天软件和它说话。它的用户已经远远超出了做 AI 工程的圈子。它的设计选择和前三个面向编程任务的运行框架很不一样，下面四条按 2026 年 11 月的文档来写。这些机制改得很快，之前的几次变动见资料说明。

  • 定时自动运行。除了等用户发消息，它还能按固定的间隔自动运行一轮，看看有没有需要处理的事。这件事由一个定时任务来做，这个任务要用户明确设置才会创建，创建之后默认每 30 分钟运行一次。没有事的时候，它回复一个约定的标记 NO_REPLY，用户就不会收到任何消息。
  • 一个长期运行的 Gateway 进程。所有聊天渠道的连接都由这一个进程持有，一台机器上只运行一个。
  • 身份由 Markdown 文件拼成。AGENTS.md、SOUL.md、IDENTITY.md、USER.md 和 MEMORY.md 这几个文件的内容会被放进 system prompt。agent 是谁、该怎么做事、用户是谁、记得些什么，都写在这些文件里，人可以直接打开来读和改。其中 MEMORY.md 只在文件存在、并且是和用户的私聊会话时才放进去。子 agent 只拿到 AGENTS.md。
  • 每晚整理记忆。凌晨 3 点有一个默认开启的后台任务，文档里把它叫作 dreaming。它分三个阶段依次运行，读的是近期的每日笔记、会话记录和召回记录。每日笔记是 agent 按日期存放的 Markdown 文件，记的是当天的经过和观察。召回记录记的是哪些笔记内容在搜索记忆时被查到过。只有最后一个阶段把值得长期保留的内容写进 MEMORY.md。

这四条依次出自 OpenClaw 文档的 heartbeat、架构、system prompt、dreaming 各节。

同一个问题，不同的答案

把前三个面向编程任务的例子摆在一起，可以看到同一个问题有不同的答案，每个答案都有它适合的场合。

第一个问题是命令之间要不要保留状态。mini-SWE-agent 不保留，放进 Docker 这类隔离环境做评测时省事。OpenHands 保留，切换过的目录、设过的环境变量在后面的命令里都还在，不用在每条命令前面重写一遍。

第二个问题是历史怎么存。mini-SWE-agent 用一条线，发给模型的消息就是完整的运行轨迹。OpenHands 用事件日志，完整的历史和给模型看的内容分开，还能恢复中断的会话。Pi 用一棵树，可以回到之前的某条消息另开一支，原来那一支不会丢。

换一个运行框架，结果差多少

设计选择不同，结果自然会不同。HarnessTax 是 2026 年 9 月发表在 arena.ai 博客上的一篇文章，作者是 Pan 等六人，它专门量了这件事：让同一个模型分别配三个运行框架，在同一批任务上跑，比较成功率和花费。三个运行框架是上一节的 Pi、OpenAI 的 Codex 和 Anthropic 的 Claude Code。

文章一共测了 7 个模型，用了两个基准测试（benchmark，一组题目加一个打分的办法）。一个是 Terminal-Bench 2.0，它让 agent 在命令行环境里完成任务，有 89 个任务。另一个是 SWE-bench Lite，是从 SWE-bench 里选出的 300 道题。下面的图和表只包含其中 4 个 Claude 模型在 Terminal-Bench 2.0 上的结果。

测法是这样的。所有组合用的是从 Terminal-Bench 2.0 里随机抽出的同一批 30 个任务，每个任务跑 3 次，每个组合一共 90 次运行，每次运行最多 100 轮。一轮（turn）是运行框架记下的 agent 的一步，文章说明各个运行框架对一轮的算法不同。花费按 2026 年 9 月 1 日的一份固定价格表计算。

怎么读这张表

读这张表有五点要注意。

  • 样本不大。每个组合只跑了 30 个任务，没有跑全部 89 个。所以每个成功率的置信区间都很宽，上下大约各 15 个百分点。
  • 成功率在多数模型上只差几个百分点，分不出高低。Fable 5、Opus 4.8、Sonnet 4.6 这三个模型，三个运行框架之间最多相差不到 5 个百分点。以 Claude Fable 5 为例，Claude Code 的 75.6% 比 Pi 的 71.1% 高，文章给出的差值是 4.4 个百分点。这个数是按四舍五入之前的成功率算的，所以和表里两个数直接相减得到的 4.5 差 0.1。文章给出的这个差值的置信区间是负 1.1 到正 11.1 个百分点，包含了零，也就是这批数据分不出两者谁高。
  • 差得最多的一组，这批数据也判断不了。Claude Haiku 4.5 在 Pi 和 Codex 上相差 16.7 个百分点。上一条的那个差值有文章给出的置信区间，这个差值没有。图表附带的数据还给每一行加了一句说明：这些数只是对这 30 个任务上的结果的描述，没有做统计检验。统计检验是用来判断一个差别会不会只是碰巧出现的计算。只凭 30 个任务，判断不了这个差距是否可靠。
  • 花费的差距更确定。同样是 Claude Fable 5，Claude Code 每次运行的花费是 Pi 的 1.44 倍，这个比值的置信区间是 1.08 到 1.94 倍，整个区间都在 1 以上。表里花费差得最多的也在这个模型上：Claude Code 的 1.55 美元是 Codex 的 0.98 美元的约 1.6 倍。
  • 模型自家的运行框架不一定最好。Claude Code 是 Anthropic 为 Claude 做的。按表里的成功率，四个 Claude 模型里它只在 Fable 5 上最高。前面说过这些成功率的差别大多分不出高低，所以这一条的意思是：这批数据没有显示自家的运行框架更好。

Meta-Harness：让模型自己改运行框架

既然运行框架是一段代码，而模型会写代码，那么可以让模型来写运行框架。Lee 等人 2026 年的论文 Meta-Harness 做的就是这件事：在外面套一层搜索，不断提出新的运行框架代码，在任务上评估，保留好的。

{{fig 87 | Meta-Harness 的搜索循环。第一步，一个 agent 读一个文件系统，里面存着之前所有候选运行框架的源代码、运行记录和分数，然后提出一个新的运行框架。第二步，在评估任务上运行这个新的运行框架。第三步，把这一轮的代码、推理过程和分数全部存回文件系统，再开始下一轮。图片来源：Lee 等，2026。}}

负责提出新代码的那个 agent，在论文的实验里是配 Opus 4.6 的 Claude Code。历史都存在文件里，它用 grep、cat 这样的命令按需查看，需要看哪次失败的运行记录就打开哪个。每个候选的运行框架是一个单文件的 Python 程序。

{{fig 88 | 论文的两组结果。左：在文本分类任务上，横轴是评估过的运行框架个数，纵轴是到那时为止最好的准确率。Meta-Harness 的红线上升得最快，也停在最高处。右：在 Terminal-Bench 2.0 上（论文里写作 TerminalBench-2），模型固定为 Claude Haiku 4.5，各个运行框架的通过率。红色是 Meta-Harness 搜出来的，深蓝色是人写的。图片来源：Lee 等，2026。}}

同一个模型 Claude Haiku 4.5，排行榜上人写的运行框架通过率从 13.9% 到 35.5% 都有，Meta-Harness 搜出来的是 37.6%。

这里的差距比上一节大得多。两处比的对象不同：上一节是三个成熟的运行框架，在同一批任务上跑，多数模型上只差几个百分点。这里是排行榜上各式各样的运行框架，分数取自排行榜。

换成 Opus 4.6，Meta-Harness 搜出来的运行框架通过率是 76.4%，在使用 Opus 4.6 的 agent 里排第二。排第一的用的是另一个运行框架 ForgeCode，成绩是 81.8%，论文作者说明他们没能用公开的代码复现这个成绩。

搜索和评估用的是同一批题

论文写明，在 Terminal-Bench 2.0 这个实验里，搜索和最终评估用的是同样的 89 个任务。作者给了两条理由。第一条，这个基准测试题少、跑一遍很贵，再分出一份留作测试，留给搜索的题就更少，搜索时更难看出哪个候选更好。第二条，公开的运行框架本来也在这批题上反复调整过。他们另外用人工检查和正则表达式（一种按文字模式查找字符串的写法）排查了运行框架里有没有混入针对具体题目的字符串。

读 Terminal-Bench 2.0 的这些数字，有三点要留意。
  • 成绩是在搜索用过的题上报告的。这个 37.6% 是一个针对 Terminal-Bench 2.0 调出来的运行框架在 Terminal-Bench 2.0 上的成绩。拿它和 Claude Code 直接比，条件并不对等：Claude Code 是面向各种任务的通用产品。
  • 它是从两个现成的强运行框架出发的。搜索的起点是 Terminus 2 和 Terminus-KIRA，它们在上面的表里是 28.3% 和 33.7%。搜索带来的提高要和起点比：37.6% 比其中较高的 Terminus-KIRA 高 3.9 个百分点。
  • 同一个组合，两处的数不一样。Claude Code 配 Claude Haiku 4.5，这里是 27.5%，上一节 HarnessTax 的表里是 41.1%。两个数的来历不同：一个取自排行榜，针对全部 89 个任务；一个是抽 30 个任务自己跑的，Claude Code 的版本和设置也不一定相同。第 13 讲会讲到这一点：分数要连同它是怎么跑出来的一起看。

另外两组实验

论文的另外两组实验有独立的测试数据，所以没有上面第一点说的问题。

  • 文本分类。这是上面左图的实验。任务里，模型每次拿到一条带标签的样例，更新自己的记忆，最后在留出的测试集上接受评估。运行框架在这里管的是记下什么、每次调用时给模型看什么。ACE（Agentic Context Engineering）是此前人工设计的这类程序里最好的一个，论文把它叫作上下文管理系统。Meta-Harness 搜出来的运行框架，准确率比 ACE 高 7.7 个百分点，用的上下文 token 只有四分之一左右。
  • 数学题。搜出来的一个运行框架让五个没参与搜索的模型在 200 道国际数学奥林匹克难度的题上，准确率平均提高 4.7 个百分点。

这一部分的小结

  • 搭 agent 没有唯一的办法。工具、记忆、上下文管理、执行，每一项都有不止一种合理的选择。
  • mini-SWE-agent 和 Pi 走极简的路线，OpenHands 把状态和历史管得更细，OpenClaw 面向的是长期在线的个人助手。它们的差别来自各自要做的事不同。
  • agent 的表现有一部分取决于运行框架。报告一个 agent 的成绩时，模型和运行框架要一起说明。
  • 运行框架本身也可以被优化，前提和优化 prompt 一样：要有任务和评估。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • mini-SWE-agent 的说明和现在的代码有两处出入。仓库的说明写着 agent 的主体类只有大约 100 行 Python，按 2026 年 11 月的代码，这个类大约是 150 行。「每条命令开一个新进程」在说明里写的是用 subprocess.run，现在的代码换成了一个等价的写法，超时时能把子进程一并结束。出处：mini-SWE-agent 的说明。
  • OpenClaw 的定时运行和记忆整理改过几次。2026 年 6 月的文档里，表示「没事」的标记还是 HEARTBEAT_OK，到 10 月的文档里已经是 NO_REPLY。2026 年 10 月上旬，定时运行还是一个独立的内置机制，默认间隔是 30 分钟，用 Anthropic 的账号登录时默认间隔是 1 小时。2026 年 10 月 21 日之后，这个独立的机制被取消，换成一个普通的定时任务，要用户明确设置才会创建，默认仍是每 30 分钟一次。记忆整理从 2026 年 7 月底起默认开启，之前要用户自己打开。出处：OpenClaw 文档的 heartbeat 和 dreaming 两节。
  • HarnessTax 的「高达 5 倍」出现在哪个模型上。文章的正文没有写明这个最大的倍数出现在哪个模型、哪个基准测试上。这一页「换一个运行框架，结果差多少」一节的表只列了四个 Claude 模型在 Terminal-Bench 2.0 上的结果，表里最大的差距约 1.6 倍。出处：HarnessTax。
  • Claude Haiku 4.5 那一组差值的置信区间。Claude Haiku 4.5 在 Pi 和 Codex 上相差 16.7 个百分点，这个差值的置信区间没有在文章里找到。文章给了置信区间的是 Claude Fable 5 在 Claude Code 和 Pi 之间的差值。
