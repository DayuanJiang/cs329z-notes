先看结论

  • 保持简单。有些任务用不着 agent（能自己调用工具、分很多步完成任务的语言模型系统）。步骤固定的任务用 workflow（步骤由程序写定的多次模型调用）更可靠，也更好调试。
  • 让失败看得见、能恢复。记录每次模型调用、工具调用、状态变化和错误；设好超时、重试次数和预算；工具出错时把错误信息交还给 agent，让它换个办法再试。
  • 做评估，并且在你自己的任务上做。设计上的选择要靠评估的结果来定。公开的编程基准测试（benchmark，一组题目加一个打分的办法）只在你做的就是通用编程 agent 时才是合适的目标。
  • 框架（framework，写程序时调用的库）把底层的细节包起来，省了事，也让你离系统实际在做的事更远。要知道它在底下做了什么，至少要看过它发给模型的 prompt（给模型的输入文字）。

保持简单

这一讲的第一部分按控制流把系统排成了一条线，控制流指程序里「接下来执行哪一步」由谁决定。下面的图把这条线再画了一遍。图里说的编排（orchestration）指安排多个步骤按什么顺序执行、中途出错怎么办。

{{fig 124 | 按控制流划分的那条线。左端是单个模型，它只是更大系统里的一小部分。中间是 workflow，逻辑和编排写在程序里。右端是 agent，控制流由模型决定。}}

在这条线上选位置的原则是：从能解决问题的最简单的那一档开始，每增加一分复杂度都要有理由。下表是沿着这条线的三条建议。

+
Anthropic 的同一条建议。Anthropic 2024 年 12 月的文章 Building effective agents 写道：用语言模型做应用时，建议先找尽可能简单的方案，只在需要时才增加复杂度，这可能意味着根本不做 agent 式的系统。出处：Building effective agents。

让失败看得见、能恢复

长时间运行的系统一定会遇到失败。要做的是两件事：失败发生时能被看到，以及系统能自己从失败里恢复。

下表列出四条做法。右边一列的例子都在这一讲前面出现过：DSPy 和 LangGraph 是写程序用的框架，Temporal 管可靠性，MLflow、LangSmith、Langfuse 管可观测性（observability，能从外面看到系统内部每一步发生了什么），OpenHands 和 mini-SWE-agent 是两个开源的运行框架（harness，包在模型外面、给它工具并管理多轮对话的程序）。

第二条做法的四个例子限制的东西各不相同。先交代三个名字。GEPA 是 DSPy 的一个优化器，它根据数据和度量（metric，给输出打分的函数）自动改写 prompt，度量调用指用度量给一次输出打一次分。dspy.RLM 是 DSPy 里处理很长输入的模块，它让模型写代码去查看输入。HarnessTax 是第五部分讲的一篇比较运行框架的文章。

把错误交还给 agent

工具调用失败时，还有一种恢复办法：程序继续运行，运行框架把错误信息当作这次工具调用的结果返回给模型，让它自己决定怎么办。

{{fig 125 | 上半部分用英文列出上面表里的四条做法，右边是 Temporal、MLflow、Langfuse 三个工具的标志。下方的截图来自 Claude Code。模型发出了一条命令：先 sleep 30 秒，再用 grep 查一个日志文件。运行框架拦下了这条命令，返回了一段错误信息。}}

截图里返回的那段文字有三层内容。第一层说这条命令被拦下了。第二层说原因：它先 sleep 30 秒再检查。第三层说应该怎么做：等一个条件时用专门的监控工具，等一条自己启动的命令时让它在后台运行，不要用几个更短的 sleep 绕过这条限制。模型读到之后，可以换一种写法再试。

这里的要点是错误信息要写给模型看。一句「命令失败」帮不上忙；说明哪里不对、该怎么改，模型才有恢复的依据。这一讲的日历应用 tinycal 也是这样设计的：输入不合法时，它抛出一个带说明文字的错误，agent 可以读到并据此改正。

+
在接口层面是怎么做的。Claude 的 API 里，工具的执行结果放在 tool_result 里交还给模型。工具执行出错时，可以把错误信息放进去，并标上 is_error。文档建议把错误信息写得有指导性，让模型有足够的信息去恢复或调整。Claude Code 的文档也写明，一次工具调用被拦下时，拦下的理由会展示给模型。出处：Claude API 文档；Claude Code 文档的 hooks 一节。

一个研究的例子：让另一个 agent 来盯着

观察运行记录、发现问题、回退重试，这些事也可以交给一个 agent 来做。Yu 等人 2026 年的论文 Shepherd 把这样的 agent 叫作 meta-agent：创建、操作和管理其他 agent 的更高一层的 agent。

{{fig 126 | Shepherd 论文的图。上半部分：一个 meta-agent 创建了一个 agent 并观察它的运行。agent 的某一步改坏了代码，meta-agent 介入，把状态回退到那一步之前，另开一个分支重做，这一次通过了。右边是对应的代码。下半部分是三组实验的结果。图片来源：Yu 等，2026。}}

它的做法是把一个 agent 的整个执行过程变成一个可以操作的对象。模型的每个动作、每次工具调用、环境的每次变化，都记成一条结构化的事件，连成一条像 Git 提交历史一样可以回退的记录。meta-agent 可以订阅这条记录来观察，可以往里面插入事件来干预，可以回到过去的任何一个状态，也可以从某个状态分出一份副本另做尝试。

图的下半部分有三组实验。下面逐组来看，每组先说量的是什么，再列结果，最后说读这组数要知道的背景。三组数字和图一致，取自论文的正文和表格。

第一组：运行时干预

这组实验用的是 CooperBench 这个基准测试。两个 agent 并行地各做一个功能，量的是两个功能都通过测试的比例。干活的是两个 Claude Haiku 4.5，meta-agent 在它们运行的时候观察和干预。

最后一行是同一篇论文给的对照。一个 agent 单干的 57.2%，比加了 Opus 4.7 监督的 54.7% 还高。所以 meta-agent 在这里做到的，是把并行协作损失掉的成绩大部分补了回来。它没有超过一个 agent 单干。

第二组：事后优化

这组实验用的是 LiveCodeBench 这个基准测试。用几种方法分别优化同一个 agent，量的是优化之后在留出的 100 道题上的通过率，留出的题没有在优化时用过。

参加比较的方法有三种。Meta-Harness 是第五部分讲的让模型自己改运行框架的方法，论文里写作 MetaHarness。GEPA 是上一节提过的 DSPy 优化器。CRO 是这篇论文提出的方法，全名 Counterfactual Replay Optimization：先找出之前运行里失败的原因，提出对 agent 流程的修改，再从这个修改会改变行为的那一步起把运行重放一遍，检验修改有没有用。

CRO 比 GEPA 高 2.3 个百分点，而论文的表里两者各自的标准差在 1.5 到 1.7 个百分点。差距和波动差不多大，这个领先有可能只是波动。GEPA 用的时间更短，是 73 分钟，CRO 是 117 分钟。

第三组：训练

这组实验用强化学习微调两个开放权重的模型。强化学习是让模型反复尝试、按结果的好坏调整参数的训练办法，开放权重指模型的参数公开，可以下载下来自己训练和运行。量的是微调之后在 Terminal-Bench 2.0 的 89 个任务上的通过率，Terminal-Bench 2.0 是一个让 agent 在命令行环境里完成任务的基准测试。

比较的是两种训练办法。GRPO 是一种强化学习算法。Tree-GRPO 是论文提出的做法：由 meta-agent 在运行中途选一步，从那里分出几个分支接着跑，用分支之间结果的差别来判断每一步的好坏。

Tree-GRPO 比普通的 GRPO 在两个模型上分别高 5.2 和 3.4 个百分点。测试集只有 89 个任务。论文的表在每个通过率后面标了一个正负多少的数，大小在 3 到 4 个百分点，表的说明没有写明它是标准差还是别的量。这个数和提高的幅度在同一个量级，所以这个提高也有可能只是波动。

不管由人还是由 agent 来做，道理是同一个：系统运行的时候，要有人或程序在观察运行记录，发现问题时介入。

做评估，在自己的任务上做

为 agent 做设计上的选择，最好的依据是评估的结果。没有评估，每一个「这样改应该会更好」都只是猜测。

  • 评估让优化成为可能。第三部分里优化器能把小模型的 prompt 改好，前提是先有了 50 封带标注的邮件和一个精确匹配的度量，也就是日期、开始时间、时长三项都和标准答案完全一致才算对。手工改系统时也一样，评估告诉你一个改动是帮了忙还是帮了倒忙。
  • 评估要早搭。搭一个像样的评估是做 AI 系统最重要的几步之一，也常常被低估。一个项目里最先该做的事情之一，就是把评估搭好，后面的设计选择才有依据。
  • 度量要选对。准确率是最容易想到的。花费和延迟也可能很重要，面向用户的产品尤其看重延迟。
  • 测试的任务要有代表性，也要包括边界情况和会失败的场景。只在顺利的情形下测试，会让你以为系统总是那样工作，据此做出错误的设计决定。
{{fig 128 | 左边打了叉的是三个公开的编程基准测试：Terminal-Bench、SWE-bench 和 DeepSWE。右边打了勾的是「你自己领域的评估」。}}

各家公司发布模型和 agent 时，都会报告在几个知名基准测试上的成绩。看到这些数字，很容易觉得自己的系统也该以这些成绩为目标。这通常选错了目标。

这一讲的演示就是一个小规模的例子：任务是从邮件里提取日程，评估就是 50 封这类邮件加一个检查日期、时间和时长的度量。怎样把一个评估做得可靠，第 13 讲和第 15 讲会讲到。

框架的局限

这一讲用了 DSPy、LangGraph 两个框架和 Temporal 这个平台，也看了几个现成的运行框架。用它们有三点要留意，列在下表里。

表里有三个词先说明一下。抽象指框架把底层的细节包起来之后，留给写程序的人用的那几个概念。PyTorch 是一个用来训练神经网络的 Python 框架。反向传播是训练神经网络时算导数的那一步，在 PyTorch 里只要写一行代码，数学由框架在底下做。

表里第一条局限的应对办法，Anthropic 2024 年 12 月的文章 Building effective agents 也提过。它建议开发者先直接调用模型的 API，很多模式几行代码就能实现。如果用了框架，要确保理解底下的代码。

i
一个就发生在这一讲用的框架上的例子。第二部分展示的 prompt 格式，是 DSPy 3.4 的默认行为。2026 年 11 月 10 日发布的 DSPy 3.5.0 把默认的 adapter（把 signature 转成 prompt 的部件）换成了另一种。发布说明写明，这会改变 prompt 和输出的约定，即使你的 signature（DSPy 里对模型输入和输出的声明）一个字没改。也就是说，同一份代码在升级前后，发给模型的文字不一样。在旧格式下优化出来的指令，换了格式之后效果是否还一样，需要重新评估才知道。出处：DSPy 3.5.0 的发布说明。
+
「把 prompt 给我看」。Hamel Husain 2024 年 2 月有一篇文章，标题的意思是「把 prompt 给我看」。文章主张：想弄懂一个框架，先看它发给模型的 prompt。他的论点是：这些工具发给模型的 prompt，就是对它们在做什么的自然语言描述，是理解它们最快的途径。他用一个拦截网络请求的工具，逐个查看了 Guardrails、Guidance、LangChain、Instructor 和 DSPy 实际发出的请求。对 DSPy，他发现官方的入门示例跑了 30 多分钟，向模型发了几百次请求，原因是优化器在反复抽样例、挑选效果最好的组合。他也说明自己不反对这些库，只是对那些让人离模型太远的框架保持警惕。出处：Husain 的文章。

在这一讲里，不用另装工具也能做同样的检查。DSPy 自带的 inspect_history 会打印最近发给模型的 prompt，前面几部分已经多次用到。

工程是一个循环

把 agent 当工程来做，是不断重复四步：搭建，运行，评估，改进。第一次搭出来的系统，通常不会是最后上线的那一个。

第三部分的演示就走了这样一圈：搭一个提取日程的程序，交给小模型运行，在 20 封测试邮件上评估，只有 11 封全对。用优化器改写指令之后再评估，20 封全对。

在这个循环里，前面讲的四条做法都用得上：

  • 从简单的开始，每增加一分复杂度都要有理由。
  • 为失败和恢复做设计。想好系统的每一部分失败时会发生什么，用上能帮你恢复的工具。
  • 用证据和评估来判断质量、花费和延迟。先搭评估，跑评估，再根据结果做设计决定。
  • 彻底弄懂你的系统是怎么工作的。出了问题时，原因可能在最底下的某一层。
