先看结论

  • 保持简单。有些任务用不着 agent（能自己调用工具、分很多步完成任务的语言模型系统）。步骤固定的任务用 workflow（步骤由程序写定的多次模型调用）更可靠，也更好调试。
  • 让失败看得见、能恢复。记录每次模型调用、工具调用、状态变化和错误；设好超时、重试次数和预算；工具出错时把错误信息交还给 agent，让它换个办法再试。
  • 做评估，并且在你自己的任务上做。设计上的选择要靠评估的结果来定。公开的编程基准测试只在两种情况下才是合适的目标：你做的是通用的编程 agent 的运行框架，或者是一项对各种 agent 都适用的改进。基准测试（benchmark）是一组题目加一个打分的办法。运行框架（harness）是包在模型外面、给它工具并管理多轮对话的程序。
  • 框架（framework，写程序时调用的库）把底层的细节包起来，省了事，也让你离系统实际在做的事更远。要知道它在底下做了什么，至少要看过它发给模型的 prompt（给模型的输入文字）。

保持简单

这一讲的第一部分把系统排成了一条线，依据是控制流由谁决定。控制流指程序里「接下来执行哪一步」的决定。下面的图把这条线再画了一遍。图里说的编排（orchestration）指安排多个步骤按什么顺序执行、中途出错怎么办。

在这条线上选位置的原则是：从能解决问题的最简单的那个位置开始，每增加一分复杂度都要有理由。下表是沿着这条线的三条建议。

后两条建议各补一句。第二条里的工具该怎么选，可以看第五部分的「四个开源的例子」一节，那里的几个运行框架给模型的工具各不相同，比如 mini-SWE-agent 只给一个，Pi 给四个。第三条是否适用要看任务本身，比如它原来要分多少步。有的任务可以整个写成「一个输入对应一个输出」，这就是表里写的情形，可以由一个专门微调过的模型一步做完。

+
Anthropic 的同一条建议。Anthropic 2024 年 12 月的文章 Building effective agents 写道：用语言模型做应用时，建议先找尽可能简单的方案，只在需要时才增加复杂度。有时候，最简单的方案就是根本不搭 agentic system。文章用 agentic system 这个词统称 workflow 和 agent。出处：Building effective agents。

让失败看得见、能恢复

长时间运行的系统一定会遇到失败。要做的是两件事：失败发生时能被看到，以及系统能自己从失败里恢复。

这两件事落到具体的措施上有四项，列在下表里。右边一列的例子都在这一讲前面出现过。MLflow、LangSmith、Langfuse 是管可观测性（observability，能从外面看到系统内部每一步发生了什么）的工具，OpenHands 和 mini-SWE-agent 是两个开源的运行框架。

第二项措施的四个例子限制的东西各不相同。先交代三个名字。GEPA 是 DSPy 的一个优化器，它根据数据和度量（metric，给输出打分的函数）自动改写 prompt，度量调用指用度量给一次输出打一次分。dspy.RLM 是 DSPy 的一个 module（DSPy 里决定怎样调用模型的部件），用来处理很长的输入，它让模型写代码去查看输入。HarnessTax 是第五部分讲的一篇比较运行框架的文章。

把错误交还给 agent

上面第二张表里 Temporal 的重试，是由程序来恢复：一步失败了，就把这一步再执行一次。agent 还有一种恢复办法，是让模型自己来恢复。一次工具调用失败了，或者被运行框架拦下了，程序都继续运行，运行框架把错误信息当作这次工具调用的结果返回给模型，让它自己决定怎么办。

{{fig 125 | 上半部分用英文列出这一节第一张表里的四项措施：追踪调用和错误，设置超时、重试上限和预算，记下输出，监控系统的状态。右边是 Temporal、MLflow、Langfuse 的标志。下方的截图来自 Claude Code，它是 Anthropic 做的、面向编程任务的运行框架。模型发出了一条命令：先 sleep 30 秒，再用 grep 查一个日志文件。运行框架拦下了这条命令，返回了一段错误信息。}}

截图里返回的那段文字有三部分内容。第一部分说这条命令被拦下了。第二部分指出被拦下的是哪种写法：先 sleep 30 秒，后面接着做检查。第三部分说等待应该怎么做：等一个条件时用专门的监控工具，等一条自己启动的命令时让它在后台运行，不要改用几个更短的 sleep 来绕过这次拦截。这段文字没有写明不让这样等待的原因。模型读到之后，可以换一种写法再试。

这里的要点是错误信息要写给模型看。错误信息写明哪里不对、该怎么改，模型才有恢复的依据。这一讲的日历应用 tinycal 也是这样设计的：输入不合法时，它抛出一个带说明文字的错误，agent 可以读到并据此改正。

+
在接口层面是怎么做的。Claude 的 API 里，工具的执行结果放在 tool_result 里交还给模型。工具执行出错时，可以把错误信息放进去，并标上 is_error。文档建议在错误信息里写明哪里出了错、模型接下来该试什么，让模型有足够的信息去恢复或调整。Claude Code 的文档也写明，一次工具调用被拦下时，拦下的理由会展示给模型。出处：Claude API 文档；Claude Code 文档的 hooks 一节。

一个研究的例子：让另一个 agent 来监督

观察运行记录、发现问题、回退重试，这些事也可以交给一个 agent 来做。Yu 等人 2026 年的论文 Shepherd 把这样的 agent 叫作 meta-agent：创建、操作和管理其他 agent 的更高一层的 agent。

{{fig 126 | Shepherd 论文的图。上半部分：一个 meta-agent 创建了一个 agent 并观察它的运行。agent 的某一步改坏了代码，meta-agent 介入，把状态回退到那一步之前，另开一个分支重做，这一次通过了。右边是对应的代码。下半部分是三组实验的结果。图片来源：Yu 等，2026。}}

Shepherd 的做法是把一个 agent 的整个执行过程记下来，交给 meta-agent 查看和改动。具体地说，模型的每个动作、每次工具调用、环境的每次变化，都记成一条结构化的事件，连成一条像 Git 提交历史一样可以回退的记录。meta-agent 可以订阅这条记录来观察，可以往里面插入事件来干预，可以回到过去的任何一个状态，也可以从某个状态分出一份副本另做尝试。

图的下半部分有三组实验。下面逐组来看，每组先说量的是什么，再说比较的是哪几种做法，然后列结果，最后说这组数该怎么读。三组数字和图一致，取自 Shepherd 论文的正文和表格。图上三组的纵轴都写着 Pass Rate，三组量的东西各不相同，下面分别叫通过率、做对的比例和成功率。

第一组：运行时干预

这组实验用的是 CooperBench 这个基准测试。两个 agent 并行地各做一个功能，量的是两个功能都通过测试的比例，下面叫通过率。执行任务的两个 agent 用的模型都是 Claude Haiku 4.5，meta-agent 在它们运行的时候观察和干预。下表里的 Sonnet 4.6 和 Opus 4.7 是另外两个 Claude 模型。

CooperBench 的论文记录了一个现象：并行写代码的 agent 即使可以互相发消息，配合得也不好，成功的比例低于一个 agent 独自做。这组实验看 meta-agent 能把这个差距补回多少。

最后一行是 Shepherd 论文给的对照。一个 agent 独自按顺序做是 57.2%，两个 agent 并行做是 28.8%，并行让通过率少了 28.4 个百分点。Shepherd 论文的解释是，并行时每个 agent 只看得到对方发来的消息，这些消息只反映发送方自己看到的那部分情况。

meta-agent 能直接看到两边的全部动作。由 Opus 4.7 担任时，它把通过率提到 54.7%，补回了这个差距的 91%，仍低于一个 agent 独自做的 57.2%。

第二组：事后优化

这组实验用的是 LiveCodeBench 这个基准测试，它的题目是从 LeetCode、AtCoder、CodeForces 三个编程竞赛网站陆续收集的新编程题。量的是优化之后在留出的 100 道题上做对的题所占的比例，留出的题没有在优化时用过。

被优化的是一个解这些题的 workflow。它是一段 Python 程序，执行它的模型是 GPT-5.4-mini。用三种方法分别优化这个 workflow，提出修改的模型都是 GPT-5.4。

参加比较的方法有三种。Meta-Harness 是第五部分讲的让模型自己改运行框架的方法，Shepherd 论文里写作 MetaHarness。GEPA 是第三部分讲的 DSPy 优化器。第三部分的演示里，它改写的是 prompt 里的指令。DSPy 的文档说明，GEPA 改写的是一个系统里的文字部分，prompt 是其中一种。在这组实验里，Shepherd 论文让它改写的是 workflow 的代码。CRO 是 Shepherd 论文提出的方法，全名 Counterfactual Replay Optimization。

CRO 分三步，前两步由一个 meta-agent 来做。第一步，meta-agent 读这个 workflow 之前运行留下的记录，找出失败的原因。第二步，它提出几处对 workflow 代码的修改。第三步由程序逐个检验这些修改：对每一处修改，在之前的运行记录里找到最先受它影响的那一步，从那一步起用改过的 workflow 重新往下跑，前面的各步原样保留。名字里的 counterfactual 指的就是第三步回答的问题：假如当时改了这一处，结果会怎样。

CRO 比 GEPA 高 2.3 个百分点。表里的每个数是三次评估的平均值，Shepherd 论文的表还给出了这三次评估的标准差，GEPA 是 1.5 个百分点，CRO 是 1.7 个百分点。标准差是衡量多次评估的结果之间波动有多大的数。差距和波动差不多大，这个领先有可能只是波动。

GEPA 完成一次优化用的时间更短，是 73 分钟，CRO 是 117 分钟。

第三组：训练

这组实验用强化学习微调两个开放权重的模型。强化学习是让模型反复尝试、按结果的好坏调整参数的训练办法，开放权重指模型的参数公开，可以下载下来自己训练和运行。量的是微调之后在 Terminal-Bench 2.0 的 89 个任务上的成功率，Terminal-Bench 2.0 是一个让 agent 在命令行环境里完成任务的基准测试。

比较的是两种训练办法。GRPO 是一种强化学习算法。它让模型把同一个任务做好几遍，每一遍做完才得到一个分数。训练时拿每一遍的分数和其余几遍的分数比，得出这一遍比别的几遍好还是差，再把这个结论原样记给这一遍里的每一步。所以它分不出同一遍当中哪几步做得好、哪几步做得差。

Tree-GRPO 是 Shepherd 论文提出的做法：由 meta-agent 在运行中途选一步，从那里分出几个分支接着跑。这几个分支在分支点之前完全相同，结果的差别只来自分支点之后的各步，所以可以用分支之间结果的差别来判断这些步骤的好坏。

Tree-GRPO 比普通的 GRPO 在两个模型上分别高 5.2 和 3.4 个百分点。测试集只有 89 个任务。Shepherd 论文的表在每个成功率后面标了一个正负多少的数，大小在 3 到 4 个百分点，表的说明没有写明它是标准差还是别的量。这个数和提高的幅度在同一个量级，所以这个提高也有可能只是波动。

三组实验做的事不同，用的都是这一节开头说的那条可以回退的记录。第一组里，meta-agent 靠它在运行当中看到两个 agent 的全部动作，发现问题时介入。第二组在运行结束之后回到记录里的某一步，用改过的 workflow 重新往下跑，检验修改有没有用。第三组在运行中途从某一步分出几个分支，供训练时比较。

第一组的结果和上一节「让失败看得见、能恢复」是同一个道理：系统运行的时候，要有人或程序在观察运行记录，发现问题时介入。两个并行的 agent 有 meta-agent 观察和干预时，通过率比没有时高。

三组的结果都要连同各自的限制一起读。第一组里有 meta-agent 的并行仍低于一个 agent 独自做，第二组和第三组的领先有可能只是波动。

做评估，在自己的任务上做

为 agent 做设计上的选择，最好的依据是评估的结果。没有评估，每一个「这样改应该会更好」都只是猜测。

  • 有了评估，才能做优化。第三部分里优化器能把小模型的 prompt 改好，前提是先有了 50 封带标准答案的邮件和一个精确匹配的度量，也就是日期、开始时间、时长三项都和标准答案完全一致才算对。手工改系统时也一样，评估告诉你一个改动让系统变好了还是变差了。
  • 评估要早搭。把评估搭好是做 AI 系统最重要的几步之一，也常常被低估。它应该是一个项目里最先做的事情之一，有了它，后面的设计选择才有依据。
  • 量什么要选对。准确率是最容易想到的。花费和延迟也可能很重要，面向用户的产品尤其看重延迟。
  • 测试的任务要有代表性，也要包括边界情况和会失败的场景。只在顺利的情形下测试，会让你以为系统总是那样工作，据此做出错误的设计决定。

评估还要在自己的任务上做。下面的图拿三个公开的编程基准测试和自己领域的评估对照，三个基准测试是 Terminal-Bench、SWE-bench 和 DeepSWE。

先说明这三个基准测试各考什么。Terminal-Bench 让 agent 在命令行环境里完成任务，上一节第三组实验用的是它的 2.0 版。SWE-bench 的题目取自 GitHub 上真实的软件问题。这里的 DeepSWE 指 Datacurve 2026 年发布的基准测试，有 113 个软件工程任务。它的官方页面说这些任务是 long-horizon 的，也就是要连续做很多步才能完成，题目都是专门新写的，没有拿已有的代码提交来改编。

{{fig 128 | 左边打了叉的是 Terminal-Bench、SWE-bench 和 DeepSWE 这三个基准测试的标志。右边打了勾的是「你自己领域的评估」。}}

各家公司发布模型和 agent 时，都会报告在几个知名基准测试上的成绩。看到这些数字，很容易把这些成绩当作自己系统的目标。它们通常不适合当这个目标，下表列出两种情况各该拿什么来评估。

这一讲的演示就是一个小规模的例子：任务是从邮件里提取日程，评估用的是 20 封带标准答案的测试邮件，加一个检查日期、开始时间和时长的度量。这 20 封是从 50 封这类邮件里留出来的，另外 30 封交给优化器。怎样把一个评估做得可靠，第 13 讲和第 15 讲会讲到。

框架的局限

这一讲用了 DSPy、LangGraph 两个框架和 Temporal 这个平台，也看了几个现成的运行框架。用它们有三点要留意，列在下表里。

表里有三个词先说明一下。抽象指框架把底层的细节包起来之后，留给写程序的人用的那几个概念。PyTorch 是一个用来训练神经网络的 Python 框架。反向传播是训练神经网络时算导数的那一步，在 PyTorch 里只要写一行代码，数学由框架在底下做。

表里第一条局限的应对办法，Anthropic 2024 年 12 月的文章 Building effective agents 也提过。它建议开发者先直接调用模型的 API：文章里介绍的那些搭 workflow 和 agent 的常见写法，很多用几行代码就能实现。如果用了框架，要确保理解底下的代码。

+
「把 prompt 给我看」。Hamel Husain 2024 年 2 月有一篇文章，标题的意思是「把 prompt 给我看」。文章主张：想弄懂一个框架，先看它发给模型的 prompt。理由是这些 prompt 用自然语言写明了框架实际在做什么，读它们是弄懂一个框架最快的办法。他用一个能拦截网络请求的程序，逐个查看了 Guardrails、Guidance、LangChain、Instructor 和 DSPy 这几个库实际发出的请求。对 DSPy，他发现官方的入门示例跑了 30 多分钟，向模型发了几百次请求，原因是 DSPy 的优化器在反复抽取示例放进 prompt，再用度量比较，留下效果最好的那些示例。他也说明，文章里的许多库如果用得仔细、用在合适的地方，是可能有帮助的。他见过太多人没弄懂这些库在做什么就用上了。他提防的是那些把使用者和模型隔得太远的框架。出处：Husain 的文章。

在这一讲里，不用另装软件也能做同样的检查。DSPy 自带的 inspect_history 会打印最近发给模型的 prompt，第二部分已经用过。

表里第三条局限提到，库的行为可能会变。这一讲用的 DSPy 就有一个例子。

i
DSPy 3.5.0 换了默认的 prompt 格式。第二部分展示的 prompt 格式，是 DSPy 3.4 的默认行为。2026 年 11 月 10 日发布的 DSPy 3.5.0 把默认的 adapter（把 signature 转成 prompt 的部件）换成了另一种。发布说明写明，这会改变 prompt 和输出的约定，即使你的 signature（DSPy 里对模型输入和输出的声明）一个字没改。也就是说，同一份代码在升级前后，发给模型的文字不一样。在旧格式下优化出来的指令，换了格式之后效果是否还一样，需要重新评估才知道。出处：DSPy 3.5.0 的发布说明。

工程是一个循环

把 agent 当工程来做，是不断重复四步：搭建，运行，评估，改进。第一次搭出来的系统，通常不会是最后上线的那一个。

第三部分的演示就把这四步做了一遍：搭一个提取日程的程序，交给小模型运行，在 20 封测试邮件上评估，只有 11 封全对。用优化器改写指令之后再评估，20 封全对。

在这个循环里，这一页「先看结论」列的四条做法都用得上：

  • 从简单的开始，每增加一分复杂度都要有理由。
  • 设计时就考虑失败和恢复。想好系统的每一部分失败时会发生什么，用上能帮系统从失败里恢复的平台，比如 Temporal。
  • 用证据和评估来判断质量、花费和延迟。先搭评估，跑评估，再根据结果做设计决定。
  • 彻底弄懂你的系统是怎么工作的。出了问题时，原因可能在最底下的某一层。
