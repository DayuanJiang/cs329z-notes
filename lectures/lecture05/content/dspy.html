先看结论

  • DSPy 有三个核心概念。signature（签名）声明模型的输入和输出，回答「要什么」。module（模块）决定用什么方式调用模型，回答「怎么做」。optimizer（优化器）根据数据和度量自动改进 prompt 或模型权重。这一页讲前两个，优化器在下一部分。
  • signature 里只有字段的名字、类型、一句可选的描述，和一句任务说明。发给模型的 prompt（给模型的输入文字）由 DSPy 按固定的规则拼出来，拼的过程不调用模型。
  • 换一种推理方式只需要换 module。dspy.Predict 直接要结果，dspy.ChainOfThought 让模型先写一段推理再给结果，signature 不用改。
  • 自定义的 module 里可以把几次模型调用和普通的 Python 代码写在一起。步骤的顺序和分支都由代码决定，这样的程序就是一个 workflow（步骤由程序写定的多次模型调用）。

三个概念：signature、module、optimizer

DSPy 是一个 Python 框架（framework，写程序时调用的库，它规定了一套写法，并替你处理底层的细节）。它出自斯坦福大学 Omar Khattab 等人 2023 年的论文，名字是 Declarative Self-improving Python 的缩写，意思是「声明式的、能自我改进的 Python」。它的主张是：用代码声明你要模型做什么，prompt 的具体措辞交给框架去生成和改进。

最简单的 signature：一个字符串

signature 最简单的写法是一个字符串，箭头左边是输入字段，右边是输出字段。下面三行就是一个能对话的程序：

signature = "message -> response"
chat = dspy.Predict(signature)

print(chat(message="Hello, how are you?").response)

dspy.Predict 是最简单的 module，它拿到 signature 之后生成一个可以调用的对象。调用时传入的参数名 message，和取结果时用的属性名 response，都和 signature 里写的字段名一致。运行后模型回了一句问候。

以前要让模型做情感分类，得写一段 prompt 说明任务和回答的格式。有了 signature，把输出字段改个名字就行：

sentiment_signature = "message -> sentiment"
sentiment_classifier = dspy.Predict(sentiment_signature)

print(sentiment_classifier(message="I am very happy today!").sentiment)
print(sentiment_classifier(message="I am very angry today!").sentiment)
print(sentiment_classifier(message="I am very confused today!").sentiment)

三次调用的输出依次是 positive、Negative、negative。结果有两个毛病：大小写不统一，后面的程序没法直接拿它做判断；「情感」有哪几种取值完全由模型自己决定。原因是这个 signature 只给了一个字段名，没有规定输出该是什么样子。

给字段加上类型

解决办法是给字段标上类型。下面把输出限定为三个取值之一，并且多要一个浮点数表示把握有多大：

typed_signature = "message: str -> sentiment: " \
   "Literal['positive','negative','neutral'], confidence: float"
typed_sentiment_classifier = dspy.Predict(typed_signature)

print(typed_sentiment_classifier(message="I am very happy today!"))

现在输出是一个结构化的 Prediction 对象，sentiment 一定是三个取值之一，confidence 一定是浮点数。

signature 变成了什么 prompt

模型只认文字，所以 signature 最后还是要变成一段 prompt。DSPy 里做这件事的部件叫 adapter（适配器）。调用 dspy_llm.inspect_history(n=1) 可以把最近一次发给模型的内容原样打印出来。上面那个带类型的 signature，发出去的 system message（对话开头给模型的总说明）节选如下：

Your input fields are:
1. `message` (str):
Your output fields are:
1. `sentiment` (Literal['positive', 'negative', 'neutral']):
2. `confidence` (float):
All interactions will be structured in the following way, with the appropriate values filled in.

[[ ## message ## ]]
{message}

[[ ## sentiment ## ]]
{sentiment}        # note: the value you produce must exactly match (no extra characters) one of: positive; negative; neutral
...
In adhering to this structure, your objective is:
        Given the fields `message`, produce the fields `sentiment`, `confidence`.

模型的回答也按同样的标记来写：先是 [[ ## sentiment ## ]] 和取值，再是 [[ ## confidence ## ]] 和数字，最后是 [[ ## completed ## ]]。DSPy 按这些标记把回答切开，转成对应的 Python 类型，放进 Prediction。

关于这个转换，有三点值得知道。

  • 它是确定性的。从 signature 到 prompt 是普通的代码按规则拼字符串，不经过语言模型。同一个 signature，在 adapter 和输入都相同时，每次拼出来的 prompt 都一样。
  • 格式由 DSPy 检查。模型的回答如果切不开，或者类型对不上，DSPy 会发现。上面这种带 [[ ## 字段名 ## ]] 标记的格式出自名叫 ChatAdapter 的 adapter。它解析失败时，会换成要求模型输出 JSON 的 JSONAdapter 把请求重发一次。还是不行才报错。
  • 没有写任务说明时，DSPy 会补一句。上面最后一行「给定字段 message，产生字段 sentiment、confidence」就是自动补的。
i
这里看到的 prompt 格式属于 DSPy 3.4。演示是在 2026 年 10 月初运行的，当时 DSPy 默认使用 ChatAdapter。2026 年 11 月 10 日发布的 3.5.0 把默认的 adapter 换成了 XMLAdapter，用 XML 风格的标签来标记字段，文档还说明 ChatAdapter 将来会被弃用。signature 的写法没有变，变的是它被拼成的 prompt。用新版本运行同样的代码，inspect_history 打印出来的内容会和这里不同。出处：DSPy 文档的 adapter 一节；3.5.0 的发布说明。

用类来写 signature

字段一多，字符串就不好读了。signature 也可以写成一个类。下面这个类就是后面一直在用的「提取日程」：

import datetime as dt

class ExtractEvent(dspy.Signature):
    """Extract event details from an email."""
    email: str = dspy.InputField()
    event_name: str | None = dspy.OutputField()
    date: dt.date | None = dspy.OutputField()
    start: dt.time | None = dspy.OutputField(desc="24-hour clock")
    duration_minutes: int | None = dspy.OutputField(desc="duration of the event in minutes, if known")

extract = dspy.Predict(ExtractEvent)
extract(email="We have a meeting scheduled for this Friday, October 9th at 10 AM PST.")

运行的结果是 event_name='meeting'、date=datetime.date(2026, 10, 9)、start=datetime.time(10, 0)、duration_minutes=None。日期和时间已经是 Python 的日期和时间对象，后面的代码可以直接用。

关于 signature 的几个问题

module：换一种推理方式

signature 说的是要什么，module 说的是怎么让模型给出来。把 dspy.Predict 换成 dspy.ChainOfThought，signature 一个字不改：

extract_cot = dspy.ChainOfThought(ExtractEvent)
extract_cot(email="We have a meeting scheduled for this Friday, October 9th at 10 AM PST.")

结果里多了一个排在最前面的字段 reasoning，内容是模型的推理：邮件说这个星期五 10 月 9 日上午 10 点有一个会议，所以名称是 meeting，日期是 10 月 9 日，开始时间是 10:00，没有给出时长。后面四个字段和之前一样。

ChainOfThought 做的事很简单：在输出字段的最前面加一个 reasoning。字段的顺序在这里有用。模型是从前往后生成文字的，推理排在前面，它就得先把推理写出来，再填后面的答案。

这是演示所用的 DSPy 3.4 的行为。从 3.5.0 起，如果模型本身带有推理功能，ChainOfThought 会直接使用模型自带的推理，reasoning 字段里可能是空的。

把 module 和 Python 代码组合起来

真实的程序很少只调用一次模型。这个例子需要第二次调用：给日程挑一个表情符号。先为它写一个 signature：

class PickEmoji(dspy.Signature):
    """Pick one emoji that best represents a calendar event."""
    event_name: str = dspy.InputField()
    emoji: str = dspy.OutputField(desc="exactly one emoji character")

pick_emoji = dspy.ChainOfThought(PickEmoji)
pick_emoji(event_name="Dentist")

输入 Dentist（牙医），模型选了一颗牙齿的表情符号。

然后写一个自己的 module，把两次模型调用、一个判断和一次日历调用串起来。写法模仿了 PyTorch：在 __init__ 里声明要用的子模块，在 forward 里写执行的过程。

class UpdateCalendarFromEmail(dspy.Module):
    def __init__(self):
        self.extract = dspy.ChainOfThought(ExtractEvent)   # LLM call 1
        self.pick_emoji = dspy.ChainOfThought(PickEmoji)   # LLM call 2

    def forward(self, email: str):
        details = self.extract(email=email)
        # Plain Python control flow: not every email contains an event.
        if details.event_name is None or details.date is None or details.start is None:
            return dspy.Prediction(event=None, status="no event found in email")
        emoji = self.pick_emoji(event_name=details.event_name).emoji
        event = tinycal.add_event(title=details.event_name, date=details.date, start=details.start,
                                  duration_minutes=details.duration_minutes, emoji=emoji)
        return dspy.Prediction(event=event, status="added to calendar")

中间的 if 是普通的 Python：名称、日期、开始时间缺了任何一样，就认为这封邮件里没有日程，直接返回。这条规则是写程序的人定的，和 DSPy 无关。时长可以缺，tinycal 在没有时长时默认按 1 小时算。

这一部分的小结

  • signature 定义输入和输出的约定。字段名、类型、desc 和文档字符串都会进到 prompt 里。
  • module 规定怎样完成这个约定，比如 dspy.Predict、dspy.ChainOfThought、dspy.BestOfN。
  • 自定义的 module 把多个 signature 和 Python 逻辑组合成一个程序。
  • 想知道框架到底给模型发了什么，随时可以用 inspect_history 把 prompt 打印出来看。
