先看结论

  • 有些问题的答案分散在整篇文档里，甚至分散在很多篇文档里，任何单独的一块都答不了。索引里只有一个个单独的块时，这类问题很难答好。
  • RAPTOR 把块组织成一棵树：把相近的块聚在一起，让语言模型写摘要，摘要再聚、再写摘要。查询时树上所有层的节点一起参加检索，问细节的问题会对上原文的块，问主题的问题会对上摘要。
  • GraphRAG 先让语言模型从文档里抽出实体（人、组织、地点等）和它们之间的关系，连成一张图，再把连接紧密的实体分成一个个社区，给每个社区写摘要。查询时让每个社区的摘要各自回答，再把这些部分的回答合成一个总的回答。
  • 结构越复杂，能回答的问题层次越高，建索引也越贵。很多大规模的问答系统仍然用简单的切块，因为它快，而且能应付大多数问题。
  • 向量多了之后，逐个比较太慢，要用近似最近邻搜索：牺牲一点召回，换来快得多的速度。召回（recall）指真正最近的那几个向量里实际找到了多少。HNSW 是近似搜索里用得很广的一种办法。

序列、树、图：三种组织块的办法

上一部分的做法，不管怎么切、怎么补背景，都是把文档当成一串前后相接的块，检索时每一块单独和查询比较。补背景能让一块说清自己出自哪篇文档、哪个位置，但它装的仍然只是原文的一小段。块和块之间有什么关系、整篇文档合起来讲了什么，索引里没有记录。

这对一类问题是不够的。问「灰姑娘的故事主题是什么」，答案不在任何一段里，要读完整个故事才能概括出来。问「公众怎么看待某个话题」，可能要综合十篇以上的文档。借用数据结构的说法，块可以按三种方式组织。

RAPTOR：从下往上建一棵摘要树

RAPTOR 是斯坦福大学的 Sarthi 等人发表在 ICLR 2024 的工作。它的出发点是：答案分散在文档各处的问题，单独一块的向量帮不上忙，所以要在块的上面再建几层更概括的内容。

{{fig 32 | 左：一棵建好的树，最下面是原文的块，往上每一层是对下一层的摘要。中：一层是怎么建出来的，先把下面的节点聚成几组，再让语言模型给每一组写摘要。右：一个节点里存的东西，包括编号、它的子节点、摘要的文字和这段文字的向量。图片来源：Sarthi 等，2024。}}

建树是从下往上的，一共四步，反复做。

  1. 切块并算向量。把文档切成大约 100 个 token（模型处理文字的最小单位）的块，不在句子中间切断。每一块用一个向量模型算出向量。这些块是树的叶子。
  2. 聚类。按向量把相近的块聚成一组。RAPTOR 用的聚类办法允许一个块同时属于几个组，因为一段文字可能和好几个话题有关。
  3. 写摘要。让语言模型给每一组写一段摘要。这段摘要成为这一组块的父节点。
  4. 对摘要重复前面的步骤。给摘要算向量，再聚类，再写摘要，一直到没法再聚为止。

配图中间那一格里，5 个块被聚成了三组，编号 3 和 5 的块各自出现在两组里，这就是「一个块可以属于几个组」的样子。

+
论文里建树用的模型和树的大小。聚类用的是高斯混合模型（一种按概率把点分到各组的聚类办法，一个点可以同时属于几个组），聚类前先把向量降到较低的维数。写摘要用的是 gpt-3.5-turbo。平均下来，一个父节点有 6.7 个子节点，每个子节点约 86 个 token，摘要约 131 个 token。论文另外给了一个平均的比例：摘要的长度是它所概括内容的 28%。这个比例是论文单独报告的，用前面三个平均数相除得不到它，见资料说明。建树花的时间和 token 数随文档长度大致成正比。出处：Sarthi 等，2024，第 3 节和附录。
+
摘要会不会写错。论文抽查了 150 个摘要节点，其中 6 个（4%）含有轻微的不实内容。论文说这些错误没有传到上一层，对问答的结果也没有看得出的影响。出处：Sarthi 等，2024，附录。

RAPTOR 怎么查，效果如何

树建好之后，查询有两种办法。一种是从树顶开始，一层一层往下挑。另一种不分层（论文叫 collapsed tree）：把所有层的节点放在一起，直接和查询比较，挑出最相近的。论文发现第二种一直更好，因为它能让每个问题自己找到合适的详略程度：问细节的问题会对上叶子，问主题的问题会对上高层的摘要。

论文还统计过，在三个数据集上，检索回来的节点里有 18.5% 到 57% 来自叶子以上的层，说明摘要层确实被用到了。

{{fig 33 | 一棵给灰姑娘故事建的树，最下面一排是原文的块，上面两排是摘要。两个问题是：故事的中心主题是什么；灰姑娘是怎样得到幸福结局的。带框的节点是 RAPTOR 为两个问题选出的内容，箭头指着的是 DPR 选出的块。图片来源：Sarthi 等，2024。}}

配图里用来对比的 DPR 是一种向量检索器（见第四部分），它只在原文的块里找，所以箭头全部指向最下面一排。RAPTOR 选出的节点大多在上面两排，是摘要。

第二个问题尤其如此：要回答「她怎样得到幸福结局」，先要知道她是谁、幸福结局指什么，这些是把好几段合起来才有的信息。论文对这张配图的说明是：RAPTOR 取回的内容往往已经包括了 DPR 取回的信息，要么直接包括那一块，要么包含在更高层的摘要里。

论文摘要里更醒目的数字是：RAPTOR 配上 GPT-4，在 QuALITY 的测试集上达到 82.6% 的准确率，此前最好的成绩是 62.3%。测试集是数据集里留到最后用来报告成绩的另一批题目。此前最好的系统用的是另一个小得多的阅读模型，所以这 20 个百分点里既有检索办法的贡献，也有换成 GPT-4 的贡献。

GraphRAG：先建知识图谱，再按社区总结

RAPTOR 的树针对的是答案分散在一篇文档各处的问题。有些问题问的范围更大，是整个文档库，比如「这批资料里主要的主题有哪些」。这类问题没有哪一块、哪一篇文档能回答，普通的向量检索只能取回零散的几块。微软研究院的 Edge 等人 2024 年提出的 GraphRAG 针对的就是这类问题。

{{fig 34 | 左：GraphRAG 的流程。紫色的框是建索引时做的事：左边一列从上到下，再接到右边一列最下面的两个框。绿色的框是查询时做的事，在右边一列的上面两个。右：检测出来的图社区，每种颜色是一个社区。图片来源：Edge 等，2024。}}

建索引时

建索引分五步，从配图里的原始文档（Source Documents）一步步做到社区摘要（Community Summaries），也就是配图里紫色的那几个框。

  1. 切块。把文档切成块。论文用的是每块 600 个 token，相邻的块重叠 100 个 token。
  2. 抽实体和关系。让语言模型从每一块里找出重要的实体（人、组织、地点等）和它们之间的关系。
  3. 连成图。实体是节点，关系是边，合起来是一张知识图谱（knowledge graph）。
  4. 检测社区。用图上的社区检测算法（论文用的是 Leiden 算法），把连接紧密的实体分成一个个社区。这一步是分层做的：大社区里面再分小社区。
  5. 写社区摘要。让语言模型给每个社区写一段摘要。

查询时

查询时不去搜原文的块。社区是分层的，先选定用哪一层的社区摘要，然后分两步。

  1. 每个社区各自回答。把问题和社区摘要一起交给语言模型，让它根据这部分摘要写一个局部的回答，同时给这个回答打一个 0 到 100 的分数，表示它对回答问题有多大帮助。0 分的回答直接丢掉。
  2. 合成一个总的回答。把局部的回答按分数从高到低排好，依次放进一段输入里，放满为止，再让语言模型根据它们写出最后的回答。

所以查询时不用事先挑选看哪些社区：选定的那一层的社区摘要全部问一遍，再用分数筛选。分数高的社区对最后的回答贡献大，不相关的社区在第一步就被去掉了。

效果和花费

论文在两个各有一百多万 token 的资料库上做了评测。一个是播客的文字稿，约 100 万 token。一个是新闻报道，约 170 万 token。每个资料库有 125 个需要通读全部资料才能回答的问题。

参加比较的有六种做法。其中五种是总结全部资料的做法：前四种是 GraphRAG 分别用四个不同层级的社区摘要，第五种不建图，直接对全部原文分段总结。第六种是普通向量检索。

评判由语言模型来做：把两种做法对同一个问题的回答放在一起，判断哪一个更好。每个问题上胜出记 100 分，落败记 0 分，评判认为两个回答相近时各记 50 分，再取平均，得到的数叫胜率。所以胜率里含有平局的贡献。

下表是五种总结全部资料的做法各自和普通向量检索两两比较的胜率。每一格的范围是这五种做法里最低和最高的数。

论文还说，和不建图、直接对原文分段总结相比，社区摘要在全面和多样两项上有小而稳定的优势，最高一层的摘要除外。

表的最后一行值得留意。在这些总结性的问题上，这五种做法的回答更全面、涉及的方面更多，普通向量检索的回答更直接。

GraphRAG 是为总结性的问题设计的，论文的评测也只用了这一类问题。问具体事实的问题上效果如何，论文没有测。论文对普通向量检索的评价是，答案集中在少数几条记录里的问题它能做好。

花费主要在建索引：要让语言模型读过每一块来抽实体，还要给每个社区写摘要。论文里播客那个约 100 万 token 的资料库，建索引用了 281 分钟。

查询时的花费取决于用哪一层的摘要。用最高层的社区摘要回答一个问题，需要读的 token 比直接对全部原文做分段总结少 97% 以上。

图上的检索不只这一种

检索增强的思路可以用到文字以外的数据上。分子结构、蛋白质、社交网络、论文之间的引用关系，只要能表示成图，都可以作为检索的对象。这是 Han 等人 2025 年的一篇综述要说明的事。

GraphRAG 这个名字也有宽窄两个意思。窄的意思是上一节那一套具体的方法：从文字里抽出图，再按社区总结。宽的意思是所有在图结构的数据上做检索增强生成的方法。这篇综述的标题是《Retrieval-Augmented Generation with Graphs (GraphRAG)》，用的是宽的意思。

{{fig 35 | 左边是文字和图像数据，右边是图结构的数据，包括知识图谱、分子、蛋白质、社交网络等。中间是综述归纳的五个部件。图片来源：Han 等，2025。}}

这篇综述把这类系统拆成五个部件。

  • 图数据源。按图的结构组织起来的信息。
  • 查询处理器。先对查询做预处理。
  • 检索器。根据查询从图数据源里取回内容。
  • 组织器。整理和提炼取回的内容。
  • 生成器。根据这些内容写出回答。

综述还把这类系统按应用分成十个领域，其中有知识图谱、文档图、科学图、社交图等。

什么时候值得用复杂的结构

从序列到树再到图，设计的目的是回答层次越来越高的问题：从「某个事实是什么」到「这篇文档讲了什么」再到「这批资料的主题有哪些」。答案就在某一块里的问题，简单的切块加检索通常已经够用。

代价是建索引的成本。树和图都要在建索引时大量调用语言模型，文档一更新，受影响的摘要也要重做。所以很多商业产品和大规模的问答系统仍然用上一部分那些简单的办法：它们快，而且已经能应付实际遇到的大部分问题。先弄清要回答的是哪一类问题，再决定要不要用树或图。

向量搜索：从逐个比较到近似搜索

按向量检索，最后都要做同一件事：给一个查询向量，从 N 个向量里找出最相近的 k 个。原文的块和 RAPTOR 的摘要都是这样检索的。前面 GraphRAG 回答总结性的问题时把社区摘要全部问一遍，是另一种流程。

最直接的办法是把查询向量和每一个向量都比一遍，叫精确搜索。每个向量有 d 维，比一次要做 d 次乘法，所以一次查询的计算量和 N 乘 d 成正比。N 通常是几百万到几千万。粗略估算一下：第四部分要讲的 DPR，索引里有约 2,100 万个 768 维的向量，逐个比较一次查询要做约 160 亿次乘法。这些乘法每来一个查询都要重做一遍，向量越多越慢。

所以实际用的是近似最近邻搜索（Approximate Nearest Neighbor，ANN）：不保证找到的一定是真正最近的那几个，也就是牺牲一点召回，换来快得多的速度。常见的办法有三种。

下面两节只展开 HNSW，它是近似搜索里用得很广的一种办法。

HNSW：分层的图上找最近的点

HNSW 的想法是把向量分到不同的层里。最底下的第 0 层有全部的向量。越往上，层里的向量越少，是下一层的一个稀疏的抽样。每一层里，相近的向量之间有边相连。

{{fig 37 | 三层的例子。红点是搜索的起点，绿点是查询要找的位置，红色箭头是搜索走过的路线。右边的竖箭头表示越往下层，每一步跨的距离越短。图片来源：Malkov 和 Yashunin。}}

分层是为了先粗后细。上面的层点少、边长，一步能跨很远，用来快速接近目标所在的区域。下面的层点多、边短，用来在这个区域里细找。

搜索从最上面一层开始，分三步。

  1. 在第 0 层以上的每一层，只保留一个当前离查询最近的点。看这个点的邻居里有没有离查询更近的，有就走过去，再看新位置的邻居。这是贪心的走法：每一步都走向眼下最近的点。
  2. 走到一个点，它的邻居都不比它更近，就说明在这一层已经走不动了。这时下到下一层，从同一个点接着走。
  3. 到了第 0 层，搜索的办法变了：同时保留一批离查询最近的候选，个数由参数 ef 决定。逐个检查这些候选的邻居，遇到更近的点就把它换进来，直到这批候选不再变化。最后从这批候选里取出最近的 k 个作为结果。

HNSW 的论文把它看作跳表（一种带多层「快速通道」的有序链表）的推广，把链表换成了图。

i
「搜索一次大约走 log N 步」是有条件的。HNSW 的论文在摘要里说，它的搜索复杂度可以按对数的规律增长，通俗地说就是搜索一次大约走 log N 步，N 是向量的总数。论文正文里的推导用了一个理想的假设，论文自己也说明实际的 HNSW 不满足这个假设，这个规律是否适用于高维的数据，还需要理论分析来确认。所以对数复杂度是理想条件下的推导加上实验观察到的结果，没有对实际算法的严格证明。实际使用中它确实很快。出处：Malkov 和 Yashunin，第 4.2.1 节。

HNSW 的图是怎么建出来的

图是一个向量一个向量插进去建成的。

{{fig 38 | 右边的图说明连边时的一个细节。绿点是新插入的向量，它落在簇 1 的边上。它最近的邻居全在簇 1 里。HNSW 挑邻居的规则另外给它连了一条通往簇 2 里 e2 的边。图片来源：Malkov 和 Yashunin。}}
  1. 每次插入一个向量。
  2. 随机决定它最高出现在第几层。层数越高，被选中的概率越小，而且是按指数规律下降：每高一层，概率缩小同样的倍数。所以大多数向量只在第 0 层，只有很少的向量能到最上面。这个向量会出现在从它的最高层到第 0 层的每一层里。
  3. 在它出现的每一层里给它连边。先用上一节的搜索办法找到它在这一层的近邻，再连接其中的 M 个。M 是事先定好的每个点的连边数。

第三步有一个关键的细节：不能只挑最近的 M 个。配图画的就是这种情况：数据分成两个簇，新来的点最近的邻居全在自己这个簇里。如果只连最近的，两个簇之间就没有边，贪心的搜索一旦进了一个簇，就再也到不了另一个簇。

HNSW 用一条启发式的规则来挑邻居。启发式指凭经验定下、不保证最优的做法。规则是从近到远检查候选：如果一个候选离某个已经选中的邻居比离新点还近，就跳过它，否则连上。这样一来，几个候选如果彼此挨得比它们离新点还近，就只有最近的那个会被连上，名额留给了别的方向上的候选。连出去的边因此朝向不同的方向，其中就包括通往别的簇的边。

+
实际使用时要调的三个参数。M 是每个点连几条边，越大图越密，召回越高，占的内存也越多。efConstruction 是建图时为每个新点保留多少个候选邻居，越大建得越慢、图的质量越好。ef 是查询时在第 0 层保留多少个候选，越大召回越高、查得越慢。出处：Malkov 和 Yashunin。
+
一组实际用过的参数。DPR 的论文给 2,100 万个向量建 HNSW 索引时，M 取 512，efConstruction 取 200，ef 取 128。在一台服务器上建这个索引用了 8.5 小时。论文没有用这三个参数名，对应关系见资料说明。出处：Karpukhin 等，2020，第 5.4 节。

这一部分的小结

  • 块可以按序列、树、图三种方式组织，分别适合答案在一处、分散在一篇文档里、分散在整个文档库里的问题。
  • RAPTOR 和 GraphRAG 都在建索引时用语言模型写摘要，把「读很多块再概括」这件事提前做了。代价是建索引更贵。
  • 向量搜索在大规模时都是近似的。HNSW 用分层的图，从稀疏的一层逐层走到最密的一层。

到这里，索引里存什么、怎么组织都讲过了。下一部分讲查询来了之后，检索器怎么从索引里把内容找出来。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • RAPTOR 的摘要占所概括内容的 28% 是怎么来的。论文附录的原话是，摘要的长度和它的全部子节点长度之和的比例，在所有数据集上平均是 0.28。同一处还给了三个平均数：摘要约 131 个 token，每个子节点约 86 个 token，每个父节点有 6.7 个子节点。拿这三个平均数相除，131 除以 6.7 乘 86 的积，得到约 23%，和 28% 不相等。论文没有说明 28% 具体是怎么平均的。出处：Sarthi 等，2024，附录。
  • DPR 建 HNSW 索引的三个数对应哪三个参数。DPR 论文的脚注写的是向量搜索库 FAISS 的设置：每个点存 512 个邻居，建图时的搜索深度是 200，查询时的搜索深度是 128。DPR 公开的代码把这三个数依次传给 FAISS 的 HNSW 索引的 M、efConstruction 和 efSearch，efSearch 就是这一页说的 ef。出处：Karpukhin 等，2020，第 5.4 节的脚注；DPR 的代码；FAISS 的文档。
