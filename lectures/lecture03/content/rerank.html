先看结论

  • 双编码器（bi-encoder）把查询和段落分开编码，各得到一个向量再比较。它快，因为段落的向量可以提前算好。它的短处是整段文字只用一个向量表示，细节丢了。
  • 交叉编码器（cross-encoder）把查询和段落拼在一起送进同一个模型，两边的每个词都能互相参照。它通常判断得更准，但每一对都要完整跑一遍模型，什么都没法提前算。
  • 所以交叉编码器只用在重排（reranking）上：先用快的检索器从全部文档里取出一批候选，再用它给这批候选重新排序。
  • ColBERT 取了一个中间位置：查询和段落仍然分开编码，但每个 token 保留一个向量，打分的时候才逐个 token 比较。在 MS MARCO 数据集上，它重排 1,000 个段落用 61 毫秒，BERT-base 交叉编码器用 10,700 毫秒，两者排序的质量接近。
  • 选检索器时看四件事：哪些东西能离线算好，查询要多久，擅长什么，会在什么地方出问题。

双编码器和交叉编码器

上一部分的 DPR 是双编码器的代表。和它相对的是交叉编码器。两者的差别在于查询和段落在什么时候相遇。

{{fig 50 | 左：双编码器。两个编码器分别处理两段输入，各自汇总成一个向量，最后算一次内积得到分数。右：交叉编码器。两段输入拼成一串，送进同一个编码器，输出一个分数。图里的 Context 和 Candidate 在检索里对应查询和段落。图片来源：Humeau 等，2020。}}

对比这两种结构的一篇论文（Humeau 等，2020）在摘要里把取舍说得很清楚：交叉编码器通常效果更好，但慢到没法实际用来检索；双编码器因为两边的表示是分开的，可以把候选的编码缓存起来反复使用。

交叉编码器有多慢，可以粗略估算一下。BERT 是 2018 年的一个预训练语言模型，BERT-base 是它较小的版本。下面会看到，BERT-base 交叉编码器给 1,000 个段落打分要 10.7 秒，平均每个段落约 10.7 毫秒。MS MARCO 数据集有 880 万个段落，如果对每个查询都把全部段落打一遍分，要 880 万乘以 10.7 毫秒，约 26 个小时。所以它扫不了整个文档库，只能处理别的检索器筛过的一小批。

查询和段落怎么相遇：四种结构

把视野放宽一些，神经网络的排序模型按「查询和段落在哪里发生比较」可以分成四种。

{{fig 51 | 上面是迟交互的定义和打分公式。下面四张小图是四种结构，绿色是查询这一侧，蓝色是段落这一侧。红框里的 (d) 是 ColBERT 的做法。图片来源：Khattab 和 Zaharia，2020。}}

比较这四种结构时，有一点要一直记着：文档的数量非常大。凡是文档这一侧的计算，能离线做完就尽量离线做完。(c) 做不到，因为它必须把查询和文档放进同一次计算里。(a) 和 (d) 可以把图上蓝色的那一部分提前算好，查询来了只算绿色的部分，再做最后那一步比较。这是它们之间最关键的差别。

ColBERT：每个 token 一个向量，最后才比较

ColBERT 是 Khattab 和 Zaharia 2020 年在 SIGIR 上发表的模型。它的做法叫迟交互（late interaction）：查询和段落各自独立地编码，每个 token 保留一个向量，两边只在打分的那一刻发生交互。

{{fig 52 | ColBERT 的结构。左下是查询编码器，右下是文档编码器，灰色的底表示文档这一侧可以离线做完。中间每个 MaxSim 对应查询的一个 token。最上面把所有 MaxSim 的结果加起来，得到分数。图片来源：Khattab 和 Zaharia，2020。}}

打分的办法叫 MaxSim，分两步。

  1. 对查询里的每一个 token，在段落的所有 token 里找出和它最相近的那一个，记下这个最大的相似度。
  2. 把查询里所有 token 的最大相似度加起来，就是这个段落的分数。
S(q, d) = 对查询的每个 token i 求和： max over 段落的 token j ( qi · dj )

可以这样理解这个分数：查询里的每个词都去段落里找一个最能对应它的词，每个词找到的对应有多好，加起来就是整体的匹配程度。段落里只要有一处很好地对上了查询里的某个词，这个词的得分就高，不会因为段落里其他不相干的内容被拉低。

这一步本身没有任何要训练的参数，只是取最大值和求和，所以很便宜。贵的部分是用 BERT 算出每个 token 的向量，而文档这一侧的这部分计算可以离线做完。

+
几个实现上的细节。
  • 每个 token 的向量是 128 维，比 BERT 原本的 768 维小，为的是省空间。向量都归一化到长度为 1，所以内积就是余弦相似度。
  • 每个查询固定用 32 个向量。查询不够长时，用 BERT 的 [MASK] 占位符补到 32 个。论文认为这些补出来的位置让模型有机会学着给查询补充新的词，或者调整已有的词的权重。
  • 文档这一侧会去掉标点符号对应的向量，以减少每篇文档的向量个数。
  • 从整个文档库里检索时分两步：先把所有文档的所有 token 向量放进一个近似搜索的索引里，查询的 32 个向量各自去搜一批最相近的 token 向量，找出它们属于哪些文档，得到候选；再对这些候选用完整的 MaxSim 打分排序。
出处：Khattab 和 Zaharia，2020，第 3 节。近似搜索的索引见第三部分。

ColBERT 的成绩

评测用的是 MS MARCO 段落排序数据集，880 万个段落，查询来自必应搜索的真实提问。指标是 MRR@10：第一个相关段落排在第几位，取名次的倒数，前 10 个里没有就记 0，再对所有查询取平均。数值越高，说明第一个有用的结果排得越靠前。

{{fig 53 | 上面的表是从全部 880 万个段落里检索的结果，下面的表是给 BM25 找出的前 1,000 个段落重排的结果。FLOPs 是浮点运算次数，括号里是相对 ColBERT 的倍数。图片来源：Khattab 和 Zaharia，2020。}}

重排：和交叉编码器比

ColBERT 的 MRR@10 和 BERT-base 交叉编码器几乎一样（34.9 和 34.7），时间是它的约 170 分之一，每个查询的浮点运算次数是它的 13,900 分之一。和更大的 BERT-large 比，ColBERT 低 1.6 分。和 (b) 类的模型比，ColBERT 慢一些，但排序质量高出一大截。

直接从全部段落里检索

这张表里有一个和召回上限有关的细节。ColBERT 只做重排时，Recall@1000 是 81.4%，和它所依赖的那份官方 BM25 候选名单（表里第一行）完全一样：重排只能调整候选的先后，候选里没有的段落，它补不回来。ColBERT 自己直接检索时，Recall@1000 升到 96.8%，MRR@10 也从 34.8 升到 36.0。

代价是索引的体积。DPR 每个段落存一个向量，ColBERT 每个 token 存一个向量。论文里直接检索用的那份 MS MARCO 索引占 154 GiB。只用于重排的索引可以做得更小：把向量从 128 维降到 24 维、每维用 2 个字节存，是 27 GiB，MRR@10 比 128 维时低 1 分。建索引用 4 块 GPU 约 3 小时。

四种检索器放在一起比

实际的应用场景差别很大：社交媒体上的帖子和满是专有名词的财务文件，适合的检索器不一样。选的时候可以问四个问题：哪些东西能离线算好，查询要多久，它擅长什么，它会在什么地方出问题。

i
DPR 的速度该怎么说。常见的概括是 DPR 的查询延迟在几十毫秒。DPR 论文里没有找到单次查询延迟的数。它报告的是：用 HNSW 索引（一种近似搜索的索引，见第三部分），在一台服务器上每秒处理 995 个问题，每个问题返回 100 个段落；同一台机器上 BM25 每个 CPU 线程每秒处理 23.7 个问题。原文没有写明 995 这个数是否包含用 BERT 编码问题的时间。出处：Karpukhin 等，2020，第 5.4 节。

这张表可以沿着一条线来读：从上到下，查询和段落之间的比较越来越细，查询到来之后才能做的计算越来越多，速度越来越慢。前三种都能把文档这一侧提前算好，其中 ColBERT 要存的东西最多；交叉编码器什么都不能提前算。没有哪一种在所有方面都最好。

实际的做法：先检索，再重排

既然快的不够准、准的不够快，实际的系统把它们串起来用，每一段处理的数量逐级减少。

  1. 检索。用 BM25、向量检索或两者的混合，从全部文档里取出一批候选，通常是几十到上千个。这一步要的是不漏掉。
  2. 重排。用交叉编码器这类更准的模型给候选逐个打分，重新排序。这一步要的是把最相关的排到最前面。
  3. 截取。只把排在最前面的少数几个交给语言模型。

第二部分里 Anthropic 的测试给了这种做法的一组数字。他们先检索出前 150 块，用一个重排模型打分，再取前 20 块交给语言模型。

两行里重排都把失败率降低了三成左右。同一篇文章也提醒了代价：重排是查询时多出来的一步，会增加延迟和费用，候选取得越多，增加得越多。取多少个候选来重排，要在效果和速度之间试出来。

重排能做的事有一个边界，上一节的表已经显示过：它只能改变候选的顺序。相关的内容如果没有进入候选，重排帮不上忙。所以第一段检索的召回，决定了整条流水线的上限。

这一部分的小结

  • 查询和段落在模型里越早相遇，通常判断越准，查询到来之后要做的计算也越多。
  • 交叉编码器通常最准，只能用来重排。ColBERT 用迟交互保留了 token 一级的比较，又让文档这一侧可以离线算好，代价是索引更大。
  • 实际的系统是分段的：快的方法负责不漏，准的方法负责排好。
