先看结论

  • 多个 agent 换来的是并行、专门化和更集中的上下文，付出的是协调的成本：派任务、发消息、合并结果都要花时间和 token。
  • 值不值，主要看工作能不能拆开。同一批多 agent 架构，在能拆开的金融分析任务上最多比单 agent 高 81%，在一步接一步的规划任务上最多低 70%。
  • 「能拆开」有两个条件：各块不改同一份东西，做的过程中也不需要对方的中间结果。只满足后一个还不够：两个可以各自实现、但要改同一批文件的功能，拆给两个 agent 比交给一个 agent 差。
  • 单 agent 已经做得不错时，再加 agent 往往得不偿失。论文观察到的界线大约是单 agent 正确率 45%，这是一个趋势，有例外。
  • 所以先做一个强的单 agent 基线。每加一个 agent 都要有明确的目的，并且测量它的贡献是否大于协调的成本。

多 agent 系统是什么

讲义的定义很短：一组 agent，朝着同一个任务一起工作。它在 AI 系统里处在最复杂的一端。

设计一个多 agent 系统，讲义说必须考虑三件事，它们是后面三个部分的主题。

换来什么，付出什么

讲义第 15 页把两种系统放在一起对比。有一行值得注意：单 agent 也能并行，它可以同时发出几个互不依赖的工具调用。所以「需要并行」本身还不足以说明要用多个 agent。

+
讲义之外：开销有多大。Anthropic 在介绍自己的多 agent 研究系统时给过数字：agent 用的 token 大约是普通对话的 4 倍，多 agent 系统大约是 15 倍。文章还说，多 agent 系统有效，主要是因为它帮你花掉了足够多的 token 去解决问题。所以任务的价值要够高，才付得起这笔开销。出处：How we built our multi-agent research system。

证据一：同样的模型，多 agent 有时更差

这一页的标题是「Sometimes Single Agent Systems Outperform」。图来自 Kim 等人 2026 年的论文，他们把工具、提示词和算力都固定下来，只换架构，一共比较了 260 种配置。

{{slide 13 | 图片来源：Kim 等，2026。}}
  • 三格分别是 OpenAI、Google 和 Anthropic 的模型。横轴是模型的能力指数，越往右模型越强；纵轴是几个评测的平均成绩。
  • 每格有五条线：单 agent（虚线）和四种多 agent 架构。四种架构在第二部分讲。
  • 模型越强，五条线都往上走。换更强的模型，对每种做法都有帮助。
  • 每格标了一个百分比。论文的图注说，它是同一个模型上成绩最好的多 agent 架构相对单 agent 的变化：GPT-5 是 +12.3%，Gemini 2.5 Pro 是 −4.6%，Claude Sonnet 4.5 是 −7.2%。

也就是说，在三家最强的模型里，有两家是单 agent 的平均成绩高于所有多 agent 架构。

证据二：差别主要来自任务

平均成绩掩盖了更大的差别。同一篇论文按评测分开看，每个箱线图上方的百分比是四种多 agent 架构相对单 agent 的变化。

{{slide 23 | 讲义把这张图放在第二部分，标题是「用哪种架构取决于你的任务」。图片来源：Kim 等，2026。}}
+
讲义之外：论文怎样解释这个差别。讲义只放了图，原因在论文正文里。
  • 能不能拆开。金融分析的任务可以自然地拆成几条并行的分析，例如一个 agent 查监管和新闻，一个查公司报表，一个评估对运营的影响，最后由一个负责统筹的 agent（orchestrator）合起来。规划任务本来就是一步接一步：论文举的例子是在 Minecraft 里合成一面墙，单 agent 三步做完（查配方、放材料、合成）；多 agent 把它拆给三个 agent，其中查配方和查库存两步是多余的，token 花在了协调上，留给推理的反而少了。
  • 单 agent 已经多好。论文的回归分析发现，单 agent 正确率超过 45% 的任务，再加 agent 的收益倾向于为负，因为能改进的空间小，协调的成本却照付。论文的最新版本里还有编程评测 SWE-bench Verified（讲义的图里没有），就是这种情况：四种多 agent 架构都低于单 agent，从 −2.1% 到 −14.9%。这是统计上的趋势，有例外：讲义图里 Workbench 的单 agent 成绩在 60% 以上，去中心方式仍然高了 6%。
  • 工具多不多。工具很多的任务，每个 agent 分到的 token 预算变少，不够用来组织复杂的工具调用。
论文自己的总结是：决定协作成败的是架构和任务是否对得上，agent 的数量本身说明不了什么。出处：Kim 等，2026，摘要和第 1、4 节。

证据三：要改同一份代码的工作，拆开更差

讲义在第五部分用 CooperBench 说明协调的代价，它同样是这里的证据。这个评测给两个 agent 各分配一个功能。论文对任务的描述是：两个功能可以各自实现，但都要改同一个代码库，不协调就可能冲突。对照组是把两个功能都交给一个 agent。

成功的标准是：两份改动能合并到一起，而且两个功能各自的测试都通过。

也就是说，同样的两个功能，分给两个 agent 去做，成功率只有交给一个 agent 时的一半多一点。论文测的五个模型，都是分开做更差。

这条证据给前面的结论加了一个限制。按讲义的标准，这些任务看起来适合多 agent：每个 agent 负责一块独立的产出，最后再合并。结果却是五个模型都更差。差别在于，两块产出要落在同一批文件上。

+
讲义之外：为什么分头做会对不上。Cognition（做 Devin 的公司）的文章 Don’t Build Multi-Agents 给了一个直观的解释，归成两条原则。
  • 要共享上下文。例子是让两个子 agent 分头做一个 Flappy Bird：一个做背景，一个做小鸟。做背景的那个把任务理解成了超级马里奥的风格，做小鸟的那个做出来的东西既不像游戏素材，动作也不对。最后负责合并的 agent 拿到的是两份互相对不上的东西。
  • 每个动作都带着没说出口的决定。就算两个子 agent 都看得到原始任务，它们看不到对方正在做什么，各自做的决定仍然可能互相冲突。
Anthropic 的文章也说了同样的边界：需要所有 agent 共享同一份上下文、或者 agent 之间依赖很多的领域，现在不适合用多 agent；大多数编程任务里真正能并行的部分，比研究类任务少。出处：Don’t Build Multi-Agents、How we built our multi-agent research system。

三处证据合起来：「能拆开」指什么

把上面的例子放在一起，「能拆开」可以拆成两个能检查的条件。这两个条件是我从讲义第 14 页的判断标准里整理出来的，讲义没有这样明说。

  1. 各块不改同一份东西。不写同一批文件，不改同一份共享的状态。
  2. 做的过程中不需要对方的中间结果。后一步不依赖前一步，各块可以同时推进。

后两行说明，第一个条件不满足时还有两条路：把工作重新切一遍，让各块不再碰同一份东西；或者用明确的办法管住共享的部分，例如认领和分开的工作区。后一条路在第四部分讲。

所以：什么时候用哪一种

讲义第 14 页的判断标准，和上面两个条件对得上。左栏前两条说的是两个条件不满足的情况：步骤高度依赖彼此，工作和一份共享的状态耦合得很紧。左栏第三条对应证据二里 45% 的趋势。右栏说的是两个条件都满足的情况，另外多一条要求：要有一个测量出来的瓶颈。

i
讲义的建议：从一个强的单 agent 基线开始。加 agent 要有明确的目的，并且测量它带来的贡献是否大于协调的成本。
+
讲义之外：Anthropic 的 Building effective agents 说的是同一个意思，范围更广：先找最简单的办法，只在需要时才增加复杂度；只有当复杂度确实改善了结果时，才值得加。出处：Building effective agents。

决定用多个 agent 之后，第一个设计问题是编排：谁分派任务，谁做决定。
