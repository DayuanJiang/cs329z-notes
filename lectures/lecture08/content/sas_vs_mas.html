先看结论

  • 多个 agent 换来的是并行、专门化和更集中的上下文。各个 agent 拿到不同的任务或上下文时，还能换来更广的探索面。付出的有协调的成本，也就是派任务、发消息、合并结果都要花时间和 token，另外还有信息丢失、动作冲突、错误传播和工程复杂度四个坏处。这里的专门化指各个 agent 按自己的职责用不同的指令、模型和工具。指令是提示词里告诉 agent 该做什么的那部分，工具是 agent 可以调用的外部功能，例如搜索网页或运行代码。上下文指模型这一次能读到的全部内容，token 是模型处理文字的最小单位。
  • 工作能拆开时，用多个 agent 可能划算，拆不开时往往更差。依据是 Kim 等人 2026 年的论文，它比较了单 agent 和四种多 agent 架构。架构指 agent 之间指挥和交流关系的一种安排，第二部分把这四种架构叫作四种编排方式。在能拆开的金融分析任务上，四种里成绩最好的一种比单 agent 高 81%。在一步接一步的规划任务上，成绩最差的一种比单 agent 低 70%。两个数都是相对单 agent 成绩的变化比例。
  • 「能拆开」有两个条件：各块不改同一份东西，做的过程中也不需要对方的中间结果。只满足后一个还不够。有一个评测里的两个功能可以各自实现，谁也不用等对方做完，但它们要改的代码有重叠或互相依赖，拆给两个 agent 比交给一个 agent 差。
  • 单 agent 已经做得不错时，再加 agent 往往得不偿失。Kim 等人的论文观察到的界线大约是单 agent 正确率 45%，这是一个趋势，有例外。
  • 所以先只用一个 agent 把任务尽量做好，拿它当比较的基准，这叫单 agent 基线。每加一个 agent 都要有明确的目的，并且测量它的贡献是否大于协调的成本。这里的「协调的成本」泛指第一条列的全部五个坏处。

多 agent 系统是什么

多 agent 系统的定义很短：一组 agent，朝着同一个任务一起工作。它在 AI 系统里处在最复杂的一端。

单 agent 加并行，和多 agent 的分界在哪里

工具调用指 agent 请求一个工具替它做一件事。单 agent 也可以同时发出几个工具调用，或者同时发出几次模型调用，所以只看有没有并行，分不出两者。一个实用的分法是看有几处在各自做决定：

  • 单 agent。只有一处在做决定，上下文也只有一份。并行的调用都从这一处发出，结果都回到这一处，由它决定下一步。
  • 多 agent。有几个 agent 各自决定自己的下一步，每个 agent 有自己的指令，通常也有自己的上下文。它们可以同时运行，也可以轮流发言或依次交接，第三部分有这样的例子。

这条界线是模糊的，两种系统之间有不少中间情况。例如一个 agent 把一部分工作派出去，交给另外几次模型调用来做：派出去的是很具体的小任务，整个流程仍然由它掌握，就接近单 agent。派出去的是一个大目标，怎么做由接手的一方自己决定，就接近多 agent。

Kim 等人 2026 年的论文也按有几处在做决定来分：单 agent 系统里只有一处在做推理，读取工具返回的结果等外界信息、定计划、采取行动都由同一个模型在一个循环里完成。这个循环指模型看到上一步的结果，决定下一步做什么并执行，再看结果，这样一步接一步地重复。带工具调用和自我反思的 agent 仍然算单 agent。自我反思指 agent 回头检查并修改自己前面的输出。出处：Kim 等，2026，第 2、3 节。

设计一个多 agent 系统，必须考虑三件事，它们是后面三个部分的主题。

换来什么，付出什么

多个 agent 一起工作，有四个好处，也有五个坏处。先把它们列出来，再举几个例子。

下面举五个例子。前三个说的是好处：第一个对应并行执行和探索面更广，第二个对应上下文更集中，第三个接着第二个说，各个负责审查的 agent 看不同的材料，也属于上下文更集中。后两个说的是坏处：第四个对应动作冲突，第五个对应错误传播。

  • 并行和探索。一道数学难题有很多条可能的证明路线，可以让不同的 agent 各试一条，同时推进。Navier-Stokes 问题是关于流体运动方程的一道数学难题，七道千禧年大奖难题之一。OpenAI 在 2026 年 9 月公布了一份由 agent 生成的解答，按它的介绍，不同的 agent 小组拿到的是问题的不同版本，并且被鼓励尝试不同的思路。出处：On the Navier-Stokes Millennium Prize Problem。
  • 上下文更集中。把写代码和审查代码交给两个 agent，就是一个例子。负责审查的 agent 的上下文里没有写这段代码时的推理过程，这样很可能更容易看出问题。
  • 几种审查叠加。接着上一条说：负责审查的 agent 可以有好几个，各看不同的材料。Cursor 是一家做 AI 编程工具的公司，它介绍过自己的 agent swarm，也就是一大群一起工作的 agent，里面被分派去干活的 agent 叫 worker。文章写道，它试过几种审查方式：让负责审查的 agent 看 worker 的完整运行记录（它每一步做了什么的记录），只看产出，或者只看代码库，也试过换别的模型来审查。文章的说法是，没有哪一种审查能发现所有问题，几种互不相关的审查可以叠加。文章推测，这套叠加的审查是产出质量能保持住的主要原因之一，没有给出对照数据。这一页把这种做法对应到最后一节判断标准里的「独立审查」，Cursor 的文章没有用这个词。出处：Agent swarms and the new model economics。
  • 动作冲突。一个 agent 说「我只改这几个文件」，后来又改了别的文件，这就是没有照自己答应过的去做。合并时就多出冲突要解决。
  • 错误传播。一个 agent 上网查资料，写成报告交给下一个 agent。下一个 agent 通常会直接采信这份报告，报告里的错误就进了后面的工作，查起来也更难。

下面的表把两种系统放在一起对比。有一行值得注意：单 agent 也能并行，它可以同时发出几个互不依赖的工具调用。所以「需要并行」本身还不足以说明要用多个 agent。

最后一行的开销有一个直接的来源：每启动一个新的 agent，系统提示词都要重新读进它的上下文，它还要自己重新查看文件、弄清状况，这些 token 都要再花一遍。所以多 agent 系统通常比单 agent 贵，第二部分的成本图上有实测的数字。

+
开销有多大。Anthropic 在介绍自己的多 agent 研究系统时给过数字。这个系统是 Claude 的 Research 功能，由一个 agent 按用户的问题定出调研的计划，再派出几个 agent 同时搜索资料。文章给的数字是：单个 agent 用的 token 大约是聊天的 4 倍，多 agent 系统用的 token 大约是聊天的 15 倍。这里的聊天指用户直接和模型对话的用法，文章没有写明一次聊天按多长算。文章还说，多 agent 系统有效，主要是因为它在一个问题上用掉的 token 足够多。所以任务的价值要够高，才付得起这笔开销。出处：How we built our multi-agent research system。

后面几节会用到四种多 agent 架构的名字，第二部分把它们叫作四种编排方式。它们的差别在两处。第一处是有没有 orchestrator，也就是一个统管全局、给其他 agent 分派任务的 agent。第二处是其余的 agent 之间能不能直接交流。直接交流指信息不经过 orchestrator 就到了别的 agent 那里，互发消息和读写同一份共享文件都算。两样都没有的叫独立方式，只有 orchestrator 的叫集中方式，只有直接交流的叫去中心方式，两样都有的叫混合方式。第二部分展开讲。

「多 agent 更贵」有一种例外。第二部分的成本图把 OpenAI、Google 和 Anthropic 三家的模型分开画，按图上实测的美元成本算，在 Google 和 Anthropic 两家的模型上，独立方式比单 agent 便宜。原因从图上看不出来。

证据一：同样的模型，多 agent 有时更差

单 agent 系统有时成绩更好。依据是 Kim 等人 2026 年的论文，他们把工具、提示词和 token 预算都固定下来，只换架构。论文的最新版本一共比较了 260 种配置，覆盖六个评测，一种配置是一个模型、一种架构和一个评测的组合。

这里固定的是预算。论文写明有两样调成了一样多：一样是用于推理的 token 预算，一样是所有 agent 加起来最多可以迭代的总次数，迭代一次就是一个 agent 推理一次。各种架构实测的开销并不相同：完成一个任务实际用的轮数差好几倍，实测的美元成本也差好几倍。一轮大致是一个 agent 推理一次、调用一次工具并拿到工具返回的结果。这些数字在第二部分。预算相同而实测的开销不同，两者怎样同时成立，论文没有说明，核对的经过见第二部分的资料说明。

论文怎样解释这个差别

图上只有结果，原因在论文正文里。论文给了三条解释：任务能不能拆开，单 agent 已经做到多好，工具多不多。

第一条：能不能拆开。金融分析的任务可以自然地拆成几条并行的分析。论文举的例子是一个 agent 查监管和新闻，一个查公司报表，一个评估公司运营受到的影响，最后由统管全局的 orchestrator 合起来。

规划任务本来就是一步接一步。论文举的例子是在 Minecraft 里合成一面墙。在这个游戏里，合成指按配方把材料摆进合成格，做出一件新物品。配方规定要用哪些材料、怎样摆放，库存是手头已有的材料。单 agent 三步做完：查配方，把材料放进合成格，合成。集中方式把这件事分给三个 agent：第一个专门查配方，第二个专门查库存，第三个执行合成。论文认为前两个 agent 的工作是多余的，因为配方一查就有，库存本来所有 agent 都看得到，只有第三个 agent 做的那一步是必要的。token 花在了协调上，留给推理的反而少了。

第二条：单 agent 已经多好。论文做了回归分析，这是一种估计几个因素各自对结果影响多大的统计方法。分析发现，单 agent 正确率超过 45% 的任务，再加 agent 的收益倾向于为负，因为能改进的空间小，协调的成本却一样要花。

论文的最新版本里还有两个评测，上面的图里没有。一个符合这个趋势。另一个的单 agent 成绩在 45% 以下，不在这个趋势说的范围里。下面的百分比和上面的图一样，都是相对单 agent 成绩的变化比例。

  • SWE-bench Verified 符合这个趋势。它是编程评测，论文说多数模型在它上面的单 agent 成绩超过 45%。四种多 agent 架构都低于单 agent，从 −2.1% 到 −14.9%。
  • Terminal-Bench 在 45% 以下，结果有高有低。它是命令行任务评测，单 agent 的平均成绩低于 45%。独立方式比单 agent 高 1.7%，集中方式低 19.2%。

45% 是统计上的趋势，有例外。上面的图里 Workbench 的单 agent 成绩在 60% 以上，已经超过 45%，去中心方式的成绩仍然比单 agent 高，高出的部分相当于单 agent 成绩的 6%。

第三条：工具多不多。论文的解释从预算出发：各种架构的 token 预算一样多，用了多个 agent，每个 agent 分到的预算就变少。在工具很多的任务上，每个 agent 分到的预算不够用来组织复杂的工具调用。论文举的例子是有 16 个工具的办公流程，对应上表里的 Workbench。上表里 Workbench 的四种架构，最好的只比单 agent 高 6%，最差的低 11%，用多个 agent 没有带来多少好处。

论文自己的总结是：决定协作成败的是架构和任务是否对得上，agent 的数量本身说明不了什么。出处：Kim 等，2026，摘要和第 1、4 节。

证据三：要改同一份代码的工作，拆开更差

CooperBench 是一个协作编程评测，第五部分用它说明协调的代价，它同样是这里的证据。这个评测给两个 agent 各分配一个功能。论文对任务的描述是：两个功能可以各自实现，彼此不矛盾，可以一起放进同一个代码库，但要改的代码有重叠或互相依赖，不了解对方的计划就可能做出互相冲突的改动。对照组是把两个功能都交给一个 agent。

成功的标准是：两份改动能合并到一起，而且两个功能各自的测试都通过。

也就是说，同样的两个功能，分给两个 agent 去做，成功率只有交给一个 agent 时的一半多一点。论文测的五个模型，都是分开做更差。

前面的结论是工作能拆开时多 agent 更可能划算，这条证据给它加了一个限制。本页最后一节的判断标准里有一条：每个 agent 可以负责一块独立的产出，最后再合并。按这一条，这些任务看起来适合多 agent，结果却是五个模型都更差。

一个很可能的原因是，两块产出要改的代码有重叠或互相依赖。两个 agent 各只知道自己那个功能的需求，这也可能有影响，实验没有把这些因素分开测量。

+
为什么分头做会对不上。Cognition（做编程 agent Devin 的公司）的文章 Don’t Build Multi-Agents 给了一个直观的解释，归成两条原则。
  • 要共享上下文。例子是把「做一个 Flappy Bird 游戏」这个任务拆成两个子任务，分给两个子 agent，子 agent 指被另一个 agent 派出去做一部分工作的 agent。两个子 agent 一个做背景，一个做小鸟。每个子 agent 只拿到自己的那个子任务，看不到原始任务，缺的就是这份上下文。做背景的那个把子任务理解成了超级马里奥的风格，做小鸟的那个做出来的东西既不像游戏素材，动作也不对。最后负责合并的 agent 拿到的是两份互相对不上的东西。
  • agent 每做一步，都包含一些没有写明的决定。上面做背景的子 agent 选了超级马里奥的风格，就是这样一个决定。文章接着说，就算改成让两个子 agent 都看得到原始任务，它们仍然看不到对方正在做什么，各自做的决定仍然可能互相冲突。
出处：Don’t Build Multi-Agents。
+
Anthropic 说的边界。Anthropic 介绍自己的多 agent 研究系统时，也说到哪些任务现在不适合用多 agent：需要所有 agent 共享同一份上下文的任务，或者 agent 之间依赖很多的任务。文章还说，大多数编程任务里真正能并行的部分，比查资料做调研的任务少。出处：How we built our multi-agent research system。

把这些例子放在一起：「能拆开」指什么

前面的例子里，金融分析拆给几个 agent 之后成绩更高，一步接一步的规划和要改同一个代码库的两个功能拆开之后更差。差别在哪里，可以归纳成两个能检查的条件。

  1. 各块不改同一份东西。不改同一处代码或同一批文件，不改同一份共享的状态。
  2. 做的过程中不需要对方的中间结果。后一步不依赖前一步，各块可以同时推进。

两个条件都可以满足得多一些或少一些。下一节的判断标准里，「可以试试多 agent」一栏的第一条写的是「子任务之间只需要很少的同步」。所以有少量共享和依赖的工作仍然可以试，协调的成本会跟着升高。

下表用这两个条件对照四个例子。

每一格的判断理由如下，都是这一页按原文对任务的描述作出的归类：

  • 金融分析。几条分析各查各的资料，查的时候用不到别的分析的结果，最后才由 orchestrator 合起来。两个条件都满足。
  • 一步接一步的规划。每一步都要用上一步的结果，所以第二个条件不满足。单 agent 的三步里，要改东西的是后两步：把材料从库存放进合成格，再在合成格里合成。这两步改的是同一份库存和同一个合成格。不管怎么把它们分给几个 agent，要改的都是这一份状态，所以第一个条件也算不满足。
  • 两个功能改同一个代码库。论文说两个功能可以各自实现，一个 agent 写自己的功能时不用等对方先做出什么，所以第二个条件满足。论文的原话是两个 agent 要改的代码有重叠或互相依赖（overlapping or interdependent code）。这里的「互相依赖」说的是两处代码之间的关系，和做事的先后无关，所以这一页把它和「重叠」一起归到第一个条件，第一个条件不满足。论文说不了解对方的计划就可能做出互相冲突的改动，起因也在第一个条件上：两份改动落在重叠或互相依赖的代码上，才需要知道对方打算怎么改。
  • 编译 Linux 内核。16 个 agent 各修各的，谁也不等谁，第二个条件满足。它们碰到的是同一个 bug，改的是同一处代码，第一个条件起初不满足。

最后一行说明，第一个条件不满足时，有时可以换一种拆法让它满足。C 编译器案例里作者改的是检验编译器的办法。原来的检验是用 agent 写的编译器编译整个内核，每个 agent 碰到的都是同一个 bug。作者改成随机挑出大部分内核文件，交给成熟的开源编译器 GCC 编译，只有剩下的文件用 agent 写的编译器编译。内核出了问题，原因就在剩下的这批文件里。文件是随机挑的，每次剩下的那一批不一样，所以各个 agent 可以在不同的文件上修不同的 bug。同时改到同一处代码的机会就少了，各自的修改仍然要合并。

第一个条件不满足时还有一种办法：给共享的部分定下明确的规则。例如 agent 动手前先认领任务，也就是登记这件事归自己，再各自在分开的工作区里改。这些做法在第四部分讲，效果目前没有对照数据。

所以：什么时候用哪一种

把三处证据和「能拆开」的两个条件合起来，可以得到下面的判断标准。左栏是优先用单 agent 的情况，右栏是可以试试多 agent 的情况。

这两栏和「能拆开」的两个条件对得上。左栏前两条说的是两个条件不满足的情况：步骤高度依赖彼此，几块工作都要改同一份共享的东西。左栏第三条和证据二里 45% 的趋势是同一个方向：单 agent 已经做得够好时，再加 agent 得不到多少好处。两者的标准不同，左栏说的是自己定的质量、成本和延迟目标，45% 是论文在它的评测上观察到的正确率。

右栏前三条说的是两个条件基本满足的情况：子任务之间只需要很少的同步，信息和产出都可以分开。右栏第四条说的是另一种情况：并行、专门化或者独立审查能解决一个已经用数据确认的瓶颈。符合右栏的某一条只说明可以试。证据三里的任务看起来符合第三条：两个功能各是一块产出，最后再合并。但按上一节的对照表，这些任务不满足第一个条件，分开做的结果更差。

i
建议：先建立单 agent 基线，也就是先只用一个 agent 把任务尽量做好，拿它当比较的基准。加 agent 要有明确的目的，并且测量它带来的贡献是否大于协调的成本。这里的「协调的成本」和「换来什么，付出什么」一节的那句总结里一样，泛指五个坏处。

怎样测量，可以照证据一里 Kim 等人的论文的做法：工具、提示词和 token 预算都保持不变，只把单 agent 换成多 agent，在同一批任务上比较成绩，再比较花掉的 token 或费用。成绩没有提高，就不加。成绩有提高时，再按任务的价值判断这点提高值不值得多花的 token 或费用。

+
Anthropic 的说法。Anthropic 的文章 Building effective agents 说的和上面的建议是同一个意思，范围更广：先找最简单的办法，只在需要时才增加复杂度。只有当复杂度确实改善了结果时，才值得加。出处：Building effective agents。
i
左栏第三条里的「成本」怎么读。这一条说的是：单 agent 已经达到目标时，不必再加 agent。反过来的情况要小心：单 agent 的成本超标时，换成多 agent 通常帮不上忙，因为多 agent 一般更贵。多 agent 有可能改善的是质量和完成任务的时间。

用不用多个 agent，现在主要由设计系统的人来判断。不过编程 agent 已经能在一次任务里自己派出子 agent。可以这样理解：让模型自己判断什么时候派、派几个，是一个正在推进的方向。

以 Anthropic 的编程 agent Claude Code 为例，它的文档写明，它用的模型 Claude 会根据请求里对任务的描述、各个子 agent 的说明和当前的上下文，自动把任务派给子 agent。自动派得不够时，用户也可以点名要求用某个子 agent。出处：Claude Code 文档的子 agent 一页。

决定用多个 agent 之后，第一个设计问题是编排：谁分派任务，谁做决定。
