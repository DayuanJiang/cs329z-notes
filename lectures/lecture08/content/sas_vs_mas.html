先看结论

  • 多个 agent 换来的是并行、专门化和更集中的上下文，付出的是协调的成本：派任务、发消息、合并结果都要花时间和 token。
  • 值不值，主要看工作能不能拆开。同一批多 agent 架构，在能拆开的金融分析任务上最多比单 agent 高 81%，在一步接一步的规划任务上最多低 70%。
  • 「能拆开」有两个条件：各块不改同一份东西，做的过程中也不需要对方的中间结果。只满足后一个还不够：两个可以各自实现、但要改的代码有重叠或互相依赖的功能，拆给两个 agent 比交给一个 agent 差。
  • 单 agent 已经做得不错时，再加 agent 往往得不偿失。论文观察到的界线大约是单 agent 正确率 45%，这是一个趋势，有例外。
  • 所以先做一个强的单 agent 基线。每加一个 agent 都要有明确的目的，并且测量它的贡献是否大于协调的成本。

多 agent 系统是什么

多 agent 系统的定义很短：一组 agent，朝着同一个任务一起工作。它在 AI 系统里处在最复杂的一端。

单 agent 加并行，和多 agent 的分界在哪里

单 agent 也可以同时发出几个工具调用，或者同时发出几次模型调用，所以只看有没有并行，分不出两者。一个实用的分法是看有几处在各自做决定：

  • 单 agent。只有一条主线，也只有一个上下文窗口。并行的调用都从这条主线发出，结果都回到这条主线，由它决定下一步。
  • 多 agent。有几个 agent 各自决定自己的下一步，每个 agent 有自己的指令，通常也有自己的上下文。它们可以同时运行，也可以轮流发言或依次交接，第三部分有这样的例子。

这条界线是模糊的，两种写法之间有不少中间情况。Kim 等人 2026 年的论文用的是同样的标准：单 agent 系统的感知、规划和行动都在同一个模型实例控制的一个循环里完成，带工具调用和自我反思的 agent 仍然算单 agent。出处：Kim 等，2026，第 2、3 节。

设计一个多 agent 系统，必须考虑三件事，它们是后面三个部分的主题。

换来什么，付出什么

下面举四个例子，前两个说的是好处，后两个说的是坏处：

  • 并行和探索。一道数学难题有很多条可能的证明路线，可以让不同的 agent 各攻一条，同时推进。Navier-Stokes 问题是关于流体运动方程的一道数学难题，七道千禧年大奖难题之一。OpenAI 在 2026 年 9 月公布了一份由 agent 生成的解答，按它的介绍，不同的 agent 小组拿到的是问题的不同版本，并且被鼓励尝试不同的思路。出处：On the Navier-Stokes Millennium Prize Problem。
  • 上下文更集中。一个常见的做法是把写代码和审查代码交给两个 agent。负责审查的 agent 从一份干净的上下文开始，不带着写这段代码时的思路，这样很可能更容易看出问题。Cursor 介绍自己的 agent swarm 时写道，它试过几种审查方式：让负责审查的 agent 看 worker 的完整运行记录，只看产出，或者只看代码库，也试过换别的模型来审查。文章的说法是，没有哪一种审查能发现所有问题，几种互不相关的审查可以叠加；文章推测，这套叠加的审查是产出质量能保持住的主要原因之一，没有给出对照数据。出处：Agent swarms and the new model economics。
  • 违背说好的事。一个 agent 说「我只改这几个文件」，后来又改了别的文件，合并时就多出冲突要解决。
  • 错误传播。一个 agent 上网查资料，写成报告交给下一个 agent。下一个 agent 通常会直接采信这份报告，报告里的错误就进了后面的工作，查起来也更难。

下面的表把两种系统放在一起对比。有一行值得注意：单 agent 也能并行，它可以同时发出几个互不依赖的工具调用。所以「需要并行」本身还不足以说明要用多个 agent。

最后一行的开销有一个直接的来源：每启动一个新的 agent，系统提示词都要重新读进它的上下文，它还要自己重新查看文件、弄清状况，这些 token 都要再付一遍。所以多 agent 系统通常比单 agent 贵，第二部分的成本图上有实测的数字和一种例外：独立方式在两家的模型上比单 agent 便宜。

+
开销有多大。Anthropic 在介绍自己的多 agent 研究系统时给过数字：agent 用的 token 大约是普通对话的 4 倍，多 agent 系统大约是 15 倍。文章还说，多 agent 系统有效，主要是因为它帮你花掉了足够多的 token 去解决问题。所以任务的价值要够高，才付得起这笔开销。出处：How we built our multi-agent research system。

证据二：差别主要来自任务

平均成绩掩盖了更大的差别。同一篇论文按评测分开看，每个箱线图上方的百分比是四种多 agent 架构相对单 agent 的变化。

{{fig 23 | 四个评测各一格，每格里是单 agent 和四种多 agent 架构的成绩分布。图片来源：Kim 等，2026。}}
+
论文怎样解释这个差别。图上只有结果，原因在论文正文里。
  • 能不能拆开。金融分析的任务可以自然地拆成几条并行的分析，例如一个 agent 查监管和新闻，一个查公司报表，一个评估对运营的影响，最后由一个负责统筹的 agent（orchestrator）合起来。规划任务本来就是一步接一步：论文举的例子是在 Minecraft 里合成一面墙，单 agent 三步做完（查配方、放材料、合成）；多 agent 把它拆给三个 agent，其中查配方和查库存两步是多余的，token 花在了协调上，留给推理的反而少了。
  • 单 agent 已经多好。论文的回归分析发现，单 agent 正确率超过 45% 的任务，再加 agent 的收益倾向于为负，因为能改进的空间小，协调的成本却照付。论文的最新版本里还有两个评测，上面的图里没有。编程评测 SWE-bench Verified 就是这种情况：四种多 agent 架构都低于单 agent，从 −2.1% 到 −14.9%。命令行任务评测 Terminal-Bench 上单 agent 的平均成绩低于 45%，结果有高有低：独立方式比单 agent 高 1.7%，集中方式低 19.2%。45% 是统计上的趋势，有例外：上面的图里 Workbench 的单 agent 成绩在 60% 以上，去中心方式仍然高了 6%。
  • 工具多不多。工具很多的任务，每个 agent 分到的 token 预算变少，不够用来组织复杂的工具调用。
论文自己的总结是：决定协作成败的是架构和任务是否对得上，agent 的数量本身说明不了什么。出处：Kim 等，2026，摘要和第 1、4 节。

证据三：要改同一份代码的工作，拆开更差

第五部分用 CooperBench 说明协调的代价，它同样是这里的证据。这个评测给两个 agent 各分配一个功能。论文对任务的描述是：两个功能在逻辑上可以并存，但要改的代码有重叠或互相依赖，不了解对方的计划就可能做出互相冲突的改动。对照组是把两个功能都交给一个 agent。

成功的标准是：两份改动能合并到一起，而且两个功能各自的测试都通过。

也就是说，同样的两个功能，分给两个 agent 去做，成功率只有交给一个 agent 时的一半多一点。论文测的五个模型，都是分开做更差。

这条证据给前面的结论加了一个限制。按后面的判断标准，这些任务看起来适合多 agent：每个 agent 负责一块独立的产出，最后再合并。结果却是五个模型都更差。一个很可能的原因是，两块产出要改的代码有重叠或互相依赖。两个 agent 各只知道自己那个功能的需求，这也可能有影响，实验没有把这些因素分开测量。

+
为什么分头做会对不上。Cognition（做 Devin 的公司）的文章 Don’t Build Multi-Agents 给了一个直观的解释，归成两条原则。
  • 要共享上下文。例子是让两个子 agent 分头做一个 Flappy Bird：一个做背景，一个做小鸟。做背景的那个把任务理解成了超级马里奥的风格，做小鸟的那个做出来的东西既不像游戏素材，动作也不对。最后负责合并的 agent 拿到的是两份互相对不上的东西。
  • 每个动作都带着没说出口的决定。就算两个子 agent 都看得到原始任务，它们看不到对方正在做什么，各自做的决定仍然可能互相冲突。
Anthropic 的文章也说了同样的边界：需要所有 agent 共享同一份上下文、或者 agent 之间依赖很多的领域，现在不适合用多 agent；大多数编程任务里真正能并行的部分，比研究类任务少。出处：Don’t Build Multi-Agents、How we built our multi-agent research system。

把这些例子放在一起：「能拆开」指什么

对照上面的例子和下一节的判断标准，「能拆开」可以归纳成两个能检查的条件。两个条件都是程度上的：判断标准的原话是「只需要很少的同步」，有少量共享和依赖的工作仍然可以试，协调的成本会跟着升高。

  1. 各块不改同一份东西。不改同一处代码或同一批文件，不改同一份共享的状态。
  2. 做的过程中不需要对方的中间结果。后一步不依赖前一步，各块可以同时推进。

最后一行说明，第一个条件不满足时，可以把工作重新切一遍。案例里重新切的是失败的定位：每个 agent 去修一个不同的 bug，同时改到同一处代码的机会就少了，各自的修改仍然要合并。另一条路是用明确的办法管住共享的部分，例如认领和分开的工作区，它在第四部分讲，效果目前没有对照数据。

所以：什么时候用哪一种

下面的判断标准，和上面两个条件对得上。左栏前两条说的是两个条件不满足的情况：步骤高度依赖彼此，工作和一份共享的状态耦合得很紧。左栏第三条对应证据二里 45% 的趋势。右栏说的是两个条件都满足的情况，另外多一条要求：要有一个测量出来的瓶颈。

i
建议：从一个强的单 agent 基线开始。加 agent 要有明确的目的，并且测量它带来的贡献是否大于协调的成本。
i
左栏第三条里的「成本」怎么读。这一条说的是：单 agent 已经达到目标时，不必再加 agent。反过来的情况要小心：单 agent 的成本超标时，换成多 agent 通常帮不上忙，因为多 agent 一般更贵。多 agent 有可能改善的是质量和完成任务的时间。

用不用多个 agent，现在主要由设计系统的人来判断。编程 agent 已经能在一次任务里自己派出子 agent。以 Claude Code 为例，它的文档写明，Claude 会根据请求里对任务的描述、各个子 agent 的说明和当前的上下文，自动把任务派给子 agent；自动派得不够时，用户也可以点名要求用某个子 agent。出处：Claude Code 文档的子 agent 一页。可以这样理解：让模型自己判断什么时候派、派几个，是一个正在推进的方向。

+
Anthropic 的说法。Building effective agents 说的是同一个意思，范围更广：先找最简单的办法，只在需要时才增加复杂度；只有当复杂度确实改善了结果时，才值得加。出处：Building effective agents。

决定用多个 agent 之后，第一个设计问题是编排：谁分派任务，谁做决定。
