先看结论

  • 16 个 agent 用近 2000 次 Claude Code 会话、两周时间、不到 2 万美元，写出一个 10 万行的 C 编译器。这个编译器能编译 Linux 6.9，但还有局限，例如 x86 上有一段启动代码要调用成熟的开源编译器 GCC 来编译。Claude Code 是 Anthropic 的编程 agent，一次会话指它从启动到退出的一次运行。
  • 这个项目是 Anthropic 的 Nicholas Carlini 做的，下面的「作者」都指他。写代码的工作由 agent 自主完成。作者负责设计 agent 周围的环境，包括测试和反馈，并在 agent 卡住时想办法。
  • 这个项目没有 orchestrator，也就是没有统管全局、给其他 agent 分派任务的那个 agent。agent 之间也没有对话，只通过 Git 仓库里的文件互通消息。协调靠三样东西：认领文件、README 和进度文件、每个 agent 自己的一份 clone。认领文件表示一个任务已经有人在做。README 是仓库里的说明文档，它和进度文件一起记下项目的情况和做到了哪里。clone 是仓库的一份本地副本。
  • 并行只在工作能拆开时有用。失败的测试有很多个、彼此不同时，每个 agent 各修一个。编译 Linux 内核是一整个大任务，16 个 agent 卡在同一个 bug 上，互相覆盖修改。作者想办法把它拆开，并行才恢复。
  • 作者说他大部分的精力花在设计 agent 周围的环境上。他说检验程序必须接近完美，否则 agent 会朝着错的目标去做。检验程序指判断任务有没有做对的程序，测试就属于这一类。
  • 这个案例没有和单 agent 比过，成品也有明显的局限。

背景

这个案例来自 Anthropic 网站上的一篇文章，标题是 Building a C compiler with a team of parallel Claudes，意思是「用一组并行的 Claude 写一个 C 编译器」。文章发表于 2026 年 2 月 5 日，作者是 Nicholas Carlini，这个项目就是他做的。本页说的「原文」都指这篇文章，「作者」都指他。

{{fig 84 | 图片来源：原文。}}

看这个案例的理由是：已经有公司在用 agent swarm（一群并行工作的 agent）做工程和科研，从这个案例可以看到这样的 swarm 可能是怎样运作的。

+
规模和成品。下面的数字取自原文。
  • 16 个 agent 并行，用的都是 Anthropic 的模型 Claude，型号是 Opus 4.6。
  • 两周里运行了近 2000 次 Claude Code 会话，用了 20 亿输入 token 和 1.4 亿输出 token，总成本不到 2 万美元。token 是模型处理文字的最小单位。
  • 成品是一个用 Rust 写的 C 编译器，约 10 万行，能在 x86、ARM 和 RISC-V 三种处理器架构上编译出可以启动的 Linux 6.9，也能编译 QEMU、FFmpeg、SQLite、PostgreSQL 和 Redis 这几个开源软件。开发过程中 agent 不能上网。
  • 它有局限。第一，它没有自己的汇编器和链接器，这是把编译结果变成可执行文件的后两步工具。第二，在 x86 上，Linux 启动时先要经过一个 16 位的阶段，原文叫 real mode，所以最先运行的那一段代码要编译成 16 位的。这个编译器编译这一段得到的结果超出了 Linux 规定的大小，所以这一段改为调用 GCC 来编译，GCC 是一个成熟的开源 C 编译器。ARM 和 RISC-V 上没有这个问题。其余的局限见本页最后一节。
出处：Building a C compiler with a team of parallel Claudes。本页其余绿色框的出处相同。

编排：没有 agent 负责分派任务

这个项目里没有负责分派任务的 agent，做什么由每个 agent 自己决定。每个 agent 都在这样一个循环里运行：

  • while true：循环永不结束。一次会话结束，马上开始下一次。本页说的一个 agent，指的就是这样一个不停运行的循环，它先后启动很多次会话。
  • claude -p "$(cat AGENT_PROMPT.md)"：每次都用同一份提示词文件，以非交互的方式启动一次 Claude Code 会话。
  • --dangerously-skip-permissions：跳过所有权限询问，agent 做什么都不用等人批准。作者在原文里提醒：要在容器里运行，不要在自己的机器上运行。容器是和主机隔开的运行环境。
  • 其余两行用当前提交的哈希（标识这次提交的一串编号）给日志文件命名，把输出写进日志。
+
没有负责编排的 agent。作者明确说他没有用负责编排的 agent，也就是没有 orchestrator。他也没有规定一套流程来管项目的大方向，做什么由每个 agent 自己决定。多数时候 agent 会挑最明显的下一个问题去做。提示词里要求 agent 把问题拆成小块，记录自己在做什么，想清楚下一步做什么，一直做到完美为止。出处：原文。

对照第二部分：这里没有 orchestrator，agent 自己挑任务，通过共享仓库里的文件交换信息。这符合去中心方式通常的定义。去中心方式是第二部分讲的四种编排方式之一，通常指没有 orchestrator、agent 通过一块共享的留言板或通信通道交换信息、自己领任务的做法。留言板指一块所有 agent 都能读写的共享区域。

第二部分里四种编排方式的成绩和开销数字，来自 Kim 等人 2026 年的论文。这篇论文在六个评测上比较了单 agent 和四种编排方式。论文实现的去中心方式是几个 agent 就同一个问题一轮一轮辩论，最后按多数票定出答案，和这里的做法不一样。所以第二部分里去中心方式的数字不能直接套到这个案例上，见第二部分的「去中心」的两种意思一节。

agent 之间靠认领来分工：开始做一个任务之前，先在共享的 Git 仓库里写一个文件，表示这个任务已经有人在做。这个文件在本页叫认领文件。每个 agent 的一次会话按下面五步走。

第四部分讲了系统可以提供的三样东西：任务台账、分开的工作区、共享记忆。这里三样都用上了。第一样是任务台账，也就是一份记下计划、谁负责什么和进度的工作记录：current_tasks/ 是一份很简单的任务台账，只回答「这件事有没有人在做」。第二样是分开的工作区：每个 agent 有自己的一份 clone。第三样是共享记忆：仓库里的 README 和进度文件让 agent 在新的一次会话里知道前面做到了哪里，下一节讲。

第四部分讲分开的工作区时，举的现成办法是 git 的 worktree 功能，它让同一个仓库同时有几个独立的工作目录。这个案例没有用 worktree，每个 agent 用的是自己容器里的一份 clone。两种办法的作用相同：每个 agent 改自己那一份文件，做的时候互不干扰。

通信：只有文件

agent 之间没有对话，互通消息只靠仓库里的文件。「协调：在 Git 里认领」一节的两张图里，README 和进度文件旁边都用红字标了两个作用：agent 之间的通信，和共享记忆。

+
为什么要有 README 和进度文件。作者说，除了「协调：在 Git 里认领」一节讲的通过共享的 Git 仓库同步以外，他还没有实现任何别的 agent 之间的通信方式。认领文件、README 和进度文件都放在这个仓库里，靠拉取和推送传给别的 agent。每次会话开始时，agent 都在一个全新的容器里，没有任何上下文。上下文是模型这一次能读到的全部内容，这时里面没有项目此前的任何情况，agent 在大项目上要花不少时间弄清状况。所以作者在提示词里要求 agent 维护详细的 README 和进度文件，并且经常更新当前的状态。agent 被某个 bug 卡住时，常常会自己维护一份文档，记下试过哪些失败的办法、还剩哪些任务。出处：原文。

对照第三部分的四种通信方式，这是一块用文件做的留言板：谁都能写，后来的 agent 都能读，而且一直留着。

这块留言板比第三部分举的例子简单。第三部分的例子是多 agent 框架 MetaGPT：它的消息有固定的字段，每个 agent 可以订阅自己关心的那几类消息，让这几类消息送到自己这里。这里两样都没有：文件怎么写没有固定的格式，也没有订阅的机制，只靠提示词里的一句要求来维持。

这种做法顺带回答了一个问题：agent 多了以后，别人的消息会不会占满每个 agent 的上下文。上下文能装下的内容有限。这里的消息都写成仓库里的文件。agent 在新的一次会话里自己读文档、用工具搜索，只取用得上的部分。工具指 agent 可以调用的外部功能，这里是在文件里搜索。第三部分把它和另一个例子放在一起讲。

几个职责互补的专门 agent

所有 agent 都在同一份编译器代码上工作，职责分成下面六种。

六种职责里，原文写明有五种各交给了一个 agent：去重、文档、编译器的性能、生成代码的效率、Rust 的设计和代码质量。这五个就是标题里说的专门 agent。实现和调试是解决问题本身的工作，做这件事的 agent 有几个，原文没有写明。

原文解释了为什么要有去重的 agent：模型写的代码经常重新实现已经有的功能。下面第六条经验「分配互补的目标」就来自这里，经验里的「目标」指的就是这一节说的职责。

这些职责是作者指定给各个 agent 的。具体怎么指定，例如是否给它们用了不同的提示词，原文没有说明。和编排一节合起来看：平时挑哪个任务由 agent 自己决定，长期的职责由作者事先定好。

并行什么时候失灵：编译 Linux 内核

并行只在工作能拆开时有用。下面的六条经验里有一条「为并行而设计」，原文里它背后有一段经过，是整个案例里最能说明这一点的一段。

+
原文的经过。
  • 能拆开时，并行很容易。作者用编译器测试集来检验这个编译器，测试集由几百个互相独立的测试组成。失败的测试有很多个、彼此不同时，每个 agent 各挑一个去修。测试集里通过的测试占到 99% 之后，每个 agent 各自去让一个不同的小型开源项目通过编译，例如 SQLite、Redis、Lua。
  • 拆不开时，并行没有用。开始编译 Linux 内核时，agent 卡住了。测试集里的测试互相独立，编译内核却是一整个大任务。每个 agent 都碰到同一个 bug，各自修掉，然后互相覆盖对方的修改。作者的原话是：运行 16 个 agent 没有帮助，因为每一个都卡在同一个任务上。「协调：在 Git 里认领」一节的认领办法在这里为什么没有起作用，原文没有说明。
  • 办法是换一种检验方式，把大任务拆开。原来的检验是用 Claude 写的编译器编译整个内核。作者写了一套新的测试，拿 GCC 当作已知正确的编译器来对照：随机挑大部分内核文件用 GCC 编译，只有剩下的文件用 Claude 写的编译器编译。编出来的内核能正常运行，说明问题不在剩下的这一批文件里。不能正常运行，就再缩小范围。原文说，这样各个 agent 就可以并行，在不同的文件上修不同的 bug。为什么会碰到不同的 bug，原文没有解释，一个很可能的原因是文件是随机挑的，每次剩下的那一批不一样。原文补充说，这一步做完之后，还要再找出那些单独编译没问题、放在一起才出错的文件组合。

这段经过和第一部分的证据说的是同一件事：并行有没有用，要看工作能不能拆开。第一部分把「能拆开」归纳成两个条件：各块不改同一份东西，做的过程中也不需要对方的中间结果。编译内核时不满足的是前一个条件：16 个 agent 碰到同一个 bug，改的是同一处代码。

这里更进一步的一点是，拆不开的工作，有时人可以想办法让它变得能拆开。这里的办法是换一种检验方式：原来用 Claude 写的编译器编译整个内核，后来每次只让随机剩下的一部分文件用它编译。

六条经验

从这个案例可以总结出六条经验。下表左列是经验，右列是原文里对应的做法。

六条里有四条（1、2、4、5）讲的都是 agent 周围的环境，也就是测试、反馈和记录。第 2 条也算在里面，因为内核那一次的办法是换一种检验方式。作者自己也说，他大部分的精力花在设计 agent 周围的环境上，好让 agent 在他不在场时，自己弄清项目现在的状况和下一步该做什么。

这个案例没有说明什么

这个案例做成了一个很大的项目，容易被当作多 agent 有效的证明。下面五点说的是它的限度，前三点取自原文，后两点是对照这一讲前面的标准得出的。

  • 成品有明显的局限。它还不能直接替代真正的编译器。它开启全部优化后生成的代码，效率还不如 GCC 关闭全部优化时生成的代码。它没有自己的汇编器和链接器，x86 上 Linux 启动时最先运行的那段 16 位代码也要调用 GCC 来编译。
  • 已经接近模型能力的极限。作者说这个编译器已经接近模型能力的极限，新功能和 bug 修复经常弄坏已有的功能。
  • 测试通过不等于做完了。作者在结尾说，自主运行的系统很容易让人看到测试通过就以为完成了，而实际上很少如此。
  • 没有和单 agent 比。第一部分建议先做单 agent 基线并测量收益，单 agent 基线指先只用一个 agent 把任务做好，当作比较的基准。这个案例没有这样的对照。所以它能说明的是这样做可以做成，用多个 agent 是否比用一个 agent 做得更好，它回答不了。
  • 只用了一种通信方式。只有共享的文件，相当于一块留言板，消息没有固定的格式，也没有订阅的机制。第三部分讲的另外几种方式这里都没有用到。其中两种是几个 agent 在同一个群里发言的共用对话，和把整场对话交给另一个 agent 的交接。另外两种是一个 agent 调用另一个 agent 替它做一件事的「把 agent 当工具用」，和让不同系统里的 agent 互相通信的 A2A 协议。所以这个案例说明不了那些方式好不好。

回到总览，那里把这一讲的五个问题和答案列在一张表里：要不要用多个 agent，编排，通信，协调，会怎样失败。
