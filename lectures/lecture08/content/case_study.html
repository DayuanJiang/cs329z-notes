先看结论

  • 16 个 agent 用近 2000 次 Claude Code 会话、两周时间、不到 2 万美元，写出一个 10 万行、能编译 Linux 6.9 的 C 编译器。写代码的工作由 agent 自主完成；人负责设计环境、测试和反馈，并在 agent 卡住时想办法。
  • 它没有 orchestrator，也就是没有统管全局、给其他 agent 分派任务的那个 agent。agent 之间也没有对话，只通过 Git 仓库里的文件互通消息。协调靠三样东西：认领文件、进度文件、每个 agent 自己的一份 clone。clone 是仓库的一份本地副本。
  • 并行只在工作能拆开时有用。失败的测试有几百个时，每个 agent 各修一个；编译 Linux 内核变成一整个大任务时，16 个 agent 卡在同一个 bug 上，互相覆盖修改。作者想办法把它拆开，并行才恢复。
  • 作者花精力最多的地方是测试和反馈。他说任务的检验程序必须接近完美，否则 agent 会去解决一个错的问题。
  • 这个案例没有和单 agent 比过，成品也有明显的局限。

背景

这个案例来自 Anthropic 网站上的一篇文章，标题是「用一组并行的 Claude 写一个 C 编译器」，作者是 Nicholas Carlini，发表于 2026 年 2 月 5 日。本页说的「原文」都指这篇文章。

{{fig 84 | 图片来源：Anthropic。}}

看这个案例的理由是：已经有公司在用 agent swarm（一群并行工作的 agent）做工程和科研，从这个案例可以看到这样的 swarm 可能是怎样运作的。

+
规模和成品。下面的数字取自原文。
  • 16 个 agent 并行，用的模型是 Opus 4.6。
  • 两周里跑了近 2000 次 Claude Code 会话，用了 20 亿输入 token 和 1.4 亿输出 token，总成本不到 2 万美元。
  • 成品是一个用 Rust 写的 C 编译器，约 10 万行，能在 x86、ARM 和 RISC-V 上编译出可以启动的 Linux 6.9，也能编译 QEMU、FFmpeg、SQLite、PostgreSQL 和 Redis。开发过程中 agent 不能上网。
  • 它有局限：没有自己的汇编器和链接器，启动 Linux 需要的 16 位 x86 部分也要调用 GCC。GCC 是一个成熟的开源 C 编译器。其余的局限见本页最后一节。
出处：Building a C compiler with a team of parallel Claudes。本页其余绿色框的出处相同。

编排：没有人分派任务

这个项目里没有负责分派任务的 agent，做什么由每个 agent 自己决定。每个 agent 都在这样一个循环里运行：

  • while true：循环永不结束。一次会话跑完，马上开始下一次。
  • claude -p "$(cat AGENT_PROMPT.md)"：每次都用同一份提示词文件，以非交互的方式启动一次 Claude Code 会话。
  • --dangerously-skip-permissions：跳过所有权限询问，agent 做什么都不用等人批准。作者在原文里提醒：要在容器里运行，不要在自己的机器上运行。
  • 其余两行用当前提交的哈希给日志文件命名，把输出写进日志。
+
没有负责编排的 agent。作者明确说他没有用负责编排的 agent，也就是没有 orchestrator。他也没有规定管理高层目标的流程，做什么由每个 agent 自己决定。多数时候 agent 会挑眼下最容易看出来该做的那个问题去做。提示词里要求 agent 把问题拆成小块，记录自己在做什么，想清楚下一步做什么，一直做到完美为止。

对照第二部分：这里没有 orchestrator，agent 自己挑任务，通过共享仓库里的文件交换信息。这符合去中心方式通常的定义。去中心方式是第二部分讲的四种编排方式之一，通常指没有 orchestrator、agent 通过一块共享的留言板或通信通道交换信息、自己领任务的做法。

第二部分引用的 Kim 等人 2026 年的论文也测了去中心方式。那里是几个 agent 就同一个问题一轮一轮辩论，最后按多数票定出答案，和这里的做法不一样。所以那篇论文里去中心方式的数字不能直接套到这个案例上，见「去中心」的两种意思。

agent 之间靠认领来分工：开始做一个任务之前，先在共享的 Git 仓库里写一个文件，表示这个任务已经有人在做。每个 agent 的一次会话按下面五步走。

第四部分讲了系统可以提供的三样东西：任务台账、分开的工作区、共享记忆。这里三样都用上了。第一样是任务台账，也就是一份记录谁在做什么的工作记录：current_tasks/ 是一份很简单的任务台账，只回答「这件事有没有人在做」。第二样是分开的工作区：每个 agent 有自己的一份 clone。第三样是共享记忆：仓库里的进度记录让新启动的 agent 知道前面做到了哪里，下一节讲。

分开的工作区在第四部分叫作 worktree 隔离。严格说这里用的是容器里各自的 clone，没有用 git 的 worktree 功能，作用相同。

通信：只有文件

agent 之间没有对话，互通消息只靠仓库里的文件。上一节的流程图里，「README 和进度文件」旁边用红字标了两个作用：agent 之间的通信，和共享记忆。

+
为什么要有进度文件。作者说，除了上面的认领办法，他还没有实现任何别的 agent 之间的通信方式。每个 agent 被放进一个全新的容器，没有任何上下文，在大项目上要花不少时间弄清状况。所以他在提示词里要求 agent 维护详细的 README 和进度文件，并且经常更新当前的状态。agent 被某个 bug 卡住时，常常会自己维护一份文档，记下试过哪些失败的办法、还剩哪些任务。

对照第三部分的四种通信方式，这是一块用文件做的留言板。留言板指一块所有 agent 都能读写的共享区域：谁都能写，后来的 agent 都能读，而且一直留着。这里的留言板没有消息格式，也没有订阅，只靠提示词里的一句要求来维持。

这种做法顺带回答了一个问题：agent 多了以后，别人的消息会不会塞满每个 agent 的上下文。这里消息不直接推给任何 agent，都写成仓库里的文件。新启动的 agent 自己读文档、用工具搜索，只取用得上的部分。第三部分把它和另一个例子放在一起讲。

几个职责互补的专门 agent

所有 agent 都在同一份编译器代码上工作，但各有各的职责。

原文解释了为什么要有去重的 agent：模型写的代码经常重新实现已经有的功能。下面第六条经验「分配互补的目标」就来自这里。

这些职责是作者指定给各个 agent 的。具体怎么指定，例如是否给它们用了不同的提示词，原文没有说明。和编排一节合起来看：平时挑哪个任务由 agent 自己决定，长期的职责由人事先定好。

并行什么时候失灵：编译 Linux 内核

并行只在工作能拆开时有用。下面的六条经验里有一条「为并行而设计」，原文里它背后有一段经过，是整个案例里最能说明这一点的一段。

+
原文的经过。
  • 能拆开时，并行很容易。失败的测试有很多个、彼此不同时，每个 agent 各挑一个去修。测试通过率到 99% 之后，每个 agent 各自去让一个不同的小型开源项目通过编译，例如 SQLite、Redis、Lua。
  • 拆不开时，并行没有用。开始编译 Linux 内核时，agent 卡住了。内核不像测试集那样由几百个互相独立的测试组成，它是一整个大任务。每个 agent 都碰到同一个 bug，各自修掉，然后互相覆盖对方的修改。作者的原话是：跑 16 个 agent 没有帮助，因为每一个都卡在同一个任务上。
  • 办法是把大任务拆开。作者拿 GCC 当作已知正确的编译器来对照：随机挑大部分内核文件用 GCC 编译，只有剩下的文件用 Claude 写的编译器编译。内核能跑，说明问题不在剩下的这一批文件里；不能跑，就再缩小范围。这样每个 agent 可以在不同的文件上修不同的 bug，并行恢复了。原文补充说，这一步做完之后，还要再找出那些单独编译没问题、放在一起才出错的文件组合。

这段经过和第一部分的证据说的是同一件事：agent 的数量帮不上忙，决定并行有没有用的是工作能不能拆成互不依赖的几块。这里更进一步的一点是，能不能拆开有时可以由人来创造，办法是换一种检验方式。

六条经验

从这个案例可以总结出六条经验。下表左列是经验，右列是原文里对应的做法。

六条里有四条（1、2、4、5）讲的都是 agent 周围的环境：测试、反馈、记录。第 2 条也算在里面，因为内核那一次的办法是换一套检验方式。作者自己也说，他大部分的精力花在设计 agent 周围的环境上，好让 agent 在没有人的情况下自己弄清方向。

这个案例没有说明什么

这个案例做成了一个很大的项目，容易被当作多 agent 有效的证明。下面五点说的是它的限度，前三点取自原文，后两点是对照这一讲前面的标准得出的。

  • 成品有明显的局限。它还不能直接替代真正的编译器。开启全部优化后生成的代码，效率还不如关闭全部优化的 GCC。它没有自己的汇编器和链接器，启动 Linux 需要的 16 位 x86 部分也要调用 GCC。
  • 到了能力的边界。作者说这个编译器已经接近模型能力的极限，新功能和 bug 修复经常弄坏已有的功能。
  • 测试通过不等于做完了。作者在结尾说，自主运行的系统很容易让人看到测试通过就以为完成了，而实际上很少如此。
  • 没有和单 agent 比。第一部分建议先做单 agent 基线并测量收益，单 agent 基线指先只用一个 agent 把任务做好，当作比较的基准。这个案例没有这样的对照，所以它说明的是「这样做能做成」，说明不了「这样做比一个 agent 更好」。
  • 用的通信方式是最简单的一种。只有共享的文件，相当于一块没有格式、没有订阅的留言板。第三部分讲的共用对话、交接、把 agent 当工具用和 A2A 协议，这里都没有用到。所以这个案例说明不了那些方式好不好。
