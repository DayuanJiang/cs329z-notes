一句话的结论

用多个 agent 有得有失：付出协调的成本，换来并行、专门化和更集中的上下文。工作能拆开时，这样做更可能划算；工作互相牵连得紧时，协调的成本更容易把好处抵消掉。划不划算，最后要和只用一个 agent 的做法比过才知道。后面讲的编排、通信和协调，都是在想办法把协调的成本降下来。

这里的「能拆开」可以归纳成两层意思：各块不改同一份东西，做的过程中也不需要对方的中间结果。两者都是程度上的，共享和依赖越少，协调的成本越低。第一部分有具体的对照。

下面四个例子支持这个结论。前两个是论文里的实验结果，第三个是一个项目里的经过，第四个是 Anthropic 研究文章里的判断，原文没有给数据。第一部分展开讲前两个，后两个分别在案例页和第三部分。

五个问题

设计多 agent 系统要考虑三件事：编排、通信、协调。在这之前要先回答要不要用，在这之后要知道会怎样失败。把它们排成五个问题。

第二个和第四个问题容易混。编排定的是团队的结构，协调管的是每一件具体的事，两者可以分开变。同样没有 orchestrator，C 编译器的案例有认领机制，CooperBench 只给了分开的工作区和发消息的工具，分工靠 agent 自己商量。第四部分的开头有一张对照表。

案例页用一个真实的项目把五个问题走了一遍：16 个 agent 写出一个能编译 Linux 内核的 C 编译器。它没有 orchestrator，agent 之间只通过 Git 仓库里的文件互通消息，再加一套测试。

读第五个问题里对多 agent 不利的结果，要记住它们的条件。有单 agent 对照的两组实验是 Kim 等人的架构对比和 CooperBench，最多用到 9 个 agent，用的是 2025 年的模型和当时的运行框架（包在模型外面、负责提示词和工具的那层程序）。前沿实验室的系统已经到约一万个同时运行的 agent，小规模上的结论能不能推到那里，目前没有公开的对照数据。细节在第五部分。
