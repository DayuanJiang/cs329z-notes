一句话的结论

用多个 agent 是一笔交易：付出协调的成本，换来并行、专门化和更集中的上下文。工作能拆开时，这笔交易更可能划算；工作互相牵连得紧时，协调的成本更容易把好处抵消掉。划不划算，最后要和只用一个 agent 的做法比过才知道。后面讲的编排、通信和协调，都是在想办法把协调的成本降下来。

这里的「能拆开」有两层意思：各块不改同一份东西，做的过程中也不需要对方的中间结果。第一部分有具体的对照。

这个结论有四处证据，前两处来自讲义引用的论文，后两处来自讲义引用的两篇 Anthropic 文章的原文。

整条线：五个问题

讲义说设计多 agent 系统要考虑三件事：编排、通信、协调。在这之前要先回答要不要用，在这之后要知道会怎样失败。把它们排成五个问题。

第二个和第四个问题容易混。编排定的是团队的结构，协调管的是每一件具体的事，两者可以分开变。同样没有 orchestrator，C 编译器的案例有认领机制，CooperBench 什么都没提供，结果差得很远。第四部分的开头有一张对照表。

案例页用一个真实的项目把五个问题走了一遍：16 个 agent 写出一个能编译 Linux 内核的 C 编译器。它没有 orchestrator，agent 之间只通过 Git 仓库里的文件互通消息，再加一套测试。
