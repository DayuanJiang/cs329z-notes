先看结论

用多个 agent 有得有失：付出协调的成本，换来并行、专门化和更集中的上下文。工作能拆开时，这样做更可能划算；工作互相牵连得紧时，协调的成本更容易把好处抵消掉。划不划算，最后要和只用一个 agent 的做法比过才知道。决定用多个 agent 之后，有三件事要设计：编排（谁分派任务）、通信（谁看到什么）和协调（每件事归谁、谁先谁后），后面各用一个部分来讲。

这一讲分成五个部分和一个案例页，第一部分讲要不要用多个 agent，各部分的内容见后面的「按部分阅读」一节。下面先说明这段结论里的三个词。

专门化指的是各个 agent 按自己的职责用不同的指令、模型和工具，工具是 agent 可以调用的外部功能，例如搜索网页或运行代码。更集中的上下文指的是每个 agent 只拿到和自己任务有关的信息，上下文是模型这一次能读到的全部内容。

协调的成本在这段结论里泛指用多个 agent 要付出的代价。第一部分把这些代价列成五个坏处：第一个是派任务、发消息、合并结果花掉的时间和 token，token 是模型处理文字的最小单位，另外四个是信息丢失、动作冲突、错误传播和工程复杂度。第一部分列这五个坏处时，把第一个叫作「协调的成本」。那一页的总结和建议里，这个词和这里一样泛指五个坏处。第四部分的名字「协调」范围更窄，只指每件事归谁、谁先谁后。

第一部分还列了第四样好处，探索面更广。它有前提：各个 agent 要拿到不同的任务或上下文。所以这段结论里没有写它。

这里的「能拆开」可以归纳成两个条件：各块不改同一份东西，做的过程中也不需要对方的中间结果。两个条件都可以满足得多一些或少一些，共享和依赖越少，协调的成本越低。第一部分有具体的对照。

下面四个例子里，前三个直接支持这个结论。第四个是一个判断，说的是工作拆开之后怎样交给对方：交出去的请求，输入和输出都定义清楚时，合作的效率高。

四个例子的性质不同。前两个是论文里的实验结果，其中 CooperBench 是一个协作编程评测，让两个 agent 各实现一个功能，再把两份改动合并。第三个是一个项目里的经过：16 个 agent 合写一个 C 编译器，这一讲把这个项目叫作 C 编译器案例，专门用一页来讲它，这一页叫案例页。第四个是 Anthropic 研究文章里的判断，原文没有给数据。第一部分展开讲前两个，后两个分别在案例页和第三部分。

五个问题

这一讲把设计多 agent 系统要考虑的事归成三件：编排、通信、协调。在这之前要先回答要不要用，在这之后要知道会怎样失败，合起来是下表的五个问题。验证不在这三件事里，第五部分把它当作第四件事来讲。

第二个和第四个问题容易混。编排定的是团队的结构，协调管的是每一件具体的事，编排相同时，协调的做法可以不同。C 编译器案例和 CooperBench 都没有 orchestrator，协调靠的东西却不同。C 编译器案例靠认领文件，agent 动手前先往共享的仓库里写一个文件，登记这个任务归自己。CooperBench 事先给两个 agent 各分配了一个功能，另外只给了分开的工作区和一个用来互发消息的沟通工具。两个功能要改的代码有重叠或互相依赖，这部分代码谁改哪里，靠 agent 自己商量。第四部分的开头有一张对照表。

案例页用一个真实的项目对照这五个问题：16 个 agent 写出一个能编译 Linux 内核的 C 编译器。它没有 orchestrator，agent 之间只通过 Git 仓库里的文件互通消息，做得对不对由一套测试来检验。编排、通信、协调三个问题，它都有具体的做法。对应「会怎样失败」这个问题的，是它的一段卡住的经过：16 个 agent 卡在同一个 bug 上，说明了并行什么时候没有用。第一个问题它回答不了，因为这个项目没有和单 agent 比过。

这一讲里对多 agent 不利的结果，读的时候要记住它们的条件：实验的规模不大，测的是当时的模型和当时的运行框架。运行框架是包在模型外面、负责提示词和工具的那层程序。Kim 等人的论文用的是 2025 年的模型，CooperBench 测的是 GPT-5 和 Claude Sonnet 4.5 这一代。有单 agent 对照的两组实验是 Kim 等人 2026 年的论文对四种编排方式的比较和 CooperBench，最多用到 9 个 agent。

规模大得多的系统已经有了。OpenAI 用 agent 解过一道数学难题，叫 Navier-Stokes 问题。它为此运行的系统把 agent 分成小组，得出解答的那一组约有 1 万个同时运行的 agent。OpenAI 属于前沿实验室，也就是训练最强模型的那几家公司。小规模上的结论能不能推广到一万个 agent 的规模，目前没有公开的对照数据。细节在第五部分。

按部分阅读

第一部分要不要用多个 agent

先划清单 agent 和多 agent 的分界，再说多 agent 换来什么、付出什么，然后用三处证据说明什么时候划算，归纳出「能拆开」的两个条件，最后给出什么时候用哪一种的判断标准。

 第二部分编排：谁分派任务，谁做决定

两个选择分出四种方式。这一部分先分清「去中心」的两种意思。去中心方式也叫 swarm，这个词平时还泛指一大群一起工作的 agent，两种用法也在这里分清。然后讲每种方式的代价，哪种适合哪种任务，实测的成本，最后讲按任务动态组队的 DyLAN。

 第三部分通信：谁看到什么

通信有四种方式：把 agent 当工具用、交接、共用一条对话、留言板。交接指一个 agent 把整场对话交给另一个 agent 接着做，共用一条对话指一组 agent 在同一个群里发言。这一部分还讲没人批准就出现的留言板，搭建时常遇到的三个问题，以及 A2A 协议。A2A 协议规定不同系统里的 agent 怎样互相发现、发任务、交回结果。

 第四部分协调：每件事归谁，谁先谁后

系统可以提供三样东西：任务台账、分开的工作区、共享记忆。共享记忆是各个 agent 都能读到的、关于以前做过什么的记录。这一部分还讲 agent 自己商量出来的三种做法。

 第五部分失败：哪里会出问题

先讲失败怎样分类，再讲协调的代价、想法趋同和目标冲突，然后说明读这些结果时要记住的条件，最后讲验证，以及主要的失败各有什么针对它的做法。

 案例16 个 agent 写出一个 C 编译器

案例页先讲这个案例怎么编排、协调和通信，各个 agent 的职责怎样分，再讲并行什么时候失灵，然后总结六条经验，最后说明这个案例没有说明什么。

容易想当然的几件事

这一节列出六个关于多 agent 系统的简化说法，说明每一个不能照字面理解的地方。六个说法都漏掉了条件或细节，其中第一个和实测的数据对不上。这张表适合读完各部分之后再看，表里的说法和例子在各部分里都有交代，出处和细节在最后一列指向的页面里。

表里会用到四种编排方式的名字。它们按两个选择来分：有没有一个统管全局的 agent（orchestrator），其余的 agent（worker）之间能不能直接交流。直接交流指信息不经过 orchestrator 就到了别的 agent 那里，互发消息和读写同一块留言板或共享文件都算。两样都没有的是独立方式，只有 orchestrator 的是集中方式，只有直接交流的是去中心方式，两样都有的是混合方式。
