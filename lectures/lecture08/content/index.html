一句话的结论

用多个 agent 有得有失：付出协调的成本，换来并行、专门化和更集中的上下文。工作能拆开时，这样做更可能划算；工作互相牵连得紧时，协调的成本更容易把好处抵消掉。划不划算，最后要和只用一个 agent 的做法比过才知道。后面讲的编排、通信和协调三部分，都是在想办法把这笔成本降下来。

这段话里有三个词需要说明。协调的成本指的是派任务、发消息、合并结果花掉的时间和 token。专门化指的是各个 agent 按自己的职责用不同的指令、模型和工具。更集中的上下文指的是每个 agent 只拿到和自己任务有关的信息。第一部分还列了第四样好处，探索面更广。它有前提：各个 agent 要拿到不同的任务或上下文。所以这句结论里没有写它。

这里的「能拆开」可以归纳成两层意思：各块不改同一份东西，做的过程中也不需要对方的中间结果。两者都是程度上的，共享和依赖越少，协调的成本越低。第一部分有具体的对照。

下面四个例子里，前三个直接支持这个结论。第四个说的是工作拆开之后怎样交给对方：交出去的请求，输入和输出都定义清楚时，合作得有效率。

四个例子的性质不同。前两个是论文里的实验结果，其中 CooperBench 是一个协作编程评测，让两个 agent 各实现一个功能，再把两份改动合并。第三个是一个项目里的经过。第四个是 Anthropic 研究文章里的判断，原文没有给数据。第一部分展开讲前两个，后两个分别在案例页和第三部分。

五个问题

设计多 agent 系统要考虑三件事：编排、通信、协调。在这之前要先回答要不要用，在这之后要知道会怎样失败。把它们排成五个问题。

第二个和第四个问题容易混。编排定的是团队的结构，协调管的是每一件具体的事，两者可以分开变。C 编译器案例和 CooperBench 都没有 orchestrator，协调的做法却不同。C 编译器案例有认领机制，agent 动手前先在共享的仓库里登记这个任务归自己。CooperBench 只给了分开的工作区和发消息的工具，分工靠 agent 自己商量。第四部分的开头有一张对照表。

案例页用一个真实的项目把五个问题走了一遍：16 个 agent 写出一个能编译 Linux 内核的 C 编译器。它没有 orchestrator，agent 之间只通过 Git 仓库里的文件互通消息，再加一套测试。

这一讲里对多 agent 不利的结果，读的时候要记住它们的条件：实验的规模不大，用的是 2025 年的模型和当时的运行框架。运行框架是包在模型外面、负责提示词和工具的那层程序。有单 agent 对照的两组实验是 Kim 等人 2026 年的论文对几种架构的比较和 CooperBench，最多用到 9 个 agent。

前沿实验室的系统已经到约一万个同时运行的 agent。小规模上的结论能不能推到那里，目前没有公开的对照数据。细节在第五部分。

按部分阅读

第一部分要不要用多个 agent

先划清单 agent 和多 agent 的分界，再说多 agent 换来什么、付出什么，然后用三处证据说明什么时候划算，最后给出什么时候用哪一种的判断标准。

 第二部分编排：谁分派任务，谁做决定

两个选择分出四种方式。这一部分先分清「去中心」的两种意思。去中心方式也叫 swarm，这个词平时还泛指一大群一起工作的 agent，两种用法也在这里分清。然后讲每种方式的代价，哪种适合哪种任务，实测的成本，最后讲按任务动态组队的 DyLAN。

 第三部分通信：谁看到什么

通信有四种方式：把 agent 当工具用、交接、共用一条对话、留言板。这一部分还讲没人批准就出现的留言板，搭建时常遇到的三个问题，以及 A2A 协议。A2A 协议规定不同系统里的 agent 怎样互相发现、发任务、交回结果。

 第四部分协调：每件事归谁，谁先谁后

系统可以提供三样东西：任务台账、分开的工作区、共享记忆。这一部分还讲 agent 自己商量出来的三种做法。

 第五部分失败：哪里会出问题

先讲失败怎样分类，再讲协调的代价、想法趋同和目标冲突，然后说明这些结果能说明到哪一步，最后讲验证，以及每种失败对应哪一项设计。

容易想当然的几件事

这一节列出六句关于多 agent 系统的一句话概括，说明每一句不能照字面理解的地方。六句都漏掉了条件或细节，其中第一句和实测的数据对不上。这张表适合读完各部分之后再看，表里的说法和例子在各部分里都有交代，出处和细节在最后一列指向的页面里。

表里会用到四种编排方式的名字。它们按两个选择来分：有没有一个统管全局的 agent（orchestrator），其余的 agent（worker）之间直接交流不交流。两样都没有的是独立方式，只有 orchestrator 的是集中方式，只有直接交流的是去中心方式，两样都有的是混合方式。
