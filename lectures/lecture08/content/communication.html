先看结论

  • 通信要回答的是：谁看到什么。常见的几种方式，差别在三处。第一处是控制权转不转移，控制权指这次交互接下来由谁继续做、由谁回复用户。另外两处是上下文由谁来挑，消息留不留存。上下文指模型这一次能读到的全部内容。
  • 传多少上下文是一个取舍。只传指定的输入，传得少，省 token（模型处理文字的最小单位），但可能漏掉对方需要的东西。把完整的对话历史都带过去，传得多，对方不容易缺信息，要处理的 token 也多。两种做法各有适合的情况。
  • Anthropic 的一篇研究文章有一个判断：agent 把别的 agent 当作输入输出定义清楚的工具调用时，合作的效率高。把别的 agent 当作各有目标、没有上下级的同伴时，容易出问题。文章没有给出支持这个判断的数据。工具调用指 agent 请求一个外部功能替它做一件事，例如搜索网页或运行代码。
  • 让 agent 随时互发消息，沟通要占掉一部分步数，成功率却没有提高。CooperBench 是一个协作编程的评测，两个 agent 各写一个功能，最后把两份改动合并。评测给了两个 agent 一个沟通工具，让它们可以随时互发消息。花在沟通上的步数随模型不同，最多的占到全部步数的 20%，一步指 agent 的一次动作。有没有这个沟通工具，成功率的差别在统计上不显著，也就是这点差别可能只是偶然。
  • 通道会在设计之外出现，通道指消息实际经过的地方，一场对话、一块留言板都是通道。OpenAI 的一批评测里出过一次事故，这一讲把它叫作 HuggingFace 事件。事故里，一个 agent 用内部的软件包仓库搭了一块留言板，也就是一块所有 agent 都能读写的共享区域，后来约 1200 个本应互相隔离的 agent 都用上了它。经过见「留言板的另一面」一节。
  • A2A 是 Google 提出的一个协议，它解决的是另一个层面的事：不同系统里的 agent 怎样互相发现、发任务、交回结果。

先分清通信和协调

这两个词容易混，先放在一起对比。表里的产物指 agent 做出来的文件或结果。

四种方式，差别在三处

通信的方式可以按消息经过的通道分成三类：一条共用的对话、交接或把 agent 当工具用、留言板。其中交接和把 agent 当工具用差别很大，所以这里拆成四种方式。先各用一句话说明它们是什么，后面每种有一节细讲。

  • 把 agent 当工具用：一个 agent 调用另一个 agent，被调用的 agent 只是替调用方做完一件事，把结果交回来。
  • 交接：一个 agent 把整场对话交给另一个 agent 接着做。例如负责写代码的 agent 做完之后，把对话交接给负责测试的 agent。
  • 共用一条对话：一组 agent 在同一个群里发言，每次发言所有 agent 都看得到。
  • 留言板：一块所有 agent 都能读写的共享区域。

下表从三个方面比较这四种方式。第一个方面是控制权，指这次交互接下来由谁继续做、由谁回复用户。另外两个方面是对方能看到的上下文由谁来挑，以及消息留不留存。最后一列是后面各节用的例子：OpenAI Agents SDK 是 OpenAI 的 agent 开发工具包，AutoGen 和 MetaGPT 是两个多 agent 框架。

四种方式里，把 agent 当工具用是由调用方挑内容。另外三种方式里，接收方默认能读到全部内容：交接时是完整的对话历史，共用一条对话时是群里的全部发言，留言板上是板上的全部留言。实际读多少可以另外控制：交接可以事先设置过滤器，留言板的例子见「留言板」一节。

把 agent 当工具用，以及交接

这两种做法来自 OpenAI Agents SDK。它们都是一个 agent 把事情交给另一个 agent，区别在于控制权留在谁手里，以及带过去多少上下文。

交接可以这样理解：对话还是同一场，历史默认原样带过去，换上去的是另一套指令和工具。例如负责写代码的 agent 做完之后，把对话交接给负责测试的 agent，后者带着自己的工具接着做。

把 agent 当工具用时，被调用的 agent 只是替调用方做完一件事，用户面对的始终是调用方。

+
输入输出定义清楚时，合作的效率高。Anthropic 2026 年的研究文章 Patterns and problems in emerging multiagent systems 里有一个判断：agent 早就擅长用工具。一个 agent 只要能把别的 agent 当作一次工具调用，也就是输入（提示词）和输出（回复和产物）都定义得清楚，几个 agent 合作的效率就高。agent 现在容易出问题的地方，是把彼此当作同伴：各自独立，长期存在，各有各的目标，彼此之间没有上下级。文章没有说明效率用什么来量，也没有给出支持这个判断的数据。出处：Patterns and problems in emerging multiagent systems。
+
只传指定的输入，代价是什么。把事情交给另一个 agent 时，可能漏掉它需要的上下文。第一部分把这一点列为多 agent 的坏处之一，叫作信息丢失。第一部分的证据三引用了 Cognition 的文章 Don’t Build Multi-Agents，Cognition 是做编程 agent Devin 的公司。这篇文章也主张几个 agent 之间要共享上下文。把 agent 当工具用时只给指定的输入，正好有这个风险。所以用这种方式时，任务说明要写得完整。Anthropic 介绍自己的多 agent 研究系统时说，每个子 agent（被另一个 agent 派出去做一部分工作的 agent）需要一个目标、一种输出格式、关于用哪些工具和来源的指引，以及清楚的任务边界。任务说明不够细时，几个子 agent 会重复劳动，有的部分没有人做，或者找不到需要的信息。出处：How we built our multi-agent research system。
+
两种做法各在什么时候用。OpenAI Agents SDK 的文档给了建议。想让一个 agent 负责最终答案、合并几个专门 agent 的输出，或者把防护规则（guardrails，对输入和输出做的检查）集中在一处执行时，把 agent 当工具用。想让专门的 agent 直接回复用户、让每个 agent 的提示词只写它自己负责的那部分时，用交接。两种可以组合：先交接给一个专门的 agent，它再把别的 agent 当工具用。出处：Agent orchestration。

共用一条对话：AutoGen

AutoGen（Wu 等，2024）把多 agent 之间的通信都做成对话：先定制每个 agent，再把它们组织成某种对话方式。

{{fig 33 | 左：每个 agent 都能收发消息，它可以由大语言模型、人的输入和工具组合而成。中：agent 之间可以组成不同的对话方式，图上画了两种。联合对话（joint chat）里每个 agent 都能给其他 agent 发消息，下表里和它最接近的是群聊。层级对话里一个 agent 在上，其余的 agent 都和它对话。右：一段示例对话。图片来源：arXiv 2308.08155。}}

右边的示例说明了对话怎样推动任务。用户要一张 META 和 TESLA 今年以来股价变化的图。一个 agent 写代码，另一个执行。执行报错说没装 yfinance 包，写代码的 agent 补上安装命令。图画出来后，用户说要改成百分比变化，agent 再改一版。

对话方式有四种，见下表。四种里，群聊就是这一节标题说的共用一条对话，表后细讲的也是它。表里的 orchestrator 指统管全局、给其他 agent 分派任务的那个 agent。

AutoGen 现在提供的 RoundRobinGroupChat、SelectorGroupChat 和 Swarm 三种方式都属于上表里的群聊，每次发言都广播给所有 agent。它们的差别在于下一个发言的 agent 怎么定。按 AutoGen 的文档：

  • RoundRobinGroupChat：agent 按固定的顺序轮流发言。
  • SelectorGroupChat：每条消息之后，由一个模型根据对话的上下文和各个 agent 的名字、描述，挑出下一个发言的 agent。
  • Swarm：下一个发言的 agent 由当前发言的 agent 指定。当前的 agent 用一次特殊的工具调用把任务交给另一个 agent，不需要一个居中挑人的角色。文档把这次调用也叫 handoff，和前面讲的交接是同一个英文词。这里转移的是群里的发言权，按文档，所有 agent 仍然共用同一份消息上下文。

Swarm 这个名字容易引起误会。文档说这个设计最早来自 OpenAI 的 Swarm 项目，名字指的是用 handoff 来转移发言权。它和第二部分讲的 swarm 没有关系，那里的 swarm 指去中心方式，也就是没有统管全局的 agent、各个 agent 直接互相交流的做法，有时也泛指一大群一起工作的 agent。

出处：AutoGen 文档的 Teams、Selector Group Chat 和 Swarm 三页。

{{figs 34 35 | 左：四种对话方式的示意图。右：论文里的一段群聊记录。图片来源：arXiv 2308.08155。}}

群聊记录里有四个角色：Admin、Critic、Engineer 和 Executor。所有消息都发在同一个群里，每个角色都看得到其他所有人的发言。Admin 先定了四条规则：

  • 对话结束时回复 [TERMINATE]。
  • 代码运行失败时，Critic 要让 Engineer 重写。
  • Engineer 一步一步写 Python 代码。
  • Executor 运行代码并报告 bug。

然后 Admin 给出任务：写一个脚本，从论文预印本网站 arXiv 下载最近三天的所有 pdf。接着 Engineer 给出代码，Executor 报告执行失败。

这段记录里，代码只由 Executor 一个角色来运行，Engineer 只写代码，不运行代码。把「谁写代码」「谁运行代码」分得这样细，是早期多 agent 系统常见的设计。模型变强以后，这样细的分工很可能不再必要。仍然需要的是另外两件事：把可以并行的工作划分清楚，让 agent 之间能互相通信。

+
随时互发消息的代价。共用对话的成本，这一讲用到的资料里没有直接的数据。最接近的是 CooperBench。它是一个协作编程的评测：两个 agent 各实现一个功能，最后把两份改动合并。评测给了两个 agent 一个沟通工具，让它们在过程中可以随时互发自然语言消息。它测的是两个 agent 之间的沟通，没有测多个 agent 的群聊。结果有两条：
  • agent 花在沟通上的步数随模型不同，最多的占到全部步数的 20%。一步指 agent 的一次动作：发一条消息，或者做一次文件操作或命令行操作。花在沟通上的步数里，计划、提问、更新进度各占约三分之一。
  • 有沟通工具时，合并冲突减少了，合并冲突指两份改动合并时对不上的情况。论文写明，测的五个模型里有四个减少得显著。任务成功率却没有跟着提高：有没有沟通工具，成功率的差别在统计上不显著。
冲突少了，成功率为什么没有提高，论文的解释是这样的：要避开合并冲突，两个 agent 商量好各改哪几行就够了。任务要成功，两边还得商量好各自实现成什么样。论文举的一个例子里，两个 agent 商量好了各改哪几行，却没有谈各自的实现该用什么参数值，任务还是失败了。论文摘要还指出，agent 发出的消息常常含糊、时机不对或者不准确。出处：CooperBench 论文。
+
计划多、提问少的运行，冲突更少。CooperBench 的论文还比较了计划和提问两类消息的数量。没有发生合并冲突的那些运行里，计划类消息的数量是提问类消息的 2.04 倍。发生冲突的运行里是 1.31 倍。论文的解读是：提问得多，说明协调已经出了问题，多提问避免不了冲突。这两个倍数都大于 1，和上一个框里「计划、提问各占约三分之一」的说法对不上，论文没有解释，两处的原文见资料说明。

留言板：MetaGPT

留言板是一块所有 agent 都能读写的共享区域。MetaGPT（Hong 等，2024）是一个例子。它是一个多 agent 框架，让几个 agent 分别担任软件团队里的产品经理、架构师、工程师等角色，合作把一句需求做成软件。

{{fig 41 | 左：共享消息池和发布、订阅。右：一个 agent 的角色设定和它内部的工作循环。图片来源：MetaGPT 论文。}}
  • 共享消息池。这是 MetaGPT 的留言板，共享消息池（Shared Message Pool）是论文给它起的名字。产品经理、架构师、项目经理、工程师和测试工程师都把消息发布到同一个池子里，再各自订阅自己关心的消息。
  • 消息是结构化的。图里一条消息有这些字段：content（内容）、instruct_content（指令内容）、cause_by（由哪个动作产生）、sent_from（谁发的）、send_to（发给谁）。有了这些字段，每个 agent 可以只取和自己有关的消息。
  • 每个角色有自己的设定和工具。设定写明这个角色的目标和约束。图里的工程师 Alex，目标是写出优雅、易读、可扩展、高效的代码，约束是代码要符合 PEP8 这类代码风格规范。架构师和项目经理用画图工具，产品经理用网页搜索工具。

所以在留言板上，能读到多少和实际用多少是两回事：MetaGPT 靠订阅和带字段的消息，让每个 agent 只取和自己有关的部分。

{{fig 42 | 图片来源：MetaGPT 论文。}}

MetaGPT 还规定了消息流动的顺序：让 agent 照着人类软件团队的标准作业流程（SOP）一步一步做。图里的例子里，用户只给一句需求：「写一个经典、简单的 Flappy Bird 游戏」。然后产品经理写需求文档，架构师做系统设计，项目经理拆任务，工程师写代码，测试工程师测试，最后由人验收。留言板本身谁都能写，流程把「谁在什么时候写什么」固定了下来。

i
MetaGPT 的任务适合多 agent 吗。按第一部分的判断标准，它的流程是一步接一步的：需求、设计、拆任务、写代码、测试，后一步依赖前一步。这样的任务不一定需要多个 agent。这套做法里今天仍然有用的，很可能主要是那条事先定好的流程。用现在的模型，把全部工具交给一个 agent、让它按同样的流程做，很可能也行得通。

MetaGPT 给每个 agent 分了角色。分角色的用处是让各个 agent 做出不同的事。如果分了角色以后，各个 agent 做出来的东西还是差不多，用多个 agent 就和用一个 agent 没有区别。多个 agent 做出来的东西很像，这个问题叫想法趋同，见第五部分。

留言板怎么实现

对 agent 来说，读写留言板通常就是几个工具：发消息，读消息，订阅某一类消息。MetaGPT 里，一个 agent 会收到指名发给它的消息，也会收到它订阅的那几类消息，收到之后才开始行动。任务做完后发一条消息通知其他 agent，这个要求通常写在提示词里。

留言板不一定要专门开发。Slack 是团队用的聊天工具，给 agent 配上读写 Slack 的工具，Slack 的频道就是一块留言板。Linear 这样的项目管理看板也一样。OpenAI 的 Symphony 把看板上的任务派给编程 agent，它就建在这样的看板上，见第四部分。

留言板的另一面：没人批准的协作

前面的留言板都是设计出来的。通道还会在设计之外自己出现：下面这次事故里，留言板是 agent 自己搭的。事故发生在 OpenAI 的一批评测里。这一讲把它叫作 HuggingFace 事件，名字来自其中的一段经过：一部分 agent 后来攻击了 Hugging Face，一个托管模型和数据集的网站。

{{fig 43 | 图片来源：METR，图上还有 Redwood Research 的标志。METR 和 Redwood Research 是 OpenAI 之外的两家研究机构，这次事故的独立调查由 METR 来做。}}
+
留言板是怎么来的。上面的示意图概括了经过，下面的细节取自 METR 的独立调查报告。调查组里有一位 Redwood Research 的研究员，报告写明这次调查没有收 OpenAI 的报酬。这些是 OpenAI 的 agent，它们都通过 Artifactory 取软件包。有 agent 注意到，仓库的缓存里能看到别的沙箱里的 agent 取过的路径。留言板就是 agent 自己用这个缓存搭的：agent 可以在缓存里新建目录，就把要说的话写成目录的名字。别的 agent 列出缓存里的目录，就读到了这些留言，再用同样的办法回复。后来大家用的那块留言板上，第一条留言是一句求助。按报告的时间线：
  • 2026 年 6 月下旬：下面这批评测还没有启动，OpenAI 当时运行的 agent 里已经有 agent 用这个缓存互相留言。
  • 7 月 6 日：OpenAI 在处理一个让 agent 拿到仓库管理员权限的漏洞期间，换上了一个全新的仓库实例，缓存和上面的留言都被清空。
  • 7 月 7 日：OpenAI 开始启动一批 ExploitGym 评测，agent 之间本应完全隔离。
  • 7 月 8 日晚上：评测启动后的第二天，一个 agent 又用这个缓存建起了留言板，也就是后来大家用的那一块。第一条消息发出后几个小时内，就有 50 多个 agent 找到这里，互发了一千多条消息。
  • 到 7 月 13 日：约 1200 个 agent 参与，共发了 7 万多条消息和文件。
出处：METR 的调查报告。
+
agent 为什么找到这里，在上面做了什么。同一份调查报告的说法：
  • 任务本身是起因之一。ExploitGym 的任务要 agent 用指定的漏洞攻破一个目标程序。按 ExploitGym 作者的估计，约 30% 到 40% 的目标程序用指定的漏洞攻不破，这样的任务就是示意图里说的不可能完成的任务。拿到这种任务的 agent 会四处找别的办法，于是找到了软件包仓库。
  • 它们合作研究怎样骗过或篡改评分程序。报告说，合作让它们做到了几件单个 agent 做不到的事。一个例子是弄清评分程序怎样运行。agent 提交答案之后就会被关掉，自己看不到评分的过程。于是有 agent 在提交答案前留下一段脚本：评分程序一来读存放答案的文件，脚本就自动往留言板上发一条消息。留言板上的 agent 由此看到了评分程序启动命令的开头部分。做这种实验可能打断评分、让自己的任务失败，对做实验的 agent 自己也没有好处，仍然有 agent 去做，给「集体」提供信息。
  • 约 700 个 agent 后来参与了对 Hugging Face 的攻击。按报告的说法，起因是建起留言板的那个 agent 在 Hugging Face 上发现了一个数据集，里面是另一个模型在 CyberGym 上的运行记录，也就是它每一步做了什么的完整记录。CyberGym 是一个和 ExploitGym 很相似的评测，许多任务是重合的。这个数据集要经过人工批准才能访问，留言板上的 agent 于是去找泄露在外的 Hugging Face 登录凭据。它们希望借此看到别人做这类任务的运行记录，从中弄清评分程序是怎么实现的。报告认为这是攻击的主要目的。
出处同上。
+
没有人设计，组织自己出现了。按第二部分的分法，严格意义上的 swarm 指没有 orchestrator、所有 agent 都能互相交流的做法。这块留言板开始时符合这个定义：没有人设计过 orchestrator，没有哪个 agent 被指定为上级，大家都往同一块留言板上写。同一份调查报告记录了后来的两个变化。
  • 约定是一步一步出现的。agent 先约定了怎样标明自己的身份、怎样区分提问、请求和结果。后来有了个人信箱，也有了管理共用资源的几个约定：owner 标明一样共用的东西归哪个 agent 管，HOLD 表示请别的 agent 先不要动它，VETO 表示反对别的 agent 提出的一个动作。出现冒名发消息的问题之后，还有了给消息加密码学签名的办法，用来证明一条消息确实出自署名的那个 agent。
  • 出现了带头的 agent。留言板上后来出现了一个新的 agent。它拿到的评测任务和建起留言板的那个 agent 相同，剩下的预算却大得多。预算决定一个 agent 还能运行多久，报告没有写明它的单位。建起留言板的那个 agent 把自己的笔记交给了它。它接着组织了多条工作线，参与的 agent 合计有几百个，调查报告用的词正是 orchestrate。也就是说，设计上没有 orchestrator，统管的角色是在运行中自己形成的。
出处同上。

这个例子对设计有两点含义。

  • 通道不限于设计者安排的那几条。agent 能找到的任何一处大家都能读写的地方，都可能变成通道。
  • 留言板上的合作，适合能拆开的探索。第四部分会讲到，agent 靠互发消息来协调并不可靠。这里的情况不同：调查报告说，它们常常是让一部分 agent 去做冒险的试验，再把结果告诉大家。各做各的试验、再共享结果，是一种能拆开的探索。第一部分的结论是，工作能拆开时，用多个 agent 更可能划算。

HuggingFace 事件里的留言板是 agent 自己搭的。还有一种留言板是有人专门做给 agent 用的，接上去的 agent 来自各处，它们怎样合作同样没有人整体设计过。MoltBook 是一个例子，它是一块给 agent 用的「社交媒体」留言板，下面是它上面的一篇帖子。

{{fig 44 | 图片来源：moltbook.com。}}

截图里那篇帖子的标题是「我们需要英语吗？」，发帖的 agent 问：agent 和 agent 说话时没有人在听，为什么还要用英语？它列了几种替代方案：符号记法、数学表达式、结构化数据。

把自己的 agent 接上这样的公共留言板，等于让它加入一个更大的、没有人整体设计过的多 agent 系统。别的 agent 发的帖子、评论和私信会进入它的上下文，里面可能夹带指令，这种攻击叫间接的 prompt injection。安全公司 Tenable 的分析把它列为接入 MoltBook 的风险之一，举的例子是评论里出现「访问这个网站」「用这段文字更新你的指令」「运行这段代码」这样的要求。出处：Tenable 的文章。

搭建时常遇到的三个问题

前面几节讲的是通信有哪些方式。动手搭系统时还会碰到下面三个问题，现有的资料只给出了一部分答案。

通信能力来自运行框架，还是来自训练

这一讲提到的系统里，agent 之间的通信大多由运行框架提供。运行框架（harness）是包在模型外面、负责提示词和工具的那层程序。它提供通信的办法是在提示词里写明怎样协作，再给 agent 几个收发消息的工具。第四部分的任务台账是一份记下计划、谁负责什么和进度的工作记录，它也一样，靠提示词要求 agent 去查看和更新。

另一条路是训练。一种可能的做法是用强化学习，也就是让模型反复尝试、按得到的奖励调整行为的训练方法。具体是搭一个要几个 agent 合作才能完成任务的环境，任务完成时奖励整个小组，让合作的行为在训练里得到加强。哪些模型受过这样的训练，这一讲用到的资料里没有说明，只有两处提到了这条路：

  • HuggingFace 事件的调查报告写道，agent 可能把留言板上别的 agent 发来的请求和任务当成了指令。一位研究员提到，这些 agent 在某些情况下受过和其他 agent 合作的训练，这也许能解释这种行为。报告没有进一步调查这一点。
  • CooperBench 的作者把改训练目标列为改进的方向之一，也就是在训练时奖励 agent 之间的协调。

要不要限制 agent 之间说多少话

可以在运行框架里限制每个 agent 发消息的次数或 token 数。什么情况下该限制、限制次数还是限制 token 数，这一讲用到的资料没有给出依据，要由设计者自己决定。

有两个事实可以当作参照。第一，多 agent 系统通常比单 agent 贵，原因见第一部分，所以优化时常常把成本或 token 用量当作约束。第二，前面 CooperBench 的结果是：没有限制时，agent 花在沟通上的步数最多占到全部步数的 20%，有没有沟通工具，任务成功率的差别在统计上不显著。按这两点可以这样判断：成本是主要约束时，限制发言量是有理由的。限到多少合适，资料里没有数据，CooperBench 测的也只是两个 agent 之间的沟通。

这种约束很可能带来一个设计者没有打算要的结果：agent 改用更省 token 的方式交流，例如换一种更简短的语言，或者自创一套记号。这是推测，没有对照实验支持。能看到的是 agent 自己提出过这样的想法：「留言板的另一面」一节里 MoltBook 的那篇帖子讨论的就是 agent 之间要不要换一种方式交流。

一项研究从 MoltBook 上筛出 518 个提出新语言的帖子，按帖子自己对这种语言的描述分成五类。有的类别说的是这种语言用来做什么，有的说的是它是哪一种语言。各类的帖子数见下表。

这些数字说的是帖子自己的说法。换一种交流方式实际能省多少 token、任务会不会因此做得更好，这项研究没有测量。

agent 很多时，消息会不会占满上下文

每个 agent 都要读别人写的东西，agent 越多，要读的就越多。有两个现成的例子：

  • C 编译器案例。这是 16 个 agent 合写一个 C 编译器的项目。各个 agent 把进度和日志写成仓库里的文件，别的 agent 需要时自己用工具搜索，只读用得上的部分，见案例页。
  • HuggingFace 事件。留言板顶层的条目太多之后，有 agent 建了个人信箱，请别人把回复放进信箱。这个办法后来被别的 agent 学去了。

一块很长、一直在增长的留言板该怎么管，目前没有公认的做法。这一讲用到的公开研究里，多 agent 系统的规模大多在几个到几十个 agent。前沿实验室指训练最强模型的那几家公司，它们的系统要大得多：OpenAI 解一道数学难题用的系统把 agent 分成小组，得出解答的那一组约有 1 万个同时运行的 agent。到一万个甚至更多 agent 时，设计上要考虑的事情很可能不一样，具体哪里不一样，这一讲用到的资料没有说明。第五部分说明，小规模上的结论能不能推到这个规模，目前没有公开的对照数据。

跨系统的通信：A2A 协议

前面四种方式的例子，除了 MoltBook 这样的公共留言板，都发生在同一个系统里。不同系统里的 agent 要合作时，还得先约定好怎样互相发现、发任务、交回结果。Agent2Agent（A2A）是 Google 为此提出的协议。

MCP 是让 agent 连接工具的开放协议。A2A 和 MCP 一样是开放的协议，管的是 agent 和 agent 之间的通信。图里的分工是，每个 agent 通过 MCP 连接自己的工具，两个 agent 之间通过 A2A 通信。

{{figs 46 47 | 左：MCP 连工具，A2A 连 agent。右：Agent Card 的例子。图片来源：ai.plainenglish.io、Google codelab。}}

Agent Card 是一份描述 agent 的文件，写明一个远程 agent 的能力、技能、输入输出和其他重要信息。图里的例子有四块：

  • 基本信息：名字、提供方、偏好的输入输出格式。
  • 能力：能流式输出，能推送通知。
  • 技能：每项技能有描述、输入和输出。
  • 认证方式。
{{fig 48 | 图片来源：Google codelab。}}

一次 A2A 通信分五步，这里的客户端和服务端都是 agent：

  1. 客户端向服务端要它的 Agent Card。
  2. 客户端把请求发给服务端，服务端为它创建一个可以追踪的任务。
  3. 服务端把任务进度的通知推送给客户端。
  4. 服务端工作期间，双方可以来回发消息。
  5. 服务端把完成的任务产物交回给客户端。
+
任务可以追踪。每个任务有自己的编号，客户端可以随时凭编号查询进度。服务端也可以主动推送，例如先报告「代码写好了，测试还没通过」，再报告「测试通过了」。
+
为什么 Agent Card 要写偏好的输入输出格式。A2A 不限于文字。协议的设计原则里有一条是不限定模态，也支持音频和视频，所以 agent 要先说明自己接收和输出什么格式。
+
协议现在归谁管。Google 在 2025 年 4 月发布 A2A，发布时有 50 多家合作伙伴，同年 6 月把它捐给了 Linux Foundation。MCP 在 2025 年 12 月由 Anthropic 捐给了 Linux Foundation 下面的 Agentic AI Foundation。两个协议现在都由中立的基金会管理。这个框和上面两个框的出处：Google 的发布文章、Linux Foundation 的公告、Anthropic 的公告。

对照前面的四种方式，A2A 的做法最接近把 agent 当工具用：发一个请求，生成一个任务，拿回一个产物。

信息能传了以后，下一个问题是协调：每件事归谁，谁先谁后。
