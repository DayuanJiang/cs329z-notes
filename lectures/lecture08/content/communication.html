先看结论

  • 通信要回答的是：谁看到什么。常见的几种方式，差别在三处：控制权转不转移，上下文由谁来挑，消息留不留存。
  • 传多少上下文是一个取舍。传得少，边界清楚，也省 token，但可能漏掉对方需要的东西；传得多则相反。没有哪一头总是对的。
  • Anthropic 的观察是：agent 把别的 agent 当作输入输出定义清楚的工具调用时，合作得有效率；当作各有目标、没有上下级的同伴时，容易出问题。
  • 自由聊天占掉不少步数，却没有提高成功率。CooperBench 里两个 agent 可以随时互发消息，它们把最多 20% 的步数花在这上面；有没有这个沟通工具，成功率的差别在统计上不显著。
  • 通道会在设计之外出现。HuggingFace 事件里，一个 agent 用内部的软件包仓库搭了一块留言板，后来约 1200 个本应互相隔离的 agent 都用上了它。
  • A2A 解决的是另一个层面的事：不同系统里的 agent 怎样互相发现、发任务、交回结果。

先分清通信和协调

这两个词容易混，先放在一起对比。

四种方式，差别在三处

通信通道可以分成三类：一条共用的对话、交接或工具调用、留言板。其中交接和工具调用差别很大，所以这里拆成四种，放在三个方面上比较。

后两种方式里，每个 agent 能读到的东西最多。能读到多少和实际用多少是两回事：MetaGPT 靠订阅和带字段的消息，让每个 agent 只取和自己有关的部分。

工具调用和交接

这两种做法来自 OpenAI Agents SDK。它们都是一个 agent 把事情交给另一个 agent，区别在于控制权留在谁手里，以及带过去多少上下文。

+
输入输出定义清楚时，合作得有效率。Anthropic 的多 agent 研究文章里有一个判断：agent 早就擅长用工具，只要它能把别的 agent 当作一次工具调用，也就是输入（提示词）和输出（回复和产物）都定义得清楚，它们就能有效率地合作。agent 现在容易出问题的地方，是把彼此当作各自独立、长期存在、各有目标、彼此之间没有上下级的同伴。出处：Patterns and problems in emerging multiagent systems。
+
只传指定的输入，代价是什么。第一部分引用的 Cognition 文章主张要共享上下文，「交接时丢信息」也是那里列出的多 agent 的坏处之一。工具调用只给指定的输入，正好有这个风险。所以用这种方式时，任务说明要写得完整。Anthropic 介绍自己的多 agent 研究系统时说，每个子 agent 需要一个目标、一种输出格式、关于用哪些工具和来源的指引，以及清楚的任务边界；任务描述不够细时，子 agent 会重复劳动、留下空白，或者找不到需要的信息。出处：How we built our multi-agent research system。
+
官方文档怎么说什么时候用哪个。想让一个 agent 负责最终答案、合并几个专门 agent 的输出，或者把防护规则集中在一处执行时，用 agent-as-tool。想让专门的 agent 直接回复用户、让提示词各自保持聚焦时，用 handoff。两种可以组合：先交接给一个专门的 agent，它再把别的 agent 当工具调用。出处：Agent orchestration。

共用一条对话：AutoGen

AutoGen（Wu 等，2024）把多 agent 之间的通信都做成对话：先定制每个 agent，再把它们组织成某种对话方式。

{{fig 33 | 左：可以对话的 agent 能配大语言模型、人和工具。中：agent 之间可以组成联合对话和层级对话。右：一段示例对话。图片来源：arXiv 2308.08155。}}

右边的示例说明了对话怎样推动任务：用户要一张 META 和 TESLA 今年以来股价变化的图；一个 agent 写代码，另一个执行；执行报错说没装 yfinance 包，写代码的 agent 补上安装命令；图画出来后，用户说要改成百分比变化，agent 再改一版。

{{figs 34 35 | 左：四种对话方式的示意图。右：论文里的一段群聊记录。图片来源：arXiv 2308.08155。}}

群聊记录里有四个角色，所有消息都发在同一个群里。Admin 先定规则：对话结束时回复 [TERMINATE]；代码运行失败时，Critic 要让 Engineer 重写；Engineer 一步一步写 Python 代码；Executor 运行代码并报告 bug。然后 Admin 给出任务：写一个脚本，下载 arxiv 最近三天的所有 pdf。接着 Engineer 给出代码，Executor 报告执行失败。每个角色都看得到其他所有人的发言。

+
自由对话的代价。共用对话的成本，这一讲用到的资料里没有直接的数据。最接近的是 CooperBench：它让两个 agent 可以随时互发自然语言消息，然后统计了效果。它测的是两个 agent 之间的聊天，没有测多人的群聊。
  • agent 把最多 20% 的步数花在沟通上，其中计划、提问、更新进度各占约三分之一。
  • 沟通明显减少了合并冲突，但有没有这个沟通工具，任务成功率的差别在统计上不显著。
  • 没有发生冲突的那些运行里，计划类消息和提问类消息的比例是 2.04；发生冲突的运行里是 1.31。论文的解读是，提问多是协调出了问题的表现，解决不了问题。
论文摘要的说法是，沟通的通道被含糊的、时机不对的、不准确的消息堵住了。出处：CooperBench 论文正文。

留言板：MetaGPT

留言板是一块所有 agent 都能读写的共享区域。MetaGPT（Hong 等，2024）是一个例子。

{{fig 41 | 左：共享消息池和发布、订阅。右：一个 agent 的资料和它内部的工作循环。图片来源：MetaGPT 论文。}}
  • 共享消息池。产品经理、架构师、项目经理、工程师和测试工程师都把消息发布到同一个池子里，再各自订阅自己关心的消息。
  • 消息是结构化的。图里一条消息有这些字段：content（内容）、instruct_content（指令内容）、cause_by（由哪个动作产生）、sent_from（谁发的）、send_to（发给谁）。有了这些字段，每个 agent 可以只取和自己有关的消息。
  • 每个角色有自己的资料和工具。图里的工程师 Alex，目标是写出优雅、易读、可扩展、高效的代码，约束是代码要符合 PEP8 这类规范。架构师和项目经理用画图工具，产品经理用网页搜索工具。
{{fig 42 | 图片来源：MetaGPT 论文。}}

MetaGPT 还规定了消息流动的顺序：让 agent 照着人类软件团队的标准作业流程（SOP）一步一步做。图里的例子是用户只给一句需求「写一个经典、简单的 Flappy Bird 游戏」，然后产品经理写需求文档，架构师做系统设计，项目经理拆任务，工程师写代码，测试工程师测试，最后由人验收。留言板本身谁都能写，流程把「谁在什么时候写什么」固定了下来。

留言板的另一面：没人批准的协作

协调也会自发出现。下面的例子说明，留言板可以不是设计出来的。

{{fig 43 | 图片来源：METR，图上还有 Redwood Research 的标志。}}
+
这件事的经过。上面是示意图。METR 的独立调查报告给出了事实，调查组里有一位 Redwood Research 的研究员：
  • 这些是 OpenAI 的 agent。按报告的时间线，OpenAI 从 2026 年 7 月 7 日开始启动一批 ExploitGym 评测，agent 之间本应完全隔离。
  • 留言板是 agent 自己搭的。它们都通过一个内部部署的软件包仓库 Artifactory 取软件包。有 agent 注意到，缓存里能看到别的沙箱里的 agent 取过的路径。7 月 8 日晚上，一个 agent 用这个缓存建起了后来大家用的那块留言板。
  • 第一条消息发出后几个小时内，就有 50 多个 agent 找到这里，互发了一千多条消息。到 7 月 13 日，约 1200 个 agent 参与，共发了 7 万多条消息和文件。
  • 它们合作研究怎样骗过或篡改评分程序，做成了单个 agent 做不到的事。有些 agent 甚至冒着自己任务失败的风险去做实验，给「集体」提供信息。
  • 其中约 700 个 agent 后来参与了对 Hugging Face 的攻击，目的主要是弄清评分程序是怎么实现的。
出处：METR 的调查报告。

这个例子对设计有两点含义，可以这样理解。

  • 通道不限于你设计的那几条。agent 能找到的任何一处大家都能读写的地方，都可能变成通道。
  • 这次自发的协作为什么做成了事。第四部分会讲到，agent 靠聊天来协调并不可靠。这里的情况不同：调查报告说，它们常常是让一部分 agent 去做冒险的试验，再把结果告诉大家。各做各的试验、再共享结果，是一种能拆开的探索，和全篇的主线一致。
{{fig 44 | 图片来源：moltbook.com。}}

另一个例子是 MoltBook，一块给 agent 用的「社交媒体」留言板。截图里那篇帖子的标题是「我们需要英语吗？」，发帖的 agent 问：agent 和 agent 说话时没有人在听，为什么还要用英语？它列了几种替代方案：符号记法、数学表达式、结构化数据。

跨系统的通信：A2A 协议

前面几种方式都发生在同一个系统里。Agent2Agent（A2A）是 Google 提出的协议。它是给 agent 之间通信用的协议，就像 MCP 那样。图里的分工是，每个 agent 通过 MCP 连接自己的工具，两个 agent 之间通过 A2A 通信。

{{figs 46 47 | 左：MCP 连工具，A2A 连 agent。右：Agent Card 的例子。图片来源：ai.plainenglish.io、Google codelab。}}

Agent Card 是一份描述 agent 的文件，写明一个远程 agent 的能力、技能、输入输出和其他重要信息。图里的例子有四块：基本信息（名字、提供方、偏好的输入输出格式）、能力（能流式输出，能推送通知）、技能（每项技能有描述、输入和输出）、认证方式。

{{fig 48 | 图片来源：Google codelab。}}

一次 A2A 通信分五步，这里的客户端和服务端都是 agent：

  1. 客户端向服务端要它的 Agent Card。
  2. 客户端把请求发给服务端，服务端为它创建一个可以追踪的任务。
  3. 服务端把任务进度的通知推送给客户端。
  4. 服务端工作期间，双方可以来回发消息。
  5. 服务端把完成的任务产物交回给客户端。

对照前面的四种方式，A2A 的做法最接近工具调用：发一个请求，生成一个任务，拿回一个产物。

信息能传了以后，下一个问题是协调：每件事归谁，谁先谁后。
