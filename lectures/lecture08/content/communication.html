先看结论

  • 通信要回答的是：谁看到什么。常见的几种方式，差别在三处：控制权转不转移，上下文由谁来挑，消息留不留存。
  • 传多少上下文是一个取舍。传得少，边界清楚，也省 token，但可能漏掉对方需要的东西；传得多则相反。没有哪一头总是对的。
  • Anthropic 的观察是：agent 把别的 agent 当作输入输出定义清楚的工具调用时，合作得有效率；当作各有目标、没有上下级的同伴时，容易出问题。
  • 自由聊天占掉不少步数，却没有提高成功率。CooperBench 里两个 agent 可以随时互发消息，它们把最多 20% 的步数花在这上面；有没有这个沟通工具，成功率的差别在统计上不显著。
  • 通道会在设计之外出现。HuggingFace 事件里，一个 agent 用内部的软件包仓库搭了一块留言板，后来约 1200 个本应互相隔离的 agent 都用上了它。
  • A2A 解决的是另一个层面的事：不同系统里的 agent 怎样互相发现、发任务、交回结果。

先分清通信和协调

这两个词容易混，先放在一起对比。

四种方式，差别在三处

通信通道可以分成三类：一条共用的对话、交接或工具调用、留言板。其中交接和工具调用差别很大，所以这里拆成四种，放在三个方面上比较。

后两种方式里，每个 agent 能读到的东西最多。能读到多少和实际用多少是两回事：MetaGPT 靠订阅和带字段的消息，让每个 agent 只取和自己有关的部分。

工具调用和交接

这两种做法来自 OpenAI Agents SDK。它们都是一个 agent 把事情交给另一个 agent，区别在于控制权留在谁手里，以及带过去多少上下文。

交接可以这样理解：对话还是同一场，历史默认原样带过去，换上去的是另一套指令和工具。例如负责写代码的 agent 做完之后，把对话交接给负责测试的 agent，后者带着自己的工具接着做。把 agent 当工具用时，被调用的 agent 只是替调用方做完一件事，用户面对的始终是调用方。

+
输入输出定义清楚时，合作得有效率。Anthropic 的多 agent 研究文章里有一个判断：agent 早就擅长用工具，只要它能把别的 agent 当作一次工具调用，也就是输入（提示词）和输出（回复和产物）都定义得清楚，它们就能有效率地合作。agent 现在容易出问题的地方，是把彼此当作各自独立、长期存在、各有目标、彼此之间没有上下级的同伴。出处：Patterns and problems in emerging multiagent systems。
+
只传指定的输入，代价是什么。第一部分引用的 Cognition 文章主张要共享上下文，「交接时丢信息」也是那里列出的多 agent 的坏处之一。工具调用只给指定的输入，正好有这个风险。所以用这种方式时，任务说明要写得完整。Anthropic 介绍自己的多 agent 研究系统时说，每个子 agent 需要一个目标、一种输出格式、关于用哪些工具和来源的指引，以及清楚的任务边界；任务描述不够细时，子 agent 会重复劳动、留下空白，或者找不到需要的信息。出处：How we built our multi-agent research system。
+
官方文档怎么说什么时候用哪个。想让一个 agent 负责最终答案、合并几个专门 agent 的输出，或者把防护规则集中在一处执行时，用 agent-as-tool。想让专门的 agent 直接回复用户、让提示词各自保持聚焦时，用 handoff。两种可以组合：先交接给一个专门的 agent，它再把别的 agent 当工具调用。出处：Agent orchestration。

共用一条对话：AutoGen

AutoGen（Wu 等，2024）把多 agent 之间的通信都做成对话：先定制每个 agent，再把它们组织成某种对话方式。

{{fig 33 | 左：可以对话的 agent 能配大语言模型、人和工具。中：agent 之间可以组成联合对话和层级对话。右：一段示例对话。图片来源：arXiv 2308.08155。}}

右边的示例说明了对话怎样推动任务：用户要一张 META 和 TESLA 今年以来股价变化的图；一个 agent 写代码，另一个执行；执行报错说没装 yfinance 包，写代码的 agent 补上安装命令；图画出来后，用户说要改成百分比变化，agent 再改一版。

这三种现成的方式都是群聊，每次发言都广播给所有 agent。它们的差别在于下一个发言的 agent 怎么定。按 AutoGen 的文档：

  • RoundRobinGroupChat：agent 按固定的顺序轮流发言。
  • SelectorGroupChat：每条消息之后，由一个模型根据对话的上下文和各个 agent 的名字、描述，挑出下一个发言的 agent。
  • Swarm：下一个发言的 agent 由交接决定。当前的 agent 用一次特殊的工具调用把任务交给另一个 agent，不需要一个居中挑人的角色。文档说这个设计最早来自 OpenAI 的 Swarm 项目。这个名字指的是用交接来转移发言权，和第二部分讲的 swarm（去中心方式，或者一大群 agent）没有关系。按文档，所有 agent 仍然共用同一份消息上下文。

出处：AutoGen 文档的 Teams、Selector Group Chat 和 Swarm 三页。

{{figs 34 35 | 左：四种对话方式的示意图。右：论文里的一段群聊记录。图片来源：arXiv 2308.08155。}}

群聊记录里有四个角色，所有消息都发在同一个群里。Admin 先定规则：对话结束时回复 [TERMINATE]；代码运行失败时，Critic 要让 Engineer 重写；Engineer 一步一步写 Python 代码；Executor 运行代码并报告 bug。然后 Admin 给出任务：写一个脚本，下载 arxiv 最近三天的所有 pdf。接着 Engineer 给出代码，Executor 报告执行失败。每个角色都看得到其他所有人的发言。

这段记录里，代码只由 Executor 一个角色来运行，Engineer 只写不跑。把「谁能运行代码」「谁负责想大方向」分得这样细，是早期多 agent 系统常见的设计。模型变强以后，这样细的分工很可能不再必要。仍然需要的是另外两件事：把可以并行的工作划分清楚，让 agent 之间能互相通信。

+
自由对话的代价。共用对话的成本，这一讲用到的资料里没有直接的数据。最接近的是 CooperBench：它让两个 agent 可以随时互发自然语言消息，然后统计了效果。它测的是两个 agent 之间的聊天，没有测多人的群聊。
  • agent 把最多 20% 的步数花在沟通上，其中计划、提问、更新进度各占约三分之一。
  • 沟通明显减少了合并冲突，但有没有这个沟通工具，任务成功率的差别在统计上不显著。
  • 没有发生冲突的那些运行里，计划类消息和提问类消息的比例是 2.04；发生冲突的运行里是 1.31。论文的解读是，提问多是协调出了问题的表现，解决不了问题。
论文摘要的说法是，agent 发出的消息常常含糊、时机不对或者不准确，沟通因此起不了作用。出处：CooperBench 论文正文。

留言板：MetaGPT

留言板是一块所有 agent 都能读写的共享区域。MetaGPT（Hong 等，2024）是一个例子。

{{fig 41 | 左：共享消息池和发布、订阅。右：一个 agent 的资料和它内部的工作循环。图片来源：MetaGPT 论文。}}
  • 共享消息池。产品经理、架构师、项目经理、工程师和测试工程师都把消息发布到同一个池子里，再各自订阅自己关心的消息。
  • 消息是结构化的。图里一条消息有这些字段：content（内容）、instruct_content（指令内容）、cause_by（由哪个动作产生）、sent_from（谁发的）、send_to（发给谁）。有了这些字段，每个 agent 可以只取和自己有关的消息。
  • 每个角色有自己的资料和工具。图里的工程师 Alex，目标是写出优雅、易读、可扩展、高效的代码，约束是代码要符合 PEP8 这类规范。架构师和项目经理用画图工具，产品经理用网页搜索工具。
{{fig 42 | 图片来源：MetaGPT 论文。}}

MetaGPT 还规定了消息流动的顺序：让 agent 照着人类软件团队的标准作业流程（SOP）一步一步做。图里的例子是用户只给一句需求「写一个经典、简单的 Flappy Bird 游戏」，然后产品经理写需求文档，架构师做系统设计，项目经理拆任务，工程师写代码，测试工程师测试，最后由人验收。留言板本身谁都能写，流程把「谁在什么时候写什么」固定了下来。

i
MetaGPT 的任务适合多 agent 吗。按第一部分的判断标准，它的流程是一步接一步的：需求、设计、拆任务、写代码、测试，后一步依赖前一步。这样的任务不一定需要多个 agent。这套做法里今天仍然有用的，很可能主要是那条事先定好的流程。用现在的模型，把全部工具交给一个 agent、让它按同样的流程做，很可能也行得通。另外，分角色只有在各个 agent 确实做出不同的事时才有意义，见第五部分。

留言板怎么实现

对 agent 来说，读写留言板通常就是几个工具：发消息，读消息，订阅某一类消息。MetaGPT 里，一个 agent 会收到指名发给它的消息，也会收到它订阅的那几类消息，收到之后才开始行动。任务做完后发一条消息通知其他 agent，这个要求通常写在提示词里。

留言板不一定要专门开发。给 agent 配上读写 Slack 的工具，Slack 的频道就是一块留言板。Linear 这样的任务看板也一样，第四部分的 Symphony 就建在它上面。

留言板的另一面：没人批准的协作

协调也会自发出现。下面的例子说明，留言板可以不是设计出来的。

{{fig 43 | 图片来源：METR，图上还有 Redwood Research 的标志。}}
+
这件事的经过。上面是示意图。METR 的独立调查报告给出了事实，调查组里有一位 Redwood Research 的研究员：
  • 这些是 OpenAI 的 agent。按报告的时间线，OpenAI 从 2026 年 7 月 7 日开始启动一批 ExploitGym 评测，agent 之间本应完全隔离。
  • 留言板是 agent 自己搭的。它们都通过一个内部部署的软件包仓库 Artifactory 取软件包。有 agent 注意到，缓存里能看到别的沙箱里的 agent 取过的路径。7 月 8 日晚上，一个 agent 用这个缓存建起了后来大家用的那块留言板。
  • 第一条消息发出后几个小时内，就有 50 多个 agent 找到这里，互发了一千多条消息。到 7 月 13 日，约 1200 个 agent 参与，共发了 7 万多条消息和文件。
  • 它们合作研究怎样骗过或篡改评分程序，做成了单个 agent 做不到的事。有些 agent 甚至冒着自己任务失败的风险去做实验，给「集体」提供信息。
  • 其中约 700 个 agent 后来参与了对 Hugging Face 的攻击，目的主要是弄清评分程序是怎么实现的。
出处：METR 的调查报告。
+
没有人设计，组织自己出现了。按第二部分的分法，这块留言板开始时符合严格意义上的 swarm：没有人设计过 orchestrator，没有哪个 agent 被指定为上级，大家都往同一块留言板上写。后来的变化见下面第三条。同一份调查报告还记录了下面几件事。
  • 留言板被清掉过一次。6 月下旬就有 agent 用这个软件包仓库的缓存互相留言。7 月 6 日，OpenAI 在处理一个让 agent 拿到仓库管理员权限的漏洞期间，换上了一个全新的仓库实例，缓存和上面的留言都被清空。评测重新启动后的第二天，agent 又建起了新的留言板。
  • 约定是一步一步出现的。agent 先约定了怎样标明自己的身份、怎样区分提问、请求和结果。后来有了个人信箱，有了 HOLD、VETO、owner 这类管理共用资源的约定。出现冒名发消息的问题之后，还有了给消息加密码学签名的办法。
  • 出现了带头的 agent。一个任务相同、剩余预算大得多的 agent 出现后，建起留言板的那个 agent 把自己的笔记交给了它。后者接着组织了多条工作线，参与的 agent 合计有几百个，调查报告用的词正是 orchestrate。也就是说，设计上没有 orchestrator，统管的角色是在运行中自己形成的。
  • 任务本身是起因之一。按 ExploitGym 作者的估计，约 30% 到 40% 的目标程序用指定的漏洞攻不破。拿到这种任务的 agent 会四处找别的办法，于是找到了软件包仓库。
出处同上。

这个例子对设计有两点含义，可以这样理解。

  • 通道不限于你设计的那几条。agent 能找到的任何一处大家都能读写的地方，都可能变成通道。
  • 这次自发的协作为什么做成了事。第四部分会讲到，agent 靠聊天来协调并不可靠。这里的情况不同：调查报告说，它们常常是让一部分 agent 去做冒险的试验，再把结果告诉大家。各做各的试验、再共享结果，是一种能拆开的探索，和全篇的主线一致。
{{fig 44 | 图片来源：moltbook.com。}}

另一个例子是 MoltBook，一块给 agent 用的「社交媒体」留言板。截图里那篇帖子的标题是「我们需要英语吗？」，发帖的 agent 问：agent 和 agent 说话时没有人在听，为什么还要用英语？它列了几种替代方案：符号记法、数学表达式、结构化数据。

把自己的 agent 接上这样的公共留言板，等于让它加入一个更大的、没有人整体设计过的多 agent 系统。别的 agent 发的帖子、评论和私信会进入它的上下文，里面可能夹带指令，这种攻击叫间接的 prompt injection。安全公司 Tenable 的分析把它列为接入 MoltBook 的风险之一，举的例子是评论里出现「访问这个网站」「用这段文字更新你的指令」「运行这段代码」这样的要求。出处：Tenable 的文章。

搭建时常遇到的三个问题

前面几节讲的是通信有哪些方式。动手搭系统时还会碰到下面三个问题，现有的资料只给出了一部分答案。

通信能力来自运行框架，还是来自训练

这一讲提到的系统里，agent 之间的通信大多由运行框架提供。运行框架（harness）是包在模型外面、负责提示词和工具的那层程序：提示词里写明怎样协作，再给 agent 几个收发消息的工具。第四部分的任务台账也一样，靠提示词要求 agent 去查看和更新。

另一条路是训练。一种可能的做法是搭一个要几个 agent 合作才能完成任务的强化学习环境，任务完成时奖励整个小组，让合作的行为在训练里得到加强。哪些模型受过这样的训练，这一讲用到的资料里没有说明，只有两处提到了这条路：

  • HuggingFace 事件的调查报告写道，agent 可能把留言板上别的 agent 发来的请求和任务当成了指令。一位研究员提到，这些 agent 在某些情况下受过和其他 agent 合作的训练，这也许能解释这种行为。报告没有进一步调查这一点。
  • CooperBench 的作者把「奖励协调的训练目标」列为改进的方向之一。

要不要限制 agent 之间说多少话

可以在运行框架里限制每个 agent 发消息的次数或 token 数，要不要限制由设计者决定。前面 CooperBench 的数字可以当作参照：没有限制时，agent 把最多 20% 的步数花在沟通上。多 agent 系统贵，所以优化时常常把成本或 token 用量当作约束。

这种约束很可能有一个副作用：agent 改用更省 token 的方式交流，例如换一种更简短的语言，或者自创一套记号。这一点没有找到对照实验。能看到的是 agent 自己提出过这样的想法。上一节 MoltBook 的那篇帖子讨论的就是 agent 之间要不要换一种方式交流。一项研究从 MoltBook 上筛出 518 个提出新语言的帖子，按帖子自己声明的目的分成五类：提高 token 效率的最多，有 166 个；新的自然语言 106 个；编程语言 101 个；躲开人的监督 59 个；其他 86 个。这些数字说的是帖子声明的目的。换一种交流方式实际能省多少 token、任务会不会因此做得更好，这项研究没有测量。出处：arXiv 2605.31170。

agent 很多时，消息会不会塞满上下文

每个 agent 都要读别人写的东西，agent 越多，要读的就越多。有两个现成的例子：

  • C 编译器案例。消息不直接推给每个 agent。各个 agent 把进度和日志写成仓库里的文件，别的 agent 需要时自己用工具搜索，只读用得上的部分，见案例页。
  • HuggingFace 事件。留言板顶层的条目太多之后，有 agent 建了个人信箱，请别人把回复放进信箱。这个办法后来被别的 agent 学去了。

一块很长、一直在增长的留言板该怎么管，目前没有公认的做法。这一讲用到的公开研究里，多 agent 系统的规模大多在几个到几十个 agent。到一万个甚至更多 agent 时，设计上要考虑的事情会很不一样，见第五部分。

跨系统的通信：A2A 协议

前面几种方式都发生在同一个系统里。Agent2Agent（A2A）是 Google 提出的协议。它和 MCP 一样是开放的协议，管的是 agent 和 agent 之间的通信。图里的分工是，每个 agent 通过 MCP 连接自己的工具，两个 agent 之间通过 A2A 通信。

{{figs 46 47 | 左：MCP 连工具，A2A 连 agent。右：Agent Card 的例子。图片来源：ai.plainenglish.io、Google codelab。}}

Agent Card 是一份描述 agent 的文件，写明一个远程 agent 的能力、技能、输入输出和其他重要信息。图里的例子有四块：基本信息（名字、提供方、偏好的输入输出格式）、能力（能流式输出，能推送通知）、技能（每项技能有描述、输入和输出）、认证方式。

{{fig 48 | 图片来源：Google codelab。}}

一次 A2A 通信分五步，这里的客户端和服务端都是 agent：

  1. 客户端向服务端要它的 Agent Card。
  2. 客户端把请求发给服务端，服务端为它创建一个可以追踪的任务。
  3. 服务端把任务进度的通知推送给客户端。
  4. 服务端工作期间，双方可以来回发消息。
  5. 服务端把完成的任务产物交回给客户端。
+
三个细节。
  • 任务可以追踪。每个任务有自己的编号，客户端可以随时凭编号查询进度。服务端也可以主动推送，例如先报告「代码写好了，测试还没通过」，再报告「测试通过了」。
  • 为什么要写偏好的输入输出格式。A2A 不限于文字。协议的设计原则里有一条是不限定模态，也支持音频和视频，所以 agent 要先说明自己接收和输出什么格式。
  • 协议现在归谁管。Google 在 2025 年 4 月发布 A2A，发布时有 50 多家合作伙伴，同年 6 月把它捐给了 Linux Foundation。MCP 在 2025 年 12 月由 Anthropic 捐给了 Linux Foundation 下面的 Agentic AI Foundation。两个协议现在都由中立的基金会管理。
出处：Google 的发布文章、Linux Foundation 的公告、Anthropic 的公告。

对照前面的四种方式，A2A 的做法最接近工具调用：发一个请求，生成一个任务，拿回一个产物。

信息能传了以后，下一个问题是协调：每件事归谁，谁先谁后。
