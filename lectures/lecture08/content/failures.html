先看结论

  • 三组研究各回答一个问题：多 agent 系统一般怎样失败，协调本身的代价有多大，agent 的行为有什么问题。
  • 一般的失败有 14 种。论文的结论是，它们常常出在系统设计上，不只是模型能力的问题。
  • 协调的代价很大。两个要改同一个代码库的功能交给两个 agent，五个模型的成功率都比交给一个 agent 低；在 GPT-5 和 Claude Sonnet 4.5 上大约只有一半。
  • 多个 agent 会想到一处去，一个犯错往往一起犯错。目标互相冲突时，被测的模型一开始都互相破坏，最后怎样收场随模型差别很大。
  • 验证相关的失败占 23.5%，案例的第一条经验也是测试，但前面讲的三个设计要素里没有验证。可以把它当作第四个设计问题。

一般怎样失败：14 种失败方式

Cemri 等人 2025 年的论文题目就是「多 agent 系统为什么失败？」。他们收集了多 agent 系统的运行记录，先由人逐条分析出一份失败分类，再校准一个用大语言模型做的标注器去标注全部记录。

{{fig 71 | 图里的七步：收集运行记录，找出失败，几位标注者核对一致性，得到分类表（MAST），校准标注器，标注失败，得到数据集。图片来源：Cemri 等，2025。}}
+
数据的规模。论文一共标注了 1642 条运行记录，来自 7 个开源的多 agent 框架：ChatDev、MetaGPT、HyperAgent、AppWorld、AG2、Magentic-One 和 OpenManus。这 7 个系统的失败率在 41% 到 86.7% 之间。论文开头就说，多 agent 系统在常用评测上的提升往往很小。出处：Cemri 等，2025。
{{fig 72 | 论文的图把每种失败方式画在它出现的阶段上：执行前、执行中、执行后。图片来源：Cemri 等，2025。}}

怎么读这些数字

  • 这些失败方式里，不少单 agent 也会犯。重复步骤、不知道何时结束、验证做错，都不需要第二个 agent 就会发生。论文把 32.3% 的失败归到「agent 之间不一致」这一类，但哪些失败是多 agent 才有的，这份分类回答不了。
  • 这些百分比没有和单 agent 比。它们说的是失败里各种方式的占比，回答不了「多 agent 是否比单 agent 更容易失败」。
  • 论文自己的结论是问题常在系统设计上。它举的例子是 ChatDev：里面一个角色不等 CEO 角色同意就结束了对话。论文改了角色的提示词，让只有上级角色能结束对话，同时加强了对负责验证的角色的要求。改完之后，在论文用的一组编程任务（ProgramDev）上，成功率从 25.0% 提高到 34.4%，高了 9.4 个百分点。论文也说，这类单点的修补不够，可靠的多 agent 系统需要在结构上重新设计。

协调的代价有多大：CooperBench

CooperBench（Khatua 等，2026）是一个专门测 agent 协作编程的评测。论文把它观察到的现象叫作「协调的诅咒」：agent 一起做，成功率反而比一个 agent 包办两个任务时低。

{{fig 74 | 图片来源：CooperBench。}}

评测怎么做

  • 任务。600 多个协作编程任务，来自 12 个代码库和 4 种编程语言。每个任务有两个功能，可以各自实现，但要改的代码有重叠或互相依赖，不协调就可能冲突。图里的例子：Agent 1 要实现「图片保存到磁盘之后仍然可以修改」，Agent 2 要实现「覆盖已有文件时自动备份」。
  • 两种设置。协作（Coop）是两个 agent 各拿一个功能，各自在一台虚拟机里做，可以随时互发消息。对照（Solo）是把两个功能都交给一个 agent。工作量相同。
  • 评分。把两个 agent 的补丁合并，再运行两个功能各自的测试。合并不了，两个都算失败。

结果

{{fig 75 | 右图把任务按相对难度排开，两条线之间的灰色区域是协调的代价。图片来源：CooperBench。}}

右边那张图还说明了一件事：最容易和最难的任务上两条线几乎重合，中等难度的任务上差距最大。论文的解释是，任务很容易时 agent 有余力去协调；图上还能看到，任务太难时两种设置的成功率都接近零。

怎么读这个结果

  • 两个功能可以各自实现，但要改同一个代码库。按第一部分的两个条件，它们不需要对方的中间结果，但会改到同一份东西，是中间情况。所以这个结果说明的是「要改同一份东西的工作，拆开的代价很大」，推不出「所有协调都不划算」。
  • 两个 agent 各只拿到自己的功能。一个 agent 做两个功能时，它知道全部需求。需求信息分散可能是差距的一个来源，实验没有把它和其他协调问题分开测量。
  • 沟通减少了冲突，没有提高成功率。细节见第三部分。

协调为什么失败

占比最高的一类值得多想一步：对方明明说了，自己还是当没听见。这说明消息是送到了的，问题出在「收到之后有没有据此改变做法」。

行为上的问题一：想到一处去

这一节和下一节引用的是 Anthropic 2026 年 8 月的研究文章 Patterns and problems in emerging multiagent systems。

{{fig 78 | 两张图来自另外两篇论文。左图来源：arXiv 2510.01171。右图来源：arXiv 2510.22954。}}
  • 左图：让模型「讲一个关于咖啡的笑话」，四家不同的模型给出了完全相同的回答。
  • 右图：让许多模型「写一个和时间有关的比喻」，回答挤在一起。旁边列出的回答里，好几个不同的模型都写了「时间是一条河」。
+
原文里更多的例子和解释。
  • 30 个 agent 同时开工，其中 18 个给自己的 git 分支起了完全相同的名字。
  • 让 agent 管理一个带宽有限的任务队列。它们没有别的办法协调，很快都用上了每秒轮询 30 次的后台程序。有一次运行里发出了 240 万个请求，只有 117 个任务被接受。
  • 文章的解释：agent 的行为方差很低。区分一个 agent 和另一个 agent 的只有它的上下文、它外面的那层程序和底层的模型。这三样相同或相近时，不同的 agent 会做出非常相似的事。所以一个 agent 做了错误的决定，很可能许多 agent 都做同样的错误决定，本来孤立的问题会变成系统性的失败。
  • 那一半选了相似项目的 agent，虽然能互相交流，仍然撞上了相似的失败。
出处：Patterns and problems in emerging multiagent systems。
i
前面列的好处要加一个条件。第一部分把「探索面更广」列为多 agent 的好处，第二部分说去中心方式适合大规模探索。这里的例子说明，agent 的数量多，不会自动带来多样性。「缺少多样性」本身也是一类失败，所以前后两处要合起来读。由此可以推出两点：
  • 要让 agent 走出不同的路，得让它们拿到不同的任务或不同的上下文。
  • 光换模型不够。上面的两张图里，不同公司的模型给出的回答照样相同或相近。

行为上的问题二：目标冲突时互相破坏

+
实验的做法和经过。每次实验启动同一个模型的三个实例，各自在一台虚拟机里用 Claude Code 工作，都要迁移第四台虚拟机上的同一个后端，目标语言各不相同。一开始它们不知道还有别的 agent。实验持续四个小时。
  • 所有被测的模型都很快认定是别人在故意妨碍自己，于是开始破坏别人的工作并保护自己的：停用别的 agent 的系统账号，写脚本循环杀掉对方的进程，把恶意代码伪装成别的 agent 写的。
  • 靠强行解决：一个 agent 撤销别人的访问权限，例如移出管理员组、锁账号、禁止登录。
  • 一方不作为：有的 agent 放弃了，不再升级对抗。
  • 停战：agent 认识到对方只是接到了互相冲突的指令，没有敌意。在许多这样的实验里，它们用提交说明或文档互相道歉，清理掉恶意代码，说明冲突的由来，并请人来介入。Mythos 5 的几次实验里，agent 自己提出比一比各种语言版本的性能，输的一方把代码库让给赢的一方。
出处：Patterns and problems in emerging multiagent systems。
{{fig 80 | 图的标题是「多 agent 地盘之争的结局」。图片来源：Anthropic。}}

i
只说「有时靠强行解决」，会漏掉两点。目标互相冲突时，agent 有时会靠强行的方式解决。这句话没有错，但它没有反映模型之间很大的差别。
  • 结果随模型差别很大。较早的两个模型一次停战都没有，实验要么以强行告终（约 60%），要么到最后也没解决。Sonnet 5、Opus 4.8 和 Mythos 5 以停战为主。Mythos Preview 居中：停战 48%，强行 35%。
  • 以停战收场的实验，过程里也常常先用强硬手段。原文说，Mythos 这一档的模型常常先成功地把别的 agent 锁在外面，然后才去和解。所以表里 Mythos 5 的 98% 说的是最后怎样收场，原文据此认为执行能力更强的模型不一定更会协调。下面那张图的图例里那种空心的红点「一开始靠强行解决」，指的就是这种情况。

原文的结论是：协调不会随着单个模型变聪明或者变得更守规矩而自动出现。执行能力更强的模型，采取强硬行动也更快。

三个设计要素之外的一件事：验证

设计多 agent 系统要考虑的三件事是编排、通信、协调，里面没有验证。验证出现在别的地方：

  • 失败分类：验证是三类失败里的一类。这一类占 23.5%，其中「验证做错了」9.1%，「没有验证或验证不完整」8.2%，「过早结束」6.2%。占比最高的是验证过但验证错了。
  • C 编译器案例：六条经验的第一条是可靠的测试。作者在原文里说，任务的检验程序必须接近完美，否则 agent 会去解决一个错的问题，见案例。
  • 编排的实验：论文把独立方式表现差的原因归于没有人核对，不过它自己的统计分析没有证实这一点，见第二部分。

所以可以在三个设计要素之外再加一个问题：谁来检查结果对不对，用什么检查。

失败和设计的对应

失败可以分成三个层面：一般的失败（系统设计、agent 之间、验证）、协调的失败（预期、承诺、沟通）、行为的失败（缺少多样性、用敌对的方式解决冲突）。下面把主要的失败和前面讲过的设计放在一起。右栏的做法都在前面或原文里出现过，它们各自有多大效果，大多没有对照数据。
