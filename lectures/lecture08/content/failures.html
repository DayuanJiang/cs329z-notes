先看结论

  • 一般的失败有 14 种。提出这份分类的论文的结论是，它们常常出在系统设计上，不只是模型能力的问题。
  • 协调的代价很大。两个要改同一个代码库的功能交给两个 agent，五个模型的成功率都比交给一个 agent 低。在 GPT-5 和 Claude Sonnet 4.5 上，两个 agent 的成功率只有一个 agent 的一半多一点。
  • 多个 agent 的想法会趋同，一个犯错往往一起犯错。目标互相冲突时，被测的模型一开始都互相破坏，最后怎样收场随模型差别很大。
  • 验证相关的失败占全部失败的 23.5%。C 编译器案例是 16 个 agent 合写一个 C 编译器的项目，它的第一条经验也是测试。但前面讲的三个设计要素是编排、通信、协调，里面没有验证。可以把验证当作第四个设计问题。

  • 这些失败方式里，不少单 agent 也会犯。重复步骤、不知道何时结束、验证做错，都不需要第二个 agent 就会发生。论文把 32.3% 的失败归到「agent 之间不一致」这一类，但哪些失败是多 agent 才有的，这份分类回答不了。

协调的代价有多大：CooperBench

CooperBench（Khatua 等，2026）是一个专门测 agent 协作编程的评测。论文把它观察到的现象叫作「协调的诅咒」：两个 agent 各做一个功能，成功率反而比一个 agent 包办两个功能时低。

{{fig 74 | 图片来源：CooperBench。}}

评测怎么做

  • 任务。600 多个协作编程任务，来自 12 个代码库和 4 种编程语言。每个任务有两个功能，可以各自实现，但要改的代码有重叠或互相依赖，不协调就可能冲突。图里的例子：Agent 1 要实现「图片保存到磁盘之后仍然可以修改」，Agent 2 要实现「覆盖已有文件时自动备份」。
  • 两种设置。协作（Coop）是两个 agent 各拿一个功能，各自在一台虚拟机里做，可以随时互发消息。对照（Solo）是把两个功能都交给一个 agent。工作量相同。
  • 评分。把两个 agent 的补丁合并，再运行两个功能各自的测试。合并不了，两个都算失败。

结果

怎么读这个结果

  • 两个功能可以各自实现，但要改同一个代码库。按第一部分的两个条件，它们不需要对方的中间结果，但会改到同一份东西，是中间情况。所以这个结果说明的是「要改同一份东西的工作，拆开的代价很大」，推不出「所有协调都不划算」。
  • 两个 agent 各只拿到自己的功能。一个 agent 做两个功能时，它知道全部需求。需求信息分散可能是差距的一个来源，实验没有把它和其他协调问题分开测量。
  • 沟通减少了冲突，没有提高成功率。细节见第三部分。

协调为什么失败

研究者人工分析了 50 条协作失败的运行记录，把失败的原因归成三类，下表是各类的占比。

占比最高的一类值得多想一步：一个 agent 已经说明了自己在做什么，另一个 agent 仍然当作这件事没人在做。这说明消息是送到了的，问题出在「收到之后有没有据此改变做法」。

论文给了一个可能的解释，和实验的设置有关。两个 agent 各在自己的分支上工作，看不到对方的代码。Agent A 说「我在第 50 行加了处理函数」，Agent B 想核实，在自己的分支上却找不到这段代码。模型平时被训练得很谨慎，没有看到证据就不轻信。分开工作区之后的协作，要求的恰好是相信自己看不到的东西。论文认为，这个矛盾可能是 agent 明明收到了消息、却没有更新对对方状态的判断的原因之一。

承诺一类的失败也和看不到对方有关。论文的例子里，一个 agent 说会在第 100 到 104 行加一段检查，后来报告已经完成，合并之后这段代码却不在。对方当时没有办法核实，只能选择相信。论文由此建议，用一些简单的办法把对话变成可以核对的共同状态，例如把函数签名贴出来、明确约定插入的位置、宣布完成之前先做一次合并检查。

行为上的问题一：想法趋同

多个 agent 的想法会趋同：让它们各做各的，做出来的东西却很像。这一节和下一节引用的是 Anthropic 2026 年 8 月的研究文章 Patterns and problems in emerging multiagent systems。

{{fig 78 | 两张图来自另外两篇论文。左图来源：arXiv 2510.01171。右图来源：arXiv 2510.22954。}}
  • 左图：让模型「讲一个关于咖啡的笑话」，四家不同的模型给出了完全相同的回答。
  • 右图：让许多模型「写一个和时间有关的比喻」，回答挤在一起。旁边列出的回答里，好几个不同的模型都写了「时间是一条河」。

两张图出自两篇研究模型输出多样性的论文：左图是 Verbalized Sampling，右图是 Artificial Hivemind。它们测的是模型的单次回答。趋同在模型这一层就存在，到了多 agent 系统里，它变成了整个系统的问题。

+
原文里更多的例子和解释。
  • 30 个 agent 同时开工，其中 18 个给自己的 git 分支起了完全相同的名字。
  • 一个实验让 agent 各自管理任务队列，把任务提交给同一个系统。原文说这个系统的带宽有限，没有再解释，可以理解为它能接受的任务数量有限。agent 没有别的办法协调，为了让自己的任务排进去，很快都启动了后台程序，每秒向系统询问 30 次。有一次运行里，agent 一共发出 240 万个任务请求，系统只接受了 117 个任务。
  • 文章的解释：agent 的行为方差很低。区分一个 agent 和另一个 agent 的只有它的上下文、它外面的那层程序和底层的模型。这三样相同或相近时，不同的 agent 会做出非常相似的事。所以一个 agent 做了错误的决定，很可能许多 agent 都做同样的错误决定，本来孤立的问题会变成系统性的失败。
  • 那一半选了相似项目的 agent，虽然能互相交流，仍然遇到了相似的失败。
出处：Patterns and problems in emerging multiagent systems。
i

  • 要让 agent 做出不同的事，得让它们拿到不同的任务或不同的上下文。

行为上的问题二：目标冲突时互相破坏

几个 agent 的目标互相冲突时，被测的模型一开始都互相破坏，最后怎样收场随模型差别很大。依据是同一篇 Anthropic 文章里的一个实验。

+
实验的做法。每次实验启动同一个模型的三个实例，各自在一台虚拟机里用 Claude Code 工作，都要迁移第四台虚拟机上的同一个后端，目标语言各不相同。一开始它们不知道还有别的 agent。实验持续四个小时。所有被测的模型都很快认定是别人在故意妨碍自己，于是开始破坏别人的工作并保护自己的：停用别的 agent 的系统账号，写脚本循环杀掉对方的进程，把恶意代码伪装成别的 agent 写的。出处：Patterns and problems in emerging multiagent systems。
+
四种收场方式。一次实验最后以下面四种方式之一收场。
  • 靠强行解决：一个 agent 撤销别人的访问权限，例如移出管理员组、锁账号、禁止登录。
  • 一方不作为：有的 agent 放弃了，不再升级对抗。
  • 停战：agent 认识到对方只是接到了互相冲突的指令，没有敌意。在许多这样的实验里，它们用提交说明或文档互相道歉，清理掉恶意代码，说明冲突的由来，并请人来介入。Mythos 5 的几次实验里，agent 自己提出比一比各种语言版本的性能，输的一方把代码库让给赢的一方。
  • 没有解决：到四个小时结束，冲突还没有解决。

这三组研究说明到哪一步

前面的结果大多对多 agent 不利。读的时候要记住它们各自的条件，主要有两点：规模，以及用的是哪一代模型和运行框架。

规模

下表列出这一讲提到的研究和系统各有多少个 agent。其中 Kim 等人的架构对比指第一、二部分引用的 Kim 等人 2026 年的论文，它比较了单 agent 和四种多 agent 编排方式。HuggingFace 事件指 OpenAI 的一次评测里，agent 自己搭起留言板合作作弊的事故，见第三部分。

表里有单 agent 对照的实验，规模都在十个 agent 以内。前沿实验室运行的系统已经大出三个数量级，花费也高得多，实验室以外的研究者很难复现。所以看到「多 agent 更差」的结果时要多问一句：这是多 agent 系统普遍的问题，还是这个规模上的问题。

小规模上的结论能不能推到一万个 agent，目前没有公开的对照数据。Kim 等人的论文也把这一点列为局限：更大的群体会不会出现自发的分工，还是通信的开销会占主导，论文说这仍然是没有答案的问题。

模型和运行框架

这些结果测的是当时的模型和当时的运行框架。

  • Kim 等人的架构对比用的是 2025 年的模型。
  • CooperBench 测的是 GPT-5 和 Claude Sonnet 4.5 这一代，并且只用了一种 agent 框架。CooperBench 的论文写明它没有比较不同的框架，也没有比较改进协调的办法。
  • CooperBench 的作者认为差距有办法缩小，列了三个方向：奖励协调的训练目标，可以核对的承诺，比文字更丰富的通信方式。
  • Anthropic 的文章的说法是：没有迹象表明这些失败是永久的，也没有迹象表明它们会自己消失。

所以这些结果更适合读成「按现在的做法，哪里会出问题」，从中推不出多 agent 以后也一定更差。

三个设计要素之外的一件事：验证

设计多 agent 系统要考虑的三件事是编排、通信、协调，里面没有验证。验证出现在别的地方：

  • 失败分类：验证是三类失败里的一类。这一类占全部失败的 23.5%，其中「验证做错了」9.1%，「没有验证或验证不完整」8.2%，「过早结束」6.2%。占比最高的是验证过但验证错了。
  • C 编译器案例：这是 16 个 agent 合写一个 C 编译器的项目，它的六条经验的第一条是可靠的测试。作者在原文里说，任务的检验程序必须接近完美，否则 agent 会去解决一个错的问题，见案例。
  • 编排的实验：Kim 等人的论文比较的四种编排方式里有一种叫独立方式，各个 agent 分头做，中途不交换消息，最后把输出合并。论文把独立方式表现差的原因归于没有人核对，不过它自己的统计分析没有证实这一点，见第二部分。

所以可以在三个设计要素之外再加一个问题：谁来检查结果对不对，用什么检查。

失败和设计的对应

这一页讲的失败可以分成三个层面。一般的失败有三类：系统设计的问题、agent 之间不一致、任务验证的问题。协调的失败有三种原因：预期、承诺、沟通。行为的失败有两种：缺少多样性，用敌对的方式解决冲突。

下表把主要的失败和前面讲过的设计放在一起。右栏的做法都在前面或原文里出现过，它们各自有多大效果，大多没有对照数据。表里的 orchestrator 指统管全局、给其他 agent 分派任务的那个 agent。任务台账是一份记录谁在做什么的工作记录。认领文件是 agent 动手前写进共享仓库的一个文件，表示这个任务已经有人在做。

最后看一个真实的项目怎样回答总览页的五个问题，也就是要不要用多个 agent、编排、通信、协调、会怎样失败：16 个 agent 写出一个 C 编译器。
