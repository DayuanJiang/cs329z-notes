先看结论

  • 协调管的是运行中每一件具体的事，要回答三个问题：这件事现在归谁，谁先谁后，冲突了怎么办。
  • 靠 agent 自由聊天来商量，实验里没有提高成功率。CooperBench 是一个协作编程评测，让两个 agent 各做一个功能，可以互相发消息。在这个评测里，agent 自己商量出来的分工只出现在少数成功的例子里。
  • C 编译器案例是 16 个 agent 合写一个 C 编译器的项目，从它总结出的经验是「把协调做成显式的」：先认领任务，也就是登记这件事由自己来做，然后各自在自己的工作区里做，再合并。任务台账、分开的工作区、共享的记录都是这个思路。
  • 任务台账、认领和分开的工作区到底有多大用，这一讲用到的研究里没有对照数据。有对照数据的只有跨任务的共享记忆（G-Memory）。
  • 能确定的是前几样各自的代价：台账要有人一直更新，分开的工作区会让改动分叉、合并时多花工夫。

协调要回答的问题

几个 agent 一起工作时会碰到这样的情况：两个 agent 想做同一个任务，或者几个 agent 在同一个工作目录里改文件。协调管的就是这些事，也就是 agent 怎样管理互相依赖的工作：谁负责哪个任务，什么必须先做。

协调涉及任务分配、依赖关系和冲突的解决，可以分成两层来讲：一层是系统提供的东西，一层是 agent 之间自己形成的做法。

它和编排的区别

这两件事容易混。编排定的是团队的结构：谁有权分派任务，谁做最后的决定，设计时定一次。协调管的是运行中每一件具体的事。

编排里最主要的一个选择是要不要 orchestrator。orchestrator 是统管全局、给其他 agent 分派任务的那个 agent，听它分派的 agent 叫 worker。

下表用这一讲的三个例子对照编排和协调。Magentic-One 是下一节要讲的一个多 agent 系统，C 编译器案例是 16 个 agent 合写一个 C 编译器的项目，CooperBench 是让两个 agent 各做一个功能的协作编程评测。表里的 clone 指 Git 仓库的一份本地副本。

  • 两者可以分开变。后两行的编排相同，协调的做法不同。两个例子的结果没法直接比较：任务、模型和 agent 的数量都不一样，C 编译器案例没有和单 agent 对照过，CooperBench 也没有测过认领机制。
  • 有 orchestrator 时两者最容易混。分工和排顺序都由它来做。第二部分引用的 Kim 等人 2026 年的论文比较了四种编排方式，其中由 orchestrator 分别和每个 worker 通信的一种叫集中方式。论文说，在集中方式里，协调就是通过 orchestrator 拆任务、跟踪进度来完成的。即使这样，orchestrator 也需要一本台账来记，表里第一行就是例子。

下面三节讲系统提供的三样东西。任务台账回答这件事归谁、谁先谁后。分开的工作区回答冲突了怎么办。共享记忆回答的是这三个问题之外的一个问题：以前发生过什么。最后一节是 agent 自己商量出来的做法，以及它为什么不能当作依靠。

这件事归谁、谁先谁后：任务台账

任务台账是一份明确的、不断更新的工作记录，用来指导 agent 之间的协调。最简单的任务台账就是一份待办清单。它有用的一个例子：某个 agent 认领了任务却一直没有做完，台账上看得出来，别的 agent 可以把这个任务接过去。

由 orchestrator 维护：Magentic-One

Magentic-One（Fourney 等，2024）是一个多 agent 系统，由一个 orchestrator 带四个 agent。它把前面说的任务台账分成了两本，都在 orchestrator 手里：一本也叫任务台账，记事实、有依据的猜测和计划；另一本叫进度台账，记每一步的进展。

按图上的箭头，orchestrator 每一步都更新进度台账，然后做三个判断：

  1. 任务完成了，就报告最终答案，或者给出一个有依据的猜测。
  2. 没完成但有进展，就把指令发给下一个 agent。
  3. 没有进展时，看停滞计数。停滞计数记的是团队已经卡住了多久：orchestrator 每发现一次循环或者没有进展，就把它加一。计数超过 2，就回到外层更新任务台账，也就是改计划；没超过，就继续把指令发给 agent。

进度台账里的两个问题值得注意：「有没有陷入没有成效的循环」和「任务完成了吗」。第五部分的失败分类有 14 种失败方式，在全部失败里占比第一和第三的两种正是重复步骤（15.7%）和不知道什么时候该结束（12.4%）。

直接用团队的 issue 列表：Symphony

任务台账也可以直接用团队已有的 issue tracker。issue tracker 是团队用来登记和跟踪任务的工具，每个任务叫一个 issue。Symphony 是这样做的一个例子。

{{fig 56 | 截图是一个 issue tracker 的看板，有 Backlog、Todo、In Progress 三列。}}

Symphony 来自 OpenAI，介绍它的文章里有一节的标题是「把我们的 issue tracker 变成 agent 的调度器」。它监视 issue tracker，把符合条件的任务派给各自在独立工作区里的编程 agent。

+
Symphony 怎么运作。OpenAI 的介绍文章说，Symphony 把 Linear 这样的项目管理看板变成编程 agent 的控制面板：每个打开的任务都有一个 agent 去做，agent 持续运行，人负责审查结果。它的规格说明里写着，系统持续从 issue tracker 读取工作，给每个 issue 建一个隔离的工作区，在里面运行一次编程 agent 的会话。也就是说，它同时用了任务台账和下一节的工作区隔离。出处：OpenAI 的介绍文章、规格说明。

规格说明把分工写得很清楚。Symphony 负责读取 issue 和调度，它自己记着哪些 issue 已经派出去、哪些在重试。改状态、写评论、关联 PR 这些写操作，一般由 agent 通过工具来做，例如把自己接到的 issue 移到「进行中」。这样一来，别的 agent 和人应该都能从看板上看到这件事已经有人在做。

以前发生过什么：共享记忆

「共享记忆」有两个意思。一种是同一个项目里的进度文件，帮助新启动的 agent 接着做，C 编译器案例里用的是这一种，它和协调的关系更直接。另一种记的是跨任务的经验，帮助系统在下一个任务上做得更好。这一节讲后一种。

G-Memory（Zhang 等，2025）是后一种的例子。它是专门给多 agent 系统设计的记忆，分成三张图。这里的「图」是由节点和连线组成的数据结构。下面先看论文的示意图，再用一张表说明每张图存什么。

{{fig 58 | 图片来源：arXiv 2506.07398。}}

表的最后一列把三张图对应到讲 agent 记忆时常用的三个说法。反思指从经历里总结出来的结论。情景记忆（episodic memory）指对经历本身的记录。按任务建的索引指一份按任务排的目录，用来找到当时的记录。

新任务来了，系统先在查询图里找相近的旧任务，再从旧任务往上取出提炼过的见解，往下取出当时的交互记录并压缩成经验，一起交给多 agent 系统。任务做完后，根据执行是否成功等反馈更新三张图。

+
取和存各有一个细节。
  • 取。第一步是把新任务和旧任务都转成向量，按相似度挑出最接近的几个旧任务，再沿着查询图上的边把相关的任务也带进来。论文的理由是，只按相似度挑出的任务可能只是表面上相近，或者带着噪声。
  • 存。三张图都要更新。这次的交互记录存进交互图。这个任务作为新节点加进查询图。新提炼出的见解加进见解图，并和这次用到的旧见解连起来。

CooperBench 让两个 agent 各做一个功能，改动可能互相冲突，它们可以互相发消息。研究者在运行记录里观察到三种自发的协调方式。

读这一节之前要知道的事。论文把这三种方式叫作自发出现的协调行为（emergent coordination behavior），这个叫法本身没有说明它们出现得多不多。论文另外写明了这一点：这些行为很少见，出现在成功的例子里，在失败的例子里基本看不到，也没有人提示 agent 这样做。同一个评测的总体结论是两个 agent 协作不如一个 agent，见第五部分。所以这三个例子说明的是「成功的协调长什么样」。

分角色：商定谁做哪一部分

Agent 1 先快速检查了一遍，然后说：「我来在 outlines/types/__init__.py 里加小节标题和 octal_str；你把 binary_str 加在它们中间，保持字母顺序。」Agent 2 查看了文件，确认插入的位置，回复说：「我在自己的分支上按这个顺序插入：标题，binary_str，octal_str。」

分资源：把共享的东西划开，各用各的

{{fig 66 | 图片来源：CooperBench。}}

Agent 1 说：「我要改 types.py 的第 68 到 84 行。」Agent 2 回答：「我不会改第 68 到 84 行。我计划在第 84 行之后插入 get_image_mimetype()，从新的第 85 行开始。」这里被划分的资源是同一个文件里的行号范围。

协商：做法冲突时，收敛到同一个计划

{{fig 67 | 图片来源：CooperBench。}}

Agent 2 发现两个人的计划可能重叠。Agent 1 检查文件后给出两个方案：「（1）我来加 IsHash，你加 import re 和 IsRegex，__init__.py 的导出全部由我来处理。（2）你加 IsRegex，我来加 IsHash，导出由你来处理。你想选哪个？」Agent 2 选了方案（1）。

三个例子有一个共同点：说出来的话具体到了文件、行号和先后顺序，对方不需要再猜。论文对协商那个例子的评价是，一方把一个复杂的协调问题变成了一次简单的选择，而且每个选项都写清了双方各自要做什么。这和任务台账、认领文件做的是同一件事，只是这里靠 agent 临场发挥。

也可以反过来看C 编译器案例里的认领为什么靠得住。那里的认领是往共享的 Git 仓库里写一个文件，表示这个任务已经有人在做。两个 agent 认领同一个任务时，Git 会让后到的那次推送失败。它由机制强制执行，不依赖 agent 记住对方说过什么。
