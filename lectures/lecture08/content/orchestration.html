先看结论

  • 编排要做两个选择：要不要一个 agent 统管全局，其余的 agent 之间能不能直接交流。统管全局的 agent 叫 orchestrator，其余干活的 agent 叫 worker。两个选择组合出四种方式：独立、集中、去中心、混合。
  • 交流越多，开销越大。Kim 等人 2026 年的论文按通信开销换算：达到同样的成绩，四种方式的 token 用量是单 agent 的 1.6 到 6.2 倍。按实测的美元成本看有例外，独立方式在两家的模型上比单 agent 便宜。
  • 论文的实验里，只把各个 agent 的输出拼在一起、没人核对的独立方式，在论文六个评测里的五个上都是四种里最差的。
  • 哪种方式好取决于任务：能拆成并行分析的任务用集中方式最好，要边找边调整的任务用去中心方式稍好，一步接一步的任务四种都比单 agent 差。
  • 「去中心」这个词有两种意思。本页的数字测的是 agent 一轮一轮辩论。C 编译器案例是 16 个 agent 合写一个 C 编译器的项目，那里的 agent 各自在共享仓库里挑任务，是另一种做法。

两个选择，四种方式

编排定的是团队的结构：谁有权分派任务，谁做最后的决定。它在设计时定一次。它容易和第四部分的协调混在一起：协调管的是运行中每一件具体的事，现在归谁、谁先谁后、冲突了怎么办。

四种方式的差别只在两处：有没有一个统管全局的 agent，agent 之间有没有直接的交流。统管全局的 agent 叫 orchestrator，其余干活的 agent 叫 worker。下表把这两处摆成行和列，每一格是一种方式和它的一句定义。

四种方式各是什么样子

  • 独立。一个典型的用法是给每个 agent 指定一个角色，让它们各自看同一份材料。例如把一份产品方案同时交给「产品经理」和「工程师」两个 agent 审阅，各自从自己的角度提意见，最后一步从中挑选或合并。这种方式的局限是几个角度之间没有交流，一个 agent 的发现帮不到另一个。2023 年前后有不少多 agent 系统给 agent 指定角色，本页后面讲的 DyLAN 就是一个例子。
  • 集中。它和单 agent 派出并行的子任务很像，界线是模糊的。一个可用的区分是看 worker 拿到的任务有多大。单 agent 派出去的通常是很具体的小任务，主要的工作仍由它自己推进。多 agent 系统里，worker 拿到的可以是「让编译器跑得更快」这样的高层目标，怎么做由 worker 自己决定。
  • 去中心。共享的状态记录通常只是一份数据，不需要由某个 agent 来担任。它可以是一份待办清单，一个列着许多 bug 的仓库，或者一批没通过的测试，各个 agent 从里面领任务。agent 再派出子 agent 之后，谁在做什么很快就难以追踪。
  • 混合。实际的系统常常是前几种的混合：有一个统管的 orchestrator，worker 之间也互相发消息。
+
下一步由谁决定。四种方式讲的是 agent 之间的关系。OpenAI Agents SDK 的文档还区分了另一件事：流程可以交给模型自己决定，也可以写在代码里。交给模型更灵活，适合开放的任务；写在代码里，速度、成本和结果都更可预测。两者可以混着用。出处：Agent orchestration。

「去中心」的两种意思

后面三节的数字都来自 Kim 等人 2026 年的论文。读这些数字之前要先分清一件事：「去中心」对应两种很不一样的做法，论文测的只是其中一种。分不清的话，会把辩论的成绩当成 agent 自己领任务那种做法的成绩。下表把两种做法放在一起。

i
所以本页「去中心」一列的数字，测的都是辩论。它们不能直接用来判断C 编译器案例里那种做法的好坏。案例也不能套用「独立」一列的数字。论文实现的独立方式只把各个 agent 的输出拼在一起，没有任何核对。案例里的 agent 能读到别人的进度文件，结果由一套测试来核对，这两样论文实现的独立方式都没有。

swarm 这个词的宽窄两种用法

去中心方式也被叫作 swarm，这个词本身也有宽窄两种用法。严格的用法里，swarm 指没有 orchestrator、所有 agent 都能互相通信的去中心方式。平时说的 agent swarm 要宽得多，泛指一大群一起工作的 agent，里面可以有 orchestrator，按本页的分法常常属于混合方式。

每种方式的代价

这一节看四种方式各要多付多少代价。Kim 等人 2026 年的论文里有两张表：一张是实测的数字，一张用大 O 记号写增长的趋势。实测的数字更容易看懂，先看它。

下表有三列数字。通信开销看完成一个任务比单 agent 多用了多少轮，每 1000 token 的成功数看 token 用得有没有效率，错误放大系数看错误在运行过程中带来了多少额外的工作。三列的确切含义在表后。

三列数字各是什么意思：

  • 通信开销量的是完成一个任务用的轮数比单 agent 多出的比例，一轮是一次推理加回应。单 agent 是基准，所以是 0%。论文测到单 agent 平均用 7.2 轮，独立方式用 11.4 轮，比单 agent 多出 58%。混合方式用 44.3 轮，多出 515%。论文说这个指标相当于 token 的用量：达到同样的成绩，四种多 agent 方式的 token 用量是单 agent 的 1.6 到 6.2 倍。58% 对应 1.6 倍，515% 对应 6.2 倍。
  • 每 1000 token 的成功数是论文的 token 效率指标。论文没有写明它怎么算，所以 67.7 这样的数值只适合用来比较几种方式的相对高低。不管哪种多 agent 方式，这个指标都比单 agent 低，混合方式只有单 agent 的五分之一。
  • 错误放大系数也以单 agent 为基准，单 agent 记作 1.0。按论文的定义，它衡量 agent 之间的协调失误带来了多少额外的计算工作，是论文分析运行记录里的 token 估算出来的，论文没有给出算式。所以它量的是运行过程里多花的工作。独立方式的 17.2，论文的读法是错误被放大到了单 agent 的 17.2 倍。

错误放大系数量的是过程，最终答案错了多少要看另一个指标。论文另外定义了一个按任务算的错误放大系数：多 agent 方式没做对的任务所占的比例，除以单 agent 没做对的任务所占的比例。按那个指标，多 agent 方式大约是单 agent 的 1.1 到 1.3 倍。表里按运行记录估算的系数在 4 到 17 之间。论文说两个指标看的是错误的不同方面，所以数值差得很远。

独立方式的 agent 互不交流，谈不上协调失误，错误放大系数却最高。论文把 17.2 归因于错误没有人拦：独立方式没有任何核对的环节，单个 agent 的错误会原样进入合并后的输出。集中方式有 orchestrator 在合并之前核对，系数降到 4.4。

i
读错误放大系数时要注意两点。
  • 17.2 测的是论文实现的独立方式：输出直接拼接，没有任何核对。前面定义的独立方式里，汇总者会审阅、合并或挑选，那样的做法没有被测到。
  • 不要把 17.2 当作独立方式成绩差的原因来讲。论文的回归分析显示，把其他指标都考虑进去之后，这个系数对成绩的影响在统计上不显著，架构之间的成绩差别更多由效率和开销来解释。

大 O 记号的那张表

大 O 记号写的是数量随括号里的量增长的趋势，例如 O(nk) 表示增长得不比 n 乘 k 的某个固定倍数更快。表里用到六个字母：

  • k 是每个 agent 最多迭代的次数。
  • n 是 agent 的数量。
  • r 是 orchestrator 的轮数。
  • d 是辩论的轮数。
  • p 是同级之间通信的轮数。
  • m 是每一轮里同级之间请求的平均次数。

「串行的深度」「并行倍数」和「记忆的复杂度」三行，论文没有另外解释。按字面，串行的深度是必须依次完成的轮数，并行倍数是最多有几个 agent 同时工作，记忆的复杂度是系统要保存的上下文的量级。

这张表最值得看的是通信开销那一行，它和上面的实测数字对应得最直接。独立方式是常数 1，不随 agent 的数量增长。集中和去中心方式是轮数乘以 agent 的数量。混合方式在集中方式的基础上又多了同级通信的一项。这个顺序和实测的通信开销一致：独立最低，集中和去中心居中，混合最高。并行倍数一行，单 agent 是 1，四种多 agent 方式都是 agent 的数量 n，所以这一行在四种方式之间分不出高低。

哪种方式适合哪种任务

第一部分用这组数据说明多 agent 好不好取决于任务。这里按架构分开看。表里的数字是每种多 agent 方式的成绩相对单 agent 的变化：+81% 表示比单 agent 高 81%，−35% 表示比单 agent 低 35%。

还有一点四行都成立：独立方式在这四个评测上都是四种里最差的。

论文最新版本加了两个评测，结果一个相同，一个相反。编程评测 SWE-bench Verified 上也是独立方式最差，相对单 agent 的变化是 −14.9%。命令行任务评测 Terminal-Bench 上，独立方式比单 agent 略高，是 +1.7%，集中方式低了 19.2%。所以「独立方式最差」只在六个评测里的五个上成立。

论文实现的独立方式没有任何核对，这可能是原因之一。但论文自己的统计分析没有证实这一点，见上一节里读错误放大系数的第二点提醒。

关于成本，图上能读出三件事：

  • 三格里最贵的都是混合方式。
  • 去中心方式和集中方式的成本接近，谁更贵三格并不一致：OpenAI 那一格去中心便宜一点，Google 那一格集中便宜一点，Anthropic 那一格几乎一样。
  • 在 Google 和 Anthropic 两格里，独立方式比单 agent 还便宜。

四种多 agent 方式之间的成本顺序，和前面通信开销的顺序一致：独立最低，集中和去中心在中间，混合最高。独立方式在两格里比单 agent 还便宜，这一点通信开销解释不了，图上也看不出原因。

!
「单 agent 最便宜，swarm 最贵」和图对不上。容易想当然的排法是，成本从低到高依次是单 agent、有 orchestrator 的系统、swarm。图上有两处和它不符。第一处，最贵的混合方式有 orchestrator。swarm 按严格的用法指去中心方式，它的成本和有 orchestrator 的集中方式接近。只有按 swarm 宽的用法把混合方式也算进去，「swarm 最贵」才和图对得上，两种用法见前面的「去中心」的两种意思一节。第二处，单 agent 并不总是最便宜，有两格里独立方式更便宜。

图上还能看到，花得多不一定成绩高。在 OpenAI 和 Anthropic 两格里，最贵的混合方式和便宜得多的单 agent 成绩差不多。成本居中的方式有时成绩最高：OpenAI 那一格里是去中心方式。所以不能按成本的高低推断成绩。选哪种方式是成本和成绩之间的取舍，要在自己的任务上量过才知道。

团队也可以按任务动态决定：DyLAN

前面四种方式里，团队的组成是事先定好的。DyLAN（Liu 等，2023）让系统自己挑出该用哪些 agent。

{{fig 25 | 左半边是团队优化，右半边是解决任务。图片来源：arXiv 2310.02170。}}
  • 先在几个问题上试运行，给每个 agent 算一个重要性分数。试运行时 agent 一轮一轮地回答。算分分三步，论文把它们叫作传播、汇总和选择：
    1. 传播。每一轮里，每个 agent 给出自己的回答，同时给上一轮的各个回答打分，从 1 分到 5 分。一个 agent 打出的几个分数再换算成比例，加起来等于 1。
    2. 汇总。从最后一轮往回，一轮一轮算出每个回答的贡献。在推理和决策类的任务上，最后一轮里答案和大家一致的那几个回答平分全部贡献。再往前，一个回答的贡献这样算：下一轮每个回答的贡献，乘以它给这个回答打的分，再加起来。所以一个回答被下一轮贡献大的回答打的分越高，它的贡献越大。
    3. 选择。把每个 agent 在各轮的贡献加起来，就是它的重要性分数。分数最高的几个 agent 留下，组成团队。
  • 解决新任务时还能中途精简。用一个大语言模型给每个回答的用处打分，去掉用处小的 agent。三分之二的 agent 答案一致时提前停止。
{{figs 26 27 | 左：算重要性分数的三步（传播、汇总、选择）。右：解决新任务时中途去掉 agent。图片来源：arXiv 2310.02170。}}

DyLAN 建立在「给每个 agent 一个角色」的思路上，论文里候选的 agent 是医生、律师、程序员、数学家这样的角色。放在这里，是用它说明团队的组成可以由系统按任务来定。负责统筹的模型变强以后，这样专门的选人算法是否还有必要，目前没有定论。

论文在决策类任务上报告了结果。任务用的是 WebShop，它是一个购物网站环境，agent 要按顾客的一句要求找到对应的商品，论文取了其中 50 个测试环境。对照的方法里成功率最高的有两种。Reflexion 的做法是让 agent 反思前面的尝试之后再试。BOLAA 是另一种多 agent 方法。

也就是说，DyLAN 的成功率略高，调用次数和 Reflexion 相当，比 BOLAA 少。论文说明，调用次数主要统计的是解决任务的阶段，前面挑选团队那一步的开销没有算在里面。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • 每 1000 token 的成功数怎么算。Kim 等人论文的 Table 5 里，这个指标只有一行数字，行名是 Success/1K tokens。论文把它叫作 token 效率，全文没有找到它的算法。出处：Kim 等，2026。
  • 通信开销按什么算。Kim 等人的论文有一处把通信开销描述成每个任务里 agent 之间交换消息的次数，给出的算式用的是轮数：多 agent 方式的轮数减去单 agent 的轮数，再除以单 agent 的轮数。Table 5 里的数值和按轮数算出来的一致，本页按算式来解释。出处：Kim 等，2026。
  • 去中心方式最后怎样定出答案。Kim 等人论文的 Table 5 只有数字，没有写各种方式怎样合成最终答案。本页那张表里去中心方式的合成办法取自同一篇论文的 Table 2：辩论的轮数是事先定的，示意图上去中心一列标的是多数票（Majority Voting）。出处：Kim 等，2026。
