先看结论

  • 让模型用上工具有两个方向。一个是改模型去适应工具，其中第三部分和第四部分讲的 Toolformer、ToolkenGPT 和 Gorilla 这三种训练方法，每来一个新 API（应用程序接口，一个程序提供给别的程序调用的入口）就要再训练一次。另一个是改工具的描述方式，让任何模型在运行时读了描述就能用。实际通行的是后一个。
  • 后一个方向做出来的是标准接口，先后有三代。REST API（按网址用 HTTP 请求去读写资源的网络接口）的文档是写给人看的。函数调用（function calling）用 JSON Schema（一种描述 JSON 数据应该长什么样的格式）把每个工具描述给模型。MCP（Model Context Protocol，模型上下文协议）是一套协议，规定 AI 应用怎样向工具服务器取工具列表、发起调用。
  • AI 应用下面简称应用。工具服务器是提供工具的程序。一个工具服务器按 MCP 写一次，各种应用都能接。
  • 函数调用里，模型只输出工具名和参数。检查参数、真正执行、把结果交回模型，都由应用完成。
  • MCP 里最常用的两个请求是 tools/list（你有哪些工具）和 tools/call（用这些参数运行这个工具）。
  • 把已有的 REST API 包成 MCP 工具只要十来行代码。要另外想清楚的是权限：谁可以调用这个工具服务器上的工具，它又用什么身份去访问后面的 API。

为什么需要标准接口

第三部分和第四部分的方法都是从学习的角度出发：让模型把工具学进去。其中 Toolformer、ToolkenGPT 和 Gorilla 每新增一个工具就要再训练。这一部分的出发点是工程上好不好用：模型不动，改的是工具的描述方式，由此定下来的接口叫标准接口。下面的图和表对照这两个方向。表里的 Toolformer、ToolkenGPT、ToolLLM 和 Gorilla，是第三部分和第四部分讲的四种训练方法。

{{fig 47 | 左：改模型去适应工具。右：改工具的描述方式，让任何模型都能用。}}

这是一个思路上的转变：适配的工作从模型这一边移到了工具这一边。原来是训练模型去适应工具，现在是每个工具用一种通用的格式说明自己叫什么、能做什么、要什么参数。模型只要能读懂这样的描述，就能用它从没见过的工具。

这个转变有一个前提：模型本身要足够强，读一段描述就能正确地写出调用。这种「读描述、写调用」的能力也是训练出来的，提供函数调用功能的模型，一般专门为这件事训练过。这种训练不针对哪一批工具，所以新增工具时不用再训练，具体的工具放到运行时再给。

三代接口

标准接口先后有三代，差别在工具的描述是写给谁的。REST 的描述是写给人看的文档。函数调用的描述是写给模型读的 JSON Schema。MCP 是 AI 应用和工具服务器之间的一套协议，一个工具服务器写一次，各种 AI 应用都能接。AI 应用是包在模型外面、把工具交给模型的那个程序，后面简称应用。工具服务器是提供工具的程序。

下面的图和表从五个方面对照这三代，后面三节各讲一代。这里的「代」指出现的先后。三种接口现在同时在用，它们怎样配合，见后面的 MCP 一节。

{{fig 48 | 从左到右三代：面向人的 REST API，面向模型的函数调用，面向各种 AI 应用和各种工具的 MCP。图上把最后一栏标作 Ecosystem-facing，指的就是这些应用和工具合在一起。每一栏下面是一个例子。}}

第一代：REST API，通过 HTTP 提供的工具

API（应用程序接口）是一个程序提供给别的程序调用的入口。REST 是一种设计网络 API 的常见风格：每样资源有一个网址，用 HTTP 请求去读或者改它。互联网上大量的服务都以这种形式开放。

{{fig 49 | 上：一次请求和它的响应。下：四种常用的请求方式。}}

图里的例子是查斯坦福的天气。

  • 请求。GET https://api.weather.com/v1/current?city=Stanford。GET 表示读取，后面是网址，问号后面的 city=Stanford 是参数。
  • 响应。状态码 200 表示成功，后面是一段 JSON（一种用键值对表示数据的文本格式）：华氏 74 度，晴。
  • 四种请求方式。GET 读取，POST 新建，PUT 更新，DELETE 删除。

局限。模型必须事先知道网址、参数的名字和返回数据的结构。这些信息散在给人读的文档里，每个服务的写法都不一样，每个服务怎样验证调用方的身份也各不相同。模型得读懂文档，再自己写出完整的请求，网址和参数名一个字都不能错。

i
REST 也可以有机器能读的描述。上一节的三代对照图把 REST 标为「没有机器可读的约定」（no machine-readable contract），指的是 REST 这种风格本身不要求有，所以不是每个服务都提供。实际上很多服务会另外发布一份 OpenAPI 规范，这是一个用 JSON 或 YAML 写的文件，列出所有网址、参数和返回的结构。YAML 是和 JSON 用途相近的另一种文本格式。本页后面的例子正是靠这份文件，把一个 REST API 自动转成了 MCP 工具。

第二代：函数调用，用 JSON Schema 描述工具

函数调用把工具描述成一种结构化的格式，直接交给模型。

这个功能由 OpenAI 在 2023 年 6 月随 gpt-4-0613 和 gpt-3.5-turbo-0613 两个模型推出，之后各家模型厂商都提供了类似的功能。OpenAI 当时的说明是：这两个模型经过微调（在已经训练好的模型上用新数据继续训练），既能判断什么时候需要调用函数，也能输出符合函数签名的 JSON。函数签名指一个函数叫什么名字、要哪些参数、每个参数是什么类型。

{{fig 50 | 左：一个工具的描述，包括名字、一句话的说明和参数。右：模型的输出，写明要调用哪个工具、参数是什么。右边的写法是简化过的，各家模型厂商的 API 实际用的字段名见下面的表。}}

工具的描述用的是 JSON Schema，一种描述 JSON 数据应该长什么样的格式。图里的例子是这样的：

{ "name": "get_weather",
  "description": "Current weather",
  "parameters": {
    "type": "object",
    "properties": { "city": {"type": "string"} },
    "required": ["city"] } }

它告诉模型三件事：工具叫 get_weather；作用是查当前天气；参数是一个对象，里面有一个字符串类型的 city，而且必须提供。

一次完整的函数调用有四步。下面说的应用，就是前面说的包在模型外面的那个程序：它把工具交给模型，管理多轮对话。它也叫运行框架（harness）。

  1. 应用把工具的描述连同用户的问题一起发给模型。
  2. 模型输出一次调用。这一步它输出的是工具名 get_weather 和参数 {"city": "Stanford"}，给用户的回答留到第四步。
  3. 应用检查并执行。应用检查参数是否符合描述，再按工具名找到对应的函数或 API，把参数交给它去执行。
  4. 结果交回模型。模型读到结果后，写出给用户的回答，或者继续调用别的工具。

和 REST 相比，模型不用再拼网址，只要填一个结构固定的 JSON。JSON 的好处在函数调用出现之前就被注意到了：早期写 prompt（交给模型的输入文字）时，要求模型按 JSON 格式回答，输出往往比自由回答更容易被程序处理。

局限。工具的描述，以及按工具名找到函数去执行的那段代码，都写在每个应用自己的代码库里。为一家模型厂商的 API 写好的工具，换到另一家厂商的 API 或另一个应用里，要重写一遍。

下面的表列出了工具的描述、一次调用和调用的结果，在 OpenAI、Anthropic 两家的 API 和下一节要讲的 MCP 里各是什么写法。前两行是模型和应用之间的格式。MCP 一行是应用和工具服务器之间的格式，模型不直接接触它。

表里 Anthropic 一行的「内容块」（content block）是 Anthropic 的 API 里的叫法：一条消息的内容是一个数组，数组里的每一项叫一个内容块，各有自己的类型。它和 OpenAI 一行里说的数组里的条目是同一类东西。

+
工具的描述要占用输入。OpenAI 的文档把工具叫作函数，把工具的描述叫作函数的定义。文档说，函数的定义会被写进系统消息，计入模型的上下文长度，并按输入 token 计费。系统消息（system message）也叫系统提示，是放在对话最前面、给模型交代背景和规则的那段文字。上下文长度是模型一次能读的输入总量。token 是模型处理文字的最小单位。文档建议一开始就交给模型的函数要少，最好少于 20 个。出处同上表。
+
说明写得好不好直接影响效果。这里的说明，指工具的描述里的 description 一项，它用文字讲这个工具做什么。Anthropic 的文档说，把说明写得非常详细，是影响工具使用效果的最重要的因素。说明里要写清工具做什么，什么时候该用、什么时候不该用，每个参数是什么意思。出处同上表。

第三代：MCP，应用和工具之间的一套协议

MCP 的全称是 Model Context Protocol（模型上下文协议），由 Anthropic 在 2024 年 11 月 25 日开源。它要解决的问题是：每接一个新的数据源或工具，每个 AI 应用都要单独写一套对接的代码。MCP 在 AI 应用和工具之间定了一套统一的协议，两边各自按协议实现一次。

{{fig 51 | 左边是 AI 应用：聊天界面、代码编辑器和其他应用。右边是数据源和工具：数据库和文件系统、开发工具、办公工具。中间是 MCP。两边的箭头都是双向的。图片来源：MCP 官网。}}

三代接口现在是配合着用的，各自用在不同的两方之间。函数调用规定的是模型和应用之间的消息格式，MCP 规定的是应用和工具服务器之间的消息格式。工具服务器后面可以就是一个 REST API，本页后面的例子就是这样。

一次调用要经过这几方。应用通过 MCP 从工具服务器取到工具列表，转成函数调用的格式交给模型。模型输出一次调用，应用再通过 MCP 把它发给工具服务器执行。

MCP 的规范说，它的设计参考了语言服务器协议（Language Server Protocol）。编辑器要支持一种编程语言，就要提供自动补全、跳转到定义这类功能。有了语言服务器协议，一种语言的这些功能只写一次，就能用在各种编辑器里。MCP 想对工具做同样的事：一个工具服务器只写一次，就能用在各种 AI 应用里。

MCP 的三个角色

MCP 把参与的程序分成三个角色：主机、客户端和服务器。主机就是前面几节说的应用，服务器就是前面几节说的工具服务器。先分清这三个角色，才能看懂下一节的请求是谁发给谁的。

{{fig 52 | 上面的黄色方框是主机，里面有四个客户端。下面是三个服务器：A 和 B 在本地，分别提供文件系统和数据库；C 在远程。每个客户端有一条专用的连接通向一个服务器，客户端 3 和客户端 4 连的都是服务器 C。图片来源：MCP 文档。}}

关于这个结构，有三点要知道。

  • 主机不需要懂每种工具的细节。文件怎么存、数据库是什么格式，主机都不用知道。它只要实现 MCP 这一种协议。
  • 服务器看不到整段对话。规范的设计原则里写明，完整的对话历史留在主机里，服务器只收到必要的信息，也看不到别的服务器。
  • 本地和远程的服务器，连接方式不同。本地服务器通常通过标准输入输出（stdio，本机上两个程序之间直接传文字的通道，不经过网络）和主机里的一个客户端通信，只服务这一个客户端。远程服务器通过 HTTP 通信，可以同时服务很多客户端。图里的客户端 3 和客户端 4 就同时连着远程的服务器 C。

除了工具，服务器还可以提供另外两样东西：资源（resources，供模型或用户读取的数据，比如文件内容）和提示模板（prompts，预先写好的 prompt 模板）。这一讲只讲工具。

两个最常用的请求：列出工具和调用工具

连接建立之后，剩下的问题是怎么知道有哪些工具可用。在第三部分和第四部分，这要靠训练模型来学。在 MCP 里，客户端向服务器发一个 tools/list 请求，服务器就把工具列表发回来。

{{figs 53 54 | 左：列出工具，请求是 tools/list，响应是一个工具列表。右：调用工具，请求是 tools/call，响应是执行的结果。}}

MCP 的消息用的是 JSON-RPC 2.0，一种用 JSON 写的远程调用格式：请求里写明要调用的方法名和参数，响应里带回结果，两者靠同一个 id 对应起来。

根据每个工具的说明来判断「这是不是现在要用的工具」，这一步由模型来做，而说明是工具的开发者写的。所以开发者把说明写得清不清楚，直接影响模型能不能选对工具。

这些 JSON 看上去很繁琐，但不需要人手写，也不需要模型来写。开发者用 MCP 的开发包写一个普通的函数，开发包会生成工具的描述，并处理这些消息的收发。模型看到的只是工具列表，它输出的只是工具名和参数。

!
「MCP 要先握手、有状态」的说法已经不适用于最新版规范。常见的说法是：MCP 是有状态的会话协议，客户端连上服务器后要先握手（initialize），双方交换各自支持的功能，然后才能列工具、调工具。会话指一个客户端和一个服务器之间前后相关的一连串交互，从握手开始。有状态的意思是服务器要记住之前和这个客户端交换过的内容，后面的请求依赖这些内容。这是 2025-06-18 版规范的写法，这一版要求握手必须是客户端和服务器之间的第一次交互。2026-07-28 版把 MCP 改成了无状态的协议：取消了握手和协议层面的会话，每个请求都在 _meta 字段里带上协议版本和客户端支持的功能，服务器不用记住之前的请求。新版另外要求服务器支持一个 server/discover 请求，客户端可以用它问服务器支持哪些协议版本和功能。出处：2025-06-18 版规范的生命周期一节和传输一节，以及 2026-07-28 版的变更说明。

三个角色的划分，以及 tools/list 和 tools/call 这两个请求各自做什么，在两个版本里是一样的。请求和响应里带的字段有差别，下面的框说明配图里能看到的两处。

i
这一节开头左右两张配图用的是 2026-07-28 版的格式。图里每个请求的参数里都有 _meta，它就是上一个框里说的那个字段。这个字段在 2025-06-18 版里就有，当时用来附带额外的元数据，也就是关于这条消息本身的附加信息。工具列表的响应里有 ttlMs，意思是这份列表可以缓存多少毫秒，它是 2026-07-28 版新增的字段。出处：2025-06-18 版规范的基础协议一节和 2026-07-28 版的变更说明。

例子：把课程管理系统的 API 变成 MCP 工具

假设一门课的课程管理系统（英文缩写 LMS，学校里用来布置作业、收作业、登记成绩的系统）有一个 REST API，可以列出作业、查看提交、登记成绩。这三件事各对应一条路由，一条路由是一个网址加一种请求方式。想让 agent（能自己调用工具、分很多步去完成任务的语言模型系统）能用这个 API，可以把它包成一个 MCP 服务器。按前面讲的三个角色，这里的 agent 是主机，由它里面的客户端去连这个服务器。

{{fig 55 | 左：三条 REST 路由和它们对应的 MCP 工具，登记成绩的 post_grade 用红框标出。右：用 FastMCP 这个 Python 库完成转换的代码。}} 
from fastmcp import FastMCP
import httpx

api = httpx.AsyncClient(base_url="https://lms.stanford.edu/api/v1")
spec = (await api.get("/openapi.json")).json()

mcp = FastMCP.from_openapi(
    openapi_spec=spec,
    client=api,
    name="Course MCP",
)

代码做了三件事：建一个访问这个 API 的 HTTP 客户端，取回它的 OpenAPI 规范文件（列出所有网址、参数和返回结构的文件），再把规范文件和这个 HTTP 客户端交给 from_openapi。FastMCP 会读规范文件，把里面的每一条路由变成一个 MCP 工具。

工具的名字默认取自规范文件里每条路由的 operationId 字段。这个字段是规范文件的作者给每条路由起的一个名字，在整份文件里不能重复。例如下表第一条路由，如果它在规范文件里的 operationId 是 list_assignments，变成的工具就叫 list_assignments。

之后，任何支持 MCP 的 agent 连上这个服务器，由它的客户端发一个 tools/list，就会得到这三个工具。

+
自动转换出来的工具，效果不如专门设计的。FastMCP 的文档自己提醒：从 OpenAPI 自动生成 MCP 服务器是开始使用 FastMCP 的好办法。但文档也说，在实际使用中，模型用精心设计和挑选过的 MCP 工具，效果明显好于用自动转换出来的工具，路由多、参数多的复杂 API 尤其如此。默认情况下，规范文件里的每一条路由都会变成一个工具，没有经过设计和挑选。所以文档建议把自动转换用于搭原型，不要用它把整个 API 照原样转成工具交给模型。出处：FastMCP 文档的 OpenAPI 一节。

例子续：谁可以调用，用谁的身份去调用

上面的转换有一个明显的问题。任何人都可以写一个 agent 连上这个服务器，而登记成绩这个工具显然不该对所有人开放。所以除了接通，还要控制谁能连上这个服务器。

{{fig 56 | 左：从上到下是 agent、课程 MCP 服务器和课程管理系统的 REST API 三个方框。agent 和服务器之间标着入站的令牌 AGENT_TOKEN，服务器和 REST API 之间标着出站的令牌 LMS_TOKEN。右：对应的代码。}}

课程 MCP 服务器夹在 agent 和 REST API 之间，两边各有一道身份检查，用的是两个不同的令牌（token，这里指一串证明身份的密钥，和模型处理文字的 token 是两回事）。

agent 永远看不到 LMS_TOKEN，课程管理系统也永远看不到 AGENT_TOKEN。agent 能做的事，只限于 MCP 服务器提供的那些工具。

两个令牌分开是 MCP 规范的要求。规范写明：MCP 服务器访问上游 API 时用的令牌，是上游另外签发的一个令牌，服务器不得把从客户端收到的令牌原样转交给上游。在这个例子里，从客户端收到的令牌就是 agent 带来的 AGENT_TOKEN。上游 API 指服务器后面的那个 API，这里是课程管理系统的 REST API。出处：MCP 规范的授权一节。

只验证身份，还不能按工具分别控制

图里的代码做的是身份验证，也就是确认来的是谁。没有 AGENT_TOKEN 的 agent 连不上服务器，拿到令牌的 agent 三个工具都能调用，登记成绩也在内。

要让某个 agent 可以查看提交、但不能登记成绩，还要给 post_grade 这个工具单独加授权检查。授权检查决定一个已经验证过身份的调用方能做什么。

FastMCP 支持按工具设置这种检查：给一个工具指定 auth 检查之后，检查不通过的调用方在 tools/list 的结果里看不到这个工具，直接调用会得到「找不到」的错误。这个例子里的工具是自动转换出来的，怎样给它们加上这种检查，本页不演示。出处：FastMCP 文档的授权一节。

i
图里的验证器只能用于开发和测试。图里用的 StaticTokenVerifier 把令牌以明文写在配置里，也就是原样保存、没有加密。FastMCP 的文档说它只用于开发和测试，绝不应该用在生产环境，也就是正式对外提供服务的环境。正式部署要换成能验证签名的令牌验证方式，FastMCP 提供的 JWTVerifier 是其中一种。用法是把建服务器时传入的验证器换成它，本页不演示。建服务器时接收验证器的那个参数也叫 auth，它做的是身份验证，和上面加在单个工具上的 auth 检查是两样东西。出处：FastMCP 文档的令牌验证一节。
i
验证签名能确认什么。签名是签发令牌的系统用自己的私钥给令牌算出的一段校验数据。私钥是只有这个系统自己保存的一个密钥，和它配成一对的公钥可以公开。拿到公钥的人能验证一个签名是不是用对应的私钥算出来的，却算不出新的签名。所以服务器用公钥验证通过，就能确认令牌由那个系统签发、没有被改过。JWTVerifier 验证的 JWT 是一种带签名的常见令牌格式。出处同上一个框。

这一部分的小结

  • 标准接口把「工具有哪些、怎么用」从模型训练时学进去的知识，移到了运行时读的一份描述里。新增工具不用再训练模型。
  • REST 要模型读给人看的文档，自己写出完整的请求。函数调用让模型只输出工具名和参数，由应用检查和执行。MCP 让应用在运行时向工具服务器取工具列表，一个工具服务器可以被各种应用复用。
  • 不管用哪一代接口，模型发出的调用都只是一段它生成的文字，会出错。这一页有两处和出错有关。模型可能选错工具，所以工具的说明要写清楚。模型可能把参数填错，所以应用要先检查参数是否符合描述，再去执行。下一部分还会讲到别的出错方式，例如不需要工具的时候也调用。

所以要有专门的办法来评估工具用得对不对。这是下一部分的内容：怎样评估工具使用，常见哪些失败。
