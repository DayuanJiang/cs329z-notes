先看结论

  • ToolLLM 把规模从 Toolformer 的 5 个工具扩大到 3,451 个工具提供的 16,464 个真实 API。训练数据由 ChatGPT 生成：先让它扮演用户写出请求，再让它真的调用 API 把请求办成，留下成功的过程，用来微调一个开源的小模型（微调是在已经训练好的模型上用新数据继续训练）。
  • 工具一多，模型会编造不存在的 API，或者选错库。Gorilla 给这种错误下了定义，并用语法树匹配来自动度量。
  • Gorilla 在训练时就在请求后面附上一份 API 文档，让模型学会参考文档。这样 API 更新之后，换一份文档就行，不用重新训练。
  • 不带检索时，微调过的 Gorilla 比 GPT-4 准确得多，编造也少得多。加上检索之后差距缩小，检索器不好时准确率反而会下降。
  • 上一部分的两种方法和这一部分的两种方法有一个共同的代价：工具的知识训练在模型里，新增工具就要再训练。Gorilla 靠检索文档能跟上已有 API 的改动，但它仍然是为一批特定的 API 训练的。

ToolLLM：让更强的模型来造数据

Toolformer 只有 5 个工具。真实世界里的 API（应用程序接口，一个程序提供给别的程序调用的入口）成千上万。Qin 等人 2023 年的 ToolLLM 把规模扩大到了 16,000 多个 API。它的数据集叫 ToolBench，全部由机器构造。

{{fig 38 | 左半边是数据构造：从 RapidAPI 收集 API，由 ChatGPT 生成指令并标注解题路径，得到 ToolBench，再用它微调 LLaMA 得到 ToolLLaMA。右半边是使用时的流程：检索器按指令找出相关的 API，ToolLLaMA 多轮调用 API，给出最终答案，由 ToolEval 评分。图片来源：Qin 等，2023。}} {{fig 62 | 左：RapidAPI 的三层结构。最上面是类别，比如金融、电影、求职；中间是工具；最下面是每个工具提供的 API，每个 API 带一份文档。右：三种指令是怎么抽样的。图片来源：Qin 等，2023。}}

退回去重试的搜索

标注路径时，如果让 ChatGPT 从头到尾只走一条路，前面一步错了后面就全错，很多指令办不成。论文让它按深度优先的方式搜索：每一步可以选择继续往下走，也可以放弃当前这条路，退回上一步换一个做法。论文的主表里，ChatGPT 只走一条路时平均通过率是 40.2%，用这种搜索是 64.8%。

使用时的流程

16,000 多个 API 的文档不可能全部写进 prompt（交给模型的输入文字）。所以使用时先由一个检索器按用户的指令找出几个相关的 API，再把这几个 API 的文档交给 ToolLLaMA。ToolLLaMA 一轮一轮地调用 API、看返回的结果，直到给出最终答案。

论文报告的结果是：用同样的搜索办法，ToolLLaMA 的平均通过率是 66.7%，ChatGPT 是 64.8%，GPT-4 是 71.1%。一个 70 亿参数的开源模型，学了 ChatGPT 的解题过程之后，达到了和 ChatGPT 相近的水平。通过率是怎么判的，见第六部分。

i
这种做法也常被叫作蒸馏，它和经典的知识蒸馏不同。经典的知识蒸馏是让小模型去拟合大模型输出的概率分布。这里的做法是收集强模型解决问题的过程，再用这些过程对小模型做有监督的微调。它用到的只是强模型看得见的行为：调用了哪个工具，传了什么参数，拿到了什么结果，最后怎么回答。强模型内部没有公开的推理过程用不到，也不需要。如果想在自己的领域里训练一个会用工具的小模型，可以照这个办法分两步造数据：先让强模型根据工具写出用户可能提的请求，再让它带着工具把请求办成。

工具一多出现的新问题：编造 API

候选的 API 多了，而且很多 API 的功能相近，模型就容易写出看上去合理、实际不存在的调用。

{{fig 39 | 同一个请求：帮我找一个 API，用 Torch Hub 把录音里的语音转成文字。三个模型的回答，红色标出的是出错的部分。图片来源：Patil 等，2023。}}

到这里为止，评价一次工具调用只有对和错两种说法。要想减少编造，先得能把「编造」和一般的「用错」分开来量。Gorilla 做的就是这件事。

Gorilla：数据是怎么来的

Gorilla 是加州大学伯克利分校的 Patil 等人 2023 年 5 月提出的系统。它涉及的 API 约 1,600 个，是 ToolLLM 的十分之一，全部是机器学习模型的调用接口。它的数据集叫 APIBench。

{{fig 41 | 从左到右：三个模型库的页面整理成 JSON，用 GPT-4 生成指令，再训练出 Gorilla。下面三个色块里写着每一步的数量。图片来源：Patil 等，2023。}}
  • 收集。API 来自三个模型库：Torch Hub 的 94 个，TensorFlow Hub 的 626 个，HuggingFace 的 925 个，一共 1,645 个。前两个库是全部收录。HuggingFace 上的模型太多，很多没有说明文档，所以只取每个任务类别里下载量最高的 20 个。
  • 整理。每个 API 的说明页整理成一条 JSON（一种用键值对表示数据的文本格式）记录，包括领域、框架、功能、API 名、调用方式、参数、环境要求、示例代码、性能和描述这些字段。
  • 生成指令。人工只写了 18 条示范，每个库 6 条。然后把示范和一个 API 的文档交给 GPT-4，让它写出真实场景里会用到这个 API 的请求，并要求请求里不出现 API 的名字。每个 API 生成 10 条，一共 16,450 条「指令加 API」。
  • 训练。用这些数据微调 LLaMA-7B，得到 Gorilla。

带着检索结果一起训练

Gorilla 使用时有两种模式。零样本模式（zero-shot）下，用户的请求直接交给模型，模型凭训练时学到的知识写出 API 调用。检索模式下，先由检索器从 API 数据库里找出最相关的一份文档，附在请求后面，再交给模型。

{{fig 42 | 用户说想看几只猫跳舞庆祝。检索器从 API 数据库里找出一条生成图像的 API 文档，和请求一起交给 Gorilla。Gorilla 给出 Stable Diffusion 的调用，执行后得到图片。下面的蓝线是不经过检索、直接交给 Gorilla 的零样本模式。图片来源：Patil 等，2023。}}

为了让模型在检索模式下表现好，训练时就把一份 API 文档放进输入里。具体做法是在每条训练数据的请求后面加一句「请参考这份 API 文档」，后面跟着一份文档，而要模型输出的仍然是正确的调用。论文把这叫作带检索的训练（Retriever-Aware Training）。它想达到两个目的。

i
第二个目的，论文的两处写法不完全一致。方法一节说训练时附上的文档「可能不正确」。实验一节写的是：微调用的参考文档来自标准答案对应的那一份，也就是始终正确的文档。训练数据里不相关的文档占多大比例，论文里没有找到。出处：Gorilla 在 NeurIPS 2024 发表的版本。

用语法树匹配来度量编造

怎么自动判断模型写的一次 API 调用对不对？直接比较字符串太严：参数顺序不同、多写一个可选参数，字符串就不一样了。真的去执行又太重：要装依赖、配环境，有的还要显卡。

Gorilla 的办法是把调用解析成抽象语法树（AST，把一段代码按语法结构拆成的树：函数名是一个节点，每个参数是它下面的节点），再到 API 数据库里看这棵树能不能对上。

{{fig 43 | 左：模型写出的一次调用和它的语法树，从上到下是 torch、hub、load、仓库名、模型名、一个可选参数。右：数据库里所有合法调用合成的一棵大树。左边的树是右边大树里的一条路径（棕色），所以这次调用是合法的。图片来源：Patil 等，2023。}}

匹配时只比较关键的参数，比如仓库名和模型名。带默认值的可选参数（图里的 pretrained）不比较。

这个办法准不准，论文做过抽查：随机取 100 条 Gorilla 的输出，语法树匹配判对的有 78 条，人工判对的也是 78 条，而且是同样的 78 条。这些代码真的拿去运行，有 72% 能成功执行，差的 6 个百分点来自调用之外的配套代码。

结果：准确率更高，编造更少

{{fig 44 | 上排：用 GPT 检索器时，五个模型在三个模型库上的准确率。下排：四种检索设置下的散点图，横轴是编造的比例，纵轴是准确率，越靠左上越好。图片来源：Patil 等，2023。}}

先看不带检索的零样本模式，也就是下排最左边那张图。

不带检索时，Gorilla 在三个库上的准确率都是最高的，编造的比例都最低。同一个 LLaMA-7B，微调前准确率是 0，几乎每次都在编造。

再看带检索的情况，也就是上排的三张柱状图。差距明显缩小了。Torch Hub 上，除了没有微调的 LLaMA，四个模型的准确率都在 59% 到 62% 之间。TensorFlow Hub 上，GPT-3.5 是 65.59%，Gorilla 是 64.96%，Gorilla 略低。有了文档可以参考，通用的大模型也能写对多数调用。

i
检索不总是有帮助。论文自己指出，给模型加上检索并不总能提高成绩，有时反而会降低。一个没有带着检索训练的 Gorilla，零样本时在 Torch Hub、HuggingFace、TensorFlow Hub 上的准确率是 59.13%、71.68%、83.79%。使用时给它接上 BM25 检索器（一种按关键词匹配程度排序的经典检索方法），准确率变成 37.63%、11.28%、34.30%。检索器找来的文档不对，模型就被带偏了。另外，上排中间那张图里 GPT-3.5 在 HuggingFace 上的 47.34，和论文表 1 里同一项的 29.08 不一致，论文没有说明原因。

四种方法放在一起

上一部分的 Toolformer、ToolkenGPT，和这一部分的 ToolLLM、Gorilla，是让模型学会用工具的四种有代表性的做法。

{{fig 45 | 四种方法的对照。}}

四种方法走的是同一条路：让模型去学，把「有哪些工具、什么时候用、怎么用」变成模型自身的能力。这条路有一个避不开的代价。API 每天都在增加和变化。模型训练完之后，只要有人发布了一个新的 API，要么重新微调模型，要么重新训练新 token 的向量。两样都要花钱花时间，也不灵活。Gorilla 的带检索训练缓解了文档变化的问题，但模型仍然是为一批特定的 API 训练的。
