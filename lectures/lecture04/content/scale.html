先看结论

  • 第三部分的 Toolformer 让模型自己给训练文本加上工具调用，再用这些文本微调，它只有 5 个工具。Qin 等人 2023 年提出的 ToolLLM 把规模扩大到 3,451 个工具提供的 16,464 个真实 API（应用程序接口，一个程序提供给别的程序调用的入口）。这些工具来自 RapidAPI 这个 API 平台，平台上一个工具下面有若干个 API，每个 API 带一份文档。
  • ToolLLM 的训练数据由 ChatGPT 生成：先让它扮演用户写出请求，再让它真的调用 API 把请求办成，留下成功的过程，用来微调一个开源的小模型。微调是在已经训练好的模型上用新数据继续训练。
  • 工具一多，模型容易写出看上去合理、实际不存在的 API 调用，这种错误叫编造。Gorilla 是一个为调用机器学习 API 而微调的模型，提出它的论文给编造下了定义，并用语法树匹配来自动度量。语法树匹配是把模型写的调用按语法结构拆开，再和已有的 API 逐项比对。
  • Gorilla 的论文训练了两个版本。一个版本训练时不附文档。另一个版本训练时在请求后面附上一份 API 文档，让模型学会参考文档，这样 API 更新之后，换一份文档就行，不用重新训练。
  • 论文拿 Gorilla 和 GPT-4 等模型比较时，分使用时不带检索和带检索两种情况。带检索指使用时先由一个检索器找出相关的 API 文档，附在请求后面交给模型。不带检索时，训练时不附文档的那个 Gorilla 比 GPT-4 准确得多，编造也少得多。带上检索之后，几个模型的差距缩小。检索也不总是有帮助：给训练时不附文档的那个 Gorilla 接上一个按关键词匹配的检索器，准确率比不接时还低。
  • 第三部分讲了 Toolformer 和 ToolkenGPT 两种训练方法，这一部分讲 ToolLLM 和 Gorilla。这四种方法都靠训练让模型学会用工具。其中 Toolformer、ToolkenGPT 和 Gorilla 每新增一个工具都要再训练。Gorilla 靠检索文档能跟上已有 API 的改动，但它仍然是为一批特定的 API 训练的。ToolLLM 微调出的模型叫 ToolLLaMA。论文报告，ToolLLaMA 只靠 API 文档就能用上训练时没见过的 API，但它仍然是在一批收集来的 API 上微调出来的。

ToolLLM：让更强的模型来造数据

Toolformer 只有 5 个工具。真实世界里的 API（应用程序接口，一个程序提供给别的程序调用的入口）成千上万。Qin 等人 2023 年的 ToolLLM 把规模扩大到了 16,000 多个 API。它的数据集叫 ToolBench，全部由机器构造。

这些 API 来自 RapidAPI，一个汇集了大量第三方 API 的平台。平台上的内容分三层。最上面是类别，比如金融、电影、求职。类别下面是工具。一个工具下面有若干个 API，每个 API 带一份文档。所以后面的数有的按工具计，有的按 API 计。

RapidAPI 另外还有一种分组，叫合集（collection），比如「中文 API」「数据库 API」。合集和类别是两套分法，合集不在类别下面。同一个合集里的工具有共同的特点，功能或用途相近，它们可以来自不同的类别。

论文说合集是比类别分得更细的一种分法。类别是 49 个大类，每个类别对应一个话题，合集有 500 多个。这里的「更细」指分出的组更多、每一组的范围更小，合集和类别仍然是并列的两套分法。

退回去重试的搜索

标注路径时，如果让 ChatGPT 从头到尾一步接一步地调用下去、中途不能退回，前面一步错了后面就全错，很多指令办不成。论文让它按深度优先的方式搜索：每一步可以选择接着做下一步，也可以放弃当前的做法，退回上一步换一个做法。

这种搜索是模型解题时的一种做法，标注和测试时都用得上。标注解题路径时 ChatGPT 用它。测试时，各个模型解题也可以用它，或者照中途不能退回的做法来解。

论文用通过率来比较这两种做法。通过率是在限定的调用次数内把指令办成的比例，办没办成由 ChatGPT 当评审来判，判法见第六部分。

比较用的是论文里比较各个模型的那张结果表，下面叫主表。主表有六组测试题，每道题是一条指令，都不在微调 ToolLLaMA 用的数据里。六组按两件事来分：指令是前面三种里的哪一种，以及指令用到的工具在微调用的数据里有没有出现过。

在这些测试题上，按六组的平均算，ChatGPT 中途不能退回时通过率是 40.2%，用这种搜索是 64.8%。

使用时的流程

16,000 多个 API 的文档不可能全部写进 prompt（交给模型的输入文字）。所以使用时先由一个检索器按用户的请求找出几个相关的 API，再把这几个 API 的文档交给 ToolLLaMA。ToolLLaMA 一轮一轮地调用 API、看返回的结果，直到给出最终答案。

论文报告的结果是：一个 70 亿参数的开源模型，学了 ChatGPT 的解题路径之后，达到了和 ChatGPT 相近的水平。下表是三个模型用同样的搜索办法时，在主表六组测试题上的平均通过率。

如果想在自己的领域里训练一个会用工具的小模型，可以照这个办法分两步造数据：先让强模型根据工具写出用户可能提的请求，再让它带着工具把请求办成。

i
这种做法也是一种蒸馏，但和经典的知识蒸馏不同。蒸馏指把一个强模型的能力转移给一个小模型，这篇论文就把 ChatGPT 叫作「老师模型」（teacher model）。经典的知识蒸馏是训练小模型，让它输出的概率分布尽量接近大模型输出的概率分布，也就是大模型给每个可能的下一个词算出的概率。这里的做法是收集强模型解决问题的过程，再用这些过程对小模型做有监督的微调。它用到的只是强模型写出来的内容和调用的记录：每一步写下的想法，调用了哪个 API，传了什么参数，拿到了什么结果，最后怎么回答。强模型写出这些内容之前在内部做的推理没有公开，这个办法用不到它，也不需要它。

工具一多出现的新问题：编造 API

候选的 API 多了，而且很多 API 的功能相近，模型就容易写出看上去合理、实际不存在的调用。

下面的例子里，用户要的是 Torch Hub 上的 API。Torch Hub 是一个公开的机器学习模型库，按仓库名和模型名就能加载别人发布的模型。图后面的表把三个模型的回答各用一句话写出来。

{{fig 39 | 同一个请求：帮我找一个 API，用 Torch Hub 把录音里的语音转成文字。三个模型的回答，红色标出的是出错的部分。图片来源：Patil 等，2023。}}

这一页前面用到的度量只有通过率。它只看一条指令最后有没有办成，分不出一次调用是编造还是别的错。要想减少编造，先得能把「编造」和一般的「用错」分开来量。Gorilla 做的就是这件事。下面先看它的数据和训练办法，再看它怎么度量编造。

Gorilla：数据是怎么来的

要量出编造，先得有一个范围确定的 API 数据库：一次调用在数据库里找不到对应的 API，才能判它是编造。要减少编造，还得有一批训练数据，每条是一个请求加上它该用的 API。这一节讲这两样东西是怎么来的。

Gorilla 是加州大学伯克利分校的 Patil 等人 2023 年 5 月提出的模型。它涉及的 API 约 1,600 个，是 ToolLLM 的十分之一，全部是机器学习模型的调用接口。它的数据集叫 APIBench。下面四步里，前两步得到 API 数据库，也就是整理好的 1,645 条 API 记录。第三步给每个 API 生成请求。API 数据库加上这些请求，合起来就是 APIBench。第四步用它训练出 Gorilla。

{{fig 41 | 从左到右：三个模型库的页面整理成 JSON，用 GPT-4 生成指令，再训练出 Gorilla。下面三个色块里写着每一步的数量。图片来源：Patil 等，2023。}}
  • 收集。API 来自三个模型库：Torch Hub 的 94 个，TensorFlow Hub 的 626 个，HuggingFace 的 925 个，一共 1,645 个。前两个模型库是全部收录。HuggingFace 上的模型太多，很多没有说明文档，所以只取每个任务类别里下载量最高的 20 个。
  • 整理。每个 API 的说明页整理成一条 JSON（一种用键值对表示数据的文本格式）记录，包括领域、框架、功能、API 名、调用方式、参数、环境要求、示例代码、性能和描述这些字段。
  • 生成指令。人工只写了 18 条示范，每个模型库 6 条。然后把示范和一个 API 的文档交给 GPT-4，让它写出真实场景里会用到这个 API 的请求，并要求请求里不出现 API 的名字。论文把这样的一条请求叫作指令。每个 API 生成 10 条，一共 16,450 条「指令加 API」，每条里的 API 就是这条指令该用的那一个。
  • 训练。用这些数据微调 LLaMA-7B，得到 Gorilla。

带着文档一起训练

API 更新的速度比重新训练模型快得多。要让模型跟上，办法是使用时由检索器找出最新的文档，附在请求后面交给模型。但检索器会找错文档。Gorilla 的训练办法就是针对这两件事设计的。

Gorilla 使用时有两种模式。零样本模式（zero-shot）下，用户的请求直接交给模型，模型凭训练时学到的知识写出 API 调用。这里的零样本指不接检索器、不附文档，和第三部分 Toolformer 评测里「不给例子」的意思不同。检索模式下，先由检索器从 API 数据库里找出最相关的一份文档，附在请求后面，再交给模型。

{{fig 42 | 用户说想看几只猫跳舞庆祝。检索器从 API 数据库里找出一条生成图像的 API 文档，和请求一起交给 Gorilla。Gorilla 给出 Stable Diffusion（一个生成图像的模型）的调用，执行后得到图片。下面的蓝线是不经过检索、直接交给 Gorilla 的零样本模式。图片来源：Patil 等，2023。}}

为了让模型在检索模式下表现好，训练时就把一份 API 文档放进输入里。具体做法是在每条训练数据的请求后面加一句「请参考这份 API 文档」，后面跟着一份文档，而要模型输出的仍然是正确的调用。论文把这叫作带检索的训练（Retriever-Aware Training）。

这个名字里的「检索」，指的是这种训练为检索模式做准备：训练时的输入，和使用时由检索器附上文档的输入，是同一种格式。训练时附的是哪一份文档，论文的两处写法不同，见下面表后的说明框。

这一页说「带检索」「不带检索」时，都指使用时接不接检索器。训练时的两种做法，这一页写作「训练时附上文档」和「训练时不附文档」。「带检索的训练」只用作论文给前一种做法起的名字。

训练时附上文档，论文想达到两个目的。

第二个目的，论文的两处写法不完全一致。表里的说法出自论文的方法一节：训练时附上的文档「可能不正确」。论文的实验一节写的是另一种做法：微调用的参考文档来自标准答案对应的那一份，也就是始终正确的文档。这一页后面讲结果的一节里，训练时附上文档的那个 Gorilla 按论文实验一节的做法来理解：它训练时附的是每道题对应的正确文档。这个版本只见过正确的文档，所以它的成绩说明不了第二个目的有没有达到。出处：Gorilla 在 NeurIPS 2024 发表的版本。NeurIPS 是机器学习领域的一个主要学术会议。

用语法树匹配来度量编造

怎么自动判断模型写的一次 API 调用对不对？直接比较字符串太严：参数顺序不同、多写一个可选参数，字符串就不一样了。真的去执行，准备的成本又太高：要装依赖、配环境，有的还要显卡。

Gorilla 的办法是把调用解析成抽象语法树（AST，把一段代码按语法结构拆成的树：函数名是一个节点，每个参数是它下面的节点），再到 API 数据库里看这棵树能不能对上。

{{fig 43 | 左：模型写出的一次调用和它的语法树。配图把这棵树画成从上到下的一串：函数名 torch.hub.load 拆成 torch、hub、load 三层，下面依次是仓库名、模型名和一个可选参数，每层一个方框。右：数据库里所有合法调用合成的一棵大树，同一层并排的方框是这一层可以取的不同的值。左边这一串从 torch 到模型名的每一层，都能在右边大树里沿着棕色标出的那条路径逐层找到，所以这次调用是合法的。图片来源：Patil 等，2023。}}

「对上」就是图里的这种情况：模型写的调用从函数名到要比较的各个参数，每一层的值都能在数据库的大树里沿着同一条路径找到。

匹配时只比较关键的参数，比如仓库名和模型名。带默认值的可选参数（图里的 pretrained）不比较。

这个办法准不准，论文做过抽查：从 Gorilla 在测试题上的输出里随机取 100 条，语法树匹配判对的有 78 条，人工判对的也是 78 条，而且是同样的 78 条。这 100 条来自哪个版本的 Gorilla、哪种检索设置，论文没有写明。

Gorilla 的输出除了 API 调用本身，还带着配套的代码，例如安装依赖、设置环境变量。把这 100 条输出真的拿去运行，能成功执行的有 72 条，比判对的 78 条少 6 条。论文说明，这 6 条的 API 调用本身没有错，是配套代码出了错，错处在 API 的调用之外。论文举的例子里，加载模型的调用是对的，出错的是后面处理返回结果的配套代码。

结果：不带检索时 Gorilla 最准，带上检索后差距缩小

Gorilla 的论文把它和 GPT-4、GPT-3.5、Claude，以及没有微调的 LLaMA-7B 放在一起比。结论有三条。不带检索时，Gorilla 的准确率最高，编造最少。带上检索之后，几个模型的差距缩小。检索不总是有帮助：给训练时不附文档的那个 Gorilla 接上一个按关键词匹配的检索器，准确率比不接时还低。

HuggingFace 一栏里，Gorilla 以外的模型是按更宽的标准判的。论文给的理由是数据集收不全：HuggingFace 上的模型太多，APIBench 只收了每个任务类别里下载量最高的 20 个。按前面讲的编造的定义推下去，调用一个真实存在、但数据集没有收录的模型，在数据库里对不上，也会被算成编造。所以对这些模型，论文只检查它们选的领域对不对。领域是 API 所属的任务类别，例如图像分类。

四种方法放在一起

第三部分的 Toolformer、ToolkenGPT，和这一部分的 ToolLLM、Gorilla，是让模型学会用工具的四种有代表性的做法。前两种这里各用几句话重述一遍。

  • Toolformer。它让模型自己在训练文本里试着插入工具调用，只留下那些能让模型把后面的文字预测得更准的调用，再用留下的文本微调整个模型。预测得准不准用损失来量，损失越低越准，下表里的「按损失筛选」指的就是这一步。
  • ToolkenGPT。它把每个工具当成词表里的一个新 token。token 是模型处理文字的最小单位，词表是模型能输出的所有 token 的清单。模型给每个 token 准备了一个向量，也就是一串数字，用它来算下一步选出这个 token 的概率。ToolkenGPT 保持原模型不动，只训练新加的这些向量。训练用的数据有两个来源：本来就标了工具调用的数据集，或者让语言模型合成的数据。使用时模型选出一个工具的 token 之后，参数由它照着 prompt 里这个工具的使用示范来填。

四种方法都靠训练让模型记住工具，把「有哪些工具、什么时候用、怎么用」变成模型自身的能力。

这样做有一个代价。API 每天都在增加和变化，而模型记住的只是训练时的那一批。对 Toolformer、ToolkenGPT 和 Gorilla 这三种方法来说，模型训练完之后，只要有人发布了一个新的 API，要让模型用上它就得再训练：要么重新微调模型，要么重新训练新 token 的向量。两样都要花钱花时间，也不灵活。

Gorilla 使用时会读检索器找来的文档。它带检索的训练，也就是训练时在请求后面附上一份 API 文档的做法，缓解了文档变化的问题。但 Gorilla 仍然是为一批特定的 API 训练的，也就是三个模型库里的机器学习 API。

ToolLLM 的论文报告的情况不一样：ToolLLaMA 只靠 API 文档就能用上训练时没见过的 API。前面说的主表六组测试题里，有三组用到的工具没有在微调用的数据里出现过。ToolLLaMA 也仍然是在一批收集来的 API 上微调出来的，这批 API 都来自 RapidAPI。

下一部分换一个方向：模型不动，改的是工具的描述方式。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • 配图里 Gorilla 回答的模型名。编造 API 一节的配图把 Gorilla 加载的模型名写成了 silero_sst。Torch Hub 按仓库里 hubconf.py 这个文件列出的名字加载模型，silero-models 仓库的这个文件里列出的模型名是 silero_stt，没有 silero_sst。图上的写法很可能是论文配图的笔误。
  • 训练时附上的文档里，不相关的占多少。论文的方法一节说训练时附上的文档可能不正确，实验一节写的是始终正确的文档。训练数据里不相关的文档占多大比例，论文里没有找到。出处：Gorilla 在 NeurIPS 2024 发表的版本。
  • GPT 检索器用的是哪个模型。论文的两个版本写法不同。2023 年发布在 arXiv（研究者公开发布论文的网站）上的版本写的是 OpenAI 的 text-davinci-003，NeurIPS 2024 发表的版本写的是 OpenAI 的 text-embedding-ada-002-v2，并把它称作 embedding 模型。arXiv 上的版本只把 text-davinci-003 称作检索模型（retrieval model），没有写它怎样检索。正文的模型名只写「OpenAI 的模型」，检索的办法按 NeurIPS 2024 发表的版本来写。
  • 结果里的 Gorilla 是哪个版本。论文写明表 1 的零样本成绩来自训练时不附文档的那个版本的 Gorilla。表 1 还列了三种检索器下的成绩，结果一节上排的柱状图对应其中用 GPT 检索器的几行。这些带检索器的成绩用的是哪个版本，论文没有明说。论文的表 2 把两个版本并排列出，各测了四种检索设置。表 1 里带检索器的这几行数字，和表 2 里「训练时附上正确文档」那个版本在同一种检索器下的数字相同，只有 HuggingFace 上接 BM25 检索器的一项，表 1 是 17.03%，表 2 是 17.04%。正文据此按训练时附上正确文档的那个版本来读。
  • 柱状图和表 1 的一处不一致。结果一节的配图上排中间那张图里，GPT-3.5 在 HuggingFace 上的准确率是 47.34%。论文表 1 里同一项是 29.08%。论文没有说明原因。
  • HuggingFace 一栏的选项是什么。论文写的是，对 Gorilla 以外的模型只检查它们能不能给出正确的领域名，接着说题目因此变成了从几个选项里选一个（原文是 picking one of multiple choices），没有另外写明选项是什么。正文说选项应当是领域的名字，这是把论文的这两句连起来读出来的。37 个领域这个数出自论文附录对数据集的介绍。论文的方法一节按大类列出的 HuggingFace 领域数是多模态 7 个、计算机视觉 8 个、自然语言处理 12 个、音频 5 个、表格 2 个、强化学习 2 个，加起来是 36 个。附录图 7 逐个列出的领域名也是 36 个。这两处和 37 差一个，论文没有解释。评测时有没有把领域的列表交给模型，论文没有写明。出处：Gorilla 在 NeurIPS 2024 发表的版本。
  • 新增工具要不要再训练。对照两个方向的那张配图在第五部分。图上「改模型去适应工具」一栏写的是 Toolformer、ToolkenGPT、Gorilla 三个名字，后面跟着「每个新 API 都要再训练一次」（every new API means another training），没有列 ToolLLM。ToolLLM 的论文写的是，ToolLLaMA 能用好训练时没见过的 API，只需要这些 API 的文档（原文是 requiring only the API documentation to adapt to new APIs）。论文主表的六组测试题里，有三组用的是微调时没见过的工具。所以正文把「每新增一个工具都要再训练」只写在 Toolformer、ToolkenGPT 和 Gorilla 这三种方法上，ToolLLM 按论文的说法单独写。出处：Qin 等，2023。
  • 对照表里的模型名称和参数量。四种方法的配图把 Toolformer 的模型写成 GPT-J 6B，把 ToolLLM 的模型写成 LLaMA 7B。按各自的论文，GPT-J 是 67 亿参数，ToolLLM 微调的是 LLaMA-2 7B，对照表按论文填写。
