先看结论

  • 工具使用可以分三层来评估：单次调用写得对不对，多步调用能不能把一件事办成，一边和用户对话一边调用工具时是否守规矩、是否每次都可靠。BFCL、ToolBench 和 τ-bench 这三个基准测试（benchmark，一组题目加一个打分的办法）各自侧重一层。
  • BFCL 用语法树匹配来判单次调用，不需要真的执行函数。多轮的题目还要检查环境最后的状态，以及必要的函数有没有调用过。
  • τ-bench 提出了 pass^k：同一个任务独立做 k 次，k 次全部成功才算数。按这个指标，单次成功率超过 60% 的 agent（能自己调用工具、分很多步去完成任务的语言模型系统），连做 8 次全对的比例不到 25%。
  • 这些基准测试自己也有问题。ToolBench 用的真实 API（应用程序接口，一个程序提供给别的程序调用的入口），后来重新调用时只有 44.4% 能成功。τ-bench 的航空任务里，什么都不做的 agent 能拿 38%。
  • 常见的失败可以归成三组八种：单次调用的三种，多步调用的两种，对话中的三种。

三个基准测试，各考一层

评估 agent 用工具用得好不好，可以从简单到复杂分成三层。

BFCL：函数调用的排行榜

BFCL 的全称是 Berkeley Function-Calling Leaderboard（伯克利函数调用排行榜），由做 Gorilla 的同一个团队维护，论文发表在 ICML 2025。它评的是模型调用函数（也叫调用工具）的能力，是查「哪个模型函数调用做得好」时最常用的参考。

{{fig 58 | 2025 年 11 月的排行榜截图，只显示了前五名。每一行是一个模型，从左到右是总分、花费，以及五个分项的准确率。图片来源：BFCL 排行榜。}}

读这张表要知道三件事。

  • 模型名后面的 FC 和 Prompt。FC 表示用的是模型自带的函数调用功能。Prompt 表示没有用这个功能，是在 prompt（交给模型的输入文字）里要求模型把调用写成文字。同一个模型用两种方式测，成绩可以不同。GLM-4.6 后面的 thinking 是榜上原有的标注，很可能表示测试时打开了模型的思考模式，排行榜的说明里没有解释这个词。
  • 花费一列。它是把整个基准测试跑一遍的估计花费。第三名和第四名的总分只差 0.13 分，花费是 298.47 美元和 4.64 美元，相差约 64 倍。
  • 分项的差别比总分大。五个模型在单轮固定题目上都在 87 到 91 之间，几乎分不出高下。多轮在 58 到 69 之间，记忆在 53 到 74 之间。论文的结论也是这样：最好的模型在单轮调用上已经很强，记忆、动态决策和长程的推理仍然是没解决的问题。

题目从哪来，怎么判分

BFCL 是分几个版本逐步扩充的。第一版只有单轮的题，用语法树来判分。第二版加入了用户和企业贡献的真实函数。第三版加入多轮对话。第四版加入网页搜索、记忆这类 agent 任务。

语法树匹配的好处是不用真的执行函数，所以能扩展到上千个函数。论文用一部分可执行的题目做了对照，两种判法的结果高度相关。多轮的题为什么要两项检查：只看最后的状态，查不出模型有没有调用那些只读取、不改动状态的函数。例如应该先按城市查邮编、再按邮编查天气，模型如果直接猜一个结果，状态检查发现不了。

{{fig 60 | 左：三类单轮题的例子。右：题目的构成，从里到外是大类、判分方式和具体的类型，括号里是题数。}}

第三类考的是模型在没有合适工具时能不能停手。排行榜把这一类的成绩单独算作「幻觉度量」：给了不相关的函数还硬要调用，就是在编造。

ToolBench：多步调用办成一件事

第四部分讲过 ToolBench 是怎么构造的：16,464 个来自 RapidAPI 的真实 API，加上 ChatGPT 生成的指令。它也被用作基准测试，考模型能不能连续调用几个 API 来完成一条指令。配套的评分工具叫 ToolEval。

这里的判分比单次调用难。API 的返回会随时间变化，完成一条指令的走法也不止一种，所以没法给每道题标一条固定的标准路径。ToolEval 的办法是让 ChatGPT 当评审，报告两个数。

+
用真实的线上 API 出题，成绩过几个月就复现不了。2024 年的 StableToolBench 论文重新检查了 ToolBench。他们把数据集里的 API 重新调用了一遍，只有 44.4% 的调用成功。在全部调用里，25.9% 因为本地文档解析出错而失败，14.8% 连不上，6.4% 没有授权，其余的失败是接口找不到或参数变了。他们按原来的设置重跑，得到的通过率和原论文报告的也对不上。此外，用 gpt-3.5 当评审，同一批结果重复评几次，分数会波动。他们的改法是给 API 加一层缓存和模拟，并换用 GPT-4 当评审。出处：Guo 等，2024。

τ-bench：工具、agent 和用户三方

τ-bench 是 Yao 等人 2024 年提出的基准测试。它在工具和 agent 之外加入了第三方：用户。agent 扮演客服，用户可能想取消航班，也可能想改签，agent 要弄清对方想要什么，再用正确的工具把事情办了。

{{fig 63 | 左：τ-bench 的构成。上面是工具，中间是 agent 和写在系统提示里的规定，下面是用户和给用户的指示。右：航空领域的一段对话。用户想改签，agent 查了订单，发现是不能改签的基础经济舱，但订票还不到 24 小时，可以取消后重订；用户同意取消，agent 调用取消订单的工具，数据库被改写。图片来源：Yao 等，2024。}}

评分看两项，两项都对才算成功：对话结束时的数据库和标注的结果完全一致；agent 对用户说的话里包含了必须告知的信息。评分不看 agent 中间调用了哪些工具。第 13 讲会从基准测试设计的角度再讲到这个评分办法。

pass^k：每次都要做对

agent 每次运行的结果有随机性。同一个任务，这次成功了，下次不一定。怎么把多次运行的结果汇总成一个数，有两种相反的做法。

{{fig 64 | 上：两个指标的计算公式。下：τ-bench 两个领域的数据规模。}}

举一个数：某个任务跑了 8 次，成功 6 次，取 k 等于 2。从 8 次里选 2 次有 28 种选法，从 6 次成功里选 2 次有 15 种，所以这个任务的 pass^2 是 15 除以 28，约 0.54。两次都失败的选法只有 1 种，所以 pass@2 是 27 除以 28，约 0.96。同一组实验数据，两个指标给出的印象完全不同。

做客服的 agent 应该用 pass^k 来衡量。用户通常只试一次。这一次没办成，对他来说就已经是一次失败的服务，再试几次里有一次能成功也改变不了这一点。下面的表按「每次运行互相独立、成功的机会相同」这个假设，算了几个例子。

τ-bench 发布时的成绩

{{fig 65 | 左：各个模型的 pass^1，也就是平均成功率。右上：零售领域里三种做法的对比。右下：零售领域里 pass^k（实线）和 pass@k（虚线）随 k 的变化。图片来源：Yao 等，2024。}}

从图和表里可以读出三点。

  • 当时最好的模型，一半的任务办不成。gpt-4o 两个领域平均 48.2%。论文把航空称为更难的领域，gpt-4o 在航空上只有 35.2%，零售是 61.2%。也有例外：论文表 2 的 12 个模型里，有 3 个在航空上的成绩比零售高。
  • 用函数调用比在 prompt 里约定格式好。右上的图比较了三种让模型调用工具的做法：自带的函数调用功能（FC），先写想法再写动作的 ReAct，以及只写动作（Act）。图里的四个模型上，函数调用的成绩都最高。
  • 两个指标随 k 的走向相反。右下的图里，虚线的 pass@k 随 k 上升，较强的几个模型到 k 等于 8 时约 90%，gpt-3.5-turbo 约 45%；实线的 pass^k 一路下降。gpt-4o 在零售领域单次成功率超过 60%，pass^8 掉到了 25% 以下。
i
为什么实测的 pass^8 比上一节表里算的 1.7% 高得多。上一节的表假设每个任务每次成功的机会都是 60%。实际的任务难度不同，论文附录里按任务画出的成功率（用的是 gpt-4-turbo）也是有高有低。很可能的解释是：有一批任务 agent 几乎每次都能做对，另一批几乎每次都做错，剩下的时对时错。pass^8 先在每个任务上算，再取平均，那批稳定做对的任务让平均值远高于 1.7%。可以这样理解：pass^k 量出的是「有多少任务能稳定做对」。

τ-bench 后来查出的问题和后续版本

τ-bench 是自动评分的，但这不等于分数没有问题。Zhu 等人 2025 年的论文检查了 10 个常用的 agent 基准测试，在 τ-bench 里发现了两处。

  • 什么都不做也能得分。航空领域有 38% 的任务故意设计成办不了，比如改签一张不能退改的机票。这类任务的成功标准是数据库没有被改动。一个只返回空回答的 agent 在航空任务上拿到 38%，比当时基于 GPT-4o 的 agent 还高。
  • 把所有信息都说一遍也能得分。「必须告知的信息」是按回复里有没有出现那几个字来检查的。agent 把可能的答案全部列出来，也能匹配上。

出处：Zhu 等，2025。第 13 讲会更详细地讲到这两处。

整讲的小结

  • 为什么要工具。有些事模型算不准，有些事它在训练时没见过，有些地方它够不着。
  • Toolformer。模型自己教自己该调用哪个 API、什么时候调用、传什么参数。
  • Gorilla。在 1,600 多个 API 上训练，并用语法树匹配来度量编造。
  • REST、函数调用、MCP。从模型手写请求，发展到应用在运行时用 tools/list 取工具、用 tools/call 调用工具。
  • BFCL、ToolBench、τ-bench。分别考单次调用、多步调用，以及工具、agent 和用户三方的交互。
  • 失败模式。选错工具，编造参数，顺序错，以及做对一次、下次又错。

把这几条连起来看：让模型用上工具这件事，重心已经从「训练模型认识每一个工具」移到了「给工具定一个任何模型都能读的接口」。接口统一之后，工具可以随时增减，剩下的难点是可靠性：调用是模型生成的文字，它会出错，所以每一层都要有对应的检查和评估。
