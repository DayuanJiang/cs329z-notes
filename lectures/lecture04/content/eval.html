先看结论

  • 工具使用可以分三层来评估。第一层是单次调用写得对不对，第二层是多步调用能不能把一件事办成。第三层是模型当客服、一边和用户对话一边调用工具时，是否按公司写给它的业务规定办事、是否每次都可靠。BFCL、ToolBench 和 τ-bench 这三个基准测试（benchmark，一组题目加一个打分的办法）各自侧重一层。
  • BFCL 主要用语法树匹配来判单次调用：把模型写的调用按语法结构拆开，和参考答案比较函数名和各个参数。参考答案是出题的人事先为每道题写好的正确结果。这种判法不需要真的执行函数，只有一部分题另外真的去执行。
  • BFCL 的多轮题是一段对话里用户先后提出几个请求，用户每发来一条消息算一轮，一轮里模型可以调用好几次函数。题里的函数运行在一个模拟的系统上，比如文件系统，调用会改动系统里的内容。这类题在每一轮结束后都要检查两件事：这一轮的调用全部做完之后，系统里的内容和参考答案是否一致，以及参考答案里必要的函数有没有调用过。
  • τ-bench 提出了 pass^k：同一个任务独立做 k 次，k 次全部成功才算数。τ-bench 发布时成绩最好的 agent（能自己调用工具、分很多步去完成任务的语言模型系统）用的是 gpt-4o。它在零售领域的任务上单次成功率超过 60%，连做 8 次全部成功的概率却不到 25%。
  • 这些基准测试自己也有问题。ToolBench 用的真实 API（应用程序接口，一个程序提供给别的程序调用的入口），后来逐个重新调用时只有 44.4% 的 API 能调用成功。τ-bench 的航空任务里，什么都不做的 agent 成功率也能达到 38%。
  • 常见的失败可以归成三组八种：「单次调用」这一层三种，「多步调用」这一层两种，「和用户对话」这一层三种。

三个基准测试，各考一层

评估 agent 用工具用得好不好，可以从简单到复杂分成三层。

BFCL：函数调用的排行榜

BFCL 的全称是 Berkeley Function-Calling Leaderboard（伯克利函数调用排行榜）。它评的是模型调用函数（也叫调用工具）的能力，按成绩给各个模型排名。BFCL 的论文自己的说法是，它已经成为评估函数调用的事实标准（de facto standard）。

BFCL 由做出 Gorilla 的团队维护。Gorilla 是第四部分讲的那个为调用机器学习 API 而微调的模型，微调是在已经训练好的模型上用新数据继续训练。BFCL 的论文发表在 ICML 2025，ICML 是机器学习领域的一个主要学术会议。

排行榜除了总分和花费，还给出五个分项的准确率。单轮的两项考的是一问一答地写出调用，题目分别是作者选的固定题和用户贡献的题。多轮考的是一段对话里用户先后提出几个请求，用户每发来一条消息算一轮。网页搜索和记忆考的是用搜索工具回答问题，和在多次对话之间记住信息。各类题目的细节见后面的「题目从哪来，怎么判分」。

按用户的消息来算，一轮里模型可以先后调用好几次函数、读好几次返回的结果，BFCL 的论文把其中的每一次叫作一步（step）。第三部分说现在的 agent 一轮一轮地工作，第四部分说模型一轮一轮地调用 API。那两处的一轮指模型读一次输入、写出一次输出，相当于这里的一步。

读这张表要知道三件事。

题目从哪来，怎么判分

BFCL 是分几个版本逐步扩充的。第一版只有单轮的题，用语法树来判分。第二版加入了用户贡献的题目，题里的函数和提问都来自用户和企业的实际使用。第三版加入多轮对话。第四版加入网页搜索、记忆这类 agent 任务。

下表列出各类题目的内容和判分办法。其中多轮题的函数运行在一个模拟的系统上，例如文件系统、股票交易系统或订票系统。有的函数会改动系统里的内容，例如新建一个文件、从自选股里删掉一只股票。表里说的系统的状态，指一轮里的调用全部做完之后系统里的内容。

语法树匹配的好处是不用真的执行函数，所以能扩展到上千个函数。论文用一部分可执行的题目做了对照，两种判法的结果高度相关。

多轮的题要做两项检查，是因为只看每一轮结束时的状态，查不出模型有没有调用那些只读取、不改动状态的函数。例如应该先按城市查邮编、再按邮编查天气，模型如果直接猜一个结果，状态检查发现不了。

ToolBench：多步调用办成一件事

ToolBench 是 ToolLLM 的数据集。ToolLLM 是 Qin 等人 2023 年提出的方法：用 ChatGPT 生成的数据微调一个开源模型，让它会调用 RapidAPI（一个汇集了大量第三方 API 的平台）上的真实 API。第四部分讲过这个数据集是怎么构造的：16,464 个来自 RapidAPI 的真实 API，加上 ChatGPT 生成的指令。

ToolBench 也被用作基准测试，考模型能不能连续调用几个 API 来完成一条指令。配套的评分工具叫 ToolEval。

这里的判分比单次调用难。API 的返回会随时间变化，完成一条指令的调用顺序也不止一种，所以没法给每道题写一份固定的参考答案。ToolEval 的办法是让 ChatGPT 当评审，报告两个数。

+
ToolBench 里的 API 后来只有不到一半能调用成功，成绩也复现不了。2024 年的 StableToolBench 论文重新检查了 ToolBench。他们把数据集里的 16,464 个 API 逐个重新调用了一遍，只有 44.4% 的 API 调用成功。论文按原因把调用失败的 API 分成几项，下面的百分比都是占全部 API 的比例。最多的一项占 25.9%，是数据集自己的问题。论文把它叫作解析错误（parsing error），只说明它是数据集保存在本地的 API 文档在后处理时出错造成的。另外几项是这些 API 的线上服务后来变了或用不了：14.8% 连不上，6.4% 没有授权，3.6% 参数变了，3.5% 接口找不到。还有 1.4% 归为其他原因。他们按原来的设置重跑，得到的通过率和原论文报告的也对不上。出处：Guo 等，2024。
+
让语言模型当评审，分数也会波动。同一篇论文还发现，用 gpt-3.5 当评审，也就是 ToolEval 原来用的 ChatGPT，同一批结果重复评几次，分数会波动。出处同上。
+
StableToolBench 针对上面两个问题各做了一项改动。针对 API 调不通，他们在模型和真实的 API 之间加了一个虚拟的 API 服务器，模型的调用都发给它。它先查缓存。缓存里存着以前调用得到的返回，同样的调用再来时，直接给出存下的返回。缓存里没有，就去调用真实的 API。真实的 API 也调不通时，由一个语言模型按这个 API 的文档写出一份模拟的返回，论文用的是 gpt-4-turbo。针对评审的分数波动，他们换用 GPT-4 当评审。出处：Guo 等，2024。

τ-bench：工具、agent 和用户三方

τ-bench 是 Yao 等人 2024 年提出的基准测试。它在工具和 agent 之外加入了第三方：用户。论文把这叫作工具、agent 和用户三方的交互，也就是前面三层里「和用户对话」的那一层。agent 扮演客服，用户可能想取消航班，也可能想改签，agent 要弄清对方想要什么，再调用正确的工具完成用户的请求。

公司的规定写在 agent 的系统提示里。系统提示（system prompt，也叫系统消息）是每次对话开始前交给模型、交代它的角色和规则的那段文字。下面的图和表说明 τ-bench 由哪几部分组成。

{{fig 63 | 左：τ-bench 的构成。上面是工具，中间是 agent 和写在系统提示里的规定，下面是用户和给用户的指示。右：航空领域的一段对话。用户想改签，agent 查了订单，发现是不能改签的基础经济舱，但订票还不到 24 小时，可以取消后重订。用户同意取消，agent 调用取消订单的工具，数据库被改写。图片来源：Yao 等，2024。}}

τ-bench 的任务分零售和航空两个领域。零售领域有 115 个任务，7 个会改动数据库的工具和 8 个只读的工具。航空领域有 50 个任务，6 个会改动数据库的工具和 7 个只读的工具。

评分看两项，两项都对才算成功。一是对话结束时的数据库和参考答案里的数据库完全一致。二是 agent 对用户说的话里包含了必须告知的信息。评分不看 agent 中间调用了哪些工具。第 13 讲会从基准测试设计的角度再讲到这个评分办法。

pass^k：每次都要做对

agent 每次运行的结果有随机性。同一个任务，这次成功了，下次不一定。怎么把多次运行的结果汇总成一个数，有两种相反的做法。

{{fig 64 | 上：两个指标的计算公式。下：τ-bench 两个领域的数据规模。}}

举一个数：某个任务跑了 8 次，成功 6 次，取 k 等于 2。估计的办法是从这 8 次已有的运行里随机抽 2 次，看抽到的是什么结果。从 8 次里选 2 次有 28 种选法，从 6 次成功里选 2 次有 15 种，所以这个任务的 pass^2 是 15 除以 28，约 0.54。两次都失败的选法只有 1 种，所以 pass@2 是 27 除以 28，约 0.96。同一组实验数据，两个指标给出的印象完全不同。

做客服的 agent 应该用 pass^k 来衡量。每个用户通常只试一次，这一次没办成，对他来说就已经是一次失败的服务，再试几次里有一次能成功也改变不了这一点。同一种请求会有很多用户各提一次，agent 要对每个人都办成，所以要看它连做 k 次是不是都成功。

下面的表是另一种算法。它假设每次运行互相独立、成功的概率相同，按这个概率算出连做 8 次的结果，没有用到实验数据。

i
为什么实测的 pass^8 比上一节表里算的 1.7% 高得多。实测的数是 gpt-4o 在零售领域的 pass^8，接近 25%。1.7% 出自上一节表里 60% 的那一行，那一行假设每个任务每次成功的概率都是 60%。实际的任务难度不同，论文附录里按任务画出的成功率（用的是 gpt-4-turbo）也是有高有低。很可能的解释是：有一批任务 agent 几乎每次都能做对，另一批几乎每次都做错，剩下的时对时错。pass^8 先在每个任务上算，再取平均，那批稳定做对的任务让平均值远高于 1.7%。可以这样理解：pass^k 量出的是「有多少任务能稳定做对」。

τ-bench 后来查出的问题和后续版本

τ-bench 的自动评分后来被查出了问题。Zhu 等人 2025 年的论文检查了 10 个常用的 agent 基准测试，在 τ-bench 里发现了两处。

  • 什么都不做也能得分。航空领域有 38% 的任务故意设计成办不了，比如改签一张不能退改的机票。这类任务的成功标准是数据库没有被改动。一个只返回空回答的 agent 在航空任务上的成功率是 38%。Zhu 等人指出，这比 τ-bench 论文里基于 gpt-4o 的 agent 还高。前面的成绩表里，gpt-4o 在航空上的单次成功率是 35.2%。
  • 把所有信息都说一遍也能得分。参考答案里列出了必须告知的信息，每一条是一小段文字。检查时只看 agent 的回复里有没有原样出现这些文字。agent 把可能的答案全部列出来，也能通过检查。

出处：Zhu 等，2025。第 13 讲会更详细地讲到这两处。

整讲的小结

这一讲回答了六个问题，下面每个问题各收成一条。

  • 检索回来的内容，模型都用得上吗。不一定。答案所在的文档排在长输入的中间时最容易被漏掉。多给文档，准确率很快就不再提高。模型给出的引用也可能对不上。
  • 为什么要工具。有些事模型算不准，有些事它在训练时没见过，有些东西它自己接触不到。
  • 模型怎样学会调用工具。靠训练，这一讲讲了两种训练方法。Toolformer 让模型自己在普通文本里试着插入工具调用，只留下看了调用结果之后能把后面的文字预测得更准的那些调用，再用留下的文本微调。模型由此学会该调用哪个工具、什么时候调用、传什么参数、怎么把结果用进后面的文字。ToolkenGPT 把每个工具做成一个新的 token（模型处理文字的最小单位），只训练它的向量，也就是模型给这个 token 准备的一串数字。
  • 工具多到上千个怎么办。ToolLLM 这种方法用 ChatGPT 生成训练数据，这批数据就是 ToolBench，里面有 16,464 个真实 API。Gorilla 这个模型在 1,600 多个 API 上训练，并用语法树匹配来度量编造，也就是模型调用了一个不存在的 API。连同上一条的两种，这四种做法都靠训练让模型学会用工具。其中 Toolformer、ToolkenGPT 和 Gorilla 每新增一个工具都要再训练。ToolLLM 的论文报告，它微调出的模型 ToolLLaMA 读了 API 文档就能用上训练时没见过的 API，但 ToolLLaMA 仍然是在一批收集来的 API 上微调出来的。
  • 工具怎样接到任何模型上。靠标准接口，也就是把工具描述成统一的格式，让模型在运行时读了就能用。接口有三代。REST 是按网址用 HTTP 请求去读写资源的网络接口，它的文档是写给人看的，模型要读文档、自己写出完整的请求。函数调用是模型厂商提供的功能，每个工具的描述按固定的格式交给模型，模型只输出要调用的工具名和参数。MCP 是一套协议，规定 AI 应用怎样向提供工具的服务器取工具列表、发起调用：取列表的请求叫 tools/list，调用工具的请求叫 tools/call。
  • 怎样评估，常见哪些失败。BFCL、ToolBench、τ-bench 分别考单次调用、多步调用，以及和用户对话。常见的失败归成三组八种，其中有选错工具，参数填错，顺序错，以及做对一次、下次又错。

把这几条连起来看：让模型用上工具这件事，重心已经从「训练模型认识每一个工具」移到了「给工具定一个任何模型都能读的接口」。接口统一之后，工具可以随时增减，剩下的难点是可靠性：调用是模型生成的文字，它会出错，所以每一层都要有对应的检查和评估。

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • BFCL 排行榜的数字。表里的数字读自 2025 年 11 月的截图。排行榜之后更新过，这里没有和现在的页面逐项核对。
  • GLM-4.6 下面的 thinking。这个词是榜上原有的字样，排行榜的说明里没有解释它。正文把它写成「很可能表示打开了思考模式」，是按字面作的推测。
  • ToolBench 的 44.4% 是按什么算的。StableToolBench 论文的正文写的是「only 44.4% of API calls are successful」，没有说明分母。附录的表 10 按 API 的个数列出三种结果：调用成功的 7,311 个，不可用的 8,095 个，没有授权的 1,058 个。三项相加是 16,464，正好是 ToolBench 的 API 总数，所以 44.4% 和 ToolBench 一节说明框里各项的百分比，都是占全部 API 的比例，每个 API 算一次。表 10 里「不可用」的 8,095 个占 49.2%，是说明框里解析错误、连不上、参数变了、接口找不到和其他原因这五项的合计。「没有授权」的 1,058 个就是说明框里的 6.4%。出处：Guo 等，2024。
  • τ-bench 修正了多少个任务。「50 多个任务」来自版本时间线的配图。航空 27 个、零售 26 个出自 tau2-bench 1.0.0 版的发布说明，合计 53 个，和配图的「50 多个」对得上。同一份发布说明的小结里还有一个数「75+ task fixes across all domains」，范围是所有领域。它比 53 多出来的部分指什么，发布说明没有写明。
