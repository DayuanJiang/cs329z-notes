先看结论

  • 在 agent 里，语言模型只是中间的一个部件，它的输出要交给工具、数据库和别的程序。agent 指能自己调用工具、分很多步去完成一个任务的语言模型系统。部件之间需要事先约定好数据的格式。
  • 约束解码（constrained decoding）在生成的每一步只允许合法的 token，从机制上保证输出符合格式。token 是模型处理文字的最小单位。SGLang 这个库做约束解码时，把格式里固定不变的几个 token 直接填上，不再为它们调用模型，所以比每个 token 都调用一次模型的普通做法更快。
  • 另一种办法是在 prompt（交给模型的那段输入文字）里把格式写清楚，再用程序去解析模型的回答。DSPy 这个库把这件事自动化了：使用的人只声明输入和输出各有哪些字段，这份声明叫 signature，写 prompt 和解析回答都由库来做。
  • 如果只需要模型在几个选项里选一个，可以不让它生成文字：在模型上接一个分类头，或者把当前状态和候选动作都变成向量来比较。分类头是接在模型上的一个很小的分类器。状态指模型当前面对的情况，比如一幅游戏画面或一段文字。候选动作是这一步可以选的几个选项。

模型在 agent 里的位置

前面六个部分讲的都是语言模型本身。在一个 agent 里，它处在中间。

{{fig 150 | agent 的几个组成部分。中间红框里是 LLM Core，也就是语言模型。上面是规划和思考（图里写作 Planning & Reasoning）、记忆，下面是工具（检索、计算器、代码、搜索、文件操作等）和 agent 的动作（调用工具、交互、回复用户）。右边是外部环境，agent 从环境里观察，再对环境采取行动。}}

模型从上面和右边拿到输入，把输出交给下面的工具和动作。接它输出的是程序，程序只能处理事先约定好的格式。模型的输入和输出各自应该是什么结构，这个主题叫结构化的输入输出（Structured I/O）。这一部分讲其中输出这一半，要回答的问题是：怎样让模型的输出符合事先约定好的格式。交给模型的输入里放什么、怎么放，第八部分再讲。

为什么需要结构化的输入输出

原因在于现在的 AI 应用很少只有一个模型，通常是好几个部件配合工作。

{{fig 152 | 左边是一个单独的神经网络，右边是由几个模型、检索、数据库、计算器、终端组成的系统。下面一行字是：越来越多新的 AI 成果来自复合系统。图片来源：伯克利人工智能研究实验室（缩写 BAIR）的博客文章，2024 年 2 月。}}

这张图出自伯克利人工智能研究实验室 2024 年的一篇博客文章，文章把这类系统叫作复合 AI 系统（compound AI system）。文章给的定义是：用多个相互配合的部件来完成 AI 任务的系统，这些部件包括对模型的多次调用、检索器和外部工具。

部件之间要来回传数据，就需要一份共同的约定，规定数据长什么样。程序之间传数据靠的是固定的格式，比如 JSON（一种用花括号、引号和冒号组织数据的文本格式）。语言模型默认输出的是自由的文字。如果它多写了一句开场白，或者少了一个引号，接它输出的程序就会出错。

约束解码：每一步只允许合法的 token

约束解码的想法是：既然输出必须符合某个格式，那就在生成的每一步，把不符合格式的 token 的概率直接设成零，模型只能在合法的 token 里选。名字里的解码，指模型一个 token 一个 token 往后生成输出的过程。

怎样知道每一步哪些 token 合法？常见的做法是先把格式写成一个正则表达式（描述字符串样式的一种规则），再把它转换成一个有限状态机（FSM）。有限状态机是一张图：图上有若干个节点，每读到一个字符就从一个节点走到下一个节点，从每个节点出发能走的路是规定好的。名字里的「状态」指的就是这些节点，和这一页开头说的模型当前面对的情况是两回事。下面把它们都叫节点。

状态机是按字符走的，模型选的是 token，一个 token 可能含好几个字符。所以一个 token 合不合法，要看从当前节点出发，它的字符能不能沿着状态机一步步走下去。解码时一直记着当前在哪个节点，下一步只允许能接着走下去的 token。

{{fig 153 | 假设输出必须以一段固定的文字开头：左花括号、引号、summary、引号、冒号、空格、引号。(a) 普通的状态机，每个字符一步。(b) 把这一整串合并成一步的状态机。(c) 用普通状态机解码：黄色方块是生成出来的 token，绿色六边形是一次模型调用，每生成一个 token 就要调用一次模型。(d) 用合并后的状态机解码：固定的这几个 token 直接填上，之后才调用模型。图片来源：Zheng 等，2023。}}

图里的例子说明了一件容易忽略的事。那段固定的开头有好几个 token，每个位置上合法的 token 都只有一个。普通的做法仍然是一个 token 调用一次模型，其实答案早就确定了。SGLang 这个库的做法是把状态机里这种「只有一条路可走」的连续几步合并成一步，直接把这几个 token 填上，只有下一个 token 不确定时才调用模型。如果某个位置有两三个合法的选择，也只需要在这两三个 token 里比较概率。

到这里一共有两个好处，来源不同。

  • 格式一定对。这是约束解码本身的好处：不合法的 token 根本选不到。
  • 更快。这是 SGLang 合并状态机带来的好处：省掉了那些结果早已确定的模型调用。

SGLang 的论文拿它和三个用来对比的系统比了吞吐量，也就是单位时间里处理的请求量。这三个系统是 vLLM、Guidance 和 LMQL。vLLM 是一个推理引擎，也就是负责运行模型、处理生成请求的程序。Guidance 和 LMQL 是两种给语言模型写程序、控制它怎样输出的语言。

{{fig 154 | SGLang 和三个用来对比的系统（vLLM、Guidance、LMQL）在 11 种任务上的吞吐量。用的模型是 Llama-7B，论文里指 Meta 的 Llama 2 的 70 亿参数版本。每组柱子都把最高的那个记作 1，其余的按比例换算，越高越好。横轴上的任务包括 agent、解数学应用题、JSON 解码、多轮对话等，其中 JSON 解码指让模型按一个用正则表达式规定的格式生成 JSON。图片来源：同上。}}

论文报告，SGLang 的吞吐量最高是对比系统的 6.4 倍，对比的系统包括上图里的 vLLM、Guidance 和 LMQL。论文没有写明这个最高的倍数出自哪一种任务、是和哪一个系统比出来的。

这个 6.4 倍是几项优化合起来的结果，合并状态机只是其中一项。单看合并状态机这一项：在 JSON 解码的测试上，用合并后的状态机时，吞吐量是不合并时的 1.6 倍。另一项优化和第五部分的 KV cache（推理时保存下来重复使用的中间结果）有关：不同的请求如果开头相同，就自动接着用同一份缓存。

i
约束解码只保证格式，不保证内容正确。对于字段固定、能用正则表达式写出来的格式，它能保证输出的 JSON 合法，字段齐全、类型正确。可以任意深度嵌套的结构，比如一条评论下面还能一层层嵌套回复的数据，有限状态机表达不了，要换用能描述嵌套结构的约束解码工具。字段里填的值是否符合事实，仍然取决于模型。

用 prompt 规定格式：DSPy 的 signature

另一种办法是不动解码过程，在 prompt 里把想要的格式讲清楚，再用程序把模型的回答解析成结构化的数据。DSPy 这个库把这件事包装成了 signature：像写函数签名那样，声明输入有哪些字段、输出有哪些字段、各是什么类型。

{{fig 155 | 左边是一段 DSPy 代码：定义一个叫 Extract 的 signature，再用它处理一条消息。右边是得到的结果，三个输出字段各有一个值。图片来源：DSPy 官网。}} 
class Extract(dspy.Signature):
    """Extract contact info."""
    message: str = dspy.InputField()
    name: str = dspy.OutputField()
    email: Optional[str] = dspy.OutputField()
    intent: Literal["meeting", "intro", "follow-up"] = dspy.OutputField()

extract = dspy.Predict(Extract)
extract(message="I'm Sarah (sarah@acme.co). Meet Thursday?")

这段代码声明了一个输入字段 message 和三个输出字段：name 是字符串，email 是字符串或者空，intent 只能是 meeting、intro、follow-up 三个值之一。交给它的是一条消息，消息里写着「我是 Sarah（sarah@acme.co）。周四见面？」，邮箱就在这条消息里。得到的结果是 name 为 Sarah、email 为 sarah@acme.co、intent 为 meeting。使用的人只写了一句任务说明「Extract contact info」，关于格式的 prompt 一句也没有写。

{{fig 156 | DSPy 实际发给模型的内容。蓝色部分是 system prompt（放在对话最前面、设定模型行为的那段文字）。这段 system prompt 列出输入字段和输出字段的名字和类型，规定每个字段前面要有一行形如 [[ ## 字段名 ## ]] 的标记，并对 email 和 intent 的取值写了具体要求，最后是任务本身「Extract contact info」。灰色部分是用户 prompt：填进了那条消息，并再次要求按顺序输出各个字段，最后以 completed 标记结束。图里的方括号标记是 DSPy 较早的默认格式，现在文档里默认用的是 XML 标签。}}

可以看到，DSPy 在背后做了三件事：把 signature 翻译成一段详细规定格式的 prompt；把输入填进去，发给模型；按约定的标记把模型的回答拆开，取出每个字段的值。按 DSPy 文档的描述，做这些事的部件叫 adapter：它把 signature 和输入变成发给模型的消息，再把模型的回答解析成输出字段。

这种办法默认靠的是「说清楚，再解析」，格式没有硬性的保证。模型如果没有照格式回答，解析就会失败。约束解码从机制上保证格式，这种办法靠 prompt 说明和事后解析，两种办法可以叠加：格式由 prompt 说明，解码时再加约束。

只要一个类别时：在模型上接一个分类头

有时需要的输出只是几个类别里的一个，比如一句话的情感是正面还是负面。这时可以不让模型生成文字。

{{fig 157 | 两个模型串在一起。下面的 DistilBERT（一个小型的语言模型）读入一句影评「a visually stunning rumination on love」，输出一个向量。上面的逻辑回归模型（一种简单的分类模型）拿这个向量，输出两个类别的概率：负面 15%，正面 85%。图片来源：Jay Alammar 的文章。}}

做法是：让语言模型把整句输入变成一个向量，图里是 768 维，再在上面接一个很小的分类器，叫分类头（head），把向量变成每个类别的分数。这些分数再换算成加起来等于 1 的概率，就是图里的负面 15% 和正面 85%，概率最高的类别就是输出。分类头是用带标签的数据单独训练的，图里的例子用的是影评情感数据集 SST-2。

语言模型输出的这种代表一整段文字的向量也叫 embedding，它和第二部分里每个 token 各有一个的词向量是两样东西。

这样得到的输出只可能是事先定好的那几个类别之一，不存在格式出错的问题，而且只需要过一遍模型，不用一个 token 一个 token 地生成。在一个大的系统里，语言模型完全可以只当一个分类器来用。

System One 模型：把状态和候选动作变成向量来比较

上一节的分类头有一个限制：类别在训练时就固定下来，换一组类别就要重新训练。agent 要选的东西常常会变，比如工具清单就经常变。这一节讲的 System One 模型没有这个限制：它的选项在每次使用时临时给出，可以随时更换。这些临时给出的选项就是页首说的候选动作。

System One 这个名字借用了心理学里的说法：系统一指快速、凭直觉的判断，系统二指缓慢、一步步的思考。2026 年这个词被用来称呼一类模型，大致可以理解为：选项可以随时更换的分类器，专门用来快速做决定。

下面是一个公开的例子：斯坦福大学和 NVIDIA 的研究者 2026 年 9 月公开的 Contrastive Language Models。它的项目页面把自己叫作 System One 模型。它的做法就是这一页开头列的第四种办法：把状态和候选动作都变成向量来比较。

{{fig 158 | Contrastive Language Models 的做法，分三步。1：对比学习，状态编码器把游戏画面变成向量，动作编码器把动作的文字变成向量，训练时让每个画面的向量靠近当时实际采取的那个动作的向量。2：把候选动作（左、跳、向右跑）写成文字，交给动作编码器。3：用当前画面的向量和每个候选动作的向量做点积，再做 softmax（把分数变成加起来等于 1 的概率），图里「跳」得到 80%，于是马里奥跳起来。点积是把两个向量对应位置的数相乘再加起来，得到的数越大，两个向量越接近。图片来源：Contrastive Language Models 的项目页面。}}

它和分类头的不同列在下表。

这种做法也能用在语言任务上。图里的状态是游戏画面。换成语言任务，状态就是一段文字，候选动作可以是选择题的几个选项、正面和负面两个情感标签，或者一份工具清单里的各个工具。工具清单经常变，所以它适合用来选工具。

成绩和延迟方面，项目页面的概述里是这样一句话：在电脑操作、游戏和工具调用这三类任务上，它的表现和一个叫 Jev 的模型相当，延迟最多降到 Jev 的九分之一左右。延迟是做一次决定要等的时间。

这句话没有写明表现用的是哪一个指标，也没有写明九分之一出自哪一类任务。页面也没有介绍 Jev 是什么模型。这些是项目自己报告的结果。

最典型的场合：调用工具

结构化输出在 agent 里最重要的用处是调用工具。模型要表达的是「现在调用哪个工具、参数是什么」，这段输出必须能被程序准确地解析出来。

{{fig 159 | 四段文字，每段中间夹着一次工具调用，用颜色标出。方括号里先写工具的名字和参数，后面跟着工具返回的结果。四个工具分别是问答系统（QA）、计算器（Calculator）、翻译（MT）和维基百科搜索（WikiSearch）。例如第二段：1400 名参与者里有 400 人通过了测试，模型调用计算器算 400 除以 1400，得到 0.29，再接着写「29%」。图片来源：Schick 等，2023。}}

这张图出自 Toolformer，一个较早教模型自己使用工具的工作。Toolformer 是拿一个现成的语言模型接着训练出来的，这个现成的模型是 67 亿参数的 GPT-J，由 Wang 和 Komatsuzaki 在 2021 年公开。

Toolformer 的格式是把调用直接写在正文里。程序在模型的输出里看到这种方括号，就暂停生成，去执行对应的工具，把结果填回去，再让模型接着写。

现在让模型调用工具的格式有很多种。很常见、也可能是最有效的一种，是直接让模型写代码或者命令行命令，由运行框架（harness，包在模型外面、给它工具并管理多轮对话的程序）去执行。

不管用哪一种格式，要求是同一个：这段输出必须能被程序解析出来。模型也许已经说出了它想做什么，但如果程序解析不出来，就不知道该去调用计算器还是搜索，这一步就得不到结果。按前面各节的内容，有三种办法在这里用得上：约束解码和 prompt 加解析可以让调用的格式能被解析，System One 模型一节讲的状态和候选动作的向量比较可以用来选工具。
