先看结论

  • 推理指使用训练好的模型生成输出，分两个阶段。prefill 是读 prompt：整段输入的所有 token 一次并行算完。decode 是写回答：一次只生成一个 token。prompt 是交给模型的那段输入文字，token 是模型处理文字的最小单位。
  • 注意力层是模型里让每个 token 参考它前面各个 token 的那一层，它为每个 token 算出 query、key、value 三个向量：query 表示这个 token 在找什么，key 表示它有什么，value 是别的 token 看它时它交出去的内容。后面的 token 要用到的是前面各个 token 的 key 和 value，所以这两个算过一次就存下来，后面生成 token 时直接用。存下来的这部分叫 KV cache，它随上下文变长而变大。
  • 限制两个阶段速度的资源不同。prefill 受 GPU 的算力限制，decode 受内存带宽限制，内存带宽是数据从内存送到计算单元的速度。对应的两个指标是首个 token 的时间和每个输出 token 的时间。
  • 推测解码用一个小模型先起草几个 token，再让大模型一次检查完。2023 年的一篇论文用 700 亿参数的大模型、每轮起草 4 个 token，测了三种设置。写摘要的测试上试了两种挑 token 的办法，生成速度是只用大模型时的 1.92 倍和 2.01 倍。写代码的测试上试了一种，是 2.46 倍。每个 token 被选中的概率和只用大模型时相同，所以加速不影响输出的质量。

先看硬件：GPU 擅长什么

语言模型的计算几乎全是矩阵相乘，跑在 GPU 上。GPU 和 CPU 的设计目标不同。

屋顶线模型：速度受算力限制，还是受内存带宽限制

一段程序在一块芯片上最快能跑多快，受两样东西限制：芯片的算力，和内存带宽，也就是数据从内存送到计算单元的速度。屋顶线模型（Roofline model）把这两个限制画在一张图上。

这张图在这里的用处是解释推理的两个阶段各受哪一样限制。读 prompt 的阶段受算力限制，写回答的阶段受内存带宽限制。讲完两个阶段之后，会把它们标到这张图上。

{{fig 122 | 屋顶线模型。横轴是算术强度，纵轴是能达到的每秒浮点运算次数。粉色的水平线是芯片算力的上限，蓝色的斜线由内存带宽决定。紫色的折线是两者合起来的上限，形状像屋顶。绿色虚线左边是受带宽限制的区域，右边是受算力限制的区域。图片来源：NERSC 的文档。}}

图上有五个词，意思如下。

图上斜线和水平线相接的那一点，下面叫折点，绿色虚线就画在这一点上。一段程序落在折点的哪一边，看的是它的算术强度。图的横轴就是算术强度：算术强度低的程序落在折点左边，受带宽限制，算术强度高的落在折点右边，受算力限制。

下一节先讲推理的两个阶段各做什么。

两个阶段：prefill 和 decode

假设你把一篇作文贴给聊天助手，请它帮忙修改。模型要做两件性质不同的事。

{{fig 123 | 上面一行是 prompt「The quick brown fox」，四个 token 在 prefill 阶段一起处理，各自产生一组 KV 向量，也就是 key 和 value 两个向量，本节后面会解释。prefill 结束时算出第一个输出 token「jumps」。之后进入 decode 阶段，每一步读进刚生成的那个 token，产生它的一组 KV 向量，再生成下一个 token。图上的第一步读进 jumps，生成 over。最上面的虚线表示前面的 KV 向量被保存下来，供后面每一步使用。图片来源：技术咨询公司 TNG 在 Hugging Face 上的文章。}}

prefill 做的计算是：prompt 里所有 token 同时进入模型，过一遍全部算完，最后得到对下一个 token 的预测。第二部分用四个 token 演示过这个过程。

这个过程里和后面关系最大的是注意力层。注意力层让每个 token 按相关程度，把它能看到的各个 token 的信息加权汇总到自己身上。一个 token 能看到的是它自己和它前面的 token。为此注意力层给每个 token 算出三个向量：query 表示这个 token 在找什么，key 表示它有什么，value 是别的 token 看它时它交出去的内容。一个 token 拿自己的 query 和它能看到的每个 token 的 key 比较，得到该多看谁的分数，再按分数把这些 token 的 value 加权汇总。

{{fig 124 | prefill。四个 token 同时进入注意力层，Q、K、V 三个矩阵分别放着各个 token 的 query、key、value，各有四行。每个 token 的 query 和各个 token 的 key 比较得到的分数排成一行，四个 token 的四行合成一个 4 乘 4 的方阵，四行都要算。方阵右上角被因果掩码盖住，因果掩码规定每个 token 只能看它自己和它前面的 token。}}

prefill 结束时，prompt 里每个 token 的 key 和 value 都已经算好。接下来的 decode 阶段，就是在这些结果的基础上一个一个地往后生成。

decode 时哪些要重算：KV cache

生成下一个 token 时，注意力层要用到前面所有 token 的 key 和 value。如果什么都不存，每一步都得把前面的 token 重新算一遍。实际上不用重算：每个 token 的 key 和 value 算一次就存下来，后面每一步直接拿来用。

下面的图用「The class was about」这四个 token 来演示，并假设它们是一个一个生成出来的。实际使用时，prompt 由 prefill 一次算完，之后每生成一个 token，计算都和图里这一步相同。

{{fig 131 | decode 到第四个 token「about」的那一步。Q 里只有 about 自己的一行。K 和 V 里有四个 token 的内容：前三个是之前存下来的，新加的是 about 的。注意力的分数只有最下面一行，输出也只有一行。}}

这一步处理的 token 是刚生成出来的 about。下表列出这一步里每样东西怎么来、算完之后怎么处理。

每一步算完，除了 key 和 value，其余的中间结果都可以清掉。

{{fig 133 | 四个 token 处理完之后留下来的只有 K 和 V 两块，这就是 KV cache。}}

关于 KV cache 有三点要记住。

  • 它在每一层都有一份。图里画的是一个注意力层。模型有很多层，每一层里又有好几个头。头是多头注意力里的一组权重：实际的模型在每一层准备好几组权重，各算一遍注意力，见第二部分。每一层、每个头都要保存各自的 key 和 value。
  • 它随上下文线性增长。每多一个 token，每一层就多存一组 key 和 value。上下文越长，KV cache 占的内存越多。这是 decode 阶段内存不断增长的来源。
  • 它依赖前面所有的内容。一个 token 在第一层的 key 和 value，只由这个 token 自己和它的位置算出来。第一层注意力的输出已经汇总了它前面那些 token 的信息，这份输出是第二层的输入。所以从第二层起，这个 token 的 key 和 value 都是在它前面那些 token 的基础上算出来的。前面的内容一变，后面那些 token 从第二层起的 key 和 value 都跟着变，存下来的这部分 KV cache 就不能再用。这一点对怎样安排上下文影响很大，见第八部分。

第三部分讲的线性注意力是另一种算注意力的办法，它在生成时要保存的东西不同。这一页讲的注意力叫标准注意力，它要保存每个 token 的 key 和 value。线性注意力保存的是一个固定大小的状态，状态是模型内部保存的一块大小固定的数据，读过的内容都汇总在里面。

为什么 prefill 受算力限制，decode 受内存带宽限制

现在把两个阶段标到屋顶线模型的图上。

{{fig 134 | 同一张屋顶线图，加上了两个标签：Decode 在受带宽限制的一侧，Prefill 在受算力限制的一侧。}}

decode 阶段算力有富余，所以服务方会把很多个请求合成一批一起 decode，把空着的算力用起来。下面讲的推测解码，用的也是这份富余。

两个指标，和它们对价格的影响

两个阶段各自对应一个衡量快慢的指标。把一次请求从发出到结束的时间画出来，是下面这样。

{{fig 135 | 一次请求的时间线。橙色的一段是 prefill，对应的指标是首个 token 的时间。蓝色的一串点是 decode，每个点是一个输出 token，对应的指标是每个输出 token 的时间。}}

这两个阶段的差别也反映在价格上。按 token 算，prefill 处理一个输入 token，比 decode 生成一个输出 token 快得多。TNG 的文章指出，这就是商业 API 的输入 token 比输出 token 便宜很多的原因。

对搭 agent 的人来说，这一页讲的内容有两条直接的推论。agent 是能自己调用工具、分很多步去完成一个任务的语言模型系统，它每一步都把一段很长的上下文交给模型，模型再写出不长的一段输出。第一条推论来自上面说的价格差别，第二条来自 KV cache 依赖前面所有内容这一点。

  • 读得多、写得少，在价格上是划算的。同样数量的 token，作为输入比作为输出便宜。agent 用掉的 token 大部分是读进去的输入，按便宜的那一种价格计费。
  • 开头不变，开头那部分就不用重算。提供模型的服务方可以把上一步算好的 KV cache 保留下来。如果这一步的上下文开头和上一步完全相同，开头那部分的 KV cache 可以直接接着用，prefill 只需要处理新增的部分。各家 API 的做法见第八部分。

推测解码：小模型起草，大模型一次检查

decode 一次只能出一个 token，每出一个都要把模型的权重和 KV cache 从内存里读一遍，所以速度受内存带宽限制，GPU 的算力有富余。推测解码（speculative decoding）用这份富余的算力，让大模型一次处理好几个 token。名字里的「解码」就是 decode，指一个一个地生成 token。

推测解码用到两个模型：大模型是真正要用的那个模型，小模型很小、很快，只用来起草。不起草、由大模型自己一个一个地生成 token 的做法，下面叫「只用大模型」，它是拿来比较的基准。

{{fig 136 | 左边：小模型从「Once」开始，一个接一个地生成 upon、a、time、there，图上把它标作起草模型（Draft Model）。右边：大模型把「Once upon a time」一次读进去，同时给出每个位置上它自己的判断，图上把它标作目标模型（Target Model）。前三个和起草的一致，打勾；第四个 there 不一致，打叉。}}
  1. 起草。小模型按普通的方式一个一个地生成几个 token，个数记作 K。这个 K 是论文里用的字母，和前面表示 key 矩阵的 K 是两回事。
  2. 检查。把这 K 个 token 交给大模型。因为这些 token 已经全部已知，大模型可以像 prefill 那样一次并行算完，得到每个位置上它自己的概率分布。
  3. 接受或拒绝。从前往后比。拿 greedy（每一步都选概率最高的 token）来说：起草的 token 如果正是大模型在这个位置上概率最高的那个，就接受。遇到第一个不一致的位置，就在那里换成大模型自己的选择，后面的草稿作废，再从这里重新起草。

如果草稿全被接受，大模型过一遍就得到了 K 个 token，本来要过 K 遍。大模型并行检查几个 token 花的时间，和它自己生成一个 token 差不多，因为 decode 阶段的算力本来就有富余。

i
每个 token 被选中的概率和只用大模型时相同。用 greedy 时，按上面第 3 步的规则，结果和只用大模型时相同。用抽样（按概率随机抽一个 token）时，DeepMind 的 Chen 等 2023 年的论文把第 3 步的规则换成一种修改过的拒绝抽样。拒绝抽样是先拿到一个候选、再按一定的概率决定收下还是丢掉的抽样办法。按这个规则，每个 token 最后被选中的概率和只用大模型抽样时相同。所以按算法，小模型只影响速度，不影响质量。实际运行时，计算机做浮点运算有误差，两种做法的输出不一定逐字相同，用 greedy 时也是这样，见资料说明。出处：Chen 等，2023。

这一部分的小结

  • prefill 并行读完 prompt，受算力限制；decode 逐个生成，受内存带宽限制。
  • KV cache 让 decode 不用重算前面的 token，代价是内存随上下文线性增长。前面的内容有一处改动，改动处后面那些 token 从第二层起的 key 和 value 就要重算。
  • 输入 token 便宜，输出 token 又贵又慢。
  • 推测解码把 decode 阶段富余的算力用起来，每个 token 被选中的概率和只用大模型时相同。

这一部分讲的是推理的时间花在哪里，推测解码一节讲了怎样把同样质量的输出更快地生成出来。下一部分反过来：推理时多花算力，换更好的答案。
