先看结论

  • 上下文工程（context engineering）要解决的是每次调用模型时，放进上下文的全部 token 怎么安排。上下文指调用一次模型时放进去的那组 token，上下文窗口是一次能放进模型的 token 数的上限，token 是模型处理文字的最小单位。
  • 不能把所有东西都放进去，原因有两个：上下文越长，模型用好其中信息的能力越差，这叫 context rot；上下文越长，每一步越贵。
  • 四条实际的做法：只放必要的工具和内容；用检索挑出最相关的再放；新内容只往后面加；每个安排都用实验来验证。第三条的原因是，模型读过的 token 的中间结果会存下来，下一次调用时接着用，这份缓存叫 KV cache，只有上下文的开头和上次完全相同时才能接着用。
  • 上下文满了之后要做 compaction，也就是把历史总结成一段摘要再继续。留多了很快又满，丢多了会丢掉完成任务必需的信息。
  • 还有一种不同的思路叫递归语言模型：把很长的输入放在代码环境的一个变量里，让模型写代码去查看它、拆分它，并对其中的片段再调用模型。

从 prompt 工程到上下文工程

ChatGPT 刚出现的那段时间，大家关心的是 prompt 工程（prompt engineering）。prompt 是交给模型的那段输入文字，prompt 工程研究的是这段文字该怎么措辞，模型才答得好。那时流行过各种写法，比如告诉模型「答不好这个问题世界就要毁灭」。

现在的 agent 要在很多轮里连续工作，能给模型的信息非常多，问题变成了：这么多信息，哪些放进去，怎么组织，怎么删减。这就是上下文工程。它管的范围比 prompt 工程大：一段文字怎么措辞只是其中的一部分。

{{fig 161 | 左：prompt 工程，上下文里只有 system prompt（放在对话最前面、用来设定模型行为的那段文字）和一条用户消息，模型回一条消息。右：agent 的上下文工程。最左一栏是可以放进去的全部材料（文档、工具、记忆文件、详细的说明、领域知识、消息历史），经过中间的挑选，只有一部分进入上下文。模型的输出除了消息还有工具调用，工具的结果又回到左边的材料里，等待下一轮挑选。图片来源：Anthropic，2025 年 9 月。}}

这张图出自 Anthropic 2025 年 9 月的文章《Effective context engineering for AI agents》。文章里有两个定义。上下文指调用一次模型时放进去的那组 token。上下文工程指在推理时挑选并维护最合适的那组 token 的一整套办法。这里的推理时，指模型一次次被调用、生成输出的时候。prompt 之外进入上下文的所有其他信息，比如工具调用的结果，也在上下文工程的范围里。

agent 的上下文里有什么

为什么不把所有东西都放进去

第一个原因是 context rot：上下文里的 token 越多，模型准确用到其中信息的能力越差。第二个原因是花费：上下文里的内容每一步都要读一遍，上下文越长，每一步越贵。

第二个原因里的「贵」，有一部分来自注意力的计算量。注意力是模型里让每个 token 用到前面各个 token 的信息的那一层计算。每个 token 直接去看前面所有 token 的注意力叫标准注意力。第二部分讲过，这种注意力的计算量随长度的平方增长。

下面用一个专门测长上下文的基准测试 OOLONG 来看第一个原因。第二个原因在做法一里有具体的数字。

OOLONG 分两个部分。合成数据的部分，上下文是用很多条现成的短文本（比如新闻、评论）拼起来的，每条随机配上一个日期，所以叫合成。真实对话记录的部分，上下文是一档桌面游戏节目的对话记录，这档节目是一集一集播出的。

{{fig 163 | OOLONG 两个部分各一道例题。左是合成数据的部分：给一批带日期的新闻，问「关于经济的新闻，9 月多还是 8 月多」。模型要判断每篇是不是讲经济的，记下日期，再数数。右是真实对话记录的部分：给其中几集的对话记录，一共 12 小时，问「角色 Jester 在这几集里一共施放了几次治疗术」。图片来源：Bertsch 等，2025。}}

这类题和第三部分里在长文章中找一个数字的测试不同。找数字的题，上下文里绝大部分内容是无关的。OOLONG 的题要求模型把上下文里每一小块都看一遍、各自做一个简单的判断，再把结果汇总起来，没有哪一部分可以跳过。

{{fig 164 | 得分随上下文长度的变化，每条线是一个模型。左图是合成数据的部分，横轴从 8K 到 512K 个 token，K 表示一千；右图是真实对话记录的部分，横轴从 64K 到 512K。黑色虚线是随机猜的基线，也就是随机乱猜能得到的分数。图片来源：同上，论文的第一版。}}

表里的三个模型在 8K 时都在 74 分以上，到 128K 时都不到 50 分，而 128K 仍然在这些模型的上下文窗口以内。

论文第一版的摘要给的是同一个结论，点名的模型和表里的有一个不同：摘要说的是 GPT-5、Claude Sonnet 4 和 Gemini 2.5 Pro，这三个模型在 128K 时，两个部分的得分都低于 50 分。摘要的原话是准确率（accuracy）低于 50%，指的就是这个得分。Gemini 2.5 Pro 没有列在上面的表里，原因见下面的说明。

i
图里最醒目的那条黄线，不适合拿来说明 context rot。左图里黄色的线是 Gemini 2.5 Pro。这条线从 8K 时的 88.13 分开始下降，到 256K 时从图上看只有 13 分左右，已经低于随机猜的基线，看上去是 context rot 最严重的例子。论文自己解释了主要原因：上下文很长时，Gemini 在给出答案之前写的思考过程常常超出最大输出长度，而它的 API 在这种情况下不返回任何内容，这道题就直接记 0 分。别的模型在同样情况下返回的是被截断的输出，还可能拿到部分分。所以上面的表没有列 Gemini 2.5 Pro。在真实对话记录的那部分，论文没有观察到这个问题，Gemini 是成绩最好的模型。出处：OOLONG 论文的第一版第 4 节。
+
context rot 这个词的来历。这个词出自 Chroma 公司 2025 年 7 月的技术报告。报告测了 18 个模型，结论是模型对上下文里各部分内容的利用有好有差，输入越长，表现越不可靠。出处：Chroma 的报告。
+
Anthropic 对 context rot 的解释。Anthropic 的文章说，模型能顾及的内容有限，它把这个限度叫作模型的「注意力预算」，上下文里每加进一个 token 都会消耗一点。文章把原因和注意力的结构联系起来，讲了两点。n 个 token 之间有 n 的平方对两两关系，上下文越长，模型顾及这些关系的能力越弱。训练数据里短序列又比长序列常见，模型处理长距离依赖的经验更少，长距离依赖指上下文里相隔很远的 token 之间的关系。文章还强调这是一个逐渐变差的过程，没有一个突然失效的点。出处：Anthropic 的文章。

怎样安排上下文没有唯一正确的办法，需要针对自己的 agent 去试。下面是几条实际的做法和要考虑的事。Anthropic 的文章给的总原则是：找到尽可能小的一组信息量高的 token，让模型最有可能给出想要的结果。

做法一：只放必要的工具和内容

放进上下文的工具定义和说明越多，每一步越贵，因为这些内容模型每一步都要读一遍。工具定义是写给模型看的文字，说明每个工具叫什么、做什么用、要传哪些参数。有时候几个工具就够了。

Pi 是一个例子。它是一个开源的、很精简的写代码的运行框架（harness，包在模型外面、给它工具并管理多轮对话的程序），只给模型四个工具：读文件、写文件、编辑文件和执行命令行命令。

一项叫 HarnessTax 的研究把 Pi 和另外两种运行框架 Codex、Claude Code 放在一起比，一共测了 7 个模型。Codex 是 OpenAI 的运行框架，Claude Code 是 Anthropic 的运行框架。

花费的差别从第一次调用模型就开始了。第一次调用模型时放进上下文的内容叫初始上下文。7 个模型平均下来，Claude Code 的初始上下文的长度是 Pi 的 10 倍以上，里面是更长的说明和更大的工具定义。这些内容每一步都要读一遍。

初始上下文长 10 倍，总花费的差距要小得多。文章的说明是，总花费还取决于缓存、模型生成的 token 和后面的各次调用。具体的差距见下面的第一条结论。

下面的图和表是这项研究在成功率和花费上的结果。

{{fig 166 | 同一个模型配三种运行框架（Pi、Codex、Claude Code），在 Terminal-Bench 2.0（一个在命令行终端里完成任务的基准测试）上的结果。左边一组柱子是每次运行的花费，右边一组是成功率。绿色边框标出每个模型里花费最低和成功率最高的那一个。图里是四个 Claude 模型。图片来源：Arena 的 HarnessTax 文章，2026 年 9 月。}}

这项研究的三条结论

这项研究一共测了 7 个模型和 3 种运行框架的 21 种组合，用了两个基准测试：SWE-bench Lite 考的是修真实代码仓库里的 bug，Terminal-Bench 2.0 是上面图里的那一个。文章自己的结论有三条。

  • 运行框架对成功率影响小，对花费影响大。同一个模型可以用相差最多 5 倍的花费达到相近的成功率。「最多 5 倍」说的是这项研究全部组合里最大的差距。上面的表只列了 Terminal-Bench 2.0 上的四个模型，它们换运行框架之后，花费最多相差约 1.6 倍。
  • 简单的运行框架，花费和成功率合起来看不输给另外两种。每个「模型加运行框架」的组合有花费和成功率两个数。如果没有别的组合比它便宜、成功率还不比它低，这个组合就在 Pareto 前沿（Pareto frontier）上。文章说，只有四个工具的 Pi 在两个基准测试上都到了 Pareto 前沿，也就是两个基准测试的前沿上都有用 Pi 的组合。
  • 模型在别家的运行框架里可能表现更好。这一条只算 Anthropic 和 OpenAI 的模型。7 个模型里有 6 个来自这两家。第 7 个是月之暗面的公开权重模型 Kimi K3（见第三部分），三种运行框架都不是它那一家的。这 6 个模型在每个基准测试上各算一组比较，2 个基准测试共 12 组。其中 9 组里，成功率最高的是别家的运行框架：对 Anthropic 的模型来说是 Codex 或 Pi，对 OpenAI 的模型来说是 Claude Code 或 Pi。公开权重指训练好的模型参数公开发布、可以下载。

第一条结论在 Terminal-Bench 2.0 上有两个具体的数。第一个数是成功率：文章说，运行框架对成功率的平均影响大约在正负 5% 以内。这个平均影响是和什么比、怎样取的平均，文章没有写明，也没有写明 5% 是百分点还是相对比例。

第二个数是花费：Claude Code 的花费大约是 Pi 的 1.5 倍。这个倍数是先在每个模型上算出两者花费的比值，再对这些比值取几何平均得到的。几何平均是把 n 个数相乘、再开 n 次方的平均办法。这项研究的 7 个模型都配了 3 种运行框架，上面的表只列了其中 4 个 Claude 模型。这 4 个模型各自的倍数在 1.0 到 1.44 之间，都低于 1.5 倍，所以 1.5 倍里还算进了表里没有列的另外 3 个模型。

文章也提醒，这些结果只来自两个公开的基准测试，模型在训练时可能见过它们。

i
这张图能读出多少。图里四个模型，Pi 的成功率在 Sonnet 4.6 和 Haiku 4.5 上最高，在 Opus 4.8 上和 Codex 并列，在 Fable 5 上最低。但每个数只来自 30 个任务，图上每根柱子都带着误差线，也就是结果可能波动的范围。从图上看，同一个模型的三根柱子的误差线都互相重叠，差距最大的一组也是这样：Haiku 4.5 上 Pi 比 Codex 高 16.7 个百分点。所以哪一种运行框架的成功率最高，这张图分不出来。它支持的是文章的第一条结论：成功率差不多，花费差得多。

Anthropic 的文章对工具也是这个意见：最常见的毛病之一是工具太多、功能重叠，让人说不清某个情况该用哪个工具。如果连工程师自己都说不清该用哪个，就不能指望 agent 做得更好。

做法二：用检索挑出最相关的内容

记忆和文件可能非常多。可以先检索，只把最相关的几条放进上下文。

{{fig 167 | 检索的流程。用户的问题，也就是图上的 Prompt，先进入绿色框里的三步，图上把这三步合起来叫检索链。第一步，用一个 embedding 模型（把一整段文字变成一个向量的模型）把问题变成向量。第二步，到向量数据库里搜索。向量数据库事先存好了每篇文档的向量，搜出来的是向量和问题的向量最接近的那些文档。第三步，用一个重排模型给搜到的结果重新排序。排在前面的文档和用户的问题一起交给语言模型，得到回答。图片来源：NVIDIA 开发者博客。}}

检索的细节第 3 讲会讲到。这里只需要知道它在上下文工程里的作用：由它来决定哪些内容值得占用上下文。

+
另一种取内容的方式：用到时再取。Anthropic 的文章描述了一种越来越常见的做法。agent 平时只在上下文里留一些很短的引用，比如文件路径、网页链接、存下来以后可以再次执行的查询语句，需要时再用工具把内容读进来。这样做的代价是比事先检索慢，并且需要给 agent 合适的工具和引导。文章认为两种可以混用：一部分内容事先放好，其余的让 agent 自己去找。出处：Anthropic 的文章。

做法三：新内容只往后加

第五部分讲过 KV cache：注意力层为每个 token 算出 query、key、value 三个向量，分别表示它在找什么、它有什么、别的 token 看它时它交出去的内容。其中 key 和 value 算一次就存下来，后面接着用。多轮对话里，上一轮算好的缓存，下一轮可以直接接着用，只需要处理新增的 token。前提是前面的内容一个 token 都没有变。

设想这样一个很自然的做法：对话进行到一半，用户提到一份文档，于是把这份文档插到上下文的最前面。

{{fig 169 | 原来的四个 token「The class was about」前面插进了一个「Actually」。红色箭头指出后面每个 token 的位置向量都变了，上面已经存好的 KV cache 被打上红叉，全部作废。位置向量是加到每个 token 的向量上、表示它排在第几个的一组数。}}

这样做会让整份缓存作废，所有 token 要重新算一遍。图里标出了一个原因：在开头插入内容，后面每个 token 的位置都往后挪了一位。它们的 key 和 value 是带着原来的位置算出来的，现在全都对不上了。

更一般的原因是后面的 token 依赖前面的 token。注意力里的因果掩码规定每个 token 只能看它自己和它前面的 token，所以每个 token 在每一层的结果，都是在它前面所有 token 的基础上算出来的。前面任何一处有改动，后面所有 token 的结果都会跟着变，即使它们的位置没有动。

i
后面的 token 是从第二层起受影响的。第一层的 key 和 value 只由这个 token 自己和它的位置算出来。从第二层起，每个 token 的输入里已经混进了它前面那些 token 的信息。所以前面任何一处有改动，后面所有 token 从第二层起的 key 和 value 都会跟着变。「后面的依赖前面的」这个更一般的解释，是根据注意力的计算方式作出的推论。

所以缓存能不能接着用，只看一个条件：开头的那一段是否和上次完全相同。各家 API 的缓存也是按这个规则设计的。Anthropic 的文档把一次请求开头的那一段叫前缀（prefix）。文档说，缓存让 API 从已经缓存的前缀之后接着处理，后续请求的前缀相同时自动使用缓存的内容。出处：Anthropic 的 prompt caching 文档。

落实到搭 agent 上，有三条具体的规则。

  • 稳定不变的内容放在最前面，比如 system prompt 和工具的定义。
  • 每一轮新增的内容，接在已有内容的后面。
  • 已经在上下文里的内容不要改动。要补充一份文档，就把它加在当前这一轮的位置上。

做法四：用实验来决定

上下文怎么安排更好，很多时候猜不出来，只能测。办法是先搭好一套基准测试或评估，每改一处就跑一遍。基准测试怎样搭、什么样的分数可信，第 13 讲会讲到。

{{fig 170 | Toolformer 论文里的一组对比，Toolformer 是一个较早教模型自己使用工具的工作。三张图分别是三类任务上的平均成绩：LAMA（补全一句话里缺的事实，比如日期或地名）、数学题和问答题。横轴是模型的参数量，单位是百万。每条线上的五个点是五个大小不同的模型，从左到右是 GPT-2 系列的四个模型（1.24 亿、3.55 亿、7.75 亿、16 亿参数）和一个更大的模型 GPT-J（67 亿参数）。GPT-2 是 OpenAI 2019 年的模型。蓝线是可以调用工具时的成绩，红线是同一个模型关掉工具时的成绩，紫色虚线是 GPT-3 作为参照。图片来源：Schick 等，2023。}}

这组图比较的是给不给工具，这也是上下文里放什么的一种选择。它说明了为什么要测：在 LAMA 和数学题上，最小的两个模型（1.24 亿和 3.55 亿参数）用不用工具，成绩几乎相同。论文的说法是，利用工具的能力要到大约 7.75 亿参数才出现。问答题是论文指出的例外，最小的模型用了工具成绩也更高。同一个设计，换一个模型，结论可能不同。

同样的办法适用于各种选择。比如上下文里的材料用 Markdown 格式好，还是用 YAML 格式好？把两种都跑一遍基准测试，看结果。

上下文满了之后：compaction

agent 工作得足够久，上下文总会接近上限。这时常用的处理叫 compaction：把到目前为止的对话历史总结成一段摘要，再从一个新的上下文继续工作，新上下文里放的就是这段摘要。

compaction 改动了已经在上下文里的内容。按做法三的道理，做完之后原来的缓存不能再用，新的上下文要重新算一遍。这种重算只发生在上下文接近上限、要做 compaction 的时候，平时的每一轮仍然只往后加。

到了需要 compaction 的时候，上下文已经非常长。这时要决定的是摘要里留什么。

  • 留得太多，很快又会满，又要再做一次。
  • 丢得太多，可能丢掉完成任务必需的关键信息。

这起事故的经过

当事人 Summer Yue 是 Meta 超级智能实验室里 AI 安全和对齐研究的一位负责人，对齐研究关心的是怎样让 AI 的行为符合人的意图。她用的是开源的 agent 程序 OpenClaw。2026 年 2 月 23 日她发帖讲了这次的经过。下面的经过出自上海纽约大学的一篇报道，其中引用了她的帖子。

此前几周她一直在一个测试用的小收件箱上试用 OpenClaw，都正常。之后她让它接着处理自己真实的收件箱，指示是：也检查这个收件箱，建议哪些该归档或删除，在她说可以之前不要动手。

按她自己的说法，真实的收件箱太大，触发了 compaction，她原来的那条指示在这个过程中丢了。之后 agent 成批地删除和归档邮件。她在手机上连发几条停止的指令都没有用，最后跑到运行这个程序的电脑前把进程结束掉。

丢失指示这个原因是当事人自己的判断。摘要里实际留下了什么，这篇报道没有给出。TechCrunch 对这件事的报道说明，它没能独立核实她的邮箱里实际发生了什么。

如果当事人的判断属实，这件事说明，摘要里丢掉的一句话，可以是整个任务里最重要的一句。它也提示了一个做法：必须一直生效的规则，放在每次都会完整带上的位置，比如 system prompt 或者一个固定的文件里，不要只在对话里说一遍。

+
Anthropic 的文章对 compaction 和长任务的建议。
  • 先求全，再求精。调整做摘要的 prompt 时，先保证它能留下所有相关的信息，再逐步去掉多余的内容。compaction 时丢得太多，会丢掉一些当时不起眼、后来才显出重要的内容。
  • 从最安全的地方删起。早先的工具调用和它们的原始结果，通常不需要再看一遍。只清掉这些内容、不做摘要的做法，文章也算作 compaction，并说它是其中最安全、改动最小的一种。清掉之后，缓存同样要从改动的地方重新算。
  • 一个实际的例子。Claude Code 做 compaction 时，让模型留下架构上的决定、还没解决的 bug 和实现细节，丢掉重复的工具输出，再附上最近访问过的 5 个文件。
  • 另外两种办法。结构化的笔记：agent 定期把进展写到上下文之外的文件里，需要时再读回来。子 agent：把一块工作交给另一个从空白上下文开始的 agent，它自己可以用掉几万个 token，交回来的只是一段 1000 到 2000 个 token 的总结。
出处：Anthropic 的文章。子 agent 的做法第 8 讲会讲到。

另一种思路：递归语言模型

前面讲的做法都围绕同一件事：怎样安排模型的上下文。有的任务输入很长，每一条内容都相关，没法靠检索挑出一小部分，前面的 OOLONG 就是这样。

对很长的输入，递归语言模型（Recursive Language Model，RLM）换了一个思路：把很长的输入留在模型的上下文之外，当成环境的一部分。它出自 MIT 的 Zhang、Kraska 和 Khattab 2025 年底的论文。

{{fig 172 | 一次 RLM 调用的过程。用户交来的 prompt 是一本很长的书和一个问题，它被存进代码环境的一个变量里。这里的代码环境是一个可以一段一段执行 Python 代码的交互环境。黑色的方框是模型写的代码和代码的输出：先打印 prompt 的前 100 个字符看看，再把 prompt 按章节切开，对每一部分调用 llm_query 函数。右边两个小框是这些调用各自启动的下一层模型，每个只处理一个片段，把结果交回来。最后模型给出最终回答。图片来源：Zhang 等，2025。}}
  1. prompt 变成一个变量。用户给的 prompt 很长，它被存进代码环境里的一个变量。模型自己的上下文里只有任务说明和「输入在某个变量里」这句话。
  2. 模型写代码去看。模型写一段代码，代码环境执行后把输出交回给它，它再写下一段，这样一轮一轮地做下去。代码可以打印变量的前 100 个字符、按某个标记把它切开、用关键词搜索，模型每次只看到代码输出的那一小部分。输出过长时会被截断。
  3. 模型可以调用模型。代码环境里有一个函数，可以把一个片段和一个问题交给另一个语言模型，拿回答案。交过去的片段和问题，就是被调用的模型的 prompt。被调用的模型也可以是一个 RLM：它把自己的 prompt 存成变量、写代码去看、再往下调用模型。这样一层套一层，所以叫递归。
  4. 给出最终回答。模型把各个片段的结果汇总，把最终答案放进一个约定的变量里，上面一轮一轮的过程到这里结束。

这样，处理很长的输入时，最外层模型的上下文始终很短，长内容由下面各层分头处理，只把需要的结果交上来。

{{fig 173 | OOLONG 的一个子集上的得分，每道题的上下文大约是 263K 个 token，也就是 26.3 万个。五根柱子从左到右：GPT-5 直接读全部上下文；GPT-5-mini 直接读全部上下文；以 GPT-5-mini 为基础的 RLM；以 GPT-5 为基础、但关掉了递归调用的 RLM；一个用 GPT-5 加关键词检索的 agent。图片来源：Alex Zhang 的文章。}}

下表列出五根柱子的得分。最后一行里，ReAct 是一种让模型轮流写思考过程和调用工具的 agent 写法，BM25 是一种按关键词匹配来检索的算法。

从这张表，再加上论文里的一组对照，能读出四件事。

  • 小模型加上这个结构，超过了大模型直接读。RLM（GPT-5-mini）比 GPT-5 高 16.9 个百分点，相对高出约 49%。文章说它每道题的平均花费还比 GPT-5 低。
  • 表里的两行 RLM 不能直接相减。关掉递归调用的版本（40.9%）用的是 GPT-5，完整的版本（51.1%）用的是 GPT-5-mini。两行的基础模型不同，所以这个差距不能全算作递归调用的作用。
  • 递归调用起了多大作用，要看同一个基础模型的对照。论文的表 1 里有这样的对照。题目也来自 OOLONG，上下文约 131K 个 token，也就是 13.1 万个，最外层的模型都是 GPT-5。不允许递归调用的版本得 36.0 分。允许一层递归调用的版本得 56.0 分，一层的意思是最外层的模型可以调用 GPT-5-mini，被调用的 GPT-5-mini 不能再往下调用。满分也是 100，和上表的百分比是同一种得分。对这个差距，论文的解释是，这类题要对很多条内容逐条做语义上的判断，光靠写代码搜索不够。Alex Zhang 的文章在自己的实验里关掉递归调用后成绩也下降，给的也是这个解释。
  • 关键词检索在这类题上帮不上忙。30.7% 比 GPT-5 直接读还低。OOLONG 的每一条内容都相关，没法靠检索挑出一小部分。

论文更大范围的结论是：RLM 能处理比模型上下文窗口长一个数量级以上的输入，在四类长上下文任务上，成绩好于直接调用模型和几种常见的运行框架，花费相当。

整讲的小结

这一讲从语言模型是什么讲到了怎样安排 agent 的上下文。下面的表按五个主题回顾一遍。表里有几个前面各部分的词，先各给一句解释。

  • temperature 是调节模型输出多样性的参数，解码策略是从概率分布里挑下一个 token 的办法。
  • Transformer 是现在的大语言模型大多采用的模型结构，它原本用的是标准注意力。线性注意力是一种省计算的注意力，代价是更难从长上下文里找回信息。
  • 预训练、中期训练、后训练是训练的先后三个阶段。
  • prefill 是模型读输入的阶段，decode 是写回答的阶段。
