先看结论

  • 十二个基准测试里，最早的是 2018 年的文字游戏，最新的是 2026 年的机器学习研究任务。它们的环境有模拟的也有真实的，问题描述有写明一切的也有只给目标的，各自的组合不同。
  • 评分办法大多是检查最后的结果：跑测试，看环境的最终状态，或者比对答案。多数基准测试给每个任务判通过或不通过。少数给的是一个有高有低的分数，例如买到的商品和要求匹配了多少、经营结束时还有多少资产。还有两个的分数是比出来的：一个和对手比输赢，一个和人类的最好成绩比。
  • 其中几个在发布的时候，也就是论文发表的时候，最好的系统成功率很低。SWE-bench 的题是修真实代码仓库里的问题，它是 1.96%。OSWorld 让 agent 操作一台装了完整操作系统的电脑，是 12.24%。WebArena 让 agent 在网站上办事，是 14.41%。也有发布时就不低的：Terminal-Bench 2.0 让 agent 在一个隔离的运行环境里按任务说明做事，它是 63%。
  • 后来的研究在其中几个基准测试的评分办法里查出了问题，分数有被高估的，也有被低估的。

评估协议和发布时的成绩

有的基准测试对其中某一项没有规定，由跑分的人自己定。这样的格子先写「不规定」，论文自己的实验用了什么，查得到的写在它后面。

表里有几个词先解释一下。

  • 测试集是用来报分数的那批题。
  • 运行框架指包在模型外面、给它工具并管理多轮对话的程序。
  • 简单循环是最简单的一种运行框架：一段程序把当前的情况交给模型，执行模型给出的动作，再把结果交回模型，这样反复，直到任务结束。
  • ALFWorld 和 WebShop 两行写着「没有运行框架」。这两篇论文测的是为这个任务专门训练出来的 agent 或模型，没有用到包在语言模型外面的运行框架。
  • 基线指论文自己拿来作比较参照的做法或成绩。
  • Vending-Bench 那一行的消息，指 agent 的对话记录里的一条，例如模型发出的一次工具调用。

这张表有两点值得注意。

  • 这几项在有的论文里写得很全，在有的论文里没有全部查到。WebArena 和 OSWorld 每个任务跑几次，在这两篇论文查阅过的章节里没有找到。这两篇论文的附录没有全部读完，所以只能说没有查到。2026 年 Terminal-Bench 的论文写明了每个任务至少跑 5 次，除了成功率，还报告了成功率的 95% 置信区间、花费、token 数和轮数。置信区间是误差范围的一种算法，误差范围指重复测量时分数可能波动的幅度，第五部分展开。token 是模型处理文字的最小单位，大致是一个词或半个词。
  • 运行框架固定不固定，各家的选择不同。CodeClash 和 Vending-Bench 固定运行框架，比的是模型。Terminal-Bench 和 BrowseComp 不规定，比的是「模型加运行框架」的整体。读分数时要先弄清比的是哪一种。

后来在这些基准测试里查出的问题

Zhu 等人 2025 年的论文《Establishing Best Practices for Building Rigorous Agentic Benchmarks》挑了 10 个常用的 agent 基准测试逐项检查，其中四个是这一讲的案例或案例的后续版本，列在下面的表里。后续版本指 SWE-bench Verified：它是 OpenAI 从 SWE-bench 里人工筛出的 500 道题，筛掉的是描述不清或测试有问题的题。

表的最后一列用到两种算法，读的时候要分清。百分点是两个百分数直接相减的差，相对的比例是这个差除以原来的成绩。举例说，成绩从 40% 变成 50%，是高了 10 个百分点，按相对的比例算是高了 25%。

表里的语言模型评审，指让一个语言模型来判断 agent 的答案对不对。

这篇论文把问题分成两类。

  • 任务有效性（task validity）。一个任务，应该在 agent 具备目标能力时才做得成，而且具备能力时一定做得成。目标能力指这个基准测试想要衡量的那种能力。有捷径可走，或者任务本身做不到，都算违反。
  • 结果有效性（outcome validity）。任务做成了就应该判通过，没做成就应该判不通过。把错的判成对的，或者把对的判成错的，都算违反。

「任务本身做不到」指的是有能力的 agent 也没法通过。τ-bench 和 OSWorld 里故意设计成办不了的任务、WebArena 里标注为「N/A」的任务是另一回事：出题的人要 agent 认出这件事办不了，认出来就算做对，所以有能力的 agent 能通过。

这两个条件各自容易在哪里出问题，论文也说了。任务的设置不当，会破坏任务有效性，任务的设置指任务描述、给 agent 搭的环境和提供给它的工具。给 agent 交出的结果评分不严，会破坏结果有效性。对照第二部分的拆法，可以这样对应：任务有效性主要和问题描述、环境有关，结果有效性和验证有关。

论文给出题的人列了一份检查清单，分三部分：任务有效性、结果有效性，以及发布基准测试时该报告什么。上面表里的问题，按这份清单这样归类。子串匹配和语言模型评审的问题属于结果有效性，也就是 τ-bench 的第二行和 WebArena 那一行。SWE-bench Verified 的测试会放过错误的补丁，这是论文给结果有效性举的例子。

OSWorld 那一行，清单记在任务有效性下面。从现象看，它是把做对的判成了不通过，按前面结果有效性的定义也算违反。清单的依据是任务有效性里讲环境的一条检查项：环境在发布时要固定下来，不依赖会变的外部网站。OSWorld 在这一项上没有通过。

τ-bench 的第一行，也就是什么都不做也能通过的那个问题，论文前后有两种归法。引言把它当作任务有效性的例子，后面的章节又把它记在结果有效性的检查项下面。

他们检查的 10 个基准测试里，7 个在结果有效性上有问题，7 个在任务有效性上有问题。

论文摘要说，这些问题会让 agent 的成绩被高估或低估，按相对的比例算最高可达 100%。论文没有写明这个 100% 是哪个成绩相对哪个成绩算的，也没有写明它出自哪一个基准测试。

出题的人自己做过哪些检查

这十二个基准测试的论文里，有几篇的作者自己也检查过评分，并写下了它的局限。下面四处来自其中四篇论文。

  • WebShop。作者抽出 100 次由人完成的运行，手工重评了一遍。做这些运行的是论文从众包平台雇来的普通工人。把 0 到 1 的分数乘以 100 之后，自动评分的平均分是 74.9，人工评的是 76.3。差距主要来自同义词没有匹配上。这两个数是人完成的运行的平均分，和前面表里模型拿到满分的比例是两个量。
  • WebArena。作者抽查了 40 个由 GPT-4 评判的例子，39 个和人的判断一致。
  • BrowseComp。作者在评测过程中发现 21 道题标注的答案有问题，或者答案的格式和题目要求的对不上，这些题被删掉了。论文也承认，不能保证每道题只有标注的答案这一个正确答案。
  • Terminal-Bench。每个任务平均经过大约三小时的人工审查。检查项里包括：让一个什么都不做的 agent 去跑，它必须不通过；让一个专门找漏洞的 agent 去跑，看能不能作弊通过。论文的结论里仍然写着，验证这些任务的正确性极其困难。

Terminal-Bench 做的第一项检查，和 Zhu 等人的一条建议用的是同一种 agent：一个什么都不做的 agent。Terminal-Bench 是在出题的时候逐个任务检查，这个 agent 必须不通过。Zhu 等人的建议是在发布的时候报告它的成绩：前面说的那份检查清单里，讲报告的那一部分有一条是，报告最简单的 agent 的成绩，比如一个什么都不做的 agent。如果 τ-bench 发布前也让一个什么都不做的 agent 跑一遍，38% 这个数很可能当时就会被看到。

把十二个案例放在一起看

把十二个案例放在一起，可以看到四点。

  • 问题描述和环境这两条轴上的各种位置都有人做。第二部分把问题描述排成一条轴，一头是把要求全部写明，另一头是只给一个开放的目标。环境也排成一条轴，一头是模拟的，另一头是真实的。环境有文字游戏、模拟的网店、自己搭的网站、完整的操作系统和真实的互联网。问题描述有写明所有条件的购物要求、真实的 GitHub issue 和只有一个目标的比赛。新的基准测试也有用模拟环境的，2025 年的 Vending-Bench 就是。
  • Zhu 等人查出的问题，这一页的表里列了五种。这篇论文一共检查了 10 个基准测试，「后来在这些基准测试里查出的问题」一节的表只列了其中和这一讲的案例有关的四个，五种问题都让分数偏高或偏低。前四种是办不了的任务只要数据库没有被改动就算成功（τ-bench）、子串匹配（τ-bench 和 WebArena）、语言模型评审（WebArena）和依赖外部网站（OSWorld）。第五种出在用测试来评分的办法上：SWE-bench Verified 是从 SWE-bench 里人工筛出的 500 道题，它的测试仍然会放过错误的补丁。
  • 评分难做对，和 agent 交出来的东西有关。Zhu 等人的论文说，agent 基准测试要 agent 交出的是文字回答、代码、文件改动这类没有固定格式的结果，要判断它们对不对，需要专门设计的办法。
  • 发布时成功率低，就给模型留出了提高的空间。「先看结论」里列的 SWE-bench、OSWorld 和 WebArena 发布时成功率都很低，这对应第四部分的第一条性质「有挑战」。Terminal-Bench 2.0 是另一种情况：发布时最好的成绩已经有 63%，论文自己也说它可能在一年内被做满，也就是最好的系统接近满分。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • 评估协议表里写着「查阅过的章节里没有找到」的两格。WebArena 和 OSWorld 每个任务跑几次，在这两篇论文的摘要、讲任务和评估的章节、实验设置、主要结果和读过的那部分附录里都没有找到。附录没有全部读完，所以表里这样写。出处：WebArena 的论文；OSWorld 的论文。
  • WebShop 的 3 次试验。论文主要结果的那张图，图注只写了这是模型在测试集上 3 次试验的结果。附录里另一个实验写得具体一些：那里的 3 次试验，是把模型训练 3 遍，每一遍用不同的随机数种子，再各自在 500 条购物要求上测。随机数种子是一个起始数字，程序里的随机结果由它决定。主要结果的 3 次试验是不是同样的做法，论文没有写明。出处：WebShop 的论文。
  • Zhu 等人的数字在论文的哪一部分。38%、1.4% 到 5.2%、28 个百分点和 24% 来自论文正文。5.3%、40% 和 9.6%、53 分钟的例子来自附录。论文里有几处数字前后略有出入，比如附录里的 5.3%，在正文讲相关研究的地方写的是 5.2%。出处：Zhu 等，2025。
  • τ-bench 的 40% 和 9.6% 里各包含什么。论文正文写的是：办不了的任务占航空任务的 38%、零售任务的 6%，按子串匹配检查数据库里原样文字的任务占航空任务的 2%、零售任务的 3.6%。附录给出两种 agent 的成绩：什么都不做的是 38% 和 6%，把数据库内容全部输出的是 40% 和 9.6%。论文没有写出加法，两组数相加都对得上。出处：Zhu 等，2025。
  • OSWorld 被低估的是哪个 agent。论文说它是当时 OSWorld 上最好的开源 agent，名字在论文里写作 UI-TAR。出处：Zhu 等，2025。
  • 24% 的名次是怎么算的。Zhu 等人引用的那项研究叫 UTBoost。它给 SWE-bench 的题目补了测试用例，重新评了排行榜上各个系统交出的补丁。SWE-bench Verified 的排行榜上当时有 45 个系统，重新评分后 11 个的名次变了，占 24.4%。Zhu 等人的论文把这个数写成「前 50 名里有 24%」。出处：UTBoost 的论文。
  • 「最高可达 100%」出自哪里。这个说法在论文的摘要、引言和结论里都出现了，都没有说明算法。论文正文里和它对得上的一个例子是另一个被检查的基准测试 SWE-Lancer：agent 一道题都不解决，也能拿到 100% 的分数。论文没有写明 100% 指的就是这个例子。出处：Zhu 等，2025。
