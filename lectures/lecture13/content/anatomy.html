先看结论

  • agent 的基准测试给的是一个任务和一个可以动手的环境。agent 在里面做很多步，最后按它做成了什么来评分。
  • 讲义把它拆成两块：任务定义（要解决什么任务）和评估协议（怎样把一个 agent 系统放到这个任务上去跑）。
  • 任务定义里有三样：问题描述、环境、验证。每一样都有一条从简单到真实的轴，不同的基准测试落在轴上不同的位置。
  • 评估协议是五个问题：每题跑几次、什么时候停、模型怎么设置、用谁的运行框架和工具、结果怎么汇总。同一个模型，这五个问题的答案不同，分数就不同。

它和考试类的基准测试差在哪

讲义给 agent 基准测试下的定义是：让一个系统在环境里做很多步动作来完成一个任务，然后给它完成的结果评分。和上一部分的考试、聊天、安全三类相比，输入、过程、输出都变了。

{{slide 31 | 左边是考试类基准测试的流程，可以写成一行 response = LM(prompt)。右边是 agent 基准测试：agent 是模型加上包在它外面的程序（工具、prompt、记忆），它和环境来回很多轮；评分看的是环境的最终状态，运行轨迹可以作为参考。}}

图里有一个细节值得记住：评分的主线是从环境的最终状态连到验证的，运行轨迹那条线是虚线。也就是说，多数 agent 基准测试评的是结果，过程怎么走的不计分。

两大块：任务定义和评估协议

{{slide 33 | 讲义用一个例子把任务定义的三样画在一条线上。问题描述是一段求助：用户运行了一条 ffmpeg 命令，想把视频缩放到 1280×720，结果输出还是 1920×1080，请 agent 查原因，可能要看 parse_args.py。agent 读了问题，在环境里工作（发出动作，收到观察结果），交出一份代码改动，最后由验证给出通过或不通过。}}

下面三节分别看问题描述、环境和验证。讲义给每一样都画了一条轴或一张表，并把后面要讲的案例放了上去。

问题描述：要 agent 做什么，交什么

问题描述要说清两件事：让 agent 做什么，以及它应该交出什么。讲义画的轴，一头是把要求全部写明的指令，另一头是只给一个开放的目标。

{{slide 34 | 从左到右，问题描述给出的信息越来越少，agent 要自己补的越来越多。}}

环境：在哪里做，手里有什么

环境要说清两件事：agent 在哪里执行任务，开始时手里有哪些东西。讲义画的轴，一头是抽象的、模拟出来的环境，另一头是真实的环境。

{{slide 35 | 从左到右，环境越来越接近人真正工作的地方。}}

环境越真实，任务越像实际工作，搭建和复现也越麻烦。第四部分会讲到，这是「自然」和「容易运行」两条性质互相拉扯的地方。

验证：agent 交出来的东西怎么评分

讲义用两个问题把评分方式分成四格。第一个问题：分数是「通过或不通过」，还是一个连续的数。第二个问题：和谁比，是和一个固定的参照比，还是和别的 agent 或人比。

表里的归类是讲义的简化。有几个基准测试的评分办法比表里写的复杂，比如 τ-bench 除了检查数据库还检查回复的内容，OSWorld 可以给小于 1 的部分分。细节见第三部分。

选哪一格，会影响后面的很多事。通过或不通过的分数好懂，但做对九成和完全没做是同一个零分。连续的分数能看出差距，但要先回答「多少分算好」。和别人比的分数不会封顶，但换一批对手，同一个系统的分数就变了。这一段是我的说明，讲义只给了分类。

评估协议：五个问题

任务定义说的是题目。评估协议说的是怎么让一个 agent 系统去做这些题。讲义列了五个问题。

讲义第 65 页有一张图把这件事说得很具体。同一个基准测试上，用最简单的运行框架跑一次是 48%，换成自己定制的运行框架跑一次是 61%，定制的运行框架跑五次取最好的一次是 72%。三个数都可以叫作「这个模型在这个基准测试上的分数」。图上的数是讲义为了说明问题画的示意，没有标出处。

到底是几块：两块、三块还是四块

这套拆法在课程材料里有三个版本，数出来的块数不一样。它们说的是同一件事，差别在于「什么时候停」和「能用什么工具」算在题目里，还是算在跑分的规定里。

i
讲义里有一处前后说法不同。第 37 页说评估协议是「和 agent 有关、不绑定在基准测试上的参数」。第 65 页讲公平时又说，要照着基准测试规定的运行框架、工具、预算、模型设置和尝试次数去跑，改了就要说明。两处合起来读，我的理解是：这些参数的值是在每次跑分时才填的，所以不属于题目本身；但基准测试通常会给出规定或默认值，排行榜上的数要能互相比较，就得按同一套值来跑。Press 的四元组干脆把停止条件写进了每个任务。

后面两部分正好各管一块：第四部分的七条性质说的是任务定义要满足什么，第五部分的四条要求说的是跑分时怎样对待评估协议。
