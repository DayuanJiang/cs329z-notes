先看结论

  • 这一部分把执行优化的那一套算法叫作优化器。前面几部分的优化器都是人写好的固定流程。这一部分的做法是把「看结果、想改法、动手改」交给一个会写代码的 agent（能自己调用工具、分很多步去完成任务的语言模型系统）。它能改的东西也从 prompt（发给语言模型的那段输入文字）扩大到任何写成代码的东西。
  • Darwin Gödel Machine 让一个编程 agent 修改它自己的代码，改出来的版本只要还能通过编译、还保有编辑代码的能力，不管分数高低都留在一个档案里。80 轮之后，它在 SWE-bench 的一个 200 题子集上的解决率从 20.0% 升到 50.0%。
  • Meta-Harness 让一个编程 agent 读取以往所有候选方案的代码、分数和运行记录，再决定下一步改什么。运行记录指系统每次运行留下的每一步的输入和输出，这一讲的其他部分也叫运行轨迹。对比实验显示，能读到原始的运行记录是最关键的一条。
  • autoresearch 用一份很短的说明，让 agent 在一个训练脚本上不停地做实验：改代码，训练 5 分钟，指标变好就保留，否则撤销。
  • agent 当优化器时，人能控制的主要是评估指标。指标有漏洞，agent 就会利用它；指标有噪声，随机的波动也会被当成改进留下来。

从固定的算法到会写代码的 agent

先回顾前面的优化器是怎么工作的。第三部分里的 OPRO、MIPROv2、GEPA 是三种让语言模型来改写 prompt 里的指令的优化器。它们每一步做什么都是事先固定的：取哪些历史记录，怎样拼成一段输入交给语言模型，拿回来的新指令怎样评估。语言模型只负责其中「写一条新指令」这一步。

这样做的局限是，语言模型提出改动时只能看到算法挑出来的一小部分历史。后面要讲的 Meta-Harness 的论文把这一点当作以往优化器的主要问题。

这一部分的三个系统换了一种做法。优化的对象是一份代码，执行优化的是一个编程 agent，它可以自己决定读哪些文件、查哪些记录、改哪一处、跑什么命令。固定下来的只有外层的循环：提出一个改动，评估，把结果记下来，再来一遍。

OPRO 已经有类似的想法：把以往的指令和分数直接交给语言模型，看它提出什么。区别在于，OPRO 每次只给它看分数最高的 20 条指令，这里接手的是一个能自己读全部文件、跑命令的 agent。

最后一行没有变。无论谁来提出改动，判断改得好不好的仍然是评估指标。这一点在本页后面会变得很重要。

Darwin Gödel Machine：让 agent 改自己的代码

Darwin Gödel Machine（下面简称 DGM）是一个会修改自身代码的编程 agent。这里的「自身代码」指 agent 的运行框架：它有哪些工具，按什么流程做事。底下的语言模型是冻结的，权重不变。

{{fig 107 | 左边是档案（Archive），里面是到目前为止留下来的所有 agent，连线表示谁是从谁改出来的。从档案里选一个 agent 当父代，让它修改自己，得到一个子代；子代在基准测试上评估后加入档案。右上是自我修改这一步的输入和输出，右下是评估这一步的输入和输出。图片来源：Zhang 等。}}

一轮里发生什么

每一轮有四步。

  • 选父代。从档案里选一个或几个 agent。档案一开始只有一个最基础的 agent，它只有两个工具：一个执行 bash 命令，一个查看和编辑整个文件。
  • 自我修改。被选中的 agent 读自己在基准测试上的评估记录，提出下一个要给自己加的功能，然后在自己的代码仓库里把它实现出来。产出是一份代码改动，也就是一个新的 agent。按论文附录的说明，「提出要加什么功能」这一步用的是一次单独的语言模型调用，实现由 agent 自己完成。
  • 评估。新的 agent 去做编程的基准测试（benchmark，一组题目加一个打分的办法），得到一个分数。
  • 加入档案。只要新的 agent 能通过编译，并且还保有编辑代码的能力，就加入档案，不管它的分数比父代高还是低。其余的丢弃。分数变低的也留下，是因为通向最好那个 agent 的路径上就有分数下降的步骤，见下面的结果。

父代怎么选

选父代的规则是：一个 agent 被选中的机会，大致和它的分数成正比，和它已经有的子代数量成反比。这样分数高、又还没怎么被尝试过的 agent 最容易被选中。分数已经是满分的 agent 不参加选择，其余每个 agent 被选中的机会都大于零。

结果

论文在两个编程基准测试上各跑了 80 轮，每轮生成一个新的 agent。这样一轮一轮提出新的 agent 并评估的过程，下面叫搜索。

{{fig 108 | 左：SWE-bench 实验里的档案，每个圆点是一个 agent，颜色越接近黄绿色分数越高，五角星是最后最好的那个。圆点边框的颜色表示它被评估到了哪一级：只做了 10 道题、做了 60 道题、做了 200 道题。右：分数随轮数的变化。浅蓝色线是档案里所有 agent 的平均分，蓝色线是到当时为止最好的分数，黑色线是通向最后最好的 agent 的那条路径，旁边标的是每一步加的功能。图片来源：Zhang 等。}}

看这组数字时有三点要留意。

  • 50.0% 是在 200 道题上的成绩。它不能直接和排行榜上 SWE-bench Verified 全部 500 道题的成绩比。论文自己做了对齐：当时排行榜上经过核查的开源系统里最好的是 53.0%，在同样这 200 道题上是 51.0%。所以论文的结论是 DGM 找到的 agent 和人设计的最好的开源系统「相当」，它也承认还比不上不开源的最好系统。
  • 路径上有分数下降的步骤。右图的黑线在第 4 轮和第 56 轮都往下走了，之后才出现超过所有前辈的 agent。如果只保留分数变高的改动，这条路径就走不通。这是保留整个档案的理由。
  • 代价不小。论文估计，SWE-bench 上跑一遍大约要两周，花费约 22,000 美元。

DGM 给自己加的功能，大多是人设计编程 agent 时也会想到的。论文里提到的有下面六项。

  • 按行查看文件，不必每次读整个文件。
  • 用替换字符串的方式改文件，不必每次重写整个文件。
  • 生成的补丁是空的就重试。
  • 上下文快满时自动做摘要。
  • 一道题生成多个补丁，再让另一次模型调用挑出最好的。
  • 生成新补丁时参考之前的尝试。

哪些设计是必需的

论文做了两个对照实验，各去掉一个设计。下面的表里还有第三种做法：保留档案，但选父代时只看分数，每次都选分数最高的那个。

{{fig 109 | 两个基准测试上，三种做法到当时为止最好的分数。蓝线是完整的 DGM。绿线去掉了自我改进：负责修改的始终是最初的那个 agent。黄线去掉了开放式探索：没有档案，每次都在最新的版本上接着改。左图顶上的红色虚线是经过核查的最好的开源系统在同样 200 道题上的成绩，右图的紫色虚线是一个有代表性的开源 agent（Aider）的成绩。图片来源：Zhang 等。}}

两个设计都需要：让变好了的 agent 来修改自己，以及回到早先的版本上另开一条路，都对最后的成绩有明显的贡献。去掉档案的那一种损失最大。有档案但每次都选分数最高的当父代，两个基准测试上的成绩也都低于完整的 DGM。

+
名字的来历。Gödel machine 是 Jürgen Schmidhuber 提出的一个理论构想（DGM 的论文引用的是他 2007 年的文章）：一个 AI 反复修改自己，每次修改之前都要先在数学上证明这次修改是有益的。实际中这种证明几乎做不出来。DGM 把「先证明」换成了「跑实验看分数」。Darwin 指的是它的做法和进化相似：从已有的个体里选一个，改一改，留下来。论文也写明了这样做的前提：在编程基准测试上分数更高，就说明编程能力更强，也就更有能力修改自己。出处：Zhang 等。

Meta-Harness：让 agent 看到全部的历史

Meta-Harness 优化的对象也是运行框架，也就是前面说的包在模型外面的那层程序。论文看重的是它管信息的部分，把运行框架定义成决定存下哪些信息、取回哪些信息、把哪些信息呈现给模型的那部分代码。

论文的主张是，以往的文本优化器给「提出改动」这一步看的东西太少了：有的只看上一个版本，有的只看分数，有的只看一段摘要。Meta-Harness 把以往所有候选方案的全部记录放进一个文件系统，让一个编程 agent 自己去翻。

{{fig 110 | 三步循环。第 1 步，一个 agent 读文件系统，里面是以往所有候选方案的代码、运行记录和分数，然后提出一份新的运行框架代码。第 2 步，把新的运行框架配上模型，在任务上评估。第 3 步，把这次的代码、推理过程和评估分数全部存回文件系统。图片来源：Lee 等。}}

几个具体的设计：

  • 提出改动的是 Claude Code，配的模型是 Opus 4.6。每个运行框架是一个单文件的 Python 程序。被它包着的那个模型是冻结的。
  • 记录比 agent 的上下文窗口大得多。agent 用 grep、cat 这类终端命令去查，不会把全部记录一次读进来。论文统计了一次实验：agent 每轮读的文件数的中位数是 82 个，其中约 41% 是以往运行框架的源代码，约 40% 是运行记录。
  • 没有选父代的规则。这一点和 DGM 不同。agent 可以查看任何一个以往的候选方案，自己决定在谁的基础上改。
  • 测试集不给 agent 看。agent 得到的反馈只来自搜索用的那部分数据。文本分类和数学推理两个实验是这样做的。Terminal-Bench 2.0 的实验是例外，搜索和最后的评估用的是同一批任务，见下面的结果表。

论文用一张表比较了各种方法每一轮可以用的信息量，单位是百万 token。token 是模型处理文字的最小单位，大致是一个词或半个词。原表有七种方法，下面列出 Meta-Harness 和第三部分讲过的三种。

表里「能看到多少历史」一列说的是以往各轮的历史以什么形式留下来。OPRO 留下的是一个有限的窗口，按第三部分的内容，窗口里是分数最高的 20 条指令。GEPA 一行的「摘要」可以这样理解：它每一轮反思时读的是当前一小批题的原始运行记录、分数和文字反馈，以往各轮的运行记录不再给它看，留下来的是已经写进指令里的结论。

autoresearch：让 agent 整夜做实验

autoresearch 是 Andrej Karpathy 在 2026 年 3 月公开的一个小项目。它把上面的思路用到了模型训练上：给 agent 一个小而完整的语言模型训练程序，让它自己不停地做实验。这个训练程序是他的 nanochat 项目的单 GPU 简化版。

{{fig 113 | 循环的各步：读上下文，提出一个改动，提交并训练，看指标有没有变好。变好了就接受这个改动，没变好就用 git 撤销。两种情况都把结果记到一个表格文件里，然后重复。图片来源：Cerebras 的文章。}}

整个项目只有三个要紧的文件，分工很清楚。

两个设计让实验之间可以直接比较。

第一，每次训练的时间固定为 5 分钟，不管 agent 把模型改成了什么样。这样大约每小时能做 12 个实验，一个晚上约 100 个。

第二，指标只有一个：验证集上的 bits per byte（简称 val_bpb）。它量的是模型预测验证集的文字时，平均每个字节需要多少比特来编码，越低说明预测得越准。

README 说选这个指标的理由是它和词表大小无关，改了模型结构之后仍然可以公平地比较。可以这样理解：一段文字有多少个字节是固定的，它被切成多少个 token 却随词表而变。所以按字节平均的数在词表不同的模型之间可以直接比，按 token 平均的数不行。按上面的文件分工，分词器放在 agent 不能改的 prepare.py 里，所以在这个项目里词表不会变。

{{fig 114 | program.md 里规定实验循环的那一段。}}

这一段规定的循环一共九步，大意如下。

  1. 看 git 的状态：现在在哪个分支、哪次提交上。
  2. 带着一个实验想法，直接改 train.py。
  3. 提交。
  4. 运行实验，把输出全部重定向到日志文件，不要让输出涌进自己的上下文。
  5. 从日志里取出结果。
  6. 如果取不到结果，说明运行崩溃了。读日志的最后 50 行找原因并尝试修复，试了几次还不行就放弃这个想法。
  7. 把结果记到表格文件里。
  8. 如果 val_bpb 变低了，保留这次提交，在它上面继续。
  9. 如果 val_bpb 一样或更差，用 git 回到开始的地方。

说明里还特别强调了一条规定：循环开始之后永远不要停下来问人要不要继续，人可能在睡觉；想不出主意了就再想，去读代码里引用的论文，把之前差一点成功的想法组合起来试。

{{fig 115 | 一次运行的记录。横轴是第几个实验，纵轴是 val_bpb，越低越好。灰点是被撤销的实验，绿点是被保留的改动，绿色折线是到当时为止最好的值，旁边的小字是每个被保留的改动的内容。图片来源：autoresearch 的代码仓库。}}

这次运行一共做了 83 个实验，留下了 14 个改动。图的标题写的是 15 个被保留的改进，图上标的 15 个点里第一个是基线，所以实际被保留的改动是 14 个。

val_bpb 从大约 0.998 降到大约 0.977，这两个数是从图上读的。

被保留的改动有下面几类，都是训练模型时常调的设置。

  • 把总的批大小减半，以便在 5 分钟里多走几步。
  • 调整学习率预热和下降的比例。训练开始时学习率从小逐渐调大，叫预热，后面再逐渐调小。
  • 改模型的深度，也就是层数。
  • 调几处学习率和初始化。初始化指训练开始时给权重取什么值。
  • 改注意力窗口的安排。注意力窗口指模型处理一个 token 时往前能看到多远的文字。
  • 调位置编码的频率。位置编码是告诉模型每个 token 排在第几个的一组数，频率是算这组数时用的一个设置。

指标成了最要紧的东西

把优化交给 agent 之后，评估指标是人手里最主要的控制手段。agent 很会把一个指标的数值做高，所以这个指标必须真的代表你要的东西。

下面三个指标出问题的例子，一个来自 DGM 的论文，两个和 autoresearch 有关。

三份材料各自给出了应对的办法，合起来是四条。

  • 把评估放在 agent 改不到的地方。autoresearch 把评估函数放在只读的文件里。DGM 的作者发现，把检测函数藏起来不让 agent 看到，钻空子的情况会少一些。要注意 autoresearch 的「只读」是写在说明里的一句话，没有技术上的限制。
  • 把接受改动的门槛定严。规则只写「变低就保留」时，随机波动带来的下降也会被留下，上面表里换随机数种子的那一行很可能就是这样。按那一行的分析，一个合理的做法是要求差距超过随机波动的幅度，并用多个种子重复实验来确认。Cerebras 的文章把整套做法归纳成一句话：定一个可以度量的目标，把控制它的代码交给 agent，规定一个改动必须满足的硬性条件，全部记下来，重复。
  • 隔离每个实验，清理上下文。Cerebras 的作者修正偏离的办法是：清掉环境里分散注意力的内容，给每个实验建干净的独立目录，加上更严、更频繁的检查点，并且人主动把 agent 拉回原来的目标。
  • 留着人的检查。DGM 的全部运行都在隔离的沙箱里，有时间上限，档案里保存着每一次修改的来历，可以回头审查。

这和古德哈特定律是一回事。DGM 的论文在讲那个钻空子的例子时，引用的就是这条定律：当一个度量变成了目标，它就不再是一个好的度量。第 13 讲会从基准测试的角度再讲它。在这里，追分数的是一个不知疲倦、每小时能试十几次的 agent，定律起作用的速度也就快得多。DGM 的作者还提醒：如果基准测试没有覆盖安全、稳健这些你也在意的性质，自我改进的循环可能把这种偏差一代一代地放大。出处：Zhang 等。

这一部分的小结

  • agent 是相当有能力的优化器。
  • 给它搭一个环境，让它能记录结果、提出想法、动手执行，它就能相当好地优化任何写成代码的东西。
  • 这时评估指标成了最需要人来仔细检查的部分。

到这里，改 prompt、改权重、让 agent 来改，三类办法都讲过了。最后一部分回答一个实际的问题：手上有一个系统要优化时，该改 prompt 还是改权重。
