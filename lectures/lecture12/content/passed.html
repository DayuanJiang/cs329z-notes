先看结论

  • 测试通过，不等于这条运行轨迹是一份好的示范。通过的轨迹里，有的是靠捷径通过的，比如从代码仓库的历史记录里找出现成的修复。有的轨迹里有无效、多余或有风险的步骤。
  • 阿里巴巴的 Qwen 团队用强化学习（让模型自己反复去做任务，做成了得到奖励）训练编程 agent 时，观察到七种容易变成捷径的行为。不加监控时，模型的测试通过率一路上升，其中靠捷径通过的比例越来越大，不靠捷径通过的比例在训练后期急剧下降。
  • 他们的办法是监控整条轨迹，发现捷径就扣奖励。在三个基准测试（benchmark，一组题目加一个打分的办法）上平均，靠捷径通过的运行占全部运行的比例从 28.57% 降到 0.56%，不靠捷径通过的运行占的比例从 40.22% 升到 60.53%。
  • SWE-Prime 这种办法分两个阶段挑通过了测试的轨迹。第一阶段按过程和结果的质量给整条轨迹评分，在每一类问题里留下总分最高的 10%。第二阶段在留下的轨迹里挑出值得学的片段。只用这 10% 的成功轨迹，训练出的模型在测过的六种组合（三个基础模型各配两个基准测试）上都好于用全部成功轨迹训练的。基础模型指拿来继续训练的那个现成的模型。

通过测试，不等于好的示范

第二和第三部分挑的是任务。任务挑好之后，让 agent 去做。agent 指能自己调用工具、分很多步去完成一个任务的语言模型系统。它每做一遍任务，得到一条运行轨迹（trajectory），也就是这一次运行里每一步的动作和看到的结果的完整记录。

两种训练都要用到轨迹。监督微调是用现成的示范继续训练模型，让它照着做。强化学习是让模型自己反复去做任务，由验证器（verifier，判断任务有没有做成的程序）判定做成没有，做成了得到奖励。

在监督微调里，轨迹是被模仿的对象。在强化学习里，轨迹里的做法按这一次运行得到的奖励被加强或削弱。两种用法都要回答同一个问题：这条轨迹是不是好的。

最简单的标准是看它有没有通过测试。这个标准对通过的和没通过的轨迹都会判错，下面的图列出了四种情况。

靠捷径通过的：The Verification Horizon

先看一个例子。编程任务常常是根据代码仓库里一次真实的修改造出来的：交给 agent 的是这次修改之前的代码，要它自己把问题修好。对这份代码来说，那次真实的修改是后来才有的修复。仓库的历史记录里如果还留着这份后来的修复，agent 用 git log 之类的命令把它找出来照着改，测试就会通过，可是它没有自己解决这个问题。

这种情况叫 reward hacking：模型找到办法让验证器判通过，却没有真正完成任务。下面把它叫作走捷径。

《The Verification Horizon: No Silver Bullet for Coding Agent Rewards》是阿里巴巴 Qwen 团队 2026 年 6 月的一篇论文，讲他们训练编程 agent 时怎样构造奖励。它的出发点是：对编程 agent 来说，生成一个复杂的候选解答已经不难，可靠地验证它成了更难的问题。

验证难，是因为能造出来的任何验证器，都只能近似地衡量人真正想要的结果。强化学习奖励的是验证器判通过的行为，被训练的模型就可能找到让验证器判通过、却没有真正完成任务的办法。论文的说法是，训练过程中的优化会扩大验证器的判定和人真正想要的结果之间的差距。

{{fig 37 | 左：一张示意图，没有数据。横轴是训练时间，纵轴是能力。红线是验证器，蓝线是被训练的模型。蓝线超过红线的地方标着 reward hacking，之后验证器升级一次，蓝线才继续上升。右：四个数据集的任务质量和规模。横轴是被判为合格的任务占的比例，纵轴是任务数（对数刻度）。图片来源：Qwen 团队，2026的图 1 和图 2。}}

左图画的就是这个过程。图里把验证器和被训练的模型各画成一条能力曲线。按论文的说法，模型的能力超过验证器之后，也就是模型已经能找到验证器查不出来的办法让它判通过，就可能开始走捷径。这时要先升级验证器，训练才能继续有效。论文的结论是验证要和 agent 一起不断升级。

论文把走捷径看成误判的一种特殊情况。一般的误判是测试设计得不够好，把没做对的判成了对的。走捷径的时候，验证器同样把没做对的判成了对的，区别是这一次的误判是 agent 主动造成的。论文在这里举的例子是利用泄露的信息，比如从网上取回这个任务原本的修复。泄露的信息指 agent 本来不该拿到、却能找到的答案线索。后面的表里还有用不到泄露的信息的做法，比如修改测试。

配图的右半边：任务越多的数据集，合格的比例越低

右图讲的是任务的质量，这是第二部分的话题，和走捷径是两件事。图上的「合格」由论文里的一个评审 agent 判定：它进到任务的环境里查看仓库、执行命令、读测试，判断任务说明是不是写清楚了，测试和任务说明是不是对得上。四个数据集的任务数和合格的比例见下表。

四个数据集里，任务越多的，合格的比例越低。SWE-Universe 用评审 agent 筛过之后，剩下约 4.6 万个任务。

SWE-bench Verified 的约 96.5% 是这个评审 agent 的判定，也就是说它判为不合格的任务只占约 3.5%。第二部分讲过 2026 年的另一次人工审查，判定者和标准都和这里不同，查出的问题也多得多。那一次 OpenAI 请工程师审查了这 500 道里的 138 道题，有 59.4% 被查出实质的问题，约 82 道。只算这 82 道，就已经超过 500 道的 16%，远多于评审 agent 判为不合格的约 3.5%。所以评审 agent 判为合格的任务里，也有人工审查认为有问题的。

七种容易变成捷径的行为

论文的实验用的是 Qwen 内部的一个模型（论文里叫 Qwen-Turbo），在 SWE-Universe 的任务上做强化学习。每个任务是根据 GitHub 上的一个代码合并请求造出来的，装在 Docker 容器（一个隔离的、可以整个重建的运行环境）里，由一个脚本判定通过或不通过。代码合并请求（pull request，简称 PR）指请求把一组代码改动并入仓库的申请。

训练之前，环境已经加固过：PR 之后的 git 历史被删掉了，用不到网络的任务断了网。即使这样，他们在模型的运行里仍然观察到七种容易变成捷径的行为。

下表列出这七种行为。表里统计的是 agent 做了这类动作的运行，比如用 git log 去查某个 PR 的编号。做了这类动作，不代表每一次都拿到了答案。

表里有几个词要先说明。issue 指代码仓库里报告问题的帖子。断言指测试里检查某个结果是否符合预期的一句代码。提交指记进仓库历史的一次代码改动。补丁（patch）指一组代码改动，参考补丁（reference patch）指任务原本的那份由人写的修复，评测时当作标准答案。看得到的测试指 agent 在环境里能读到的测试，隐藏的测试指评分时才用、agent 读不到的测试。

这张表给出的是观察到的相关关系，不能说明是这些行为导致了通过或不通过。从表里能看出三点。

  • 这些行为很常见。专门针对看得到的测试写代码出现在 30% 的运行里，翻仓库的历史出现在 21% 的运行里。
  • 直接取现成的答案很少见，但这样做的运行通过率最高。只有 4.32% 的运行这样做，这些运行的通过率是 72.34%，比总体高 12.35 个百分点。
  • 七种里只有两种的通过率高于总体。另外五种都低于总体，改评测运行环境的那些运行甚至低了 18.52 个百分点。这些数是在已经加固过的环境里统计的。

测试通过率在上升，不靠捷径通过的比例在下降

上面的表里，七种行为里有五种的通过率并不高于总体。不过强化学习是按每一次运行给奖励的：只要某一次运行靠捷径让测试通过了，这一次就得到奖励，奖励不区分它是不是捷径。所以强化学习有可能把捷径也一起加强。

论文把训练过程中的成绩画成了两种曲线。一种是测试通过率。另一种是不靠捷径通过的比例，算它要用到一个监控器：监控器检查每条轨迹里有没有走捷径的迹象，被它标记的通过也算作不通过。

图里比较了两次训练。加监控的那次用监控器扣奖励，不加监控的那次只用它来统计。监控器怎么工作，下一小节讲。

图里的三张小图是三个基准测试。SWE-bench Verified 考的是修复真实代码仓库里报告的问题，共 500 个经过人工检查的任务，都来自 Python 项目。SWE-bench Multilingual 把同一类任务扩展到 Python 以外的 9 种编程语言，共 300 个任务。SWE-bench Pro 是另一套考编程 agent 的基准测试。第一个和第三个在第二部分讲过。

{{fig 40 | 三张小图是三个基准测试：SWE-bench Verified、SWE-bench Multilingual、SWE-bench Pro。横轴是强化学习的步数。蓝色是不加监控的训练，黄色是加了监控的训练。浅色的虚线是测试的通过率，深色的实线是把被监控器标记的通过也算作不通过之后的成绩，也就是不靠捷径通过的比例。图片来源：Qwen 团队，2026的图 5。}}

看蓝色的两条线。浅色虚线（测试通过率）一直在上升。深色实线在第 70 到 80 步之后急剧下降。从图上读，在 SWE-bench Verified 上，不加监控的训练到第 100 步时，测试通过率约 78%，不靠捷径通过的比例只剩约 36%。训练开始时这两条线都在约 57%，所以不靠捷径通过的比例比训练开始时还低。

对策：监控整条轨迹

论文的做法是在强化学习的循环里加一个监控器。它检查整条轨迹里记录下来的命令、网络访问、git 操作和文件修改，和一组高风险的模式做比对。一次运行匹配上了，就扣它的奖励。

这组模式也要更新。每训练一段时间，一个负责审查的 agent 去读抽样出来的轨迹，找新出现的捷径，反复出现的就加进模式里。论文给的理由是，走什么捷径取决于模型当时的能力，模型变强之后，可能找到最初审查轨迹时还没有出现过的新捷径。

监控器是在训练的循环里起作用的。论文明确说，这是在训练时按运行的过程来修正奖励（process-aware reward correction），和训练结束之后再筛数据是两种做法。同样的检查也可以用在挑监督微调的数据上，下面的 SWE-Prime 就有一项「有没有翻 git 历史」的评分。

下面的表比较了不加监控和加了监控训练出来的两个模型。

把每一行的两种通过加起来，就是通常报告的测试通过率。在 SWE-bench Verified 上，不加监控的模型是 36.49% 加 41.35%，约 77.8%。加了监控的模型是 64.98% 加 0.70%，约 65.7%。一个只数测试通过的排行榜，会把走捷径的那个模型排在前面。

i
读这些数时要注意的两点。
  • 「靠捷径」是监控器判的。没有人逐条标注轨迹。论文没有报告监控器的准确率，所以表里的「靠捷径通过」，准确地说是「通过了并且被监控器标记」。
  • 别人没法重复这些实验。模型是 Qwen 内部的版本，训练数据也是内部的，59.99% 这个总体通过率和各种行为出现的比例都不能用公开的数据复现。

别的团队也记录了同样的行为。第三部分的 LEGO-RL（一个用强化学习训练编程 agent 的框架）在加上防护之前统计过：agent 去读 git 历史的运行占 4.6% 到 20.5%，下载参考补丁的占 1.9%，改测试文件的占 2.4% 到 19.4%。LEGO-RL 的论文没有写明这两个范围的两端各是在什么设置下测的。它的防护办法有三条。第一，agent 工作期间，仓库的全部历史被合并成一次提交，评分之前再恢复，这对应前面七种行为里的「翻仓库的历史」。第二，联网由一道 agent 改不了的防火墙控制。第三，测试到评分时才放进环境。出处：Du 等，2026的附录 A。

通过了，但过程里有不值得学的步骤：SWE-Prime

不靠捷径通过测试的轨迹，质量也有高有低。SWE-Prime（Zheng 等，2026，中山大学和华为云等）这篇论文的出发点是：任务做成了，不保证这条轨迹是高质量的示范，成功的轨迹里仍然可能有无效的、多余的或有风险的步骤。

{{fig 42 | 一条成功的轨迹，最后测试通过。中间有三步分别被标成无效、多余和有风险。图是示意。}}

拿这样的轨迹做监督微调，模型会把这些步骤一起学进去，所以下面把它们叫作不值得学的步骤。SWE-Prime 分两个阶段来挑：先挑整条轨迹，再在留下的轨迹里挑片段。

{{fig 43 | 左边是一条原始的轨迹。右上是第一阶段，从三个方面挑整条轨迹。过程的质量和结果的质量各有评分。代表性这一方面没有评分，办法是先把 issue 分类，再在每一类里按评分挑。右下是第二阶段，把轨迹切成片段，给每个片段评分，只有分数够高的片段参与训练。图左边的英文说明把第一阶段概括成按过程的质量来挑，这是简略的说法。图片来源：Zheng 等，2026的图 2。}}

两个阶段各用下面的一小节来讲。

第一阶段：挑整条轨迹

候选是 32,161 条成功解决了 issue 的轨迹，来自 Nebius 公开的一个数据集，由 Qwen3-Coder-480B 在 OpenHands 这个运行框架（包在模型外面、给它工具并管理多轮对话的程序）里生成。每条轨迹有五项评分，全部由规则从日志里算出来，没有用语言模型当评审。

挑的时候还要顾及代表性，办法是先把 issue 分类，再在每一类里各取总分最高的 10%。这样留下的轨迹覆盖各种类型的问题，不会全部集中在某一类容易得高分的问题上。

分类分两步。第一步，用一个文本向量模型（Qwen3-Embedding-8B）把每个 issue 的描述转成一串数字，意思相近的描述得到的数字也相近。第二步，用聚类算法（HDBSCAN）把数字相近的 issue 归成一类。归不进任何一类的 issue，论文只说挑的时候各自单独对待，没有写具体怎么挑。一共分出多少类，论文也没有给出。

第二阶段：挑片段

留下的轨迹里也有不值得学的步骤，所以第二阶段给轨迹里的片段打分。一个片段是意图相同的连续几步。

切片段和打分都由一个语言模型来做。它对照 issue、轨迹的上下文和参考补丁，按下面三条标准给每个片段打一个质量分，范围是 0 到 10，分越高表示这个片段越值得学。用的是哪个语言模型，论文里没有写明。

  • 贡献。这个片段有没有推进最后的修复，比如定位问题、收集信息、修改、验证或者从错误里恢复。
  • 好不好学。按当时能看到的信息，这个片段是不是一个清楚的「看到什么、做了什么、得到什么反馈」的过程。
  • 风险。里面有没有不希望模型学到的做法，比如无关的探索、没有信息量的失败、不安全的操作，或者把答案直接写进代码里。

质量分达到 7 分的片段才作为训练的目标。低分的片段不删掉，仍然留在输入里当上下文，只是不对它们计算损失（训练时衡量模型的输出和示范相差多少的数）。也就是说，模型读得到这些步骤，但不会被训练去复现它们。

结果：用挑出的 10% 成功轨迹训练，好于用全部成功轨迹

论文用三个基础模型和两个基准测试，比较了不训练和四种训练数据。

最后一列在六行里都高于「全部成功的轨迹」那一列，高出 2.05 到 10.0 个百分点。

论文摘要里说的「相对提高最多 24.2% 和 12.2%」是相对的比例，说的是其中两行，来自不同的模型。GLM-4.7-Flash 在 Verified 上从 41.4 到 51.4，相对提高 24.2%，是 10.0 个百分点。Qwen3-30B 在 Pro 上从 16.83 到 18.88，相对提高 12.2%，是 2.05 个百分点。

这张表还有四处值得看。

  • 随机取 10% 很差。它在六行里都低于用全部轨迹，多数低很多，其中四行比不训练还低。这说明只减少数据会让成绩变差，SWE-Prime 那 10% 的效果来自挑法。
  • 只挑整条轨迹不够。只做第一阶段的那一列，在六行里有四行低于用全部轨迹。「挑出的 10% 好于全部」这个结论靠的是第二阶段，也就是低分的片段只当上下文、不拿来训练的那一步。
  • 两个关键的参数是按其中一种组合的测试成绩选的。留 10% 和片段的门槛取 7 分，都是看 Qwen3-Coder-30B 在 SWE-bench Verified 上的成绩选出来的，而这正是表里报告的六种组合之一。另外五种组合沿用了这两个值。
  • 没有报告波动。论文没有报告重复训练的结果，也没有给出波动的范围。
