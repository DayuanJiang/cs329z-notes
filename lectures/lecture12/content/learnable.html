先看结论

  • 这一讲里几篇论文用的强化学习算法，是拿同一个任务的几次运行互相比较来更新模型的。几次运行的奖励全都一样时，没有可比的东西，这个任务对这一步更新的贡献是零。
  • 所以要留下模型有时做对、有时做错的任务。DAPO（训练模型做数学竞赛题的一种算法）在训练的每一步都重新筛一次。LEGO-RL 这个训练框架在训练之前让一个模型把每个任务做 4 遍，留下做对 1 到 3 遍的。
  • LEGO-RL 做难度筛选时，还没按难度筛过的任务里 72.7% 一遍都做不对，13.4% 每遍都做对。不筛就拿去训练，留出的评测任务（不参加训练，只用来测成绩）上的解决率和训练时的奖励都没有上升。
  • 难度是相对于模型的。模型变强之后，原来有对有错的任务会变成每次都对。由此可以推出，任务池（训练用的那一批任务）需要随着训练定期重新筛选或补充。WebRL（一种训练模型操作网页的强化学习方法）的办法是每一轮都用模型前面没做成的任务来生成新任务。

奖励全都一样，就什么也学不到

先说明这里的强化学习是怎么更新模型的。模型自己去做任务，每做一遍叫一次运行（rollout）。做完由验证器给一个奖励，验证器（verifier）是判断任务有没有做成的程序。

现在常用的一类算法让模型把同一个任务做好几遍，组成一组，再看每一遍比这一组的平均水平好多少。这类算法里有代表性的是 GRPO（Group Relative Policy Optimization）。每一遍和组内平均水平的差距叫优势（advantage），计算式是：

advantage = (reward - group mean) / group std

也就是：这一遍的奖励，减去组内的平均奖励，再除以组内奖励的标准差。标准差量的是这一组奖励彼此相差多大。优势是正的，这一遍的做法被加强。优势是负的，这一遍的做法被削弱。

{{fig 25 | 同一个任务做 8 遍，实心的圆表示这一遍得到奖励 1，空心的表示 0。上面一行有对有错，模型能从中学到东西。下面一行全对，梯度（模型的参数该往哪个方向调整、调整多少）为零，也就是不产生更新。图是示意。}}

如果一组里每一遍的奖励都相同，每一遍减去平均值都是零。这时标准差也是零，上面的式子成了零除以零，所以实际计算时会在分母里加一个很小的正数（LEGO-RL 的论文写的是 10 的负 6 次方）。这样算出来的优势全是零，这个任务对模型的更新没有任何贡献。全对是这样，全错也是这样。

这就是第一部分说的「没有信号」，意思是这些数据没有告诉模型哪种做法该多做、哪种该少做。没有信号的原因出在难度上：这样的任务本身可以完全正确，只是对现在的模型太容易或太难。

i
这个道理出自数学题上的研究，对 agent 的任务同样成立。提出它的是 DAPO 的论文，DAPO 是训练模型做数学竞赛题的一种算法，下一节介绍。「一组里奖励都相同就没有梯度」只取决于优势是怎么算的，和任务类型无关。agent 指能自己调用工具、分很多步去完成一个任务的语言模型系统。这一讲里有两篇训练 agent 的论文用的是同一类算法。一篇是 CodeMidas 的论文，CodeMidas 是一套自动造编程任务的流程，在第二部分介绍。另一篇是后面要讲的 LEGO-RL，它的论文里也写了同样的结论：奖励相同的一组优势恒为零，不贡献梯度。

模型越强，全对的题越多

这个问题会随着训练越来越严重。训练分成很多步，每一步取一批题让模型作答，再用这一批回答的奖励更新模型。模型变强之后，原来有时做错的题变成每次都对，于是每一批题里，能产生更新的题越来越少。

下面的图来自 DAPO（Yu 等，2025，字节跳动和清华大学等）。DAPO 是在 GRPO 的基础上改出来的算法，用来训练模型做数学竞赛题：模型写一段很长的推理，最后给出一个答案，答对奖励是 +1，答错是 −1。里面没有工具，没有环境，也没有 agent 那样的多步循环。

DAPO 每道题让模型生成 16 个回答，每生成一个回答叫一次采样（sample）。上一节示意图里画的 8 遍和 1、0 两种奖励是简化过的。

{{fig 26 | 横轴是训练步数。纵轴是准确率为 1 的题占的比例，准确率为 1 指模型对这道题的回答全都答对。论文正文用这张图说明，训练时回答全都答对、因而不产生更新的题越来越多，下面也照这样读。图上纵轴的英文标注是 avg@32 = 100%，avg@32 指重复 32 遍取平均的准确率，等于 100% 就是每一遍都答对。标注里的 32 遍和训练时每道题的 16 个回答是什么关系，论文没有解释，见资料说明。图片来源：Yu 等，2025的图 3(b)。}}

从图上读，这个比例从 0 开始，到第 1,000 步左右已经有约四分之一，到第 5,000 步左右约一半，第 7,000 步之后在 55% 到 60% 之间。按论文的解读，训练到后期，一批题里有一多半已经不产生任何更新。DAPO 的论文说，这会让每一批里有效的题数不断减少，梯度的波动变大，训练的信号变弱。

DAPO 的办法：一直抽题，直到一批里都是有对有错的题

DAPO 的做法叫动态采样（dynamic sampling）：每一步多抽一些题让模型作答，把全对和全错的题去掉，再接着抽，直到凑满一批为止。这一批里的每道题都是有对有错的，每道题都能产生更新。

{{fig 27 | 左：横轴是训练步数，纵轴是模型在 AIME 2024（一套数学竞赛题）上的准确率。紫色是用了动态采样的，青色是没用的。右：留下有对有错的题，丢掉全对和全错的题。图片来源：Yu 等，2025的图 6。}}

这样做，每一步要让模型作答的题变多了，但到达同样准确率需要的步数少了。从图上读，用了动态采样的那条线在约 2,300 步达到 43% 左右（纵轴上是 0.43），没用的那条线要到约 6,100 步才到同样的水平。论文说，采样的次数虽然增加，收敛需要的时间反而更短。收敛指训练到成绩稳定下来、不再明显上升。

这张图里的两次训练用的是一套基本的设置，论文叫 baseline setting，没有说明它包含 DAPO 的哪几项改进。所以图上的准确率不能和下面表里的数逐个对照，见资料说明。

DAPO 一共有四项改进，论文的消融实验是把它们逐步叠加上去的。消融实验指逐个加上或去掉一个部件，看成绩变多少。其中处理超长回答的那一项分成了两步，所以下面的表里一共加了五步。

表里有三项要先说明。前两项都和 token 有关，token 是模型处理文字的最小单位。

第一项是 Clip-Higher，它改的是一次更新里一个 token 的概率最多能变多少。GRPO 更新模型时，给每个 token 被选中的概率设了一个变化的范围：拿更新之后的概率除以更新之前的概率，这个比值最低到 0.8，最高到 1.2，也就是上调和下调的限度都是 0.2。

这个范围是通过损失起作用的。训练时要降低的那个数叫损失（loss）。回答里的每个 token 各有一个损失，它由这个 token 的概率比值和所在回答的优势算出来。回答的优势是正的，也就是这个回答比同一道题各个回答的平均水平好，调高其中 token 的概率，损失就下降。优势是负的，调低概率，损失就下降。比值到了范围的边界之后，算损失时用的是边界上的值，再往同一个方向调，损失不再跟着下降，所以模型没有理由再往这个方向调。

这个范围按比值定，原来概率低的 token 一次能上升的幅度就很小。论文举的例子是：一个 token 原来的概率是 0.01，一次更新最多只能升到 0.012。原来概率是 0.9 的 token，上限算出来是 1.08，等于没有限制。所以模型已经常选的 token 很容易变得更常选，原来很少选的 token 即使这一次带来了好的结果，概率也升不了多少。训练下去，模型对同一道题的各次回答会变得几乎一样，论文把这个现象叫 entropy collapse。

DAPO 把下调的限度留在 0.2，把上调的限度放宽到 0.28，也就是比值最低仍是 0.8（1 减 0.2），最高改成 1.28（1 加 0.28）。原来概率低的 token 一次能上升的幅度变大了。论文报告，这样改之后模型生成的回答更多样。

第二项是按 token 平均的损失。GRPO 先在每个回答内部把各个 token 的损失取平均，再在回答之间取平均，所以长回答和短回答的分量相同，长回答里每个 token 的分量就比短回答里的小。论文指出这有两个坏处。写得好的长回答，模型不容易学到里面的推理。写得过长的回答里常有乱码和重复的词，这些内容也得不到足够的削弱。

DAPO 改成把一组回答里所有 token 的损失放在一起取平均。这样每个 token 的分量相同，长回答的分量也就更大。

第三项是对超长回答的处理，表里占两行。训练时给回答的长度设了上限，写到上限还没写完的回答会被截断。表里说的超长的回答，指被截断的回答，或者超过预期长度的回答。论文的实验里，预期的最大长度是 16,384 个 token，再往上留 4,096 个 token 的余量，生成的上限是 20,480 个 token。

原来的做法是回答只要被截断就扣分。论文认为这会带来干扰：一个推理过程正确的回答，可能只因为写得太长就受罚。DAPO 分两步改，下面的表里这两步是先后叠加上去的，各占一行。

第一步是被截断的回答不计入损失，也就是不参与更新。

第二步是按长度扣分。扣分从预期的最大长度开始，比截断的位置早 4,096 个 token。超出得越多扣得越多，扣的分从答对答错的奖励里扣掉。论文说，这样做是让模型知道回答不要写得过长。

动态采样是最后加上的一项，带来 8 个百分点，是五步里最大的一步。这张表没有单独测动态采样，也没有换一个叠加的顺序，所以 8 个百分点是它在另外几项的基础上带来的提高。

最后的 50%，高于 DeepSeek 用同一个基础模型做强化学习得到的 47%（DeepSeek-R1-Zero-Qwen-32B），而 DAPO 只用了后者一半的训练步数。

LEGO-RL：训练之前，先让模型把每个任务做 4 遍

DAPO 的题是数学题，采样一次很便宜，可以一边训练一边筛。agent 的编程任务，一次运行要在容器（一个隔离的、可以整个重建的运行环境）里做几十步，贵得多。LEGO-RL（Du 等，2026，华为和香港中文大学）的做法是在训练开始之前把任务筛好。

LEGO-RL 是一个训练框架，让模型在现成的编程 agent 程序里（OpenHands SDK、Claude Code、OpenCode）直接做强化学习，不改动这些程序。这类包在模型外面、给它工具并管理多轮对话的程序叫运行框架（harness）。这里只看它挑任务的部分。

先查有效性，再查难度

LEGO-RL 的筛选分三步。前两步主要查有效性，也就是任务本身对不对，其中第一步的规则也看代码仓库的多样性和大致的复杂度。最后一步查难度。

前两步筛的主要是第二部分讲的有效性，从 36,884 个减到 21,681 个。

论文记录了一种很隐蔽的缺陷：在检查过的任务里，约 2.5% 的任务的验证器会在运行测试之前，自己先把参考答案的代码改动放进代码仓库。这样一来，不管 agent 做了什么，测试都会通过，奖励和 agent 做了什么没有关系。

最后一步筛的是难度，筛掉得最多：21,681 个里只留下 2,699 个，约八分之一。

{{fig 29 | 一个任务做 4 遍，按做对的遍数分成五种。做对 0 遍和 4 遍的丢掉，做对 1、2、3 遍的留下。}}

做这 4 遍的是 Qwen3.6-27B 加 OpenHands SDK。真正要训练的是另一个模型，Qwen3.5-35B-A3B。

筛选时的统计是：还没按难度筛过的任务里，72.7% 一遍都没做对，13.4% 四遍全对。这两类加起来占了 86%，能在一组运行里产生不同奖励的任务只是很小的一部分。论文把这批还没按难度筛过的任务叫作 unscreened pool，下面简称没筛过的任务。

按这两个比例算，有对有错的任务占 13.9%，比实际留下的 12.4% 略多，12.4% 就是上面说的约八分之一。这点出入论文没有解释，见资料说明。

不筛会怎样

论文做了一个对照实验。四个任务池各有 951 个任务，其余的训练设置相同。三个任务池是按做对的遍数筛出来的，第四个是在没筛过的任务里随机取的。

每种设置只训练了一次。论文自己说明，重复训练时成绩会波动多少还不知道。

任务池会过时

训练之前筛一次，筛选的结果只在一段时间内有效。筛选时「有时做对」的任务，是相对于筛选时的模型说的。模型在训练中变强，这些任务会一个一个变成每次都对。

三个运行框架的情况不完全一样。全对的任务在三个运行框架下都增加了。合计的比例在 OpenHands SDK 下上升。在 Claude Code 下，论文正文没有给合计的数。在 OpenCode 下一增一减相互抵消，基本不变。

论文根据这些结果下的结论是：任务的难度是相对于模型的，一个固定的任务池提供的信号可能越来越少。

由此可以推出，任务池需要随着训练定期重新筛选或补充。LEGO-RL 的论文没有做重新筛选的实验。下面的 WebRL 用的是补充的办法：每一轮都出一批新任务。

WebRL：每一轮都重新出题

WebRL（Qi 等，ICLR 2025，清华大学和智谱）训练的是操作网页的 agent，环境是 WebArena（一组部署在自己服务器上的网站，agent 在上面完成购物、查地图、管理代码仓库之类的任务）。评测用的是 WebArena-Lite，它是从 WebArena 的 812 个任务里选出的 165 个经过人工检查的测试任务。

WebRL 的强化学习分成 8 轮，论文把一轮叫作 phase：每一轮先出一批新任务，让 agent 去做，再用做出来的运行训练模型。上一节 LEGO-RL 的一轮指把固定的任务池过一遍，两处的轮是两回事。

WebRL 面对三个问题，列在下表里。第三个问题论文叫策略分布漂移（policy distribution drift）。策略指模型选动作的方式，一轮一轮训练下来，它会偏离前几轮的样子。

表里第一行有三个词要先说明。基准测试（benchmark）指一组题目加一个打分的办法，用来比较不同的模型。轨迹（trajectory）指一次运行里每一步的动作和看到的结果的完整记录，参考轨迹是人工标注的正确做法的记录。离线的数据集指事先收集好的一批任务和它们的参考轨迹，模型照着这些记录来训练，不用实际去操作网站。

出新任务、判成败、重新学旧数据这三个部分，下面各用一小节来讲。

新任务怎么出，怎么筛

每一轮，GPT-4o 拿 agent 在前面几轮没做成的任务当例子，写出一批新任务。新任务要过两道筛选。

  • 难度合不合适。WebRL 另外训练了一个成败预测模型（论文叫 critic），用来预测一次运行最后能不能成功。它每一轮都和 agent 一起训练。把新任务的指令和初始状态交给它，初始状态指任务开始时、agent 还没有做任何动作的那个网页。它给出一个 0 到 1 之间的分数，可以理解成 agent 现在做成这个任务的可能性。只留下分数在 0.05 到 0.75 之间的任务：太低的现在根本做不了，太高的已经会了。
  • 能不能做。再用 GPT-4o 去掉在 WebArena 里根本无法完成的任务。

每一轮选出 500 个通过筛选的新任务，一共 8 轮。

这套做法和 LEGO-RL 的难度筛选是同一个思路，区别有两处。第一，判断难度的成败预测模型每一轮都和 agent 一起训练，所以标准会跟着模型一起变。第二，新任务是拿前面几轮没做成的任务当例子生成的，所以它们的难度接近模型当前刚好做不成的水平。

没有验证器，谁来判成败

新生成的任务没有人写验证器。WebRL 训练了一个评审模型来判成败，论文叫它 ORM（outcome-supervised reward model）。它读任务的指令、agent 做过的动作和最后那个网页的 HTML，回答「是」或「否」。「是」的概率更大，奖励就是 1。

评审模型和前面的成败预测模型是两个模型。成败预测模型在出题时估计一个任务能不能做成，评审模型在一次运行结束之后判定它做成了没有。

评审模型的准确率约 80%，论文是在两组数据上量的。第一组是 WebArena-Lite 的测试集，以测试集自带的判定程序给出的结果为准，准确率是 80.8%。第二组是 100 条人工标注的运行，以人工的标注为准，准确率是 79.4%。作为对照，用 GPT-4 当评审的几种做法在这两组数据上都是约 71% 到 73%。也就是说，在这两组测试数据上，评审模型的判断大约五次里有一次是错的。

训练时评审模型要判的是新生成的任务，那里的错误率论文没有报告。评审模型判错了，模型拿到的奖励就是错的。第一部分把训练数据出问题的方式分成三种，这属于其中「信号是错的」那一种，在没有现成验证器的环境里很难避开。

重新学旧数据时也要挑

为了不忘掉前面学会的东西，WebRL 把每一轮成功的运行存进回放缓冲区，后面的轮次拿出来重新学。

拿哪些也要挑。WebRL 让上一轮的模型给存下来的每个动作算一个困惑度（perplexity），它量的是模型对这个动作有多大把握。按通常的定义，困惑度是模型给这个动作的概率的倒数，一个动作由多个 token 组成时，用的是各个 token 的概率的几何平均，也就是把这些概率相乘，再按 token 的个数开方。概率是 1 时困惑度是 1，这是最低的值。概率越低，困惑度越高。

WebRL 只重新学困惑度在 1/0.95 到 1/0.5 之间的动作，也就是约 1.05 到 2 之间，对应的概率在 0.5 到 0.95 之间。困惑度低于这个范围的动作，模型的把握已经很大，说明已经学会了。困惑度高于这个范围的动作，模型的把握太小，按它现在的水平还学不会。

论文在第一轮上比较了四种挑法，结果是只学中间一段的最好。

失败的运行不放进去。论文试过把失败的运行也存起来重新学，结果学得更慢、更不稳定。它给的理由是：一次失败的运行里就算有些动作是对的，因为最后的奖励是零，这些动作也很可能被当成坏动作来削弱。第五部分会讲失败的运行在什么条件下可以用，那里把一次运行的完整记录叫作轨迹，所以写的是失败的轨迹。

论文摘要里给的对比是 Llama-3.1-8B 这个模型在 WebArena-Lite 上的成功率：没有微调时是 4.8%，用 WebRL 训练之后是 42.4%。读的时候要知道，WebRL 的强化学习是从监督微调之后的模型（20.6%）开始的，所以强化学习这一段带来的是 20.6% 到 42.4%，约 22 个百分点。

论文还做了消融实验，这里的做法是每次去掉一个部件，看成绩变多少。去掉回放缓冲区，成绩会一轮比一轮差。去掉每轮出新题、只用第一轮的任务，进步更慢，最后的成绩也更低。

几种难度筛选放在一起看

到这一部分为止，这一讲出现过五种为强化学习按难度筛选任务的做法，下表把它们放在一起。第六部分的 LIMO 为监督微调挑数学题时用的也是这个思路，到那里再讲。

五种做法都去掉了对模型太容易的任务。太难的任务，四种一开始就去掉。CWM 开始时留着，给它们加上提示、少抽一些，到强化学习的第二阶段去掉提示，只留解决率在 0.1 到 0.7 之间的任务。其余的差别在两处：用谁来判断难度，以及多久重新判断一次。判断难度的模型越接近正在训练的模型，重新判断得越频繁，筛出来的任务就越符合模型当前的水平，花的算力也越多。

选哪一种，可以按前面几节的内容这样判断。一次运行很便宜时，可以像 DAPO 那样边训练边筛。一次运行很贵时，像 LEGO-RL 那样在训练之前筛好，代价是任务池会随着训练过时。现成的训练任务不够时，像 WebRL 那样每一轮出新题。

i
全错的任务要不要留，各家不一样。DAPO、CodeMidas 和 LEGO-RL 把它们丢掉。WebRL 靠成败预测模型的估计来筛，丢掉的是估计几乎做不成的任务，也就是分数低于 0.05 的。CWM 开始时留着：把本来不给模型看的测试加进任务说明里当提示，这些任务的单次成功率从 0 升到约 30%，抽到的机会也比别的任务少。到强化学习的第二阶段去掉提示，论文的说法是让模型学会不靠提示从头解决它们。这个阶段 CWM 也只留解决率在 0.1 到 0.7 之间的任务。丢掉的理由，除了没有信号，还有一条来自 The Verification Horizon 这篇论文的第 2.2 节，第四部分会讲这篇论文的其他内容。这条理由是：一直没有被做对过的任务里，质量有问题的任务占的比例要高得多，所以不能只把它们当成难题。CodeMidas 说的也是这件事：全对或全错可能是难度的原因，也可能是任务有缺陷，光看结果分不出来。

这一部分的小结

  • 在按组比较的强化学习里，一组运行的奖励全都相同，这个任务就不产生更新。
  • 还没按难度筛过的任务池里，这样的任务可以占到 86%，这是 LEGO-RL 筛选时的统计。
  • 筛的办法是让模型试做几遍，留下有对有错的。可以在训练前筛一次，也可以边训练边筛。
  • 筛过的任务池也会过时：LEGO-RL 在 OpenHands SDK 下，不产生更新的任务从第 1 轮的 44.7% 升到第 3 轮的 51.4%。不过在 OpenCode 下这个比例基本不变，约 43.3%。
  • WebRL 的办法是每一轮都按模型当前的水平出新题。
