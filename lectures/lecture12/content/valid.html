先看结论

  • 一个任务有毛病，主要是两种情况：问题描述没有把要求说清楚；测试查的东西和问题描述对不上，会把正确的解法判成不通过。
  • 请人检查最可靠，也最贵。SWE-bench Verified 请了 93 个开发者标注 1,699 个任务，筛掉了 68.3%。
  • 要成批地造任务，检查就得自动化。APIGen 用三层检查：格式对不对，能不能执行，结果合不合提问的意图。三层按成本从低到高排，最贵的语言模型检查放在最后，只看前两层都通过的数据。
  • CodeMidas 把每个任务实际运行很多遍：起始代码必须不通过，参考答案必须通过；再让 agent 去找泄露的答案，去核对验证器的判定。22,575 个候选任务最后留下 5,545 个。
  • 筛过的 5,545 个任务训练出的模型，在三个评测上都好于没筛过的约 8,000 个任务。

挑任务的四步

这一页说的任务，指交给 agent 去做的一件事，由三样组成：一段任务说明，一个沙盒，一个验证器。第一部分把这三样合起来叫环境，这一页和下一页按各篇论文的习惯叫它任务。

三个词各解释一句。agent 是能自己调用工具、分很多步去完成一个任务的语言模型系统。沙盒（sandbox）是一个隔离的运行环境，agent 在里面执行命令、改文件都不会影响到外面。验证器（verifier）是判断任务有没有做成的程序，在编程任务里通常是一组不给 agent 看的测试。

这样的任务主要用在强化学习里：模型自己反复去做任务，按验证器的判定得到奖励，再按奖励调整模型。

哪些任务值得拿来训练，可以分成四步来回答。第四步做完又回到前面，所以整个过程是一个循环。

一个有毛病的任务长什么样

SWE-bench 是 2023 年发布的一个基准测试（benchmark，一组题目加一个打分的办法）。它的每个任务来自一个真实的 GitHub issue，issue 指代码仓库里报告问题的帖子。做法是把 issue 的文字和修复之前的代码仓库交给 agent，agent 改代码，再用当初修复这个 issue 时加进去的测试来判定改得对不对。agent 看不到这些测试。

其中一个任务来自 scikit-learn 仓库，编号 14520。

{{fig 15 | 左：agent 能看到的全部信息，是一个用户提的问题。他发现 TfidfVectorizer 的一个方法有 copy 参数，但后面的代码没有用到它，问是不是自己漏看了什么。右：用来判定的测试。}}

右边那段测试是这样的：

def test_tfidf_vectorizer_deprecationwarning():
    msg = ("'copy' param is unused and has been deprecated since "
           "version 0.22. Backward compatibility for 'copy' will "
           "be removed in 0.24.")
    with pytest.warns(DeprecationWarning, match=msg):
        tv = TfidfVectorizer()
        train_data = JUNK_FOOD_DOCS
        tv.fit(train_data)
        tv.transform(train_data, copy=True)

这个测试要求两件事，问题描述里一件都没有提。

  • 要发出一个弃用警告（DeprecationWarning）。issue 只是问这个参数是不是没用，没有说该怎么处理它。删掉这个参数、让这个参数真正起作用，都是合理的改法，但都通不过测试。
  • 警告的文字要和测试里的那一句一字不差。这句话是当初修复的人在代码合并请求的讨论里商量出来的，agent 看不到那场讨论。代码合并请求（pull request，简称 PR）是请求把一组代码改动并入仓库的申请，改动并入之前，大家在它下面讨论。

所以一个真正理解了问题、也改对了代码的 agent，几乎不可能通过这个测试。

把这样的任务放在基准测试里，模型的分数会比它的实际能力低。把它放进训练，模型做对了也拿不到奖励。

请人来查：SWE-bench Verified

2024 年 8 月，OpenAI 和 SWE-bench 的作者一起做了 SWE-bench Verified，办法是请人把任务一个一个看过去。

怎么标的

他们找了 93 个有 Python 经验的软件开发者，从 SWE-bench 的测试集里随机抽出 1,699 个任务来标注（annotation，由人按一套固定的标准给数据打标签）。每个任务由 3 个人分别标。标注的人要回答两个主要的问题，各有 0 到 3 四档，数字越大问题越严重。

{{fig 16 | 给标注的人看的两套标准。左：问题描述够不够清楚。右：测试的判定标准合不合理。}}

两套标准的四档各是什么意思，标到哪一档就丢掉，列在下表里。

3 个人的标签不一样时，取最严重的那一个。也就是说，3 个人里只要有 1 个人认为有严重问题，这个任务就被丢掉。OpenAI 自己也说，这样做会多丢一些其实没问题的任务，换来的是对留下的任务更有把握。

最后的 SWE-bench Verified 是剩下的任务里的 500 个：先尽量放进估计要花 1 小时以上的较难任务，其余的随机抽。

筛完之后分数怎么变

OpenAI 用同一个模型（GPT-4o）配五个开源的运行框架，在原来的 SWE-bench 和 SWE-bench Verified 上各测了一遍。运行框架（harness，也叫 scaffold）指包在模型外面、给它工具并管理多轮对话的程序。五个里成绩最好的是 Agentless，下表是它的结果。

分数翻了一倍，有两种可能的原因。一种是筛掉的是有毛病的题，这种题模型做对了也通不过测试。另一种是筛掉的只是难题，剩下的题里容易的占比高了，分数跟着变高。

OpenAI 检查了是哪一种。他们按标注者估计的修复时间把任务分成几档，看每一档内部的解决率。如果筛选只是让容易的题占比变高，同一档内部的解决率不会变。实际的结果是每一档内部的平均解决率都上升了，这和「每一档里都去掉了做不出来的题」这个解释是一致的。

举两档的数，都是上面那五个运行框架的平均解决率。估计 15 分钟以内能修好的任务，从 33.2% 升到 45.1%。估计要 15 分钟到 1 小时的任务，从 12.9% 升到 20.8%。这里的 33.2% 和上面表里 GPT-4o 的 33.2% 是两个不同的数，只是碰巧相同。

人查过的也还有漏的

自动检查：APIGen 的三层

请 93 个人看 1,699 个任务，这个办法没法用到几万、几十万个任务上。成批造出来的数据，要靠自动的检查来筛。

APIGen（Liu 等，2024，Salesforce）造的是函数调用的训练数据。一条数据是一个用户的提问，加上回答这个提问需要调用哪些 API、参数各是什么。生成的办法是：从 3,673 个可以真实执行的 API 里抽几个，加上几条示例，让一个语言模型写出提问和对应的调用。

i
APIGen 检查的是一条一问一答的数据，比这一页说的任务小。论文自己写明了两条局限：只考虑了 REST API 和 Python 函数；只做了单轮的函数调用，也就是一问一答，没有多步的任务。所以它离 agent 那种要做很多步的任务还有距离。放在这里讲，是因为它分层检查的思路可以用到任务上，后面的 CodeMidas 就把同样的思路用到了完整的编程任务上。

写出来的每一条数据都要过三层检查。流程见下图。

{{fig 19 | 左：APIGen 的流程。上半部分是生成，下半部分的绿色框是三层检查，从右到左依次是格式检查、执行检查、语义检查。通过的数据会放回示例库。右上：一次函数调用的过程。右下：数据的格式。图片来源：Liu 等，2024。}}

三层检查各查什么、由谁来查，列在下表里。

三层是按成本从低到高排的。前两层是程序，又快又便宜，结果也确定。最贵、也最可能出错的语言模型放在最后，只看前两层都通过的数据。

这套办法能成立，靠的是函数调用这类数据的一个特点：答案可以直接执行，能不能跑通由程序一试就知道。只有跑通之后的结果合不合提问的意图，才需要交给语言模型判断。

每一层筛掉多少

论文用四个语言模型各生成 40,000 条数据，统计了每一层筛掉的条数。

从表里能看出两件事。第一，生成数据的模型越弱，筛掉的越多：最弱的一个只有三分之一左右通过，最强的一个有 84%。第二，较弱的两个模型，大部分数据是在执行检查这一层被筛掉的，也就是写出来的调用根本跑不通。

最后公开的数据集只用了最强的两个模型的结果，约 6 万条。

这些检查真的有用吗

论文用通过检查的数据训练出了两个模型，名字里分别带 7B 和 1B。B 指十亿个参数，按论文的说法，两个模型分别有 67 亿和 13 亿参数。成绩用 Berkeley 函数调用排行榜（BFCL）上的总准确率来量。在 2024 年 6 月 15 日的榜上，7B 的那个排第 6，总准确率是 85.65%，高于当时榜上 GPT-4o 的函数调用版本的 82.94%。1B 的那个排第 24。

这些检查本身起了多大作用，论文做了两种验证。

  • 请人抽查通过的数据。三个人检查了公开数据集里的 600 条，其中 28 条有小问题，比如参数值不准确，或者调用的次数比需要的多。也就是约 95.3% 没有问题。
  • 把筛掉的数据加回去训练。先把语义检查筛掉的数据加回训练集，再把执行检查筛掉的也加回去，两个模型在 BFCL 上的总准确率一步一步下降。从论文的图 5 读出的数是：7B 的模型加回第一批后，总准确率降了 4.06 个百分点，加回第二批后又降了 5.94 个百分点。1B 的模型先降了 9.59 个百分点，又降了 12.17 个百分点。小模型受坏数据的影响更大。

第三层的语言模型，谁来检查它

用语言模型当评审（LLM-as-judge）有一个避免不了的问题：评审自己也是语言模型，也会出错。Shankar 等人 2024 年的论文《Who Validates the Validators?》讨论的就是这件事。原话是：由语言模型生成的评审，继承了它要评的那些语言模型的全部问题，所以还得由人再验证一遍。

他们做的工具 EvalGen 用人的打分来决定留下哪一种自动检查的写法。语言模型先提出评分标准，再为每条标准生成几种候选的写法，一种写法是一段代码，或者一段写给评审模型的 prompt。同时请人给一部分输出打「好」或「坏」。最后每条标准留下判定结果和人的打分最一致的那一种写法。

他们在 9 个从业者身上观察到一个现象，叫标准漂移（criteria drift）：人需要先有标准才能给输出打分，可是给输出打分的过程又会让人修改标准。论文的结论是，在人看过实际输出之前，不可能把评分标准完全定下来。

这一讲里有两处做的就是这种「用人的判断来校准自动检查」的事：APIGen 请三个人抽查 600 条数据，下一部分的 WebRL 拿 100 条人工标注的运行来核对它的评审模型。出处：Shankar 等，2024。

把任务实际跑几遍：CodeMidas

CodeMidas（Ye 等，2026，小米等）造的是用来做强化学习的编程任务。它的特别之处是只需要源代码：不需要 issue，不需要代码合并请求，不需要提交历史，也不需要仓库里已有的测试。

任务是怎么造出来的

一个 agent 在现有的代码库里选一块有公开入口的功能，把它的核心实现删掉，再调整剩下的代码，让它成为这个任务的起始代码。公开入口指别的代码可以直接调用的函数或接口。被删掉的那段原始实现留作参考答案。

测试的期望值也来自原始实现：agent 用选好的输入去调用原来的代码，把输出记下来，测试就查新写的实现能不能给出同样的输出。

每个任务也是这一页开头说的三样：一段任务说明，一个装在容器里的开发环境，一个藏起来的验证器。容器是沙盒的一种做法，是一个隔离的、可以整个重建的运行环境。验证器平时不在 agent 能看到的容器里，评分的时候才放进去，给出通过或不通过。

任务设计这一步造出候选任务，候选任务再过五步筛选。下图中间是任务设计和每一步筛选之后留下的任务数。

{{fig 20 | 中间的漏斗是每一步之后留下的任务数。左边三个框是任务设计和头两步筛选，头两步筛选是构造测试和执行一致性检查。右边是后三步筛选，都在运行之后做。图片来源：Ye 等，2026。}}

每一步之后留下多少任务、筛掉多大的比例、查的是什么，列在下表里。第一行是任务设计，后面五行是五步筛选。

最后留下的 5,545 个任务占候选任务的 24.6%，来自 3,185 个代码库，覆盖 23 种编程语言。

测试只查任务说明里写明的东西

这条规则针对的正是前面 scikit-learn 那个任务的毛病。论文的说法分两种情况。任务说明里明确规定了的输出和性质，测试拿参考实现的运行结果当期望值。任务说明只规定了一部分的地方，测试只查规定了的那部分，其余的细节不查。论文举的例子是，测试可以要求抛出某种类型的异常，但不能把说明里没有规定的报错文字也写死。

按这条规则写的测试大致是下面这样。这段代码是为了说明规则而写的示意，不出自论文。

# Task: raise ValueError on bad input.
# The message wording is not specified.
with pytest.raises(ValueError):
    parse_config(bad_input)

它只要求抛出 ValueError，不管报错的文字怎么写。对照 scikit-learn 那个测试里的 match=msg，那一个把文字也写死了。

测试写好之后，还有一个 agent 把每一条断言再审一遍，找出任务说明里没有依据的限制，比如固定的措辞、碰巧的顺序、内部的数据结构，把它们换成只查行为的检查。

六个全新的容器

执行一致性检查把每个任务在六个全新的容器里各跑一遍。

{{fig 22 | 每个任务跑六遍。左边两遍用起始代码，必须不通过。右边四遍用参考答案，必须通过。}}

这一步查两件事。第一，任务确实需要做：没改过的起始代码通不过测试。第二，任务确实能做成：放上参考答案就能通过。同样的检查重复两遍和四遍，是为了筛掉结果不稳定的任务，比如测试有时过、有时不过。六遍里有任何一遍和预期不符，这个任务就不要。

论文在这一步还做了环境清理：把容器里可能透露被删掉的那段实现的东西去掉，包括编译出来的文件、缓存的副本和造任务的 agent 留下的文件。项目里原有的、和这块功能有关的测试也一起去掉。

运行之后的三种筛选

读这两张表时要注意的三点。
  • SWE-bench Pro 一列的差距很小。三批筛过的任务和没筛过的相差都不到 1 个百分点。论文没有给这张图报告误差范围，也没有报告重复训练的结果，所以这一列的差距是否可靠还不能确定。
  • 看不出是哪一步筛选起的作用。没筛过的那一批同时少了环境清理、六个容器的检查和三种运行后的筛选，所以这个对比说明的是整套筛选合起来的效果。
  • 各批取的训练步数不一样。论文正文给出的 CodeMidas Val 分数，1 千个的是第 30 步，3 千个的是第 65 步，全部的是第 70 步。按什么规则选的步数，论文里没有写明。

和训练之前比，用全部 5,545 个任务训练之后，MiMo-V2.5 的通过率在 SWE-bench Pro 上从 50.3 升到 54.4，在 DeepSWE 上从 10.0 升到 21.7，单位都是百分比。

这一部分的小结

三种检查任务的办法放在一起，见下表。

  • SWE-bench Verified 和 CodeMidas 筛掉了约七成到四分之三。APIGen 筛掉 16% 到 66%，生成数据的模型越弱，筛掉得越多。
  • 筛掉的比例会高于真正有毛病的比例：SWE-bench Verified 的规则会多丢一些其实没问题的任务，CodeMidas 的最后一步把没有毛病、只是难度不合适的任务也一起去掉了。
  • 检查的顺序是先便宜后贵：先查格式，再实际运行，最后才用语言模型或 agent 去判断。
  • CodeMidas 的最后一步已经在看模型做得怎么样了。一个任务就算完全没有毛病，模型每次都做对或者每次都做错，也学不到东西。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • GPT-4o 在原来的 SWE-bench 上的 16%。这个数是在 SWE-bench 的完整测试集上测的，还是在某个子集上测的，原文没有写明。出处：OpenAI，Introducing SWE-bench Verified。
  • APIGen 每一层筛掉的条数。Mixtral-8x7B 那一行的四个数加起来是 39,000，比 40,000 少 1,000，论文没有解释。出处：Liu 等，2024的表 1。
  • APIGen 把筛掉的数据加回去之后下降的幅度。4.06、5.94、9.59 和 12.17 这四个数是从论文的图 5 上读出来的，论文正文没有给。按图里柱子的排列，每个数是相对于它左边那根柱子的下降，所以正文把第二个数写成在第一次下降之后又降的幅度。出处：Liu 等，2024的图 5。
  • CodeMidas 每一步之后留下的任务数。六个数只出现在论文的图 1 里。哪个数对应哪一步，是按图里的连线读出来的，论文正文没有逐步列出。出处：Ye 等，2026的图 1。
  • CodeMidas 按运行结果筛选的细节。这一步里每个任务做几次、用的是哪个模型，论文里没有写明，只说是一个前沿模型做若干次。出处：Ye 等，2026第 3.4 节。
