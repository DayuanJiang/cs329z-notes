先看结论

  • 任务的缺陷有好几种。这一页先讲两种：问题描述没有把要求说清楚；测试查的东西和问题描述对不上，会把正确的解法判成不通过。后面还会查到另外几种，比如任务的运行结果不稳定，答案留在了运行环境里，验证器（判断任务有没有做成的程序）把错的解法判成通过。
  • 请人检查最贵，查过的也还有漏的。SWE-bench Verified 这套测试题考的是修复真实代码仓库里报告的问题。做它的时候请了 93 个开发者来标注，给 1,699 个任务逐个打标签，筛掉了 68.3%。最后定下来的 500 道题后来仍被查出不少有缺陷的题。
  • 要成批地造任务，检查就得自动化。APIGen 造的是函数调用的训练数据，每条是一个用户的提问，加上回答这个提问需要调用哪些 API、参数各是什么。它用三层检查：格式对不对，能不能执行，结果合不合提问的意图。三层按成本从低到高排，最贵的语言模型检查放在最后，只看前两层都通过的数据。
  • CodeMidas 自动造编程任务，并把每个任务实际运行很多遍：起始代码必须不通过，参考答案必须通过；再让 agent 去找泄露的答案，去核对验证器的判定。agent 指能自己调用工具、分很多步去完成一个任务的语言模型系统。22,575 个候选任务最后留下 5,545 个。
  • 用筛过的 5,545 个任务训练出的模型，在三个评测上的通过率都高于用没筛过的约 8,000 个任务训练出的模型。其中两个评测上高 4 个百分点以上，SWE-bench Pro 上只高 0.59 个百分点，这个差距是否可靠还不能确定。

挑任务的四步

这一页说的任务，指交给 agent 去做的一件事，由三样组成：一段任务说明，一个沙盒，一个验证器。第一部分把这三样合起来叫环境，这一页和下一页按各篇论文的习惯叫它任务。

三个词各解释一句。agent 是能自己调用工具、分很多步去完成一个任务的语言模型系统。沙盒（sandbox）是一个隔离的运行环境，agent 在里面执行命令、改文件都不会影响到外面。验证器（verifier）是判断任务有没有做成的程序，在编程任务里通常是一组不给 agent 看的测试。

这样的任务主要用在强化学习里：模型自己反复去做任务，按验证器的判定得到奖励，再按奖励调整模型。

哪些任务值得拿来训练，可以分成四步来回答。这四步都是挑任务。第一部分那张漏斗图里也有四步筛选，那四步从候选任务一直排到最终的训练数据，其中挑任务的只有头两步，这里的四步是把那两步再细分。第四步是在模型变强之后，按现在的模型把第三步重新做一遍，或者补进新的任务，所以整个过程是一个循环。

这一页讲前两步，它们回答同一个问题：这个任务本身是对的吗。这两步合起来，就是漏斗图里从「候选任务」到「有效的任务」的那一步。后两步都属于漏斗图里从「有效的任务」到「学得到东西的任务」的那一步。

下面先看一个有缺陷的任务，再用三个例子讲三种检查的办法：请人标注，用程序和语言模型分层检查，把任务实际运行几遍。

一个有缺陷的任务长什么样

SWE-bench 是 2023 年发布的一个基准测试（benchmark，一组题目加一个打分的办法）。它的每个任务来自一个真实的 GitHub issue，issue 指代码仓库里报告问题的帖子。做法是把 issue 的文字和修复之前的代码仓库交给 agent，agent 改代码，再用当初修复这个 issue 时加进去的测试来判定改得对不对。agent 看不到这些测试。

其中一个任务来自 scikit-learn（一个常用的 Python 机器学习库）的仓库，编号 14520。

{{fig 15 | 左：agent 能看到的全部信息，是一个用户提的问题。他发现 TfidfVectorizer 这个类的一个方法有 copy 参数，但后面的代码没有用到它，问是不是自己漏看了什么。右：用来判定的测试。}}

右边那段测试是这样的：

def test_tfidf_vectorizer_deprecationwarning():
    msg = ("'copy' param is unused and has been deprecated since "
           "version 0.22. Backward compatibility for 'copy' will "
           "be removed in 0.24.")
    with pytest.warns(DeprecationWarning, match=msg):
        tv = TfidfVectorizer()
        train_data = JUNK_FOOD_DOCS
        tv.fit(train_data)
        tv.transform(train_data, copy=True)

这个测试要求两件事，问题描述里一件都没有提。

  • 要发出一个弃用警告（DeprecationWarning）。弃用警告是程序给使用者的提示，说某个功能以后会被去掉。issue 只是问这个参数是不是没用，没有说该怎么处理它。删掉这个参数、让这个参数真正起作用，都是合理的改法，但都通不过测试。
  • 警告的文字要和测试里的那一句一字不差。这句话是当初修复的人在代码合并请求的讨论里商量出来的，agent 看不到那场讨论。代码合并请求（pull request，简称 PR）是请求把一组代码改动并入仓库的申请，改动并入之前，大家在它下面讨论。

所以一个真正理解了问题、也改对了代码的 agent，几乎不可能通过这个测试。

把这样的任务放在基准测试里，模型的分数会比它的实际能力低。把它放进训练，模型做对了也拿不到奖励。

请人来查：SWE-bench Verified

2024 年 8 月，OpenAI 和 SWE-bench 的作者一起做了 SWE-bench Verified，办法是请人把任务一个一个看过去。

怎么标的

他们找了 93 个有 Python 经验的软件开发者，从 SWE-bench 用来评测的那批任务里随机抽出 1,699 个任务来标注（annotation，由人按一套固定的标准给数据打标签）。每个任务由 3 个人分别标。标注的人要回答两个主要的问题，各有 0 到 3 四档，数字越大问题越严重。

{{fig 16 | 给标注的人看的两套标准。左：问题描述够不够清楚。右：测试的判定标准合不合理。}}

两套标准的四档各是什么意思，标到哪一档就丢掉，列在下表里。表里 3 档说的测试太窄，指测试只接受某一种特定的实现。测试太宽，指测试查了问题描述里没有要求的功能。

3 个人的标签不一样时，取最严重的那一个。也就是说，3 个人里只要有 1 个人认为有严重问题，这个任务就被丢掉。OpenAI 自己也说，这样做会多丢一些其实没问题的任务，换来的是对留下的任务更有把握。

筛完之后分数怎么变

OpenAI 用同一个模型（GPT-4o）配五个开源的运行框架，在原来的 SWE-bench 和 SWE-bench Verified 上各测了一遍。运行框架（harness，也叫 scaffold）指包在模型外面、给它工具并管理多轮对话的程序。五个里成绩最好的是 Agentless，下表是它的结果。

分数翻了一倍，有两种可能的原因。一种是筛掉的是有缺陷的题，这种题模型做对了也通不过测试。另一种是筛掉的只是难题，剩下的题里容易的占比高了，分数跟着变高。

OpenAI 检查了是哪一种。他们按标注者估计的修复时间把任务分成几组，看每一组内部的解决率。如果筛选只是让容易的题占比变高，同一组内部的解决率不会变。实际的结果是每一组内部的平均解决率都上升了。这和第一种解释一致：每一组里都去掉了一些有缺陷、做对了也通不过测试的题。

举两组的数，都是上面那五个运行框架的平均解决率。估计 15 分钟以内能修好的任务，从筛选之前的 33.2% 升到筛选之后的 45.1%。估计要 15 分钟到 1 小时的任务，从 12.9% 升到 20.8%。

这里的 33.2% 和上面表里的 33.2% 只是碰巧相同，量的东西不同。这里的 33.2% 是五个运行框架在筛选之前、估计 15 分钟以内能修好的那一组任务上的平均解决率。表里的 33.2% 是 Agentless 一个运行框架在整个 SWE-bench Verified 上的解决率。

自动检查：APIGen 的三层

请 93 个人看 1,699 个任务，这个办法没法用到几万、几十万个任务上。成批造出来的数据，要靠自动的检查来筛。

APIGen（Liu 等，2024，Salesforce）造的是函数调用的训练数据。一条数据是一个用户的提问，加上回答这个提问需要调用哪些 API、参数各是什么。生成的办法是：从 3,673 个可以真实执行的 API 里抽几个，加上几条示例，让一个语言模型写出提问和对应的调用。

i
APIGen 检查的是一条一问一答的数据，比这一页说的任务小。论文自己写明了两条局限：只考虑了 REST API（通过网络请求来调用的接口）和 Python 函数；只做了单轮的函数调用，也就是一问一答，没有多步的任务。所以它离 agent 那种要做很多步的任务还有距离。放在这里讲，是因为它一层一层检查的做法可以用到任务上，后面的 CodeMidas 也是把完整的编程任务分五步来检查。

写出来的每一条数据都要过三层检查。流程见下图。

三层是按成本从低到高排的。前两层是程序，又快又便宜，结果也确定。最贵、也最可能出错的语言模型放在最后，只看前两层都通过的数据。

这套办法能成立，靠的是函数调用这类数据的一个特点：答案可以直接执行，能不能执行成功，程序一试就知道。只有执行成功之后的结果合不合提问的意图，才需要交给语言模型判断。

每一层筛掉多少

论文用四个语言模型各生成 40,000 条数据，统计了每一层筛掉的条数。

从表里能看出两件事。第一，生成数据的模型越弱，筛掉的越多：最弱的一个只有三分之一左右通过，最强的一个有 84%。第二，较弱的两个模型，筛掉的数据里有一半以上是在执行检查这一层筛掉的，也就是写出来的调用根本执行不了。

最后公开的数据集只用了最强的两个模型的结果，约 6 万条。

这些检查真的有用吗

论文用通过检查的数据训练出了两个模型，叫 xLAM-7B 和 xLAM-1B。B 指十亿个参数，按论文的说法，两个模型分别有 67 亿和 13 亿参数。成绩用 Berkeley 函数调用排行榜（BFCL）上的总准确率来量。

论文列出了 2024 年 6 月 15 日的榜，一共排到第 46 名。xLAM-7B 排第 6，总准确率是 85.65%。xLAM-1B 排第 24，总准确率是 74.41%。

GPT-4o 在这张榜上有两行。一行标着 FC，指函数调用模式，模型直接输出 JSON 格式的函数调用。另一行标着 Prompt，指用一段专门写的 prompt 让模型给出函数调用。xLAM 的两个模型用的都是函数调用模式。GPT-4o 函数调用模式的那一行排第 11，总准确率是 82.94%，低于 xLAM-7B。

这些检查本身起了多大作用，论文做了两种验证。

  • 请人抽查通过的数据。三个人检查了公开数据集里的 600 条，其中 28 条有小问题，比如参数值不准确，或者调用的次数比需要的多。也就是约 95.3% 没有问题。
  • 把筛掉的数据加回去训练。先把语义检查筛掉的数据加回训练集，再把执行检查筛掉的也加回去，两个模型在 BFCL 上的总准确率一步一步下降。xLAM-7B 加回第一批后降了 4.06 个百分点，加回第二批后又降了 5.94 个百分点。xLAM-1B 先降了 9.59 个百分点，又降了 12.17 个百分点。小模型受坏数据的影响更大。论文的图上只标了这四个降幅，没有标出下降之前和之后的总准确率。

第三层的语言模型，谁来检查它

用语言模型当评审（LLM-as-judge）有一个避免不了的问题：评审自己也是语言模型，也会出错。Shankar 等人 2024 年的论文《Who Validates the Validators?》讨论的就是这件事。论文的说法是：语言模型写出来的自动检查，不管是一段检查代码还是一段写给评审模型的 prompt，被检查的语言模型有的问题它也都有，所以还得由人再验证一遍。

他们做的工具 EvalGen 用人的打分来挑自动检查。被检查的是一个语言模型按某个 prompt 产生的一批输出。EvalGen 先让语言模型提出几条评分标准，再把每条标准写成几种候选的自动检查，每一种就是上面说的一段检查代码或一段 prompt。

同时，EvalGen 请人给这批输出里的一部分打「好」或「坏」。最后每条标准只留下一种自动检查，留的是判定结果和人的打分最一致的那一种。

他们请 9 个在工作中用过语言模型的从业者试用 EvalGen，观察到一个现象，叫标准漂移（criteria drift）：人需要先有标准才能给输出打分，可是给输出打分的过程又会让人修改标准。论文的结论是，在人看过实际输出之前，不可能把评分标准完全定下来。出处：Shankar 等，2024。

这一讲里另有两处也请人来检验自动检查的结果，人的判断在那里只用来量自动检查有多准。APIGen 请三个人抽查了 600 条通过检查的数据。下一部分的 WebRL 是一种训练模型操作网页的强化学习方法，它用一个评审模型来判断模型每一次做任务有没有做成，并请人给模型 100 次做任务的结果标出成败，拿来核对这个评审模型判得准不准。

把任务实际运行几遍：CodeMidas

CodeMidas（Ye 等，2026，小米等）造的是用来做强化学习的编程任务。它的特别之处是只需要源代码：不需要 issue，不需要代码合并请求，不需要提交历史（代码仓库里每一次改动的记录），也不需要仓库里已有的测试。论文把一个项目的源代码叫代码库（codebase），也就是代码仓库里的那份源代码，这一节照论文的叫法。

任务是怎么造出来的

一个 agent 在现有的代码库里选一块有公开入口的功能，把它的核心实现删掉，再调整剩下的代码，让它成为这个任务的起始代码。公开入口指别的代码可以直接调用的函数或接口。被删掉的那段原始实现留作参考答案。

测试的期望值也来自参考答案：agent 用选好的输入去调用还没有删掉这段实现的代码库，把输出记下来，测试就查新写的实现能不能给出同样的输出。

每个任务也是这一页开头说的三样：一段任务说明，一个装在容器里的开发环境，一个藏起来的验证器。容器是沙盒的一种做法，是一个隔离的、可以整个重建的运行环境。验证器平时不在 agent 能看到的容器里，评分的时候才放进去，给出通过或不通过。

任务设计这一步造出候选任务，候选任务再过五步筛选。下图中间是任务设计和每一步筛选之后留下的任务数。

{{fig 20 | 中间的漏斗是每一步之后留下的任务数。左边三个框是任务设计和头两步筛选，头两步筛选是构造测试和执行一致性检查。右边是后三步筛选，这三步都要先让 agent 进到任务的环境里去试，再看试的结果。图片来源：Ye 等，2026。}}

测试只查任务说明里写明的东西

这条规则针对的正是前面 scikit-learn 那个任务的缺陷。论文的说法分两种情况。任务说明里明确规定了的输出和性质，测试拿参考答案的运行结果当期望值。任务说明只规定了一部分的地方，测试只查规定了的那部分，其余的细节不查。论文举的例子是，测试可以要求抛出某种类型的异常，但说明里没有规定报错文字时，测试不能要求报错文字和某一句话一字不差。

按这条规则写的测试大致是下面这样。这段代码是为了说明规则而写的示意，不出自论文。

# Task: raise ValueError on bad input.
# The message wording is not specified.
with pytest.raises(ValueError):
    parse_config(bad_input)

它只要求抛出 ValueError，不管报错的文字怎么写。对照 scikit-learn 那个测试里的 match=msg，那一个连警告的文字也规定了，要求一字不差。

测试写好之后，还有一个 agent 把每一条断言再审一遍。断言是测试里检查某个结果是否符合预期的一句代码。这个 agent 找出任务说明里没有依据的限制，比如固定的措辞、碰巧的顺序、内部的数据结构，把它们换成只查行为的检查。

这一步也会去掉任务。论文写明的一种情况是：某条断言依赖一个不对外公开的内部名字，比如内部的函数或变量，又找不到只查行为的检查来代替它，这个任务就被去掉。表里这一步筛掉的 29.0% 里还有没有别的原因，论文没有写明。

六个全新的容器

执行一致性检查把每个任务在六个全新的容器里各运行一遍。

{{fig 22 | 每个任务运行六遍。左边两遍用起始代码，必须不通过。右边四遍用参考答案，必须通过。}}

这一步查两件事。第一，任务确实需要做：没改过的起始代码通不过测试。第二，任务确实能做成：放上参考答案就能通过。同样的检查重复两遍和四遍，是为了筛掉结果不稳定的任务，比如测试有时过、有时不过。六遍里有任何一遍和预期不符，这个任务就被去掉。

论文在这一步还做了环境清理：把容器里可能透露被删掉的那段实现的东西去掉，包括编译出来的文件、缓存的副本和造任务的 agent 留下的文件。项目里原有的、和这块功能有关的测试也一起去掉。

后三步筛选：先让 agent 去试，再看结果

头两步筛选里没有 agent 去做任务：测试是对照任务说明写出来再审的，六个容器里运行的是起始代码和参考答案。后三步都要先让 agent 进到任务的环境里去试，再看试的结果。泄露检查里 agent 的目标是找现成的答案，判定复核和按尝试结果筛选里 agent 是真的去做任务。

{{fig 23 | 图上最左边的 Candidate task 在这里指通过了头两步筛选的任务。它们从左到右经过后三步筛选，每一步下面写着什么情况下丢掉。}}

按尝试结果筛选这一步丢掉的任务，原因可能有两种。每次都通过或每次都不通过，可能是因为任务太容易或太难，也可能是因为任务还有没查出来的缺陷，比如测试太弱，或者任务说明漏了要求。论文说，只看结果分不出是哪一种原因，所以每次都通过和每次都不通过的任务都去掉，只留下有成有败的任务。这一步同时也是下一部分要讲的难度筛选。

筛过的和没筛过的，训练出来差多少

论文用强化学习训练小米的 MiMo-V2.5 模型，奖励只有通过和不通过两种。训练用的任务换了四批，其余设置不变。

四批里有三批取自筛过的 5,545 个任务。第四批是约 8,000 个没筛过的任务。

按论文的说法，这约 8,000 个任务是在筛选之前取的，每个任务都已经有任务说明、开发环境和验证器，也就是测试已经写好了。论文写明它们没有做环境清理和六个容器的检查，也没有做后三步筛选。第一步构造测试时也会去掉一部分任务，它们是不是都通过了第一步，论文没有写明。这一页说它们没筛过，指的是没有做上面写明的这几项检查。

读这两张表时要注意的三点。
  • SWE-bench Pro 一列的差距很小。三批筛过的任务和没筛过的相差都不到 1 个百分点。论文没有给这张图报告误差范围，也没有报告重复训练的结果，所以这一列的差距是否可靠还不能确定。
  • 看不出是哪一步筛选起的作用。没筛过的那一批同时少了环境清理、六个容器的检查和后三步筛选，所以这个对比说明的是这几项合起来的效果。
  • 各批取的训练步数不一样。论文正文给出的 CodeMidas Val 通过率，1 千个的是第 30 步，3 千个的是第 65 步，全部的是第 70 步。按什么规则选的步数，论文里没有写明。

这一部分的小结

三种检查任务的办法放在一起，见下表。

  • SWE-bench Verified 和 CodeMidas 筛掉了约七成到四分之三。APIGen 筛掉 16% 到 66%，生成数据的模型越弱，筛掉得越多。
  • 筛掉的比例不等于真正有缺陷的比例。筛选会多丢：SWE-bench Verified 的规则会多丢一些其实没问题的任务，CodeMidas 的最后一步把没有缺陷、只是难度不合适的任务也一起去掉了。筛选也会漏掉：SWE-bench Verified 最后定下来的 500 道题后来仍被查出不少有缺陷的题。
  • APIGen 的三层检查是先便宜后贵：先查格式，再实际执行，最后才用语言模型去判断，语言模型只看前两层都通过的数据。
  • CodeMidas 的最后一步已经在看模型做得怎么样了。一个任务就算完全没有缺陷，模型每次都做对或者每次都做错，也学不到东西。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • GPT-4o 在原来的 SWE-bench 上的 16%。这个数是在 SWE-bench 用来评测的全部任务上测的，还是在其中一部分上测的，原文没有写明。出处：OpenAI，Introducing SWE-bench Verified。
  • 「测试太窄」和「测试太宽」的解释。2024 年的标注标准里只有 3 档的那一句，没有展开这两个词。这一页的解释用的是 OpenAI 2026 年那篇文章的定义，那里把强制要求某种特定实现的测试叫 narrow test cases，把查了问题描述里没有要求的功能的测试叫 wide test cases。出处：OpenAI，2026 年 2 月。
  • o3 不能稳定做对的 138 道题。文章的原话是 did not consistently solve over 64 independent runs，没有写明 64 遍里做对多少遍以下算不能稳定做对。出处同上一条。
  • APIGen 每一层筛掉的条数。Mixtral-8x7B 那一行的四个数加起来是 39,000，比 40,000 少 1,000，论文没有解释。出处：Liu 等，2024的表 1。
  • APIGen 把筛掉的数据加回去之后下降的幅度。4.06、5.94、9.59 和 12.17 这四个数是从论文的图 5 上读出来的，论文正文没有给。按图里柱子的排列，每个数是相对于它左边那根柱子的下降，所以这一页把第二个数写成在第一次下降之后又降的幅度。图上没有标出下降之前和之后的总准确率。出处：Liu 等，2024的图 5。
  • CodeMidas 每一步之后留下的任务数。六个数只出现在论文的图 1 里。哪个数对应哪一步，是按图里的连线读出来的，论文正文没有逐步列出。出处：Ye 等，2026的图 1。
  • CodeMidas 按尝试结果筛选的细节。这一步里每个任务做几次、用的是哪个模型，论文里没有写明，只说是一个前沿模型做若干次。出处：Ye 等，2026的第 3.4 节。
