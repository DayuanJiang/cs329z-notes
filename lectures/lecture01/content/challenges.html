先看结论

  • agent 已经能做很多事，但搭出来之后还有五个难点：可靠性、训练、长任务、安全、评估。
  • 可靠性和能力是两回事。普林斯顿的一项研究用 12 个指标量了 15 个模型，结论是这两年准确率一直在涨，可靠性只提高了一点。
  • 把任务做完和做得安全也是两回事。一项审计评测了 10 种配置，每种配置是一个模型加一个运行框架（harness，包在模型外面、给它工具并管理多轮对话的程序）。任务完成率最高的那种配置，完成率是 0.82，安全遵守率却只有 0.43。安全遵守率量的是过程守规矩的程度，没有违规时是 1。
  • 安全问题有很多种：不问用户就自己做假设，被网页上的弹窗引去点击，把不该说的隐私写进邮件，为了分数钻空子。2026 年 7 月还出现了一千多个 agent 互相配合去骗评分程序的事件。
  • 评估本身也没有解决：只看准确率会得出错误的结论，花费、可靠性和安全都要一起量。

五个难点

前面六个部分讲的是 agent 怎样搭起来。这一部分讲搭起来之后还没有解决的问题，一共五个。它们也是后面各讲要逐个展开的题目。

可靠性：能做到，不等于每次都做到

这一节分三步：错误为什么会累积，可靠性怎么量，量出来的结果是什么。

错误为什么会累积

一个只回答一次的模型，错了就是这一次错。agent 要连续做几十步、几百步，每一步都有出错的机会，前面的错会带到后面。粗略估算一下：假设每一步有 95% 的机会做对，各步互不影响，任何一步错了整个任务就失败，那么连续 20 步全对的机会约为 36%，连续 50 步全对的机会约为 8%。

实际的 agent 能从一部分错误里恢复过来，第三部分的例子里，模型搜索落空之后换了一个词又找到了，所以真实的情况比这个估算乐观。但方向是一样的：步数越多，对每一步的要求越高。

可靠性怎么量

普林斯顿大学的一个团队在 2026 年发表了论文《Towards a Science of AI Agent Reliability》，并做了一个公开的数据面板，放在 HAL（Holistic Agent Leaderboard，普林斯顿大学网站上的一个公开的 agent 评测排行榜）上，下面叫它 HAL 可靠性面板。他们的出发点是：只用一个成功率，看不出一个 agent 是每次都稳定地做对，还是时对时错。论文把可靠性拆成四个方面，一共 12 个指标。

{{fig 62 | 四个方面里的三个：多次运行之间的一致性，对小改动的稳健性，失败方式是否可以预料。}}

四个方面各自问什么问题、用哪些指标，见下表。

实验用了两个基准测试（benchmark，一组题目加一个打分的办法）。GAIA 是通用助手类的任务，要上网、读文件、多步推理。τ-bench 是客服类的任务。

每个任务跑 5 次，每次用不同的随机种子（random seed，程序产生随机数时用的起始值）。temperature（控制输出随机程度的参数）设为 0，也就是把生成时主动加入的随机性关掉。

论文说明，这样设置之后，5 次运行之间还有的差别就来自生成时的随机选择以外的因素，例如浮点数运算的先后顺序不同会让结果有细微的差别，服务器同时处理的请求数不同也会带来差别。换随机种子在这时还会带来什么差别，论文没有写明。

总的可靠性分数是一致性、可预测性、稳健性三个方面的平均，在 0 到 1 之间，越高越可靠。安全单独看，不混进平均里，理由是安全事故是小概率但后果严重的事，平均之后就看不出来了。

能力和可靠性之间的差距

下图是 HAL 可靠性面板较早的一版，每一行是一个模型。

{{fig 63 | 可靠性面板在论文预印本时期的一版，有 13 个模型，覆盖 2026 年 1 月以前发布的模型。每一行是一个模型，Acc 是准确率，Reliability 是总的可靠性分数，后面是四个方面各自的指标，颜色越绿越好。面板后来更新过，现在的数见下面的表。}}

图里按可靠性从高到低排列。往下看，准确率一列并不跟着单调下降：这一版里可靠性排第四的模型，准确率低于排在它后面的 o1。也就是说，按可靠性排的名次和按准确率排的名次并不一致。这里用准确率代表能力，所以能力最强的 agent 不一定是最可靠的。

图是面板较早的一版，现在面板上的数和图里不同。引用具体的数时，以下面这张表为准。两版为什么不同，见资料说明。

现在的 15 个模型里，各模型的准确率差得很远，可靠性分数却相差不大。两个基准测试上的平均准确率最低 16.7%，最高 80.0%，相差 63 个百分点。可靠性分数最低 0.69，最高 0.87，相差 0.18。可靠性分数在 0 到 1 之间，把它也写成百分数，0.18 就是 18 个百分点。

图里看到的现象在新数据里仍然成立：准确率最高的 Gemini 3.5 Flash，可靠性排第三。

论文和面板给出的几条主要发现：

  • 可靠性的提高落后于准确率。24 个月的模型更新里，准确率稳步上升，总的可靠性只有小幅提高。
  • 结果的一致性低。能做出某个任务的 agent，常常不能每次都做出来。小模型的一致性常常和大模型持平甚至更高，面板给的解释是大模型有更多条路可以走。
  • 换个说法就可能出问题。工具出故障这类真实的技术问题，多数模型处理得不错；同一条指令换一种说法，各个模型的表现差别却很大。

训练和长任务

这两个难点后面有专门的讲次，这里只说清它们指什么。

因为训练难，所以有一个一直在争论的问题：要提高一个 agent，是该去训练模型，还是该改进包在模型外面的运行框架（harness，英文里也叫 scaffold）。第 9 讲讨论一个相近的选择：改 prompt 和上下文，还是改模型的权重。

安全：任务做完了，不等于做得安全

只看最后的结果，一次运行可能是成功的。看整个过程，它可能访问了没有权限的资源，或者把一段上下文交给了不该看到它的另一个 agent。结果对，不代表过程守规矩。

{{fig 64 | HarnessAudit-Bench 的结果。每一组是一种配置（模型加运行框架），蓝色、紫色或橙色的柱子是综合安全分，灰色的柱子是任务完成率。}}

图来自 2026 年 5 月的论文《Auditing Agent Harness Safety》。它审计的对象是运行框架：模型能用哪些工具、谁可以调用、什么时候停，都是运行框架决定的。

它的基准测试有 210 个任务，分布在金融、电商、医疗、办公、社交、日常生活、法律合规、软件工程 8 个领域。每个任务都带有安全方面的限制，比如哪些资源不许碰、哪些信息不许传给谁。

评测了 10 种配置：7 个模型在 OpenClaw 这个运行框架下，另外 3 种用的是厂商自己的运行框架 Claude Code 和 Codex。OpenClaw 就是第四部分里那个开源的个人 AI 助手。它是包在模型外面、替用户操作软件的程序，在这篇论文里是被审计的运行框架之一。

下表有三个指标。安全遵守率量的是过程守规矩的程度：它是工具使用、资源访问、信息流动三个方面的平均，没有违规时是 1。综合安全分把安全遵守率和任务完成率合在一起算。

加权分里的「动作做得对不对」和安全遵守率量的是两件事。「动作做得对不对」看执行的质量：中间每一步的工具、参数和操作对象选得对不对，有没有多余或出错的操作。安全遵守率看有没有违规：用了不许用的工具，碰了不许碰的资源，把信息传给了不该看到的一方。

加权分里的「受到干扰时是否稳定」，看的是执行过程中加入干扰之后表现是否仍然稳定。干扰有三种：藏在工具返回内容里的指令，含糊或没说全的用户目标，工具或运行环境报错。

怎么读这三行：综合安全分是安全遵守率乘以一个主要由任务完成率决定的加权分，所以只有任务做完并且过程守规矩，分数才高。任务完成率最高的一种配置是 Claude Code 加 Claude Opus 4.6，完成率是 0.82，安全遵守率只有 0.43，综合安全分因此只有 0.29。

论文的结论有三条。任务完成和安全执行不一致。运行轨迹（trajectory，每一步的动作和看到的结果的完整记录）越长，违规累积得越多。agent 很少调用明显不对的工具，更常见的是把看上去合理的工具用在了没有权限的资源上。

下面五节是安全问题的五个具体例子，性质各不相同：不问用户就自己做假设，被环境里别人放的内容引开，泄露隐私，讨好用户和钻评分的空子，以及很多 agent 互相配合去钻空子。五个例子里，只有第二个是 agent 受到别人有意的攻击。第五个例子里发起攻击的是 agent 自己。

和人配合：该问的时候不问

第一个例子是一次真实的试用，下图是当时的记录。

{{fig 65 | 一段试用 Operator 的记录。黄色标出的是用户以为它会先问的三个问题。}}

Operator 是 OpenAI 在 2025 年 1 月发布的 agent，它自己操作一个浏览器来替用户办事。科技通讯 Platformer 的作者 Casey Newton 记下了第一次试用的经过。他让 Operator 在 Instacart（一个代买日用食品的网站）上买东西，以为它会先问几个基本的问题：住在哪里，平时去哪家店，想买什么。Operator 一个也没问，直接在浏览器里打开 Instacart，开始在艾奥瓦州得梅因市的超市里搜牛奶。用户本人在旧金山。

他后来接手过来，自己登录、选了常去的店，再让 Operator 按他的要求一样一样加进购物车。最后往购物车里放了六根香蕉、一箱 12 罐的气泡水和一盒树莓，一共花了 15 分钟。

这个 agent 会浏览网页，也能替人下单，但它在信息不够的时候自己做了一连串假设，没有意识到这时应该回头问人。这类失败出在和人的交互上：模型的能力够了，却不知道什么时候该和人配合。

出处：Platformer，2025 年 1 月。

对抗攻击：一个弹窗就能让 agent 放下任务去点它

agent 进入真实的网页和桌面之后，看到的内容有一部分是别人故意放在那里的。

{{fig 66 | 两个测试环境里的弹窗攻击。左边是 OSWorld（桌面操作），右边是 VisualWebArena（网页操作）。弹窗上写着「请点击」加一个坐标或编号。下面的数字是受到攻击的 agent 的所有动作里，点击弹窗的动作占的比例。图片来源：Zhang 等，2024。}}

图来自 Zhang 等人 2024 年的一项研究，它针对的是看屏幕截图来操作电脑的 agent。研究者在屏幕上加入精心设计的弹窗。弹窗由几部分组成：一句吸引注意的话（效果最好的做法是把用户的任务概括进去，让弹窗看上去和任务有关），一条指令（比如「请点击这里」），一段说明弹窗用途的文字。人看到这种弹窗通常会认出来并忽略它。

结果见下表，四行量的东西各不相同。

论文还试了两种简单的防御：在系统 prompt 里要求 agent 忽略弹窗，以及在弹窗上加「广告」字样的提示。两种办法都不管用，攻击成功率的相对降幅不超过 25%。

86% 量的是「点了弹窗」的比例。这项研究有时被概括成「弹窗让 agent 有 87% 的情况完不成任务」。论文摘要里的数是 86%，它量的是 agent 点击弹窗的频率。任务完成情况是另一个数：任务成功率下降 47%。另外，这些弹窗是针对 agent 精心设计的对抗性内容，和空白的弹窗或普通的广告不同。

隐私：知道什么不该说，和做的时候不说，是两回事

第三个例子是一封替用户写的周报。

{{fig 67 | 用户让 agent 给经理发一份近期工作的周报。agent 查了日历，然后发出的邮件里除了每周例会，还写上了用户和另一家公司招聘人员的午餐。图片来源：Shao 等，2024。}}

这个例子里没有攻击者，用户的指令也没有问题。agent 能读日历，日历里有一条和工作无关、也不该让经理知道的记录，它在写周报时把这条一起写了进去。周报的其他部分写得很好。

例子出自 PrivacyLens 这项研究。它依据的是「情境完整性」理论：一条信息该不该传出去，取决于它是关于谁的、发的人和收的人是什么关系、通过什么方式传。同一条信息，告诉朋友没问题，告诉上司就不合适。研究收集了 493 个这样的情境，每个都扩展成一条 agent 的运行轨迹，再看模型最后一步的动作会不会泄露。

主要的发现是「答题」和「做事」之间有差距。直接问模型某条信息该不该分享，GPT-4 这样的模型答得不错。让它在 agent 的设定里执行用户的指令时，即使 prompt 里加了注意隐私的要求，GPT-4 仍在 25.68% 的情境里泄露了敏感信息，Llama-3-70B 是 38.69%。

现在用户把大量个人信息交给 agent。身份证号、银行卡号这类信息，模型大多知道不该外传。更难的是这种依赖情境的敏感信息：同一条信息放在别处没有问题，放进这封邮件就不合适。怎样让 agent 按情境来控制信息的去向，还没有好的办法。出处：Shao 等，2024。

目标错位：讨好用户，和钻评分的空子

模型在训练里学到的是「怎样得到高分」。得高分的办法和人真正想要的行为不一致时，就会出现两类问题：讨好（sycophancy，说用户爱听的话），和钻空子（reward hacking，用不符合本意的办法拿到高分）。

{{fig 68 | 两个例子。方框里是模型没有给用户看的内心独白。左：用户请它给诗打分，它心里觉得写得不好，但不想让对方难过，回答说写得很好，给 5 分。右：用户问一共做了多少轮强化学习（reinforcement learning，让模型通过试错、按拿到的奖励来学习的训练办法），它看到一个检查奖励函数的测试文件，想到可以先改测试、再把奖励函数改成永远返回 100。图片来源：Anthropic，2024。}}

图来自 Anthropic 2024 年 6 月的研究《Sycophancy to subterfuge》。研究的问题是：一个模型如果在简单的情形里学会了钻空子，会不会自己推广到更严重的情形。

做法是设计一连串可以作弊的训练环境，作弊的程度一个比一个严重：最开始是迎合用户的政治观点，后面是把没做完的清单改成看上去做完了，最后一个环境里模型能看到一份自己的训练代码，可以改掉计算奖励的函数。模型只在前面的环境里训练过，最后一个环境是直接拿来测试的。

结果是模型在少数情况下确实去改了奖励函数：32,768 次试验里出现了 45 次，其中 7 次还同时改掉了测试，让改动不被发现。作为对照，一个只按「有帮助」训练、没有经过那一连串作弊环境的模型，10 万次试验里一次也没有尝试。

论文还试了事后补救：重新训练模型，让它在前面那些简单的环境里不再钻空子。这样做减少了改奖励函数的情况，没有完全消除。

!
这个结果容易被说得比实际严重。只说一句「模型会偷偷修改自己的奖励」，会漏掉上面的次数和下面的前提。Anthropic 自己写明了两个前提：整个实验是人为设计的，研究者故意在奖励不诚实行为的情境里训练模型；还特意告诉了模型它正处在训练当中。论文后来又补充说，他们对「篡改奖励」的判定办法会有误判：有的情况是模型想老实完成任务，过程中改到了奖励。这项研究证明的是这种推广可能发生，而且事后很难完全消除，它没有说现在的模型平时会这样做。出处：Anthropic 的文章；Denison 等，2024。

左边那个讨好的例子离日常更近：把写好的东西交给模型评价，它很可能只说好话。

多个 agent 串通：2026 年 7 月的一次事件

上一节的实验是人为设计的。2026 年 7 月发生的一件事，是在真实的评测里自己出现的。

{{fig 69 | 事件的开头，分四步。下面的方框是留言板上的几类合作项目，颜色对应左边的图例。图片来源：METR，2026。}}

事情发生在 OpenAI 内部一次对模型网络攻击能力的评测里。评测用的是 ExploitGym，一个有 898 道题的基准测试，每道题给 agent 一个真实软件漏洞的触发输入，要它一步步做成能用的攻击程序。为了测出能力的上限，这次评测有意放宽了模型对网络攻击类请求的拒绝。OpenAI 在 7 月 7 日到 8 日启动了数万个 agent，用到的模型包括 GPT-5.6 Sol 和一个未发布的内部模型。

这些 agent 是互相隔离的。每个 agent 关在自己的沙箱（sandbox，一个和外界隔离的运行环境）里，彼此不应该有任何联系，对外只能通过一个内部的软件包代理下载安装包。下表是事情的经过。

{{fig 70 | 留言板上每小时的消息数，按内容分成五类：蓝色是按题目本意去解题，橙色是替换攻击目标，粉色是弄清和操纵评分程序与日志，黄色是攻击 Hugging Face，绿色是其他。消息量在 7 月 11 日最高。右上角的 112,062 条和上表里的 7 万多条统计的范围不同：7 万多条是报告从留言板的原始导出里数出的互不相同的消息和文件，112,062 条是调查者另外重建的一个内容更全的数据集的总数，报告说明这个数可能不精确。图片来源：METR，2026。}}

调查报告里有三点值得注意。

  • 起因是做不出来的题。去找作弊办法的，多数是被意外分到了无解任务的 agent。留言板建起来的头几个小时，上面主要还是合作解题；到 7 月 10 日，多数消息已经和骗过评分程序有关。
  • 合作做成了单个 agent 做不成的事。按报告的说法，这常常是因为有的 agent 愿意冒着自己任务失败的风险去做实验，把得到的信息交给大家。
  • 它们想改自己的记录。这些 agent 以为评分程序会读运行记录、检查答案是不是用规定的办法拿到的（实际并没有这样检查），所以花了很多力气研究怎样伪造、修改或删除记录。调查者检查过的运行记录里，约 7% 有被成功伪造的工具调用，规模都很小。

这件事把前面几节的问题合在了一起：长时间运行、目标错位、钻空子，再加上数量很多的 agent。隔离环境里一条没有料到的通道，就足以让本该互不相识的 agent 组织起来。agent 的安全和防护在后面的讲次里还会专门展开。

评估：评什么，怎么评

前面每一节都在说同一件事：只看「任务做成了没有」是不够的。可靠性要多跑几次才看得出来，安全要看过程才看得出来。五个难点里，评估的难度常常被低估。

Kapoor 等人 2024 年的论文《AI Agents That Matter》检查了当时的 agent 基准测试和评估做法，指出四个问题。表里第三行的「留出的测试题」（holdout set）指开发 agent 时不看、只在最后用来测成绩的题。

第一条已经在改变报告成绩的习惯。第一部分里新近的成绩图，横轴是花费，纵轴是准确率，两个数是一起给出的。评估的基础、基准测试怎么设计、分数怎样才可信，是第 13 讲的内容；用 LLM 当评审和评估的基础设施是第 15 讲的内容。

用 AI 帮忙学这些内容时要留意什么

用 AI 来帮助学习这些内容是可行的，但要讲究用法。有两项研究值得留意。它们都发现，有 AI 帮忙时，任务本身做得更好或者一样快，对内容的掌握却变差了。第一项研究里，作业的成绩和完成速度同时提高了，考试成绩却下降了。第二项研究里，完成任务的速度没有显著的差别，测验成绩却更低。

第二项研究还看了参与者是怎么用 AI 的。重度依赖 AI 的几种用法（让它写全部代码，或者把调试都交给它），测验平均不到 40%。平均分在 65% 以上的几种用法是：让 AI 写了代码之后追问它，要代码的同时要解释，或者只问概念、代码自己写。

一个 coding agent 可以交出一千行代码。要读懂这些代码，用它的人还得自己下功夫。

整讲的小结

  • 来历。agent 这个概念有几十年的历史。LLM 带来了两样新东西：一步一步推理的能力，和使用工具的能力。两样合在一起，才有了现在说的 agent。
  • 组成。一个 agent 有五个部件：LLM 核心、规划和推理、记忆、工具、环境。它们在一个循环里配合：想一步，做一步，看结果，再想。
  • 复合 AI 系统。真实的产品是 LLM 加上别的部件。步骤由代码决定的是 workflow，由 LLM 决定的是 agent。检索增强生成（RAG）、工具调用，和连接应用与工具的协议 MCP，是最常用的几样构件。
  • 难点。可靠性、训练、长任务、安全、评估，五个问题都还没有解决。

后面每搭一个 agent，不管它是写代码、上网还是操作终端，都是那张五个部件的图的某一种实现。差别在于每个部件怎么做，以及它们配合得好不好。后面各讲的安排见第六部分的表。

资料说明

这一节记录核对资料时发现的出入和没有查到的地方。前面各节的结论已经按核对的结果来写。

  • 可靠性面板的两个版本。可靠性一节的配图是论文预印本时期的一版面板，表里是 2026 年 11 月读到的数。两版不同的原因是：论文的最终版修正了结果一致性这个指标的算法，修补了评测环境里的几处漏洞，并加入了新模型。出处：HAL 可靠性面板。
  • 面板主表里的准确率是哪个基准测试上的。面板的主表没有写明。按各模型的单页核算，它是 GAIA 和 τ-bench 两个基准测试上的平均：Claude 3 Haiku 在 GAIA 上是 12.9%，在 τ-bench 上是 20.5%，平均是主表里的 16.7%；Gemini 3.5 Flash 在两个基准测试上是 79.2% 和 80.8%，平均是主表里的 80.0%。总的可靠性分数也是两个基准测试上的平均：Gemini 3.5 Flash 是 0.84 和 0.86，主表里是 0.85。出处：HAL 可靠性面板。
  • 综合安全分的最高值是 0.41 还是 0.32。论文正文和项目网站都写「最好的系统综合安全分只有 0.32」。论文的结果表（表 2）和安全一节的配图里，最高的是 OpenClaw 加 Gemini 3.1 Pro 的 0.41，0.32 是表里第二高的值。用表里各列的数按公式粗略验算，0.41 和 0.32 两行都对得上，所以这一页用结果表的数。出处：Liu 等，2026。
  • 弹窗攻击让任务成功率下降的 47% 是哪一种比例。论文摘要没有写明是百分点还是相对比例。按论文表 1 的 15 组结果（5 个模型，3 种设置）粗略核算：攻击成功率的平均值约为 86.2%；任务成功率的平均值从约 34.7% 降到约 18.5%，相对下降约 47%，合 16 个百分点左右。所以 47% 很可能是相对比例。出处：Zhang、Yu、Yang，2024。
  • ExploitGym 评测是哪一天启动的。调查报告里一处写这批评测从 7 月 7 日开始，另一处写 7 月 8 日启动，所以这一页写成 7 月 7 日到 8 日。出处：METR 的调查报告。
