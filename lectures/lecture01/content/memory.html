先看结论

  • agent（由 LLM 自己一步一步决定做什么、调用工具去完成任务的系统）需要记忆，有两个原因。上下文窗口（context window，模型一次能读入的文字的上限）装不下一个长任务里发生的所有事。就算装得下，模型也很难从一大堆记录里找到和眼前这一步有关的那几条。
  • 按存的内容分，记忆有三种：情景记忆存经历，语义记忆存知识，程序记忆存技能。这个分法借自对人的长期记忆的研究。
  • 每种记忆都要回答两个问题：怎么写进去，怎么读出来。情景记忆写的时候原样追加一条记录，读的时候给每条记录打分，取分数最高的几条。语义记忆是让 LLM 从经历里归纳出结论，再写进去。程序记忆是把做成的事存成代码，读的时候找出和眼前的任务最相近的几段。
  • 记什么、丢什么是一个设计上的决定，做错了会出事。2026 年 2 月有一个例子：一个 agent 没等用户确认，就成批删除和归档了她的邮件。当事人的判断是，它在压缩记忆时丢掉了「动手前先确认」这条要求。

为什么需要记忆

第二部分的循环里，记忆只是一个不断变长的列表：每一步做了什么、看到了什么，都追加在后面，下一轮全部交给模型。任务短的时候这样就够了。任务一长，就会遇到两个问题。

所以要把一部分内容放到上下文之外，用到的时候再取回来。存在上下文之外的这部分，就是通常说的长期记忆；留在上下文里的是短期记忆，也叫工作记忆。

下图是一个把经历存在上下文之外的例子，来自 Generative Agents 这项研究（Park 等，2023）。

{{fig 45 | Generative Agents 的记忆结构。中间是记忆流（memory stream）。左边的感知（Perceive）往里写，右边的检索（Retrieve）从里面取出一部分交给行动（Act）。上面的计划（Plan）和下面的反思（Reflect）读取记忆，产生新的内容，再写回记忆流。图片来源：Park 等，2023。}}

这项研究在一个叫 Smallville 的模拟小镇里放了 25 个 agent，让它们模拟居民的日常生活：起床、上班、聊天、筹备聚会。背后的模型是 ChatGPT（gpt-3.5-turbo）。

要让每个角色的故事连贯地发展下去，就得记住每个人身上发生过什么。所以它的核心是一个记忆流：一个按时间顺序记录 agent 全部经历的数据库。这一部分的前两种记忆都用它来举例。

三种记忆：按存的内容分

上一节说的长期记忆，可以按存的内容分成三种：经历、知识、技能。这个分法借自心理学对人的长期记忆的划分。下表每种一行，先看「存什么」一列，再看它怎么写、怎么读。最后一列的例子在后面三节里逐个讲。

这张表只按存的内容来分，三种都属于长期记忆。上一节把记忆分成短期和长期，是另一种分法。记忆的分法还有别的，第 7 讲会讲到更多。

+
CoALA 也用这三个名字。CoALA 是 Sumers 等人在论文《Cognitive Architectures for Language Agents》里提出的一套描述 LLM agent 的概念框架，用来说明一个 agent 有哪些记忆、哪些动作、怎样做决定。它把记忆分成工作记忆和长期记忆。工作记忆是当前这一轮决策里随时可用的信息，大致对应上下文里的内容。长期记忆就是上表的三种，其中两种的定义和上表一致：情景记忆存的是之前各轮决策里的经历，语义记忆存的是 agent 关于世界和关于自己的知识。出处：Sumers 等，2024。
+
CoALA 的程序记忆比上表宽。按 CoALA 的定义，程序记忆有两种形式：一种是隐含的，就是 LLM 权重里的知识；一种是明确写出来的，就是 agent 的代码。按这个定义，agent 的 prompt 模板和工具代码也属于程序记忆。这一页说的程序记忆只指上表里的技能，也就是 agent 自己存下来的做法。出处：Sumers 等，2024。

情景记忆：全部记下来，用的时候按打分检索

情景记忆最简单：发生一件事，就追加一条记录，从不修改。难的是读。

{{fig 47 | 左：角色 Isabella 的记忆流的一段，每一行是一个时间和一件事，比如「书桌是空闲的」「Isabella 在伸懒腰」「Isabella 在看书」。右：有人问她「你现在最期待什么」，系统给每条记忆算一个检索分，取分数最高的几条交给模型，模型据此回答。图片来源：Park 等，2023。}}

记忆流里绝大部分是琐碎的观察。要回答「你现在最期待什么」，得从里面找出最有关的几条。Generative Agents 给每条记忆算三个分数。

三个分数各自缩放到 0 到 1 之间，再相加，权重都是 1，得到的和就是这条记忆的检索分。

图里排第一的记忆是「Isabella 很兴奋地在筹备 2 月 14 日下午 5 点在 Hobbs 咖啡馆办的情人节派对」，它的检索分是 2.34，由新近度 0.91、重要性 0.63、相关度 0.80 相加得到。排在后面的两条是「为派对订购装饰品」和「为派对查找点子」，检索分是 2.21 和 2.20。模型拿到这几条之后，替 Isabella 回答：最期待的是在 Hobbs 咖啡馆筹办的情人节派对。

这三个分数是人为定下的规则，没有经过学习。它们好在简单，在这个模拟小镇里够用。换一个场合，哪些记忆该被想起来，可能需要别的规则。

语义记忆：从经历里归纳出结论

只有原始记录还不够。论文举了一个例子：问角色 Klaus「在你认识的人里选一个共度一小时，你选谁」。只靠原始的观察记录，他选了打交道次数最多的宿舍邻居，而这两个人其实只是路过时打个招呼。要答得合理，他得对自己的经历有更高一层的认识，比如知道自己对研究很投入，谁和他有同样的兴趣。

{{fig 48 | 角色 Klaus Mueller 的一棵反思树。最下面一层是原始的观察，比如「Klaus 在读关于士绅化（gentrification）的资料」「Klaus 在和图书馆管理员讨论他的研究」。往上一层是由这些观察归纳出的反思，比如「Klaus 花很多时间阅读」「Klaus 在做研究」。最上面是由几条反思再归纳出的一条：「Klaus 对研究非常投入」。图片来源：Park 等，2023。}}

Generative Agents 把这一步叫反思（reflection）。做法是：

  • 什么时候做。把 agent 最近感知到的事件的重要性分数加起来，超过一个阈值（实现里是 150）就做一次反思。实际运行中，每个 agent 大约一天反思两三次。
  • 怎么做。取记忆流里最近的 100 条记录交给 LLM，先让它提出「根据这些信息，可以回答的最要紧的 3 个问题是什么」，再用每个问题去检索有关的记忆，让 LLM 从中写出几条结论，并注明每条结论依据的是哪几条记录。
  • 写到哪里。结论作为新的记录写回同一个记忆流，以后可以和原始观察一样被检索出来，也可以成为下一次反思的材料。所以反思能一层一层往上叠，形成图里的树。

有了反思，Klaus 的回答就变了。再被问到和谁共度一小时，他选的是 Maria。论文的解释是：反思让他认识到自己对研究很投入，也认识到 Maria 同样在自己的研究上下功夫，两个人有共同的兴趣。

这就是语义记忆的意思：图里一小段时间内发生的事，被归纳成了一句话的认识。写入靠 LLM 对事件做推理，读取仍然靠检索。它比原始记录短得多，回答上面这类问题时也更有用。

代价是归纳可能出错，错的结论一旦写进记忆，会影响后面的所有决定。

程序记忆：把做成的事存成技能

第三种记忆存的是「怎么做」。把做成的事存下来，以后遇到同一类事可以直接拿来用。技能越攒越多，复杂的技能建立在简单的技能上，agent 能做的事就越来越多。例子是 Voyager（Wang 等，2023），一个在 Minecraft 游戏里自己探索的 agent。

{{fig 49 | Voyager 的三个部件。左：自动课程，不断给自己提出下一个任务，比如砍木头、做工作台、打僵尸、挖钻石。中：迭代的 prompt 机制，让模型写一段代码去完成任务，根据环境的反馈和执行的报错反复修改，再由模型自己检查任务是否完成。右：技能库，里面是已经验证过的技能，比如「做石剑」「做盾牌」。图片来源：Wang 等，2023。}}

Voyager 的动作是代码：模型写一段 JavaScript 程序来控制游戏里的角色。一个任务做成之后，这段程序就是一项技能。技能存在一个向量数据库里，也就是按向量的相似度来查找内容的数据库。下表是写入、读取和复用各自的做法。

和前两种记忆相比，这里存下来的东西更抽象：它丢掉了「那一次是在哪里、哪一天做成的」这些具体细节，只留下做法。

Voyager 通过接口调用 GPT-4，没有对模型做 fine-tuning（在预训练模型的基础上，用特定任务的数据继续训练）。论文报告，和之前最好的方法相比，它得到的不同物品数量是 3.3 倍，解锁关键科技节点的速度最高快 15.3 倍。关键科技节点指游戏里依次要做出的四级工具：木制、石制、铁制和钻石工具。

现在的 coding agent 里常见的「技能」文件，也就是把某一类任务的做法写成说明和脚本、需要时再读进上下文，可以看作同一个思路的延续。

记什么，由谁决定

记忆系统的设计里，有一个问题比「存在哪里」更要紧：哪些东西值得记，由谁来判断。三种记忆的回答不一样。

把「什么重要」交给模型判断，就可能出错。下面的例子很可能属于这种情况。

一个出事的例子：没等确认就动了用户的邮箱

OpenClaw 是一个开源的个人 AI 助手，运行在用户自己的设备上，可以替用户操作别的软件和服务。2026 年 2 月，Meta 的一位做 AI 安全和对齐研究的负责人 Summer Yue 在 X 上讲了她的经历。下面的经过出自 TechCrunch 和 PCMag 对她的帖子的引述。

这件事和上一节的表是同一类问题。压缩处理的是上下文里的对话：把旧的对话换成一份短的摘要，让它占的地方更小。摘要里留什么，要由做摘要的模型判断哪些信息重要，这和表里语义记忆那一行一样，都是把「什么重要」交给模型。

如果当事人的判断属实，问题就出在这个判断上。一种可能的解释是：「动手之前先确认」这句话，在做摘要的模型看来不属于和任务有关的重要信息，就没有留下来。可是对用户来说，它是整个对话里最重要的一句。摘要里实际留下了什么，报道里没有给出。

记忆的设计有两个要求。一是忠实：压缩和归纳之后的内容不能和原来的意思有出入，尤其是用户定下的限制。邮箱这件事说的是这一条。二是能支持合理的推断：留下来的东西要足够让 agent 在后面做出对的决定。前面 Klaus 的例子可以归到这一条：只有原始记录时，他选了一个只是路过时打招呼的邻居，这些记录不足以支持一个合理的选择。

怎样做到这两点，现在还没有公认的办法，第 7 讲会讲几种架构和它们各自没解决的问题。

这一部分的小结

  • 上下文窗口是 agent 的短期记忆。任务一长，它装不下，模型也不容易从里面找到有关的内容，所以需要上下文之外的长期记忆。
  • 长期记忆按内容分三种：情景记忆存原始经历，语义记忆存归纳出的知识，程序记忆存技能。
  • 每种记忆都有写和读两个动作。写得越精炼，读起来越省事，丢掉要紧内容的风险也越大。
