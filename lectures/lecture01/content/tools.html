先看结论

  • 工具让模型做到它光靠生成文字做不到的事：拿到权重（模型内部由训练定下来的那些数值）里没有的信息，做需要精确结果的计算，对外部世界产生作用。
  • 模型只负责写出「调用哪个工具、参数是什么」。校验和执行由运行框架（harness）完成，它是包在模型外面、给它工具并管理多轮对话的程序。
  • 早期的做法是靠训练教模型用工具。有两项这样的研究：Toolformer（2023 年 2 月）教会一个模型用 5 个工具，Gorilla（2023 年 5 月）把范围扩大到 1,645 个 API。
  • 现在一次工具调用分四步：从上下文里的工具说明中选一个，填参数，校验，执行并把结果放回上下文。上下文指模型每次生成时能读到的全部文字。
  • MCP（Model Context Protocol）是连接 AI 应用和外部工具的标准协议。数据库、代码仓库这类提供工具的外部系统按它实现一次，支持它的应用都能用，不必为每一对应用和外部系统单独写对接代码。

工具解决什么问题

第二部分举过几个例子：模型不知道今天的讲座在哪间教室，算不准多位数乘法，读不到用户电脑上的文件。把这类例子归纳起来，模型光靠生成文字做不到的事有三类，都要靠工具来做，见下表。前两个例子分别属于第一类和第二类。第三个例子里，读文件是为了拿到模型没有的信息，也属于第一类。第三类说的是另一件事：模型生成的只是文字，要改一个文件、下一个订单，得有工具替它去做。

有了工具，agent（由 LLM 自己一步一步决定做什么、调用工具去完成任务的系统）的动作就建立在查到的事实和算出的结果上，更可靠。结果也更一致：同一道题交给计算器，每次算出的结果都相同。还有一个好处：需要某种能力时，可以把它交给一个专门的工具，底层的模型不必自己具备。下面 Gorilla 的例子里，用户想要一张图，模型自己不会画，它只要知道该调用哪个画图的模型。

模型按规定的格式输出一个函数名和一组参数，这一步常被叫作 function calling（函数调用）。它是一次工具调用里由模型完成的那一部分，校验和执行由运行框架完成。

Toolformer：让模型自己学会什么时候用工具

现在的做法是把工具的说明写进上下文，由模型当场选用。在这之前，有过靠训练教模型用工具的做法。这一节和下一节各看一个，后面才看得出变化在哪。

这一节看的是 Toolformer。它把工具调用直接嵌在文字生成的过程里：模型在生成文字的中途，到了需要的地方就插入一次调用。调用的写法是固定的：方括号里先写工具名和参数，再写一个箭头，箭头后面是工具返回的结果。

{{fig 51 | 右边是四个例子。彩色的部分是模型在句子中间插入的工具调用，方括号里是工具名和参数，箭头后面是工具返回的结果。四个例子依次用了问答系统、计算器、翻译系统和维基百科搜索。图片来源：Schick 等，2023。}}

看第一个例子。模型要续写的这句话说的是：《新英格兰医学杂志》是某个机构的注册商标。写到该填这个机构名字的位置，它插入一个调用：向问答系统提问「《新英格兰医学杂志》的出版方是谁」。问答系统返回「马萨诸塞州医学会」。模型再接着这个结果往下写。第二个例子里，模型写到「1400 名参与者中有 400 人」，调用计算器算 400 除以 1400，得到 0.29，然后写出「29%」。

Toolformer 是 Meta 的研究者 2023 年 2 月发表的工作。它要教会模型四件事：调用哪个工具，什么时候调用，传什么参数，怎样把结果用到后面的生成里。难处在于没有现成的训练数据，没有人给大量文本标注过「这里该查一下」。它的办法是让模型自己造数据。

第三步是关键。它看的是把调用和结果插进去之后，模型预测后面文字的误差有没有变小，这个误差就是模型的预测损失。这个判断由模型自己算出来，不需要人来标注，所以论文的标题是 Language Models Can Teach Themselves to Use Tools，意思是语言模型可以自己教自己用工具。

训练好之后，模型在生成时一旦写出调用里的那个箭头，就表示它在等工具的结果。这时生成暂停，由运行框架调用工具，把结果接在箭头后面，再继续生成。

它用的模型是 GPT-J，参数量 67 亿。参数量指模型里权重的个数，说的是模型有多大。这一页别处单说的「参数」，都指调用工具时填的参数。工具一共五个：问答系统、计算器、维基百科搜索、翻译系统、日历。数量很有限。后来的系统能用的工具多得多，做法还是上一段那样：模型写出调用，运行框架执行，再把结果交还给模型。

Gorilla：从五个工具到上千个 API

工具从几个变成上千个，新的问题就出现了：模型记不住这么多 API，会写出根本不存在的调用。Gorilla（伯克利，2023 年 5 月）针对的就是这个问题。

{{fig 52 | 左上：数据的来源和训练的过程。左下：带检索器使用时的过程，用户的请求先经过检索器找到相关的 API 文档，再由 Gorilla 写出调用。右：纵轴是准确率，横轴是幻觉的比例，越靠左上越好，幻觉在这里指调用了 API 库里不存在的 API，API 库是论文收集的全部 API 和它们的文档。上面一张是不带检索器的结果，下面一张是配了一个按关键词匹配的检索器之后的结果。图片来源：Patil 等，2023。}}

它的做法分四个环节，对应图的左半边。

图左下的例子：用户说「想看几只猫跳舞庆祝」。检索器找到一个文生图模型 Stable Diffusion 的文档，Gorilla 写出加载这个模型的那行代码，执行之后得到一张图。底层的语言模型自己不会生成图片，它把这件事交给了一个外部的工具。

这篇论文把两种错误分开统计。幻觉指调用了一个 API 库里根本不存在的 API，也就是凭空想出一个工具。普通的错误指 API 是存在的，但用得不对。

下表里的两个比例，分母都是全部的测试请求。准确率是写对了的请求占的比例：模型写出的调用和参考答案比对，调用的函数和指明是哪个模型的那几个参数都对得上才算对。幻觉的比例是出现幻觉的请求占的比例。

一个参数量只有 70 亿的小模型，专门训练之后，在「写对 API 调用」这件事上超过了当时的 GPT-4，凭空编造 API 的情况也少得多。这张表里两个模型都没有带检索器，所以它说明的是专门训练的效果：工具一多，通用模型光凭记忆写调用很容易出错。

查文档有没有用，论文是另外测的，结论取决于检索器好不好。给 GPT-4 配上一个总能找到正确文档的理想检索器，它在 Torch Hub 上的准确率从 38.70% 升到 66.12%，幻觉的比例从 36.55% 降到 0.53%。换成按关键词匹配的 BM25 检索器，准确率是 35.48%，比不带检索器时还低一点。论文的说法是，检索器不够好时，找来的文档有时会误导模型，带来更多的错误。

一次工具调用里发生了什么

上面两项工作讲的是模型怎样学会用工具。从系统的角度看，现在的一次工具调用分四步。

{{fig 58 | 上面是四个步骤。下面是一个例子：用户问 test.py 里有什么。}}

下表列出四步各自做什么、由谁做，最后一列是图里的例子。表里的运行框架（harness）指包在模型外面、给它工具并管理多轮对话的程序。

把例子里在上下文中出现的三段内容写出来，大致是下面的样子。格式因厂商而异，这里只是示意。

# 1. tool schema placed in the model's context
{"name": "read_file",
 "description": "Read a text file and return its content",
 "parameters": {"type": "object",
                "properties": {"path": {"type": "string"}},
                "required": ["path"]}}

# 2. what the model generates
{"name": "read_file", "arguments": {"path": "test.py"}}

# 3. what the harness appends after running the tool
"def add(a, b): ..."

这里要分清谁在做什么。在这次工具调用里，模型做的只有一件事：生成第 2 段那一行文字，选哪个工具、填什么参数都写在这一行里。读文件的是运行框架，模型看到的是运行框架放回来的结果，再根据它回答用户。所以交给模型哪些工具、每个工具允许做什么，由运行框架决定。一个工具调用要不要先经过人的批准，也在这一层控制。

第二部分说一个环境里可以做哪些操作由环境决定。环境指 agent 之外、它的动作作用在上面的那个世界，比如一个终端、一个网页浏览器。这句话和上一段说的是两层：环境决定有哪些操作可做，比如在终端里可以执行命令。运行框架决定把其中哪些做成工具交给模型，以及每个工具允许做到哪一步。

+
约束解码是什么。模型每生成一个 token（模型处理文字的最小单位），本来可以从整个词表（模型能输出的全部 token 的清单）里任选。约束解码（constrained decoding）在每一步只允许它选那些不会破坏规定格式的 token。它保证的是格式。参数的值对不对，不在它的检查范围内。约束解码在第 2 讲展开。出处和下一个框相同：OpenAI，2024（存档页面）。
+
约束解码的一个例子：OpenAI 的 Structured Outputs。OpenAI 在 2024 年 8 月推出的 Structured Outputs 就是这样做的。开发者用 JSON Schema 描述想要的输出，JSON Schema 是一种写明一段 JSON 里有哪些字段、各是什么类型的格式。系统把它转成一套语法规则，生成时只保留符合规则的 token。OpenAI 还专门训练了模型 gpt-4o-2024-08-06，让它更会按给定的 JSON Schema 输出。按 OpenAI 的说明，只靠这项训练，这个模型在 OpenAI 自己的测试里有 93% 的输出符合给定的 JSON Schema，加上约束解码之后是 100%。出处：OpenAI，2024（存档页面）。

从靠训练学会用工具，到把工具的说明写进上下文

把 Toolformer、Gorilla 和上一节的四步调用放在一起看，工具使用的做法有一个明显的变化。下表按三个问题比较这三种做法。

变化的好处写在表的第一行：换工具不用重新训练模型。工具的说明后来怎样有了统一的格式，第 4 讲展开。

最后一列的做法还留着两个问题。第一，工具的说明要占上下文，工具越多，占得越多。上下文里该放什么、怎样控制长度，是第 2 讲的内容。第二，执行调用的是应用自己的运行框架，所以每个应用都要为每个工具写一份对接的代码。下面的 MCP 处理的是第二个问题。

MCP：给工具定一个统一的接口

模型要用的工具，来自数据库、代码仓库、办公软件这类系统，这一节把它们叫作外部系统。如果每个 AI 应用都要为每个外部系统单独写一套对接代码，应用和外部系统一多就做不下去了。举例来说，3 个应用要接 5 个外部系统，就是 15 套对接代码；再多一个应用，又是 5 套。

{{fig 59 | 左边是各种 AI 应用：聊天界面、代码编辑器、别的应用。右边是数据来源和工具：数据库和文件系统、开发工具、办公工具，也就是正文说的外部系统。中间是 MCP 这个标准协议，两边的数据可以双向流动。图片来源：MCP 官方文档。}}

Model Context Protocol（简称 MCP）是 Anthropic 在 2024 年 11 月 25 日开源的一个标准，用来把 AI 应用和外部系统连起来。有了它，每个外部系统这一边按协议实现一次，做成一个 MCP 服务器，一个服务器可以提供很多个工具。应用这一边按协议实现一次，就能连上所有的 MCP 服务器。上面的例子变成 3 加 5 一共 8 份实现。

MCP 里有三个角色。下面的三个角色、服务器提供的三样东西和协议的两层，都按 2026 年 7 月 28 日版的架构文档来写。

表里说的工具、资源和 prompt 模板，是服务器可以向应用提供的三样东西：

  • 工具（tools）。AI 应用可以调用的函数，用来执行动作，比如操作文件、调用接口、查询数据库。
  • 资源（resources）。提供上下文信息的数据，比如文件的内容、数据库里的记录。
  • prompt 模板（prompts）。可以重复使用的模板，比如一段系统 prompt（开发者事先写给模型的那段固定说明）或者几个示范。

协议本身分两层。数据层规定消息的内容，用的是 JSON-RPC 2.0（一种用 JSON 表示远程调用的通用格式）。传输层规定消息怎么送：服务器和应用在同一台机器上时，用标准输入输出；通过网络连接时，用 HTTP。

MCP 只规定应用和服务器之间怎样交换这些内容。应用怎样使用 LLM、怎样管理拿到的内容，它不规定。

i
MCP 和 function calling 是两个层次的东西。function calling 说的是模型怎样输出一次调用。MCP 说的是应用怎样发现有哪些工具、怎样把调用送到工具那里并把结果取回来。一个应用通常两样都用：先通过 MCP 从服务器拿到工具的说明，把它们放进模型的上下文；模型按 function calling 的格式输出一次调用；应用再通过 MCP 把这次调用发给服务器执行。
+
协议还在变，读别处的介绍时要留意它说的是哪个版本。协议的版本按日期编号。2026 年 7 月 28 日的版本把协议改成了无状态的：每个请求自带协议版本和有关的能力信息，服务器可以单独处理每一个请求。能力（capabilities）是协议里的说法，指客户端或服务器声明自己支持哪些功能。无状态说的是每个请求的内容自成一体，上面表里客户端和服务器之间的那条连接在这个版本里照样有。协议的归属也变了：2025 年 12 月 9 日，Anthropic 把 MCP 捐给了 Linux 基金会下面新成立的 Agentic AI Foundation，这个基金会由 Anthropic、Block 和 OpenAI 共同发起。出处：MCP 架构文档，2026-07-28 版；Anthropic，2025。MCP 最初的发布见 Anthropic，2024。
+
客户端也可以向服务器提供能力。上面讲的三样东西都是服务器提供给应用的。反过来，客户端也可以向服务器提供能力。2026 年 7 月 28 日的版本里这类能力只列了一项，就是让服务器向用户追问信息（elicitation）。早先版本里让服务器借用应用的模型来生成文字的能力（sampling），在这个版本里已经标为弃用。出处：MCP 架构文档，2026-07-28 版。

这一部分的小结

  • 模型光靠生成文字有三类事做不到，要靠工具来做：拿到权重里没有的信息，做需要精确结果的计算，对外部世界产生作用。
  • 模型只生成「调用哪个工具、参数是什么」这段文字。校验和执行由运行框架完成，结果作为观察放回上下文。
  • Toolformer 和 Gorilla 靠训练教模型用工具。现在更常见的做法是把工具的说明放在上下文里，由模型当场选择。
  • MCP 把应用和工具之间的对接标准化，提供工具的外部系统实现一次，各个应用都能用。

工具使用的更多内容，包括怎样设计工具、怎样评测、常见的失败，在第 4 讲。到这里，agent 的几个部件都看过了。下一部分把它们放回到完整的系统里，看workflow 和 agent 的区别：下一步做什么由事先写好的代码决定的是 workflow，由模型自己决定的是 agent。
