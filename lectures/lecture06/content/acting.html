先看结论

  • agent（由语言模型自己决定下一步、在循环里调用工具的系统）每一步发出的动作可以有不同的形式。这一部分讲两个关于动作的想法：用代码当动作，以及先计划再执行。
  • CodeAct：让模型写一段代码当作动作，工具是代码里可以调用的函数。循环、判断、把一个工具的结果传给另一个工具，都可以在一段代码里完成，所以轮数更少，在要连续用多个工具的任务上成功率更高。
  • ReWOO 和 LLMCompiler：先让模型把要调用的工具和它们之间的依赖关系写成一份计划，再由程序去执行。这等于把 agent 的执行过程重新变成了一个 workflow（控制流写在程序里的系统）。
  • 两者的收获不同。ReWOO 一次写完计划、按顺序执行，主要的收获是省 token（模型处理文字的最小单位，花费按它计算）。LLMCompiler 让互不依赖的步骤并行执行，还可以在中途重新计划，主要的收获是快。
  • 这些想法今天以两种形式留在 agent 里：直接生成代码，和一次回复里发出多个并行的工具调用。计划仍然重要，尤其是在主 agent 把工作分给几个子 agent（主 agent 派出去单独做一部分工作的另一个 agent）的时候。

CodeAct：用代码当动作

先看最常见的动作形式。模型每一步输出一次工具调用：工具的名字加上参数，写成一行文字，或者写成一个 JSON 对象。运行框架（harness，包在模型外面、替它执行工具并管理多轮对话的程序）执行这次调用，把工具返回的内容交回给模型，这份返回的内容叫观察结果（observation）。模型读了观察结果，再输出下一次调用。

CodeAct 这篇论文（Wang 等，2024）的主张是：代码是更合适的动作形式。用同一个任务比较两种写法。任务是：确定在哪个国家买 CodeAct 1 这款手机最划算，要考虑的国家是美国、日本、德国和印度。可用的工具有五个：查某国的汇率和税率，查手机在某国的价格，把价格换算并加税，估算运到某国的运费，算出最终价格。

{{fig 44 | 用文字或 JSON 当动作。模型先想：应该算出每个国家以美元计的价格，再找出最划算的。然后一步只能调用一个工具：查德国的汇率和税率，环境返回 1.1 和 0.19；查德国的价格，返回 700；换算并加税，返回 916.3；后面还要查运费、算最终价格，再对其余三个国家各重复一遍。最底下是五个可用的工具。图片来源：Wang 等，2024。}}

按图里的做法粗略数一下，四个国家各要五次工具调用，一共大约二十轮来回，每一轮模型都要读一遍结果再决定下一步。同样的任务用代码来做，只要一轮：

{{fig 45 | 用代码当动作。想法是一样的，但动作是一段 Python 程序：对四个国家做循环，在循环里依次调用五个工具，最后用 Python 自带的 min 函数取出最便宜的。环境返回的只有一行：Japan 904.0。图片来源：Wang 等，2024。}} 
countries = ['USA', 'Japan', 'Germany', 'India']
final_prices = {}
for country in countries:
    exchange_rate, tax_rate = lookup_rates(country)
    local_price = lookup_phone_price("CodeAct 1", country)
    converted_price = convert_and_tax(local_price, exchange_rate, tax_rate)
    shipping_cost = estimate_shipping_cost(country)
    final_price = estimate_final_price(converted_price, shipping_cost)
    final_prices[country] = final_price
best = min(final_prices, key=final_prices.get)
print(best, final_prices[best])

两种写法最后的回答相同：最划算的是日本，价格是 904 美元。CodeAct 仍然是一个 ReAct 式的循环（先想，再动作，看结果）：如果这段代码的结果还不够，模型可以再写一段。只是每一步的动作从「调用一个工具」变成了「运行一段程序」。

论文列了代码当动作的四个好处。

CodeAct 的效果：多工具的任务上更好，单次调用时不一定

论文用一个新做的基准测试（benchmark，一组题目加一个打分的办法）比较了三种动作形式：代码、JSON、文字。这个基准测试叫 M3ToolEval，有 82 个人工编写的任务，每个任务都要在多轮里调用多个工具，最多允许 10 轮。论文一共测了 17 个模型，下面的图和表是其中八个模型的结果。

{{fig 46 | 八个模型在 M3ToolEval 上的结果，每个模型三根柱子，对应三种动作形式：代码、JSON、文字。左图是成功率，越长越好。右图是平均交互轮数，越短越好。图片来源：Wang 等，2024。}}

在最强的模型 gpt-4-1106-preview 上，代码的成功率比另外两种里较好的一种高 20.7 个百分点，平均少用 2.1 轮。图里的八个模型，代码的成功率都是三种里最高的；轮数上只有 text-davinci-003 一个例外，它用 JSON 时轮数略少。

下结论之前还要看三件事。

  • 图里只有 17 个模型中的八个。看全部 17 个模型，在 M3ToolEval 上，代码的成功率最高的有 12 个，轮数最少的也是 12 个。例外的 5 个里有 claude-instant-1：它用 JSON 的成功率是 31.7%，用代码是 20.7%。
  • 只做单次工具调用时，哪种形式最好要看模型。论文在另一个基准测试 API-Bank 上测了每次只调用一个工具的情况，这时代码的控制流派不上用场。gpt-4-1106-preview 用 JSON 的正确率是 82.7%，用代码是 76.7%。17 个模型里，代码最好的有 8 个，JSON 最好的有 5 个，文字最好的有 4 个。论文的推测是，gpt-4-1106-preview 这样的闭源模型很可能针对 JSON 形式的工具调用专门训练过。
  • 换成代码，补不上模型本身的差距。在 M3ToolEval 上同样用代码当动作，当时最好的开源模型成功率是 13.4%，gpt-4-1106-preview 是 74.4%。论文针对这个差距收集了约 7,000 条用代码当动作的多轮运行记录，用它们微调（fine-tuning，用数据继续训练模型）了两个 70 亿参数的模型。微调之后差距仍然很大。以 Mistral 7B 为基础的那个，在 M3ToolEval 上的成功率是 12.2%，没有微调的对照模型是 0，论文说 12.2% 和 700 亿参数的开源模型相近。以 Llama-2 7B 为基础的那个没有提高，成功率仍是 0。

所以更准确的说法是：任务需要把多个工具组合起来用的时候，代码这种形式在多数模型上明显更好。只调用一个工具时，JSON 并不差。动作的形式只是影响成绩的因素之一，模型本身弱的时候，换成代码成功率仍然很低。

i
工具很多时，要不要把每个工具的用法都先告诉模型？模型要先从 prompt（发给模型的输入文字）里读到一个工具的名字和用法，才能在代码里调用它。工具多了，全部写进去，模型容易选错。应对的办法是只在需要时才告诉模型某个工具的存在和用法，这叫渐进式披露（progressive disclosure），见第六部分。

先计划，再执行

ReAct 式的循环里，模型每调用一次工具就要停下来看结果，再想下一步。这样停下来有两个代价。一是每走一步都要调用一次模型，开头的说明、示范的例子、之前每一步的想法和观察结果都要重新发送一遍，步数越多，重复发送的内容越多。二是工具调用只能一次接一次地进行，两次调用互不依赖时也要依次等。

另一个思路是：让模型一开始就把整个计划写出来，也就是要调用哪些工具、按什么顺序、哪个工具的输出要交给哪个工具，然后由程序照着计划执行。

这个思路的要点是：有了计划，agent 执行动作的过程就重新变成了一个 workflow。

workflow 是控制流写在程序里的系统：做哪些步骤、按什么顺序做，都由程序决定，执行到一半不用再让模型决定下一步。第一部分讲过它。这里的不同之处在于，这个 workflow 是模型针对眼前的问题临时写出来的。

变成 workflow 之后，上面的两个代价都可以减小。模型调用的次数少了，重复发送的内容就少，所以省 token。互不依赖的步骤可以同时执行，所以更快。有两篇论文是这个思路的代表：ReWOO 主要做到了省 token，LLMCompiler 主要做到了快。

ReWOO：不看观察结果，先把计划写完

ReWOO 是 Reasoning WithOut Observation 的缩写，意思是不依赖观察结果的推理，观察结果就是工具返回的内容。它把一次任务分给三个模块：Planner、Worker 和 Solver。

{{fig 48 | 左上的 Planner 写出计划，每一步有一句说明和一个带编号的变量。右上的 Worker 逐条执行，把得到的结果填进变量。下面的 Solver 读完整的计划和结果，给出答案。图片来源：Xu 等，2023。}}

例子里的问题是：Hennchata 的主要原料是哪家干邑酒庄生产的？Hennchata 是一种鸡尾酒，不知道它是什么的人完全无从下手。Planner 写出的计划如下，计划后面的表说明三个模块各做什么。

Plan: Search for more information about The Hennchata.
#E1 = Wikipedia[The Hennchata]
Plan: Find out the main ingredient of The Hennchata.
#E2 = LLM[What is the main ingredient of The Hennchata? Given context: #E1]
Plan: Search for more information about the main ingredient.
#E3 = Wikipedia[#E2]
Plan: Find out the cognac house that makes the main ingredient.
#E4 = LLM[What is the name of the cognac house that makes the main ingredient #E2? Given context: #E3]

和 ReAct 比，差别在于模型什么时候看到工具的结果。ReAct 是生成一次工具调用，执行，看结果，再生成下一次。ReWOO 是事先把要调用的工具、调用的顺序、谁的输出给谁，全部写好。

这和 CodeAct 有相通的地方：写代码时也是把一个函数的返回值存进变量，再传给下一个函数。

为什么省 token

模型的接口是无状态的：每调用一次，都要把到目前为止的全部内容重新发一遍，包括开头的说明、示范的例子、之前每一步的想法和观察结果。ReAct 每走一步就调用一次模型，所以这些内容被反复发送，步数越多，重复得越厉害。论文把这叫作 prompt 的冗余。ReWOO 的 Planner 和 Solver 各只调用一次，开头的说明和例子不会被重复发送很多遍。

ReWOO 的效果

论文在六个公开的基准测试和一个自己整理的数据集上，比较了四种做法的准确率和消耗的 token 数：ReWOO，ReAct，以及两种不用工具的做法。不用工具的两种做法，一种是让模型直接回答，另一种是 CoT（chain of thought，让模型在回答之前先一步步写出推理过程）。下面的图画的是 ReAct 和 ReWOO，表里是四种做法的数字。

{{fig 49 | 横轴是消耗的 token 数，越靠左越好。纵轴是准确率，越靠上越好。颜色代表方法，绿色是 ReAct，紫色是 ReWOO。圆点是六个公开基准测试的平均，三角是论文自己整理的一个数据集。红色箭头从 ReAct 指向 ReWOO。图片来源：Xu 等，2023。}}
  • token 省得很明确。在六个公开基准测试上，ReWOO 平均比 ReAct 少用约 64% 的 token。六个基准测试之一的 HotpotQA 是一个问答数据集，题目要把两处以上的信息连起来才能回答。单看它，ReAct 平均每题用 9,795 个 token，ReWOO 用 1,986 个，大约是五分之一。
  • 准确率略高。六个公开基准测试的平均准确率，ReAct 是 58.3%，ReWOO 是 60.9%，ReWOO 高 2.6 个百分点。单看 HotpotQA，ReAct 是 40.8%，ReWOO 是 42.4%，ReWOO 高 1.6 个百分点。论文摘要里说的「HotpotQA 上准确率提高 4%」是相对的比例，说的就是这 1.6 个百分点。
  • 工具不一定有帮助。在公开基准测试上，不用任何工具、只让模型先写推理再回答的 CoT，平均准确率是 59.9%，比 ReAct 的 58.3% 还高。论文自己也指出了这一点。工具的好处在那个国情咨文数据集上才显出来，很可能是因为模型在训练时没有见过这些内容。

先写计划还有一个附带的好处：工具出故障时，成绩掉得少一些。论文做了一个让所有工具都失效的实验：每个工具都只返回「没有找到证据」。按两种做法的流程，这时 ReAct 每走一步读到的观察结果都是这句话，再根据它想下一步。ReWOO 的计划在调用工具之前已经写完，Solver 最后读到的仍然是完整的计划，只是每一步的结果都换成了这句话。

实验的结果是，ReAct 在 HotpotQA 上的准确率从 40.8% 掉到了 0，ReWOO 从 42.4% 掉到 13.2%。论文只报告了这两个数，没有分析 ReWOO 剩下的这 13.2% 是怎样答对的。

它的局限也来自「不看结果就计划」。如果后面的步骤要等看到前面的结果才能决定，事先就写不出计划。论文举的例子是在一个陌生的房间里找花瓶：Planner 不知道花瓶在哪里，只能把所有可能的地方都列进计划。

LLMCompiler：并行执行，必要时重新计划

LLMCompiler（Kim 等，2023 年 12 月首次发布，发表在 ICML 2024）沿着同一个思路往前走了两步：一是计划里互不依赖的步骤同时执行，二是计划可以在执行中途重新生成。它有三个部件，下面的图用一个例子画出了它们的分工，图后面是这个例子的计划和三个部件的说明。

{{fig 50 | 用户的问题是：微软的市值要涨多少才能超过苹果？Function Calling Planner 写出四个任务，其中 $1、$2 是占位符，代表前面任务的输出。Task Fetching Unit 取出可以执行的任务交给 Executor，Executor 并行地调用工具。图片来源：Kim 等，2023。}} 
$1 = search(Microsoft Market Cap)
$2 = search(Apple Market Cap)
$3 = math($1 / $2)
$4 = llm($3)

例子里前两个搜索互不依赖，可以同时发出。第三步的计算要等前两步都回来。第四步再让模型根据计算结果组织答案。下面的图把 ReAct 和 LLMCompiler 处理另一道题的过程放在一起比较。

{{fig 51 | 问题是：Scott Derrickson 和 Ed Wood 是同一个国家的人吗？左边是 ReAct：搜索第一个人，把结果接到 prompt 后面，再搜索第二个人，再接上，最后回答，三次模型调用依次进行。右边是 LLMCompiler：两个搜索同时发出，然后一次模型调用给出回答。在这道题所属的 HotpotQA 基准测试上，LLMCompiler 的平均延迟约为 ReAct 的 56%（加速比 1.80）。图片来源：Kim 等，2023。}}

重新计划是怎么做的

有些问题的执行流程在一开始定不下来。LLMCompiler 的做法是：Executor 把中间结果送回 Planner，Planner 根据这些结果生成一批新的任务，再交下去执行，如此循环，直到得到最终结果。论文用的例子是 24 点游戏：先并行地提出一批候选的算式并打分，留下分数最高的几个。如果没有一个能凑出 24，就把留下的这几个候选交回 Planner，由它在这些候选的基础上再计划下一批。

所以这里的重新计划是一个反馈循环，用在后面的步骤取决于前面结果的场合。它和 ReWOO 的两点差别，正是论文自己强调的：可以并行调用，可以重新计划。

效果

论文在四个基准测试上比较了准确率和延迟，结果在下面的表里。读表之前先说明三个名字。基线指拿来作比较的现有做法，表里加速比为 1.00 的那一行就是基线：前三个基准测试的基线是 ReAct，24 点游戏的基线是 Tree-of-Thoughts（一种让模型考虑几条不同的推理路线、自己评估之后再决定往哪一条走的做法）。ParallelQA 是这篇论文自己做的基准测试，题目要先搜索几个实体的事实，再拿搜到的数做计算。

  • 主要的收获是快。四个基准测试上的加速比在 1.80 到 3.74 之间，也就是延迟降到基线的 27% 到 56%。花费也降了，电影推荐上的花费约为 ReAct 的 15%，也就是 ReAct 的花费大约是它的 6.7 倍。论文摘要里写的「花费最多节省 6.7 倍」，说的就是这一项。
  • 用 GPT 模型时，准确率大多和基线接近。四个基准测试里有三个和基线相差不到 1.5 个百分点，其中 HotpotQA 上还低 0.47 个百分点。只有电影推荐上高得多，高 4.66 个百分点。
  • 摘要里的「准确率最多提高约 9%」来自一个开源模型。它出自用 LLaMA-2 70B 这个开源模型跑 ParallelQA 的结果：ReAct 的准确率是 59.59%，LLMCompiler 是 68.14%，高 8.55 个百分点。上面的表里没有这一组。
  • ReAct 的两种失败。论文观察到 ReAct 会重复发出已经发过的工具调用，也会在中间结果还不完整时过早地停下。表里前两个基准测试的 ReAct，就是为了减少这两种情况而加了专门的 prompt。
  • 模型厂商同时做了同一件事。表里的「OpenAI 的并行函数调用」是 OpenAI 在 2023 年 11 月 6 日发布的功能：模型在一次回复里发出多个工具调用。论文说它和 LLMCompiler 是同时出现的。它的加速效果已经接近 LLMCompiler。

今天这些想法变成了什么

把上一部分和这一部分合起来，四个想法今天的去向如下。

先计划再执行这个模式，在很大程度上已经被代码生成取代了。让模型直接写出要执行的代码，比让它生成一张专门格式的任务图灵活得多，代码里一样可以表达「先做什么、谁的结果给谁、哪些同时做」。

在代码里，语言模型本身也可以作为一个函数被调用。前面两种计划里已经有这种用法：ReWOO 计划里的 LLM[...] 和 LLMCompiler 计划里的 llm(...)，都是把一次模型调用当作计划里的一步。

计划这件事本身没有过时。agent 在动手之前先定计划仍然很常见。主 agent 把工作分给几个子 agent 时，有时还会用到 workflow：主 agent 让这组子 agent 按一份事先写好的流程去执行。子 agent 是主 agent 派出去单独做一部分工作的另一个 agent，第六部分会讲到。

下一部分讲这一讲的第三组设计决定：每次调用模型时，上下文里放什么。前两组是控制流在谁手里，以及模型怎样推理和行动。
