先看结论

  • Pi 是一个开源的编程 agent 运行框架（harness，包在模型外面、给它工具并管理多轮对话的程序）。它的做法是只留最少的东西：默认 4 个工具，一段很短的 system prompt（每次调用都放在最前面的固定指令），其余的功能交给使用者自己加。
  • 前面几部分的模式在它身上都能找到：循环是 ReAct 式的，上下文靠事件日志（只追加、不修改的记录，每次从它生成模型的输入）、按需加载的 skill（写着某类工作该怎么做的说明文件）和 compaction（压缩，把旧的历史换成一段摘要）来管理。
  • 它没有内置子 agent（主 agent 派出去单独做一部分工作的另一个 agent）、计划模式、待办清单、后台命令，也不在执行命令前征求同意。每一项都是有意的取舍，作者给出了理由和替代做法。
  • 没有权限检查是它最需要小心的地方。官方文档的建议是把它放进容器或虚拟机里运行。
  • 这么简单的运行框架够用，一个很可能的原因是模型本身已经很强。可以这样理解：模型弱一些的时候，运行框架要多做一些事。

Pi 是什么

Pi 是 Mario Zechner 写的一个命令行编程 agent，代码开源。这里的 agent，指能自己决定下一步调用什么工具、分很多步去完成任务的语言模型系统。Pi 官网对自己的介绍是两句话：

Pi 是一个极简的 agent 运行框架。让 Pi 来适应你的工作方式，不要反过来。

作者在 2025 年 11 月的文章里解释了为什么要自己写一个。他原先主要用 Claude Code（Anthropic 的编程 agent），后来觉得它的功能越加越多，其中大部分他用不上；它的 system prompt 和工具每个版本都在变，会改变模型的行为；运行框架在背后往上下文里加的东西，在界面上也看不到。他的原则是：自己用不到的功能就不做。

Pi 可以接十几家模型服务商的模型，有四种用法：在终端里交互，在脚本里跑一次并输出结果，通过标准输入输出被别的程序控制，以及当作 TypeScript 库嵌进别的应用。因为核心很小、容易扩展，很多开源的 agent 是在它上面搭起来的，官网举的例子是 OpenClaw（一个开源的个人 AI 助手）。

+
出处。Pi 官网和文档；代码仓库 earendil-works/pi（原来的地址 badlogic/pi-mono 会跳转到这里），按 GitHub 页面的数字，2026 年 11 月有 12 万多个 star；Mario Zechner 的文章 What I learned building an opinionated and minimal coding agent（2025 年 11 月 30 日）。这一页说到「现在的文档」时，指的是 2026 年 11 月读到的版本。

它故意没有做的东西

别的主流编程 agent 内置的几样功能，Pi 都没有内置。下面的表列出作者在 2025 年 11 月的文章里给的理由，以及他建议的替代做法。

这些功能没有内置，但都可以加回来。Pi 的扩展（extension）是加载进 Pi 进程的 TypeScript 模块，可以注册工具和命令，可以拦截或修改工具调用，可以在每次调用模型前改写上下文，也可以替换 compaction 的做法。官方仓库里就有子 agent、计划模式、权限确认、沙箱（把程序隔离起来运行的环境）这几种扩展的示例。使用者写了大量的扩展，把别的运行框架有的功能一样一样补了上去。

i
「没有什么」的清单是会变的。2025 年 11 月的那篇文章里，作者写的是 Pi 不支持、以后也不会支持 MCP。MCP（Model Context Protocol）是一种把外部工具接给模型的标准接口。他的理由是，常见的 MCP 服务器在每次会话里都把全部工具说明放进上下文。他举了两个 MCP 服务器当例子，它们的工具说明分别占 13,700 和 18,000 个 token（模型处理文字的最小单位，大致是一个词或半个词）。那时 Pi 也还没有 compaction。现在的文档里，这两样都是内置的。MCP 服务器的工具默认不直接声明给模型，也就是不把它们的名字和用法写进发给模型的请求，要用的时候再查找或者在脚本里调用。compaction 默认开启。所以读这类清单时要看日期。出处：Zechner 的文章；Pi 文档的 MCP 一页。

工具：默认只开四个

Pi 一共内置 8 个工具，默认只打开 read、bash、edit、write 四个。

这 8 个之外，Pi 的内置扩展还带两个工具：codemode 和 tool_search，默认也是关闭的。codemode 在下一节会提到，tool_search 用来查找没有直接声明给模型的工具。

工具少，有两个好处。一是每次调用模型时，工具说明占的 token 少。作者在 2025 年 11 月的文章里说，当时 Pi 的 system prompt 加上工具定义，合起来不到 1,000 个 token。二是模型不容易选错工具。

四个工具够用，是因为能在终端里运行的命令，模型都可以通过 bash 这一个工具来运行，搜索文件、列目录、跑测试、上网下载都是这样。grep、find、ls 三个工具能做的事，bash 本来就能做。它们单独存在，是为了让人可以只开只读的工具，把 bash 关掉：

pi --tools read,grep,find,ls

这样启动的 Pi 只能看，不能改文件，也不能运行任意命令。

循环：ReAct 式，历史存成一棵树

Pi 的主循环是 ReAct 式的。ReAct 是第四部分讲的模式：模型每一步先写出想法，再发出动作，看到结果后再想下一步。

按 Pi 文档的描述，一轮（turn）分三步。Pi 先把 system prompt、当前的对话历史、可用的工具和模型设置拼成一次请求。模型返回一段回复，里面可以有文字和工具调用。Pi 再执行每一个工具调用，把结果记下来。如果工具结果需要模型接着处理，就开始下一轮，否则这次运行结束。

动作的形式是 JSON 格式的工具调用。不过 bash 工具的参数可以是一整段脚本，所以一次工具调用也可以做第五部分里 CodeAct 那样的事：在一段代码里循环、判断、把几条命令串起来。Pi 的内置扩展里有一个默认关闭的 codemode 工具，让模型写一段 JavaScript 去调用其他工具，只有脚本的输出会回到模型那里。

做到一半想换一种做法重新试，又想把原来的尝试留着，Pi 的办法是把一次会话存成一棵树：从中间某一条记录可以分出新的分支，原来的分支仍然保留。

{{fig 80 | 每个圆点是会话里的一条记录，箭头从上一条指向下一条。从中间某一条可以分出新的分支，原来的分支仍然保留。}}

会话文件是 JSONL 格式（每行一个 JSON 对象），每条记录有自己的 id 和上一条记录的 parentId，靠这两个字段连成一棵树。从根到当前这条记录的路径叫当前分支，发给模型的历史只来自当前分支。下表是在这棵树上换分支的三个命令。

用 /tree 离开一个分支时，Pi 可以让模型给被离开的那一段写一份摘要，附在新分支上。这样在旧分支上试过什么、得到了什么结论，新分支上的模型是知道的，但不用带上旧分支的全部消息。

上下文管理：三种模式一起用

Pi 用到了第六部分的三样：事件日志，渐进式披露（上下文隔离的一种做法），compaction。

一、从事件日志生成模型的输入

会话文件只追加，不修改。消息、工具调用和结果、切换模型、compaction，都是往文件末尾加一条记录。每次调用模型之前，Pi 沿着当前分支走一遍，把这些记录转换成模型能接受的用户消息、助手消息和工具结果消息。

连「改历史」也是用追加来实现的。有一种记录叫 context_edit，它指向之前的某一条记录，说明以后发给模型时把那一条省掉，或者换成另一段内容。原来那条记录仍然留在文件里，界面、导出和费用统计看到的都是原样。

二、用 skill 做渐进式披露

skill 是一个目录，里面有一个 SKILL.md 文件，写着某一类工作该怎么做，旁边可以带脚本和参考资料。启动时，Pi 只把每个 skill 的名字、一句描述和所在路径放进 system prompt。任务用得上某个 skill 时，模型自己用 read 工具去读它的 SKILL.md，再照着做。

这样做，详细的说明在用到之前不占上下文。

Pi 官网还提到另一个好处：system prompt 没有变，prompt 缓存就不会失效。prompt 缓存是模型服务商的一项功能：下一次请求的开头和上一次完全相同时，这部分的计算结果可以直接复用，更快也更便宜。开头一有改动，从改动的地方往后都要重算。system prompt 排在请求的最前面，所以它一变，整个缓存都用不上了。缓存的事见第六部分。

三、compaction

上下文快满时，Pi 把较早的历史交给模型写成一份摘要，最近的消息原样保留。触发的条件是下面这个式子，其中 contextTokens 是当前上下文的 token 数，contextWindow 是模型的上下文窗口（模型一次调用能接受的输入加输出的总长度）。

contextTokens > contextWindow - reserveTokens

reserveTokens 是一个设置项，默认是 16,384 个 token。它只决定 compaction 什么时候开始：当前上下文离窗口的上限不到这么多 token 时就触发。举例来说，上下文窗口是 200,000 个 token 的模型，当前上下文超过 183,616 个 token 时就会触发。

{{fig 81 | 下面的深色框是 compaction 之后模型看到的内容，从左到右是：system prompt，来自 compaction 记录的摘要，然后是从 firstKeptEntryId 开始原样保留的消息。usr 是用户消息，ass 是模型的回复，tool 是工具结果。}}

有三个细节值得看。

  • 切分点不能落在工具结果上。一条工具结果必须和发起它的那次工具调用待在一起，所以切分点只能是用户消息、模型的回复这几类记录。通常切在用户消息的边界上。
  • 摘要按固定的栏目写。先是目标、约束和偏好，然后是进度（已完成、进行中、受阻）、关键决定、下一步和关键的上下文，最后附上读过的文件和改过的文件的列表。这些栏目正是第六部分说的「保持连续」要留住的东西。
  • 原来的记录没有被删。被总结掉的消息仍然在会话文件里，只是以后不再发给模型。这是事件日志和 compaction 配合的结果。

skill 的清单在 system prompt 里，而 system prompt 在 compaction 之后仍然排在最前面。所以压缩之后，模型仍然知道有哪些 skill 可以用。

安全：执行工具之前不征求同意

Pi 以启动它的那个账户的权限运行，执行工具之前不征求同意。工具调用能做什么，只受这个账户的权限限制。

有的运行框架会在执行危险命令之前要求确认，或者让人在两种模式之间切换：手动模式下每次工具调用都要人同意，自动模式下不用人同意就直接执行。Pi 没有这些，可以把它看成永远开着自动模式。

它的文档写得很直接。模型生成的命令和代码要当作不可信的。Pi 能读、能改、能执行的范围，就是启动它的账户能做的范围。文件、注释、命令输出里的文字都可能通过提示注入（prompt injection，把指令藏在模型会读到的内容里）影响模型。

Pi 内置的保护只有一项，叫项目信任（project trust）。它管的是进入一个目录时，要不要加载这个目录自带的设置、扩展和 skill。有了它，一个陌生的目录不能在使用者同意之前让 Pi 加载它带的可执行扩展。它不限制工具调用能访问什么。

工具调用能访问什么，取决于 Pi 在什么环境里运行。文档列了三种运行方式，各自保护的东西不同。

作者的看法是，别的编程 agent 的安全措施多数只是做样子，所以干脆不做。这个看法不能照搬到所有场合，不加保护的风险有多大，要看用在什么地方。在自己的开发机上改一个代码仓库，和接上生产环境的凭证去操作，风险差得很远。风险高的场合，按上表选保护范围最大的那一种：把 Pi 整个放进容器、虚拟机或沙箱里。

安全是 Pi 明显弱的一项，用它之前要先想好让它在哪种环境里运行。

这么简单，为什么够用

一个没有子 agent、没有计划模式、执行工具之前也不征求同意的运行框架，够不够用？作者自己做过一次测试。他拿 Pi 配 Claude Opus 4.5 跑了 Terminal-Bench 2.0（一个考 agent 在终端里完成任务的基准测试），每个任务跑 5 次，再把结果和文章里贴出的排行榜放在一起比。这张排行榜是 2025 年 12 月 2 日的。

读这个名次要注意：榜上各个条目用的模型不同，也没有别的运行框架配 Claude Opus 4.5 的成绩，所以从它分不出有多少来自运行框架、有多少来自模型。它能说明的是，一个这么小的运行框架配上很强的模型，成绩可以排在前面。

对于这么少的东西为什么够用，作者的解释是：前沿模型在训练时已经大量练习过当编程 agent，它们本来就知道编程 agent 该怎么干活，也熟悉 read、write、edit、bash 这几种工具的用法，所以不需要很长的 system prompt 去教。他在文章里的原话是「看起来不需要 10,000 个 token 的 system prompt」。这是一种解释，上面的测试验证不了它。

反过来，想省钱时能不能用一个便宜些、弱一些的模型，再配一个更好的运行框架？可以这样搭配。按上面的解释推下去，最好的模型只需要很简单的运行框架，弱一些的模型需要运行框架多做一些事，比如更细的工具说明、更多的检查和分步。这是推断，没有数据。两种搭配哪个更合算，要在自己的任务上测：用同一批任务，比较两种搭配的成功率和花费。

i
这和前面讲 workflow（控制流写在程序里的系统）时的建议是一致的。第一部分引过 Anthropic 的建议：先用能解决问题的最简单的做法，确实需要时再加复杂度。Pi 是把这条建议用到了运行框架本身：先做一个很小的核心，需要的功能再用扩展加上去。

Pi 的小结，和整讲的小结

这一讲的三组设计决定是：控制流在谁手里，模型怎样推理和行动，每次调用模型时上下文里放什么。下表把它们放到 Pi 身上。第二组分成「怎样推理」和「动作的形式」两行，最后另加安全这一项，所以一共五行。

整讲可以归纳成五条。

  • 搭 agent 系统要做很多设计决定。设计模式给的是现成的思路，但它给的只是大致的解法，用的时候要按自己的情况补完。
  • workflow 的控制流写在程序里，好预测、好调试；agent 的控制流交给模型，更灵活。workflow 有五种常见的模式，真实的系统是它们的组合。
  • agent 怎样推理和行动，有四个留下来的想法：行动之前先推理，从失败里反思，用代码当动作，先计划再执行。第一个仍然是大多数 agent 的主循环，第二个大多并进了模型自己的推理，这是一个判断，没有实验数据验证。后两个变成了代码生成和并行的工具调用。
  • 上下文管理有五种模式：事件日志、把信息存到记忆里、compaction、屏蔽旧的观察结果、上下文隔离。它们可以一起用，背后是两条原则：让上下文只装当前需要的东西，以及改动上下文时保持连续。
  • Pi 展示了这些模式在一个真实的运行框架里是怎样取舍的。它的做法背后有一个判断：模型越强，包在外面的东西可以越少。
