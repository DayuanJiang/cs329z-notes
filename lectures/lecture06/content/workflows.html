先看结论

  • workflow 是控制流写在程序里的系统：有若干次语言模型调用，先后顺序和分支由代码决定。常见的搭法有五种，这套分类来自 Anthropic 的《Building Effective Agents》。
  • 五种模式是：prompt chaining（把任务拆成一串步骤），routing（先分类再分流），parallelization（同时做几件事再汇总），orchestrator-workers（由模型临时拆出子任务再分派），evaluator-optimizer（一个生成，一个评审，循环改进）。
  • 区分它们可以问四个问题：有没有分成几路，分出的几路是不是都执行，几路的数量和内容是不是事先定的，有没有循环。
  • 每一种都是拿更多的模型调用去换更好的结果，所以要先确认这笔交换划算。

五种模式一览

下面的表先把五种模式放在一起。prompt 指发给模型的输入文字，LLM 是大语言模型的英文缩写，下面的图里每一个绿色方框是一次 LLM 调用。

这篇文章里，五种模式的共同基础是一个「加强过的 LLM」：给模型配上检索、工具和记忆。下面每一种模式里的一次 LLM 调用，都可以是这样一个配了工具的模型。

prompt chaining：把任务拆成一串步骤

prompt chaining 把一个大任务拆成一连串小步骤，每一次 LLM 调用处理上一次的输出。

{{fig 16 | 输入先经过第一次 LLM 调用，得到输出 1。中间的 Gate 是一个检查点：通过就继续第二次、第三次调用，不通过就直接退出。}}

图里的 Gate 是程序做的检查，相当于一个 if、else 分支，用来确认流程还在正轨上。比如第一步的输出为空，或者格式不对，就不必再往下走。

以第一部分处理邮件的例子来说，完全可以只写一个 prompt：「给你这封邮件，把里面的日程都提取出来，各挑一个表情符号，再调用命令加进日历。」拆成几次调用，是因为每一次只做一件事，模型更容易做对。

  • 换来的是准确率，付出的是延迟。两次调用通常比一次慢，调用次数越多越慢。
  • 什么时候值得。任务复杂，而且拆开之后每一步明显更容易。邮件加日历这个例子本身不算复杂，任务越复杂，拆分越有用。

Anthropic 的文章举的两个例子：先写营销文案，再翻译成另一种语言；先写文档的大纲，检查大纲是否符合要求，再照大纲写全文。

routing：先分类，再分流

routing 让一次 LLM 调用先看输入属于哪一类，再把它交给对应的下一步。可以把这次调用想成程序里的一个 switch 语句。

{{fig 17 | 输入先到 LLM Call Router。它从三条路里选一条（实线是被选中的，虚线是没被选中的），由那一条路上的 LLM 调用给出输出。}}

不同的路之间，可以是模型不同（大小不同，或者专门针对某类任务），也可以是模型相同、prompt 不同。有两种常见的用法。

  • 按类别分开处理。比如先判断一封邮件是在说日程，还是有一件要处理的事项，再交给各自的后续流程。文章里的例子是把客服问题分成一般咨询、退款、技术支持，各自走不同的流程、prompt 和工具。这样每一路的 prompt 可以写得更专门；如果所有输入共用一个 prompt，为某一类输入做的优化可能会让另一类变差。
  • 省钱和省时间。设想一个解数学题的 workflow，第一步先判断题目的难度。简单的题交给一个很小的模型，前沿水平的难题才交给最强的模型。

这个模式有一个前提：分类本身要能做准。负责分类的可以是 LLM，也可以是传统的分类模型或规则。

parallelization：同时做，再汇总

parallelization 让几次 LLM 调用同时进行，再由一个汇总步骤把结果合起来。它和 routing 的图很像，差别在于由谁决定分路：routing 是那次分类调用选一条路走；parallelization 是程序规定每次都分成这几路，全部执行。

{{fig 18 | 输入同时交给三次 LLM 调用，三个结果都进入 Aggregator（汇总），再输出。}}

sectioning 还有一个好处：每次调用只看一个方面，注意力更集中。例如要让语言模型当评审，按一份有 10 条标准的评分表给一个回答打分。可以把 10 条标准分成 10 次调用同时进行，每次只评一条。这样每一条评得更专注。10 次调用是同时发出的，总的等待时间大致等于其中最慢的一次，不会随着条数成倍增加。

Anthropic 的文章对投票还举了一个例子：用几个不同的 prompt 分别审查同一段代码有没有安全漏洞，任何一个发现问题就标出来。

orchestrator-workers：由模型临时拆任务

orchestrator-workers 里，一个 LLM（orchestrator，编排者）看了输入之后，把任务拆成若干子任务，分派给别的 LLM（worker，执行者），最后把它们的结果合成一个输出。

{{fig 19 | Orchestrator 把任务分给三次 LLM 调用，虚线表示分给几个、分给谁是临时定的。结果交给 Synthesizer（合成）再输出。}}

它和 parallelization 的图几乎一样，关键的差别是：子任务有几个、各是什么，是 orchestrator 看了具体的输入之后才定的，程序里没有事先写好。所以它适合那些很难预料需要哪些子任务、需要多少个的问题。

举一个例子：给一个很难的编程任务，比如「从零做一个 Photoshop」。这需要很多相互独立的部分：界面、取色器等等。orchestrator 可以把它们列出来，每一项交给一个 worker 去做。Anthropic 的文章举的例子也是编程：一次改动要改多少个文件、每个文件怎么改，取决于具体的任务，事先定不下来。

把这个模式里的 worker 换成 agent（由模型自己决定下一步、在循环里调用工具的系统），就是主 agent 加子 agent 的结构，第 8 讲会讲到。

evaluator-optimizer：一个生成，一个评审

evaluator-optimizer 是一个循环：一个 LLM 先生成一个答案，另一个 LLM 评审它。评审通过就输出；不通过，就把反馈交回给生成的那个 LLM 重做，直到通过。

{{fig 20 | 左边的 Generator 生成答案交给右边的 Evaluator。被接受（Accepted）就输出，被拒绝（Rejected）就带着反馈回到 Generator。}}

用这个模式要满足三个条件。

评审的一方不一定是 LLM，也可以是一个外部的检验手段，比如运行测试。评审和生成也可以用不同的模型：让一个大一些的模型当评审，判断小模型做的够不够好，不够就把反馈给它，让它再做一遍。

文章举的例子是文学翻译：译稿里有些细微之处，负责翻译的 LLM 第一遍抓不住，评审的 LLM 能指出来。

怎样分清这五种模式

五张图里有三张都是「一分多，再合一」的形状，容易混。可以用下面四个问题来分。

五种模式交给模型决定的事情各不相同：routing 让模型选走哪一路，orchestrator-workers 让模型决定任务怎么拆，evaluator-optimizer 让模型判断结果是否过关。以 orchestrator-workers 为例，模型决定了任务怎么拆，但整个流程的骨架（拆分、执行、合成）仍然是程序定的，所以它还是 workflow。

i
每一种模式都有代价。五种模式都是用更多的模型调用，去换更好的结果。多出来的每一次调用都要花 token（模型处理文字的最小单位，花费按它计算），所以五种模式的花费都会增加。prompt chaining 和 evaluator-optimizer 的调用是一个接一个的，等待时间也跟着明显变长。parallelization 和 orchestrator-workers 的几次调用同时发出，等待时间增加得少一些。Anthropic 的文章对组合使用这些模式的建议是：只有当增加的复杂度确实能改善结果时才加。

这一部分的小结

  • workflow 比 agent 更容易复现和调试，因为每次运行走的是同一张流程图。
  • 常见的 workflow 模式有五种：prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer。
  • 这五种是基本的零件。真实的 workflow 通常比其中任何一种都大，是几种模式拼在一起的结果。
