先看结论

  • 设计模式是对「这类问题通常怎么解」的总结。软件工程里早就有，搭 agent 系统也有。模式给的只是大致的解法，用的时候要按自己的情况补完。
  • 搭一个基于语言模型的系统，第一个要定的是控制流在谁手里。写在程序里的叫 workflow，交给模型自己决定的叫 agent。
  • workflow 更好预测，也更容易评估、调试和复现。agent 更灵活，能应付事先想不到的情况，代价是更难预测，花费更高，错误会一步步累积。
  • 能用简单的做法解决就不要上复杂的。真实的系统往往两种都用。

设计模式是什么

设计模式在软件工程里早就很常见，做法是把写代码时反复出现的问题和成熟的解法起一个名字，写下来，让别人可以照着用，也方便互相交流。最有名的一本书是 1994 年出版的《Design Patterns: Elements of Reusable Object-Oriented Software》，四位作者是 Erich Gamma、Richard Helm、Ralph Johnson 和 John Vlissides，书里一共讲了 23 种模式。

{{fig 3 | 左边是那本书的封面。右边是其中一种模式「单例」（Singleton）的示意：一个类只允许有一个实例，别的代码都通过 getInstance() 拿到同一个对象。图片来源：refactoring.guru。}}

搭 agent 系统也可以有设计模式。这里的 agent，指能自己决定下一步调用什么工具、分很多步去完成任务的语言模型系统。不过用模式之前要记住一句话，它出自 Martin Fowler（《企业应用架构模式》一书的作者）2003 年的一篇专栏：

模式是半成品：你总得自己把它做完，并且按自己的环境去调整。

所以这一讲介绍的模式是帮助思考的工具。它们能告诉你有哪些现成的做法可以用，但实际做的时候，方案总要按自己的任务去改，也完全可以在它们的基础上做出新的东西。

+
出处。书的出版年份、作者和模式数量见维基百科的 Design Patterns 条目。Fowler 的这句话出自他在 IEEE Software 2003 年 3、4 月号上的专栏《Patterns》，「半成品」对应的原文是 half-baked。他在 2002 年出版的那本书的引言里有一句意思相同、措辞不同的话。

搭 agent 系统要做哪些设计决定

搭一个 agent 系统要做很多设计决定。这一讲把它们归成三组，每一组都有几种现成的模式。

既然每次都要按自己的情况改，那有没有哪些东西是不太会变的？这个领域还很新，很多做法仍在变化。相对稳定的有两样。一是「先推理、再行动、看结果、再推理」这个循环，也就是第四部分的 ReAct，它已经沿用了好几年。二是 MCP（Model Context Protocol，一种把外部工具接给模型的标准接口），它正在成为组织工具的常见方式。

控制流在谁手里：模型、workflow、agent

控制流，就是「下一步执行什么」是怎么决定的。按这个问题，基于语言模型的系统可以排成一条线。

{{fig 9 | 一条线上的三个点。左：模型，它只是一个更大的系统里的一小块。中：workflow，也叫复合 AI 系统（compound AI system），逻辑和编排都写在程序里。右：agent，控制流由模型负责。每个点下面是例子。}}

Anthropic 在《Building Effective Agents》这篇文章里给的定义和这条线是一致的。它把两类系统统称为 agentic system，再按架构分成两种：workflow 是语言模型和工具按预先写好的代码路径来编排的系统；agent 是语言模型自己动态地决定流程和工具用法、自己掌握怎样完成任务的系统。出处：Schluntz 和 Zhang，2024。

可预测和灵活，很难两头都要

控制流放在哪里，决定了系统的两个性质：有多好预测，和有多灵活。

{{fig 10 | 一张手绘的示意图。纵轴是可预测的程度，横轴是自主的程度。workflow 在左上角，agent 在右下角，中间是一条下降的曲线。图上没有刻度，只表示方向。图片来源：LangChain 的文章。}}
  • workflow 更好预测。控制流在程序逻辑里，会发生什么是事先写明的。这也让它更容易评估、更容易优化，出了问题更容易复现和调试。
  • agent 更灵活。控制流在模型的决定里，它可以按看到的情况临时调整。同一个 agent 每次运行走过的步骤都可能不一样，所以更难预测，也更难评估和优化。

图的出处是 LangChain 的 Harrison Chase 在 2025 年 4 月写的一篇文章。原文的说法是：系统越是由模型自己做主，就越不好预测；有时候出于用户信任、监管要求或别的原因，你需要系统是可预测的；应该站在这条曲线的哪个位置，取决于具体的应用。

一个例子：处理邮件

用同一类任务看两种写法。左边是一个 workflow：收到一封邮件，把里面提到的日程提取出来，给每个日程挑一个表情符号，再加到日历里。右边是一个 agent 的结构。

{{fig 11 | 左：workflow 的流程图。从开始到 extract（提取日程），再到 pick_emoji（挑表情符号），再到 add_to_calendar（加进日历），最后结束；extract 之后有一条虚线直接连到结束，表示没有日程时跳过后两步。右：agent 的流程图。model 和 tools 之间来回循环，由 model 决定什么时候走到结束。}}

左图里有几步、按什么顺序、什么情况下跳过，都是写程序的人定的，每次运行走的都是这张图。右图只有一个循环：模型调用工具，拿到观察结果（observation，工具返回的内容），再决定调用哪个工具，直到它自己判断做完了。如果把右图每次运行实际走过的路径画出来，每次都可能是不同的形状。

workflow 和 agent 的对照

最后一行的两个例子发生在同一个场景里，都是处理 IT 支持的工单。差别在于要做到哪一步。只需要在收到工单时自动回一封信，流程是固定的，workflow 就能做。需要真的把问题解决掉，就得先查清问题出在哪里，再动手处理，查的过程事先写不出来，这时才需要 agent。

怎么选

选哪一种，先看任务的步骤能不能事先写出来。Anthropic 的文章给了几条更具体的建议。

这篇文章也写明了代价。agentic system 通常是拿延迟和花费去换更好的任务表现，要想清楚这笔交换什么时候划算。agent 自主运行，花费更高，前面一步的错误还会带到后面去越积越多，所以文章建议先在隔离的环境里充分测试，并配上合适的防护措施。

两种做法可以一起用。真实的系统常常把它们组合起来：一个 workflow 的某一步可以是一个 agent，一个 agent 也可以把一部分工作交给一个固定的 workflow 去做。LangChain 那篇文章的观察是，生产环境里见到的 agentic system，几乎都是 workflow 和 agent 的组合。
