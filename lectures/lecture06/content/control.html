先看结论

  • 设计模式是对「这类问题通常怎么解」的总结。软件工程里早就有，搭基于语言模型的系统也有。模式给的只是大致的解法，用的时候要按自己的情况补完。
  • 搭一个基于语言模型的系统，第一个要定的是控制流在谁手里，也就是下一步做什么由谁来决定。写在程序里的叫 workflow，交给模型自己决定的叫 agent。
  • workflow 更好预测，也更容易评估、调试和复现。agent 更灵活，能应付事先想不到的情况，代价是更难预测，花费更高，错误会一步步累积。
  • 能用简单的做法解决，就不要用复杂的做法。真实的系统往往两种都用。

设计模式是什么

设计模式在软件工程里早就很常见，做法是给写代码时反复出现的问题和成熟的解法起一个名字，写下来，让别人可以照着用，也方便互相交流。

最有名的一本书是 1994 年出版的《Design Patterns: Elements of Reusable Object-Oriented Software》，四位作者是 Erich Gamma、Richard Helm、Ralph Johnson 和 John Vlissides，书里一共讲了 23 种模式。

{{fig 3 | 左边是那本书的封面。右边是其中一种模式「单例」（Singleton）的示意：一个类只允许有一个实例，别的代码都通过 getInstance() 拿到同一个对象。图片来源：refactoring.guru。}}

搭 agent 系统也可以有设计模式。「agent 系统」在这一讲里是基于语言模型的系统的统称：下一步由程序定的 workflow 和下一步由模型定的 agent 都算在内。其中的 agent，指由语言模型自己决定下一步、在循环里调用工具的系统。工具是模型可以调用的外部功能，比如搜索和运行代码。

用模式之前要记住一句话，它出自 Martin Fowler（《企业应用架构模式》一书的作者）2003 年的一篇专栏：

模式是半成品：你总得自己把它做完，并且按自己的环境去调整。

所以这一讲介绍的模式是用来帮助思考的。它们能告诉你有哪些现成的做法可以用，但实际做的时候，方案总要按自己的任务去改，也完全可以在它们的基础上做出新的东西。

那有没有哪些做法已经固定下来，可以直接照着用？这个领域还很新，很多做法仍在变化。相对稳定的有两样。一是「先推理、再行动、看结果、再推理」这个循环，也就是第四部分的 ReAct，它已经沿用了好几年。二是 MCP（Model Context Protocol，一种把外部工具接给模型的标准接口），用它给模型接工具正在成为常见的做法。

+
出处。书的出版年份、作者和模式数量见维基百科的 Design Patterns 条目。Fowler 的这句话出自他在 IEEE Software 2003 年 3、4 月号上的专栏《Patterns》，「半成品」对应的原文是 half-baked。他在 2002 年出版的《企业应用架构模式》的引言里有一句意思相同、措辞不同的话。

搭 agent 系统要做哪些设计决定

搭一个 agent 系统要做很多设计决定。这一讲把它们归成三组，每一组都有几种现成的模式。

控制流在谁手里：模型、workflow、agent

控制流，就是「下一步执行什么」是怎么决定的。按这个问题，可以把模型、workflow 和 agent 排成一条线。图里的「编排」（orchestration），指安排各次模型调用和工具调用谁先谁后、什么情况走哪条分支。

{{fig 9 | 一条线上的三个点。左：模型，它只是一个更大的系统里的一小块。中：workflow，也叫复合 AI 系统（compound AI system），逻辑和编排都写在程序里。右：agent，控制流由模型负责。每个点下面是例子。}}

Anthropic（开发 Claude 系列模型的公司）在《Building Effective Agents》这篇文章里给的定义和这条线是一致的。它把两类系统统称为 agentic system，也就是这一讲说的 agent 系统，再按架构分成两种。workflow 是照事先写好的代码来编排语言模型和工具的系统。agent 是由语言模型自己动态地决定流程和工具用法的系统，任务怎样完成始终由模型来定。出处：Schluntz 和 Zhang，2024。

可预测和灵活很难兼得

控制流放在哪里，决定了系统的两个性质：有多好预测，和有多灵活。下面的图把这两个性质画在一起。图的横轴写的是自主的程度，也就是有多少决定交给模型自己来做：交给模型的决定越多，系统越灵活，也越不好预测。

{{fig 10 | 一张手绘的示意图。纵轴是可预测的程度，横轴是自主的程度。workflow 在左上角，agent 在右下角，中间是一条下降的曲线。图上没有刻度，只表示方向。图片来源：LangChain 的文章，LangChain 是一家做 agent 开发框架的公司。}}
  • workflow 更好预测。控制流在程序逻辑里，会发生什么是事先写明的。这也让它更容易评估、更容易优化，出了问题更容易复现和调试。
  • agent 更灵活。控制流在模型手里，它可以按看到的情况临时调整。同一个 agent 每次运行走过的步骤都可能不一样，所以更难预测，也更难评估和优化。

这张图出自 LangChain 的 Harrison Chase 在 2025 年 4 月写的一篇文章。文章说，系统越是由模型自己做主，就越不好预测。有时候出于用户信任、监管要求或别的原因，需要系统的行为可以预测。该把多少决定交给模型，取决于具体的应用。

一个例子：处理邮件

下面的图把两种结构放在一起看。左边是一个处理邮件的 workflow：收到一封邮件，把里面提到的日程提取出来，给每个日程挑一个表情符号，再加到日历里。提取日程和挑表情符号各是一次模型调用，加到日历这一步是程序调用日历的接口。右边是 agent 的一般结构，它没有针对某一个具体的任务。

{{fig 11 | 左：workflow 的流程图。从开始到 extract（提取日程），再到 pick_emoji（挑表情符号），再到 add_to_calendar（加进日历），最后结束；extract 之后有一条虚线直接连到结束，表示没有日程时跳过后两步。右：agent 的流程图。model 和 tools 之间来回循环，由 model 决定什么时候走到结束。}}

左图里有几步、按什么顺序、什么情况下跳过，都是写程序的人定的，每次运行走的都是这张图。右图只有一个循环：模型调用工具，拿到观察结果（observation，工具返回的内容），再决定调用哪个工具，直到它自己判断做完了。如果把右图每次运行实际走过的路径画出来，每次都可能是不同的形状。

怎么选

选哪一种，先看任务的步骤能不能事先写出来。Anthropic 的文章给了几条更具体的建议。

这篇文章也写明了代价。和不搭 agent 系统的简单做法相比，agent 系统通常更慢、花费更高，换来的是更好的任务表现，要想清楚什么情况下值得这样做。这一条对 workflow 和 agent 都成立。

agent 这一种还有它自己的代价。它自主运行，这意味着花费更高，前面一步的错误还会带到后面去越积越多。所以文章建议先在沙箱里充分测试，并配上合适的防护措施。沙箱（sandbox）指把程序隔离起来运行的环境，它和真实的数据、真实的系统隔开，agent 在里面做错了事也影响不到外面。防护措施（guardrails）指加在模型外面的限制和检查，用来拦住不该执行的动作和不该给出的输出。

两种做法可以一起用。真实的系统常常把它们组合起来：一个 workflow 的某一步可以是一个 agent，一个 agent 也可以把一部分工作交给一个固定的 workflow 去做。LangChain 那篇文章的观察是，生产环境里见到的 agent 系统，几乎都是 workflow 和 agent 的组合。
