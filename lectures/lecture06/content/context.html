先看结论

  • agent（由语言模型自己决定下一步、在循环里调用工具的系统）每次调用模型之前，都要决定这一次的输入里放什么。这件事叫上下文工程（context engineering）。
  • 要做这件事，是因为输入越长，模型用好其中信息的能力越差，花费和延迟也越高。
  • 两条原则：让上下文只装当前任务需要的东西；改动上下文时保持连续，不要丢掉目标、要求、约束和进度。
  • 五种模式：事件日志、把信息存到记忆里、compaction（让模型把旧的历史写成一段摘要）、屏蔽旧的观察结果（观察结果指工具返回的内容）、上下文隔离。它们互相兼容，真实的系统会同时用好几种。
  • 每种模式都有代价。compaction 要多调用一次模型，并且会丢信息。改动旧内容会让缓存失效，缓存指服务商把上一次请求里开头相同的那部分计算结果留下来复用。把任务交给子 agent（主 agent 派出去单独做一部分工作的另一个 agent）要多花 token（模型处理文字的最小单位）。

从写 prompt 到管理上下文

agent 的循环里，模型每一轮看到的输入都要有人拼出来：哪些历史消息、哪些工具的说明、哪些文档。可以把负责这件事的部分叫作上下文管理器。上下文窗口（context window）是模型一次调用能接受的输入加输出的总长度，上下文管理要解决的就是往这个有限的窗口里放什么。

{{fig 57 | 左：prompt 工程。上下文窗口里只有 system prompt（放在最前面的固定指令）和一条用户消息，模型回答一次。右：agent 的上下文工程。左边一栏是可以给模型的东西：文档、工具、记忆文件、详细的指令、领域知识、消息历史。经过筛选，一部分进入上下文窗口。模型发出工具调用，工具的结果又回到消息历史里。图片来源：Anthropic，2025。}}

prompt（发给模型的输入文字）工程是 2022、2023 年前后大家最关心的事：怎样把一段指令写好，让模型按想要的方式回答。

上面的图出自 Anthropic 在 2025 年 9 月发表的文章《Effective context engineering for AI agents》，这一页后面把它叫作 Anthropic 的上下文工程文章。按这篇文章的定义，上下文工程的范围更大：它指一整套办法，用来在每次调用模型时挑出最该放进输入的内容，并随着任务的进行不断更新这些内容，prompt 之外进入上下文的所有信息都算在内。

文章给这张图配的说明点出了两者的差别：写 prompt 是做一次的事，筛选上下文则在每一次决定给模型什么的时候都要做。

为什么不能把所有东西都放进去

上下文窗口越来越大，为什么不把全部历史和资料都放进去？有两个原因：输入越长，模型越难用好其中的信息；输入越长，花费和延迟也越高。先看第一个原因。一个常被引用的实验是 Greg Kamradt 在 2023 年 11 月做的「大海捞针」测试（Needle in a Haystack）。

做法是：用 Paul Graham 的文章拼成一篇很长的文档，在某个位置插入一句不相干的话（「在旧金山最值得做的事，是在晴天坐在 Dolores 公园里吃一个三明治」），再问模型在旧金山最有意思的事是什么，由 GPT-4 判断答得对不对。文档的长度和这句话的位置各换 35 档，每种组合测一次，结果画成下面这张图。

{{fig 58 | 每个格子是一次测试。横轴是输入的总长度，从 1 千到 20 万 token，共 35 档。纵轴是那句被插入的话在文档里的位置，最上面是开头，最下面是结尾，共 35 档。绿色是模型答对了，红色是没答对。被测的是 Claude 2.1。图片来源：Kamradt 的代码仓库。}}

他报告的结果是：这句话在文档最开头或最末尾时，几乎总能被找到；输入越长，找到的比例越低。

在这次测试的两周前，他用 GPT-4 Turbo 做过同样的测试，结果类似：输入超过 7.3 万 token 之后开始变差，这句话落在文档 7% 到 50% 的位置时最容易被漏掉。

!
这张图容易被读成「模型找不到长文档中间的信息」。图里的红格子有一部分另有原因：模型不愿意回答。Anthropic 在 2023 年 12 月重做了这个测试。他们只是在 Claude 回答的开头预先填上一句「这是上下文里最相关的一句话：」，Claude 2.1 在整套测试上的总成绩就从 27% 升到了 98%。他们的解释是，那句话明显是被硬塞进文档的，模型不太愿意只凭这样一句话来回答。出处：Anthropic，2023。

这个测试对现在的模型已经太容易。Chroma 在 2025 年 7 月测了 18 个模型，报告说现在的模型在这种原始的测试上接近满分。

输入越长表现越差，这一点在更难的任务上仍然成立。Chroma 的同一份报告把任务换难一些（要按意思去匹配，文档里有干扰项，或者是很长的对话），所有实验里模型的表现都随输入变长而下降。Anthropic 的上下文工程文章把这个现象叫作 context rot，并说它在所有模型上都会出现，只是下降得快慢不同。按这篇文章的说法，表现是随着输入变长逐渐下降的，没有到某个长度突然变差。出处：Chroma，2025；Anthropic，2025。

第二个原因是花费和延迟。模型的花费按输入和输出的 token 数计算，输入越长，每一次调用越贵，等的时间也越长。

模型在这方面一直在进步。但按上面 Chroma 的报告和 Anthropic 的上下文工程文章，现在的模型在输入变长时表现仍然会下降，所以对最好的模型，把上下文管理好也仍然有帮助。两个原因合起来，要关心的是：让对的内容出现在上下文里，用不上的不放进去。

两条原则

决定上下文里放什么、删什么的时候，有两条原则要同时照顾。下表列出它们的意思和违反之后的结果。表里的观察结果指工具返回的内容。

Anthropic 的上下文工程文章对第一条的说法是：用尽可能少、但每个都有用的 token，让模型最有可能给出想要的结果。

两条原则是互相牵制的。最简单的上下文是把全部历史原样留着，连续性最好，但不聚焦。一旦开始删减，就要小心别把不能丢的东西删掉。

还有一个实际的限制：别让缓存失效

除了两条原则，改动上下文时还要顾及一个实际的限制：缓存。模型处理一段输入时，会为每个 token 算出一些中间结果，叫 KV 缓存（key-value cache）。如果下一次请求的开头部分和上一次完全相同，服务商可以直接复用这部分中间结果，更快也更便宜。这个功能在接口上叫 prompt 缓存。

  • 只有开头完全相同的那一段能复用。复用的条件是从头开始的那一段完全一致。前面任何一处有改动，从改动的地方往后都要重算。OpenAI 和 Anthropic 的文档都是这样写的。
  • 差价很大。按 Anthropic 的价目，读缓存的 token 一般按正常输入价的十分之一收费。
  • agent 的输入远多于输出。Manus（一个通用 agent 产品）的团队说，他们的 agent 输入和输出的 token 数之比平均约为 100 比 1。所以他们把缓存命中率（可以理解成输入的 token 里有多大比例是从缓存里读到的）看作生产环境里最重要的一个指标，并建议让上下文只在末尾追加，不改动前面的内容。

这个限制和第一条原则有冲突：聚焦要求删掉旧内容，缓存要求不动旧内容。删掉旧内容省下了 token，却要重新建立缓存，两边要取舍。后面讲屏蔽旧的观察结果时会看到一个具体的例子。出处：Anthropic 的 prompt 缓存文档；OpenAI 的 prompt 缓存文档；Manus 的文章，2025。

五种模式一览

下表先把五种模式放在一起，列出每种模式做什么、代价是什么，后面各有一节展开。表里的子 agent，指主 agent 派出去单独做一部分工作的另一个 agent。

事件日志：每次从日志重建输入

事件日志的做法是：把发生过的每件事原样记进一份只追加、不修改的日志，每次调用模型之前，从日志重新生成这一次的输入。这样做，之后无论怎样做摘要或删减，变的只是「怎样把日志呈现给模型」，原始的记录都还在。

很多 agent 都用这个模式，这里以 OpenHands 为例。OpenHands 是一个开源的编程 agent 平台，它把这份事件日志叫作事件流（event stream）：按时间顺序记下的所有动作和观察结果，包括 agent 自己的动作和用户的输入。

{{fig 62 | 中间是事件流，黄色是用户的消息，蓝色是 agent 的动作，橙色是环境返回的观察结果，按编号排列。左边的 agent 读事件流，产生新的动作。右边的运行环境在一个 Docker 容器里执行动作（运行 Python、运行 shell 命令、操作浏览器），得到观察结果，写回事件流。图片来源：Wang 等，2024。}}

图里的例子是：用户说「创建一个 1 到 10 的数字列表，并做一个网页在 5000 端口显示它们」。agent 写文件、启动服务、打开浏览器查看，每一个动作和它的结果都作为一条带标签的记录写进事件流，记录里有来源（用户还是 agent）和内容。

到了要调用模型的时候，输入是从事件流重新生成的，分四步：

{{fig 63 | 从事件流到模型输入的四步：取出全部事件；筛出可以转成模型消息的那几类；把同一次模型回复里发出的多个动作合在一起；转换成消息，作为模型的输入。图片来源：OpenHands 的文档。}}

第二步会筛掉一些事件，因为有些事件只是内部的状态记录，不该给模型看。第三步是为了处理并行的工具调用：模型在一次回复里发出的几个动作，要合成一条带多个工具调用的消息。

每次都从事件日志重新生成输入，有三个好处。

  • 发生过的一切都原样保留。日志只追加、不修改，裁剪上下文时日志本身不受影响。agent 做过的每个动作都有完整的记录。
  • 裁剪上下文的规则可以都写在转换这一步里。每次调用的输入都是重新生成的，所以后面几种模式（compaction、屏蔽观察结果）都可以实现成这个转换步骤里的规则。在 OpenHands 里，compaction 是往日志里追加一条特殊的事件，里面列出哪些事件以后不再给模型看，并带上一段摘要。
  • 每写入一条事件，都可以触发别的程序。这些程序可以监控系统状态，更新界面，或者在某类事件之后自动发起别的操作。
+
OpenHands 的来历。OpenHands 原名 OpenDevin，论文 2024 年 7 月首次发布，后来发表在 ICLR 2025，作者之一是卡内基梅隆大学的 Graham Neubig。它同时也是一家公司的产品。出处：Wang 等，2024。

把信息存到记忆里

把信息写进记忆或文件，上下文里对应的部分就可以放心删掉，因为它在别处有保存。这里只简单介绍，记忆的各种做法第 7 讲会讲到。

{{fig 64 | MemGPT 论文里的两段对话。左：用户提到男朋友 James 给她烤了生日蛋糕，这时系统提示上下文快满了，agent 往工作记忆（prompt 里一块留给 agent 自己改写的文字）里写入两条：生日是 2 月 7 日，男朋友叫 James。右：后来的一次对话里，用户说去了六旗游乐园，agent 搜索以前的消息，找到「James 和我是在六旗认识的」，于是问：是和 James 一起去的吗？图片来源：Packer 等，2023。}}

MemGPT 的思路借自操作系统的虚拟内存。prompt 里的 token 相当于内存，外部的数据库相当于硬盘，模型通过工具调用在两者之间搬数据：往里写，或者搜索后取回。图里左边的工作记忆在内存这一边，是 prompt 的一部分；右边搜索的以前的消息在硬盘这一边。

什么时候往外搬，由系统按 token 数提醒。论文里的例子是，token 数超过窗口的 70% 时，系统插入一条提醒，让模型抓紧把重要的东西存起来；到 100% 时，把一部分旧消息移出去并更新摘要，移出去的消息以后仍然搜得到。

实现的办法有好几种：检索增强生成（RAG，先按问题从外部资料里搜出相关的片段，再放进模型的输入），工具调用，或者直接读写文件。共同点是：关于用户、关于过往经验的事实放在记忆里，不必每时每刻都占着上下文窗口。

compaction：让模型总结旧的历史

compaction 是在上下文太长时，让语言模型把之前的想法、动作、观察结果总结成一段摘要，用更少的 token 代替它们。

{{fig 65 | 左边一列是不做任何处理的 agent：system prompt、用户的 prompt，然后是三轮，每轮有想法、动作、观察结果。右边一列是做了 compaction 之后：前两轮被一段摘要代替，第三轮原样保留。图片来源：Lindenbauer 等，2025。}}
  • 最简单的做法。把允许的上下文长度设得比模型真正能处理的长度短一些。一旦超过，就把历史交给模型，让它写摘要。
  • 更复杂的做法。让 compaction 本身也成为一个 agent：它可以调用工具、搜索，把真正需要的上下文找齐再写摘要。
  • 取舍。简单的做法比较快；复杂的做法摘要质量可能更好，但人要等它做完才能继续。

Anthropic 的上下文工程文章以 Claude Code（Anthropic 的编程 agent）为例描述了摘要里留什么：保留架构上的决定、没解决的 bug 和实现细节，丢掉重复的工具输出。compaction 之后，agent 带着摘要和最近访问过的 5 个文件继续工作。一个具体的实现见第七部分里 Pi 的做法。

屏蔽旧的观察结果：比 compaction 更简单的办法

JetBrains Research 的 Lindenbauer 等人在 2025 年的论文《The Complexity Trap》里提出：compaction 比实际需要的复杂，有一个更简单的办法效果差不多。出发点是下面这张图。

{{fig 66 | 一个不做任何上下文管理的编程 agent，平均每一轮里三类 token 的占比：观察结果 83.9%，想法 9.6%，动作 6.5%。数据来自论文的预备实验，用的是 SWE-agent（一个开源的编程 agent）配 GPT-4.1-mini，在 50 个任务上测的。图片来源：Lindenbauer 等，2025。}}

编程 agent 的上下文主要是被观察结果撑大的：读一个文件，整个文件进了上下文；跑一条命令，全部输出进了上下文。想法和动作只占一小部分。

屏蔽观察结果的做法是：agent 已经用过旧的观察结果里的信息了，所以可以把它们换成很短的几行，或者直接删掉。论文的实现是保留全部的想法和动作，把 10 轮以前的观察结果换成一句占位的话，比如「之前的 8 行省略」。下面的图把它和不做处理、compaction 放在一起比较。

{{fig 67 | 三列对比。(a) 不做处理。(b) 屏蔽观察结果：第一、二轮的观察结果换成很短的占位符（Mask），想法和动作都留着，最近一轮原样保留。(c) compaction：前面几轮换成语言模型写的一段摘要。图片来源：Lindenbauer 等，2025。}}

屏蔽观察结果的整个过程用程序就能完成，不需要调用模型。它和事件日志配合得很好：观察结果都在日志里，只要在转换步骤里加一条规则就行。

效果：花费和解决率都和 compaction 差不多

论文让 SWE-agent 在 SWE-bench Verified 上比较了三种做法：不做处理、屏蔽观察结果、compaction。SWE-bench Verified 是一套编程题，共 500 道，从 SWE-bench 这个基准测试（benchmark，一组题目加一个打分的办法）里经人工筛选出来，每道题要 agent 修好真实代码仓库里的一个问题。解决率是做对的题占的比例。论文测了五种模型配置，下面的图画了其中三种，表里是五种的全部数字。配置名里的「开启思考」，指让模型在给出回复之前先生成一段推理。

{{fig 68 | 横轴是每个任务的花费（美元），纵轴是解决率。黑色圆点是不做处理，紫色三角是屏蔽观察结果，粉色方块是 compaction。越靠左上越好。图片来源：Lindenbauer 等，2025。}}

读这张表要先知道误差有多大。500 道题只是一个样本，换一批题目再测，结果会上下浮动。95% 置信区间是对这个浮动范围的估计，表里每个解决率的浮动范围大约是正负 4 个百分点。两个数的差别小到落在浮动范围以内时，这个差别可能只是碰巧出现的，下面的「在误差范围以内」和「在统计上不显著」都是这个意思。

  • 五种配置里有四种，两种办法都把花费减了大约一半。这四种配置下，花费比不做处理低 41% 到 57%。例如 Qwen3-32B 不开思考时，屏蔽观察结果让花费降了 51%，compaction 降了 55%。
  • 有一种配置花费几乎没降。Qwen3-32B 开启思考时，屏蔽观察结果只让花费降了约 10%，compaction 降了 0%，这两个变化在统计上都不显著。
  • 两种办法之间，解决率分不出高下。差距大多在误差范围以内。屏蔽观察结果更简单，也没有等模型写摘要的那段延迟。
  • 有一种配置的解决率明显下降。Gemini 2.5 Flash 开启思考的那一组，两种办法的解决率都明显低于不做处理：屏蔽观察结果是 36.4%，compaction 是 31.4%，不做处理是 40.4%。Qwen3-32B 的两种配置下，解决率和不做处理的差别都在误差范围以内。
  • compaction 有两处额外的开销。写摘要的调用最多占到一个任务总花费的 7.2%。另外，用 compaction 时 agent 会跑更多轮：用 Gemini 2.5 Flash 时，compaction 平均跑 52 轮，屏蔽观察结果是 44 轮。论文的推测是摘要掩盖了本该让 agent 早点停下的失败信号。

用屏蔽观察结果时要注意的两件事

屏蔽观察结果和缓存是冲突的。每屏蔽一次旧的观察结果，前面的内容就变了，从那里往后的缓存都要重建。实际做的时候可以隔几轮集中清理一次，比如每 5 轮或每 10 轮。

屏蔽观察结果也挡不住上下文一直变长。想法和动作仍然在累积，任务足够长时还是会碰到窗口的上限，那时仍然要做 compaction。所以两种办法常常叠起来用。论文试过一种混合的做法，在一个模型、50 个任务上，花费比单用屏蔽观察结果低 7%，比单用 compaction 低 11%。

这个结论只在编程任务上测过。这是一篇 NeurIPS 2025 研讨会论文，作者自己说，编程任务的工具输出又长又多，天然有利于屏蔽观察结果。

上下文隔离：子 agent 和渐进式披露

上下文隔离的意思是：把内容分开放，一部分工作放到另一个上下文窗口里做，暂时用不到的说明等到需要时再放进上下文。有两种做法：把一部分工作交给子 agent，和渐进式披露。

子 agent

有些任务要大量地搜索、读很多文档，会把上下文撑得很满。可以让主 agent 派一个子 agent 去做。子 agent 是另一个 agent，它在自己的上下文窗口里装满完成这件事所需的信息，做完之后只向主 agent 交回一段简短的总结。

{{fig 69 | 上面的 Plan 是负责计划的主 agent，它把工作分给 Agent 1 和 Agent 2。每个虚线框是一个独立的上下文窗口。图片来源：LangChain 的文章。}}

Anthropic 的上下文工程文章给过一个量级：一个子 agent 可能用掉几万个 token 去探索，交回来的浓缩总结通常是 1,000 到 2,000 个 token。

代价是总的 token 花费更高。Anthropic 在介绍自己的多 agent 研究系统时说，多 agent 系统用掉的 token 大约是普通聊天的 15 倍。多 agent 的设计，第 8 讲会讲到。

渐进式披露

另一种做法是渐进式披露（progressive disclosure）：不必一开始就把所有工具和说明都放进 prompt，需要的时候再给模型看。

现在常见的实现是 skill。一个 skill 是一段写给模型的说明，讲的是「遇到这种情况该怎么做」。它存成一个目录，里面有一个 SKILL.md 文件，旁边可以带脚本和参考资料。下面的图是一个 skill 的例子，图后面的表说明它的内容分三层进入上下文。

{{fig 70 | 一个处理 PDF 的 skill 的 SKILL.md 文件。上半部分是开头的元数据：名字和一句描述。下半部分是正文：概述、快速上手的代码，并提到更详细的内容在 reference.md 和 forms.md 两个文件里。图片来源：Anthropic，2025。}}

skill 里还可以带脚本。图里的 PDF skill 带了一个提取表单字段的 Python 脚本，模型可以直接运行它，脚本本身和 PDF 的内容都不必进入上下文。

skill 和工具的区别在于被调用时发生什么。工具被调用时会对环境做动作。skill 被调用时不做动作，效果是把那段「遇到这种情况该怎么做」的说明加进上下文，之后 agent 仍然要自己去调用工具把事情做完。

skill 的清单（名字和描述，或者去哪里找它们）是 system prompt 的一部分，所以在 compaction 之后仍然在。

五种模式互相兼容。可以先把知识存进记忆，再做 compaction。可以用事件日志来生成上下文，同时截短观察结果。真实的系统是其中多种甚至全部的组合。下表列出四种组合，以及每种组合为什么可以一起用。
