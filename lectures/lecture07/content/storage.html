先看结论

  • 设计一个记忆系统，要回答三个问题：存什么、取什么；什么时候触发存和取；用什么办法存和取。各个系统的差别，都可以归结为这三个问题的答案不同。
  • 触发存取的方式常见的有三种：agent（能自己调用工具、分很多步去完成任务的语言模型系统）按需调用工具，后台的流程自动处理，由某个事件触发。
  • 存放的办法常见的有三种：文件系统、数据库、知识图谱。文件系统最简单，查找时靠模型自己一步步翻，所以慢。数据库查得快。知识图谱能表达事物之间的关系和随时间的变化，建起来最费事。
  • 一个实用的建议是：能用文件系统就先用文件系统。对查找速度有要求时，再考虑另外两种。
  • 后面三部分讲四种架构模式：从经验里学做法，分层的记忆，反思式整理，记忆维护。

三个问题：存什么，何时，怎么存

读后面任何一个记忆系统时，都可以拿这三个问题去问它。第五部分最后的对照表就是按这三个问题把四种模式排在一起的。

什么时候存取：三种触发方式

三种方式可以同时用。MemGPT 就是表里第一种和第三种的结合：平时由模型自己决定存什么、查什么，上下文窗口快满时由事件提醒它。

选哪种方式，背后是一个取舍。让 agent 自己决定最灵活，但它可能忘了去存，也可能忘了去查，第一部分开头的 Luna 就是存了却没有去查的例子。交给后台的流程更可靠，代价是多一套要设计和运行的东西。

怎么存取：三种存放的办法

不管记忆是哪一种，底层都需要一个办法把信息写到磁盘上，以后再读出来。最常见的三种办法是文件系统、数据库和知识图谱。下面三节各讲一种，之后一节放在一起比较。

文件系统：每条记忆是一个文件

最直接的办法是把每条记忆存成一个文件，让 agent 自己管理这些文件。这样做有三个特点。

  • 天然有层级。文件放在文件夹里，文件夹可以再套文件夹。agent 可以先看一个文件夹里有什么，再进到子文件夹里看。
  • 不需要专门的记忆工具。列目录的 ls、搜索文字的 grep 这些命令行工具，就是读记忆的工具。写记忆就是写文件。
  • 模型本来就会用。现在的模型很擅长操作文件系统，不用额外教。
{{fig 26 | 三种长期记忆各对应一组文件。程序性记忆是 AGENTS.md 和 mcp.json。语义记忆是几个文件夹，里面有 SKILL.md 和知识文件。情景记忆是 conversations 文件夹里按日期存的对话记录。图片来源：LangChain 的博客。}}

图里的三种长期记忆是第一部分讲过的：程序性记忆（procedural memory）存做法，语义记忆（semantic memory）存知识，情景记忆（episodic memory）存经历。AGENTS.md 是放在项目里、给 agent 看的说明文件，写着这个项目的规矩和常用做法。mcp.json 列出 agent 可以连接的外部工具。

一个真实产品的做法和教训

这张图出自 LangChain 2026 年 2 月的一篇博客，讲的是他们的产品 LangSmith Agent Builder 怎样做记忆。这个产品让不写代码的人搭建 agent，这类 agent 通常反复做同一种任务，所以这一次学到的东西下一次很可能用得上。博客里有几处细节值得知道。

最后一条教训和第五部分的记忆维护是同一个问题：只往里加、不整理，记忆会越来越乱。博客说他们计划加一个后台进程，大约每天运行一次，回顾所有对话并更新记忆。

图和产品有两处对不上。图是一张概念图。按博客正文，这个产品目前没有情景记忆，图里 conversations 那一行是计划中的做法：把以前的对话作为文件放进文件系统。另外，产品用的是自己定义的 tools.json，没有用图里写的 mcp.json，原因是他们想让用户只把一个外部工具集里的一部分工具交给 agent，免得工具说明把上下文窗口占满。博客还把技能文件归为语义记忆，这一讲把它归为程序性记忆，见第一部分的说明。

数据库：把记忆存成可以检索的记录

第二种办法是把记忆存进数据库，用检索的办法取。第 3 讲讲过检索增强生成（RAG，先检索相关的资料，再让模型根据资料作答），那里介绍的技术在这里都用得上。按怎么查，可以分成三种。

三种查法经常混着用，也可以对不同的内容用不同的查法。第四部分的 MemGPT 就是这样：上传的文档转成向量来搜，对话的原文则保留全文，按字符串和日期来查。哪些内容该转成向量、哪些该保留全文做精确查找，没有统一的答案，要看具体的应用。

知识图谱：把记忆存成实体和关系

第三种办法最不直观。知识图谱（knowledge graph）把信息存成一张图：节点是实体，比如人、公司、产品；边是实体之间的关系，比如「任职于」「喜欢」。这里用 Zep 来说明。Zep 是一个面向 agent 的商业记忆服务，它的论文在 2025 年 1 月上传，核心是一个叫 Graphiti 的知识图谱引擎。

{{fig 28 | 左：Zep 官网上的示意图。节点是人、公司、话题、产品，边上写着关系，其中一条是「任职于，到 2026 年 3 月为止」。右：一篇教程里画的 Zep 的三层结构，从上到下是原始数据、实体和关系、实体的聚类和摘要。图片来源：getzep.com 和 Daily Dose of Data Science。}}

三层结构

举一个例子。用户在一次对话里聊到自己的狗，还提到表弟很喜欢这条狗。系统读了这段对话，会建两个实体，「表弟」和「狗」，再在两者之间连一条边「喜欢」。对话越积越多，这张图会变得很大。这时第三层就有用了：先在各个社区的摘要里找到相关的那一群实体，再进去看细节。

按 Zep 论文自己的说法，原始片段这一层对应情景记忆，实体和关系这一层对应语义记忆。知识图谱主要用来存语义记忆。做法这类程序性记忆也可以硬写成「先做这一步、再做那一步」的图，但很少有人这样做。

事实会过期

Zep 的一个特点是每条事实都带时间。一条边上记着这件事从什么时候开始成立、到什么时候不再成立。新的信息进来时，语言模型把它和图里相关的旧事实对比，如果发现矛盾，旧的那条边会被标上失效的时间，但不会被删掉。图里那条「任职于，到 2026 年 3 月为止」的边就是这个意思：这个人曾经在这家公司工作，现在不在了，两件事图里都记着。

这个设计针对的是第一部分里饮食偏好那个例子暴露的问题：用户的情况变了，记忆得知道哪一条是现在的、哪一条是过去的。

查的时候有什么不同

图谱比前两种办法多出来的，是可以沿着关系查。Zep 提供三种搜索：向量相似度，BM25 关键词匹配，以及从某个节点出发、沿着边向外一层层找的广度优先搜索。前两种找的是文字上或意思上相近的内容，第三种找的是在图上离得近的内容。搜到的结果再经过一次重新排序，最后把事实连同它成立的时间段一起交给 agent。

换一个角度看，三种办法的差别在于查找时的判断由谁来做。文件系统的办法让模型自己一步步去翻。图谱的办法在存入时先把关系整理好，查找时由检索程序沿着这些关系去找，留给模型做的判断就少一些。

+
Zep 论文里的两组成绩，以及作者自己的保留意见。
  • 深度记忆检索（DMR）。这是 MemGPT 论文提出的测试，考 agent 能不能回答关于以前对话的问题。用 GPT-4 Turbo 时，Zep 的准确率是 94.8%，MemGPT 论文报告的是 93.4%，把完整对话直接放进上下文窗口是 94.4%。三个数很接近。Zep 的作者自己说，这个测试里每组对话只有 60 条消息，放得进现在模型的上下文窗口，不足以用来评价记忆系统。
  • LongMemEval。对话历史平均约 11.5 万 token（模型处理文字的最小单位，大致是一个词或半个词）。用 GPT-4o 时，把全部历史放进上下文窗口的准确率是 60.2%，每次回答约 28.9 秒；用 Zep 只取大约 1,600 个 token 的内容，准确率是 71.2%，每次约 2.58 秒。论文摘要里说的「准确率最多提高 18.5%」是相对比例，换成百分点是 11 个百分点。分类型看，有一类问题的成绩是下降的。
这是产品方自己发表的论文，拿来对比的参照做法（基线，baseline）是把全部历史放进上下文窗口，没有和别的记忆系统在这个测试上比。出处：Rasmussen 等，2025。

三种办法怎么选

每篇论文都会说自己的系统最好，所以很难给出一个通用的排名。一个实用的建议是：能用文件系统的地方，就先用文件系统。这条建议来自实践中的经验，属于一种看法：搭一个最简单的结构、把主导权交给模型，效果往往不错。告诉模型「这是你的文件系统，把它当记忆来用」，很多时候就能工作。要在查找速度上做取舍的时候，才需要另外两种办法。

文件系统的代价是延迟。agent 每查一次记忆，都要运行命令、读结果、推理、再决定下一步，来回好几轮。第六部分的 LongMemEval-V2 基准测试（benchmark，一组题目加一个打分的办法）给出了一组具体的数字。它考的是记忆系统能不能从 agent 过去的大量运行轨迹（trajectory，每一步的动作和看到的结果的完整记录）里找到答案。

准确率最高的做法，查询耗时是最基本的检索的几百倍。这是「文件系统准、数据库快」这个取舍的一个实例，其中有一部分差距来自模型不同。

四种架构模式一览

有了存放的办法，还要决定怎样组织和使用记忆。已有的系统可以归纳成四种模式。

这四种模式是对已有论文的一种归纳，没有公认的标准分法。一个系统也可以同时用到几种模式，比如 Generative Agents 既有反思，也有按时间衰减的检索。把它们分开讲，是为了看清每一种做法各自解决什么问题、带来什么代价。
